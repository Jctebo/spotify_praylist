### 2.2 Build shape — server (app/worker/src/index.ts)

- **Ora Pro Nobis (Q2 A) rides the RSS kind:** one def appended to POD_RSS_SERIES_LIST — `{ key: "ora-pro-nobis", title: "Ora Pro Nobis", feedUrl: (env) => ownFeedUrl(env), window: 500 }` — after daily-readings, so every standing entry's order and shape stay byte-untouched and the own kind (The AI Signal) still closes the Podcasts category (Q4 A: the kind files under Podcasts by construction). Window 500 is the Daily Readings precedent (v549 §2.3): at ~10 episodes a day it carries ~50 days of the show. No migration: rss_snapshots and the listen stores already stand. The own-kind alternative (player_episodes) was rejected: no whole-show rows stand in that store — its rows are per-date segment rows, and the feed is the show's standing catalog (the v427 precedent: the Worker already enumerates this feed for the day's novena ids and the day-set assets).
- **Novenas (Q3 A + the 09:19 CT clarification) — a new kind, "novena", on the same discipline:** a catalog build parses the own feed with the standing podRssParseFeed, keeps the items whose enclosure stem yields a novena episode id under the standing stem rule generalized to any date (novenaEpisodeIdOfStem's canon: stem starts with its date → rest after `<date>-` → the LAST `-day-` at index > 0 → episodeId `novena-` + rest before it; dayN = the digits after that `-day-`), and groups them by episodeId. Per novena: the display name is the feed title minus its trailing ` Day <n> - <Month D, YYYY>`; the saint sort key is the name minus a leading "Traditional Novena to " / "Novena to " / "Novena for " / "Traditional " prefix. The catalog is stored as ONE snapshot row in rss_snapshots under the series key `novenas-catalog` (payload = { builtAt, novenas: [{ slug, name, saint, episodes: [{ key (the stem), guid, title, date, dayN, label, url, durationS }] }] }), read-to-refresh at the same 2 h max age, stale-on-failure, zero-yield = failed build — so the index and every series page build from the one snapshot and can never disagree. No migration.
- **Payloads:** `?series=novenas` → { ok, kind: "novenas", series: "novenas", title: "Novenas", available, novenas: [{ key: "novena-<slug>", slug, name, saint, total, latestDate, latestLabel }] } with the novenas array SORTED BY SAINT server-side (payload order is the paint order; no client sort stands anywhere). `?series=novena-<slug>` → { ok, kind: "novena", series: "novena-<slug>", title: <name>, available, total, entries: [{ key (stem), title, label, date, dayN, url, durationS, imageUrl: null, descText: null }] }, entries ordered date DESC, dayN ASC within a date (newest run first; the standing newest-first page grammar). Both routes seat in BOTH read routes (the session read and the door mirror, composed WITH the kind per the v454/v464 lesson) BEFORE the video def lookup; they carry no listen state, so stripListenState has nothing to strip and both shapes answer identically. Unknown `novena-` keys answer the kind's unavailable surface (available: false), never a 400 — the grouping's own keys are born from the index payload. Novena series keys do NOT join validateProfileLayers' list: the Podcasts layer's picks remain the seriesList series; the novenas stand behind their own grouping, per the clarification's separate-grouping shape.
