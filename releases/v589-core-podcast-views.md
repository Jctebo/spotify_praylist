### 2.3 The core design

- **Store:** a new on-device store, key `opn-podcast-core-v1` (device shape; web shape keeps it in memory only, the standing web discipline — nothing persists). It stands beside the personal-data file, NOT inside it: playback state has always stood outside the carried file, and the v578 vault covers the personal document — that posture is unchanged and named here. Shape:
  `{ format:'opn-podcast-core', version:1, series:{ [seriesKey]: {series,title,kind,category,total,episodeKeys:[…]} }, episodes:{ [series|episodeKey]: {series,key,kind,day,label,title,url,durationS} }, listens:{ [series|episodeKey]: {listenDate,listenedAt,source} }, positions:{ [series|episodeKey]: {positionS,durationS} }, migration:{…} }`
- **Canonical identity (one keying for every kind):** series key = the registry key (`bible-in-a-year`, `exorcist-files`, `the-ai-signal`, `novena-<slug>`, video keys). Episode key = the payload entry's own key, which is already canonical per kind: sequence `prefix:day-N` / `prefix:bonus-<slug>[-<hash8>]` · RSS the feed GUID (enclosure-URL fallback) · own `the-ai-signal-<date>` · novena the catalog stem. The core key is the compound `series|episodeKey` — the same compound the device store already used, now the ONLY key anywhere; no surface derives another.
- **Projection (the one fold):** `opnPodCoreProject(payload)` replaces `opnFoldPlaybackIntoPodcasts` at the single `api()` seat. It (1) INGESTS: every series/episode identity in the payload registers into the core; at ingest, core listens/positions for that series that name no standing episode are DROPPED and counted in `migration.dropped` (the standing discipline, enforced at the moment identity is known). (2) PROJECTS: each entry gains `listened/listenDate/listenedAt/source/positionS` from the core alone; a series payload's `listenedCount` is recomputed as entries ∩ core listens and its `currentKey` re-derived by the standing rule (first unlistened day-kind entry, else first unlistened) for the sequence kind, latest-entry for RSS; an index payload's per-series `listenedCount/currentKey/currentLabel` are recomputed from the core (registry ∩ listens when the registry stands; the series' core listen count before first ingest — the same set the rows will read, so the card and the page cannot disagree once either has been read, and agree exactly after any series read).
- **Writes:** the local emulator's mark/unmark/position routes write the CORE (the legacy playback store keeps only `dayPositions` — day-form state, §2.4). The painters' in-memory recomputes retire: `podToggleMark`/`writePodMarkQuiet` flip the entry for paint, then take `listenedCount/currentKey` from the projection helper over the open payload — one derivation, called, not copied. Queue descriptors and the title card keep reading the projected entry (their standing seats) — they become views by construction, since the payload they copy from is the projection.
- **Server mode is untouched:** the layer never runs there; the server fold serves, as today.

### 2.4 The boundary — server listen rows vs the local core (designed, named)

- On the public host the server state is stripped by design and personal reads answer empty; on the private host the client runs in server mode and the local layer never runs. **No on-device automatic import from the server is therefore possible in either shape** — any design claiming one would be fiction.
- THE CHOICE: the core gains one import seam, `opnPodCoreImportListens(rows)` behind the local route `POST /api/player/podcasts/import-listens` (device shape only), taking `{series, seqKey, listenDate, source}` rows and landing each only where it matches exactly one ingested-or-ingestable episode identity (validated against the series' next payload ingest; unmatched rows are refused and counted, never guessed). The bridge that carries John's server rows to it is the standing data net: **the v570-style import file gains an optional `podcastListens` section** (operator-generated from D1 — the same route his personal-data import file took at v570), restored on-device at Ship. His 322 Bible rows are the first payload through that seam; the harness proves the seam against them (§2.5).
- His personal data and prayer seats stand byte-exact: the import touches only the new core store; the server rows themselves are read, never written, by this release.

### 2.5 The migration

1. **Legacy device store:** at first core load (device shape), `opn-playback-local-v1`'s `listens`/`positions` move verbatim into the core (their compound keys are already canonical) and are struck from the legacy store, which keeps `dayPositions` only; the move is recorded in `migration.fromPlaybackV1 {movedListens, movedPositions}`. Validation is deferred to each series' first ingest (§2.3), where a key naming no standing episode is dropped and counted — never guessed onto another episode.
2. **Server rows (the v588 repair):** through the §2.4 seam. Fixture proof (harness): ingest the production Bible snapshot, import the 322 production rows → core count **322**, current **`biy:day-322`**, Days 1–321 + the bonus listened, Day 322 unlistened; the index projection reads the same 322. A planted row naming no episode is refused and counted.
3. **Idempotent:** re-running either leg moves/imports nothing twice (keys are set membership, not counters).
