### Discovery — the player as it stands (verified first-hand, trunk @ a74833c)

1. **One audio element serves everything.** `ui.ts` line 29 stands a single `<audio id="audio" preload="none">` in the shell, outside every tab's render; `client.ts` line 8 binds it as `audioEl`. Every sound the app makes passes through `startDesc(desc)` (client.ts:82–90), which sets `audioEl.src` and plays. There are no other elements and no second playback path. Consequence: `audioEl.playbackRate` is a property of the one element — a speed setting applies to whatever plays, with no per-family plumbing.
2. **All three families named in this item play through that same path.** Own episodes: descriptors built by `trackDesc()` from the `/api/player/day` payload, played by card button (`playTrack`) or queued (`startQueue` / per-block queue buttons / Play All). External streams (v324): payload tracks with `kind: 'external'` and a `streamUrl` become descriptors through the same `trackDesc()` and the same queue — the client does not distinguish them at playback time. Intentions segments: on the Prayers screen they are `seg:` descriptors in the same payload and queue; on the Intentions tab the chip bar calls the legacy `play(url)` (client.ts:96–100), which wraps the bare URL into a one-off descriptor (`episodeId: 'url:…'`, title "Intentions") and calls the same `playTrack`. v334's client-resolved slots, when it lands, will feed the same descriptor path at open — nothing in its Plan touches the element or the transport.
3. **Nothing sets playbackRate today.** The only occurrence in the client is a read: `updatePositionState()` (client.ts:76) already passes `audioEl.playbackRate` into the Media Session position state — so the lock screen / Android Auto position reporting stays truthful the moment a rate is set, with no new plumbing. No speed control exists anywhere.
4. **The v326 dock, exactly as shipped.** A shell-level element in SHELL_HTML (ui.ts:30): logo thumb, title (`#dock-title`), meta line (`#dock-meta` — the track's block, else the date label), a play/pause button (`#dock-play`), a next button (`#dock-next`, disabled when no queue stands), and a 3px display-only progress line along its bottom edge. Visibility is derived, no flag: the dock stands exactly while `state.current` is set (client.ts:197–214, `updateDock()` is the only sync path). Its buttons drive the standing paths — play/pause calls `playTrack(state.current)`, next calls `advanceQueue(1)`. A tap anywhere else on the dock calls `dockJump()` (see the deviation callout). The dock's own design record (client.ts:164–186) states the progress line is display-only by decision: "seek stays on the lock screen."
5. **There is no in-app seek surface anywhere — re-verified.** No element in the client displays a scrubbable position or accepts a seek input. Seeking exists only in the Media Session handlers (client.ts:392–404: `seekto`, `seekforward`, `seekbackward` — lock screen / car), in the resume mechanism (`loadResume` sets `currentTime` on `loadedmetadata`), and nowhere else. The element's `duration` / `currentTime` are continuously available; the standing `timeupdate` listener already drives the dock progress line, the sleep tick, the position state, and the throttled resume save.
6. **Previous/next already exist as paths.** `advanceQueue(-1)` and `advanceQueue(1)` carry the standing skip rule (an unavailable track is passed over and named on its card); both are already exercised by the Media Session `previoustrack` / `nexttrack` handlers. The dock exposes next only; a full-screen surface can expose both without new transport logic.
7. **The sleep timer (v320) is a shell-scope state with one arm surface.** `state.sleep` is exactly one of off / minutes-with-deadline / end-of-track; `armSleepMinutes`, `armSleepTrack`, `disarmSleep` are the only mutators, and the fade-out rides the element's volume in the last 15 seconds. Its only control surface today is the **Sleep · …** button in the Prayers Play All row, which opens `openSleepSheet()` — a `.sheet`-pattern overlay of choice chips. The label is its state (`sleepLabel()`), refreshed by `updateSleepLabel()` against `#sleep-btn`, an element that exists only while the Prayers tab is rendered.
8. **The full-screen sheet pattern already stands.** `.sheet` (ui.ts:109) is `position:fixed; inset:0; z-index:50` over a cream ground — the sleep sheet, the editors, and v318's Read view all use it. The Read view is the governing precedent for this item: `openRead(t)` (client.ts:688) builds a sheet whose play/pause calls `playTrack` on the same descriptor and the same element, **closing the sheet never stops or resets playback**, and `updateDock()` is called at its open point so the dock stays truthful behind it. A Now Playing sheet inherits every one of those properties by construction.
9. **The Read view's reach.** A track carries a Read control only where the payload says it has text (`hasText` + `textUrl`) — own episodes only; externals carry no text and no Read control, and Intentions segments carry none (v318 §1: segment texts stand out of the app read-along). `state.readTracks` / `state.dayDescs` already map the day's tracks for exactly this lookup.
10. **Persistence precedent.** The client persists exactly one thing today: the resume record, `localStorage['opn-resume-v312']` (date, episode, position). The sleep timer deliberately persists nothing (a session arm). A playback speed is a listener preference, not a session arm — the estate's nearest kin is v307's Focus length on the Goals Board, persisted per user. The recommendation (D1) follows the preference pattern: a small localStorage key of the client's own, applied to the element at boot and never sent anywhere.
11. **Shared files with v334 — the sequencing fact.** v334 (client-side externals) stands in Implement now; its Plan (commit 98d8f83 on release/v334) pins changes to the same two files this item touches — `app/worker/src/client.ts` (externals resolution at Prayers open, the day cache) and `app/worker/src/ui.ts` (the SW cache pin, currently `ora-pro-nobis-v328-1` at ui.ts:140). Two builds in these files at once would collide at landing. This release's chain therefore sequences behind v334 (Scope Record, constraint C1).

### Scope Record

- **Outcome:** the player gains (a) a playback-speed control — one rate, chosen from a fixed set, applied to everything the app plays and remembered across opens — and (b) a full-screen Now Playing surface, opened from the dock, carrying the seek bar the app has never had, previous/next, the speed control, the sleep control, and Read where the track has text; minimizing it returns to the dock with playback running, untouched.
- **In scope:**
  1. **Speed state** — a single client-side rate from the D1 set, held in shell scope beside `state`, applied to `audioEl.playbackRate` at boot, on change, and confirmed on every `startDesc` (so no path can inherit a stale element rate). A change mid-track takes effect immediately, without restarting the track or moving its position.
  2. **Speed persistence** — the chosen rate persists across app opens and across days in a client localStorage key of this release's own (D1); 1× is the first-run default. Nothing is sent to the server; no payload, route, or migration changes.
  3. **Speed controls** — a speed button naming the current rate (e.g. "1×") standing in the Now Playing surface, opening the standing chip-sheet pattern (the sleep sheet's own shape) with the rate set; the armed rate reads as the active chip.
  4. **The Now Playing surface** — a `.sheet`-pattern full-screen view standing over the tabs (z-50, the Read view's layer), rendered once and updated in place from the same events the dock already syncs on (`startDesc`, play/pause, `ended`, `timeupdate`) — one source of truth, no polling, no second state. Contents per D3.
  5. **The seek bar** — the app's first in-app seek surface: a scrubbable bar with elapsed and remaining times at the app's font floor, riding the standing `timeupdate` listener; a scrub sets `audioEl.currentTime` (clamped to duration) and the Media Session position state follows through the standing `seeked` hook. Seeking while paused stands paused at the new position.
  6. **Open and minimize wiring** — the dock tap per the deviation callout and D5; a minimize control on the surface; closing/minimizing never pauses, never moves position, never touches the queue or the sleep state (the Read view's standing rule).
  7. **Sleep and Read inside Now Playing** — the sleep control calls the same arm/disarm functions and shows the same `sleepLabel()` state as the Play All row button (one state, two surfaces, kept in agreement); Read opens the standing v318 Read view for the current track where it has text, and stands absent where it does not (D3).
- **Out of scope:** any change to how tracks are chosen, queued, ordered, or placed (v325/v328/v334 surfaces stand) · a queue-list UI · episode descriptions or show notes · a volume control (the phone's volume is the control; v320's fade probe already showed element volume is not honoured on every platform) · per-track or per-family speed memory · speed on the lock screen beyond what the Media Session position state already reports · any Worker route, payload, D1, or nightly-job change · any change to the dock's visibility rule, its buttons, or its progress line beyond the tap target in D5.

- **Risk class:** low — client-only presentation and one element property; no data, no migration, no auth, no server surface. Size S–M. Review on a candidate build with John's phone check as its last criterion (the v324/v326 pattern for player interaction changes).

### Decisions (recommendations — John's approval settles each)

- **D1 · Speed set + persistence.** Set: **0.5 · 0.75 · 1 · 1.25 · 1.5 · 1.75 · 2**. The choice **persists** — across opens and across days — in the client's localStorage, applied at boot. Reason: a spoken-prayer listener settles on a pace and keeps it; re-choosing every morning is friction with no benefit, and 1× remains one tap away on the sheet. (The sleep timer's no-persistence rule is not the precedent: a sleep arm is a one-night instruction, a speed is a standing preference.)
- **D2 · What the speed applies to.** **Everything the app plays — own episodes, external streams, and Intentions segments alike.** Reason: there is one audio element and one transport path (Discovery 1–2); a subset would need the rate silently swapped as the queue crosses families, so a Divine Office track at 1.5× would drop to 1× at the following novena with no visible cause. One rate, named on the surface, applying to whatever stands in the element.
- **D3 · Now Playing contents.** Standing: the podcast logo artwork · the track title · its block and source line (the dock meta's own facts, at reading size) · the seek bar with elapsed / remaining · previous · play/pause · next (previous/next under the standing queue rules; previous stands disabled where no earlier queue track stands, next mirrors the dock's rule) · the speed button (current rate as its label) · the sleep button (the standing label-as-state) · a Read button where the current track has text, absent where it has none · the minimize control. Out: everything listed under Out of scope above.
- **D4 · Minimize.** Minimizing returns to whatever tab stood open, the dock standing as today, **playback running and untouched** — minimize is a view change, never a transport action. Reached by the surface's minimize (chevron-down) control; a downward swipe is named as a Plan-time option only if it rides the sheet pattern without new gesture machinery — the button is the committed route.
- **D5 · The dock tap (THE DEVIATION — see the callout).** Recommendation: **the tap opens Now Playing, replacing the jump-to-card** — the behavior this item asks for by name. Alternative, if John prefers to keep what he has: the tap keeps its jump, and Now Playing opens from a new affordance (e.g. the dock's logo thumb becomes the open control). Either way, the dock's play/pause and next buttons are untouched, and under the recommendation the Prayers card list remains one tab tap away, exactly as today.
- **D6 · Sequence against v334.** v336's Plan seats only after v334 lands on trunk; before Implement, release/v336 rebases onto the post-v334 trunk and re-pins whatever v334 moved (the SW cache name above all). Merge order is strict: **v334 first, v336 second** (constraint C1). No part of v336 is built against the pre-v334 client.

### 2.2 Build spec — speed (client.ts only)

- **P1 · State + storage.** One shell-scope rate beside `state`: `state.rate`, a number from the D1 set {0.5, 0.75, 1, 1.25, 1.5, 1.75, 2}. Persisted under the client's own localStorage key **`opn-speed-v336`**, stored as the bare number's string. Read once at boot (beside the `audioEl` binding): a missing, unparsable, or out-of-set value falls back to 1. Never sent to the server; no payload, route, or storage change anywhere else.
- **P2 · Application points (exactly three).** (a) **Boot:** `audioEl.playbackRate = state.rate` immediately after the stored value is read. (b) **Every `startDesc`:** re-assert `audioEl.playbackRate = state.rate` before `audioEl.play()` — no path can inherit a stale element rate (§1 Scope item 1). (c) **On change:** the setter `setRate(r)` validates against the set, writes `state.rate`, sets `audioEl.playbackRate`, persists, calls `updatePositionState()` (so the lock screen's position math corrects at once — the standing function already reads the element's rate), and refreshes the Now Playing speed button + any standing speed sheet's active chip. The Media Session `play` handler (393) needs no change: the rate lives on the element it plays.
- **P3 · The speed sheet.** `openSpeedSheet()`, built exactly on `openSleepSheet()`'s pattern (a `.sheet` div appended to body, chips, a Close control that removes only itself): one chip per D1 rate, label = the rate + "×" (`0.5×` … `1×` … `2×` — the 1 rate labels "1×", never "1.0×"), the current rate's chip carries `active`. Choosing a chip calls `setRate`, marks the chip, and leaves the sheet standing (the sleep sheet's own behavior — the user closes it, or taps a different chip). Opened from the Now Playing speed button (§2.3); it appends after Now Playing in DOM order, so it stands on top, and closing it returns to Now Playing standing beneath.

### 2.3 Build spec — the Now Playing surface (client.ts + ui.ts CSS)

- **P4 · Construction — the Read pattern.** `openNowPlaying()` removes any standing `.np-sheet`, builds one `.sheet` div (class `sheet np-sheet`), appends it to body, and wires its controls — exactly `openRead`'s construction discipline. No SHELL_HTML change; no new element stands while nothing plays. Contents, top to bottom, with pinned ids: the podcast logo (`/logo.png`, the dock thumb's own source, at reading size) · `#np-title` (the track title) · `#np-meta` (block, then source where the descriptor carries one, else the date label — the dock meta's facts) · the seek row (§2.5): `#np-elapsed`, `input[type=range]#np-seek`, `#np-remain` · the transport row: `#np-prev`, `#np-play` (a `playbtn` whose glyph mirrors the dock's — ▶ while paused, ❚❚ while playing), `#np-next` · the control row: `#np-speed` (label = current rate + "×"), `#np-sleep` (label = `sleepLabel()`), `#np-read` (stands only under §2.6's rule).
- **P5 · Sync — one path, the dock's.** `updateNowPlaying()` is called from inside `updateDock()` (after the dock's own sync) and from the standing `timeupdate` handler beside `updateDockProgress()` (seek fill + elapsed/remaining only). It guards on the sheet's existence and returns at once when no sheet stands — no polling, no second state, the §1 "one source of truth" term. It re-renders: title, meta, play glyph, prev/next disabled states (§2.4), the speed button's label, the sleep button's label, and Read's presence (rebuilt against the current track each sync — a track change under an open sheet swaps the whole surface's facts, never its frame). When `updateDock()` hides the dock because `state.current` cleared (queue end, advanceQueue's end-clear), it also removes a standing `.np-sheet` — the surface's visibility is derived from `state.current` exactly as the dock's is.
- **P6 · The one descriptor change.** `trackDesc()` additionally carries **`source`** (`t.source || ''`) and **`durationS`** (`t.durationS || t.durationSec || 0`). Additive only; both queue builds (renderPrayers, extRebuildDescs) flow through it, so own, external, and segment descriptors gain the fields uniformly. Nothing that reads descriptors today changes behavior (the fields are new).

### 2.5 The seek bar — behavior per family (pinned)

The bar is one control with one behavior; what differs is what the element can do with each family's URL, stated plainly:

- **Mechanics.** `#np-seek` is a range input 0–1000 (per-mille, for a smooth thumb on long episodes). Display duration = `audioEl.duration` when finite, else the descriptor's `durationS` when > 0, else unknown. While the duration is unknown, elapsed shows the element's position and remaining shows `--:--`, and the bar stands disabled. On `input`, a scrubbing flag suppresses the `timeupdate` fill (the thumb follows the user's finger, not the player); on `change`, the flag clears and the seek commits: `audioEl.currentTime = clamped target` (0 … duration). The standing `seeked` listener refreshes the Media Session position state — no new wiring. Seeking while paused moves the position and stands paused (the element's own semantics; the resume save on pause already records it). Labels format `m:ss`; remaining carries a leading `-`.
- **Own episodes — exact, ranged.** The URL is the Worker's Range route (§2.1 item 2): a scrub issues ranged reads and lands at the target within the element's own accuracy, playing or paused, buffered or not. This is the daily prayer's main body, and it is the family §1 criterion 6 judges.
- **Downloaded externals — exact, local.** The URL is a Blob URL over the device copy (v334 A1): seek is local and exact, no network involved. A slot still downloading or missing is `available: false` and can never stand as `state.current`, so the bar never faces a half-landed external. (The mid-play cache-discard edge: invalidation deletes `opn-ext-audio-v1`, but a playing external's Blob URL is already materialized — playback and seek continue from the blob; the discard bites the NEXT open, as v334 designed.)
- **Intentions segments — element-native over a full-body file.** The standing-name route returns the whole file (§2.1 item 3). Inside the buffered range the seek is exact; a jump past the buffer re-reads the file (234–570 KB) and lands as the buffer arrives — a beat, not a failure, at segment sizes. The bar shows the true duration once metadata lands (on play, promptly for files this size); before that, the descriptor carries no segment duration, so the bar follows the unknown-duration rule above. No Worker change is made to give segments Range in this release — §1 placed Worker routes out of scope, and the honest cost is named here rather than papered over.
