### Discovery findings (verified — the facts that shape this design)

1. **What exists today is data + API, not an app surface.** The GoalPost prayer module (board v56, 2026-11-04; rules settled v58) holds the intentions pool, the draws, the completions, and the day addendum in the board's D1. Its Prayer day VIEW was removed in v58 at John's direction ("Remove the Prayer view — pool stays in Settings"): the only screen left is pool configuration in Settings → Prayer (list, add, edit, retire, delete, priorities). The module's tables and endpoints stay because the nightly job composes from them. **Consequence:** this app is not a screen move — its Intentions home (a real day view: today's blocks with the drawn intention on each item, check-offs, the addendum line) is a new surface that restores what v58 removed, now in the place John actually wants it.
2. **The live data is small and exact** (board D1, read 2026-11-08): `prayer_items` 35 rows, all enabled, in six blocks (Morning · Midmorning · Midday · Afternoon · Evening · Night; block start hours 0/9/12/15/18/21 Chicago). `prayer_intentions` 11 rows, ALL active, split exactly **3 High / 7 Medium / 1 Low** — the pool is the active set; there is no separate pool table. `prayer_draws` 175 rows (35 per day × 5 days), latest date 2026-11-08. `prayer_completions` 9 rows. `prayer_addenda` 5 rows. `prayer_block_labels` carries per-block labels. The data model is migration 0015, itself a 1:1 port (ids preserved) of the retired suite app's tables — the port pattern is proven twice already.
3. **The draw rule is precise and must not change.** One active intention per enabled item per date, weighted **High = 4 · Medium = 2 · Low = 1**, persisted per date, **fill-missing only** (an existing draw is never re-rolled), repeats across items allowed and kept. Adding an intention only adds it — it first enters a draw at the next nightly fill (v58 rule). Retiring an intention deletes its draws from today forward and refills; deleting removes all its draws and refills. The day addendum (the saint-of-the-day "pray for us" line) is part of the day payload.
4. **The one hard consumer is the midnight job.** Cron `daily-devotional-artifact` (00:00 CT) drives the module through the board's agent door: step 7a POSTs `/api/agent/prayer/day` {date, addendum} — sets the day's addendum and ensures the day's draws exist — then GETs the day payload and composes all seven segment prayers (six blocks + the Mass split) from it; step 7e writes each block's script into the Intentions subtask notes of that block's Activities occurrence in the Opus Dei goal, attaches the rendered MP3, and sets the parent task's notes to the script; step 9 verifies the module payload (every item carries a drawn intention; the addendum matches). **If the intentions move and this job is not repointed the same night, the segment prayers and the Intentions audio stop.** Every other consumer reads the composed output, not the module.
5. **The remaining consumers are soft.** (a) The Activities tasks' Intentions subtasks and their audio consume the cron's composed scripts — their shape does not change; only the composition source's door changes. (b) The Devotional Suite's /prayer/ page already 302-redirects to the board root (suite Worker, retired 2026-11-04) — after the move it should redirect to the new app instead; the suite's own /api/prayer/* endpoints are legacy data, unused. (c) Segment audio hosting stays where it is (board attachments since v73/v74); the module only ever linked to it.
6. **Access today is actor-based; the new app can be stricter.** On the board, Pam is an allowed Access identity for the app as a whole and is refused per-route (403 on every /api/prayer/* route; the agent prayer door is Muse-only). The DevOps Board app shows the stronger house pattern for private data: Cloudflare Access allows John's identities only, the Worker itself refuses any other Access email, and there is no Pam path at all. **This app follows the DevOps pattern, not the board pattern** — see the Access section below.
7. **Confession / examination is greenfield.** A search of the board Worker, the board client, and the DevOps Worker finds no examination or confession code, tables, or content anywhere. The module is designed from the practice (below), not ported.
8. **House app shape (verified against the DevOps Board app).** Own repo · own Cloudflare Worker · own D1 with numbered migrations · own AGENT_TOKEN agent door on /api/agent/* with writes · Cloudflare Access (Google) in front + a Worker-side identity check · PWA-installable shell · harness gate tests against a local D1 · the project's releases run through this same DevOps pipeline. The new app follows this shape without exception found.
