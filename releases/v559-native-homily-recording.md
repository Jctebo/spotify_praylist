## 2 · Plan

- **D1 · Capture mechanism: MediaRecorder with a per-recorder preferred device (API 31+ path is his path).** The plugin records with `android.media.MediaRecorder`: audio source `MIC`, output format `MPEG_4`, encoder `AAC`, 44,100 Hz mono, 128 kbps, written to an app-private file. The chosen input (resolved from the pick key against the live device list, exactly as `applyAudioInput` resolves it) is set on the recorder itself — `recorder.setPreferredDevice(device)` (API 31+) — before `prepare()`. Why not AudioRecord: per-recorder routing exists on both, but AudioRecord delivers raw PCM and would need a hand-built MediaCodec + MediaMuxer AAC pipeline — a second encode stack to prove, for no routing gain. MediaRecorder is the platform's recorder: one object owns source, routing, encode, and the file. John's Galaxy Z Fold 8 runs Android 15+ (API 35+), so the API 31+ path is his path. Pre-31 courtesy path (recorded, minimal, mirroring v557 D3): `setPreferredDevice` does not exist for MediaRecorder below API 31, so a Bluetooth pick rides the communication-mode/SCO start (D2) alone and a built-in pick records unsteered — the legacy limit, stated, not hidden.
- **D2 · Bluetooth SCO handling (his Ray-Ban Meta glasses).** A Bluetooth SCO microphone only opens its channel in communication mode. For a Bluetooth pick the native start, in order: (1) save the current audio mode; (2) `AudioManager.mode = MODE_IN_COMMUNICATION`; (3) API 31+: `setCommunicationDevice(target)`; pre-31: `startBluetoothSco()` + `isBluetoothScoOn = true`; (4) brief settle wait for the SCO link (the start answers only once the route stands or the wait expires — a failed SCO open with the device present still records, from the preferred-device route, and the answer says so); (5) `recorder.setPreferredDevice(target)`; (6) start. At stop/cancel: recorder released, communication device cleared, SCO stopped (pre-31), saved mode restored. For a built-in pick: preferred device only, no mode change (the phone mic needs no communication mode; holding one would change the device's call behavior for nothing). For the System default pick: no steering at all — the recorder takes the system default input, the native equivalent of today's behavior.
- **D3 · Encode: AAC in M4A (`audio/mp4`) — confirmed against the app's playback path.** The store's playback assembles the take's chunks into one Blob typed by the index entry's `mimeType` (`homilyTakeBlob`) and plays it through the standing element path (the v556 homily arm). The WebView plays `audio/mp4` (AAC-LC in M4A) natively — v551's own `homilyMimePick` already lists `audio/mp4` as a capture candidate — so a native M4A take is indistinguishable from a WebView take once stored: same store, same Blob assembly, same playback. Sample rate 44,100 Hz (the AAC-LC profile's safe rate on every supported device), mono (a homily is one voice; the glasses' SCO channel is mono narrowband anyway), 128 kbps (transparent for speech, ~0.94 MB per minute — a 30-minute homily ≈ 28 MB, sized in D4).
- **D4 · Hand-off: chunked bridge pull into the standing chunk store.** One base64 string for a whole homily is rejected on size math: 28 MB of audio is ~38 MB of base64 through the bridge's JSON channel in a single call — slow, memory-heavy on both sides, and a single failure loses the whole transfer. Instead, at stop the file stands complete in app-private storage and the page PULLS it in slices: `readNativeTakeChunk({ offset, length })` answers `{ data, eof, sizeBytes }` with base64 of a 256 KB raw slice (~341 KB per call, ~113 calls for the largest expected take, each independently retryable). The page decodes each slice to a Blob (`audio/mp4`) and writes it as the next chunk row of the take (`homilyIdbPut('chunks', { id, seq, blob, mimeType })`), updating the index entry's `chunkCount`/`sizeBytes` as it goes — the exact rows `homilyTakeBlob` later reads, in seq order. When the pull reads EOF, the page calls `discardNativeTake()` (the shell deletes its copy; the device's only copy is the store's, as v551 intends), finalizes the entry `ready`, mints the blob URL, and paints the saved note — v551's finish dress, unchanged. A pull that fails mid-way retries the same offset; a pull abandoned (page death) leaves the entry in `recording` state with the chunks that landed — v551's finalization rule then keeps it as a partial take if any chunk landed, which is MORE than the native file alone could promise.
- **D5 · Bridge surface (OraDayBridgePlugin, five additive methods; no standing method changes).** `startNativeRecording({ key })` → `{ started, name, fellBack, mimeType }`: resolves the key exactly as `applyAudioInput` does (same `micDevices`/`micKeyOf` seams); an absent picked device answers `fellBack: true` with the name actually used and records from the system default device (Q5 A, D7); a `default` key records unsteered. RECORD_AUDIO: the shell checks the runtime grant before starting; if it does not stand, the plugin asks (the Capacitor permission flow, saved call) and the start proceeds or fails on the answer — a denial answers `started: false, reason: 'permission'` and NO take starts (D8). `stopNativeRecording()` → `{ sizeBytes, durationMs, mimeType }`, the file finalized and standing for the pull. `readNativeTakeChunk({ offset, length })` → D4. `cancelNativeRecording()` → stops, deletes, restores route/mode; the page's abort path calls it. `discardNativeTake()` → deletes the standing file after a completed pull (also called at any new start, clearing a stale file). One recording at a time: a start while one stands answers `started: false, reason: 'busy'`. Elapsed time is the PAGE's timer (v551's `homilyRec.startedAt` dress, unchanged); the entry's `durationS` at finalize is the bridge's measured `durationMs` (the recorder's own span), falling back to page elapsed — the same max() discipline as v551's finish.
- **D6 · Client integration (the record card; bridge-native world only).** Detection: `oraBridgePlugin()` exposes `startNativeRecording` (new shell) → the native path; the bridge stands but offers no native recording (APK 1.0.47/1.0.48 shells) → the v557 path stands exactly as shipped (prepare-steer + WebView capture); no bridge (browser) → v551's path, byte-identical. On the native path, Record tap: (1) create the index entry exactly as `homilyStartCapture` does today — same id, same name ("Homily — <long date>"), same dateKey/dayName, `mimeType: 'audio/mp4'`, state `recording` — and the `takes` row; (2) call `startNativeRecording({ key: <the remembered pick's key, or 'default'> })`; on `fellBack`, the Q5 A notice stands on the card BEFORE the take audibly starts (the start answer returns before capture is audible — the notice paints with the recording dress, the same words as v557's M3 notice); on `started: false`, the entry is removed (v551's abort discipline) and the card shows "Microphone not available on this device." — never a silent WebView substitute (D8); (3) `homilyRec` stands in its native form (`{ id, native: true, startedAt, timer, wakeLock }`) — the recording dress, timer tick, and wake lock are v551's, and the dress's microphone line names the start answer's `name`. Stop tap → `stopNativeRecording()` → the D4 pull → finalize (v551's `homilyFinishRecord` shape: entry ready, duration, size, mint, saved note, repaint). The WebView capture functions (`homilyStartCapture`, the MediaRecorder wiring, `homilyMicPrepare`/`homilyMicRelease`) are NOT modified — the native path branches at `homilyStartRecord` before them and reuses the shared entry/finish discipline; on the native path `homilyMicPrepare` is never called (the bridge owns the route end-to-end; calling `clearAudioInput` from the page mid-native-take would clear the communication device under the recorder — the release seam is the bridge's own stop/cancel). The microphone row, picker, and remembered pick (`opn-homily-mic-v557`, v558's `homilyMicRows()` grouping + pick migration) are untouched — the native start consumes the same stored key the steering consumed.
- **D7 · Q5 A on the native path.** Chosen input absent at record time: `startNativeRecording` resolves no device for the key → records from the system default device and answers `fellBack: true` + the default route's name → the card notice stands in v557's exact words ("<Name> not connected — recording from <name>.") before the take starts; recording is never blocked and never silent. A Bluetooth device that is present but whose SCO channel fails to open: the take still records (preferred-device route), the answer names the device — recorded here as the honest limit: presence is provable in code, channel quality is a field fact.
- **D8 · No silent downgrade (the stop rule).** In the new shell, a native start failure NEVER falls back to WebView capture: a WebView take in the shell would record whatever the system route gives — the exact defect John reported — while wearing the picked microphone's name. Failure shows the unavailable note and no take starts. (The OLD-shell and browser worlds keep their standing paths whole: there the WebView path is the only path and makes no per-device promise beyond v557's shipped dress.) STOP RULE for the chain itself: if Implement finds code-level evidence that per-recorder routing cannot capture from a chosen Bluetooth device on his phone class (API surface absent, recorder refuses the device class), the chain holds and reports with the evidence — no lesser shape ships.
- **D9 · The dead-session trade-off (named, accepted by design).** WebView takes flush chunks into the store during recording, so a dead session leaves a partial take (v551 P4). Native takes transfer at stop: a session that dies mid-recording leaves the entry `recording` with zero chunks, and v551's finalization drops it — the take is lost, and the orphaned native file is discarded at the next native start. The mitigations that stand: the wake lock is held for the whole take (v551's discipline, carried onto the native path), and the app is foreground by design while recording a homily. Recorded plainly so the difference is a decision, not a surprise: partial-take recovery is weaker on the native path; capture correctness — the thing John ordered — is what this release buys.
