### 1.1 Discovery — what "native Android app" can honestly mean for this app

Researched 2026-11-10 against Google's own documentation (sources at §1.5). Three routes exist; they are NOT three sizes of the same thing — they differ in kind on the Android Auto question.

**Route A — TWA (Trusted Web Activity).** Bubblewrap generates a small Android project from the live manifest; the APK opens the live origin full-screen in Chrome, verified by Digital Asset Links (`/.well-known/assetlinks.json` on the origin, matched to the signing key). The web app stays the only codebase; every web deploy is the app update. **Gives:** a real Play listing, a launcher entry that is a genuine app (own entry in Android app settings, own uninstall), fullscreen with no browser UI. **Does NOT give Android Auto — at all.** Android Auto discovers media apps by a native media browser service declared in the APK's manifest (§1.2); a TWA declares none and has no native code to declare. A TWA in Android Auto is not a limited version of the thing — it is absent from the car screen. **Access inside a TWA:** the TWA renders in Chrome with Chrome's own cookie jar, so John's existing Access session in Chrome carries over and the Google sign-in runs in real Chrome — the one route where sign-in is a non-event. **One estate-specific friction:** the Digital Asset Links file must be fetchable by Google's verifier WITHOUT authentication; Access sits in front of the whole hostname and would redirect the fetch, which fails verification and drops the TWA back to a browser-tab look. The fix is narrow (an Access bypass for the single `/.well-known/assetlinks.json` path), but it is a real Worker/Access change, priced at Plan if this route is chosen.

**Route B — Capacitor shell + a native media module.** Capacitor packages the web build (the same client) inside a real native app with a WebView, plus native plugins. **Gives:** a real APK with its own identity, sideload or Play distribution, an update path that does not depend on Chrome, and — the decisive part — a place to hang native code: Android Auto support is added as a custom native module (Kotlin) implementing the media browser service + media session (§1.2), fed by the app's standing day payload, playing the same audio URLs natively. **Costs / frictions, named plainly:** (1) Capacitor ships NO Android Auto support itself — the Auto module is hand-written native code either way; Capacitor only hosts it. Community music-controls plugins expose notification controls, not the Auto browse tree. (2) **Sign-in is this route's sharp edge.** Google refuses OAuth inside embedded WebViews (`disallowed_useragent`), and the Access cookie from a system-browser login does not flow into the WebView's own store. Escape routes exist — an email one-time-code login method added to this app's Access application (works inside a WebView; Google stays the browser method), or the native module + shell authenticate by a per-device credential instead of the browser session — Plan prices them; none is free. (3) Two build systems to keep (web + Android) where today there is one.

**Route C — Fully native media app.** A native Android app (Media3 / MediaSession + a media library service) whose browse tree IS the app's day: the eight blocks as the root level, tracks under them, playback native end to end. The phone UI can stay the web app; the native app exists for the car (and can grow a phone face later). **Gives:** the complete Android Auto form — browse tree on the car screen, voice actions, the platform's own playback engine (which also sidesteps the web-audio stopping behavior John is still pinpointing for v358 — stated as context, not as a promised cure). **Costs:** the largest build by a wide margin; a second client of the same payloads to keep in step forever; and it needs its own credential path to the payloads (they stand behind John's browser Access session — a per-device token route on the Worker, the agent-door pattern turned to a new purpose; that is an auth-surface change and is John's decision, §1.3 Q4).

**Baseline named for honesty — Route 0, no build:** Chrome can already install the web app (WebAPK): launcher entry, app-settings row, no browser UI. It costs nothing and proves the management half weakly — but it is not a native app, has no Play presence, and cannot appear in Android Auto either. Recorded so the test's added value is measured against the real baseline, not against "browser tab."

### 1.2 Android Auto — the platform facts the decision turns on

- A media app appears in Android Auto ONLY through a native service: the app declares a `MediaBrowserService` / `MediaLibraryService` and a `MediaSession` in its manifest (Google: "Use MediaBrowserService and a MediaSession to create an app that Android Auto and AAOS can connect to" — Media apps for cars overview, developer.android.com). Android Auto connects to that service, reads its browse tree, and sends playback commands to the session. There is no web API for this surface: the web Media Session API the app already uses drives the phone's lock screen and notification, and is invisible to the car.
- Therefore NO wrapper of the web page — TWA, WebAPK, or a bare WebView shell — can appear in Android Auto. The minimum native unit is the media service itself; everything else about the app may stay web.
- Browse scope is a real choice: the service can expose a flat root ("Today" → the day's tracks, appear-and-play) or the app's full shape (eight blocks → tracks, intentions interleaved as in the app). The flat root is a small service; the full tree is the same service with the whole payload walked.
- **Testing without Play:** Google documents two test paths (Test Android apps for cars, developer.android.com): the Desktop Head Unit (DHU) emulates a car head unit on a development machine against a real phone; and for a real vehicle, the app must normally be installed from a trusted source (a Play internal test track or Internal App Sharing avoids the full review) — with ONE exception: Android Auto's own developer mode (tap Version 10× in Android Auto settings) offers "Allow unknown sources," which lets media apps installed by sideload run in the car. That exception is what makes a sideloaded TEST build viable in John's own X5.
- Production distribution is a different country: an Android Auto media app on Play goes through car-app quality review, and a new Play developer account carries the 12-tester / 14-day closed-test gate before production. Neither applies to an internal-track or sideloaded test; both are priced later only if John takes the app past a test.

### 2.4 The payload read path — the client hands the native side its resolved day (DECIDED)

- **The problem, from first-hand reading:** `/api/player/day` serves the day SHELL only (blocks, labels, `introTexts`, liturgical day, settings version — playerDayPayload, index.ts:542) and refuses non-session callers; the actual track list is built on the device at open: the client assembles `state.dayDescs` from the prayer payload, the intentions feed, and the external resolutions (some direct, some through the session-only Worker courier legs) — v334's approved client-side model. There is no standing server payload a native caller could read, and the agent door's day read is the same shell.
- **The design:** the client already computes the one true resolved day inside John's Access session. A small Capacitor plugin, **`OraDayBridge`**, receives a snapshot of that resolved day from the client and persists it to app-private storage; the media service (§2.3) serves the snapshot. No new Worker route, no native feed resolution, no machine credential in the app.
  - **Snapshot shape:** `{ presentedDay, dateLabel, generatedAt, tracks: [{ id (episodeId), block, title, kind, durationS, mediaUri, needsAuth }] }` — tracks in day order, available tracks only, `mediaUri`/`needsAuth` computed per §2.5 from the descriptor's PRE-BLOB source fields (a `blob:` URL never enters the snapshot — blob URLs are WebView-local and meaningless to native code).
  - **The one client touch:** at the end of the resolution pass (the point the presented day's descriptors stand final) and again on a day rollover while the app stands open, the client — ONLY when `window.Capacitor` is present — calls the bridge with the snapshot JSON. Guarded and inert everywhere else: browser, installed PWA, and desktop behavior are byte-identical, and the bridge call can never fail the day build (wrapped, fire-and-forget). This touch is inside Route B's premise (the shell + module must receive the day somehow), changes no web behavior, and is the only client edit in the release.
  - **Freshness rule:** at browse/play time the service compares `snapshot.presentedDay` to the America/Chicago calendar date. Equal → serve. Stale or absent → the root holds ONE non-playable item, "Open Ora Pro Nobis on your phone to load today", and nothing plays. **Named cost, accepted for the test:** the car cannot cold-fetch a day the phone app has not built; the car test protocol (§2.8) opens the app first, which is John's standing daily pattern anyway.
- **Alternatives weighed and rejected:** (a) a new full-day Worker route — server-side resolution contradicts the approved v334 model and grows the auth surface with a full-descriptor route; (b) native re-implementation of the feed resolution — a second resolver that drifts from the contracts source of truth; (c) the agent-door token inside the app — a machine credential standing in for John on his own phone, the wrong principal. All three stay rejected at Review.

### 2.5 Media URI rules — by descriptor class

- **Own + intention tracks:** `mediaUri` = `<origin>/api/player/audio/<presentedDay>/<episodeId>` — the standing session-gated Range route (index.ts, player audio) — with `needsAuth: true`. (The client's blob form cannot cross; this route is the native equivalent and seek depends on its Range support, which stands.)
- **External tracks whose resolved URL already stands on the app origin** (the courier / audio pass-through legs): the resolved URL as-is, `needsAuth: true`.
- **External tracks with a direct enclosure URL:** the URL as-is, `needsAuth: false`. **Named risk:** a host that refuses non-browser reads fails in the car the way the v358 class failed in the browser. The verification plan (§2.8) plays one direct external at the on-phone desk step, where an ExoPlayer error is visible and attributable; a refusal is a valid TEST finding, recorded as such and routed to a follow-on — it is not silently patched inside this release.
- **Auth transport:** for `needsAuth` requests the native player attaches the `CF_Authorization` cookie for the app origin, read from the WebView's CookieManager after sign-in (Capacitor's WebView is the system WebView; its cookie store is readable by the app). The cookie is re-read at every play start; a 403 surfaces as a service error state, and re-sign-in happens where the login lives — the shell's WebView (§2.6) — never in native UI.
