### Confirmed mechanism (Scope's own verification, trunk d54ac03)

Both Step-1 findings verified first-hand against the source. Evidence grades are stated per finding.

**Finding 1 — cross-family ordering (REPRODUCED + code-read, deterministic).**

- `ownInsertCards` (client.ts:1882) inserts each block's own rows at the head of the block — at `heads[bi].nextSibling`, immediately after the block heading — sorted only among themselves by sortOrder.
- `extInsertCards` (client.ts:1737) inserts each block's externals before the NEXT block's heading, i.e. at the block's end; its own header comment states the rule: placeholders "stand after the block's own tracks, in settings sort order within the block". The render pass calls `extInsertCards` then `ownInsertCards` (client.ts:2410–2411), so own rows land at the head no matter what ran before.
- `extRebuildDescs` (client.ts:1776) — the queue builder — repeats the same family split: per block it emits payload tracks, then the block's own rows (sorted within the own family), then the block's externals (sorted within the external family). No code path ever compares an own row's sortOrder against an external slot's.
- Consequence for Midmorning (settings 1 Exegesis/external · 2 Novenas/own · 3 Terce/external): cards and queue both stand Novenas → Exegesis → Terce on every open, on every device. The exegesis can never stand first while this split stands.
- Reproduction on record: the estate's harness-v337 logs carry the actual Midmorning card list from real runs — `["seg:Midmorning", "novena-st-fixture", "novena-st-jude", "ext-gospel-exegesis", "ext-midmorning-prayer"]` — novenas ahead of the exegesis, exactly as the code dictates (the leg named 'Exegesis card stands in Midmorning at the head of its externals' FAILs in three of the standing logs on the seg-card variance and passes in others only because its expected array itself encodes novenas first — the card ORDER it records is the defect, in every run).

**Finding 2 — resolution fragility (code-read, mechanism certain; occurrence on John's phone probabilistic).**

- The slot table (client.ts:1468) pins `ext-gospel-exegesis` to `download: 'passthrough'` with matcher `latest-by-release-date` against the Anchor feed.

2. **Robust exegesis resolution.** The slot must settle present and playable with the contract's latest-by-release-date pick without depending on two fragile full-feed fetches. Plan settles the exact mechanism among the shapes the estate already owns: resolving the pick through the Worker (the `/externals/live` courier pattern — the Worker fetches with its 15-second budget and returns just the pick, so the phone never downloads or parses 3.16 MB), a retry on the client leg, and a retry on the single passthrough download route (every other slot's download already retries; this slot's one route gets the same second attempt). The contract's matching rule does not change: latest by release date, not after the presented day, enclosure required — the same pick the Step-1 feed check verified for today.
3. **Nothing else.** No settings change (the rows are already correct), no contract change, no payload change beyond what the resolution mechanism needs, no other slot's matcher or route changes, no nightly-job change.
