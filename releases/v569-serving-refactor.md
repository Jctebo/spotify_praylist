## 2 · Plan

- **Zone (connector, read-back verified):** Smart Tiered Cache ON for orapronobis.media (one fill per region rides the upper tier). - **Worker (index.ts):** (a) `GET /api/prayer/day-manifest?date=` — ONE call carrying the day's whole shape: the standing day payload, the day's Mass payload, the day's readings payload, and the day-set asset list (every own-feed enclosure whose stem carries the date, feed order, deduped, with byte sizes). (b) Immutable day builds at the app layer: a settled day (before Chicago today) answers its day + manifest with `Cache-Control: private, max-age=31536000, immutable`; today keeps the standing uncached shape (settledJson). (c) Nothing else: PRAYER_AUDIO byte-identical, playback routes untouched, the agent day-read untouched.
- **Client (client.ts):** `daySetPrefetch(date)` — one manifest call per day (a per-date local stamp stops repeats), then the day set downloads in ONE pass, sequentially, through the standing feed-audio pass-through (the enclosure host sends no CORS header), into the standing device audio cache (`opn-ext-audio-v1`) under each asset's own URL — the key the cache-restore playback paths already read. Already-cached entries skip; a failed asset never blocks the pass or the day. Purely additive: no playback route changes; the pass warms the cache so the day replays locally, offline included. Called once behind the boot.

First run stands in §3.
- **Cache warmer (runner/warm_day_cache.py):** at publish time, walk the published day's dated assets and request each once through the edge (then a ranged re-check reporting cf-cache-status) so the first listener per region reads the tiered cache, not the origin. Ships as a repo tool for the publish flow to call; the nightly runner wiring is a named follow-up (§5), deliberately not landed tonight beside the Nov 23 publish repair.
