### Discovery findings (verified this pass)

1. **The text already exists, exactly, before any audio.** Ora is script-first: pass 1 of the nightly run writes one script file per episode into the run directory (`script-morning-prayer.txt`, `script-daily-rosary.txt`, `script-daily-reflection.txt`, one `script-novena-*.txt` per novena, and the rest — 16 script files stand in the 2026-11-10 run directory). These are the exact words rendered to audio — names, saints, and prayers spelled as approved, with no transcription error possible. No ASR is involved anywhere in this release.
2. **The feed carries no text today.** A current item holds: title · guid · link (the MP3 on the public audio host) · a one-to-two-sentence description · pubDate · author · itunes:author · enclosure. The full text stands in **zero** items: the feed fetched first-hand in this pass (2,804 items) contains **no transcript tag and no `podcast:` namespace declaration at all** (grep count 0).
3. **The transcript tag form.** Podcast apps read a creator transcript from the item-level tag `<podcast:transcript url="…" type="text/plain"/>` (Podcast
...[truncated 9116 chars]ing 2.0 namespace; the channel must declare `xmlns:podcast` for the tag to be valid). Apple's published rule: a creator-supplied transcript delivered this way **takes precedence** over any machine-generated one ("Transcripts on Apple Podcasts", https://podcasters.apple.com/support/5316-transcripts-on-apple-podcasts — the analyst document's cited source). The tag points at a transcript **file at a public URL**; it does not embed the text in the feed.
4. **A public host for the files already stands.** Episode audio is served from `https://audio.orapronobis.media` (the `AUDIO_PUBLIC_BASE` constant in runner/pass2_build.py; the feed's enclosures resolve there). Transcript files publish to the same public host/bucket pattern at publish time — no new host, no new account. The exact key layout is Plan's (e.g. a per-episode `.txt` beside its MP3).
5. **The graft point is one place.** runner/pass2_build.py builds and grafts each item and verifies the live feed afterwards; the channel header is emitted by the same publish path. Adding the namespace declaration (once, channel-level) and one tag per new item (graft-time only) touches no existing item.
6. **The app half is designed against v312 — and only works after it.** v312's `player_episodes` table (its §2, element E1) carries **no text column and no transcript key**: date · episode_id · title · block · sort · duration_s · r2_key · size_bytes · audio_state · pushed_at. The app half of this release is therefore an **extension of v312's design**: the push manifest gains the day's texts (or transcript keys), the store gains a place for them under the same one-day replace-day sweep, and the client gains a read view. **Hard dependency: the app half cannot be built or shipped before v312 ships** — there is no episode store to extend until it does. The public-feed half has **no** such dependency (scripts exist at build time today).
7. **Constraints that stand:** endpoints frozen — the feed **address** does not change; adding a namespace declaration and per-item tags changes the feed document's content, which is the approved surface change named above, not an endpoint change · no checklist / no done state in the app (the read view is text, not a task surface) · the app stays John-only · one-day retention governs the app copy (yesterday's text leaves with yesterday's audio) · the Intentions segments are app audio, not feed episodes — they are not part of the feed half; whether their text joins the app read view is Plan's question, answered under the same one-day rule.

### Scope Record

- **Outcome:** every new episode publishes with its exact text attached — in the public feed as a transcript apps can read, and in John's app as a read-along view for the stored day — so the prayers can be read, searched, and prayed in silence as well as heard.
- **In scope:**
  1. **Transcript files at publish (public-feed half).** At pass 2, each published episode's run-directory script file becomes its public transcript file on the audio host (plain text, the script's words as rendered — Plan settles any light cleanup, e.g. production-only markup, and names it; the words themselves are never edited). Upload joins the publish step's existing R2 reconciliation shape, before the feed graft, so a published item never points at a missing file.
  2. **The feed change (public-feed half).** The channel gains the `xmlns:podcast` declaration; each newly grafted item gains `<podcast:transcript url="<the episode's public transcript URL>" type="text/plain"/>`. **New items only** — the 2,804 standing items are not backfilled and stay byte-identical (backfill is out of scope below). The publish verification step extends to read back one new item's tag and fetch its transcript URL (200 + the episode's opening words).
  3. **The nightly report (public-feed half).** The closing report gains a named field — **"Transcripts (v318)"**: episodes published · transcripts uploaded · tag read-back result — in the v298/v306 field pattern.
  4. **The app store extension (app half — after v312).** v312's push gains the episode texts: the pushing job includes each episode's text (or its app-bucket transcript key) in the replace-day commit; the store holds the text under the **same one-day rule** (the commit's sweep removes the prior day's texts with its rows and audio). A transcript that cannot be supplied for an episode is named in the push result the way a missing track is named in v312 — counted, never silently absent.
  5. **The read-along view (app half).** Each track card on the Prayers tab gains a **"Read"** affordance opening the episode's text in a reading view: the full text at the app's reading size (the v312 font floor governs), scrollable, with play/pause reachable from the same view so a listener can read along or pray in silence. No following/highlighting of the spoken position (that is a timing-sync feature and is out of scope). A track with no text shows the plain not-available line in place of the view, named as in v312's missing-track shape.
- **Out of scope:** backfilling transcripts for already-published episodes (the feed's standing items stay untouched) · timed/caption formats (SRT/VTT) and word highlighting · transcripts on Spotify playlist surfaces or any other platform surface beyond the feed tag · any change to the scripts' content or the production text pipeline · the public website (orapronobis.media pages) — the text publishes through the feed tag and the file host only · Pam access (none exists; none is added).
- **Affected surfaces:** the nightly production run (pass 2 + its report) · the public feed document (namespace + new items' tags) · the public audio host (new text files) · — after v312 — the app Worker (push + payload), the app store, and the app client (one new view).
- **Review placement:** **BEFORE the trunk landing for the app half** (it extends v312's storage and read path — shared-core, the v312 rule). The public-feed half is verified at its first live publish (the nightly run's read-back field) — its Review evidence is the feed itself, read back after the first tagged drop.

### Concerns and Information Needs
