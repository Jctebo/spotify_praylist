# v558 — Microphone list cleanup — one row per real input, friendly names

- **Registry:** DevOps Board, ora-pro-nobis, row 1508 · version v558 · slug v558-microphone-list-cleanup
- **Intake:** Goals Board task 1062 (Muse Jobs, goal 16)
- **Status:** PLAN — production-defect fix-forward (standing v553/v556 precedent; no scope package — the approved v557 shape is the spec)

## 1 · Fix brief

- **Field evidence:** John, main chat, 2026-11-20 15:32 CT — screenshot from his Galaxy Z Fold 8 (SM-F971U1), APK 1.0.47 + v557 web live. The record card's microphone list reads: 1. ✓ System default — "Android chooses the input." · 2. SM-F971U1 — "This device's built-in microphone." · 3. Bluetooth microphone — "Bluetooth microphone · Records at call quality." (his Ray-Ban Meta glasses route, under a generic type label) · 4. SM-F971U1 — (no sub-line) · 5. SM-F971U1 — "This device's built-in microphone." · 6. SM-F971U1 — (no sub-line). John's words: "Why so many mic?"
- **The spec it is measured against:** v557 as approved (Q4 A) and planned (release doc v557, Plan D4): the list shows friendly names — built-in → "Phone microphone"; one row per real input. The shipped list shows the phone's model number four times instead. This fix restores the approved shape; it changes nothing John approved.
- **Cause, proven in the shipped code (GitHub main ba08a735 + android main 78aceb03):** the shell bridge (`OraDayBridgePlugin.listAudioInputs`) returns `AudioManager.getDevices(GET_DEVICES_INPUTS)` raw — one entry per `AudioDeviceInfo`. Android enumerates the one physical built-in microphone as several entries (different ids/types), all carrying the product name "SM-F971U1"; the bridge's `micProductName` returns that raw product name whenever it is non-blank, so the "Phone microphone" fallback never fires on this phone. Two of the four entries carry kind "builtin" (the sub-line stands), two carry an unmapped type → kind "other" (no sub-line) — the screenshot exactly. The client's `homilyMicListHtml()` renders one row per raw entry, verbatim; no grouping exists on either side. The Bluetooth entry's generic label is the bridge's standing permission gate (product name only when BLUETOOTH_CONNECT stands granted) — v557 D3 behavior, not part of this defect.
- **Fix shape (determined):** one row per real input source — System default first (unchanged) · ONE "Phone microphone" row merging every built-in mic entry · one row per distinct Bluetooth device, named by the device's own product name when the system provides a non-generic one, else "Bluetooth microphone" · one row per distinct wired/USB device under its name when present. The remembered pick (`opn-homily-mic-v557`) still resolves after the merge; steering behavior unchanged.

## 2 · Plan

- **D1 · Where the dedupe lives: the client. The bridge does not change; no APK.** Evidence: (1) the bridge contract already carries everything the grouping needs — `{ key, name, kind }` per raw entry — and the raw keys ARE the steering contract: `applyAudioInput` resolves a pick by exact key match against the same raw enumeration, so a client-side merge leaves steering byte-identical in behavior. (2) The defect is presentation — one physical source rendered as several rows — and list rendering is the client's seat (`homilyMicListHtml`). (3) The standing harness pattern (harness-v557) stubs the bridge and drives the real client: a client fix is provable end-to-end against John's exact list shape, while a Kotlin grouping could not be exercised by that harness at all. (4) No install burden: the fix reaches John with the web deploy alone; APK 1.0.47 stands as the shell. The bridge's raw enumeration stays available and honest underneath — grouping is a view rule, recorded here.
- **D2 · The grouping rule (new `homilyMicRows()` in client.ts, consumed by `homilyMicListHtml`):** rows build from the raw bridge list in first-appearance order. (a) PHONE GROUP: every entry with kind "builtin", plus every entry with kind "other" whose name equals a built-in entry's name (the phone's own mic exposed under an unmapped type — on John's phone both carry "SM-F971U1"). One row: name "Phone microphone", kind "builtin" (the sub-line "This device's built-in microphone." stands), apply key = the first true "builtin" entry's key (else the first grouped entry's key), member keys = every grouped raw key. Built-ins merge regardless of name (the kind rule); the name-match rule only admits "other"-kind entries that carry a built-in entry's exact name, so no foreign device can be swept in. (b) EVERY OTHER ENTRY groups by its raw key — the bridge already keys one Bluetooth device identically across its SCO/BLE faces (`bt:<address>`), so same-device duplicates merge; distinct devices (distinct keys) stand as distinct rows, each under its returned name and kind note (Bluetooth keeps "Bluetooth microphone · Records at call quality."; a Bluetooth device whose own product name the bridge provides renders under that name — the bridge's standing gate decides, unchanged). Wired/USB likewise. (c) "System default" stands first, unchanged, rendered outside the grouping.
- **D3 · The remembered pick survives (migration in code, no storage rewrite):** a display row counts as the current pick when the pick's key equals the row's apply key OR any of its member keys — a pick stored against any merged built-in entry resolves to the Phone microphone row; a Bluetooth pick resolves by its unchanged key. On list load, when the pick matches a row through a member key, or its stored name differs from the matched row's display name, the stored pick is re-saved in place as `{ key: <row apply key>, name: <row name> }` — the value migrates forward; the store key `opn-homily-mic-v557` does not change. If the list is never opened, nothing breaks: the stored raw key still steers exactly, because `applyAudioInput` resolves raw keys. A pick matching no row keeps v557 behavior whole: the "Not connected" row stands in the list and Record falls back per Q5 A with its notice.
- **D4 · Non-changes (guardrail):** capture (`getUserMedia`, MediaRecorder, the IndexedDB chunk store), the apply/clear steering calls and their order, the Q5 A fallback and its notice text, the recording-state microphone line, and the bridge (Kotlin, manifest, build.gradle) are untouched. `homilyMicPrepare` still passes the stored key; after a list-open migration that key is the canonical apply key — both forms resolve in the bridge by exact match, so record-start behavior is identical. index.ts byte-identical; ui.ts untouched (the merged rows reuse the standing list dress); NO migration.
- **D5 · Harness (app/tests/harness-v558.mjs, harness-v557's pattern — stubbed bridge, real client):** the stub returns John's raw list shape: two "builtin" entries named SM-F971U1 (distinct `t<type>:SM-F971U1` keys), two "other" entries named SM-F971U1, one Bluetooth entry (`bt:` key, name "Bluetooth microphone"). Legs: L1 the open list renders exactly 3 rows — System default · Phone microphone · Bluetooth microphone — with the built-in and call-quality sub-lines standing. L2 a named Bluetooth device (product name returned) renders under its own name. L3 a pick stored against the SECOND built-in raw key marks the Phone microphone row current (no "Not connected" row) and, after the list loads, the stored value reads back migrated to the canonical apply key + "Phone microphone". L4 steering unchanged: tapping the Phone row stores the canonical key and Record calls `applyAudioInput` with it before capture; a Bluetooth pick applies its own key; stop calls `clearAudioInput`. L5 the Q5 A leg stands: a pick for an absent device shows "Not connected", apply falls back, the notice stands, capture proceeds. L6 bridge-absent world unchanged (row reads System default, no Change act, v551-parity record). Run on the build tree and a clean checkout of the committed tree; counts must match.
