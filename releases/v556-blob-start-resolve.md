## 1 · Scope

- **Field reports:** John, Ora Pro Nobis thread — 2026-11-20 13:12 CT, verbatim: "The ai signal stuff doesn't work"; split answer 13:14 CT: "I tap an episode and it does not play" (the series stands, the episode list stands, playback fails on tap). 13:16 CT, with screenshot: the first homily recorded in the v551 field test stands in the Homilies list ("Homily — Friday, November 20, 2026", 0:25) and its playback fails — the mini player reads "Couldn't play — unresolved-start".
- **Diagnosis (read-only, 2026-11-20, code at GitHub main 8b4177e; delivered to the Ora thread; recorded in full in intakes 1057 + 1058):** ONE defect class across both surfaces. On the one-engine shell a playback start must resolve through the native contract (`nativeContractFor` → `nativeContractItem` → `oraSnapshotTrack`); an unresolvable start no longer falls back to the WebView element — `nativeStartFailed` refuses it by name via `refuseNativeStart` (v472 Step 5). Both failing surfaces are starts whose playable source is a WebView-local blob URL, which the contract cannot carry.
  - **Homily (1058), proven end to end:** the take is healthy in IndexedDB; the entry and its 0:25 read from the localStorage index metadata, never the blob. At play, `homilyDescFor` builds kind `'homily'` with the minted blob URL — and `oraSnapshotTrack` returns null for kind `'homily'` by design (v551 P7.4: a homily never enters the native snapshot), so `nativeContractItem` yields null, the contract refuses, and `nativeResolveStart` — whose only arms are kind `'podcast'` and day-external slots — falls through to `nativeStartFailed(desc, 'unresolved-start')`: the exact string in John's screenshot. In a browser or the old shell the same path runs `elementStartTail` and plays; v551's exclusion assumed that fallback, and the one-engine refusal removed it.
  - **AI Signal (1057), server side fully healthy:** Settings row `the-ai-signal` stands with enabled = 1; the own-episode store carries 11 episodes, all `audio_state='present'`, newest 2026-11-20 (495 s · 3,965,605 B, matching the produced episode byte for byte); the R2 objects answer 200 · audio/mpeg. The failure is today's entry only: `podOwnDesc` swaps today's URL to the device-local blob minted by `aiSettleSwap` (the normal state on John's phone) but the descriptor carries no `enclosureUrl`, so `oraSnapshotTrack`'s own-episode branch finds no address and falls to its synthesis — `/api/player/audio/<date>/the-ai-signal-2026-11-20`, keyed on the composite entry key, which is not a store id (the store id is `the-ai-signal`) — the route 404s and the tap does not play. Older entries carry no swap and resolve correctly.
- **Scope of the fix:** client.ts only — one resolver arm (homily) + one descriptor field (AI Signal). No server change, no migration, no APK change. Nothing else moves: the v551 homily build, the AI Signal production line, the offline swap, and every other start path stand as shipped.

Reasons:
  - The alternative — a same-origin route serving the take that the contract can carry — cannot stand under the v551 decided set (Q1 C, Local only): the take never leaves the device, the Worker cannot read the device's IndexedDB, and the native engine fetches the contract's mediaUri outside the page — a service-worker or blob address is exactly as WebView-local as the blob itself. The route shape would require the audio to leave the device. Rejected as unsafe against the decided set.
  - The element tail is the take's only possible engine in every pair: P7.4 excludes a homily from the native snapshot by design (its blob URL is meaningless off the page), so v472 Step 5's refusal — written to stop dual-engine starts for tracks the native engine CAN carry — has no native engine to protect here. The arm is one branch, kind-keyed, running the standing `elementStartTail` — no second copy of the start tail. startDesc's bookkeeping (pending start · current · media session) has already run at the funnel, and the element's play event clears the pending start through the standing listener, exactly as in the old pair.
