### John's decision (settled — not re-opened by this section)

John, Ora Pro Nobis thread, 2026-11-08 16:53 CT, chose **option (a)** from the player diagnosis, with three standing rules for the app:

1. **Storage:** the nightly run pushes the day's episode entries into the app's own D1 at publish time; the player reads D1 only; the live-RSS read path comes out. (The public feed stays the podcast's feed; its staleness is a separate matter and is not this release's problem to fix.)
2. **One-day retention:** the app store keeps one day only — each day's push replaces the prior day's episode entries and player audio (episode index rows + app-store audio for episodes and intentions). No archive in the app.
3. **Today-centered:** the app is organized around today's prayer — the Prayers tab opens on today, blocks in order; no archive or back-catalog browsing as a goal.
4. **Full playback:** Play All for the whole day and Play All per block · a continuous queue in block order · background playback (screen locked / app backgrounded) · lock-screen / media-session controls (play / pause / next / previous / seek) · autoplay-next · resume where sensible. A missing track is named plainly in place, never silently dropped from the count.

**Fold ruling:** standalone. This release stands as its own row by John's direction at registration; it does not fold into any other release, and no other release folds into it.

### Diagnosis of record — and how option (a) cures it

Verified 2026-11-08 (the v305 player report): the feed address the app reads, `https://jctebo.github.io/spotify_praylist/podcast.xml` (hard-coded as `FEED_DEFAULT` in app/worker/src/index.ts, overridable only by a harness env var), 301-redirects to `orapronobis.media/podcast.xml`, whose newest item at diagnosis time was **Nov 5, 2026** — zero current episodes at the address the app reads, so the player showed the day's prayers unavailable or absent.

Scope-pass evidence gathered 2026-11-08 (this pass, live fetch): the redirect target currently carries 2,804 items / 2,886 pubDates spanning 2026-05-02 → 2026-11-10, ≈ 2.0 MB of XML. That does not change the decision, and it sharpens the second half of the diagnosis: the app's playback depends on an external file it neither controls nor verifies, and even on a good day the read path must download and regex-parse ~2 MB at read time to find one day.

The fragile read path, verified in code (app/worker/src/index.ts, `feedEpisodes` + `playerDayPayload`):

- At request time the Worker fetches the feed, splits items with a regex, and extracts title / enclosure / pubDate with three more regexes. An item missing any one of the three is silently skipped.
- Matching is by string: the Chicago date derived from pubDate must equal the requested date, and the episode's title prefix (title minus a trailing " - Month D, YYYY") must equal either a `player_sources` title or a prayer item's name. Anything unmatched falls into an "unmapped" bucket rendered at the bottom as "From today's podcast."
- The mapping is nearly empty: production D1 holds **7 `player_sources` rows — 6 playlist (Spotify link) rows and exactly 1 rss row** ("Morning Prayer"). Every other episode track depends on the name-matching fallback against the 35 prayer items.
- A module-level cache holds the parsed result for **300,000 ms (5 minutes) — including the empty result**: a failed or stale fetch caches an empty day for five minutes.
- A fetch failure is swallowed (`catch {}`): the player renders tracks `available: false` with nothing naming the cause.

**How (a) cures both halves:** the day's episodes become rows the nightly run writes into the app's own D1 at the one moment their identity is certain — publish time, from the run's own manifest. The player then reads only its own store: no external fetch in the read path (the stale-address failure cannot occur), no parse, no prefix matching, no empty-result cache (the fragility cannot occur). What the run published is what the player shows, and a day the run did not publish reads as a named missing day, not as a silently empty one.

### Discovery findings (verified)

1. **The player today.** `GET /api/player/day?date=` builds the payload per request from three sources: `player_sources` (D1), the live feed (above), and `prayer_audio` (the Intentions segments). Blocks stand in the fixed six-block order (Morning · Midmorning · Midday · Afternoon · Evening · Night). Each block renders its matched tracks plus an Intentions card; the Intentions card is the one surface already served from the app's own store (segment-file route only, no Spotify link — Amendment 9's hard rule, preserved by this release).
2. **The client player is minimal.** One `<audio>` element in the shell (app/worker/src/ui.ts), `preload="none"`. Per-track play/pause; a per-block queue (`playQueue`) that chains on the `ended` event. There is **no Play All for the whole day**, **no Media Session API anywhere in the app** (zero hits for `mediaSession` / `MediaMetadata` / `setActionHandler` across app/), no seek or next/previous controls, no playback-position memory (no resume), and the per-block queue is built from *available tracks only* — an unavailable track is dropped from the queue silently even though its card is shown. The app also opens on the **Intentions tab** (`setTab('intentions')` at boot), and the Prayers screen carries day navigation (prev / next / date picker) — back-catalog browsing, which the today-centered rule retires.
3. **The app holds no episode data today.** Production D1 tables: the six prayer tables, `player_sources`, `prayer_audio`, the examination and confession tables. There is no episode-shaped table. `prayer_audio` holds exactly **one date — 2026-11-08, all 6 blocks** (the v305 first push). No episode index rows and no episode audio exist in the app store.
4. **The publish point.** The nightly run (job `ora-pro-nobis-nightly-run`, daily 00:00 CT, target = run date + 2) finalizes the day at its step 4, `runner/pass2_build.py --publish`: it renders, assembles, brands, loudnorms, verifies, uploads MP3 + sidecar JSON to the podcast R2 with manifest reconciliation, grafts the items onto the live feed, commits docs/podcast.xml, verifies the live feed, and flips the ledger to published — the ledger flip is last, and the step-4 timeout rule's `--reconcile` mode completes only the missing tail (ledger flip still last). The run's own record (report.json) carries, per episode: episode_id, title, kind, the built MP3 file name, duration seconds, and bytes. A real day: **2026-11-10 — 16 episodes, all built, 4,093.5 s total**. The built MP3s stand on disk in the run directory at publish time.
5. **The door pattern for the push already exists.** The app's agent door (Bearer AGENT_TOKEN, `~/workspace/.tools/prayer_door.py`) already accepts the nightly Intentions audio push: `POST /api/agent/prayer/audio` with raw MP3 bytes and X-Prayer-Date / X-Prayer-Block headers, writing R2 under `segments/<date>/<block>.mp3` and upserting `prayer_audio`. The episode push follows this exact pattern — it is an extension of a proven route shape, not a new mechanism.
6. **Audio surfaces.** Episode audio today lives only on the podcast's hosts (the feed's enclosure URLs on the podcast R2 / Pages chain) — outside the app's control, which is the point of failure. The app's own R2 bucket (`ora-pro-nobis-audio`) holds only the Intentions segments. Under this release the episode audio joins the app bucket, under the one-day rule.
7. **Constraints that stand:** John-only at Cloudflare Access, no Pam path · the Intentions card keeps its segment-file route and never carries a Spotify link · no checklist / no done state in Prayers · examination data has no agent-door route (unchanged — the push touches player data only) · the public podcast feed, RSS/Pages endpoints, R2 audio host, and Spotify IDs are untouched by this release · the GoalPost prayer module and its fallback stand untouched.

After a completed push, the app store holds exactly one date across episode rows, episode audio, and segment audio. A push that fails partway leaves the prior day intact and named as the stored day — replacement completes as one verified step (read-back of row count and per-track audio presence) or not at all; the nightly report names which date the app holds.

Its inputs are the run's own report/manifest: the episode list (id, title, duration, bytes), the built MP3 files, and the block resolution. It also carries the v299 rule's shape: idempotent — re-running the push for the same date replaces the same day and changes nothing else. The closing report gains a named field: the app push result (date pushed · episode count · audio verified per track · the stored date after the push).

The feed fetch, the regex parse, the prefix/date matching, the 5-minute cache, and the `FEED_DEFAULT` constant come out. `player_sources` playlist rows remain only as the blocks' "Open in Spotify" links (presentation data, no longer a playback source); the single rss mapping row is retired with the read path. A request for any date other than the stored day returns the stored day named as such — there is no other day to serve.

     - **Play All (whole day):** one control at the top of the Prayers tab; plays every available track in the day's order (block order, then push order inside the block, then the unblocked group).
     - **Play All per block:** the per-block queue control that exists today, kept and rebuilt on the stored order.
     - **Continuous queue:** one queue model for both Play All shapes; `ended` advances to the next available track automatically (autoplay-next, below); the queue is visible in place — the currently playing track is marked on its card, as today.
     - **Autoplay-next:** on track end, the next track starts without a tap, through the whole queue, including across block boundaries in a whole-day queue.
     - **Background playback:** playback continues with the screen locked and with the app backgrounded. The audio element and queue live outside the tab view (the shell-level `<audio>` element already stands outside the view; the queue state moves with it), and switching tabs never stops or resets playback.

Next/previous move within the active queue.

### Build elements

**E1 — Episode index storage: migration 0007 (app D1).**
- New file `app/migrations/0007_player_episodes.sql` (0006 is the last standing migration; 0007 is next and is this release's only migration).
- Table `player_episodes`: `date TEXT NOT NULL` · `episode_id TEXT NOT NULL` (the run manifest's own id, e.g. `daily-rosary`) · `title TEXT NOT NULL` (the full manifest title) · `block TEXT NOT NULL` — one of the six block names, or the explicit unblocked marker **`'unblocked'`** (§1's explicit-marker rule) · `sort INTEGER NOT NULL` (position within the whole day, assigned at push time; block order then sort renders the day) · `duration_s REAL NOT NULL DEFAULT 0` · `r2_key TEXT NOT NULL DEFAULT ''` (empty only on a missing row) · `size_bytes INTEGER NOT NULL DEFAULT 0` · `audio_state TEXT NOT NULL` — `'present'` or `'missing'` · `pushed_at TEXT NOT NULL`. PRIMARY KEY `(date, episode_id)`; INDEX on `(date, sort)`.
- Table `player_day` (the stored-day singleton): `id INTEGER PRIMARY KEY CHECK (id = 1)` · `date TEXT NOT NULL` · `episode_count INTEGER NOT NULL` · `pushed_at TEXT NOT NULL`. The commit step (E2) writes this row last inside its D1 batch — it is the one explicit answer to "which day does the app hold," and the read path (E3) keys off it, never off a MAX() guess.
- One data retirement inside the same migration: `DELETE FROM player_sources WHERE source_kind = 'rss';` — the single rss mapping row retires with the read path (§1 item 5). The six playlist rows stand untouched (presentation "Open in Spotify" data).
- No other table changes. `prayer_audio` stands exactly as migration 0002 built it.

**E2 — The door push surface (app Worker, agent door — extension of the proven prayer-audio pattern).**
Three agent routes, Bearer AGENT_TOKEN, mirroring `POST /api/agent/prayer/audio`'s header shape (`app/worker/src/index.ts` lines 413–432 is the template):
1. `POST /api/agent/player/episodes/audio` — headers `X-Episode-Date` (YYYY-MM-DD) + `X-Episode-Id`; raw MP3 body; writes R2 key **`episodes/<date>/<episode_id>.mp3`** (content-type `audio/mpeg`) and returns `{ok, date, episodeId, size}`. **It writes no D1 row** — staging only, so a push that fails partway leaves the prior stored day fully intact (§1 item 3's failure rule).
2. `POST /api/agent/player/day` — the **replace-day commit**. JSON body `{date, episodes: [{episode_id, title, block, sort, duration_s, size_bytes, audio_state}]}` (block already resolved by the pusher, E8). The handler, in order: (i) for every `audio_state='present'` entry, verify the staged R2 object exists and its size equals the manifest's `size_bytes` — any mismatch aborts the commit with a named 409 and writes nothing; (ii) one D1 batch: `DELETE FROM player_episodes WHERE date <> ?` · upsert the day's rows · `DELETE FROM prayer_audio WHERE date <> ?` · upsert the `player_day` singleton; (iii) R2 sweep after the batch: delete every object under `episodes/` whose key date is not D, and every `segments/<other-date>/` object (the segment keys of the deleted `prayer_audio` rows); (iv) read back and return `{ok, storedDate, rowCount, perTrack: [{episode_id, audio: 'verified'|'missing'}], segmentsHeld: [blocks for D]}`. Idempotent: re-committing the same date with the same manifest changes nothing (§1's v299 shape).
3. `GET /api/agent/player/stored-day` — the read-back the nightly report consumes: `{storedDate, episodeCount, tracksPresent, tracksMissing, segmentBlocks}` from `player_day` + `player_episodes` + `prayer_audio`.
- **Missing rows:** a manifest entry the run could not build arrives with `audio_state='missing'`, `r2_key=''`, `size_bytes=0`; the commit accepts it without an R2 check. That is the only door through which a counted-but-unplayable track enters the store (§1 item 7's missing-track rule, criterion 5).

The measured need is real: the Daily Rosary runs 19,738,317 B (2026-11-09) to 19,926,237 B (2026-11-10).
