## 1 · Scope

- One file: the on-device personal-data file v568 stands up, carried as a versioned JSON envelope — format `orapronobis-personal-data`, formatVersion 1, exported-at stamp, per-class sections (intentions · Conscience · profiles · config · favorites and starred tracks), and a per-class counts header as the migration guard (v567 Plan §4/§6).
- In-app flow, plain language: Settings → **My data on this phone** → **Save a copy** (share sheet / Files / Drive) · **Restore from a copy** (file picker). Restore is whole-file; a pre-restore local snapshot is kept on the device for undo. A restore refuses a newer formatVersion with a plain message.
- PIN material (pin_state hashes, salts, recovery) does NOT travel in the file — a restore sets a fresh PIN on the device. The v568 layer already keeps PIN state in its own on-device store outside the sections; no export path reads it.
- John's import file: generated from his existing private data in the app D1 (database 3a177d55-7baa-424c-9c4d-0d60cd9fe332), READ-ONLY generation — his private app and its data stay untouched — in this same format, per the class mapping in the v567 Plan document, and delivered to him as a file to import into the newly shaped app.
- Web shape: the My data surface on web renders the app-pointer card (personal data lives in the app; the web build never stores it) — never a dead end, never an account ask. Private shape: the surface does not stand; John's app is untouched.

The counts header is additive metadata: the v568 loader ignores unknown top-level fields, and a v570 restore cross-checks counts before adopting.

Commits f921f9d5 + 3c0a4495 on release/v570.

## 4. Review

- Envelope discipline re-read against the v568 layer: Save serializes a clone (the stored document is never stamped with exportedAt/counts); the validator refuses before any state changes (format, newer version, count mismatch — the standing document byte-identical after each refusal, L4–L6); the snapshot is written before adoption and consumed by undo (L7).
- PIN census: the export/import code slice contains no read of the PIN store (S5, static), and with a PIN set on the device the export string carries none of the record's hash/salt material and no PIN field (L2, dynamic, against the four secret fields explicitly — a blanket value census false-fires on the record's plain createdAt timestamp, which the export's own exportedAt can share to the millisecond).
