## Task

Research how to implement this clarified scope:

- ordered daily OneDrive `Playlist Audio` exports using `<FolderName> - <Order> - <EntryName>.<ext>`
- managed daily truncation and rebuild of playlist-audio outputs
- page-content sync only for prayers with reliable text sources
- no regression to Morning Prayer's current working page-body behavior

## Executive Summary

- The repo already has the scheduling, audio generation, and OneDrive upload plumbing needed for this enhancement.
- Spotify playlist order already comes from the top-level Opus Dei `Order` field in `jobs/playlist/refresh_playlist.py`.
- OneDrive page-audio export already exists in `jobs/notion/generate_page_audio.py`, but filenames are still title-based and there is no managed-folder truncation step.
- Page-content sync already exists, but it is a mix of destructive full-page replacement, builder-specific `page_content`, rich-text property sync, and audio-only cases.
- Morning Prayer is already a good path and should be preserved. Its current runtime reads and rebuilds the intended page structure instead of relying on a generic page-content writer.
- The real implementation split is:
  - shared ordered export metadata for OneDrive
  - managed daily truncation for exported playlist-audio folders
  - mixed text-sync behavior that preserves established full-page writers and adds a safer managed-section path only where new page-content coverage is needed

## Current Architecture Findings

### 1. Ordered top-level prayer sequencing already exists

`build_queue_for_playlist_from_notion(...)` in `jobs/playlist/refresh_playlist.py` already:

- loads Opus Dei rows
- filters eligible Spotify rows
- reads top-level `Order`
- sorts by `Order`, then title
- resolves queue items in that order

This is the correct existing source for top-level playlist order.

### 2. OneDrive page-audio export already exists, but naming is title-based

`page_audio_output_library_paths(...)` in `jobs/notion/generate_page_audio.py` currently exports as:

- `<Playlist Audio root>/<Output Folder>/<Title>.mp3`
- `<Playlist Audio root>/<Output Folder>/<Title>.json`

The exporter already knows how to route by folder and write a colocated sidecar, but it does not yet include top-level `Order` in the stem.

### 3. Daily OneDrive sync already exists

`.github/workflows/daily_novena_prayer.yml` already:

- prefetches the OneDrive `Playlist Audio` library locally
- runs `jobs/notion/generate_page_audio.py`
- uploads the rebuilt library back to OneDrive with `rclone sync`

This means the missing work is export contract and cleanup behavior, not new infrastructure.

### 4. Morning Prayer is already a preservation case

The repo contains both a legacy Morning Prayer builder and the active two-list Opus Dei path, but the current runtime behavior already treats Morning Prayer as a strongly validated page-content writer.

Important behavior in `build_morning_prayer_plan(...)` and the newer two-list tests:

- Morning Prayer reads the live page structure
- it preserves the intended block grouping
- it skips old autogenerated novena blocks
- it reinserts refreshed novena content through the existing contract
- it fails closed when the canonical Morning Prayer fragment contract is incomplete

This is not a page that should be pushed into a generic managed-section writer.

### 5. Page-content sync has two distinct behavior classes

The repo currently mixes:

- established full-page writers that already return `page_content` and structured blocks
- text-bearing plans that can be normalized into `page_content` from plain text, but do not have a page-specific block-preservation template

That split matters because the enhancement does not need one global page-content strategy. It needs a mixed strategy.

### 6. Marker-based managed sections already exist elsewhere in the repo

`jobs/novena/generate_daily_novena_prayer.py` already has marker-based helpers that:

- identify autogenerated sections by marker text
- remove only prior generated sections
- preserve unrelated manual content

That pattern is the safest local precedent for adding non-destructive page-content sync to prayer families that need new page-body coverage without changing established full-page writers.

## Clarified Implementation Direction

### Ordered OneDrive Export

Use the top-level Opus Dei `Order` contract that already drives Spotify queue sorting, and apply it to page-audio export stems:

- folder routing: `Output Folder` first, fallback to `Playlist`
- filename stem: `<FolderName> - <Order> - <EntryName>`
- matching `.json` sidecar with the same stem

### Managed Daily Truncation

Treat the page-audio workflow's touched `Playlist Audio/<FolderName>/` directories as automation-managed for exported audio artifacts:

- compute the eligible export folders before rendering
- clear prior managed audio and JSON artifacts locally
- keep using `rclone sync` so stale remote files disappear after upload

### Mixed Text-Sync Behavior

Use two text-sync behaviors instead of one:

1. Preserve existing correct full-page writers
2. Use a managed autogenerated section only when text is being promoted into `page_content` from a reliable but more generic source

This fits the user direction:

- Morning Prayer stays on its current working template path
- already-correct structured page-content writers stay intact
- newly promoted page-content paths gain manual-block safety

## Risks That Planning And Implementation Must Respect

### Morning Prayer regression risk

If implementation forces Morning Prayer into a generic page-content strategy, it risks breaking its current block grouping, placeholder behavior, or novena insertion flow.

### Stale remote filename risk

If managed local cleanup does not happen before the existing OneDrive sync, renamed files can linger remotely.

### Duplicate ordered-stem risk

If two rows resolve to the same sanitized folder + order + title stem, the exporter can overwrite files silently unless collisions are validated first.

### False page-content completeness risk

If a prayer is marked for `page_content` but only resolves source audio with no reliable text, the run can appear successful while still missing page-body text.

## Recommendation For Implementation

Implement the enhancement in this order:

1. update the enhancement docs so scope, research, and plan are consistent
2. add a shared top-level order normalization contract for queueing and export naming
3. add managed local truncation for playlist-audio export folders
4. preserve Morning Prayer and other established full-page writers
5. add a managed autogenerated-section path only for text being newly promoted into `page_content`
6. verify with targeted tests focused on ordering, truncation, text coverage, and Morning Prayer non-regression
