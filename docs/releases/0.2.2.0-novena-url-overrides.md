# Release 0.2.2.0 - Novena URL Override Contracts

Date: 2026-04-29
Status: Shipped
Branch: enhancement/novena-url-overrides
Depends On: 0.2.1.0

## Scope

### Problem
- Maintainers need a local utility that can turn either one novena page or the whole supported novena catalog into valid override contract drafts without manually copying details out of the site.
- The current novena authoring flow can create feast-day contracts, but it still expects the author to know the canonical identifiers, feast date, saint name, and file placement ahead of time.
- That manual step is slow and error-prone when the source of truth is already published on a novena website.
- Why now: there is already a working novena contract system, so the missing wedge is a fast import path from either a known URL or a full-site batch into the existing JSON contract format.

### Audience
- Primary user: the maintainer authoring or updating novena contracts locally.
- Secondary stakeholders: future maintainers who need a predictable way to import a new novena page without reverse-engineering the site every time.
- Secondary stakeholders: readers of the repo who benefit from fewer transcription mistakes in published novena metadata.

### Current Status Quo
- Contract authors currently create novena JSON by hand or by using the existing feast-contract helper with explicit saint and feast inputs.
- A real novena page has to be inspected manually to recover the values that should go into the contract.
- That workflow is acceptable for one-off edits, but it becomes tedious as soon as the source pages already contain the needed metadata.
- The result is extra copy/paste work and a higher chance of mismatched names, dates, or slugs.

### Goal
- Accept a novena page URL in `single` mode or a site-wide batch request in `bulk` mode and generate validated override contract drafts from it.
- Reuse the existing novena contract schema and file layout rather than inventing a new contract type.
- Make the output deterministic enough that the same page URL produces the same contract shape on reruns.
- Success criteria: a supported URL can be turned into a valid JSON contract with the right canonical identifiers and a sensible output path, while bulk mode can walk the supported site index and produce the same kind of drafts for every supported page it finds.
- Success criteria: any page that cannot be confidently parsed should be flagged, marked disabled so it does not run, and included in a readable report.
- Follow-on goal: simplify highly repetitive novena contracts before the OpenAI rewrite step so the importer sees a smaller, more structured representation instead of nine copies of the same prayer block.
- Follow-on goal: treat named prayer references such as `Our Father`, `Hail Mary`, and `Glory Be` as canonical prayer tokens, then expand them into full spoken text before TTS normalization instead of relying on the model to infer them from shorthand alone.

### Constraints
- This should stay a local authoring utility, not a runtime novena pipeline change.
- The first version should favor one trusted source domain over a generic web scraper.
- The utility should fail closed when the page cannot be parsed into a clear saint/feast identity.
- Existing novena publishing, RSS, and audio generation behavior should remain unchanged.
- The implementation should fit the current contract shape and validation rules already used in `jobs/novena_contracts/`.
- Bulk mode should stay scoped to the supported novena site and its index/listing pages, not become a general-purpose crawler.
- Single mode and bulk mode should share the same parser, validation rules, and output contract shape.
- Failed or uncertain imports should be represented in a way that prevents accidental runtime execution, likely through an `enabled: false` marker or equivalent disabled-state metadata that the planner verifies against the actual schema.
- Bulk mode should emit a human-readable report of successes, skips, and failures.
- Because the schema currently lacks a top-level `enabled`, adding one will require updating the dataclass, serializer, validator, and any reader that assumes the current shape is complete.

### Narrow Wedge
- Add a `single` mode that takes one URL and a `bulk` mode that walks the supported site index and drafts every supported novena page it can find.
- Start with one source domain, using `https://catholicnovenaapp.com` as the reference case.
- Extract only the minimum contract data needed to create a valid override draft: canonical id, display name, feast date or equivalent resolved identifier, and output filename.
- Keep manual flags available for anything the page cannot infer cleanly, and keep the same parsing logic in both modes.
- Add a disabled-or-flagged path for uncertain entries so they are visible in the report but cannot run accidentally.
- Add a compaction pass for repetitive novenas that stores one shared prayer body when the site repeats the same text every day, then rehydrates it into per-day sections for review and downstream TTS normalization.
- Add a prayer lexicon pass that resolves short prayer names into canonical spoken forms before the OpenAI prompt runs, so the model receives full prayer text rather than ambiguous shorthand.
- Preserve day-specific instructions and intentions when deduplicating, so compaction never erases actual novena-specific differences.

### Non-Goals
- Do not build a general-purpose crawler for every novena site.
- Do not change the novena runtime, resolver, RSS publisher, or audio pipeline.
- Do not introduce account sign-in, browser automation, or remote publishing.
- Do not attempt fuzzy matching across arbitrary saint names or feast dates in this first pass.
- Do not redesign the existing selector-family novena contract model.
- Do not promise that bulk mode will successfully parse every page on the site if a page is missing the metadata needed to make a valid contract.
- Do not use a generic web-wide crawl; bulk mode should stay inside the supported novena site.
- Do not silently drop unparseable pages; every failure should be visible in the report.

### Risks And Unknowns
- The source page may not expose a canonical feast date or saint identifier in a consistent machine-readable way.
- Different novena sites may use different naming conventions, so the utility may need a domain-specific extraction path rather than one universal parser.
- The best output shape is not yet fully settled: the helper may need to write a JSON file, print a dry-run payload, or both.
- The biggest question is whether the URL alone is enough to produce a trustworthy override contract, or whether the user will still need a small amount of manual metadata.
- Bulk mode adds a second failure surface: one bad page must not break the rest of the batch, so the error model needs to decide whether to stop, skip, or report partial success.
- The site index may not include every page in a format that is easy to scrape consistently, so bulk mode might need a curated starting list or a fallback discovery rule.
- The exact shape of the disabled marker needs to match the existing novena contract schema or be added without breaking validation.
- If repetitive days are compacted too aggressively, the importer could accidentally hide a day-specific petition or instruction that should remain visible to the maintainer.
- Prayer-name expansion has to stay faithful to the traditional wording, because a loose paraphrase would make the TTS output sound incorrect even if it is technically readable.

### Recommended Next Step
- Run `/research-astack` to inspect the supported source page structure, confirm which fields can be extracted reliably, and decide the smallest `single`-plus-`bulk` interface worth building first.

## Research
### Scope Baseline
- Build a local authoring utility with two input modes: `single` for one novena page URL, and `bulk` for the Catholic Novena App catalog page plus all parsable novena detail pages it links to.
- Keep both modes scoped to one source domain, `catholicnovenaapp.com`, because the catalog page and individual pages already expose the minimum facts needed for contract drafting.
- This is an authoring-time import path, not a runtime change to novena publishing or scheduling.

### Relevant Files
- `scripts/new_novena_contract.py` - existing manual contract-authoring CLI for explicit feast-day and selector-family payloads; it remains the handcrafted authoring path, not the URL importer entrypoint.
- `jobs/novena_contracts/contracts.py` - owns the current novena contract dataclasses, output-path normalization, and load/serialize behavior that the new utility must continue to satisfy.
- `jobs/novena_contracts/validators.py` - enforces contract shape, feast-vs-selector rules, template requirements, and filename normalization assumptions.
- `jobs/novena_contracts/resolver.py` - useful for understanding how the runtime maps canonical ids and feast metadata, especially where the helper needs a stable id or feast lookup.
- `tests/test_novena_contracts.py` - current coverage for the helper CLI and contract validation; the new URL path should extend this test surface.
- `requirements.txt` - currently includes `requests` but not `beautifulsoup4` or `lxml`, so HTML parsing has to use the stdlib or add a dependency deliberately.
- `contracts/novenas/feast-days/*.json` - the target file family for explicit override-style novena contracts.
- `jobs/novena/generate_daily_novena_prayer.py` - existing repo pattern for URL parsing and HTTP fetch behavior; not a direct dependency, but a good style reference for local URL handling.
- `jobs/novena_contracts/contracts.py` and `jobs/novena_contracts/validators.py` together show that the schema currently has no top-level `enabled` field; only `publishing.audio.enabled` and `publishing.rss.enabled` exist, and both are required to stay true.

### Current System Map
- `build_contract_payload()` in `scripts/new_novena_contract.py` constructs the novena JSON from CLI args, choosing either a selector family or a feast override shape.
- `resolve_romcal_identifier()` and `resolve_romcal_date()` already give the repo a canonical-name normalization path for saint and feast references.
- `validate_novena_contract()` fails closed when the contract is missing a saint/feast shape, a template, or valid publishing metadata.
- `_default_output_path()` already places explicit feast contracts under `contracts/novenas/feast-days/` and derives the filename from the normalized contract id.
- The Catholic Novena App catalog page at `https://catholicnovenaapp.com/list-of-all-novenas/` already exposes the full catalog by month, with each entry showing the novena title, `Starts:` line, and `Feast:` line.
- Individual novena pages such as `https://catholicnovenaapp.com/novenas/our-lady-of-fatima-novena/` and `https://catholicnovenaapp.com/novenas/sacred-heart-novena/` expose a consistent facts block with the page title, `Novena Starts`, `Feastday`, and the prayer body.
- Some pages map cleanly to fixed dates, while others use relative liturgical language like `10 days after Pentecost` or `Second Friday after Pentecost`.
- The page title and URL slug are not always the same shape, so URL slug alone is not a reliable canonical id source.
- Bulk discovery appears feasible from the catalog page alone, with detail-page fetching only needed for the contract payload.
- There is no current runtime field for disabling a novena contract at the top level, so any `enabled:false` behavior would be a schema addition rather than a reused toggle.

### Reuse Opportunities
- Reuse the existing CLI and contract validator instead of creating a second novena authoring entrypoint.
- Reuse the current `--dry-run`, `--output`, and `--force` behavior so URL import remains a thin front end over the same JSON contract generator.
- Reuse Romcal-based normalization for feast identifiers when the page maps to a known fixed or movable liturgical celebration.
- Reuse the current feast-day output folder and filename normalization so generated files stay consistent with the rest of the repo.
- Reuse `requests`-based fetch patterns already present elsewhere in the repo for page fetching.
- Reuse the catalog page as the bulk-mode source of truth instead of inventing a spider or maintaining a separate seed list.

- Another fixed-date example: `https://catholicnovenaapp.com/novenas/our-lady-of-peace-novena/`

- No official API was found in the repo or on the site snippets surfaced so far; the utility likely has to parse HTML content directly.
- The list page is the strongest bulk-mode anchor because it already enumerates the catalog in month sections with direct links to detail pages.

### Constraints
- The first pass should stay on one trusted domain and fail closed outside it.
- The helper cannot assume every page has a fixed month/day feast date; some pages use relative liturgical language like `10 days after Pentecost` or `Shrove Tuesday`.
- The helper must preserve the existing novena contract schema so downstream validation and release artifacts continue to work unchanged.
- URL parsing needs to tolerate title formats that vary between `Our Lady of ... Novena`, `Novena to the ...`, and `St. ... Novena`.
- The implementation should not require browser automation or any remote login.
- Bulk mode needs an explicit policy for partial failure: stop early, skip and report, or continue with warnings.
- The parser needs a deterministic ordering rule for bulk output so repeated runs write files in a stable order.

### Risks
- A page may have enough text to identify the saint but still not expose a stable feast date in a form the current contract schema can represent without extra mapping.
- Some pages use movable-feast phrasing, which may require Romcal lookup or a manual override flag instead of pure URL inference.
- The site structure may change, and there is no documented API to insulate the helper from HTML churn.
- URL slugs are not canonical identifiers by themselves, so a naive slug-to-id mapping could misname the output file or contract id.
- Bulk mode magnifies HTML drift risk because the catalog page and detail pages both become dependencies.
- Adding a new top-level disable flag creates a compatibility risk if any consumer assumes the current contract shape is final.

### Assumptions To Validate
- The Catholic Novena App page title plus the facts block are enough to determine the contract id for the first supported page family.
- The helper can derive either a fixed feast date or a Romcal identifier from the page facts without extra user input for the common case.
- A new dedicated URL-import CLI is the cleanest entrypoint for this utility rather than overloading the existing manual contract helper.
- A local HTTP fetch against the page is acceptable for this repo’s workflow and does not require a browser session.
- The catalog page is complete enough to drive bulk discovery for the supported site.
- Each catalog entry maps to exactly one detail page that can be fetched independently.
- Bulk mode can use the same extraction logic as single mode after discovery, without a second parser.
- If we add `enabled:false`, every current novena contract consumer will need to tolerate the new field without breaking existing shipped behavior.

### Unknowns
- Whether the first version should support only fixed-date novenas or also movable-feast novenas like Sacred Heart and Holy Face.
- Whether the helper should emit a draft file immediately, print a dry-run payload, or both.
- Whether the page facts are sufficiently consistent to make URL-only import reliable across the full Catholic Novena App catalog.
- Whether a small domain-specific parser is enough, or whether the utility needs manual fallback flags for title, saint, feast date, or Romcal id.
- Whether bulk mode should accumulate partial successes and failures in one report or stop at the first bad page.
- Whether bulk mode should write files directly, stage them for review, or support both behaviors.
- Whether the disabled/flagged state belongs inside the generated contract, in a sidecar report, or in both.
- Whether the top-level `enabled` marker should be treated as a soft authoring flag or a hard runtime exclusion gate once added.

### Recommended Direction
- Create a dedicated novena URL importer CLI with `single` and `bulk` modes that share one parsing and validation pipeline.
- Use the catalog page for bulk discovery, then fetch each linked detail page and generate the same feast-style contract shape used by single mode.
- Preserve manual override flags for ambiguous or movable-feast cases, and decide the bulk failure model before planning implementation.

## Plan
### Summary
- Build a dedicated novena URL importer with `single` and `bulk` modes instead of folding the new workflow into the existing feast-contract helper.
- Teach the novena contract schema about a top-level `enabled` flag so uncertain imports can be written as valid but disabled contracts.
- Keep the existing novena runtime unchanged except for honoring `enabled:false` as a hard skip at load/resolution time.
- Use Catholic Novena App as the only supported source domain for the first release, with the catalog page as the bulk discovery seed.
- Write a human-readable bulk report and a JSON sidecar so partial failures are visible without stopping the whole import run.

### What Already Exists
- `jobs/novena_contracts/contracts.py`, `jobs/novena_contracts/validators.py`, and `jobs/novena_contracts/resolver.py` already define the novena contract boundary, canonical id normalization, and active-window resolution.
- `contracts/novenas/feast-days/*.json` already matches the kind of single-feast contract file the importer should emit.
- `requests` is already available, and the Catholic Novena App pages expose stable title/facts HTML that can be parsed without browser automation or new dependencies.
- The repo already has an `artifacts/` tree for generated outputs, which is a sensible home for bulk reports.

### Architecture
- The importer is split into a reusable module and a thin CLI:
  - `jobs/novena_contracts/url_import.py` handles fetching, HTML parsing, confidence classification, contract construction, and report assembly.
  - `scripts/new_novena_url_contract.py` exposes `single` and `bulk` subcommands and wires the module to the filesystem.
- Output flow:

```text
single URL
  -> fetch detail page
  -> extract title + facts
  -> normalize id/date/feast type
  -> classify: enabled=true | enabled=false | hard fail
  -> validate contract
  -> write contract JSON
  -> append report row

bulk catalog URL
  -> fetch catalog page
  -> collect detail URLs in catalog order
  -> run the same single-page parser for each entry
  -> write per-page contract JSON
  -> write bulk report (.md + .json)
  -> exit non-zero only for hard failures
```

- Contract semantics:
  - `enabled:true` means the page parsed cleanly and the contract may run.
  - `enabled:false` means the page was structurally parseable but needs review, so it stays in the repo but is skipped by the runtime.
  - A hard failure means the page could not be turned into a valid contract at all, so only the report is written.
- Runtime semantics:
  - `load_novena_contracts()` loads both enabled and disabled contracts.
  - `resolve_active_novenas()` skips disabled contracts and does not let disabled explicit feast contracts suppress selector-family contracts.
- Parsing approach:
  - Use `requests`, `html.parser`, `re`, and `urllib.parse` only.
  - No new third-party dependency is needed for the first cut.

### UX And States
- Single mode:
  - Success: write one contract JSON under `contracts/novenas/feast-days/` and print a short summary.
  - Disabled: write the contract with `enabled:false`, write a report row, and exit with success unless a hard error also occurred.
  - Hard fail: write only the report row and return non-zero.
- Bulk mode:
  - Success: write every supported contract plus a report that shows what was written, disabled, skipped, or failed.
  - Partial success: continue past page-level failures, keep the good contracts, and include the failures in the report.
  - Hard failure: if the catalog page itself cannot be read or parsed, stop immediately and return non-zero.
- Generated artifacts:
  - Contracts land in `contracts/novenas/feast-days/`.
  - Bulk reports land in `artifacts/novena-url-overrides/` as both `bulk-report.md` and `bulk-report.json`.

### Failure Modes
- Catalog drift: if the list page layout changes, bulk discovery can miss pages or mis-order them.
- Partial parse: if a page is parseable but not trustworthy enough, the importer writes `enabled:false` and the report records why.
- Hard parse failure: if a page cannot be turned into a valid contract at all, the importer skips writing a contract and records a failure row.
- Runtime skip regression: if disabled contracts are not filtered in the resolver, the novena pipeline could still publish them accidentally.
- Compatibility regression: if the new `enabled` field is not defaulted correctly, existing novena contracts could fail validation or change behavior.

### Deviations
- The importer now uses BeautifulSoup to extract the live prayer HTML because the content is too structured for a dependable regex-only parser.
- The generated novena contract now embeds the prayer sections directly in `novena.template`, and the repeated prayer-heavy blocks can also point at a canonical prayer fragment library so the imported file stays self-contained while becoming much smaller and more reusable.
- Disabled duplicate contract ids are allowed to load when the duplicate file is disabled, so a disabled draft can coexist with an enabled runtime contract without blocking the run.
- Single-mode imports now emit a report file by default as well, so both modes share the same review trail.
- TTS normalization is opt-in via the importer CLI or the `OPENAI_API_KEY` environment; when OpenAI is unavailable, the importer still applies a local rule-based normalization pass so the contracts remain usable offline.
- The importer also reads OpenAI settings from `config/local/openai.env` or the `OPENAI_API_KEY_FILE` override before falling back to environment variables.
- The importer now compacts repeated novena sections before the OpenAI rewrite step by caching identical normalized source blocks and reusing the first resolved result for later matches.
- The importer now writes both expanded `sections` and compacted `blocks` into the generated novena template, and the compact blocks can also reference a top-level canonical prayer fragment library so repeated prayers are reused as text fragments instead of being inlined everywhere.
- The single-import markdown report now favors the compact block preview so the shared day ranges and fragment references are easy to inspect at a glance.
- The novena renderer now prefers compact `blocks` for audio fragment generation, which gives repeated novenas a small day-specific intro and reusable fragment-level prayer blocks that the fragment cache can reuse across days.
- Imported traditional novenas now carry a distinct published title so they can coexist with the auto-generated novena titles.
