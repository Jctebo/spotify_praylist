# Release 0.1.5.3 - Publish Pipeline Cleanup

Date: 2026-04-26
Status: Scoped
Branch: enhancement/publish-pipeline-cleanup

## Scope

### Problem
- The repo has several partially overlapping publishing ideas: custom TTS contracts, page-audio generation, Notion output, legacy archived configs, new `config/publish` draft contracts, and GitHub Pages exports.
- The next step needs one small, generic publishing spine where structured repo content is the source of truth and downstream outputs are products of the same contract data.
- This matters now because Morning Prayer and Rosary draft contracts are already being moved into `config/publish`, and path cleanup alone will not prevent the next round of source-of-truth drift.

### Audience
- Primary user: the maintainer who runs and extends daily prayer publishing.
- Secondary stakeholders: listeners who consume generated audio through podcast clients, including Spotify after RSS ingestion.
- Secondary stakeholders: future maintainers who need to add new content contracts without editing core logic for each prayer.

### Current Status Quo
- Morning Prayer has an active custom TTS/page-audio path centered on `config/custom_tts/morning-prayer.json` and `jobs/notion/generate_page_audio.py`.
- Rosary has legacy and draft contract history, with current draft publish config under `config/publish/contracts/rosary.json`.
- Draft publish templates now live under `config/publish/templates/...`, separate from older `config/content/...` paths.
- Notion text output, MP3 generation, public RSS, and GitHub Pages delivery are not yet one clean contract-driven flow.
- Existing code still contains content-specific concepts from prior Morning Prayer and Rosary work that should not define the new generic publishing boundary.

### Goal
- Build a simple, config-driven publishing system with two independent output surfaces:
- Text surface: publish normalized contract entries to Notion.
- Audio surface: generate MP3 files, write podcast RSS, and serve `/docs/podcast.xml` plus `/docs/audio/*.mp3` through GitHub Pages.
- Treat `config/publish/contracts/morning-prayer.json` and `config/publish/contracts/rosary.json` as the first two draft contracts using the same schema.
- Make `contract.frequency` required and use it in resolver and job metadata so scheduling is explicit rather than inferred from filenames.
- Success criteria:
- Both initial contracts validate against one shared schema and declare `frequency: daily`.
- Text jobs are produced for non-skipped entries with `text_config.enabled` defaulting to true.
- Audio jobs are produced only for approved entries with `audio_config.enabled: true`.
- Morning Prayer can enable audio by config, while Rosary can leave audio disabled by config, with no hardcoded contract IDs.
- Notion upserts by stable `entry_id` without duplicate rows.
- MP3 generation skips unchanged content by `content_hash` and regenerates when text or relevant audio settings change.
- Podcast RSS includes only successfully generated audio and remains stable across repeated runs.

### Constraints
- Contract files are the only source of truth for publishable content and per-entry behavior.
- Pipelines must be independent: text publication cannot require audio generation, and audio publication cannot require Notion.
- Core logic must not special-case Morning Prayer, Rosary, file names, or contract IDs.
- Missing optional config blocks should fall back to sensible defaults, but required identity and schedule fields should fail validation.
- Generated audio must live under `docs/audio/{entry_id}.mp3`; the RSS feed must live at `docs/podcast.xml`.
- Public enclosure URLs must be derived from configurable GitHub Pages base URL metadata, not embedded per contract in ad hoc ways.
- The first implementation should be idempotent and testable locally before any scheduled workflow depends on it.

### Narrow Wedge
- Define one shared publish contract schema for daily entry-based content:
- `contract`: `id`, `type`, `frequency`, `timezone`, `version`, and optional channel/output metadata.
- `entries`: stable `entry_id`, `date`, `title`, `status`, `text`, optional `text_config`, and optional `audio_config`.
- Convert or replace the two draft publish contracts so Morning Prayer and Rosary use that same shape.
- Implement generic validation plus two generic resolvers:
- Text resolver outputs normalized text jobs for all eligible entries.
- Audio resolver outputs normalized audio jobs for approved, audio-enabled entries.
- Implement minimal generic publishers:
- Notion publisher upserts text jobs by `entry_id` into configurable Notion target fields.
- Audio runner creates or reuses MP3s based on `content_hash`.
- Podcast publisher writes a valid, deterministic RSS feed from completed audio files.
- Add simple runners:
- `run_text_pipeline`: validate contracts, resolve text jobs, publish to Notion.
- `run_audio_pipeline`: validate contracts, resolve audio jobs, generate audio, publish RSS.
- Add focused tests for validation, defaults, resolver inclusion/exclusion, idempotent audio skip/regeneration, Notion duplicate prevention behavior through mocks, and RSS item/enclosure shape.

### Non-Goals
- Do not migrate every legacy page-audio or Spotify playlist contract in this release.
- Do not build liturgical-calendar novena scheduling in this release.
- Do not submit or configure the podcast in Spotify in this release; RSS compatibility is enough.
- Do not preserve old custom TTS contract compatibility as the new schema unless research proves it is cheaper and safe.
- Do not couple this publishing system to the Spotify playlist refresh pipeline.
- Do not require live Notion or live OpenAI calls in the default test suite.
- Do not solve podcast artwork, categories, transcript generation, or multi-feed hosting unless required for a valid first feed.

### Risks And Unknowns
- The draft `config/publish/contracts/*.json` files currently look resolver-based, while the proposed schema is entry-based; research needs to decide whether to transform templates into entries at build time or make the contracts directly entry-based.
- Notion target shape is not fully specified: database ID, field names, and optional audio fields need confirmation against the live workspace or existing conventions.
- GitHub Pages public base URL and repository Pages settings need confirmation before feed enclosure URLs can be final.
- Text-to-speech provider details, voice defaults, and content hash inputs need to be pinned so audio idempotency is trustworthy.
- If `entry_id` is manually authored, validation must prevent duplicates across all contracts, not just inside one file.

### Recommended Next Step
- Run `/research-astack` to map the current publish, page-audio, Notion, TTS, GitHub Pages, and workflow code paths.
- Research should specifically answer whether to adapt existing `jobs/notion/generate_page_audio.py` pieces or create a new smaller `jobs/publish/` boundary for the generic contract pipelines.
- Research should also inspect the two draft contracts and templates to propose the least risky conversion into the shared entry-based schema.

### Constraints
- The new publish system must be generic and not special-case Morning Prayer or Rosary by name in core logic.
- The first release should stay idempotent and local-testable, which favors deterministic hashing and stable entry IDs.
- The draft contracts already in `config/publish` are not a clean fit for the scoped entry-based contract model, so the schema direction has to be decided before implementation.
- The existing page-audio runtime still serves archived and legacy behavior; we should not accidentally widen that surface while adding publish-specific code.
- The publishing flow must keep text and audio independent, even if both consume the same source content.
- The implementation should favor a fresh publish path over layering more behavior into the current page-audio runtime.
- Legacy publish paths should be retired deliberately as part of the migration, not left in place as long-term fallback code.

### Risks
- The biggest technical risk is contract-shape drift: the current draft contracts are resolver trees, while the scoped target is entry-centric.
- A second risk is overfitting to `jobs/notion/generate_page_audio.py`; that module already mixes validation, rendering, storage, and Notion operations in one place.
- RSS enclosure URLs and GitHub Pages paths are easy to get wrong early, and later changes are expensive once clients subscribe.
- Notion upsert semantics need a stable `entry_id` and a clear page/database target model, or duplicates will appear quickly.

### Assumptions To Validate
- The repo should likely create a smaller publish boundary instead of extending the current page-audio module in place.
- Morning Prayer and Rosary should probably become data-driven entry lists under one shared schema, not just renamed resolver trees.
- Audio publication likely wants the same deterministic content hash to drive skip/regenerate behavior across reruns.
- The public feed should probably live under `docs/` so GitHub Pages can serve it without additional hosting.

### Unknowns
- Whether the current `config/publish/contracts/*.json` drafts should be transformed at load time or rewritten to the new schema directly.
- Which Notion database/page targets and field names should store text jobs and optional audio metadata.
- What base public URL should be used for RSS enclosures on GitHub Pages.
- Whether a new `jobs/publish/` package should own the orchestration, or whether the current page-audio module should be split into reusable helpers plus a thin new runner.
- Which audio settings should be included in the content hash so regeneration stays correct without being noisy.

### Recommended Direction
- Move into `/plan-astack` with a new publish boundary as the default assumption: a small generic `jobs/publish/` layer or equivalent new package, plus only the reusable helpers that still make sense from `jobs/notion/generate_page_audio.py` and the contract-loader pattern from `jobs/playlist/spotify_contracts.py`.
- Treat the current Morning Prayer and Rosary publish files as draft inputs to the new schema, not as the final runtime contract shape.
- Prefer a clean cutover that rewrites or replaces legacy publish paths instead of extending them, while still reusing proven ideas for validation, hashing, and output writing.
- Keep compatibility shims only if they reduce migration risk materially; otherwise, the cleaner long-term shape should win.

## Plan

### Summary
- Build a fresh generic publish path under a new `jobs/publish/` boundary instead of extending the current page-audio runtime.
- Rewrite `config/publish/contracts/morning-prayer.json` and `config/publish/contracts/rosary.json` into one shared entry-based publish schema.
- Keep the existing `config/publish/templates/*` files as the source text assets that entries point to.
- Publish text and audio independently, with Morning Prayer using Notion + RSS and Rosary using Notion/text only, then cut over workflows and retire legacy paths deliberately.

### What Already Exists
- The repo already has a proven contract-loader pattern in `jobs/playlist/spotify_contracts.py`.
- The repo already has Notion helpers, content hashing, and file-writing patterns in `jobs/notion/generate_page_audio.py`.
- GitHub Pages deployment already exists in `.github/workflows/daily_devotional_image_remote.yml`.
- The current Morning Prayer and Rosary draft files under `config/publish/contracts/` and the text assets under `config/publish/templates/` give us concrete first inputs.

### Architecture
- New package: `jobs/publish/` owns contract loading, validation, job resolution, Notion publishing, audio generation, and RSS writing.
- Contract shape:
  - `contract`: identity, `type`, required `frequency`, `timezone`, `version`, and any feed/channel metadata.
  - `notion_target`: contract-owned display name plus any canonical page/database identifiers needed for upsert behavior.
  - `entries`: stable `entry_id`, `date`, `title`, `status`, `text_config`, `audio_config`, and an ordered list of content blocks or sections.
  - each content block can use a generic selector or source type such as `inline_text`, `file`, `monthly_template`, `weekday_map`, `date_rule`, `fixed_text`, or `prompt`.
  - selector evaluation happens in one shared resolver layer using the contract timezone and the target date, so Rosary weekday routing and Morning Prayer monthly intentions stay on the same engine.
  - each contract names its canonical Notion target by display name, so Morning Prayer can target `Morning Prayer` and Rosary can target `Daily Rosary` without hardcoding those labels in the runtime.
  - prompt blocks should resolve through the same generic LLM interface used by the rest of the repo, with the prompt definition remaining in contract data rather than code.
  - feed metadata should derive a GitHub Pages base URL from the repository deployment settings, with a fallback that matches the published Pages origin.
- Data flow:
```text
config/publish/contracts/*.json
        |
        v
validate + normalize
        |
        +--> text jobs --> Notion upsert
        |
        +--> audio jobs --> MP3 cache/write --> docs/audio/*.mp3 --> docs/podcast.xml
```
- Text and audio pipelines share the same contract reader but do not depend on each other at runtime.

### Failure Modes
- Invalid JSON or schema drift blocks loading before any publishing happens.
- Duplicate `entry_id` values cause a fail-closed load error instead of duplicate Notion rows or duplicate feed entries.
- Missing or disabled audio config yields an empty audio job set instead of partial RSS output.
- A failed MP3 render leaves the RSS feed untouched for that entry.
- A Notion API failure stops the text pipeline without creating duplicate rows on retry.
