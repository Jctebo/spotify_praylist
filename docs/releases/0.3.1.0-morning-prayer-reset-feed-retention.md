# Release 0.3.1.0 - Morning Prayer Reset Feed Retention

Date: 2026-05-02
Status: Shipped
Branch: enhancement/morning-prayer-reset-feed-retention
Depends On: 0.3.0.4

## Scope

### Problem
- The May 3 Morning Prayer run failed because the daily opening block could not find today's Gospel data.
- The publish flow treated that missing upstream data as a hard failure, even when the block was optional enough to recover safely.
- Why now: one missing liturgical or Gospel lookup was blocking the whole run, and we needed a way to recover the May 3 publish without turning every dynamic block into a silent no-op.

### Audience
- Primary user: the maintainer running the Morning Prayer publish job and needing it to complete even when one dynamic block has no data.
- Secondary stakeholders: listeners who rely on the daily episode being published on schedule.
- Secondary stakeholders: future authors of custom blocks that use OpenAI logic or custom calendar lookups and need a predictable skip rule.

### Current Status Quo
- `jobs/publish/daily_intro.py` fetches Romcal celebrations and USCCB Gospel readings, and it now has a Gospel-free fallback path when the Gospel section or Gospel text is missing.
- `jobs/publish/contracts.py` wires the daily intro into the Morning Prayer contract, and it can also skip optional dynamic blocks that explicitly opt into `skip_if_missing`.
- Other custom blocks that depend on generated calendar data or OpenAI output still use the same fail-closed contract path unless they opt into the skip behavior.
- The Morning Prayer contract now declares that the daily intro may omit the Gospel sentence when the lookup is unavailable.

### Goal
- Keep the May 3 Morning Prayer publish from failing when today's Gospel lookup is unavailable.
- Add an explicit block-level opt-in flag that allows a custom block to be skipped when its required dynamic data is missing.
- Let the daily intro render a Gospel-free variant when the Gospel text is unavailable, instead of failing the whole prayer.
- Success criteria: the default behavior still fails closed for required content, while flagged blocks can be omitted cleanly with a clear log or summary message.

### Constraints
- Preserve fail-closed behavior by default so missing data does not disappear silently from existing blocks.
- Keep the new skip behavior opt-in at the block level, not a global toggle for the whole pipeline.
- Keep the Gospel-free daily intro fallback narrowly scoped so it only applies to the Morning Prayer opening block when explicitly enabled.
- The solution has to work for both OpenAI-backed blocks and custom calendar-backed blocks, because the same failure pattern can appear in either path.
- Keep the change narrow to block resolution and contract schema rather than redesigning the full publish pipeline.

### Narrow Wedge
- Introduce one boolean skip-on-missing flag for dynamic blocks.
- Apply it first to the daily intro / Gospel-dependent opening block so the May 3 blocker can recover cleanly.
- Add a Gospel-free fallback mode for the daily intro so the opening block can still render when the Gospel lookup is unavailable.
- Add regression coverage for both the missing-data failure path and the Gospel-free path.

### Non-Goals
- Do not change the wording or theology of the generated Morning Prayer content.
- Do not make every block optional by default.
- Do not split the audio or RSS feed into separate series.
- Do not redesign the OpenAI prompt flow beyond what is needed to skip cleanly when data is absent.
- Do not add a broad "ignore all errors" mode.

### Risks And Unknowns
- We need a precise definition of "missing" versus "present but empty" so the skip flag does not hide real content bugs.
- If the skip flag is too broad, a bad upstream response could silently remove important blocks.
- If it is too narrow, the May 3 run may still fail on a different custom calendar or OpenAI-backed block.
- It is not yet confirmed whether the cleanest implementation lives in block normalization, block rendering, or the contract validator.
- The OpenAI prompt still remains a hard dependency for the daily intro; the Gospel-free fallback only removes the Gospel sentence, not the model call itself.

### Recommended Next Step
- Run `/research-astack` to map the dynamic block execution path, confirm the safest place to add a block-level skip-on-missing flag, and verify which block kinds should support it first.

- `tests/test_publish_contracts.py`, `tests/test_publish_text_pipeline.py`, and `tests/test_publish_audio_fragments.py` - cover contract resolution, text job construction, and fragment assembly that inherit the skip behavior once the resolver returns empty output.
- Live probes in the current workspace: `fetch_daily_gospel_context(datetime.date(2026, 5, 3))` returns `RuntimeError: Mass readings returned no mass object.` after the helper logs `No mass for date: 2026-05-03, types: [DEFAULT]`. Direct calls into the dependency can also raise `HTTPError: HTTP Error 403` from the lower-level `_get_mass(...)` path, which the public `get_mass_from_date(...)` wrapper suppresses into `None`.
- Live probes in the current workspace show the transport layer is flaky and challenge-driven: some curl-cffi sessions can reach the real USCCB page, but repeated fresh sessions also hit `403` "Checking connection" responses. That means the wrapper can surface either a real mass or a suppressed transport failure depending on the upstream edge state.

### Current System Map
- `config/publish/contracts/morning-prayer.json` defines one `daily_intro` block followed by static sequences/files. If Gospel data is missing, the intro can still render in a shorter Gospel-free form and the rest of the prayer still renders normally.
- `jobs/publish/contracts.py` is the central renderer. `resolve_block_content(...)` directly calls `build_daily_intro_text(...)` for `daily-intro` blocks, and `build_daily_intro_text(...)` calls `fetch_daily_gospel_context(...)` before any text is produced.
- `fetch_daily_gospel_context(...)` has three missing-data failure points before the prompt even runs: no Romcal rows, no usable celebration names, or no Gospel section/text from USCCB. A missing citation alone does not fail because the helper can fall back to the mass URL.
- `fetch_daily_gospel_context(...)` also inherits transport instability from `catholic_mass_readings`: the dependency can log and swallow a 403-like fetch failure as `None`, so the code path needs both a fetch hardening layer and a block-level omission fallback.
- `_build_text_sections(...)`, `expand_audio_fragments(...)`, and `section_toggle_blocks(...)` already prune empty results downstream, so a resolver that returns `""` can be omitted without changing later pipeline stages.
- `build_text_jobs(...)` and `build_audio_jobs(...)` both gate on `approved` status and entry-level config, so whole-entry skip semantics already exist. They still do not have block-level optionality or per-block skip semantics.
- The current contract normalizer already preserves unknown block fields, which means a new boolean flag can likely be added with low schema churn as long as the resolver understands it.
- Inference for the May 3 run: the failure happened before OpenAI prompt generation, inside `fetch_daily_gospel_context(...)`, because that is the first place the code can raise when today's Gospel data is unavailable. The code path is vulnerable to live HTTP transport failures that are silently downgraded to `None`.

### Reuse Opportunities
- Reuse the existing empty-text pruning in `_build_text_sections(...)`, `expand_audio_fragments(...)`, and `section_toggle_blocks(...)` so skipped blocks disappear naturally from both text and audio output.
- Reuse the existing `text_config.enabled` and `audio_config.enabled` patterns as the closest current examples of opt-in gating, even though they are entry-level rather than block-level.
- Reuse the current `daily_intro` metadata wiring in `config/publish/contracts/morning-prayer.json` so the new Gospel-free flag can live beside `calendar`, `locale`, and `prompt_model`.
- Reuse the current test harnesses in `tests/test_publish_daily_intro.py`, `tests/test_publish_contracts.py`, `tests/test_publish_text_pipeline.py`, and `tests/test_publish_audio_fragments.py` to prove both the hard-fail and skip-enabled paths.
- Reuse the `curl_cffi` session knobs already exposed by the dependency to test a safer fetch profile before introducing a bespoke HTTP client.

### External References
- `catholic_mass_readings` / USCCB mass lookup: the daily intro depends on this library returning a Gospel section with usable text.
- `openai` API client: the daily intro prompt path still uses OpenAI for the intro, so the Gospel-free fallback must not mask prompt-generation failures that are separate from missing upstream data.
- USCCB's published daily readings for 2026-05-03 are the Fifth Sunday of Easter and include a Gospel reading (`John 14:1-12`), so the blocker is not the liturgical calendar lacking Gospel content; it is in our fetch/parse path or a live dependency failure.
- The `catholic_mass_readings` package in this repo is a live HTTP client over `bible.usccb.org` using `curl_cffi` and `BeautifulSoup`; it does not use a local cache.
- The USCCB edge can serve a `403` "Checking connection" challenge page to the client, which is why a valid readings page may still resolve to `None` upstream.
- `curl_cffi` supports browser impersonation, custom headers, and retry settings; those are the first knobs to try before replacing the dependency.

### Constraints
- The block-level skip must be opt-in; existing contracts should keep failing when required dynamic data is absent.
- The change has to work for both OpenAI-backed dynamic text and custom calendar/lookups, because the same failure class can appear in multiple block kinds.
- The downstream pipeline already knows how to ignore empty content, so the safest fix is to convert "missing data" into empty output at the resolution layer.
- The implementation should not broaden into a global "ignore all errors" mode.

### Risks
- The key risk is confusing "missing upstream data" with a genuine contract bug or file/path error, which could hide real defects if the skip rule is too broad.
- If the skip logic only covers `daily-intro`, later custom calendar blocks like `weekday_map` or `monthly_template` could still fail in the same way.
- If the skip logic swallows too much, a broken prompt or malformed selector could silently remove meaningful content instead of surfacing the problem.
- If logging is not added at the resolver layer, skipped blocks could become invisible in run summaries.
- The live dependency is currently vulnerable to upstream HTTP 403 responses from USCCB's anti-bot edge, and the library converts that into `None`. Without better logging or retries, a transport block looks exactly like missing Gospel data.
- The fetch hardening may reduce but not eliminate 403s, so the Gospel-free fallback still needs to exist even if we improve the HTTP profile.

### Assumptions To Validate
- The intended behavior is to keep the rest of Morning Prayer publishing even if the opening Gospel-dependent block has to be skipped.
- The block-level flag should likely live on the block object itself, not on the whole entry.
- A skipped block should be omitted from both text and audio output without breaking the ordering of the remaining sections or fragments.
- Missing-data errors from Romcal/USCCB/OpenAI should be separable from missing-file or malformed-contract failures.

### Unknowns
- Should the new flag be named `skip_if_missing`, `allow_missing`, or something more explicit about omission?
- Should the skip rule catch only missing-data exceptions from `daily_intro`, or also the "no match" cases in `weekday_map` and `monthly_template`?
- Where should the user-visible skip message live: resolver logging, pipeline summary, or both?
- Should the contract validator begin recognizing the new field explicitly, or is pass-through normalization enough for the first release?

### Recommended Direction
- Move into `/plan-astack` with a dual-track fix: first harden the USCCB fetch path in `jobs/publish/daily_intro.py` using the dependency's HTTP knobs and retry behavior, then add the resolver-layer skip-on-missing fallback in `jobs/publish/contracts.py` so the publish can still complete when the upstream edge blocks us.

## Plan
### Summary
- Build a small, explicit wrapper around the daily Gospel fetch path so the May 3 failure can recover from transient USCCB transport issues instead of collapsing into an opaque `None`.
- Add a block-level boolean `skip_if_missing` so dynamic blocks can opt into omission when required upstream data is unavailable.
- Keep fail-closed behavior as the default for every existing block that does not opt in.

### Implementation Order
1. Harden `jobs/publish/daily_intro.py` so Gospel lookup has a deliberate retry and fallback path before it gives up.
2. Teach `jobs/publish/contracts.py` to recognize `skip_if_missing` on a block and omit only the blocks that explicitly opt in.
3. Turn the Morning Prayer daily intro on with `allow_missing_gospel: true` so the Gospel sentence can be bypassed without skipping the whole prayer.
4. Add regression tests for the direct failure path, the transport-fallback path, the Gospel-free daily intro path, and the resolver skip path.

### Technical Design
- `jobs/publish/daily_intro.py` will stay the source of truth for the daily Gospel context, but it will stop treating the dependency result as a single brittle call.
- The new wrapper will try the current `catholic_mass_readings.USCCB` path first, using the existing live HTTP client behavior and retry knobs where available.
- If the dependency returns no usable mass or the upstream edge blocks the request, the wrapper will fall back to an explicit USCCB HTML fetch/parse path rather than immediately failing the publish.
- The fallback parser can reuse the same general USCCB-reading extraction shape already present in `jobs/novena/generate_daily_novena_prayer.py`, so we do not need to invent a second reading format.
- If both fetch paths fail to produce usable Gospel data, the wrapper will raise a narrow missing-data error that the resolver can recognize as skippable.
- `jobs/publish/daily_intro.py` will also support an opt-in Gospel-free variant so the opening block can render without the reading-dependent sentence when `allow_missing_gospel: true`.
- `jobs/publish/contracts.py` will treat missing-data signals as optional only when the block config says `skip_if_missing: true`; otherwise it will continue to fail closed.
- The resolver should log that a block was skipped and why, while the daily intro can now degrade to a shorter Gospel-free prompt when explicitly allowed.

### Config Changes
- Add `skip_if_missing: true` to the Morning Prayer `daily_intro` block in `config/publish/contracts/morning-prayer.json`.
- Add `allow_missing_gospel: true` to the Morning Prayer daily intro metadata in `config/publish/contracts/morning-prayer.json`.
- Leave the default for all other blocks as false so existing contracts keep their current behavior unless they opt in.
- Keep the flag available for future custom blocks that depend on OpenAI output or custom calendar lookups, since those blocks can fail for the same missing-data reason.

### Test Plan
- Extend `tests/test_publish_daily_intro.py` to prove the wrapper still resolves a real Gospel context, retries or falls back when the live dependency returns no mass, and renders a Gospel-free intro when the new flag is set.
- Extend `tests/test_publish_contracts.py` to prove `skip_if_missing` omits only the opted-in block and does not change the behavior of non-optional blocks.
- Extend `tests/test_publish_text_pipeline.py` and `tests/test_publish_audio_fragments.py` to prove the skipped block disappears cleanly from both text and audio output without breaking the remaining order or fragment assembly.
- Keep a regression test for the original May 3 failure shape so we know the wrapper and the Gospel-free daily intro path both solve the same blocker from different angles.

### Rollout Notes
- This is a pipeline-only change; there is no UI surface to redesign.
- The first release should only opt Morning Prayer into the new Gospel-free fallback behavior.
- The new skip behavior must not become a blanket error suppressor for the whole publish system.
- If the live USCCB edge remains flaky after the fetch hardening, the daily intro can still publish a shorter Gospel-free variant when that omission is acceptable.

### Acceptance Criteria
- The May 3 Morning Prayer publish no longer fails because the opening Gospel lookup is unavailable.
- The May 3 Morning Prayer publish can still render without the Gospel sentence when that fallback is enabled.
- Dynamic blocks can explicitly say "skip this block if the required data is missing" without affecting unrelated blocks.
- Existing required blocks continue to fail closed when they lose required data.
- The resolver logs make skipped blocks visible enough to diagnose why the output changed, while the daily intro can degrade in a controlled way when allowed.
