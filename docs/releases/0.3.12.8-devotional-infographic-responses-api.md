# Release 0.3.12.8 - devotional-infographic-responses-api

- Status: Shipped
- Shipped Date: 2026-08-12
- Created Date: 2026-08-12
- Last Updated: 2026-08-12
- Depends On: 0.3.12.7
- Notes: Replace the current two-call devotional-art rendering path with a Responses API agent workflow that produces one fact-checked Catholic devotional infographic for every eligible calendar subject and every enabled novena subject, then publishes the same approved asset to the portrait and wide delivery paths.

## Scope

### Problem
- The current job creates generic, text-free devotional art, overlays only a title locally, and uses the legacy Images API twice per target: once for portrait and again for wide.
- It generates for liturgical-calendar celebrations and configured monthly devotions, but does not systematically cover all enabled novena contracts.
- A saint/novena image needs concise, verified Catholic biographical copy, historically appropriate symbols, and consistent series styling; the render model must not be relied on as the factual source.
- The supplied Saint Jane Frances de Chantal infographic establishes the desired series language: ivory parchment, navy/antique-gold ornament, centered devotional portrait, structured information panels, and a Spiritual Themes footer.

### Audience
- Primary user: the maintainer publishing daily devotional imagery to OneDrive, GitHub Pages, and client devices.
- Secondary stakeholders: listeners and prayer-site visitors who need a clear, reverent visual introduction to each saint or novena subject.

### Current Status Quo
- `jobs/novena/generate_devotional_image.py` selects eligible Romcal celebrations and configured devotions, deduplicates them, then drafts a prompt with `client.responses.create`.
- The job separately calls `client.images.generate` for portrait and wide files, applies a local title overlay, and publishes separate files into `Current Devotion` and `Current Devotion Wide` plus their archives/manifests.
- Enabled novena contracts already define the repository's active novena corpus, but are not a first-class image target source.
- The remote workflow restores/syncs the four existing image folders and builds the public Pages tree from the current portrait and wide folders.

### Goal
- Use the Responses API as the orchestration and image-generation surface for a deterministic four-stage workflow: research, structured infographic copy, primary poster render using the master reference, and visual QA/targeted repair when needed.
- Produce one approved devotional infographic per unique eligible subject, including all enabled novena contracts as well as the existing calendar/devotion sources.
- Publish that same approved image asset to both existing delivery pipelines: `Current Devotion` and `Current Devotion Wide`; retain their archive and manifest contracts.
- Preserve traceable factual source data, approved copy, generation prompt/reference identity, QA result, and repair history as non-public metadata.
- Success means every enabled novena subject can be resolved into exactly one deduplicated target and each successful target has valid portrait and wide published outputs derived from one approved render, not two unrelated generations.

### Constraints
- Use authoritative Catholic research in priority order: Vatican/Holy See, bishops' conferences, official order/shrine/cause organizations, established Catholic reference works, then established Catholic publications. Do not invent unavailable facts.
- The research/copy contract, not the image, is the factual source of truth. Preserve supplied dates and titles exactly and cite/record the supporting sources.
- Use the supplied infographic as the initial master style reference; preserve its design language without copying its subject, copy, or unrelated logos.
- Keep existing OneDrive, GitHub Pages, folder names, manifest schema compatibility, archive/reuse semantics, local runner, and workflow scheduling unless a migration is explicitly planned.
- Do not expose research source URLs, structured copy, prompts, reference images, or QA diagnostics in the public image manifests.
- The exact current Responses API image-tool schema, supported image dimensions, output extraction shape, and `input_fidelity` behavior must be verified against official OpenAI documentation before implementation. GPT Image 2 supports Responses API and high-fidelity image inputs ([official model page](https://developers.openai.com/api/docs/models/gpt-image-2)).

### Narrow Wedge
- Add a contract-derived novena target adapter that includes every enabled novena and deduplicates it against calendar/devotion targets by a stable canonical subject identity.
- Introduce one versioned structured data contract for verified research, infographic copy, visual symbols, sources, and QA outcomes.
- Render one primary portrait infographic through the Responses API with the master reference image and the approved copy; inspect it; issue at most a bounded targeted edit/repair sequence when copy, identity, or layout fails validation.
- Derive both delivery variants from that approved source asset using a deterministic, documented transformation that preserves legibility and composition; do not make a second independent subject render.
- Store durable private sidecars sufficient to skip a verified existing target and to reproduce or repair it without repeating research.

### Non-Goals
- Building a general-purpose research CMS, interactive editorial review UI, or human approval queue.
- Changing novena prayer text, audio generation, Spotify integrations, or liturgical eligibility rules outside their use as image-target inputs.
- Guaranteeing pixel-perfect transcription from a generative model without a repair path.
- Replacing the existing public folder/manifest/client-sync contract or publishing private research metadata.
- Generating a different original illustration for portrait and wide layouts.
- Treating non-saint concepts with uncertain identity data as though they were canonized saints; titles and claims must follow verified source data.

### Risks And Unknowns
- Generated text may be misspelled, omitted, clipped, or non-legible. Automated image inspection may not reliably validate every factual string, so the implementation needs explicit pass/fail criteria, bounded repair attempts, and a fail-closed no-publish behavior for unresolved critical errors.
- Some enabled novenas concern Marian titles, feasts, mysteries, or causes rather than an individual saint; the copy schema and canonical identity rules must support those subjects without fabricated biographical fields.
- "All novenas" depends on the actual enabled-contract inventory and the stable mapping from a contract to a unique image subject/window. Research must enumerate and classify it before implementation.
- A single portrait master may require an intentional crop/letterbox/layout derivative for wide delivery. The transformation and validation threshold must be tested against the public site placements.
- Source research can change or be unavailable, and a web-search-capable Responses model may return insufficient citations. The implementation needs source allowlisting, response-schema validation, cached evidence, and clear fallback/failure handling.
- Reference-image rights, storage location, and versioning have not yet been established; implementation must choose a repository-owned or approved asset path.

### Recommended Next Step
- Run `/research-astack` to map enabled novena contracts and their subject types, identify the canonical subject/window/deduplication contract, inspect the current OpenAI Python SDK and official Responses image-tool schema, and define an offline-testable QA/derivative strategy before `/plan-astack`.

## Research

### Scope Baseline
- Replace the current independent portrait/wide Images API generations with a Responses API research, copy, render, QA, and repair workflow.
- Cover every enabled novena contract as a first-class target while retaining calendar and configured-devotion targets.

### Relevant Files
- `jobs/novena/generate_devotional_image.py`: owns targets, prompt drafting, image writes, archive reuse, overlays, and manifests; its `build_image_prompt` already uses Responses, while `generate_image_bytes` uses `client.images.generate`.
- `jobs/novena_contracts/contracts.py` and `validators.py`: load and validate enabled contracts with `saint`, `intro`, `feast`, `selector`, and `novena` metadata.
- `jobs/novena_contracts/resolver.py`: proves the existing contract domain has stable active-window and explicit-over-selector precedence behavior.
- `tests/test_devotional_image_job.py`: existing isolated coverage for target deduplication, storage, title overlay, and manifest behavior.
- `.github/workflows/daily_devotional_image_remote.yml`: supplies model settings and restores/syncs the current plus archive portrait/wide folders.
- `requirements.txt`: OpenAI Python SDK dependency; implementation must verify the installed SDK's Responses image-tool item schema rather than assume it.

### Current System Map
- `generate_devotional_image.py` loads Notion or local style/devotion/pipeline configuration, makes calendar/devotion `RenderTarget` values, then deduplicates them.
- Each target currently receives a Responses text-prompt call and up to two Images API calls, after which the job locally overlays the subject title and writes one file into each current folder.
- Novena contracts are file-backed and validation requires enabled contracts to carry canonical saint/event information; selector-family contracts resolve at runtime, while explicit contracts carry subject data directly.
- The public delivery contract is folder/manifest based. Private prompt/window sidecars already live under `Devotional Metadata Archive` and are excluded from public manifests.

### Reuse Opportunities
- Extend `RenderTarget`, target IDs, archive sidecars, manifest generation, and current/archive movement instead of adding a second image publisher.
- Use `load_novena_contracts` and validated `NovenaContract` data for contract-derived targets; reuse resolver precedence where a selector overlaps an explicit contract.
- Reuse `client.responses.create`, `extract_output_text`, existing OpenAI environment handling, and image/Pillow helpers.
- Reuse `unittest` mocks in `tests/test_devotional_image_job.py` for contract target discovery, structured-response parsing, response-image extraction, repair boundaries, and single-render/dual-publication behavior.

### External References
- [OpenAI image-generation guide](https://developers.openai.com/api/docs/guides/image-generation): current source for Responses image-generation tool inputs, image outputs, reference-image handling, and editing.
- [GPT Image 2 model page](https://developers.openai.com/api/docs/models/gpt-image-2): confirms GPT Image 2 accepts image input/output and supports the Responses endpoint.
- Catholic source policy from Scope governs the research stage; implementation must persist source URLs/titles alongside structured facts.

### Constraints
- The pipeline must fail closed when verified copy, an image response, or critical QA is unavailable; it must not publish an unvalidated poster.
- Every output needs one canonical subject identity, source window, prompt/copy hash, reference-version identifier, and private research/QA sidecar so reruns are deterministic.
- Novena subjects include saints, Marian titles, feasts, grouped martyrs, and intentions, so fields such as birth/death or patronage must be optional rather than fabricated.

### Risks
- Visual generation can corrupt text. OCR/vision QA must compare the final image with approved structured copy and repair only bounded, identified errors.
- A portrait-first master may crop poorly in wide output; implementation needs a deterministic wide derivative plus dimension/legibility tests.
- A Responses SDK/tool response may emit image content in a different item shape than the legacy `b64_json` object; adapter tests must use the documented current shape.

### Assumptions To Validate
- `load_novena_contracts` can enumerate the complete enabled corpus without needing to resolve every calendar date; validate that selector-family targets have a safe subject identity strategy.
- The configured OpenAI SDK supports the Responses image-generation tool and high-fidelity reference image input; verify through docs and a mocked adapter before a live run.
- The supplied reference can be checked into an approved repository asset or otherwise given a stable versioned path.

### Unknowns
- The exact automated visual-QA threshold and whether the job should include an OCR dependency or use a second Responses vision pass.
- Whether all existing Notion image-pipeline rows should opt in immediately or whether an explicit infographic style/pipeline row is needed.

### Recommended Direction
- Add a small dedicated infographic module/contract beneath `jobs/novena` rather than expanding the existing prompt string into an untestable monolith.
- Make the image job coordinate this module, add enabled-novena target enumeration, render one portrait master via Responses with a versioned reference asset, produce both delivery files from it, and persist private audit sidecars.
- Proceed to `/plan-astack`; the remaining unknowns are implementation decisions that can be resolved with testable defaults.

### Failure Modes
- Invalid research/copy or wrong title/date: schema validation or QA comparison fails before publication.
- Responses API tool output lacks an image: adapter fails with a clear subject/response error.
- Wide derivative cannot preserve dimensions: local image validation fails before write.
- Novena duplicate or unsupported subject: canonical identity dedupes it or records an explicit skipped reason.
