## §2 Grounding — where the mix is born (shipped client + Worker, base = pin ora-pro-nobis-v647-1)

Read firsthand from `app/worker/src/client.ts` and
`app/worker/src/index.ts` on the base tree, the live payload above,
and app D1 `ext_resolutions`.

1. **The choice carries no image.** `opnExtChoice628` (client.ts
   ~2172) returns `{ title, streamUrl, source, backup }` — the entry
   re-ordered for the user — and no image field anywhere. Its backup
   side is built from `e.backup.streamUrl` + source only. The
   payload's backup object itself carries no image (verified live,
   §1), and the server's backup write is the reason:
   `extResolutionBackupWrite` (index.ts ~2408) stores only
   `backup_url` + `backup_source`; `externalsLivePayload` (~3098)
   builds `entry.backup = { streamUrl, source, title }` from those
   two columns. The Sing the Hours image EXISTS server-side at
   backup-write time — the watcher holds the matched feed item and,
   for a fill, writes the row's image as the item's image else the
   feed's `channelImageUrl` (the StH fill write, index.ts ~2831) —
   it is simply never stored for the backup.

2. **Live settle: title/stream from the choice, image from the
   standing entry.** The courier leg applies the choice and calls
   `settleMeta(slot, { title: choice628.title, enclosureUrl:
   choice628.streamUrl, source: choice628.source, backup:
   choice628.backup, imageUrl: e.imageUrl || null, … })` — the image
   is the SERVED entry's image (the Divine Office logo) regardless of
   the chosen source. With Sing the Hours first, the record is born
   titled StH with DO art.

3. **The download: the pass-through is choice-blind — this is where
   the audio splits.** `extDownload` routes by the meta's source:
   for 'Sing the Hours' the routes are `[passThrough,
   meta.enclosureUrl]` — the Worker pass-through FIRST (castos sends
   no CORS header; the direct read fails, v631). But
   `GET /api/player/externals/audio` (index.ts ~5770) never reads
   `ext_resolutions` and never learns the client's choice: it
   re-resolves the slot from the feeds, Divine Office first
   (`extMatchDivineOffice`), falling to Sing the Hours only when the
   DO match FAILS (the v631 fail-soft). Today the DO feed answers,
   so the pass-through streams the **Divine Office episode with
   HTTP 200** into a download whose meta names Sing the Hours. The
   client accepts the blob as the chosen source's audio, stores it
   in `opn-ext-audio-v1` under the slot's source-blind key
   (`offlineDayKey(date, slotId)`), and settles present: title StH ·
   source StH · enclosureUrl the castos pointer · **bytes the Divine
   Office episode**. The direct castos route never fires — the
   pass-through "succeeded". (Under v631's field conditions the
   server ROW itself stood StH-filled, so the same route served StH;
   the blindness was invisible until v634 stood both sources on one
   row with DO standing.)

4. **The v638 flip resettle repeats both halves.** The hook
   (`state.extResettleLabeled638`) re-applies the choice and calls
   the same `settleMeta` with `imageUrl: e.imageUrl || null` — the
   standing entry's image again — and its download takes the same
   routes through the same choice-blind pass-through. A flip swaps
   the title (and the record's named enclosure) but neither the art
   nor, when the pass-through answers, the audio's true source.

5. **The day cache stores a partial record — and the audio cache
   makes the mix durable.** `writeCache` stores a labeled record as
   `{ state, title, streamUrl, durationSec, sizeBytes, source,
   block, sortOrder, imageUrl, descText }` — **no backup** (the v637
   doc's named fact). The v637 prune deletes a cached labeled slot
   only when `c.source !== wantFirst`; a record whose source names
   the choice but whose blob is the other source's audio passes the
   prune untouched, and `extRestoreCached` mints whatever blob
   stands under the slot's audio-cache key — the poisoned blob
   restores under the corrected-looking record on every later open.
   No prune condition looks at the image or the backup at all.

6. **Paint and play read the record whole — so the record's mix IS
   the row's mix.** `extSlotTrack` builds the descriptor from the
   one slot record (`title · streamUrl · source · imageUrl`);
   `trackDesc` carries those fields through the composed set
   (v642's paint source of record); `queueLiveDesc` re-resolves a
   queued ext descriptor against the LIVE slot record at advance
   time. There is no second record for title, stream, or image to
   disagree with — they disagree because the settled record itself
   was composed from two sources (§§2.2–2.3) and, for the image,
   because the choice has none (§2.1).

7. **The Ora artwork is the null-image fallback firing.** Every art
   surface reads the descriptor's `imageUrl` — the row card, the
   dock thumb (`cur.imageUrl || '/logo.png'`), Now Playing
   (`npArtRender`: a null art stands the Ora logo), the media
   session artwork. A labeled record whose imageUrl stands null
   therefore paints Ora art on an office row. Null is reachable in
   production: the choice supplies no image (§2.1), and the server
   itself stands labeled rows with `image_url` NULL on
   synthesis/scrape-filled days (app D1, both labeled slots,
   2026-11-23 — read firsthand). On such a day the settle writes
   `imageUrl: null` under either choice and the row paints the logo.

## §3 Plan — the atomic settle

One rule, applied at every seam: **for the two labeled slots, the
settled record is built from the choice's whole record — title,
stream, source, backup, and image — and the download fetches the
CHOSEN source's audio.** Non-labeled slots are byte-untouched.

1. **Server: the backup gains its image (migration 0051).**
   `ext_resolutions` gains `backup_image_url`. The backup writes
   carry the Sing the Hours image — the matched item's image else
   the feed's `channelImageUrl`, the same fallback the fill write
   uses: `extResolutionBackupWrite` (the watcher's backup-needs
   leg) and the v634 displacement write inside
   `extResolutionWrite`. `externalsLivePayload`'s backup object
   gains `imageUrl` from the new column. Migration applies before
   the deploy and is PRAGMA-verified (the v625 discipline); rows
   written before 0051 carry NULL until the watcher's next
   backup write for that day — the client treats a NULL backup
   image as an incomplete record (§3.4), never as a paintable one.

2. **Client: the choice returns the whole record.**
   `opnExtChoice628` gains `imageUrl` on both sides: the chosen
   side carries its own image (the entry's `imageUrl` when the
   standing source is chosen; the backup's `imageUrl` when Sing
   the Hours is chosen), and the returned backup carries its image
   likewise. Its signature and its other fields are unchanged;
   every consumer reads the new field from the choice result.

3. **Client: settle paths take the choice's image.** The courier
   leg's `settleMeta` call and the v638 hook's `settleMeta` call
   pass `imageUrl: choice.imageUrl || null` for the two labeled
   slots (the choice result already stands in both places; the
   non-labeled path keeps `e.imageUrl`). The backup-flip retry
   inside `extDownload` already carries `meta.imageUrl` — with the
   choice's image in the meta, the flip's settle is consistent
   whole.

4. **Server + client: the pass-through serves the asked source.**
   `GET /api/player/externals/audio` accepts `src` for the two
   labeled slots. When `src` stands, the route serves from the
   day's `ext_resolutions` row: `src` === the row's source → the
   row's `stream_url`; `src` === the row's `backup_source` → the
   row's `backup_url`; a `src` matching neither → 404 (never a
   silent serve of the other source). The fetched enclosure then
   streams exactly as today (range honored, headers as standing).
   With no `src`, the route is byte-identical to today (every
   other slot and caller untouched — the v631 fail-soft included).
   Client side: `extDownload`'s pass-through URL for a labeled
   slot carries `&src=` + the meta's source, and
   `oraSnapshotTrack`'s native mediaUri for a labeled slot carries
   the slot record's standing source the same way — the native
   engine's hand-off names the same chosen source as the web
   download. The direct-enclosure route stands as the second route,
   unchanged.

5. **Client: the cache record stands whole, and the prune checks
   the whole record.** `writeCache` stores the labeled record's
   backup `{ streamUrl, source, title, imageUrl }` alongside the
   standing fields (the settled record's backup rides
   `state.extSlots` from `settleMeta` as today — it is simply no
   longer dropped at the cache write). The v637 prune extends: a
   cached labeled slot leaves the record — and its
   `opn-ext-audio-v1` entry under `offlineDayKey(date, slotId)` is
   evicted in the same act — when ANY of these stands: its source
   is not the preference's first choice · its backup is missing ·
   its `imageUrl` is null. The courier then re-settles the slot
   from the live payload under §§3.2–3.4, both sources whole, and
   the fresh download replaces the evicted blob. (Eviction fires
   only on a prune — a whole record's blob is never disturbed.)

6. **Queue: the settled record governs — no queue change.**
   Gate 5's discipline is the standing one, named: a queue item
   re-resolves against the live slot record at advance
   (`queueLiveDesc`), so a queue built before a flip plays the
   re-settled record's source whole — title, stream, and image of
   the one chosen source; the sounding item keeps the v638 mint
   guard (it finishes as it is). No queue code changes.

  courier leg in `resolveExternals`). The confirm
