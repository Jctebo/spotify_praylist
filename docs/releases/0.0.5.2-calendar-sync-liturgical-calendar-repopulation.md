# Release 0.0.5.2 - calendar-sync-liturgical-calendar-repopulation

- Status: Shipped
- Shipped On: 2026-03-23
- Last Updated: 2026-03-23

## Scope

### Problem
- The Liturgical Calendar Notion database was populated once, but it is not yet clear whether the yearly script can be rerun safely as a true sync/upsert.
- The calendar needs to be repopulated for 2026 and 2027 with the updated Easter precedence logic, including the local Palm Sunday and Easter Sunday exceptions.
- We need to know whether the current workflow updates existing rows, creates new rows, and removes exact duplicates, or whether it only behaves like a one-time import.

### Audience
- Primary user: the maintainer who owns the Notion Liturgical Calendar and runs the yearly sync/backfill.
- Secondary stakeholders: downstream Notion pages, exports, and devotional jobs that read the calendar database.

### Current Status Quo
- `jobs/novena/sync_liturgical_calendar.py` collects Romcal rows over a date range and writes them into Notion.
- Existing rows are matched by `Feast Day` plus `Name` and updated in place; new rows are created when no match exists.
- A dedupe pass can archive exact duplicate date/title rows in the selected sync window.
- The workflow already supports `target_year`, `start_date`, and `end_year` inputs, so it can backfill this year and next year without code changes.
- The docs describe this as a yearly population job, which makes it easy to mistake for a one-time import.

### Goal
- Repopulate the Liturgical Calendar database for 2026 and 2027 using the updated Easter precedence logic.
- Confirm the job can be rerun idempotently instead of treating it as a one-off import.
- Keep Palm Sunday and Easter Sunday represented correctly in Notion according to the chosen precedence rules.
- Leave the calendar in a state that can be refreshed in future years with minimal manual cleanup.

### Constraints
- This pass should not change production code or live Notion data.
- The repo already has shared Romcal overlay and liturgical eligibility helpers used by other jobs.
- The live Notion database contents are not in the repo, so any cleanup assumptions need to be validated against the actual database.
- The sync job uses Notion page title/date matching, so title drift could create duplicates if not handled carefully.

### Narrow Wedge
- Verify whether the current sync job is a true upsert plus dedupe path for the Liturgical Calendar database.
- Map the exact inputs needed to repopulate 2026 and 2027 with the new Easter precedence logic.
- Identify the smallest safe repopulation strategy that updates existing rows instead of replacing the whole database.

### Non-Goals
- Do not redesign the Romcal overlay or the general liturgical ranking model.
- Do not expand this into a full Notion schema migration unless the current property mapping is proven wrong.
- Do not change unrelated devotional or playlist jobs.
- Do not wipe and recreate the whole database unless research shows upsert cannot satisfy the goal.

### Risks And Unknowns
- If the live Notion database has manual edits or title drift, the date/title upsert key may not match every row.
- Exact duplicate cleanup only removes rows inside the selected sync window and only when date plus normalized title match.
- The current workflow sets `NOTION_SAINT_RADAR_ENABLED=true`, so the calendar sync is piggybacking on the Saint Radar upsert path.
- It is not yet clear whether Palm Sunday and Easter Sunday should be preserved as-is or reclassified beyond the current special-sunday overlay.

### Recommended Next Step
- Use `/research-astack` to confirm the sync path, Notion matching rules, and the least risky repopulation plan for 2026 and 2027.

## Research

### Scope Baseline
- Investigate whether the Liturgical Calendar yearly job is a true sync/upsert that can be safely rerun for 2026 and 2027.
- Focus on the current Romcal-to-Notion pipeline, the Easter precedence handling, and the exact duplicate cleanup path.

### Relevant Files
- `jobs/novena/sync_liturgical_calendar.py`
  Why it matters: this is the yearly Liturgical Calendar entrypoint, computes date ranges, calls the calendar collector, upserts rows, and archives exact duplicates.
- `jobs/novena/generate_daily_novena_prayer.py`
  Why it matters: it owns the shared Romcal overlay, special Sunday normalization, `infer_celebration_rank`, and the Notion helpers reused by the sync job.
- `jobs/novena/liturgical_model.py`
  Why it matters: it defines the shared liturgical eligibility contract and the Easter Octave precedence exclusion used by devotional jobs.
- `jobs/novena/export_liturgical_ics.py`
  Why it matters: it reads the same Notion liturgical fields and is a useful cross-check for the database schema and precedence metadata.
- `.github/workflows/liturgical_calendar_yearly_sync.yml`
  Why it matters: it wires the scheduled/manual sync inputs and shows how the job is intended to be rerun for future years.
- `README.md`
  Why it matters: it documents the Liturgical Calendar workflow, the Notion properties, and the yearly sync behavior that users will rely on.
- `tests/test_novena_job.py`
  Why it matters: it covers the shared Romcal normalization behavior for special Sundays and Easter Octave precedence.

### Current System Map
- `sync_liturgical_calendar.py` resolves the date range from `target_year`, `start_date`, `end_year`, or the default next-year yearly schedule.
- The job calls `collect_calendar_days_window(...)`, which includes all Romcal celebrations surfaced for each day, including optional/suppressed entries.
- `sync_saint_radar(...)` performs the actual Notion upsert by matching on normalized `Name` plus `Feast Day`, then updates properties or creates a page when missing.
- `dedupe_exact_rows(...)` archives duplicate pages when both the date and normalized title collide in the synced window.
- `collect_calendar_days_window(...)` uses `infer_celebration_rank(...)`, which normalizes special Sundays to `solemnity` and maps Easter Octave weekdays to the pseudo-rank `solemnity-easter octave`.
- The yearly workflow is a backfill-friendly job, not a delete-and-recreate job.
- The same shared helpers are already used elsewhere in the repo, so a calendar repopulation should reuse them instead of inventing a second representation of the liturgical calendar.

### Reuse Opportunities
- Reuse `collect_calendar_days_window(...)` rather than introducing a second Romcal window collector.
- Reuse `sync_saint_radar(...)` for Notion upsert behavior and property mapping.
- Reuse `dedupe_exact_rows(...)` for cleanup after repopulation.
- Reuse the special Sunday / Easter Octave inference logic already embedded in `generate_daily_novena_prayer.py`.
- Reuse the existing workflow inputs for ad hoc backfills instead of adding a separate one-off script.

### External References
- Notion API database query, page create, and page update behavior matter here because the sync job depends on title/date matching and property patching.
- Romcal behavior matters because the job derives both celebration rank and precedence from Romcal mass-calendar rows.

### Constraints
- The live Notion data model is authoritative for the database schema, but its actual contents are not visible in this repo.
- The workflow is date-range driven, so the repopulation must be expressed as a backfill or yearly rerun rather than a manual page-by-page fix.
- If the calendar title or feast-day property names have drifted in Notion, the upsert path may miss rows or create duplicates.

### Risks
- A title/date mismatch in Notion could cause duplicate pages instead of an update.
- The dedupe pass only catches exact normalized duplicates, so near-duplicate rows would survive.
- If the Easter precedence rule changes how Romcal rows are classified, the sync may need both a data backfill and a contract update in downstream jobs.
- The current code path is shared with `sync_saint_radar`, so changes to the liturgical calendar model could have broader effects than the yearly sync alone.

### Assumptions To Validate
- The target Notion database is the intended `Liturgical Calendar` database and has the expected `Name`, `Feast Day`, `Celebration Rank`, and `Precedence` properties.
- Palm Sunday and Easter Sunday should remain included in the synced calendar rows rather than being filtered out.
- The repopulation should preserve existing page identities whenever the date/title pair already exists.
- Running the job for 2026 and 2027 is sufficient for the requested backfill.

### Unknowns
- Whether any existing rows in the live Notion database were manually edited in a way that would break the date/title upsert key.
- Whether the "new logic for Easter precedence" only affects how rows are labeled, or whether it should also affect which rows are included.
- Whether the current dedupe window is broad enough to clean up prior partial imports from the one-time population.

### Recommended Direction
- Proceed to `/plan-astack` after validating the live Notion schema and confirming the exact backfill window for 2026 and 2027.

## Plan

### Summary
- Reuse the existing Liturgical Calendar sync job as the source of truth for repopulating Notion.
- Add narrow regression coverage so we can prove the job is rerunnable, date/title-upsert based, and safe to backfill.
- Run the backfill for `2026-01-01` through `2027-12-31` with the current Easter precedence logic, so both this year and next year are populated in one consistent pass.
- Keep Palm Sunday and Easter Sunday in the synced calendar rows, while preserving the shared special-Sunday / Easter-Octave normalization already in the codebase.

### What Already Exists
- `jobs/novena/sync_liturgical_calendar.py` already computes a date range, collects Romcal rows, upserts into Notion, and archives exact duplicates.
- `jobs/novena/generate_daily_novena_prayer.py` already provides the shared special-Sunday normalization and Easter-Octave precedence mapping used by calendar rows.

### Architecture
- Data flow:
  `Romcal mass calendar -> collect_calendar_days_window() -> sync_saint_radar() -> dedupe_exact_rows() -> Notion Liturgical Calendar`
- The sync job should remain a rerunnable upsert, not a destructive replace.
- The only calendar-specific state we rely on is the existing Notion page identity key: normalized `Name` + `Feast Day`.

```text
Romcal 2026-2027
      |
      v
collect_calendar_days_window()
      |
      v
sync_saint_radar()  --upsert by Name + Feast Day-->
      |
      v
dedupe_exact_rows()
      |
      v
Liturgical Calendar Notion DB
```

### Failure Modes
- If the live Notion schema does not match the expected `Name` / `Feast Day` property names, the upsert key can miss rows and create duplicates.
- If there are manual edits or historical title drifts in Notion, the dedupe pass will only catch exact normalized matches.
- If the backfill window is wrong, the job may leave a gap at the start of 2026 or overpopulate beyond 2027.
- If the live calendar logic changes again later, downstream consumers like ICS export and devotional jobs may need another backfill.
