# v661 — Finished track sometimes stands unmarked: the native completion drain loses the track's identity (occurrence · office side)

## §1 The item (DevOps Board row 1638 · production defect · fix-forward · run level To Ship, same-day notice given in the Ora thread at registration)

John's report (2026-11-25 09:59 CT, verbatim): "Sometimes a song finishes and it's traxk isn't marked. It just happened on singnthr hours this am" — a track plays to completion and its played mark does not land; this morning's instance is a Sing the Hours office track.

Standing discipline the fix must honor: played marks key per copy — occurrence keys (v610) and per SIDE for the office hours (v650: each side its own mark, cache identity, engine hand-off via &src=). v655 fixed the CARD/menu mark write to pass the full key. The COMPLETION path — the mark written when playback finishes a track — is a different path, outside v655's scope.

## §2 Grounding (firsthand, 2026-11-25, on the shipped client at the post-v659 tree + the shell source + an extraction probe driving the real functions)

Base tree: main at the v659 ship (local mirror 7263f14 == remote c34ceeb, tree-exact; pin ora-pro-nobis-v659-1, Worker dd1d9297). The completion machinery is byte-identical to the v660 tree — the v659 card rebase did not touch it (probe §2.5 re-run on this tree, same result).

### 2.1 Two completion paths exist; only one runs on John's phone

- **The web path** — the audio element's `ended` handler calls `markCompleted(state.current)` (client.ts, the ONLY completion writer for the element). It holds the FULL descriptor and writes the full key: `writePlayed(desc.episodeId, d, 'played', desc._occ ? (desc.block || desc._block) : desc.block, desc._occ || 0, desc._side650 || null)`. Correct for every shape (probe Leg 1, the control).
- **The native path** — John's phone (APK 1.0.55) is a one-engine pair: the shell's service is the engine, the element never plays a day track, `ended` never fires. The service records each natural end itself and the page folds the records in through `drainNativeCompletions()`. This is THE completion path on his phone.

### 2.2 The shell knows the finished item exactly — and writes down almost none of it

In the shell (OraLibraryService.kt): `onEngineTransition` (auto) and `onEngineEnded` (the queue's last item) both call `markItemPlayed(contract, item)` with the exact contract item that finished. For a day item it appends to `NativeCompletionsStore` a record of exactly **{episodeId, date = contract.day, block}** (FaceStateStore.kt: "Records are {episodeId, date, block} — identity only"). The contract items themselves carry no more: `nativeContractItem` / `oraSnapshotTrack` serialize {id, block, title, kind, durationS, mediaUri, needsAuth, artUri} — no occurrence, no side. Two further shell facts:

- The store's `add()` dedupes by **(episodeId, date)**: two finishes of the same slot on one day — both office sides under Both, or an original and its duplicate copy — collapse into ONE record; the second add silently replaces the first.
- The service DOES already know the distinguishing facts at the moment of the mark: the item's index in its contract (fromIndex / nativeIndex()) and its mediaUri — for a labeled slot the mediaUri carries `&src=`, naming the side. It simply does not record them.

### 2.3 The client fold writes the base key, whatever finished

`drainNativeCompletions()` folds each record as:

```js
writePlayedQuiet(rec.episodeId, rec.date || presentedDateStr(), 'auto', rec.block || '');
```

`writePlayedQuiet(episodeId, dateStr, via, block, occ, side650)` — occ and side650 are NEVER passed. The write therefore lands on `playedKeyOcc(id, block, 0, null)` — the BASE key — in every case.

The rows read richer keys (`descMarkKey` / `isPlayedDesc`):

| shape | the row reads | the drain writes | result |
|---|---|---|---|
| ordinary episode | `id` (or `id\|block`) | same | **marks** — the "sometimes" |
| office side 1 (first painted, no tag) | `id\|block` | `id\|block` | marks — even when only side 2 played (a FALSE mark) |
| office side 2 (`_side650`, e.g. Divine Office under Both) | `id\|block@do` | `id\|block` | **never marks** |
| duplicate copy (`_occ` ≥ 1, v610) | `id\|block#1` (or `id#1`) | base | **never marks**; the mark lands on copy 0 |

So under Both, the second-painted side's finish marks the FIRST side's row and leaves its own row unmarked — the mark visibly lands on the wrong track or, from the player's seat, "doesn't land" on the track that sounded. This morning's Sing the Hours instance stands in this family: whichever side of the office pair the drain's base key names is not the side whose finish he watched.

### 2.4 The drain also only runs while a live page resolves a contract index

`drainNativeCompletions` has exactly three call sites, all inside `applyNativeState`: the video-boundary arm, the stopped arm, and the current-change arm — the last gated on `nativeContractDescs[st.queueIndex]` resolving to the published track. No call stands at page stand / boot / restore / foreground return. A finish whose publishes reach a dead or backgrounded page (or a resumed standing contract whose descs stand empty, so `changed` never fires) leaves its record sitting in the shell's file store while the row stands unmarked — the store's own header promises "the page applies it … when it next stands", and no stand-time drain exists to make that true. This is the second, independent leg of "sometimes": even a base-key shape (an ordinary episode, a first side) can stand unmarked until the next playback contact.

### 2.5 The probe (Plan-phase, scratch — the release harness at §4 supersedes it)

An extraction probe (the real `playedKey`/`playedKeyOcc`/`descMarkKey`/`isPlayedDesc`/`writePlayedQuiet`/`markCompleted`/`drainNativeCompletions` lifted verbatim from the shipped client.ts, production-shaped descriptors, the shell's record shape) — 7/7 legs as predicted, on BOTH the v660 tree and this post-v659 tree:

- CONTROL: web `markCompleted` marks the DO side and the occ copy exactly, sibling untouched.
- DEFECT: a native record for a DO finish writes only `ext-morning-prayer|Morning` — the finished side reads UNMARKED, the unplayed StH side reads MARKED.
- DEFECT: a native record for an occ-copy finish writes the base key — the finished copy reads UNMARKED.
- Ordinary episode through the drain reads marked.

Coverage note: the standing harnesses never legged this seam with the shapes it drops — harness-v610, harness-v650, and harness-v655 contain ZERO drain legs; the drain was only ever legged with plain identity records (v466 B6, v656). The v645/v655 lesson repeats: the path that was not driven is the path that failed.

### 2.6 What does not move

The mark stores' shapes (localStorage `opn-played-v344`, key grammar incl. `|block`, `#occ`, `@side`), the web completion path, the manual mark paths (v639 row menu · v655 card write), the shell's mark rule (natural end only; skips save position, never mark), and the day-position write-backs. Podcast completions ride the server route from the service and never enter this store — untouched.

## §3 The fix (two legs: shell record + client fold; the seam is the shell→client record, so both sides of it move)

### 3.1 Shell leg (android repo, APK 1.0.56) — the record learns which item finished

- `NativeCompletionsStore.Completion` gains `queueIndex: Int` and `mediaUri: String` (defaulting −1 / "" on parse, so records written by an older shell still read). `add()`'s dedupe key widens to (episodeId, date, queueIndex, mediaUri) — two sides and two copies of one slot on one day each keep their own record.
- `markItemPlayed(contract, item)` gains the item's index (the transition's fromIndex; the ended handler's nativeIndex()) and records `item.mediaUri` with it. No other shell behavior changes: same mark rule, same day-position write-back, same podcast route.
- Version: versionCode 56 / versionName 1.0.56, signer unchanged (CN=Ora Pro Nobis Test — the phone updates in place).

### 3.2 Client leg (client.ts) — the drain resolves the record to its descriptor, then writes that descriptor's full key

`drainNativeCompletions` resolves each record to a standing descriptor before writing, in this order:

1. **By queue index** — `rec.queueIndex` resolves through `nativeContractDescs` and that descriptor's episodeId + block match the record → that descriptor (the contract that produced the record still stands).
2. **By mediaUri** — each candidate descriptor standing in `state.queue` ∪ `state.dayDescs` for the record's (episodeId, block) is run through `oraSnapshotTrack(desc, rec.date)`; a mediaUri equal to the record's names its descriptor. For a labeled slot the pass-through `&src=` distinguishes the sides; this leg is what resolves a record whose contract has already retired (page was dead at the finish).
3. **By sole candidate** — exactly one descriptor matches (episodeId, block) across the same candidate set → it (the common single-source office and ordinary shapes, and every old-shell record for them).
4. **Fallback** — no resolution: today's base-key write, byte-identical (an old-shell record under Both with a dead contract; named limitation, closes as phones take 1.0.56).

The write then mirrors `markCompleted`'s argument shape exactly: `writePlayedQuiet(desc.episodeId, rec.date || presentedDateStr(), 'auto', desc._occ ? (desc.block || desc._block) : desc.block, desc._occ || 0, desc._side650 || null)`, with the standing dayPositions delete and the closing `refreshPlayedChrome()` unchanged.

### 3.3 Client leg — the drain runs when the page stands

One added call: `drainNativeCompletions()` at the day-stand seam (where the restored queue stands / the day paint completes — Implement names the exact seat from the boot path) and on return to the foreground (visibilitychange to visible). The function is already idempotent-shaped (take() empties the store; an empty records list returns silently), so the added calls cost nothing when no record stands.

### 3.4 Rollout honesty

The web leg ships first-class on its own: legs 2–3 of the resolution repair every record an OLD shell can produce for sole-candidate shapes, and the stand-time drain (§3.3) repairs the timing leg for all shapes. The Both/occ identity legs reach full strength only with APK 1.0.56's richer records; the What's New and this doc say so plainly. The APK is a deliverable of this release, built and published to the standing download in the Ship phase (v651 precedent).
