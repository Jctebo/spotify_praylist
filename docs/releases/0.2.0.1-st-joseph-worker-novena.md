# Release 0.2.0.1 - St. Joseph the Worker Novena Publish Debug

Date: 2026-04-28
Status: Shipped
Branch: enhancement/novena-st-joseph-worker
Depends On: 0.2.0.0

## Scope

### Problem
- The novena workflow is not publishing output for Saint Joseph the Worker on Friday even though the liturgical calendar includes that feast.
- We need to understand whether the miss is in contract authoring, novena resolution, or the workflow date window that decides what gets published.
- Why now: the combined publish workflow is already running on a schedule, so missing this feast means the automation is silently skipping a date the calendar already knows about.

### Audience
- Primary user: the maintainer who expects feast-day novenas to appear automatically in the published feed.
- Secondary stakeholders: listeners and podcast apps that depend on the novena feed being populated on the correct feast date.
- Secondary stakeholders: future maintainers who need a clear rule for when a liturgical feast becomes a published novena episode.

### Current Status Quo
- `jobs/novena_contracts/resolver.py` only publishes novenas that are backed by authored contracts, selector rules, or explicit feast mappings.
- `contracts/novenas/` currently has the standard novena template and a Sacred Heart feast example, but no Saint Joseph the Worker contract file was found during repo search.
- `docs/liturgical.ics` includes Saint Joseph the Worker on Friday, which proves the feast exists in the calendar data, but that does not automatically create a novena publish job.
- The combined workflow in `.github/workflows/publish_audio.yml` runs daily and dispatches both audio and novena pipelines, but it does not appear to add feast output on its own.

### Goal
- Determine why Saint Joseph the Worker is not producing a novena publish on the relevant Friday.
- Make the workflow emit the expected novena audio, sidecar, and RSS output when that feast is supposed to be active.
- Treat this feast as part of the solemnity-ranked publish path if the liturgical selector rules say it belongs there.
- Keep the fix additive and specific to this feast-trigger path unless the research shows a broader contract or resolver bug.

### Constraints
- The fix should reuse the existing contract-first novena pipeline rather than reintroducing the legacy novena runtime.
- The combined publish workflow should remain daily and additive unless research shows the schedule window itself is the actual bug.
- Existing novena behavior for other feast-day and selector-based contracts should stay intact.
- Any solution must remain deterministic so the same feast date always resolves to the same episode output.

### Narrow Wedge
- Start by tracing the Saint Joseph the Worker feast from the liturgical calendar into the novena resolver and the combined workflow to find the missing link.
- Check the solemnity clause first, since that is the intended trigger path for this feast.
- If the feast is missing a contract, add the smallest contract mapping needed for that feast rather than generalizing calendar publication rules too early.
- If the contract exists but the workflow window skips Friday, fix the date window and prove the publish job emits the expected artifact.

### Non-Goals
- Do not redesign the full novena contract system.
- Do not add Spotify playlist behavior or Notion sync changes.
- Do not rewrite the whole liturgical calendar integration unless the research proves that is the actual root cause.
- Do not change unrelated public URL or feed-URL work in this branch.

### Risks And Unknowns
- The biggest unknown is whether this is a missing feast contract, a resolver selection bug, or a workflow date-window problem.
- It is also unclear whether the intended behavior is to publish on the feast date itself, the novena prep window, or both.
- If the feast has no authored contract yet, we need to decide whether to model it as an explicit feast override or as part of a selector family.

### Recommended Next Step
- Run `/research-astack` to map the Saint Joseph the Worker path through the novena contracts, resolver, and combined workflow, then confirm which missing piece is preventing publication.

## Research

### Scope Baseline
- Debug why the novena pipeline is not publishing Saint Joseph the Worker on Friday, even though Romcal includes that feast in the calendar data.

### Relevant Files
- `jobs/novena_contracts/resolver.py` - current selection logic for feast-day and selector-based novenas; this is where the date rows are filtered and the likely bug sits.
- `jobs/novena_contracts/contracts.py` - defines the selector ranks and novena contract shapes that the resolver is supposed to honor.
- `jobs/novena/liturgical_helpers.py` - provides Romcal access plus rank/precedence helpers used by the resolver to decide whether a day is eligible.
- `contracts/novenas/families/standard-9-day.json` - the selector family currently accepts `solemnity`, `feast`, `memorial`, and `optional_memorial`, so Saint Joseph the Worker should be eligible if the resolver reaches the right row.
- `docs/liturgical.ics` - confirms Saint Joseph the Worker is present on May 1 in the local calendar data.
- `tests/test_novena_pipeline.py` and `tests/test_novena_job.py` - existing novena coverage; useful for adding a regression around multi-row liturgical days.

### Current System Map
- `resolve_active_novenas()` asks Romcal for the day rows and currently takes `rows[0]` as the primary celebration.
- On May 1, 2026, `romcal_fetch_day("general_roman", "en", date)` returns the weekday first and Saint Joseph the Worker second.
- `infer_celebration_rank()` classifies the first row as `weekday`, and `devotional_output_is_eligible()` rejects that rank.
- Because the resolver stops after testing the first row, it never evaluates the Saint Joseph the Worker optional memorial row that appears later in the same day.
- This means the bug is not a missing feast contract in the current repo shape; it is a row-selection bug inside the selector resolver path.

### Reuse Opportunities
- Reuse the existing selector family in `contracts/novenas/families/standard-9-day.json`; it already allows `optional_memorial`, which matches the Saint Joseph the Worker calendar row.
- Reuse the existing `romcal_fetch_day()` and rank helpers instead of adding a separate calendar query path.
- Reuse the novena pipeline and feed writing flow once the resolver is fixed; the rest of the publish stack already knows how to render and publish the output.

### External References
- Romcal calendar data, as surfaced through `romcal_fetch_day()` and the generated `docs/liturgical.ics`, is the source of the feast ordering behavior.
- No external API change appears to be needed; this is a local selection bug in how the repo reads Romcal rows.

### Constraints
- The fix should keep the contract-first novena model intact.
- Existing feast-day and selector-family behavior should continue to work for other days.
- The resolver should remain deterministic and should not start publishing from every row on the calendar day unless that is explicitly intended.

### Risks
- The current resolver may be skipping any day where the first Romcal row is a weekday or otherwise ineligible, not just Saint Joseph the Worker.
- If the fix is too broad, it could start publishing on suppressed or incidental rows that happen to share the same date.
- If tests only cover single-row days, this bug could regress again without detection.

### Assumptions To Validate
- Saint Joseph the Worker should be published via the existing selector family path, not via a new dedicated feast contract.
- The intended liturgical rank to honor here is `optional_memorial`, not `weekday`.
- The workflow date window is correct and the missing publication is not caused by the schedule itself.

### Unknowns
- Whether the resolver should choose the highest-ranked eligible row on a given date by iterating all rows and taking the first eligible candidate, or by collecting all eligible rows and sorting by precedence before choosing.
- Whether any other multi-row dates have the same failure mode and need a shared regression.

### Recommended Direction
- Update the resolver to evaluate every Romcal row for a date and select the first eligible celebration by rank/precedence instead of stopping after `rows[0]`, then add a regression that proves Saint Joseph the Worker on May 1 resolves through the selector family path.

## Plan

### Summary
- We are fixing the novena resolver so a multi-row Romcal day is scanned end to end instead of stopping at the first row.
- The chosen behavior is: ignore ordinary weekday rows, keep the existing rank gate, and publish the first eligible celebration that matches the selector family.
- This is the smallest change that makes Saint Joseph the Worker publish on Friday without broadening the system to treat normal weekdays as novena triggers.

### What Already Exists
- `jobs/novena/liturgical_helpers.py` already classifies devotional eligibility and already excludes `weekday` rows.
- `contracts/novenas/families/standard-9-day.json` already allows `solemnity`, `feast`, `memorial`, and `optional_memorial`, which covers Saint Joseph the Worker.
- `jobs/novena_contracts/pipeline.py` and `jobs/novena_contracts/rss_publisher.py` already know how to turn resolved novenas into output once the resolver returns the right runtime.
- `tests/test_novena_resolver.py` already exercises selector-family resolution and explicit override precedence, so it is the right place to add the regression.

### Architecture
- Flow:

```text
Romcal day rows
    -> resolver scans rows in order
    -> skip rows that fail devotional eligibility
    -> skip rows whose rank is not in the selector contract
    -> skip rows hidden by explicit feast overrides
    -> pick the first eligible celebration
    -> pipeline renders audio and rebuilds RSS
```

- We do not need a new workflow, new contract family, or a new liturgical helper boundary.
- The fix stays inside the existing resolver-to-pipeline path.

### Concrete Changes
- `jobs/novena_contracts/resolver.py`
  - Update `resolve_active_novenas()` so selector-based contracts iterate every `romcal_fetch_day()` row instead of only checking `rows[0]`.
  - Preserve the current gates: devotional eligibility, selector rank filtering, explicit override de-duplication, and active novena date-window checks.
  - Select the first eligible row in Romcal order and build the runtime from that row.
- `tests/test_novena_resolver.py`
  - Add a regression for a multi-row feast day where row 0 is a weekday and row 1 is `optional_memorial`.
  - Assert that the resolver skips the weekday and resolves Saint Joseph the Worker through the selector family path.
- `tests/test_novena_pipeline.py`
  - Add or extend one pipeline smoke test only if needed to confirm the resolver change still flows through to published novena output.

### UX And States
- There is no UI change in this fix.
- User-visible behavior is simply that the expected novena now appears for Saint Joseph the Worker on the feast date.
- Failure should remain fail-closed: if no eligible row exists, the day stays unpublished rather than falling back to a weekday.
