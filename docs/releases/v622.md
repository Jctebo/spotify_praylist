### The gate inventory — grounded firsthand from the code

Every PIN prompt in the app stands on one of two seams:

**Seam A — `renderPinGate`** (the PIN-token gate: pad → POST /api/pin/verify → session token). Its seats: the **Conscience tab gate** (`gatedTabRender('conscience', …)`) · the **Settings entry gate** (`renderPinGate('settings', …)` from the CONFESSION PIN card) · the **refusal re-stand** (`pinRefusalGate`, on token expiry). This seam carried **no biometric path at all** — the named defect: "Conscience still uses pin."

**Seam B — the vault unlock card** (`opnUnlockCardHtml` + `opnBindUnlockCard`, the v587 pad card). Its seats: **`profVaultGate594`** (the Configure surfaces, the in-place editor, the ladder screens) · the **slot picker** (v596, three seats, all through profVaultGate594) · the **Praylist lock gate** (`opnBindLockGate609`, which additionally auto-fires the prompt on visit, v609 repair 2) · the **Intentions** surface · the **Favorites** page · **Settings → My data on this phone**. This seam already had a biometric button (manual tap, revealed when the bridge reports available + enrolled) with v606 error surfacing — but nothing governed it: no preference read it, and the Conscience seam had no path to honour.

**The PIN set flows — grounded:** exactly one create flow exists: `openPinSetSheet('set')` → POST /api/pin/set → `opnPinSet` + `opnVaultCreate` in the same action (the vault create rides the set). The re-set flows: `renderPinRecoveryForm` (Conscience gate's recovery) and the unlock card's recovery form (both → /api/pin/recover → rewrap). Change PIN (`openPinSetSheet('change')`) re-strikes the PIN + recovery wraps only. Enrolment before v622 stood only in Settings → CONFESSION PIN, behind four conditions (PIN set · session unlocked · device mode · vault standing), and only while native status read available + not-enrolled.

**The biometric machinery (v578/v606, unchanged):** the shell bridge `OraDayBridge` holds a Keystore-wrapped copy of the raw vault key behind the device prompt; the client's four calls are `vaultBiometricStatus / Enroll / Unlock / Clear`. Enrolment requires the raw vault key in memory (a PIN unlock / set / recover in this session). John's fingerprint stands enrolled since 2026-11-21 (v606 field confirmation); his PIN record carries the advisory `biometricEnrolled` flag.

## §2 Decisions (adopted under the overnight approval)

- **D1 — One preference, stored where a locked gate can read it.** The Touch ID preference is one boolean, `biometricPref`, on the on-device PIN record (OPN_PIN_KEY) — the one store every gate can read while the vault stands locked (the personal document is ciphertext then; the PIN record already carries the enrolment flag). An absent field reads **ON**: the default follows his standing state (fingerprint enrolled; the Praylist already prompts first). The switch stands in Settings → CONFESSION PIN whenever a PIN is set in the device shape, locked or unlocked; flipping it writes that one field and nothing else — PIN hash, wraps, and enrolment are untouched. PIN remove deletes the record whole, preference with it (no PIN → no gates → the preference is moot; a later set re-defaults). Read through one helper, `opnBioPref622()`, device mode only — on the web there is no local PIN record and no bridge, so the helper reads off and every gate keeps its standing shape.
- **D2 — Every gate reads the one preference.** Seam A gains the biometric path (§3): under the preference with an enrolment standing, the prompt fires **first** on the gate's stand (once per stand, the Praylist discipline), the button stands for manual retry, and success does exactly what a PIN verify does — the vault key is applied by the standing unlock, and the session token is issued from the client's own registry (`opnPinIssueToken`, the one the local layer checks). Seam B's button reveal, the Praylist auto-fire, and the Praylist enrolment note all read the same helper. Preference **off**: every gate is PIN-only, painted exactly as before v622 — no button, no fire, no note.
- **D3 — The Conscience boundary does not move.** The PIN gate stays on the Conscience tab only; no new gate appears anywhere. The Conscience gate gains the biometric path under the same preference — that is the whole of the named defect's fix.
- **D4 — Enrolment onboarding inside PIN setup.** One helper, `opnBioOffer622(next)`, stands a sheet offering fingerprint enrolment as the flow's own next step — after the recovery code's one showing — at every seat where a PIN is (re)set with the vault key in memory: the **set sheet**, the **Conscience recovery form**, and the **unlock card's recovery form**. The offer stands only when it can complete (device mode · preference on · vault standing · bridge available · not already enrolled) and enrols through the standing `opnBiometricEnroll`. Skipping leaves PIN-only working whole. **Change PIN does not offer**: the biometric wrap seals the raw vault key, which a PIN change never rotates (v606 diagnosis, cause 4), so an enrolment survives a change; the Settings re-enrol line covers the rest. The Settings enrol / re-enrol acts stand untouched.
- **D5 — Web-only; no APK.** Every biometric call the fix makes is a standing v606 bridge method (proven by grep: the client calls exactly the four, harness T2). The gate's token issue is client-side. No native method, no manifest change, no new signer risk — **no APK bump ships with v622**; APK 1.0.52 stands.
- **D6 — Failures named, as v606 set.** A failed prompt at the gate names its bridge code in the gate's message and the pad stands as fallback. A `key-invalidated` failure clears the stale wrap, retires the act, and names the re-enrol seat (Settings → CONFESSION PIN). The PIN lockout (retry-after) governs PIN attempts as before; the biometric prompt is a separate factor under the OS's own lockout and fires regardless — recorded, not left implicit.
- **D7 — The passkey stands apart.** The unlock card's passkey button is a separate unlock (WebAuthn PRF), not the Touch ID preference; it is untouched.
