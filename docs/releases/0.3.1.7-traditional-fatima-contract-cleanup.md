## Scope

### Problem
- The traditional Our Lady of Fatima novena contract is hard to read because it inlines the same `Our Father`, `Hail Mary`, and `Glory Be` sequence twice, so the day body currently contains six of each prayer instead of the intended three.
- That makes the source brittle to edit and hard to verify against the intended prayer count.
- The current shape is easy to misread as an accidental duplicate, even though the extra cycle should be removed.

### Audience
- Primary user: the maintainer who needs to audit and update the traditional Fatima novena content.
- Secondary users: listeners who rely on the same prayer sequence being published every day of the novena.
- Secondary stakeholders: future maintainers who need a contract shape that makes repeated prayer cycles obvious.

### Current Status Quo
- The checked-in traditional Fatima contract repeats the three-prayer set twice inside each daily block instead of expressing the repetition once.
- The content still renders, but the source makes it hard to tell whether the duplication is intentional or accidental.
- The short-form Fatima companion is out of scope for this cleanup.
- The branch also carries two adjacent manual contract cleanups: Morning Prayer no longer ships a duplicate petition block, and the Daily Examen queue contract no longer points at a malformed Spotify URI.

### Goal
- Make the traditional Fatima contract easier to read and maintain while reducing the daily prayer body to one `Our Father` / `Hail Mary` / `Glory Be` cycle, each repeated three times.
- Preserve the day structure and feast-day behavior.
- Success criteria: the contract source is clearer, the rendered output contains exactly three of each canonical prayer, and tests prove the cleaned structure still publishes correctly.
- Ship the adjacent manual contract cleanups without reintroducing duplicate Morning Prayer text or breaking the Daily Examen queue contract.

### Constraints
- Do not change the spoken prayer wording or the feast-day schedule.
- Do not alter the listener-facing output unless research proves the current double cycle is actually wrong.
- Keep the fix narrow to the traditional Fatima novena contract and any shared template or fragment it can reuse.
- Avoid changes to Spotify playlist logic or unrelated novena contracts.
- Keep the manual Morning Prayer and Daily Examen contract adjustments valid so the broader branch still loads cleanly.

### Narrow Wedge
- Remove the duplicated second prayer cycle from the traditional Fatima daily block so the source defines one `Our Father` / `Hail Mary` / `Glory Be` trio, each repeated three times.
- Prove the rendered text and audio now contain exactly three of each canonical prayer.

### Non-Goals
- Do not redesign the novena engine.
- Do not rewrite the Fatima prayer text.
- Do not change how novena dates, titles, or feed entries are generated.
- Do not touch the short-form Fatima contract.
- Do not tackle other novenas that happen to reuse the same prayer trio unless they block the Fatima cleanup.
- Do not expand the branch into any new Spotify playlist feature work.

### Risks And Unknowns
- The duplicated trio may have been preserved intentionally by the original import, so removing it changes the historical source shape.
- A source-only cleanup could still change output if fragment repetition or day mapping is normalized incorrectly.
- It is unclear whether the best cleanup is a manual fixture edit or a regeneration from the importer with the extra cycle removed.
- The manual contract cleanup outside Fatima could leave stale expectations in publish or Spotify tests if the contract counts or URI shapes are not kept in sync.

### Recommended Next Step
- Run `/plan-astack` to choose the exact contract-only normalization shape, then define the regression tests needed to prove the traditional Fatima output stays at three of each canonical prayer.

## Research

### Scope Baseline
- The requested cleanup is for the shipped traditional Our Lady of Fatima novena contract only.
- The issue is in the contract representation itself: the JSON fixture is overly expanded and repeats the same prayer trio twice inside each daily block.
- The goal is to make the contract source easier to read and maintain without changing the published prayer sequence or feast-date behavior.

### Relevant Files
- `contracts/novenas/feast-days/our_lady_of_fatima.json` - primary fixture to clean up; it contains the traditional Fatima blocks, sections, and the duplicated prayer cycle.
- `contracts/novenas/feast-days/our_lady_of_fatima_short_form.json` - comparator only; the short-form companion exists but is explicitly out of scope.
- `config/publish/contracts/morning-prayer.json` - manual Morning Prayer contract cleanup that removes the duplicated `petition-church` content from the petitions sequence.
- `config/publish/templates/morning-prayer/petition-church.txt` - retired petition text file removed by the Morning Prayer cleanup.
- `config/spotify/contracts/daily-examen.json` - Daily Examen queue contract that now needs a valid Spotify episode URI shape.
- `config/spotify/contracts/daily-examen-labor.json` and `config/spotify/contracts/daily-examen-parents.json` - removed sidecar contracts from the Daily Examen cleanup.
- `jobs/novena_contracts/contracts.py` - loads novena contracts into `TemplateSpec`, `TemplateSection`, `TemplateFragment`, and `NovenaRuntime`.
- `jobs/novena_contracts/validators.py` - defines what the novena template schema can express, including `fragment_key`, `repeat`, `blocks`, and `fragments`.
- `jobs/novena_contracts/url_import.py` - shows the repo’s existing compaction path for canonical prayer text and repeated fragments.
- `jobs/novena_contracts/engine.py` - renders repeated fragment parts into audio/text output, so the source can change without changing the runtime result.
- `jobs/playlist/spotify_contracts.py` - validates queue contract URI shapes, which is why the Daily Examen cleanup must keep a real `spotify:` URI.
- `tests/test_novena_url_import.py` - proves the importer compacts repeated canonical prayers into fragment parts and fragment libraries.
- `tests/test_novena_engine.py` - proves the runtime flattens repeated fragment parts into the rendered output.
- `tests/test_novena_contracts.py` - proves embedded templates and repeated fragment metadata survive contract loading.
- `tests/test_publish_contracts.py` - covers the Morning Prayer publish contract shape and fragment counts.
- `tests/test_spotify_contracts.py` and `tests/test_refresh_job_contract_path.py` - cover Spotify queue contract loading and the Daily Examen path through the refresh job.

### Current System Map
- Novena contract loading already supports `blocks`, `sections`, `fragments`, and per-fragment `repeat` counts.
- Canonical prayers such as `Our Father`, `Hail Mary`, and `Glory Be` are already reusable fragment assets in the novena importer path.
- The engine expands repeated fragment parts at render time, so the contract can be structurally cleaner without altering what listeners hear.
- The traditional Fatima fixture currently carries very large day bodies and a duplicated prayer cycle directly in the fixture, which makes the contract hard to audit even though the underlying schema already supports fragment reuse.
- The short-form Fatima fixture uses the same contract family machinery but is not part of this cleanup.
- The Morning Prayer contract still uses the publish contract sequence model, so pruning a petition block should be reflected in the fragment-count test rather than in runtime code.
- The Daily Examen entry still uses the Spotify queue contract model, so its URI must stay in a loader-approved `spotify:` shape even when the sidecar contracts disappear.

### Reuse Opportunities
- Reuse the importer’s canonical prayer fragment library and `repeat` handling instead of inventing a new contract syntax.
- Reuse the existing block/fragment schema if the cleanup is expressed as a fixture rewrite rather than a new feature.
- Reuse the existing tests for importer compaction and engine flattening to verify that source cleanup does not change rendered output.
- Reuse the traditional Fatima contract’s current feast/date metadata and keep the runtime identity unchanged.
- Reuse the short-form contract only as a shape reference, not as a target for changes.
- Reuse the publish-contract fragment-count tests and Spotify queue validation tests to keep the manual contract cleanup from drifting.

### External References
- No external API or third-party spec change is required for this cleanup.
- The only external dependency involved indirectly is the bundled Romcal data used by contract validation and feast-date resolution, but the cleanup itself should stay local to the fixture.

### Constraints
- Preserve the exact traditional Fatima prayer wording and day structure while correcting the prayer count to three of each canonical prayer.
- Do not change title generation, episode ids, or feed identity for this release.
- The schema supports repeating a fragment, but not a higher-order grouped repeat of an entire `Our Father` / `Hail Mary` / `Glory Be` cycle, so any cleanup has to fit the existing contract language.
- Keep the change narrow enough that unrelated novenas do not drift.
- Keep the Morning Prayer contract change limited to removing the duplicate petition file entry, and keep the Daily Examen contract change limited to restoring a valid Spotify queue URI.

### Risks
- The duplicated cycle may be intentional liturgical structure, not accidental duplication.
- A naive rewrite could change output if the repeated cycle is normalized incorrectly or if day-level section text diverges from the compacted block.
- If the contract is regenerated from importer logic, notes and section ordering may change even when the audible output stays the same.
- Changing the fixture shape could accidentally create a precedent that affects other feast-day contracts that use the same importer conventions.
- The manual contract cleanup could accidentally invalidate the publish or Spotify loaders if the old counts or URI shapes were preserved too literally.

### Assumptions To Validate
- The user wants the traditional fixture cleaned up, not the short-form companion.
- The intended published output for each Fatima day is one three-prayer cycle, not the current duplicated cycle.
- The desired cleanup is source organization and readability, not a change in prayer content.
- It is acceptable for the cleaned contract to express the same output via fragments or a more compact imported shape.

### Unknowns
- Whether the safest cleanup is a hand-edited fixture normalization or regenerating the contract through the importer path.
- Whether the day sections should remain fully expanded for readability or be condensed to mirror the reusable block structure.
- Whether the tests should assert exact fixture structure, exact rendered output, or both.

### Recommended Direction
- Run `/plan-astack` to choose the exact contract-only normalization shape, then define the regression tests needed to prove the traditional Fatima output stays identical without changing any runtime code.

## Plan

### Summary
- Normalize the traditional Our Lady of Fatima contract so each day publishes one `Our Father` / `Hail Mary` / `Glory Be` cycle, with each prayer repeated three times.
- This is a contract-data fix, not a runtime refactor: the novena loader and renderer already support the structure we want.

### What Already Exists
- `jobs/novena_contracts/contracts.py` already loads the Fatima fixture into blocks, fragments, and repeat counts without needing code changes.
- `jobs/novena_contracts/engine.py` already renders repeated fragment parts into final text/audio output.
- `jobs/novena_contracts/url_import.py` already uses the same canonical prayer fragments and repeat counts that the fixed Fatima contract should mirror.
- Existing novena tests already cover contract loading and render-time fragment expansion, so we can add a Fatima-specific regression rather than inventing a new harness.

### Architecture
- No new services, branches, or feature flags.
- The fix stays in the source contract and the test suite.
- Flow remains:

```text
our_lady_of_fatima.json
  -> load_novena_contracts()
  -> resolve_active_novenas(today)
  -> render_novena(runtime)
  -> write_novena_artifact()
  -> RSS / audio output
```

### Concrete Changes
- `contracts/novenas/feast-days/our_lady_of_fatima.json`
  - Remove the duplicated second `Our Father` / `Hail Mary` / `Glory Be` cycle from `novena.template.blocks[1].parts`.
  - Keep the remaining three fragment parts at `repeat: 3`.
  - Update the block notes so they describe a single cycle instead of two.
- `tests/test_novena_contracts.py`
  - Add a Fatima-specific fixture test that asserts the `days-1-9` block contains exactly three fragment parts with keys `our_father`, `hail_mary`, and `glory_be`, each repeated three times.
- `tests/test_novena_engine.py`
  - Add a render regression using the real traditional Fatima contract/runtime that asserts the rendered text contains exactly three occurrences of each canonical prayer and no second cycle remains.

### UX And States
- No UI state changes.
- Success means the traditional Fatima day sounds like one three-prayer cycle, not two.
- Failure means the fixture still contains the second cycle or a prayer was removed entirely.
- If the contract becomes malformed, the novena load should still fail closed before publish output is written.

### Implementation Phases
#### Phase 1: Normalize the Fatima fixture
- Goal: remove the extra prayer cycle from the traditional Fatima contract source.
- Exact files to edit: `contracts/novenas/feast-days/our_lady_of_fatima.json`
- Symbols/interfaces touched: `novena.template.blocks[1].parts`, block notes, canonical fragment repeat counts.
- Change summary: delete the second `Our Father` / `Hail Mary` / `Glory Be` triplet so the daily block expresses one cycle of three prayers repeated three times.
- Verification steps or commands: run a small JSON count check against `contracts/novenas/feast-days/our_lady_of_fatima.json` to confirm the block has exactly three fragment entries and the repeat counts are `[3, 3, 3]`.
- Rollback note: restore the second cycle if the content owner says the six-prayer shape was intentional.
- Dependencies on earlier phases: none.

#### Phase 2: Add regression coverage
- Goal: prove the contract source and rendered output both reflect the intended three-prayer count.
- Exact files to edit: `tests/test_novena_contracts.py`, `tests/test_novena_engine.py`
- Symbols/interfaces touched: `load_novena_contracts()`, `render_novena()`, Fatima fixture loading and rendered text assertions.
- Change summary: add one fixture-shape assertion and one render-time count assertion for the real traditional Fatima contract.
- Verification steps or commands: `python -m unittest tests.test_novena_contracts tests.test_novena_engine`
- Rollback note: remove the new assertions only if the contract shape changes for a documented reason.
- Dependencies on earlier phases: depends on Phase 1 fixture normalization.

### Failure Modes
- The second prayer cycle remains in the fixture, so the rendered body still contains six of each prayer.
- The first cycle is removed too aggressively, so the rendered body contains fewer than three of a prayer.
- The regression tests should catch both by checking the loaded block parts and the rendered canonical-prayer counts.

### QA And Test Matrix
- `tests/test_novena_contracts.py`
  - Assert the real Fatima fixture loads with a single `days-1-9` cycle.
  - Assert the block contains exactly `our_father`, `hail_mary`, and `glory_be`, each with `repeat == 3`.
- `tests/test_novena_engine.py`
  - Render the real traditional Fatima runtime with a fake text generator.
  - Assert the rendered text contains exactly three `Our Father` texts, three `Hail Mary` texts, and three `Glory be` texts.
  - Assert the rendered text does not include a second repeated cycle.
- Command: `python -m unittest tests.test_novena_contracts tests.test_novena_engine`

- Existing published items are unaffected unless the feed is rebuilt from the updated contract.

### Not In Scope

- Any novena engine or importer refactor.

### Open Questions
