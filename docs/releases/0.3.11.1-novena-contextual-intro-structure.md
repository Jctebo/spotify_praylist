# Release 0.3.12.0 — Novena Contextual Intro Structure

Branch: enhancement/novena-contextual-intro-structure

## Scope

### Problem
- Novena openings currently prioritize a natural prayer-led invitation, but do not require listeners to first hear the standard Ora Pro Nobis welcome, the exact novena day, a concise identity of the saint or sacred event, and a clear connection to today’s calendar.
- A consistent structure is needed across generated, short-form, and traditional novenas without changing their prayer bodies.

### Audience
- Primary user: a listener starting a daily Ora Pro Nobis novena episode.
- Secondary stakeholders: maintainers who need safe, fact-bounded generated copy and deterministic behavior when the LLM is unavailable.

### Current Status Quo
- All novena types flow through the shared novena devotional-intro profile, which receives the saint/event name, novena day, daily focus, and canonical liturgical context.
- The current prompt favors natural one- or two-sentence prose and gives calendar material a priority order, but does not make the welcome, day announcement, saint/event description, patronage, and single calendar bridge explicit output requirements.

### Goal
- Every novena opening begins with the standard Ora Pro Nobis welcome and explicitly welcomes the listener to Day {N} of the named novena.
- For saint novenas, include a brief, supplied-context-only description of the saint’s life and patronage; for mysteries, Marian titles, or events, give a brief description of the event or devotion instead.
- End the opening with one sentence that connects the novena to today’s winning calendar focus, using the existing priority order: solemnity/feast, Gospel, memorial, liturgical season, then fallback.
- Preserve reverence, TTS-friendly prose, fallback safety, cache freshness, and the unchanged novena prayer body.
- Ensure a saint or event has one active novena form: use its traditional contract when present; otherwise generate one checked-in short-form contract that references the reusable standard template.
- Audit the completed traditional catalog against effective calendar dates and devotion identity, correct erroneous calendar mappings, and retain one active contract for each duplicate devotion.

### Constraints
- The LLM must not invent biography, patronage, or historical claims; it may only use structured contract/context data supplied to it.
- The existing daily-calendar winner remains the sole source for the bridge’s priority; no new calendar-selection system is introduced.
- Non-novena prayer introductions, voices, RSS behavior, and contract prayer content are out of scope.
- Multiple distinct saints or devotions may legitimately share a calendar date; those are not catalog duplicates.

### Narrow Wedge
- Add a deterministic catalog audit and repair the known duplicate/mis-mapped contracts, including reusable relative movable-feast rules for the recorded exceptions.

### Non-Goals
- Rewriting every novena prayer or manually adding biographies to all existing contract bodies.
- Changing the liturgical calendar provider or its priority rules.
- Guaranteeing patronage where the available canonical data does not support it.
- Removing distinct devotions merely because their feast dates coincide.

### Risks And Unknowns
- Existing contract metadata may not contain concise, authoritative biography and patronage fields for every saint or event.
- A strict multi-part opening could exceed the current one- or two-sentence length target, so the spoken-length and sentence policy may need a controlled adjustment.
- Imported source labels can resolve to a nearby but incorrect Romcal identifier; date equality alone is therefore insufficient evidence of a duplicate.

### Recommended Next Step
- Enumerate the supported Romcal calendar across a representative multi-year range, generate one short-form reference contract for every eligible celebration lacking a traditional contract, and make the selector redundant or retire it after parity verification.

## Research

### Scope Baseline
- Keep the existing branded Ora Pro Nobis welcome, then make each novena-specific opening announce the named Day N, briefly identify the saint or event, and end with one bridge sentence based on the canonical daily-calendar winner.
- Store LLM-seeded identity and patronage metadata in explicit traditional contracts; keep the standard short-form contract's baseline prompts in its reusable selector contract.

### Relevant Files
- `jobs/novena_contracts/engine.py` — builds the novena context and generates the Day N intro fragment shared by fixed, hybrid, short-form, and traditional contracts.
- `jobs/publish/devotional_intro.py` — owns the novena prompt, generated-output validation, deterministic fallback, retry, and freshness policy version.
- `jobs/publish/daily_liturgical_context.py` — selects the canonical calendar focus in the required order: major feast, Gospel, memorial, season, fallback.
- `jobs/publish/audio_branding.py` and `config/publish/audio_branding.json` — already prepend the standard Ora Pro Nobis welcome (`Welcome to Ora Pro Nobis. Where we pray with the saints.`) when final audio is assembled.
- `jobs/novena_contracts/contracts.py` and `jobs/novena_contracts/validators.py` — load and validate the reusable `saint`, `feast`, and `novena` contract payloads; this is the appropriate seam for new intro metadata.
- `tests/test_publish_devotional_intro.py` and `tests/test_novena_engine.py` — direct coverage for intro rules, fallback behavior, context propagation, and first-fragment ordering.

### Current System Map
- `render_novena` builds a runtime context, delegates to the shared `NOVENA_PROFILE`, and places the resulting Day N fragment before the prayer body.
- Final audio rendering applies the branded welcome independently of novena text fragments. The requested sequence is therefore already partly present: branded welcome, then a novena-specific Day N intro, then the prayer.
- The shared intro profile is currently constrained to one or two sentences and validates only the day and daily novena focus for novenas. Its fallback is likewise generic.
- The daily liturgical context persists the selected `source`, celebration/season/Gospel material, and shared transition. The novena context receives that payload unchanged, so the bridge can follow the existing selection without reimplementing priority rules.
- Explicit contracts expose a saint/event identity and now carry contract-owned intro metadata. The standard short-form contract is intentionally generic: import/resolution supplies the calendar saint and its baseline prompt at materialization time.

### Reuse Opportunities
- Reuse final audio branding for the standard welcome; do not duplicate it in the generated novena prose or create a second welcome fragment.
- Add intro metadata to explicit contracts, and add baseline intro-prompt guidance to the standard short-form selector; thread both through `runtime_context` and the shared intro generator.
- Reuse the established `daily_liturgical_context.source` winner and its supplied fields for exactly one bridge sentence.
- Reuse policy-version freshness to regenerate future target-date novena sidecars after the intro contract changes.

### External References
- No external API change is required for the calendar bridge; it is wholly sourced from the existing Romcal/Gospel-derived daily context.
- Authoritative sources will be required to populate a complete saint-life/patronage and event-description catalog; the repository does not currently contain one.

### Constraints
- A requirement that every saint include patronage cannot be satisfied faithfully from current contract metadata.
- Scraping or parsing claims from prayer bodies would be error-prone, difficult to review, and could treat devotional wording as biography; it should not be used as an intro-data source.
- The additional identity and bridge content will likely require a controlled three- to four-sentence intro allowance, while keeping the standard branded welcome outside that count.

### Risks
- The highest-risk part is preserving resolver precedence so a traditional contract is selected instead of the standard short-form contract for the same calendar saint/event.
- Validation based only on string presence cannot prove a generated biography is factually supported unless the allowed metadata is separately passed and checked.
- Duplicating the welcome in the intro would produce a repeated welcome because branding already plays it first.

### Assumptions To Validate
- The requested “standard intro” means the existing audio-branding welcome, not a second spoken welcome inside the novena-specific generated fragment.
- The intended routing is one novena per calendar saint/event: traditional when present, otherwise the materialized standard short form.

### Unknowns
- None. The user has chosen LLM-seeded, production-eligible metadata for explicit contracts and baseline prompts for the standard short-form contract.

### Recommended Direction
- Preserve the existing resolver route: traditional contract first, standard short-form contract otherwise. Apply explicit-contract metadata to traditional novenas and baseline prompt guidance to the materialized short-form novena, then enforce the common Day N and calendar-bridge structure.

## Plan

### Summary
- Keep the generic selector-based standard short-form contract as the reusable standard path for calendar saints without a traditional contract. Existing traditional contracts own their LLM-seeded intro metadata; the standard short-form contract owns a baseline LLM prompt that produces its saint/day identity and calendar bridge from the resolved calendar saint.
- Use that record immediately in the spoken novena intro, after the existing branded welcome and Day N announcement, then add exactly one sentence bridging to the already-selected calendar focus.
- This is the chosen approach because it keeps traditional novenas authoritative while retaining the existing calendar-driven short-form coverage and its baseline prompts.

### What Already Exists
- `jobs/publish/audio_branding.py` already speaks the standard Ora Pro Nobis welcome before all novena audio.
- `jobs/novena_contracts/engine.py` builds one first intro fragment for every fixed, hybrid, short-form, and traditional novena path.
- `jobs/publish/daily_liturgical_context.py` already selects and exposes the calendar winner in the required priority order.
- `scripts/new_novena_contract.py`, the contract loader, and the URL importer provide established patterns for producing and validating repo-owned JSON contracts.
- `jobs/novena_contracts/url_import.py` contains the repository’s existing OpenAI request, JSON parsing, and failure-handling conventions.

### Architecture
```text
traditional contract                         standard short-form contract
  ├─ saint/event + LLM-seeded intro metadata   ├─ baseline short-form prompts
  └─ fixed/romcal feast rule                    └─ calendar selector
                    \                           /
                     v                         v
                 import/resolver materializes traditional first; otherwise short form
             |
             v
runtime context + canonical daily calendar winner
             |
             v
Ora Pro Nobis branded welcome (existing audio branding)
             |
             v
Day N + identity/patronage or event summary + one calendar bridge
             |
             v
unchanged novena prayer body
```

### Concrete Changes
- Add `intro` schema support to `jobs/novena_contracts/validators.py` and preserve it through `jobs/novena_contracts/contracts.py` runtime payloads. The schema will require:
  - `kind`: `saint` or `event`;
  - `summary`: one concise, TTS-safe identity description;
  - `patronage`: a non-empty string list for saints and an empty list for events;
  - seed provenance (`provider`, `model`, `generated_at`) for the initial LLM-generated entries.
- Add `scripts/seed_novena_intro_metadata.py`, a deliberate local CLI that calls OpenAI for strict JSON, validates the returned record, supports `--dry-run`, `--contract`, `--model`, and `--force`, and writes only explicit contract `intro` blocks. The seed is production-eligible as directed; failures leave the existing contract unchanged.
- Add baseline `intro_prompt` guidance to `contracts/novenas/families/standard-9-day.json` so the existing dynamic short-form contract uses the resolved calendar saint, the established short-form daily-focus prompts, and the canonical calendar bridge without requiring a separate checked-in contract for every saint.
- Preserve the auto-selected `contracts/novenas/families/standard-9-day.json` source. During contract import/resolution, the existing explicit-contract precedence materializes a traditional novena when present and otherwise materializes the standard short form for the resolved calendar saint; no per-saint short-form JSON migration is created.
- Update `jobs/novena_contracts/engine.py` to pass `intro.kind`, `intro.summary`, and `intro.patronage` into the shared novena intro context.
- Update `jobs/publish/devotional_intro.py` to use a three-part novena-specific structure after the already-branded welcome: Day N announcement, supplied identity/patronage-or-event description, and exactly one priority-selected calendar bridge. Raise the novena allowance to a compact three or four sentences, validate all required supplied anchors, and build the same structure deterministically on LLM failure. Advance `DEVOTIONAL_INTRO_POLICY_VERSION`.
- Add or update focused tests in `tests/test_novena_contracts.py`, `tests/test_novena_engine.py`, `tests/test_publish_devotional_intro.py`, and `tests/test_novena_pipeline.py`.
- Update `README.md` and this release artifact with the contract format, seeding command, policy behavior, and verification record.

### Catalog Audit And Deduplication
- Treat a duplicate as two active contracts for the same devotion, not merely two contracts on the same civil date. Distinct saints and devotions sharing a date stay active.
- Add a repository audit that reports active contract IDs, effective feast-rule identities, unresolved date rules, and candidate duplicate devotions. It must run without network or LLM calls.
- Correct the three mis-mapped Pentecost contracts: Sacred Heart maps to `most_sacred_heart_of_jesus`; Immaculate Heart maps to the existing derived `immaculate_heart_of_mary` rule; retain the established Holy Spirit Pentecost contract and disable the newly imported duplicate `the_holy_spirit` contract.
- Add a first-class relative-to-Romcal feast rule and use it for the recorded exceptions: Holy Face of Jesus (one day before Ash Wednesday) and Mary, Queen of the Apostles (two days after Ascension). Keep Holy Family mapped directly to `holy_family_of_jesus_mary_and_joseph`.

### Materialized Short-Form Coverage
- Enumerate eligible General Roman Calendar celebrations over a multi-year date range, deduplicate by stable Romcal celebration ID, and exclude IDs already covered by active traditional contracts.
- Generate one checked-in `novena_feast_rule` contract for each remaining celebration. Each contract references `template_id: standard-9-day`, carries the standard baseline prompt, uses the stable Romcal ID, and includes LLM-seeded intro metadata.
- The generated contracts are the short-form catalog. The reusable `standard-9-day` template remains a shared definition rather than the only runtime contract.
- The former runtime selector is disabled after materialized coverage is generated, preventing it from creating a second novena for any celebration.

### UX And States
- Audio flow: the listener hears the unchanged Ora Pro Nobis welcome, then a clear welcome to the exact novena day, a brief saint/event identity, and one concise connection to today’s calendar before prayer begins.
- Successful seed: the CLI writes formatted metadata only after schema validation and reports every changed contract.
- Seed failure: the CLI reports the contract and leaves it untouched; it never writes partial or unvalidated JSON.
- Missing/invalid metadata: contract loading fails before publishing, preventing an intro that would make unsupported factual claims.
- No UI changes.

### Failure Modes
- LLM returns prose, wrong keys, unsupported patronage type, or invented extra fields: strict JSON parsing and schema validation reject it without writing.
- LLM request fails mid-catalog: the CLI reports failures and continues safely; already validated contract writes remain individually valid and can be rerun idempotently.
- A traditional contract fails to win over the standard short-form selector: resolver precedence tests detect the duplicate before publishing.
- Intro model omits the identity, patronage, Day N, or calendar bridge: validation triggers one corrective retry, then deterministic fallback uses the stored metadata.
- Missing daily calendar information: the existing fallback source supplies the one bridge sentence without inventing a feast or Gospel.
- Branded welcome is repeated: tests assert that generated novena prose never contains the Ora Pro Nobis welcome text.

### QA And Test Matrix
- Contract schema: valid saint record, valid event record, empty saint patronage, event patronage, missing summary, invalid provenance, and optional metadata for the dynamic standard short-form selector.
- Import/resolver: a traditional saint/event materializes only from its explicit contract; a calendar saint without a traditional contract materializes only from the existing standard short-form selector.
- Seed CLI: dry-run writes nothing; mocked valid OpenAI JSON produces formatted metadata; invalid/failed output changes no contract; rerun is idempotent without `--force`.
- Intro prompt/validation: Day N, saint/event summary, patronage for saints, one calendar bridge for feast/Gospel/memorial/season/fallback, no duplicated branded welcome, TTS length boundaries.
- Integration: generated, short-form, traditional, fixed, and compact-block novenas place the intro before prayer content; sidecar freshness rerenders under the policy version change.
- Commands: `python -m unittest tests.test_novena_contracts tests.test_novena_engine tests.test_publish_devotional_intro tests.test_novena_pipeline`; then `python -m unittest discover -s tests -p "test_*.py"`; then `git diff --check`.

### Rollout Notes
- Run the seed CLI with configured `OPENAI_API_KEY` for explicit contracts, then commit the generated metadata alongside the updated baseline short-form prompt.
- Production uses LLM-seeded metadata immediately, as requested. The stored `seed` provenance makes later editorial correction and re-seeding auditable.
- Incremented intro policy metadata causes target-date sidecars to regenerate through normal publishing; historical audio is unchanged until republished.

### Not In Scope
- Live external fact lookups during episode publication.

- Changes to the underlying prayer body, TTS provider/voice configuration, RSS structure, or daily-calendar priority algorithm.

### Open Questions
