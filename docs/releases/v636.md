# v636 — Rename Ora's own "Morning Prayer" to "Morning Offering (Extended)"

## §1 Scope — the name's surfaces, grounded

**The order (John, 2026-11-23 12:55 CT, verbatim):** "morning prayer appears twice — one of them is my morning offering so I need to rename that prayer through and through and do it that way." **The new name (John, 2026-11-23 13:05 CT):** exactly **"Morning Offering (Extended)"**. **Reach: DECIDED — going forward only** (§2). The release stays HELD at Scope; the chain (chain-v636) builds its Plan on this surface map.

**Which prayer this is.** Ora's own morning prayer — the show's daily opening production, publish contract `config/publish/contracts/morning-prayer.json` (contract id `morning-prayer-elevenlabs`, entry key `morning-prayer`). Its blocks, from the contract: the daily intro · **Opening Prayers** (`morning-offering.txt` — the traditional morning offering · `daily-consecration.txt` · `baptismal-renewal.txt` — the baptismal renewal with its renunciations) · **Petitions** · the **Intercessory Litany** (a custom Litany of the Saints, `saints-litany` block with a day-specific intro). It is NOT the Divine Office's Morning Prayer (the external slot `ext-morning-prayer`), which keeps its name everywhere — every surface below is the OWN prayer's name only, and two near-miss surfaces that name the office hour are listed at the end as expressly out.

### 1.1 The app

- **Praylist row · opened view · Now Playing** — all read the day descriptor's title. For own episodes the title is set at push time: `jobs/push_episodes_to_app.py` derives it from the feed title with the date stripped (`strip_date`, lines 332–364) and writes it into the day payload. No client-side title table exists for this prayer: rename the feed title template (1.2) and every new day's row, opened view, and Now Playing follow on their own. Already-pushed day payloads keep the old title; they age out of the served window (the player serves built days, today forward).
- **Contents universe label (the Add ladder + editor)** — `client.ts` builds own-source items as `{kind: 'source', key: r.sourceKey, label: r.title}` from the day's standing rows (line 21833): the label rides the payload title, the item's identity is its KEY. The Add ladder's Pray branch and the editor paint from this universe — both follow the payload with no change of their own.
- **Stored user contents — the identity answer (load-bearing).** Every stored reference to this prayer is **by key, never by name**: profile contents and today-layer items carry `{kind: 'source', key: 'morning-prayer'}`; played marks, positions, and favorites key on the episode id `morning-prayer`. Verified against John's own exported document (`john-personal-data-import-v589.json`): the string `morning-prayer` occurs 6 times — 1× his own source key, 4× the Divine Office family's keys (`do-morning-prayer`, `ext-morning-prayer` ×3 counting the midmorning slot), and exactly **one stored name copy** (next bullet). No contents item, mark, or favorite carries the words "Morning Prayer". **Consequence: the rename needs NO contents migration and NO key change** — the key `morning-prayer` stands; saved profiles, the today layer, marks, and favorites resolve under the new label untouched. (The mig609 append-only contents move is not needed: that pattern exists for moving contents between keys, and no key moves here.)
- **The one stored name copy: the Source mapping row.** Each user's document stores `sourceSettings.sources`, seeded from `OPN_SEED_SOURCES` (`client.ts` line 2592: `{sourceKey: "morning-prayer", name: "Morning Prayer", family: "own", block: "Morning", …}`), and the Settings Source mapping paints the row's stored `name`. The client never rewrites a stored row's name: the source-settings write route updates block/dayRule/enabled/sortOrder only (client.ts ~3570), and no seed-reconciliation pass exists. So a seed-only rename would leave every EXISTING user's mapping row reading "Morning Prayer" forever. The build must touch that one stored field for existing documents — the estate's standing vehicle is the load-time migration pattern (runs at first run and inside vault unlock; the mig609 precedent) — OR the Plan may instead make the mapping paint resolve the own row's name from the seed by key. Either shape is one field on one row; the Plan picks. New documents take the renamed seed directly.
- **Seed data** — `OPN_SEED_SOURCES` (client.ts line 2592), the row above: its `name` becomes "Morning Offering (Extended)".
- **The intro pairing tables (two copies, one contract)** — `jobs/compose_app_audio.py` `OWN_PAIRING` (line ~133) and `app/worker/src/index.ts` `INTRO_PAIRING` (line ~909) both carry `"morning-prayer": "Morning Prayer"` — the name the episode pairs under in the composed app audio. The v338 two-places rule stands in the code's own comment: a change lands in both in the same release, or in neither.
- **NOT a surface: the Prayer Book.** The book's entry slug `morning-offering`, title "Morning Offering", is a different, single traditional prayer that already stands under that name; the episode is a composed production, not a book entry. Nothing in the book renames. (Noted because the names now nearly coincide — the episode's "(Extended)" is exactly what keeps the two apart.)
