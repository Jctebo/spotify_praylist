### The field defect

The live first-visit web test (2026-11-23 07:16–07:20 CT, production pin v622-1, fresh browser profile) walked the plain-tab shape: Settings offered "Set a PIN"; the sheet opened (two pads, "NEW PIN (4-8 DIGITS)" / "NEW PIN AGAIN", copy promising a one-time recovery code); the test PIN 246810 was entered in both pads; the red "Set PIN" button did nothing across five clicks — no confirmation, no recovery code; after a reload, Settings still read "No PIN is set."

### The three modes (settled design, v567/v578 — stated, not changed)

- **Native shell** (APK 1.0.52): full device shape — vault, PIN, fingerprint bridge.
- **Installed PWA** (standalone display mode): COUNTS AS A DEVICE — encrypted on-device data + PIN in the PWA's own storage; no native bridge (no fingerprint; the WebAuthn passkey unlock stands apart).
- **Plain browser tab**: NO personal data — personal surfaces POINT to the app (the Conscience tab's card, `opnPointerHtml`, is the standing pattern), never a dead end.

Mode detection is the client's own: `opnMode()` reads 'device' when `oraInShell()` (the Capacitor bridge stands) or `opnInstalledPwa()` (matchMedia `(display-mode: standalone)`, or iOS `navigator.standalone`) in the public shape; otherwise 'web'.

### Diagnosis — why the set dies in a tab (grounded firsthand from the code)

The set path is `fillPinSection` (Settings → CONFESSION PIN) → `openPinSetSheet('set')` → `post('/api/pin/set')` → `opnLocalApi` → the local PIN route → `opnPinSet` + (device only) `opnVaultCreate`. `openPinSetSheet` is the ONE door to the flow (three call sites: the gated-tab setup prompt, Settings set, Settings change).

In a plain tab every step of that path is rigged to fail while presenting as completable:

1. **The state read is fabricated on web.** `fetchPinState()` → local `/api/pin/state` → `opnPinLoad()`, which hard-returns `null` when `opnMode() === 'web'` ("web never stores personal data" — `opnSave()` likewise no-ops). So the Settings section ALWAYS reads "No PIN is set" in a tab and ALWAYS offers the live Set a PIN button: `fillPinSection`'s no-PIN branch never read the mode at all.
2. **The save is refused before the route.** `opnLocalApi`'s web-write guard throws 403 — "Your personal prayer data lives in the app on your phone — open Ora Pro Nobis there to change it." — for every personal write in web mode (podcast marks excepted); `/api/pin/set` is such a write, so the PIN route is never reached.
3. **The refusal is buried.** The sheet's catch paints that 403 text into `#ps-msg`, the sheet's small message line (probe-verified on the base tree: after a save click the line carries the refusal, the sheet stands open, no recovery sheet, no PIN record, state still reads not-set). The flow presents as a completable set whose only possible outcome is that one small line — a dead end by construction, matching the field report's "nothing happened."

In the device shapes the same path is the standing, working set flow (John's daily use in the shell; the PWA shares the exact device-mode path — proven by harness, §4). Nothing in the diagnosis touches them.

## §2 Decisions

- **D1 — The tab points; it does not offer.** In web mode the CONFESSION PIN section stands as the pointer card (`opnPointerHtml`, the Conscience pattern) — no Set / Change / Enter button is painted in a tab. The plain tab is NOT widened into a personal-data shape: that would reverse v567/v578 and is out of scope.
- **D2 — The one door refuses by name.** `openPinSetSheet` in web mode stands the sheet as the pointer — no pads, no save button — so any present or future caller reaches a named refusal, never a silent no-op.
- **D3 — Device shapes byte-untouched.** The fix is two mode branches at the two seams; the set flow in the shell and the installed PWA runs exactly the standing code.

## §3 Implement

`app/worker/src/client.ts` only (two hunks), plus the new `app/harness-v623.mjs`:

- **`fillPinSection`** — after the section head is built, a web-mode branch paints `opnPointerHtml()` into the section and returns, before any PIN branch (set / change / enter / the v622 preference switch / the enrolment card) can paint.
- **`openPinSetSheet`** — at entry, a web-mode branch stands the sheet with the pointer as its body (same sheet shell + drawer mount) and returns; the pads and the save stand only in the device shapes.

No data change anywhere: John's PIN record, vault, and enrolment are untouched (the diff reads mode and paints; it writes nothing).
