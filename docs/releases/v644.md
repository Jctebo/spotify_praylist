# v644 — Share engages the system share sheet in the app + the standard share icon

## §1 Scope (streamlined path — Scope + Plan in one pass)

Use the standard share icon" — a field report on the live v640 build (pin ora-pro-nobis-v640-1), on his Galaxy Z Fold in the APK (1.0.52). Streamlined small-release path, fix-forward **To Ship**. Coordinator: chain-v644, contract 980 (Plan).

**Defect 1 — the sheet never engages on the phone.** v640 shipped the player Share on the web discipline. Grounded in the shipped client (`app/worker/src/client.ts`, base tree):

- Every Share act (the player's `shareTrackSheet`, the day-row / podcast-row / Favorites-mirror menus) funnels into `openShareSheet(o)`. It paints a "Share…" row **only when `navigator.share` exists**; otherwise the sheet carries only "Copy link".
- The APK is a Capacitor 7 WebView shell. `navigator.share` does not stand in that WebView, so on John's phone the "Share…" row never paints and the tap can only land on the copy fallback. The payload (title + the Ora app link, `shareAppUrlFor`) is correct — the route to the system sheet is what is missing.
- The shell's standing bridge pattern is the custom Capacitor plugin **OraDayBridge** (`OraDayBridgePlugin.kt`, registered in the shell; the client reaches it via `oraBridgePlugin()` / `oraInShell()`), which already carries the vault-biometric methods, the day snapshot, downloads, wallpaper and the native queue. The shell's dependency set is `@capacitor/core` + `@capacitor/android` + `@capacitor/app` only — **no `@capacitor/share`** is in the build.

**Defect 2 — the icon.** The player's Share button (`#np-share`, end of the Now Playing transport row) carries the glyph `&#10548;` (⤴, a bent arrow) — not a share mark in any platform's discipline. The other transport buttons are text/entity glyphs; the share button is the only pictorial one and it reads wrong. The menu Share acts (the player's menu row, the row-menu items) are text labels ("Share", "Share…") with no glyph — they conform to the menu discipline and do not deviate; the one deviant glyph is `#np-share`'s.

## §2 Plan — the fix

**Route (Defect 1): extend the standing bridge; a new APK is required and is part of this release.** No web-only change can engage Android's system share sheet from inside the WebView — `navigator.share` is absent and no client code can conjure it. Two native routes were weighed:

- **Chosen: a `shareTrack` method on the existing OraDayBridge plugin.** One `@PluginMethod` that builds an `ACTION_SEND` intent (`text/plain`, `EXTRA_SUBJECT` = title, `EXTRA_TEXT` = title + line + URL in the standing payload shape) and starts `Intent.createChooser`. No new dependency, no new plugin registration surface — the same bridge the client already probes for shell presence. Rejection of the call (old APK without the method) falls back to today's behavior exactly.
- Weighed and not chosen: adding `@capacitor/share` — an official plugin, but a new dependency + registration in a shell whose standing pattern is the hand-written bridge; the bridge method carries the exact payload with less new surface.

**Client change (app repo, `client.ts` only):**

- A helper `nativeShareTrack(o)`: when `oraInShell()` and the plugin exposes `shareTrack`, call it with `{ title, text, url }` (text composed exactly as the web `navigator.share` call composes it today: `title + ' — ' + line`, url separate) and return true; otherwise false.
- `openShareSheet`: the "Share…" row stands when `navigator.share` **or** the native route stands; its click tries the native route first in-shell, else `navigator.share`, exactly as today. Out-of-shell shapes are byte-identical in behavior: PWA/tab keep `navigator.share` → copy fallback, the "Link copied." note unchanged.
- Payload unchanged: v640's title + line + `shareAppUrlFor` app link. No share-text change anywhere.

**Shell change (Android repo, Jctebo/ora-pro-nobis-android):**

- `OraDayBridgePlugin.kt`: one `@PluginMethod fun shareTrack(call)` — reads `title` / `text` / `url`, fires the chooser on the activity, resolves the call; a missing activity rejects with a named error (the client then falls back).
- `android/app/build.gradle`: versionCode 52 → **53**, versionName "1.0.52" → **"1.0.53"**.
