# Release 0.1.3.3 - morning-prayer-generation-assembly

- Status: Draft
- Last Updated: 2026-03-28
- Created Date: 2026-03-28
- Depends On: 0.1.3.2
- Roadmap: `docs/roadmaps/stabilization.md`
- Notes: This release keeps the custom TTS contract surface rooted in `config/custom_tts/` and the existing `config/content/morning-prayer` tree, and focuses on regression testing the current boundary before any page-writing work.

## Scope

### Problem
- The current custom TTS contract surface still has enough coupling between page configuration, page audio, and assembly that regressions can hide until runtime.
- The repo already has a file-backed content layout under `config/content/morning-prayer`, but the active boundary for `config/custom_tts/` has not been validated with a focused regression pass.
- The current surface is still Morning Prayer only, but the release needs to prove the custom TTS directory scan, enabled flag, and contract shape still behave as expected before any page-writing changes.
- Why now: the desired custom TTS contract surface has already been drafted, and the current worktree is ready for validation rather than a write-path rewrite.

### Audience
- Primary user: the maintainer who runs custom TTS generation and assembly.
- Secondary stakeholders: listeners and downstream consumers who depend on Morning Prayer output staying stable.
- Secondary stakeholders: future maintainers who need one obvious contract path instead of a legacy fallback maze.

### Current Status Quo
- `jobs/notion/generate_page_audio.py` previously centered legacy Morning Prayer loading; this release moves the canonical custom TTS contract surface to `config/custom_tts/morning-prayer.json`.
- `config/custom_tts/morning-prayer.json` exists in the worktree as the current enabled custom TTS contract candidate.
- `config/content/morning-prayer/content/*.txt` and `config/content/morning-prayer/templates/monthly-intention/*.txt` already provide the file-backed assembly content.
- The current contract shape already knows how to combine contract-driven resolvers with file-backed content fragments, so this is a configuration and wiring change rather than a redesign.

### Goal
- Validate the existing custom TTS contract boundary with regression coverage.
- Keep the current Morning Prayer contract using the existing `config/content/morning-prayer` content tree.
- Preserve the current contract structure while confirming the custom TTS directory scan, enabled flag, and defaults behave correctly.
- Update the contract schema and payload to include the top-level output metadata needed by the runtime, specifically `output_type` and `path`.
- Success means the runtime stays stable in local and remote runs and the tests clearly prove the contract surface and contract shape that are already in use.

### Constraints
- Do not redesign the custom TTS contract surface into a new prayer model.
- Do not change the content text itself unless a missing or broken assembly dependency forces it.
- Do not widen this release into TTS-provider migration or broader page-audio cleanup.
- Keep the file-backed content tree as the assembly source of truth for the prayer text.
- Keep direct execution and repo-root bootstrap behavior working from arbitrary working directories.
- Focus this release on regression coverage, contract shape updates, and validation, not on introducing a new page-writing path.

### Narrow Wedge
- Verify the existing custom TTS surface still pulls enabled content from `config/content/morning-prayer`.
- Add the minimum docs and tests needed to prove the current directory scan, enabled flag, and shape are stable.
- Leave page-writing changes for a follow-up release.
- Leave unrelated prayer families and provider migration for later releases.

### Non-Goals
- Rewriting the Morning Prayer text content.
- Migrating the TTS provider.
- Refactoring Rosary or other prayer contracts.
- Reworking unrelated shared helper boundaries.
- Building new AI-generated content logic.
- Introducing page-writing changes in this release.

- The runtime may still assume that page config and page-content writing move together, so the boundary needs explicit validation.
- The assembly path may still work only because of implicit defaults, so the regression pass needs to cover the directory loader, enabled-flag behavior, and output metadata shape.
- The worktree currently contains a legacy Morning Prayer file deletion, which may be part of the intended cutover or may need to be preserved differently once implementation starts.
- It is not yet proven whether any tests or docs still reference the active Morning Prayer contract path incorrectly.

### Recommended Next Step
- Use `/research-astack` to validate the current custom TTS directory loading and assembly flow, then confirm exactly which files need regression coverage.

- `jobs/notion/generate_prayer.py` reuses `build_morning_prayer_plan(...)`, so the wrapper and the page-audio runtime need to agree on the same contract assumptions.
- The current `config/custom_tts/morning-prayer.json` already contains the expected 13-resolver Morning Prayer shape with `page_id`, `random-intention`, `monthly-intention`, the petition fragments, and the top-level `enabled` flag that gates loading.
- The content tree under `config/content/morning-prayer` is already stable and should stay the source of truth for the spoken text.

### Constraints
- The contract file must remain JSON-schema compatible and keep `header.page_id`, `header.model`, and the ordered resolver list intact.
- The contract must add and preserve top-level `output_type` and `path` metadata in the shape expected by the runtime and docs.
- The custom TTS surface must use a top-level `enabled` flag so the loader can admit or skip each JSON file in `config/custom_tts/`.
- The assembly path should continue to resolve the same file-backed content fragments, including the monthly template folder.
- `jobs/notion/generate_page_audio.py` and `jobs/notion/generate_prayer.py` both still reference the legacy Morning Prayer path, so the regression tests need to cover the directory loader and enabled filter, not just a single hardcoded file.
- The worktree already contains a deleted `config/legacy/morning-prayer.json` and an untracked `config/custom_tts/` directory, so the release should treat that state as intentional only if the path change is truly meant to retire the legacy file.

### Risks
- The loader boundary can remain coupled even if the new contract exists, which would make the separation look complete in docs but not in runtime behavior.
- `jobs/notion/generate_prayer.py` could keep the old contract coupling alive unless it is covered by tests.
- There is no dedicated Morning Prayer regression test in the visible test files, so the path change could slip through without direct coverage.
- The deleted legacy file in the worktree may be an intended removal or an accidental gap; either way, it is a release risk until the path is confirmed.

### Assumptions To Validate
- `config/custom_tts/morning-prayer.json` is the intended enabled Morning Prayer contract file in the custom TTS surface, not just a staging copy.
- The release wants the old legacy Morning Prayer file removed or at least retired from the active surface, not preserved as an implicit fallback path.
- The wrapper script `jobs/notion/generate_prayer.py` should keep using the same Morning Prayer contract as the page-audio runtime.
- The user wants the docs updated to describe the active contract path and the test coverage boundary.
- The contract should gain explicit top-level `output_type` and `path` metadata rather than relying only on implicit file-backed resolver behavior.
- The custom TTS loader should skip any JSON file in `config/custom_tts/` that does not declare `enabled: true`.

### Recommended Direction
- Keep the current custom TTS surface on the existing assembly/content path, and add a focused regression test that proves the directory scan, enabled filter, and output metadata shape stay stable without changing page writing yet.

## Plan
### Summary
- Promote `config/custom_tts/` to the canonical custom TTS contract surface everywhere the runtime loads the custom TTS family.
- Keep assembly on the existing `config/content/morning-prayer` tree and the existing `build_morning_prayer_plan(...)` path.
- Document and verify that the page-audio destination is configurable through `PAGE_AUDIO_LIBRARY_DIR`, so the Morning folder on OneDrive can be selected without changing code.
- Keep the plan focused on the custom TTS engine surface and the local launch path that wraps it.

### What Already Exists
- `jobs/notion/generate_page_audio.py` already has the custom TTS assembly path, the content-tree loaders, and `PAGE_AUDIO_LIBRARY_DIR` support.
- `jobs/notion/generate_prayer.py` already reuses the Morning Prayer builder instead of inventing a second renderer.
- `scripts/run_page_audio_local.ps1` already forwards page-audio environment variables, including the library directory override.
- `config/content/morning-prayer/content/*.txt` and `config/content/morning-prayer/templates/monthly-intention/*.txt` already hold the file-backed assembly sources.
- The release worktree already contains `config/custom_tts/morning-prayer.json`, which matches the intended 13-resolver contract shape.

### Architecture
- The canonical flow is:

```text
config/custom_tts/*.json
            |
            v
custom_tts loader
            |
            +--> jobs/notion/generate_prayer.py
            |
            v
build_morning_prayer_plan(...)
            |
            v
config/content/morning-prayer/*
            |
            v
PAGE_AUDIO_LIBRARY_DIR
            |
            v
OneDrive\...\Morning  (or any other configured target)
```

- Contract selection stays explicit and env-overridable, with the enabled custom TTS contract surface treated as the canonical path in the docs.
- Only JSON files with `enabled: true` are eligible for load.
- Output location stays env-overridable through `PAGE_AUDIO_LIBRARY_DIR`, so the runtime can write to the Morning folder you used earlier without baking that path into code.
- The contract also needs explicit output metadata, so the runtime can reason about top-level `output_type` and `path` instead of inferring destination behavior.

### Concrete Changes
- `jobs/notion/generate_page_audio.py`
  - Change the custom TTS loader to scan `config/custom_tts/*.json` and admit only files marked `enabled: true`.
  - Keep the existing Morning Prayer assembly logic and file-backed content lookups.
- `docs/architecture/morning-prayer-contract.schema.json`
  - Add the new top-level `enabled` field to the custom TTS contract shape.
  - Keep the existing resolver ordering and file-backed content references intact.
- `config/custom_tts/*.json`
  - Add the top-level contract output metadata fields needed by the runtime and docs, including `output_type`, `path`, and `enabled`.
  - Keep the existing resolver ordering and file-backed content references intact.
- `jobs/notion/generate_prayer.py`
  - Update the standalone Morning Prayer wrapper so direct runs follow the enabled custom TTS contract surface.
  - Keep the existing override parameters intact for ad hoc validation and rollback.
- `scripts/run_page_audio_local.ps1`
  - Keep the local launcher wired to the configurable output directory so the Morning folder on OneDrive can be selected without code changes.
- `tests/test_page_audio_job.py`
  - Add or restore generic page-audio regression coverage for:
    - loading only enabled contracts from `config/custom_tts/`
    - skipping disabled contracts in `config/custom_tts/`

    - Morning Prayer assembly still resolving through `config/content/morning-prayer`
    - top-level `output_type` and `path` validation for the custom TTS contract
- `README.md`
  - Update the Morning Prayer and page-audio docs to state that the canonical enabled contract is `config/custom_tts/morning-prayer.json`.
  - Add an example that shows how to point `PAGE_AUDIO_LIBRARY_DIR` or `-PageAudioLibraryDir` at the Morning folder on OneDrive.

### UX And States
- Default state: enabled custom TTS contracts run without any extra flags.
- Configured state: the same job can write to a different local or OneDrive target when `PAGE_AUDIO_LIBRARY_DIR` is set.
- Missing-contract state: the runner should fail fast if the canonical file is absent or malformed.
- Override state: advanced users can still point the loader at a different contract file for validation.

### Failure Modes
- The canonical contract file is missing or malformed, which should fail at startup instead of silently falling back.
- The wrapper and the main page-audio runner drift apart again, which would cause different defaults for the same prayer.
- A disabled JSON file is picked up by mistake, which would make the custom TTS surface behave unpredictably.
- The configured target path is wrong or unavailable, which would make output land in the wrong folder or fail on write.
- The custom TTS contract shape stops matching the schema, including top-level `output_type` and `path`, which would break assembly before output is written.
