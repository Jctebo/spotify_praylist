# Release 0.2.0.0 - Novena Publishing System

Date: 2026-04-28
Status: Shipped
Branch: enhancement/novena-publishing-system
Depends On: 0.1.5.7

## Scope

### Problem
- Novena publishing is split across more than one runtime path today, which makes the behavior harder to reason about and harder to replay from a single source of truth.
- The current novena flow mixes liturgical selection, prayer rendering, and audio handling, while the publish pipeline separately handles MP3 output, sidecars, and RSS rebuilding.
- There is no repo-owned contract model that defines a novena once and lets the runtime determine the active novena day only from today's date.
- The standard novena family should auto-populate eligible celebrations from liturgical data, while explicit feast contracts remain available as overrides when needed.
- Operators need a deterministic system that can regenerate the same novena output from the contract and the date, with traceable artifacts for debugging and reruns.

### Audience
- Primary user: the maintainer who authors novena contracts and runs the daily publishing pipeline.
- Secondary stakeholders: listeners who receive MP3 episodes and RSS updates.
- Secondary stakeholders: future maintainers who need a deterministic contract-to-output path that is easy to inspect and debug.

### Current Status Quo
- `jobs/novena/generate_daily_novena_prayer.py` currently owns liturgical-window selection, AI text generation, and optional audio upload for the existing novena flow.
- `jobs/publish/run_audio_pipeline.py`, `jobs/publish/audio.py`, and `jobs/publish/rss.py` already support contract-driven audio output, JSON sidecars, and RSS rebuilding for publish contracts.
- `jobs/publish/audio.py` already writes one JSON sidecar per audio output and can rebuild the feed from archived sidecars plus newly rendered jobs.
- The repo does not yet have a single feast-day contract file that defines the full novena behavior, nor a runtime resolver that determines the active novena solely from today's date and contract metadata.
- There is no dedicated helper for authoring one feast-day novena contract with validation and embedded-template support.
- The existing system still mixes runtime selection, output generation, and surface-specific publishing in a way that is harder to debug than the requested contract-driven model.

### Goal
- Author each novena once as a single feast-day JSON contract.
- Author selector-based family contracts once and let the runtime auto-populate eligible celebrations without enumerating ids.
- Resolve the active novena and active day from today's date and contract metadata only.
- Render fixed, AI-generated, and hybrid prayer content from the same contract.
- Produce MP3, JSON sidecar, and RSS outputs as separate publishing steps driven by the same runtime artifact.
- Rebuild the RSS feed deterministically from published artifacts after each run.
- Make debugging possible from the sidecar alone, without relying on per-year pre-generated instance files.

### Constraints
- The repo already has established `jobs/novena/` and `jobs/publish/` boundaries, so the new system should extend those surfaces instead of inventing a second parallel runtime tree.
- No pre-generated novena instance files should be committed to the repo.
- The scheduler must remain thin and call only the resolver with today's date.
- Feast contracts must be repo-owned, validated, and easy to author by hand.
- The system must remain deterministic and idempotent on reruns.
- Existing non-novena podcast episodes should not be lost when the RSS feed is rebuilt.
- Contract validation should fail closed on invalid feast dates, duplicate ids, invalid content modes, missing template files, or malformed embedded templates.
- Embedded templates must override `template_id` when both are present.

### Narrow Wedge
- Start with a contract-driven novena pipeline for one selector-based family that can author, resolve, render, write sidecars, and republish the required audio and feed surfaces from a single runtime contract.
- Support embedded templates and template references, plus fixed, AI-generated, and hybrid content modes.
- Rebuild the podcast feed from published artifacts and preserve existing non-novena episodes.
- Add a contract-creation helper script so new feast-day files can be authored safely without hand-editing scaffolding.
- Keep the first release limited to the existing daily novena publishing path and do not expand into Spotify playlist assignment, multilingual, multi-feed, or calendar-trigger abstraction work yet.

### Non-Goals
- Do not generate or store per-year novena instance files in the repo.
- Do not build a UI for authoring feast contracts.
- Do not add multilingual support yet.
- Do not add liturgical-calendar-trigger generalization yet.
- Do not add Spotify playlist management in this change; that will be a separate future contract update.
- Do not make the sidecar artifact an input to the resolver or engine.
- Do not migrate unrelated prayer workflows into this contract system in the same release.

### Risks And Unknowns
- The biggest risk is overlap between the new novena contract model and the existing `jobs/novena/generate_daily_novena_prayer.py` flow, especially around audio ownership.
- The contract schema needs to be simple enough for hand authoring but strict enough to prevent malformed feast rules or invalid template references.
- The contract schema also needs a crisp boundary between selector-based families and explicit feast overrides so the same celebration never gets duplicated.
- It is unknown whether the new system should reuse the existing publish contract rendering primitives or introduce a parallel novena-specific renderer.
- The repo needs a clear decision about whether RSS rebuild reads only sidecars, only live outputs, or both.

### Recommended Next Step
- Run `/research-astack` to map the current novena and publish modules, confirm the best selector-vs-override contract shape and reuse boundaries, and identify exactly which existing code should become the resolver, engine, artifact writer, and publishers.

## Research
### Scope Baseline
- Build a contract-driven novena publishing path that resolves the active novena and day from today's date only, renders fixed/AI/hybrid content, and writes MP3 plus JSON sidecar plus RSS outputs.
- Let selector-based family contracts auto-populate eligible celebrations from the liturgical calendar, with explicit feast contracts used only when a specific override is needed.
- Keep this release inside the existing audio/feed boundary; Spotify and Notion are explicitly out of scope for this change.
- The main planning question is how much of the existing publish contract machinery can be reused without making novena contracts awkward to author.

### Relevant Files
- `jobs/novena/generate_daily_novena_prayer.py` - current legacy novena runtime; still owns liturgical-window selection, AI drafting, and optional audio upload.
- `jobs/novena/liturgical_helpers.py` - shared Romcal/timezone/eligibility helpers used by the current novena and devotional flows.
- `jobs/publish/contracts.py` - existing repo-owned contract loader, validation, selector evaluation, and audio job construction.
- `jobs/publish/formatting.py` - date-aware title and episode-id rendering primitives.
- `jobs/publish/audio.py` - MP3 output, sidecar writing, and output-idempotency checks.
- `jobs/publish/fragments.py` - fragment caching, fragment sidecars, and ffmpeg assembly helpers.
- `jobs/publish/rss.py` - deterministic RSS rebuild from current and archived audio jobs.
- `jobs/publish/run_audio_pipeline.py` - orchestration boundary that fans in rendered jobs and republishes the feed.
- `config/publish/contracts/*.json` - concrete examples of the repo's current contract-driven authoring style.
- `config/publish/templates/*` - reusable text assets and template-folder patterns already used by the publish pipeline.
- `tests/test_publish_contracts.py` - coverage for contract validation, date-scoped rendering, and fragment expansion.
- `tests/test_publish_audio_pipeline.py` - coverage for feed rebuilds and sidecar-backed reruns.
- `tests/test_publish_audio_fragments.py` - coverage for fragment hashing, caching, and reuse.
- `tests/test_novena_job.py` - coverage for the current legacy novena entrypoint and liturgical helpers.
- `scripts/run_daily_novena_prayer_local.ps1` and `jobs/notion/generate_prayer.py` - legacy operator path that shows how the old Morning Prayer workflow is still wired.

### Current System Map
- The repo already has two distinct surfaces: `jobs/novena/` for the legacy novena generator and `jobs/publish/` for the newer contract-driven audio/feed pipeline.
- `jobs/publish/contracts.py` already does most of the hard parts needed for a deterministic authoring model: validation, date-aware metadata, block expansion, and audio job assembly.
- `jobs/publish/audio.py` already persists one JSON sidecar per episode and treats the sidecar as the replay source of truth for reruns.
- `jobs/publish/rss.py` already rebuilds the feed from rendered jobs plus archived sidecars, which matches the desired “rebuild from outputs” shape.
- `jobs/novena/generate_daily_novena_prayer.py` still owns the liturgical selection and AI generation path, so it is the main legacy boundary to simplify or replace.
- The current local runner still points at `jobs/notion/generate_prayer.py`, which shows the operational surface is not yet aligned with the cleaner publish pipeline.

### Reuse Opportunities
- Reuse `build_publish_context`, `render_publish_template`, and `derive_episode_id` for deterministic, date-scoped novena metadata.
- Reuse `expand_audio_fragments` plus fragment caching/assembly so novena audio can keep the same sidecar and reuse behavior as the publish pipeline.
- Reuse `load_published_audio_jobs` and `build_rss_feed` so the feed continues to rebuild from output artifacts instead of a separate RSS model.
- Reuse the existing contract authoring pattern from `config/publish/contracts/*.json` if the novena schema can express feast-day timing cleanly.
- Reuse the existing test style that fixes the date and checks idempotent reruns, hash reuse, and deterministic feed output.

### External References
- `romcal` provides the liturgical calendar and feast-day eligibility logic the novena resolver will need.
- The OpenAI API client is the existing path for AI drafting and TTS generation.
- `imageio_ffmpeg` and `ffmpeg` back the fragment assembly path used by audio publication.
- GitHub Pages URL conventions already define the public audio and RSS locations used by the publish pipeline.

### Constraints
- Outputs must stay deterministic: given the same date and contract, the runtime should produce the same active day, episode id, sidecar, and RSS ordering.
- Existing RSS episodes must survive republishing; the feed is a rebuild from outputs, not a fresh feed that forgets history.
- The new novena system should fit the existing repo layout instead of introducing another parallel `src/` tree.
- Validation should fail closed on invalid dates, duplicate ids, broken templates, or malformed embedded-template shapes.
- Since Spotify and Notion are out of scope here, this release should not wait on either surface to define the novena contract shape.

### Risks
- The biggest integration risk is picking the wrong reuse boundary between the legacy novena runtime and the existing publish contract engine.
- The repo has overlapping “novena” and “publish” concepts, so it is easy to duplicate schema logic or drift into a second contract grammar.
- The current operator entrypoint is still tied to the legacy Morning Prayer wrapper, so the runtime story will remain confusing until the new path is introduced cleanly.
- Feed rebuilds assume sidecars already exist and are valid, so the novena writer must keep the output schema compatible with the current audio pipeline.

### Assumptions To Validate
- The new novena contract should likely be its own schema rather than a forced variant of the existing publish contract, with selector-based families and explicit feast overrides sharing the same runtime shape.
- The resolver should derive the active novena day from feast date plus offset, not from any pre-generated yearly instance file.
- The first implementation should keep the existing `docs/audio/<episode_id>.mp3` plus JSON sidecar convention so RSS rebuild stays compatible.
- AI-generated sections should plug into the same rendering path as fixed sections instead of a separate one-off text pipeline.
- Selector families should keep a stable family id, while runtime contract ids are derived from the liturgical celebration itself and saint display names remain separate metadata for authoring and episode text.

### Unknowns
- Whether the new novena renderer should reuse the legacy `jobs/novena` helpers or be rebuilt around the publish formatting primitives.
- How embedded templates and `template_id` references should be represented without making the contract hard to author.
- Whether the first release needs a dedicated novena sidecar schema version for replay/debugging.
- Whether any of the existing `config/publish/templates` assets can be reused directly for feast-day novenas or whether a separate novena template directory is cleaner.
- Whether the contract helper should expose Romcal ids directly, accept saint names and normalize them to Romcal ids, or support both with one canonical storage form.

### Recommended Direction
- Move to `/plan-astack` after deciding whether the selector grammar should stand alone or intentionally mirror the existing publish-contract structure where possible.

## Plan
### Summary
- Build a new contract-first novena workflow in a fresh boundary instead of extending the legacy `jobs/novena/generate_daily_novena_prayer.py` path.
- The new system will resolve feast-day contracts from today's date, render fixed/AI/hybrid content, generate MP3 + JSON sidecar outputs, and republish RSS deterministically.
- We will reuse low-level publish primitives where they fit, especially audio fragment assembly and RSS feed writing, but the novena contract/runtime model itself is new.
- Selector-based family contracts auto-populate eligible celebrations from the liturgical calendar; explicit feast contracts are overrides, not duplicates.

### What Already Exists
- `jobs/publish/fragments.py` already solves fragment hashing, cache reuse, silence insertion, and ffmpeg assembly.
- `jobs/publish/audio.py` already proves the repo can write idempotent audio outputs with JSON sidecars.
- `jobs/publish/rss.py` already proves the feed can be rebuilt from current outputs plus archived sidecars.
- `jobs/publish/formatting.py` and `jobs/publish/contracts.py` already show how the repo handles date-aware rendering, selector evaluation, and contract validation.
- `jobs/novena/liturgical_helpers.py` and `jobs/novena/generate_daily_novena_prayer.py` provide behavioral reference for liturgical timing and output shape, but the new workflow should not depend on them directly.
- `tests/test_publish_contracts.py`, `tests/test_publish_audio_fragments.py`, and `tests/test_publish_audio_pipeline.py` already cover the reuse boundary we want to preserve.

### Architecture
- Introduce a fresh contract-first package under `jobs/novena_contracts/` rather than retrofitting the legacy novena script.
- `jobs/novena_contracts/contracts.py` and `validators.py` own the feast-contract schema, loading, and fail-closed validation.
- `jobs/novena_contracts/resolver.py` maps `today` plus feast contracts into a runtime object with the active novena day and resolved template.
- `jobs/novena_contracts/engine.py` renders the runtime object into structured sections and per-section audio fragments, using a small AI stub boundary for generated text.
- `jobs/novena_contracts/artifact_writer.py` writes the novena JSON sidecar and keeps it compatible with the existing publish-side replay shape so RSS rebuild stays simple.
- `jobs/novena_contracts/audio.py` or a thin pipeline adapter uses the existing publish fragment helpers to render and assemble MP3 output.
- `jobs/novena_contracts/rss_publisher.py` rebuilds the feed from published novena sidecars plus any already published audio jobs, then writes `docs/podcast.xml`.
- `jobs/novena_contracts/pipeline.py` orchestrates the run order: load contracts, resolve active novena, render, generate audio, write artifact, rebuild RSS.
- Contract files use stable Romcal feast ids for explicit overrides, while selector families keep a stable family id and `scripts/new_novena_contract.py` may accept either a saint name or a Romcal id for explicit feast contracts or create an auto-populated family contract.

### UX And States
- No UI is in scope; this is a contract authoring and CLI pipeline feature.
- Authoring state: `scripts/new_novena_contract.py --dry-run` should validate and print the new contract without writing files.
- Success state: a contract for today resolves to a specific novena day, renders content, writes the MP3 and JSON sidecar, and republishes the feed.
- Empty state: if no contract is active for today, the pipeline should exit cleanly without writing outputs.
- Error state: malformed feast dates, invalid content modes, missing templates, or bad embedded template shapes should fail closed before audio generation starts.
