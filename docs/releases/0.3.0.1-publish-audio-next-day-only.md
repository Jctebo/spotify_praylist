# Release 0.3.0.1 - Publish Audio Next-Day Only Bugfix

Date: 2026-05-01
Status: Shipped
Branch: enhancement/publish-audio-next-day-only
Depends On: 0.3.0.0

## Scope

### Problem
- The published podcast feed is surfacing tomorrow's episodes, but it is not keeping older episodes in the feed the way an append-style podcast archive should.
- The current publish-audio path may be rebuilding from only the latest window instead of preserving the existing feed history.
- Why now: the podcast is already public, so a feed-retention bug shows up immediately as disappearing back catalog episodes rather than a harmless internal mismatch.

### Audience
- Primary user: the maintainer who runs the audio publish pipeline and expects the podcast feed to reflect the correct episode window.
- Secondary stakeholders: listeners subscribing to the podcast feed who should see the right day's content at the right time.
- Secondary stakeholders: future maintainers who need clear test coverage around publish-mode behavior and feed rebuilding.

### Current Status Quo
- `jobs/publish/run_audio_pipeline.py` defaults the daily mode to the next day only.
- `jobs/publish/rss.py` rebuilds the feed from rendered, archived, and sidecar jobs, so the date window chosen upstream controls what ends up visible.
- Manual `bootstrap` and `reset` modes already publish today plus tomorrow, but the default routine does not.
- The result is a podcast that can look like it is one day ahead of expectation when only the daily path is used.

### Goal
- Keep the daily publish path on the tomorrow-only window, but make the RSS/feed write behave like an append so older episodes remain visible.
- Preserve already-published episodes when the feed is rebuilt from local sidecars or archived RSS items.
- Success criteria: the published feed keeps prior episodes while still adding the new daily episode set for the current run.
- Success criteria: regression tests prove the feed append behavior, history retention, and dedupe rules all match the intended archive model.

### Constraints
- Keep the fix narrow to the publish-audio/feed-selection boundary unless the research step proves a shared helper is the safer home.
- Preserve existing episode IDs, RSS GUIDs, and sidecar files so previously published items remain stable.
- Do not broaden the scope to unrelated content generation, Spotify refresh behavior, or novena contract work.
- Keep RSS ordering deterministic after the selection logic is corrected.

### Narrow Wedge
- Fix the RSS/feed rebuild so it appends new episodes without dropping older ones, then verify the daily tomorrow-only publish path still produces the expected fresh episode window.
- Add regression tests that pin append behavior, history retention, and feed-rebuild cases.

### Non-Goals
- Do not redesign the podcast brand, feed schema, or episode naming convention.
- Do not change the daily intro text generation itself unless a test proves it is part of the feed-retention bug.
- Do not modify Spotify playlist refresh logic or novena publishing behavior.
- Do not add a new publishing mode unless the current modes cannot express the correct window.

### Risks And Unknowns
- The phrase "append" needs a precise implementation boundary: append to the RSS feed file, append from archived jobs, or both.
- Existing archived sidecars may already be incomplete, so the fix may need to preserve history while also recovering older items into the rebuilt feed.
- Timezone boundaries can make an episode appear to move a day earlier or later if the publish date is derived from UTC instead of the intended local window.
- The feed merge logic may already be correct, and the bug may be that only the newest slice of jobs is being passed in while older items are being filtered out upstream.

### Recommended Next Step
- Run `/plan-astack` focused on RSS append semantics, feed retention, and the tests around archived jobs versus newly rendered jobs.

## Research
### Scope Baseline
- The scoped task is to find why the podcast publish flow is dropping older episodes instead of appending new ones to the archive.
- The daily tomorrow-only window is probably intentional; the bug is more likely in feed retention, merge inputs, or how older jobs are reloaded.

### Relevant Files
- `jobs/publish/run_audio_pipeline.py` - chooses the publish modes and the target date list passed into the audio pipeline.
- `jobs/publish/contracts.py` - turns publish contracts into dated audio jobs and sets `published_date` / `episode_id` from the selected target date.
- `jobs/publish/audio.py` - renders audio jobs and rebuilds published sidecars into feed inputs.
- `jobs/publish/rss.py` - merges rendered jobs, archived RSS items, and sidecar jobs into the final podcast feed.
- `tests/test_publish_audio_pipeline.py` - covers the default, reset, and multi-day publish behavior and is the best regression map for this bug.
- `tests/test_publish_contracts.py` - verifies that publish jobs are date-scoped and that audio jobs inherit the selected target date.
- `tests/test_publish_text_pipeline.py` - useful for confirming that the text pipeline is not the source of the off-by-one behavior.
- `.github/workflows/publish_audio.yml` - documents the intended publish modes and their default behavior in the deployed workflow.

### Current System Map
- Fact: `run_audio_pipeline()` builds audio jobs from `build_audio_jobs()` and only then writes the RSS feed, so the upstream date window controls which episodes are even eligible to appear.
- Fact: `_target_dates_for_mode()` in `jobs/publish/run_audio_pipeline.py` returns tomorrow only for the default mode, and returns today plus tomorrow for `bootstrap` and `reset`.
- Fact: `build_audio_jobs()` in `jobs/publish/contracts.py` stamps each job with a `published_date` derived from the selected target date.
- Fact: `build_rss_feed()` in `jobs/publish/rss.py` deduplicates by `episode_id`, then sorts by `published_date` descending before writing the feed.
- Fact: `load_podcast_feed_jobs()` in `jobs/publish/rss.py` pulls existing feed items from the local `docs/podcast.xml` file and optionally from the remote GitHub Pages feed, so the feed layer already has an append-like merge path.
- Fact: the repository tracks `docs/podcast.xml`, but it does not track `docs/audio/`, so local sidecar history is not durable in the checkout.
- Fact: the remote feed load in `load_podcast_feed_jobs()` is best-effort and silently ignores failures, which makes history retention depend on GitHub Pages being reachable and current at publish time.
- Inference: the likely bug is that old items are not surviving the merge because the only durable archive is the remote feed, and that archive is not guaranteed to be present when the writer runs.
- Inference: the RSS writer still matters because it decides which archived and local jobs survive into the final feed, but the real persistence gap may be the missing local archive rather than the sort/dedupe logic itself.

### Reuse Opportunities
- Reuse the existing publish-mode tests in `tests/test_publish_audio_pipeline.py` instead of adding a new test harness.
- Reuse the dated job model already produced by `jobs/publish/contracts.py`; the bug should be fixable by changing the window, not the contract schema.
- Reuse the RSS merge logic in `jobs/publish/rss.py`, because it already handles archived jobs and local sidecars and is the natural place to preserve append behavior.
- Reuse the existing workflow modes `daily`, `bootstrap`, and `reset` rather than introducing a new publish mode.
- Reuse the novena pipeline's `reset_feed` pattern as a reference for when the feed should deliberately truncate versus when it should preserve history.

### External References
- No new third-party APIs or libraries appear necessary for this fix.
- The publish feed uses standard RSS 2.0 plus iTunes podcast namespaces in `jobs/publish/rss.py`, but that appears stable and already implemented.

### Constraints
- Preserve episode IDs, GUIDs, audio paths, and sidecar filenames so old feed items stay stable.
- Keep the fix compatible with the existing `daily`, `bootstrap`, and `reset` workflow semantics.
- Avoid broad changes to text generation, Spotify playlists, or novena publishing unless the research later proves they are directly involved.
- Timezone handling matters because `published_date` is derived from the selected date and later used as the RSS sort key.
- The feed must remain append-like even when the current run only renders the newest date window.
- Any solution that relies on remote GitHub Pages fetches needs a fallback, because a transient network failure currently erases the append source from the merge inputs.

### Risks
- Historical sidecars in `docs/audio/` may already encode partial feed history, so the visible feed could remain confusing until the archive is validated.
- `load_podcast_feed_jobs()` in `jobs/publish/rss.py` merges local and remote feed items; a duplicate episode ID could mask the real change if the same episode already exists in another source.
- If the fix changes only the default mode, manual runs and scheduled runs may still diverge in a way that is surprising unless the docs are updated too.
- If the remote feed is unreachable or stale, the rebuild can fall back to only the current run's jobs, which would make the feed look like it stopped appending.
- The current checkout has no tracked `docs/audio/` archive, so history retention depends on either the remote feed or a future committed archive strategy.

### Assumptions To Validate
- The intended daily window can remain tomorrow-only if the feed is made append-like.
- The visible bug is not caused by a malformed or stale RSS item already present in the feed archive.
- The maintainer wants the feed to retain older episodes automatically rather than requiring a separate manual archive step.
- The team is okay with depending on the remote feed at publish time, or we should intentionally add a local archive source that survives across runs.

### Unknowns
- Whether the correct fix is to make the feed writer fail closed when the archive is missing, or to add a durable local archive source under version control.
- Whether any existing feed artifacts need cleanup after the retention bug is corrected.
- Whether the workflow docs should be updated in the same change so the daily/bootstrapping/append semantics are explicit.

### Recommended Direction
- Move to `/plan-astack` focused on archive durability, feed merge inputs, and remote-feed fallback behavior before changing any publish-mode defaults.

## Plan
### Summary
- We are fixing the podcast archive to behave like an append by default instead of silently truncating history on manual publish runs.
- The chosen approach is to keep the existing RSS merge mechanics, change the combined publish workflow default away from `reset`, and lock the behavior with regression coverage.
- This is the smallest complete fix because `jobs/publish/rss.py` and `jobs/novena_contracts/rss_publisher.py` already preserve history when they are allowed to read the existing feed archive.

### What Already Exists
- `jobs/publish/rss.py` already merges current render jobs with the prior feed and local sidecars, then deduplicates by `episode_id`.
- `jobs/novena_contracts/rss_publisher.py` already supports two modes: preserve history by default or truncate history when `reset_feed=True`.
- `tests/test_novena_pipeline.py` already covers both preservation and explicit reset truncation.
- `tests/test_publish_audio_pipeline.py` already covers the daily audio path and the next-day target-date behavior.
- `.github/workflows/publish_audio.yml` already exposes `daily`, `bootstrap`, and `reset` as the public publish modes.

### Architecture
- The combined publish workflow is the user-facing switchboard.
- The audio publish job renders the next-day slice and writes/refreshes `docs/podcast.xml`.
- The novena publish job appends the current novena slice onto the existing feed unless `reset` is explicitly requested.
- History should remain in `docs/podcast.xml` and the published audio sidecars, not in an extra hidden archive format.

```text
workflow_dispatch / schedule
  -> publish_audio.yml
      -> audio pipeline (daily = next-day slice)
      -> novena pipeline (append existing feed unless reset is explicit)
      -> write docs/podcast.xml

explicit reset
  -> publish_audio.yml
      -> novena pipeline(reset_feed=True)
      -> intentionally rebuild feed without prior history
```

### Concrete Changes
- `.github/workflows/publish_audio.yml`
  - Change the `workflow_dispatch` default from `reset` to `daily`.
  - Update the mode description so `daily` is documented as the append-safe default and `reset` is documented as destructive/manual recovery only.
- `README.md`
  - Update the publish-audio section to match the new default and make the append vs reset behavior explicit.
- `tests/test_publish_audio_pipeline.py`
  - Add a small regression that reads the workflow file and asserts the dispatch default is `daily`.
  - Keep the existing daily/reset coverage that proves the pipeline still produces tomorrow-only audio and can seed today+tomorrow when asked.
- `tests/test_novena_pipeline.py`
  - Keep the existing preservation and reset truncation tests as the behavior contract for the RSS rebuild path.

### UX And States
- No UI changes.
- Default manual publish becomes safe for the archive: it appends instead of truncating.
- `reset` stays available for explicit recovery when the maintainer intentionally wants to rebuild the feed from scratch.
- Error state remains unchanged: if the feed archive is absent or stale, the rebuild still reports a smaller-than-expected feed and the operator can decide whether to rerun or reset.

### Implementation Phases
#### Phase 1: Make append the default
- Goal: stop accidental truncation on the combined publish workflow.
- Exact files to edit: `.github/workflows/publish_audio.yml`, `README.md`.
- Symbols/interfaces touched: the `workflow_dispatch` default value and the mode-description text.
- Change summary: switch the default from `reset` to `daily`, and explain that `reset` is only for intentional archive truncation.
- Verification steps or commands: inspect the workflow YAML, then run the existing novena and audio pipeline tests to confirm append and reset behavior still match the code.
- Rollback note: revert the workflow default and docs text if the append-by-default behavior causes an unintended operational change.
- Dependencies on earlier phases, if any: none.

#### Phase 2: Lock the default with regression coverage
- Goal: prevent the workflow default from drifting back to destructive behavior.
- Exact files to edit: `tests/test_publish_audio_pipeline.py`.
- Symbols/interfaces touched: add a tiny file-based assertion against `.github/workflows/publish_audio.yml`.
- Change summary: assert the workflow dispatch default is `daily` while keeping existing runtime tests for preservation and reset.
- Verification steps or commands: run `python -m unittest tests.test_publish_audio_pipeline tests.test_novena_pipeline`.
- Rollback note: remove the config assertion if the workflow file layout changes and replace it with a more stable check.
- Dependencies on earlier phases, if any: Phase 1.

### Failure Modes
- If the workflow default remains `reset`, manual runs will keep truncating the feed and old episodes will disappear again.
- If the feed archive is missing, the rebuild can only preserve whatever is already present in `docs/podcast.xml` and the current sidecars.
- If `reset` is used intentionally, the feed will drop older items by design; that is expected, but it must be an explicit operator choice.

### QA And Test Matrix
- `tests/test_publish_audio_pipeline.py`
  - Verify the workflow file advertises `daily` as the default dispatch mode.
  - Verify the audio pipeline still targets tomorrow by default and can render today+tomorrow when explicitly instructed.
- `tests/test_novena_pipeline.py`
  - Verify a rebuild preserves an existing `morning-prayer` item and appends the new novena episode.
  - Verify `reset_feed=True` intentionally removes the old item.
- Manual smoke checks
  - Open `docs/podcast.xml` after a daily run and confirm prior GUIDs are still present.
  - Open `docs/podcast.xml` after a reset run and confirm prior GUIDs are absent.

### Rollout Notes
- No data migration is required.
- Changing the manual dispatch default is backward-compatible for scheduled runs, but it removes the hidden destructive default for operators.
- The explicit `reset` path remains available for recovery or feed surgery.

### Not In Scope
- Changing the tomorrow-only publish window.
- Redesigning RSS sorting or GUID generation.
- Adding a new archive format or moving feed history out of `docs/podcast.xml` / audio sidecars.
- Changing Spotify playlist refresh behavior.
