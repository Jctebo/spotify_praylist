# Release 0.1.2.0 - morning-prayer-contract-loop

- Status: Shipped

## Scope

### Problem
- The Morning Prayer job is still failing because the runner is looking for a config file at a path that does not exist in the current repo layout.
- The job contract is not being treated as durable data flowing through the runtime; instead, path assumptions are leaking into the workflow and runner.
- We need a single contract loop so the job can discover the right Morning Prayer config without hardcoded filesystem knowledge.
- This matters now because the GitHub Actions workflow is the production entrypoint, so a path mismatch blocks the daily run.

### Audience
- Primary user: the maintainer running Morning Prayer through GitHub Actions.
- Secondary stakeholders: any future prayer jobs that should reuse the same contract-loading pattern instead of hardcoding their own file path.

### Current Status Quo
- The workflow invokes the generic prayer runner with `PRAYER_CONFIG_FILE` set, but the runner still defaults to a repo-specific path if that env var is absent or mis-set.
- The repo currently has a root-level `config/morning-prayer.json`, while older docs and scripts still reference nested or legacy Morning Prayer paths.
- The current setup makes the job feel like it depends on one exact filename rather than on a contract loop that can resolve the active config from one source of truth.

### Goal
- Make the Morning Prayer job resolve its contract through a loop or registry-like contract loader instead of relying on a hardcoded file location.
- Keep the workflow contract-driven so the job can run the same way locally and in GitHub Actions.
- Preserve Morning Prayer as a reusable prayer contract, not a one-off special case.
- Make the contract source of truth obvious enough that future jobs can follow the same pattern.

### Constraints
- Do not break the existing Morning Prayer runtime path while fixing the contract resolution.
- Keep the solution small and boring: one contract source of truth, one loader path, one runner entrypoint.
- Preserve backwards compatibility long enough to avoid disrupting existing workflow dispatches or local scripts.
- Avoid adding a second hidden default path that would just recreate the same bug in a different place.

### Narrow Wedge
- Teach the generic prayer runner to resolve Morning Prayer from the active contract file system pattern used by the repo today.
- Remove any hardcoded Morning Prayer path assumption from workflow, script, or runner defaults that can bypass the contract file.
- Add regression coverage that proves the job uses the contract loop and fails clearly if the contract is missing.

### Non-Goals
- Rewriting the whole prayer generation engine.
- Redesigning the Morning Prayer content schema.
- Expanding the fix to every other job unless they share the same contract-loading bug.
- Changing the actual Morning Prayer text content or Notion row structure unless the contract fix requires it.

### Risks And Unknowns
- There may be more than one stale path reference, so fixing only the workflow would leave the runner broken.
- The contract loop may need to support both the current root-level file and older references during migration.
- If the loader logic is too permissive, it could mask a missing contract instead of surfacing a useful error.
- The biggest unknown is whether the runner should infer the active contract from a registry, a naming convention, or explicit workflow input.

### Recommended Next Step
- Use `/research-astack` to map every Morning Prayer contract entrypoint, identify the active source of truth, and decide whether the fix should be a loader normalization, a registry loop, or both.

## Research

### Scope Baseline
- The Morning Prayer workflow fails because the GitHub Actions job is still pointing at a stale nested contract path while the repo’s current active Morning Prayer contract lives at the root-level `config/morning-prayer.json`.
- The requested fix is to make contract selection data-driven and loop-based, not hardcoded to one file path.

### Relevant Files
- `.github/workflows/daily_novena_prayer.yml`
  - Currently passes `PRAYER_CONFIG_FILE: config/morning-prayer/morning-prayer.json`, which does not exist in the current repo layout.
- `jobs/notion/generate_prayer.py`
  - Generic prayer runner entrypoint; it defaults to `config/morning-prayer.json` and validates the selected config file.
- `jobs/notion/generate_page_audio.py`
  - Defines the broader Morning Prayer contract loading behavior and confirms the root-level contract path pattern used elsewhere.
- `scripts/run_daily_novena_prayer_local.ps1`
  - Local runner default also resolves to `config/morning-prayer.json`, which matches the newer root-level contract shape.
- `README.md`
  - Documents `config/morning-prayer.json` as the active Morning Prayer contract.
- `tests/test_generate_prayer.py`
  - Current regression coverage asserts the runner can load `config/morning-prayer.json` and run successfully when that env var is set.

### Current System Map
- There are two different contract path conventions in the repo history:
  - legacy nested Morning Prayer paths under `config/morning-prayer/`
  - the current root-level contract file `config/morning-prayer.json`
- The runner itself is not inherently parameter-only:
  - it reads `PRAYER_CONFIG_FILE` when present
  - otherwise it falls back to `config/morning-prayer.json`
- The manual GitHub Actions failure comes from the workflow overriding the runner with the stale nested path, so the default never gets a chance to help.
- This means the failure is primarily a workflow/config mismatch, with a secondary risk that any other stale path reference could recreate the same breakage.

### Reuse Opportunities
- Reuse the existing generic prayer runner instead of adding a second Morning Prayer entrypoint.
- Reuse the root-level `config/morning-prayer.json` contract as the active source of truth.
- Reuse the current runner validation and tests as the regression baseline for the fix.

### External References
- No external library or API research is needed for the contract-path issue itself.
- GitHub Actions workflow semantics matter here: `workflow_dispatch` does not imply parameter values, so explicit env overrides control which config gets loaded.

### Constraints
- The fix should not reintroduce a hardcoded nested path in another place.
- Backwards compatibility may matter if any local scripts or old docs still reference the legacy path.
- The loader should keep failing clearly when the selected contract file is truly missing.

### Risks
- Fixing only the workflow would leave local scripts or future callers vulnerable if they still point at the stale nested path.
- Broadening the loader too much could hide real misconfiguration instead of surfacing it.
- If the active contract path changes again, the same bug could reappear unless the contract source of truth is centralized.

### Assumptions To Validate
- The intended active Morning Prayer contract is `config/morning-prayer.json`, not the older nested path.
- The generic prayer runner should remain the canonical entrypoint for Morning Prayer.
- The contract-selection loop should be implemented as a small resolver layer, not as a second special-case runner.

### Unknowns
- Whether the workflow should stop setting `PRAYER_CONFIG_FILE` entirely and rely on the runner default.
- Whether a contract registry or naming convention is needed for future prayer jobs, or whether this fix should stay Morning Prayer-specific.
- Whether any other workflow, script, or test still encodes the stale nested path.

### Recommended Direction
- Update the workflow and any stale references to use the current root-level contract source of truth, then decide in `/plan-astack` whether the long-term solution is a lightweight contract registry/loop or simply centralizing the default path in the runner.

### Follow-Up Research Notes
- The repo already has multiple prayer contracts that could be grouped for fan-out:
  - `config/morning-prayer.json`
  - `config/rosary.json`
  - `config/afternoon_prayer_page_audio.json`
  - `config/angelus_*.json`
  - `config/daily_examen_page_audio.json`
  - `config/bible_in_a_year_page_audio.json`
  - `config/daily_mass_readings_page_audio.json`
  - `config/divine_office_*.json`
  - `config/saint_of_the_day_page_audio.json`
  - `config/sing_the_hours_*.json`
- The current generic runner already accepts one contract path at a time, which makes it naturally compatible with a matrix/fan-out orchestration layer.
- A GitHub Actions matrix is the clearest way to kick off multiple sub-jobs at once because each contract can run as its own isolated job with its own env vars and logs.
- A sequential loop inside one job would be simpler, but it would not give true parallelism and would make one failure harder to isolate from the rest.
- If the goal is “run all contracts nightly,” the best shape is likely:
  - a small manifest of contract entries
  - a matrix job that passes one contract path per job
  - an optional include/exclude list for contracts that should not run on every schedule
- If the goal is “run one contract manually,” keep the single-job dispatch path and use the matrix only for scheduled fan-out.

## Plan

### Summary
- Replace the existing scheduled prayer job with one GitHub Actions matrix job that fans out over a curated list of prayer contract files.
- Keep manual dispatch available, and have it execute the same full default matrix set so there is one orchestration path to maintain.
- The matrix should be derived from the JSON files directly under `config/`, not from nested folders.
- Use one contract path per matrix entry so each prayer runs as its own isolated job with independent logs, failures, and retries.
- Keep the runner contract-driven and path-agnostic beyond the selected config file, so the workflow does not encode another hidden contract convention.

### What Already Exists
- `jobs/notion/generate_prayer.py` already runs one contract file at a time through the generic prayer runner.
- `config/morning-prayer.json` is the current active Morning Prayer contract.
- The repo already contains other prayer contracts that are eligible for fan-out, including Rosary, Divine Office, Sing the Hours, Angelus, Bible in a Year, Daily Mass Readings, Saint of the Day, Daily Examen, Afternoon Prayer, and Auxilium Christianorum.
- Existing local scripts and tests already show the single-contract runner shape.

### Architecture
- Discover runnable contracts from the root-level `config/*.json` files.
- Use a GitHub Actions matrix to launch one job per contract entry in the existing workflow.
- Have the same workflow support `workflow_dispatch` by running the full default matrix set, so manual and scheduled runs share the same fan-out behavior.
- The runner stays unchanged except for any required hardcoded-path cleanup, because the orchestration layer is the right place to fan out.

ASCII flow:
```text
scheduled workflow
    |
    +--> matrix entry 1 -> contract A -> generate_prayer.py
    +--> matrix entry 2 -> contract B -> generate_prayer.py
    +--> matrix entry 3 -> contract C -> generate_prayer.py
    |
    v
independent job logs + isolated failures
```

### Concrete Changes
- `.github/workflows/daily_novena_prayer.yml`
  - Add a discovery step that emits a matrix from the JSON files directly under `config/`.
  - Replace the single hardcoded `PRAYER_CONFIG_FILE` with a matrix-driven `PRAYER_CONFIG_FILE` value sourced from that discovery step.
  - Keep manual dispatch support, but route it through the same matrix shape and default contract set.
- `jobs/notion/generate_prayer.py`
  - Keep the runner contract-file-based and remove any stale path assumptions if they remain.
- `tests/test_generate_prayer.py`
  - Add coverage that proves the runner honors the selected config file and does not depend on a nested path.
- `README.md`
  - Document the fan-out workflow and the difference between manual single-contract runs and scheduled matrix runs.

### UX And States
- Manual dispatch:
  - User launches the workflow and the full default contract matrix runs.
- Scheduled fan-out:
  - GitHub shows one matrix row per contract.
  - Each row is independently visible and can fail without obscuring the rest.
- Error state:
  - If a contract path is missing, that matrix row fails with a clear file-missing error tied to that contract only.

### Failure Modes
- A matrix entry points at a stale path.
  - Detection: one matrix row fails with a missing file error.
  - User experience: only that contract fails; the rest still complete.
- The workflow accidentally drops manual dispatch support.
  - Detection: no single-contract rerun path in the workflow.
  - User experience: maintainers lose the easy one-off recovery path.
- The contract list gets out of sync with the repo.
  - Detection: tests or workflow validation fail on missing file paths.
  - User experience: a scheduled row fails loudly instead of silently skipping.
