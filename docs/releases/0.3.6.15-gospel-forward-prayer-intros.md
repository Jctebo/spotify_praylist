# Release 0.3.6.15 - Gospel-Forward Prayer Intros

Date: 2026-06-22
Version: 0.3.6.15
Status: Shipped
Last Updated: 2026-06-22
Branch: enhancement/gospel-forward-prayer-intros
Depends On: 0.3.6.14

## Scope

### Problem
- The current daily-theme system gives generated prayers one shared daily focus, but listener-facing intros can still sound theme-first rather than Gospel-first.
- Morning Prayer should set the day by clearly foregrounding today's Gospel in the opening, not merely mention it as one supporting source for the theme.
- Other generated prayers should explicitly reference both today's Gospel and the shared daily theme so the listener hears continuity across the full prayer day.
- Daily Rosary decade reflections need the same treatment: each mystery reflection should be modified by today's Gospel and the shared day theme, not only by the fixed mystery fruit or generic liturgical focus.
- The current light-transition prayers can name `daily_theme_title` without naming the Gospel citation or Gospel movement that shaped the theme.
- Why now: the daily theme cache and novena sidecar freshness work are already in place, so this is a small, testable content-quality improvement on top of the existing shared context instead of a new pipeline.

### Audience
- Primary user: the maintainer shaping Ora Pro Nobis prayer audio and judging whether the generated intros sound coherent, Gospel-rooted, and Catholic.
- Daily listeners who pray Morning Prayer, Rosary, Daily Reflection, Auxilium Christianorum, Marian Antiphons, or novenas from the same daily feed.
- Future maintainers adding new prayer contracts who need a clear rule for how Gospel and theme should appear in intros.

### Current Status Quo
- `jobs/publish/daily_liturgical_context.py` builds an inclusive `daily_liturgical_context` payload with `gospelCitation`, `gospelTheme`, `sharedThemeTitle`, `sharedThemeExplanation`, `sharedThemeTransition`, and `sharedThemeSources`.
- `jobs/publish/contracts.py` resolves one canonical daily theme per date/calendar/locale and passes that payload through publish text and audio jobs.
- `jobs/publish/daily_intro.py` can accept `shared_theme` and already validates that a Gospel-present generated Morning Prayer intro mentions the Gospel.
- Morning Prayer begins with a `daily_intro` block in `config/publish/contracts/morning-prayer.json`.
- Marian Antiphons also contain a `daily_intro` followed by a `prayer_intro`, while Auxilium Christianorum uses a light `prayer_intro`.
- Rosary and Daily Reflection already use the shared theme more deeply, but tests should verify their listener-facing intro/reflection text connects the Gospel and theme rather than only the theme.
- Rosary reflection prompts already pass Gospel text in some branches, but the release needs an explicit contract that each decade reflection is shaped by today's Gospel and shared daily theme together.
- Novena rendering already receives daily theme context and persists `daily_liturgical_context` in sidecars, but its intro currently relies on theme transition language rather than a deliberate Gospel-and-theme sentence.

### Goal
- Morning Prayer intro must be Gospel-forward:
  - Open by orienting the listener to today's Gospel or Gospel citation when available.
  - Explain how the Gospel reveals or sharpens the shared daily theme.
  - Still mention the liturgical day/season naturally, but the Gospel should be the emphasized source.
- All other generated prayer intros should reference today's Gospel and the shared daily theme at an appropriate depth:
  - Daily Rosary: intro and every decade reflection should explicitly connect the mystery set, today's Gospel, and shared theme.
  - Daily Rosary reflections must keep the mystery and fruit visible while letting today's Gospel and day theme modify the reflection's application for the day.
  - Daily Reflection: title/body/examen should remain shaped by the shared theme and should name the Gospel grounding when available.
  - Auxilium Christianorum and Marian Antiphons: one concise transition should reference the Gospel citation or Gospel movement plus the shared theme before the fixed prayer.
  - Daily novenas: one short intro sentence should connect the novena's saint/day focus to today's Gospel and shared theme without replacing the novena text.
- Preserve fixed prayer bodies, official text boundaries, episode IDs, Spotify lookup durability, and deterministic fallback behavior.

### Constraints
- This turn is scope-only; no implementation before `/plan-astack`.
- Follow the mandatory astack flow: `/scope-astack`, `/plan-astack`, `/implement-astack`, `/review-astack`, `/ship-astack`.
- Reuse the existing shared daily liturgical context and Gospel helpers; do not add a new calendar, readings, or Gospel dependency unless planning proves the current data is insufficient.
- Generated and fallback text must remain concise, reverent, Catholic, and spoken-audio friendly.
- Tests must stay offline by mocking Romcal, USCCB/readings, OpenAI, ElevenLabs, Spotify, Notion, and R2 boundaries.
- If Gospel data is missing, intros must not pretend Gospel grounding exists; they should fall back to the liturgical day, season, and theme with a clear fallback path.
- Avoid changing required Spotify match terms or IDs to include variable Gospel/theme language.

### Narrow Wedge
- Treat the existing `daily_liturgical_context` as the canonical source for Gospel citation, Gospel theme, and shared daily theme.
- Update the intro-generation contract so Gospel-present days expose specific runtime/template fields such as Gospel citation, Gospel summary/movement, shared theme title, and Gospel-theme bridge text.
- Tighten Morning Prayer `daily_intro` prompt, validation, and deterministic fallback so Gospel is the primary opening emphasis.
- Update light `prayer_intro` rendering/templates for Auxilium and Marian Antiphons so they mention both the Gospel and the shared theme in one natural sentence.
- Tighten Rosary reflection generation and fallback so each reflection receives and uses the Gospel bridge plus day theme alongside the mystery/fruit.
- Update novena intro rendering to include a Gospel-and-theme bridge when Gospel context is present.
- Add regression coverage proving Gospel-present render contexts produce Gospel-forward Morning Prayer text and Gospel-referencing intros for the other generated prayer surfaces.

### Non-Goals
- Do not rewrite fixed prayer bodies for Auxilium Christianorum, Marian Antiphons, Rosary canonical prayers, imported novenas, or official source texts.
- Do not add a homily-length commentary to every prayer.
- Do not change Rosary mystery scheduling.
- Do not change Spotify playlist membership, Notion row names, website grouping, feed ownership, R2 publishing, or episode IDs.
- Do not redesign the website UI.
- Do not solve missing-Gospel data at the source unless existing helper behavior is broken.
- Do not regenerate checked-in audio artifacts during scoping.

### Risks And Unknowns
- The shared theme payload currently stores Gospel citation and theme, but may not store a short Gospel movement/summary suitable for every transition sentence; planning must decide whether to derive this deterministically or pass through existing Gospel text safely.
- Morning Prayer validation must be strict enough to prevent Gospel omission without becoming brittle for legitimate Gospel-free fallback days.
- Rosary reflection prompts must avoid replacing the mysteries with a Gospel mini-homily; each reflection should still be recognizably about the current mystery and fruit.
- Repeating the same Gospel citation in every prayer may sound mechanical; wording should vary by depth while preserving the explicit Gospel connection.
- Novena sidecar reuse can hide changed intro text unless freshness checks include the new Gospel-forward intro inputs.
- Some liturgical days have long citations or multiple Gospel options; templates need length-safe handling.
- Existing caches will invalidate for changed intro fragments, which is expected but should be called out during implementation and ship.

### Recommended Next Step
- Run `/plan-astack` next.
- The plan should map the exact runtime fields available in `daily_liturgical_context`, decide the minimal Gospel bridge fields needed for templates, then define small implementation phases for Morning Prayer, light prayer intros, Rosary/Daily Reflection checks, novena intro freshness, and tests.

## Research

### Scope Baseline
- Make the existing shared daily theme system more explicitly Gospel-forward in listener-facing intros.
- Morning Prayer should open with the Gospel as the main daily orientation when Gospel data is available.
- Rosary, Daily Reflection, Auxilium Christianorum, Marian Antiphons, and novenas should reference both today's Gospel and the shared daily theme without changing fixed prayer bodies.
- Rosary decade reflections are in scope, not only the Rosary intro: each reflection should be modified by today's Gospel and the shared day theme while preserving the mystery and fruit.
- The likely implementation is a small extension of the existing `daily_liturgical_context` and intro-rendering paths, not a new readings/calendar pipeline.

### Current System Map
- Publish audio/text flow:
  - `load_publish_contracts()` loads `config/publish/contracts/*.json`.
  - `build_text_jobs()` and `build_audio_jobs()` create one `DailyThemeRuntimeCache`.
  - Each approved entry receives `_entry_runtime_context(..., shared_theme_runtime=cache.get(...))`.
  - Runtime context flows into metadata rendering, text body rendering, audio fragments, resume markers, and final sidecar `render_context`.
- Shared daily theme flow:
  - `DailyThemeRuntimeCache` calls `build_canonical_daily_theme_runtime_context()` strict first with `allow_missing_gospel=false`.
  - If strict Gospel resolution fails, it retries with `allow_missing_gospel=true`.
  - Runtime fields include `daily_liturgical_context`, `daily_theme_title`, `daily_theme_explanation`, `daily_theme_transition`, `daily_theme_reflection_focus`, `daily_theme_sources`, and `daily_theme_version`.
- Current Morning Prayer intro flow:
  - `resolve_block_content()` calls `build_daily_intro_text(..., shared_theme=runtime_context["daily_liturgical_context"])`.
  - If shared theme exists, the prompt requires sentence 2 to begin `Today's focus is` and sentence 3 to begin `In today's Gospel`.
  - `_validate_theme_intro()` requires a focus phrase and Gospel mention when Gospel data exists.
  - The deterministic fallback says `Today the Church celebrates...`, then theme explanation, then `In today's Gospel...`.
- Current light prayer intro flow:
  - `_resolve_prayer_intro_content()` renders one sentence from a contract template.
  - Supported placeholders are currently `{day_theme}`, `{daily_theme_title}`, `{daily_theme_transition}`, `{daily_theme_explanation}`, `{prayer_title}`, and `{devotion}`.
  - Auxilium and Marian templates name the theme but not Gospel citation or Gospel movement.
- Current Rosary flow:
  - `build_rosary_day_context()` fetches Gospel context separately, accepts shared theme payload, and lets shared theme override `focus_title` and `focus_prompt_label`.
  - Rosary reflection prompts include Gospel-specific rules and Gospel text when present.
  - Rosary reflection prompts already list each mystery and fruit; the plan should make Gospel bridge and shared daily theme explicit inputs for every generated reflection, including feast-day paths.
  - Rosary intro prompt includes shared daily focus but does not explicitly require a Gospel sentence.
- Current Daily Reflection flow:
  - `_get_or_build_ignatian_reflection_episode()` converts the runtime payload back into a `DailyLiturgicalContext` and calls `build_ignatian_reflection_episode()`.
  - Generated prompt receives full JSON context.
  - Deterministic fallback mentions `gospelTheme` but not citation.
- Current novena flow:
  - `publish_daily_novena()` resolves canonical daily theme context for target dates.
  - `render_novena()` merges that context into novena runtime context.
  - `_intro_fragment()` prepends one fixed welcome sentence plus `daily_theme_transition`.
  - Sidecar freshness compares canonical daily context metadata and refreshes target-date sidecars when theme fields drift.

### Reuse Opportunities
- Reuse `DailyLiturgicalContext` as the single source of Gospel/theme truth instead of fetching or deriving Gospel context independently in new places.
- Add a compact, deterministic Gospel bridge field near `_shared_theme_payload()` and flatten it through `daily_theme_runtime_fields()`.
- Reuse `_resolve_prayer_intro_content()` placeholders for light transitions by adding Gospel placeholders instead of adding new block kinds.
- Reuse Morning Prayer `daily_intro` fallback and validation machinery, but revise the shape so Gospel-forward output can pass intentionally.
- Reuse existing Rosary `RosaryDayContext` fields and reflection-set generation; tighten prompts/fallbacks/tests so every decade reflection is explicitly Gospel-and-day-theme-shaped.
- Reuse Daily Reflection's existing full-context prompt and deterministic fallback; likely add citation-aware wording and tests rather than a structural change.
- Reuse novena `_intro_fragment()` and freshness keys; if the new Gospel bridge is stored in the daily context, sidecar freshness can detect changes through `sharedThemeTransition` or a new explicit key.

### Risks
- Morning Prayer currently enforces a liturgical-celebration first sentence; changing it to Gospel-first may break existing tests and assumptions around sentence shape.
- Adding a Gospel bridge field only to flattened runtime fields but not top-level `daily_liturgical_context` would make publish and novena behavior drift; it should be present in both or derived consistently.
- If the Gospel bridge is generated from raw Gospel text without guardrails, it could become too long or unsupported by tests; deterministic short templates are safer for the first wedge.
- Rosary already prioritizes feast focus before Gospel in some cases; forcing explicit Gospel language in every Rosary intro may conflict with feast-day precedence unless carefully worded as Gospel-plus-theme, not Gospel-only.
- Rosary reflections have multiple generation branches; implementation must cover ordinary Gospel, feast-focused, and deterministic fallback paths or some days will remain theme-only.
- Novena sidecar skip logic may preserve old intro text outside target dates by design; target-date freshness should be enough for publish, but planning should not promise immediate refresh of all historical sidecars.
- Repeating `today's Gospel, {citation}` verbatim in every prayer can sound mechanical; plan should provide a small set of context-specific phrases.

### Assumptions To Validate
- The desired Morning Prayer behavior is allowed to change the first sentence away from `Today the Church celebrates...` to a Gospel-first opening, while still mentioning the liturgical day shortly after.
- It is acceptable for non-Morning Prayer intros to use a concise citation-level Gospel reference rather than summarize the Gospel text each time.
- The canonical shared daily theme's `gospelTheme` plus `gospelCitation` is enough to create a safe Gospel bridge for light transitions; we do not need to pass full Gospel text into every intro template.
- Historical sidecars outside the current publish target dates do not need forced regeneration for this release.

### Unknowns
- Exact listener-facing wording standard:
  - Should light transitions say `today's Gospel, Matthew 5:43-48` every time, or use softer wording such as `the Gospel's call to humility` when `gospelTheme` exists?
- New field shape:
  - Add `sharedGospelBridge` / `daily_gospel_bridge`, or derive it inside renderers from existing `gospelCitation` and `gospelTheme`?
- Versioning:
  - Whether Gospel-forward intro changes should bump `SHARED_THEME_VERSION` or rely on changed fragment text/content hashes and existing sidecar freshness.
- Daily Reflection depth:
  - Whether generated prompt rules must explicitly require the Gospel citation, or whether deterministic fallback and metadata coverage are enough.

### Recommended Direction
- In `/plan-astack`, keep the implementation to four small phases:
  - Add a deterministic Gospel bridge to the shared theme payload/runtime copy path.
  - Make Morning Prayer `daily_intro` Gospel-forward with revised validation and fallback.
  - Add Gospel placeholders to `prayer_intro` and update Auxilium/Marian templates, plus Rosary intro/reflection and Daily Reflection prompt/test tightening.
  - Update novena intro wording and target-date sidecar freshness/tests.
- Prefer deterministic, citation/theme-based bridge wording over summarizing full Gospel text in every intro.
- Do not add new external dependencies or alter publish job architecture.

## Plan

### Summary
- Build a Gospel-forward intro pass on top of the existing shared daily liturgical context.
- Add one deterministic Gospel bridge to the shared theme payload/runtime fields, then reuse it in Morning Prayer, light prayer intros, Rosary, Daily Reflection, and novenas.
- Chosen approach: extend existing context/rendering seams instead of adding a new Gospel source or new publish block type, preserving episode IDs, Spotify lookup terms, and fixed prayer bodies.

### What Already Exists
- `DailyLiturgicalContext` already carries Gospel citation, Gospel theme, shared theme title, explanation, transition, reflection focus, sources, and version.
- `DailyThemeRuntimeCache` already resolves one canonical strict-Gospel-first context per `(date, calendar, locale)` and shares it across publish entries.
- `build_daily_intro_text()` already receives shared theme context and has validation/fallback hooks.
- `_resolve_prayer_intro_content()` already renders one-sentence bridge blocks from contract templates.
- Rosary and Daily Reflection already consume shared theme context.
- Novenas already receive canonical daily theme context and persist it in sidecars with freshness checks.

### Architecture
```text
build_daily_liturgical_context()
  -> DailyLiturgicalContext(sharedGospelBridge, sharedTheme...)
  -> daily_theme_runtime_fields()
       daily_gospel_bridge
       daily_gospel_citation
       daily_gospel_theme
  -> build_text_jobs/build_audio_jobs runtime_context
       -> daily_intro: Gospel-forward Morning Prayer intro
       -> prayer_intro: Auxilium/Marian Gospel + theme bridge
       -> rosary_intro/reflections: Gospel + mystery + day-theme prompts
       -> ignatian_reflection: Gospel-grounded prompt/fallback
       -> novena intro: saint/day focus + Gospel + theme bridge
```

- `sharedGospelBridge` will be deterministic and short:
  - Gospel present with theme and citation: `today's Gospel, {citation}, draws us into {gospel_theme}`.
  - Gospel present without citation: `today's Gospel draws us into {gospel_theme}`.
  - Gospel missing: empty string.
- Runtime will expose both camel-case payload and snake-case flattened fields:
  - `daily_liturgical_context.sharedGospelBridge`
  - `daily_gospel_bridge`
  - `daily_gospel_citation`
  - `daily_gospel_theme`
- Morning Prayer will change from celebration-first validation to Gospel-first validation only when Gospel text is available:
  - Sentence 1 begins with `In today's Gospel`.
  - Sentence 2 begins with `Today's focus is`.
  - Sentence 3 begins with `Today the Church celebrates` or otherwise names the liturgical day/season.
- Gospel-missing Morning Prayer keeps the existing liturgical-day fallback behavior and must not mention Gospel.
- Light `prayer_intro` remains exactly one sentence.
- No UI scope.
