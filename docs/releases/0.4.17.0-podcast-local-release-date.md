## Scope

### Problem
- The Oct 12 audio workflow generated Oct 13 daily prayer and novena episodes, but the Oct 12 devotional-image workflow later redeployed an older podcast feed built from a stale audio cache. The image workflow is also an active podcast-feed publisher and must remain enabled.
- RSS `pubDate` is noon UTC (7:00 AM Chicago time), which can also keep current-date episodes hidden in podcast apps during the early morning.

### Audience
- Primary user: listeners expecting the daily prayer and novena podcast episodes on their Chicago-local calendar date.
- Secondary stakeholders: podcast apps consuming the shared RSS feed.

### Current Status Quo
- `jobs/publish/rss.py::_published_at` combines each episode's `published_date` with 12:00 UTC.
- The Oct 12 scheduled run logged Oct 13 episode IDs, and its Pages artifact contains Oct 13 items dated `Tue, 13 Oct 2026 12:00:00 +0000`.
- At 5:08 AM Chicago time on Oct 13, the live feed showed Oct 12 as its newest date, while the Oct 12 audio workflow artifact contained Oct 13 items.
- The devotional-image workflow restored the audio archive cache at 15:27 UTC, before the audio workflow saved its updated cache at 15:45 UTC; it then deployed Pages at 15:56 UTC, after the audio workflow deployed at 15:46 UTC. Both workflows can rewrite and deploy the shared podcast feed without a common concurrency lock.
- Daily prayer and novena items share the RSS builder, so the same publication timestamp rule affects both.

### Goal
- Keep both active Pages publishers running while ensuring a stale devotional-image Pages deployment cannot replace a newer audio feed.
- Make each episode eligible for podcast app display at the start of its published date in America/Chicago.
- Keep episode IDs, titles, dates, ordering, retention, and audio URLs unchanged.

### Constraints
- Preserve the `published_date` calendar date and existing RSS metadata.
- Serialize the two workflows that deploy the shared GitHub Pages tree; keep the devotional-image workflow enabled because it also publishes the audio feed.
- Use a DST-aware `America/Chicago` timezone when constructing RSS publication timestamps.
- Include the IANA timezone data package in the base dependencies so `ZoneInfo` also works on Windows developer machines.
- Keep the fix confined to RSS publication timing; do not change the scheduling target date or audio generation.

### Narrow Wedge
- Give both Pages-deploying workflows the same non-canceling concurrency group so only one archive restore/build/deploy sequence runs at a time.
- Change the shared RSS publication timestamp from noon UTC to midnight America/Chicago for each episode's `published_date`.

### Non-Goals
- Changing podcast provider refresh behavior or forcing client-side refreshes.
- Changing the daily workflow schedule, target-date selection, episode content, or audio generation.
- Changing the separate devotional-wallpaper workflow, infographic generation, image generator code, or stored images.

### Risks And Unknowns
- Podcast apps may cache feeds independently; correctly published items can still take time to appear after RSS is updated.
- Shared workflow concurrency permits only one pending run per GitHub Actions concurrency group; a new pending run can replace an older pending run, so inspect GitHub's scheduling behavior and keep the two daily schedules staggered.
- Midnight local publication dates convert to different UTC offsets across daylight saving transitions; tests should verify the Chicago zone is applied rather than a fixed offset.

### Recommended Next Step
- Confirm both workflows are the only publishers of the shared Pages tree and use the shared `_published_at` helper for all podcast episodes; then implement the shared lock and Chicago-local release timestamp, preserving the image workflow as an active part of audio publishing.

## Research

- `gh run 38262747407` (Oct 12 audio) created Oct 13 episode IDs and its uploaded Pages artifact contains 19 Oct 13 items.
- `gh run 38270148024` (Oct 12 devotional images) restored published audio cache at 15:27 UTC and deployed at 15:56 UTC. The audio run saved its updated archive cache at 15:45 UTC and deployed at 15:46 UTC. The image workflow therefore deployed the older cache after the newer audio feed.
- The live feed at `https://jctebo.github.io/spotify_praylist/podcast.xml` listed Oct 12 as its newest episode date at 10:08 UTC on Oct 13.
- Only `.github/workflows/publish_audio.yml` and `.github/workflows/daily_devotional_image_remote.yml` upload/deploy GitHub Pages artifacts. Neither has a shared concurrency group. A repository architecture note already identifies concurrent Pages deploys as a feed-loss risk.
- `jobs/publish/rss.py::_published_at` sets every `published_date` to 12:00 UTC; in Chicago this is 7:00 AM during daylight time and 6:00 AM during standard time.
- `jobs/novena_contracts/rss_publisher.py` delegates to the same shared RSS builder, so one timestamp fix covers daily and novena podcast episodes.
- `docs/architecture/publish-audio-feed-retention.md` already warned that concurrent Pages deployments could race; this release updates that note to describe the shared lock.
- The image workflow remains enabled and is part of the audio feed publishing path; its generator and image assets are outside this change.

## Plan

### Summary
- Keep both the audio and devotional-image workflows enabled and serialize their shared GitHub Pages deployments, preventing an image run from redeploying a stale audio archive after a newer audio run.
- Set podcast `pubDate` to midnight America/Chicago so current-date episodes are eligible to appear in Spotify and other podcast apps as soon as the daily build finishes.
- These changes directly address the observed Oct 12 deployment order and the current-date release delay.

### What Already Exists
- The audio workflow saves the refreshed `docs/audio` archive cache and deploys `docs/` to GitHub Pages.
- The devotional-image workflow restores `docs/audio`, rebuilds `podcast.xml` from that cache, and also deploys GitHub Pages.
- Both daily and novena RSS generation call `jobs.publish.rss.build_rss_feed`, which uses the shared `_published_at` function.
- The schedules are staggered by 15 minutes, but the audio workflow can take longer than the image workflow's start delay; without a shared lock, the image workflow can redeploy a stale audio cache.

### Architecture
```text
audio workflow (render -> refresh cache -> deploy) ---------+
                                                           +--> shared Pages lock --> deploy in sequence
image workflow (render images + restore archive -> feed -> deploy) --+

published_date -> midnight America/Chicago -> RSS pubDate -> podcast app
```

### Concrete Changes
- `.github/workflows/publish_audio.yml`
  - Add workflow-level concurrency group `podcast-pages-publish` with `cancel-in-progress: false`.
- `.github/workflows/daily_devotional_image_remote.yml`
- Keep the workflow enabled and use the identical concurrency group and non-canceling behavior so its cache restore and deploy cannot overlap audio publishing.
- `jobs/publish/rss.py`
  - Make `_published_at` construct midnight in `ZoneInfo("America/Chicago")` for the job's `published_date`; Python's timezone database will apply the correct daylight or standard offset.
- `requirements.txt`
  - Add the same pinned `tzdata` version already used by the devotional wallpaper dependency set, ensuring the timezone database is available on Windows.
- `docs/architecture/publish-audio-feed-retention.md`
  - Document that both shared Pages publishers are serialized and keep the residual risk tied to future publishers that bypass the lock.
- `docs/releases/VERSION` and this release artifact
  - Track release version `0.4.17.0`, scope, implementation, and QA status.

### UX And States
- No interactive UI changes. Current-date episodes are dated at the beginning of the Chicago-local date.
- If an RSS app caches the feed, it may still take time to refresh after the server publishes the updated feed.

### Implementation Phases
#### Phase 1: Prevent stale Pages deployments
- Goal: Keep the image workflow running while preventing it from deploying an audio archive snapshot older than the latest audio workflow.
- Files: `.github/workflows/publish_audio.yml`, `.github/workflows/daily_devotional_image_remote.yml`.
- Symbols/interfaces: workflow-level `concurrency` configuration.
- Change: Assign both active workflows the same concurrency group, with cancellation disabled. The lock covers archive restore through Pages deployment, so a waiting image run restores cache only after the audio workflow has finished saving it.
- Verification: inspect both workflow definitions for identical group and cancellation settings; compare the Oct 12 run ordering against the resulting serialization behavior.
- Rollback: remove the two workflow-level concurrency blocks together; retain both workflows.
- Dependencies: none.

#### Phase 2: Publish episodes at Chicago midnight
- Goal: Remove the 7:00 AM Chicago release delay caused by a noon UTC `pubDate`.
- Files: `jobs/publish/rss.py`.
- Symbols/interfaces: `_published_at`.
- Change: attach `published_date` to local midnight in `America/Chicago`, preserving the calendar date while allowing timezone rules to select the correct UTC offset.
- Verification: inspect RSS timestamp conversion for dates in both daylight and standard time; confirm RSS formatting still emits a valid RFC date.
- Rollback: restore the prior UTC-noon timestamp.
- Dependencies: none.

#### Phase 3: Include timezone data for Windows
- Goal: Keep `ZoneInfo("America/Chicago")` resolvable outside Linux runners.
- Files: `requirements.txt`.
- Symbols/interfaces: base runtime dependencies.
- Change: add the repository's existing pinned `tzdata` version to the base requirements used by the audio workflow and local development.
- Verification: confirm the version matches `requirements-devotional-wallpapers.txt` and that the audio workflow installs the base requirements.
- Rollback: remove the new requirement if the runtime stops relying on IANA timezone data.
- Dependencies: Phase 2.

### Failure Modes
- If the concurrency groups differ, the race remains; both workflow files must use the exact same group value.
- If cancellation is enabled, a waiting daily publish could be canceled and leave the feed stale; keep it disabled.
- A wrong timezone or fixed UTC offset could publish on the previous local date; use the IANA `America/Chicago` zone.
- Podcast apps may cache RSS after the server has the new feed; the server-side feed date and content are the source of truth for verification.

### Not In Scope
