## Scope

### Problem
- Dynamic prayer links on the daily prayer homepage currently open Spotify show pages or search results instead of the individual item listeners expect.

### Audience
- Primary user: listeners opening a prayer from the daily prayer homepage.
- Secondary stakeholder: site maintainer publishing the daily Pages artifact.

### Current Status Quo
- Fixed Spotify items already link directly.
- Episode-lookup contracts link to their show, while resolver-backed contracts fall back to Spotify search.
- Group-level buttons already link to the configured Spotify playlists.

### Goal
- Every available prayer item on the homepage links directly to its Spotify track or episode.
- No prayer link points to a Spotify search or show page.
- Existing group playlist links, order, and membership stay unchanged.
- If a dynamic item cannot be resolved, keep its label visible without adding a misleading destination.

### Constraints
- Reuse the existing Spotify contract resolver and repository credentials.
- Resolve items during the Pages artifact build; do not expose credentials or add browser-side Spotify API calls.
- Do not alter playlist refresh behavior, audio publishing, RSS, wallpaper selection, or page layout beyond a clear unavailable state.

### Narrow Wedge
- Change page-data generation to map current Spotify URIs to direct item URLs and preserve playlist URLs as currently configured.

### Non-Goals
- Reordering playlists, changing playlist membership, changing audio/RSS feeds, or adding new prayer content.
- Updating Spotify API credentials or changing Spotify resolver rules.

### Risks And Unknowns
- Local Spotify credentials are invalid in this environment, so the production resolver result must be verified by the Pages workflow after merge.
- A missing current Spotify result leaves that item unavailable on the page until a successful build resolves it.

### Recommended Next Step
- Reuse `jobs/playlist/refresh_playlist.py` resolution inside the static Pages builder, then test direct URL conversion, auth failure, no-result behavior, and unchanged playlist links.

## Research

- `scripts/build_pages_artifact.py` currently maps fixed item URIs to direct links, episode lookups to show URLs, and resolver-backed contracts to search URLs.
- `jobs/playlist/refresh_playlist.py` already provides `sp_client`, resolver configuration, and `resolve_contract_uris`, using the same Spotify credentials as the daily refresh workflow.
- `.github/workflows/publish_audio.yml` builds Pages after audio/RSS publishing and currently lacks Spotify credentials in that step; `daily.yml` already has the required repository secrets.
- `config/site/site.js` renders each prayer as an anchor and already has a separate playlist action built from each group's unchanged `playlist_url`.
- Existing tests cover page artifact ordering and assets in `tests/test_build_pages_artifact.py`, with workflow checks in `tests/test_publish_site.py`.
- The builder resolves only contracts referenced by the active playlist definitions, avoiding calls for unused contracts.

## Plan

### Summary
- Resolve the active prayer contracts during the Pages build, emit direct Spotify track/episode URLs, and keep the playlist buttons unchanged.

### What Already Exists
- The contract loaders provide the active ordered membership and fixed item IDs.
- The playlist refresh module resolves dynamic contracts through Spotify and uses the repository Spotify credentials.
- The frontend renders safe Spotify links from the generated `prayers.json` payload.

### Architecture
- The Pages artifact builder resolves active contracts with the existing Spotify client/resolver. It writes only direct item URLs; if no item resolves or auth is unavailable, it writes `null` and warns. The browser leaves the prayer label visible without an outbound link.
- Playlist URLs continue to derive from the same playlist IDs and remain independent from item resolution.

```text
Playlist contracts ──> existing Spotify resolver ──> track/episode URLs ──┐
                                                                           ├─> prayers.json ──> page
Playlist definitions ──────────────────────────────> unchanged playlist URLs ┘
```

### Concrete Changes
- `scripts/build_pages_artifact.py`: convert resolved Spotify URIs only when the type is `track` or `episode`; use the first URI for a contract that resolves multiple episodes; never create search/show links; handle missing credentials/API errors without breaking audio/RSS publishing.
- `.github/workflows/publish_audio.yml`: pass the existing three Spotify secrets only into the Pages build step.
- `config/site/site.js` and `config/site/site.css`: render unresolved prayer labels as unavailable text, not a non-direct anchor.
- `tests/test_build_pages_artifact.py`: test fixed and resolved direct item URLs, invalid/non-item URI rejection, missing resolver/auth behavior, and unchanged playlist links.
- `tests/test_publish_site.py`: verify Spotify credentials are scoped to the Pages build step.
- `tests/test_publish_rosary_reflections.py`: isolate an existing provider lookup in the deterministic-fallback test so the full suite does not depend on live provider output.

### UX And States
- Resolved prayer: normal link opens the exact Spotify track or episode.
- Unresolved prayer: label remains visible and is styled muted; no misleading Spotify destination appears.
- Playlist action: stays enabled and targets the existing playlist URL.

### Failure Modes
- Spotify credentials are missing/invalid: dynamic prayer links are omitted with a warning; the other Pages assets still build.
- A contract has no current Spotify item: its page label remains visible without an outgoing link.
- A resolver returns a show or other non-item URI: it is rejected; playlist links remain unchanged.
- A Spotify URI changes: normalization or the direct-item type allowlist rejects it rather than generating a search destination.

- Verify a `spotify:track:<id>` remains a direct track link.
- Verify no-resolver, auth-failure, show, and unsupported URI cases never produce search/show URLs.

### Not In Scope
