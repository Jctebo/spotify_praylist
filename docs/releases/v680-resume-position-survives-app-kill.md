### §2.2 Where position is captured and written today — NATIVE path (the APK, John's phone)

The service's ExoPlayer is the engine; **the element never plays** (Fork B header, client.ts:19608–19622). Consequences, seat by seat:

- `timeupdate` **never fires** — the 15 s position ticks, the 5 s `saveResume`, and the 5 s queue-snapshot leg of the element handler never run.
- The element `pause` event **never fires** — the pause saves at client.ts:6725–6726 never run.
- The client's own position-save functions read `audioEl.currentTime`, which stands at **0** under the native engine, so every save that IS reached (visibility hidden, `pagehide`, skip-away, `exitPlayer`'s first act) returns on its own `pos > 0` guard. The header states this as design (client.ts:19615–19620): *"Marks and positions under the native engine are the SERVICE's write-backs … this client's own position saves stand down on their own guards (the element never plays, so its position reads 0 …) — nothing double-posts."*
- **The service's write-backs are the only native position writes**, and every one of them is an EVENT write, per the standing record in this repo (the shell source is a separate Android repo, not in this tree — seats below are the client/doc record of the shell's behavior):
  - on **pause** — "the service writes its pause position while its contract still stands" (client.ts:19540, `exitPlayer` comment);
  - on **skip / transition** — the shell's mark rule: "skips save position, never mark" (docs/releases/v661.md §unchanged-stores note);
  - on **natural end** — the completion record + the 0/0 day-position write-back (`NativeWriteback.kt:68 postDayPosition`, cited at docs/releases/v651.md:214–217; the client drain's comment, client.ts:19859–19864).
  - **No periodic native write-back is named anywhere** — not in the client, not in v466/v651/v661. During continuous playback the position exists only in the service's player and in the page's `nativeMirror` (client.ts:19623, fed by `applyNativeState`, client.ts:19969).
- The ONE periodic native write that exists: `nativeMirrorTick` runs on the standing 5 s interval (client.ts:20299) and calls `saveQueueSnapshot(Math.floor(playPos().pos))` (client.ts:20175). But `saveQueueSnapshot` (client.ts:4844) **removes the record and returns when no queue stands** (`!state.queue.length || !state.current`), and removes it for Starred/homily queues. So it persists position only for a standing QUEUE play — and only into the queue record, whose sole reader is the boot restore (§2.3), never the per-episode stores a tap reads.

### §2.4 THE KILL GAP — named, per path

**Native path (John's field case) — THE defect.** During native playback, NO write of the playing position reaches any kill-surviving store at any moment while the episode plays:

1. The client's periodic writes are element-driven and never fire; its event writes read the element's 0 and stand down by design (§2.2).
2. The service's write-backs fire only on pause / skip / natural end — **a hard kill runs none of them**: the process dies mid-playback and the position dies with the player.
3. The 5 s mirror queue snapshot is the sole exception and it does not reach the tap path: it writes only when a queue stands, only into `opn-queue-v355`, and a fresh tap on the episode never reads that record — `startDesc` reads `podPositionS` / the day fold (§2.3), which under native playback were last written by a pause/skip/end that, in the kill case, never happened (or never happened for this episode at this position).

Result on return: the tap-time folds read 0 / stale / absent → `pendingResume` stands null → the contract's `startPositionS` is 0 → **the episode starts over. John's report, exactly.** For a single-episode tap (no queue — the Podcasts-side / episode-page play, where `saveQueueSnapshot` removes its record by construction) there is not even the queue-record exception: no persistent position exists at all.

**Web / element path — bounded, not the field defect, two named weaknesses:**

1. **Day positions have no offline/kill safety net:** `writeDayPositionQuiet` is a bare post with no local slot (client.ts:11168–11178, contrast the podcast slot at client.ts:11084). A tick or event post that fails (offline, torn connection at the kill moment) is lost whole; the podcast path's slot-and-drain discipline has no day twin.
2. **Staleness bound:** the position ticks run at 15 s with a ≥ 5 s movement gate, so even a clean web kill can lose up to ~15 s. That is a rewind, not a restart — named here so Implement does not claim the web path was broken the same way, and so the fix's single cadence (§2.5) closes it uniformly.

### §2.5 The fix shape (Implement's spec)

Client only — `app/worker/src/client.ts`, plus the pin in `ui.ts`. No server change, no migration, no route change: the fix writes through the STANDING routes (`/api/player/podcasts/position`, `/api/player/day-position`), which already land in the kill-surviving stores of §2.1 in both shapes.

1. **One native-aware position source.** A single helper reads the current track's live position engine-correctly: native mode → `playPos()` (the mirror, accepted only when `nativeMirror.trackId === state.current.episodeId`, the v617 live-carry guard); element mode → `audioEl.currentTime`. The position-save family (`podPositionSaveCurrent`, `dayPositionSaveCurrent`, and their skip-away twins) reads through this helper instead of `audioEl` directly, with their standing guards preserved in substance (never on the ended path, never at/past the end — the end test reads the helper's duration — never at/below the threshold in step 3). This un-stands-down the client saves in native mode **through the standing routes only**; the shell's own pause/skip/end write-backs are untouched and remain the service's business (a duplicate write of the same value through the same route is the stores' standing last-writer-wins upsert — no double-post hazard class is created, and the periodic leg in step 2 is the client's, not a second event post).
2. **Periodic write DURING playback — interval 5 s, both paths.**
   - Native: extend `nativeMirrorTick`'s standing 5 s interval (client.ts:20299) — while the mirror reports the current track PLAYING and fresh, run the position saves through step 1's helper (podcast and day legs by kind). This is in addition to, and does not alter, its queue-snapshot call.
   - Web/element: the position legs of the `timeupdate` handler move from the 15 s tick to the standing **5 s** cadence already used by `saveResume`/`saveQueueSnapshot` in the same handler (client.ts:6745–6748). The ≥ 5 s movement gate stands (a write whose value has not moved ≥ 5 s since the last sent value is still skipped — at a 5 s cadence this bounds writes to roughly one per 5 s of actual progress, and a paused track writes nothing periodically; the pause save is its write).
   - **Guarantee this buys:** at any kill moment, the newest persisted position is at most ~5 s behind the live position (plus one post's flight time; the podcast slot covers that flight — step 4 covers the day leg).
3. **Threshold — 5 s stands as "not started."** Today the stores carry no explicit opening threshold: event saves accept any `pos > 0` and the ticks carry the ≥ 5 s movement gate (§2.1). The fix makes the standing gate the named rule: **a persisted position < 5 s is not a resume position** — the periodic and event saves do not write below 5 s (a save that would land below it writes nothing; it does NOT delete a standing higher value from an earlier session leg — deletion remains the ended/mark paths' act), and the tap-time read treats a stored position < 5 s as 0. Net effect: an episode heard only for its opening seconds starts at the top on return, deterministically, on both paths.
4. **Day-position slot parity.** Day saves gain the podcast path's coalesced local slot discipline: a synchronous `localStorage` slot write BEFORE the post (`opn-daypos-pending-v1`, keyed `episodeId|date`, newest wins), the entry dropped only when a post succeeds holding that same value, and a drain at the standing drain moments (app open beside `drainPodPositions`, and `online`). A 0 (ended-clear) write drops the slot entry and posts the delete as today. This closes §2.4 web weakness 1 and gives the native day leg the same mid-flight kill cover the podcast leg already has.
5. **Event writes on the native seams that DO run.** In `applyNativeState`: (a) a playing→paused flip for the current track runs the position saves (the mirror holds the position the element pause event would have carried); (b) a track-change (`changed`) block runs the skip-away save for the OUTGOING track at the mirror's last position for it, before the current updates — the native twin of `startDesc`'s skip-away, guarded exactly as step 1 (the v617 transition seek in the same block is untouched); (c) the `stopped` publish runs the saves before its clear, when a current stands. Visibility-hidden and `pagehide` handlers already call the saves — with step 1 they now write real values in native mode with no change to those handlers.
6. **Tap-time read — no new reader.** `startDesc`'s standing reads (§2.3) stand, with only step 3's < 5 s rule applied at the two read seats (podcast branch `desc.podPositionS`, day branch fold value — `queueMarkPos617` applies the same rule so queue tracks and single taps agree). Because the writes now land in the same stores the folds read, a post-kill reopen + payload fetch carries the position onto the descriptor, and the tap resumes — on the Praylist and on the episode's own page, which share the descriptor builders named in §2.3.

**Boundaries (unchanged, by name):**

1. **Completion governs.** A finished episode stands read with no resume: listened → `podPositionS` null (index.ts:3512), position row deleted at mark/ended, slot dropped at mark. No leg of this fix writes a position for a listened episode (the server route itself stores nothing for one, index.ts:5767 area; the core refuses, client.ts:2556).
2. **Opening threshold:** < 5 s = not started (step 3).
3. **v649 boot restore untouched** beyond the current track's position: the queue record's shape, readers, and stand discipline do not change; this release only makes the per-episode stores — which the restore does not read — survive the same kill.
4. **Contract shape untouched:** no new bridge fields; an old shell parses the same bytes. The v617 transition seek, the no-ack watch, and the stale-neutral rule in/around `applyNativeState` keep their exact guards — step 5's saves ride beside them, never inside their conditions.
5. **Kinds with no position store stay positionless:** book prayers (kind `prayer`, v484 §2.6) and homilies (device-local, v551) — both save legs already exclude them; step 1's helper does not widen either leg.

### §2.8 Risks

- **Duplicate position writes in native mode.** The client's new periodic/event saves and the shell's standing pause/skip/end write-backs can both post for one episode. Both go through the same routes into last-writer-wins upserts with near-identical values (the mirror lags the player by at most one publish); the failure shape is a position a few seconds stale, never a wrong episode or a resurrected finished track (listened rows refuse writes server-side and in the core). Accepted, named — the alternative (suppressing the shell's writes) is a shell change this release does not take.
- **Mirror staleness at the periodic write.** The native 5 s write uses the mirror's extrapolated `playPos()`; a stale mirror (publisher gone) could write a position ahead of the truth. Guard carried in §2.5 step 2: the write runs only while the mirror is FRESH (the standing freshness notion — last publish within two 5 s cycles, the stale-neutral bound's own measure); a stale mirror writes nothing.
- **Battery / traffic cost of 5 s writes.** One small POST per ~5 s of actual progress while playing (movement gate stands), the same order as the standing 5 s `saveResume`/snapshot writes the web path already makes. No write while paused, none while idle. Accepted for a streamlined release; if field data objects, the cadence is a one-constant change.
- **Day slot growth.** `opn-daypos-pending-v1` is bounded by the count of partway day episodes (coalesced, newest-wins, dropped on post success or on the ended-clear) — the podcast slot's standing bound, mirrored.
- **Threshold change is a behavior change.** Positions of 1–4 s saved by today's event saves will no longer resume. That is the task's named boundary ("a position in the opening seconds may stand as not started") made deterministic; flagged here so Review/John see it as a decision, not a side effect.
- **Page-dead / service-alive playback** (§2.6) remains uncovered by design. If John's field re-test kills only the page (app swiped while playback continues from the notification), the position still will not persist — the Plan's answer is the named shell follow-up, and the field leg's wording (kill the app, then reopen) is what distinguishes the two cases at re-test.

### §2.9 Amendment — the 95% read leg (John, 2026-11-25 21:50 CT; added at Implement, before the build)

**Rule:** when a playing track's live position crosses **95% of its duration**, it stands READ at that moment, and its saved in-progress position clears at the same moment — exactly as a completed track behaves at its natural end.

**Threshold-test seats (exact, per path — both paths carry it client-side; no path is left uncovered):**

- The test lives in the periodic position ticks this release rewires — `podPositionTick` and `dayPositionTick` (client.ts:11091 / 11180 at base) — evaluated on the native-aware live position from §2.5 step 1's helper (`livePos680`: element `currentTime` on the web path; `playPos()` over `nativeMirror`, track-matched and fresh, on the native path), against the track's duration (element duration / mirror duration, falling back to the descriptor's `durationS`).
- Web/element path: the ticks run on the `timeupdate` handler's standing 5 s cadence (§2.5 step 2), so the crossing is caught within one 5 s interval of it happening.
- Native path: `nativeMirrorTick`'s standing 5 s interval (§2.5 step 2) calls the same two ticks while the mirror reports the current track playing and fresh — the threshold test therefore stands on the native path too, through the client's own mirror channel; no shell change is needed for this leg either.
- Kinds: the podcast tick tests podcast tracks; the day tick tests day tracks (its standing exclusions stand — book prayers, kind `prayer`, hold no mark and no position, v484 §2.6; homilies mark through `markCompleted`'s own homily arm and hold no position store).

**Flip path (the universal flip, no new mark writer):** the crossing calls `markCompleted(desc)` — the standing sole completion writer (client.ts:5166), the same call the `ended` handler makes at its top. For a podcast that is `writePodMarkQuiet(seqKey, series, 'auto')` (client.ts:9438): the mark post, the in-memory payload flip, `podSyncQueueListened` (client.ts:9380 — every standing copy flips at once: queue, current, preview, `state.dayDescs`, settled daily copies), the core listen write, and `refreshPlayedChrome`. For a day track it is `writePlayed(...)` + `refreshPlayedChrome` through the same `markCompleted` body. The threshold changes only the TRIGGER (95% crossing instead of the end event); the mark machinery is byte-identical.

**Position-clear seats (same moment, all stores for that track):**

- Podcast: inside `writePodMarkQuiet` itself — `podPosSlotDrop` kills the pending-slot entry (client.ts:9449 area), the payload entry's `positionS` nulls beside the listened flip, the core listen write deletes the core position (`opnPodCoreSetListen`, client.ts:2544), and the server mark route deletes the position row. The descriptor copy's own `podPositionS` is nulled by the tick seat as it fires the mark.
- Day: the tick seat fires `writeDayPositionQuiet(episodeId, 0, 0)` beside the mark — the ended handler's own clear (client.ts:6593): the fold entry deletes in memory, the 0 post deletes the store row, and under §2.5 step 4 the day slot entry drops with the 0 write.
- Session guard: a crossed track's episodeId stands in a session set (`crossed95`); the position ticks and the event saves (pause · hide · pagehide · skip-away) stand down for it, so no later save in the same play resurrects the cleared position. `startDesc` clears the track's entry from the set when the track is started again.

**Boundary — crossed, then rewound and replayed:** the track behaves as a completed track does today. The read stands until marked unread through the standing unmark paths (unchanged); the position stands cleared, so a later play starts fresh at the top through the standing reads (listened → `podPositionS` null; day fold deleted). A rewind behind 95% after the crossing does NOT unmark and does NOT restore the cleared position.
