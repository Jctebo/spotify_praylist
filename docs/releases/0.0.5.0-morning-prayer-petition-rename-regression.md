# Release 0.0.5.0 - morning-prayer-petition-rename-regression

- Status: Shipped
- Shipped On: 2026-03-22
- Last Updated: 2026-03-22

## Scope

### Problem
- Morning Prayer now depends on owner-linked `Detailed Fragments`, but one fragment appears to have been renamed from `Petition - Church` to `Petition - Right Use of Technology`.
- The current runtime still validates Morning Prayer against a hard-coded exact-label contract, so a label-only rename may cause generation to fail even if the prayer text itself is valid.
- This matters now because Morning Prayer is a daily output and a single mismatched fragment can block page-audio generation for the row.

### Audience
- Primary user: the maintainer operating the Morning Prayer Notion workflow and depending on the generated page/audio output.
- Secondary stakeholders: anyone consuming the generated Morning Prayer page/audio and future maintainers touching the two-list fragment schema.

### Current Status Quo
- Morning Prayer assembly is driven from the two-list `Opus Dei` row plus linked `Detailed Fragments`.
- The codebase still treats Morning Prayer as a special case with a canonical ordered fragment contract rather than a looser user-editable fragment list.
- Fragment titles appear to function as part of the runtime contract, not just editor-facing labels.

### Goal
- Determine whether renaming `Petition - Church` introduced a real Morning Prayer regression.
- Identify the exact failure boundary: live generation, migration/preflight tooling, or both.
- Produce enough implementation context to safely decide whether the fix should be a Notion data correction, a code contract update, or both.

### Constraints
- This pass should not change production code or Notion data yet.
- The repo is mid-migration from older release-note conventions into the new `docs/releases/` artifact model.
- We can inspect code and tests locally, but we do not have the live Notion database contents in this repo.

### Narrow Wedge
- Research the Morning Prayer assembly path, its fragment validation contract, and the migration/preflight path.
- Confirm whether the renamed title conflicts with exact expected labels and document the likely break modes.
- Defer code changes until planning.

### Non-Goals
- Do not implement the fix in this step.
- Do not redesign the full Morning Prayer fragment model.
- Do not broaden this into a general fragment-authoring UX overhaul.
- Do not modify live Notion data from this workflow step.

### Risks And Unknowns
- The active Notion fragment row may still use the old title, so the bug may be theoretical rather than live.
- The row could fail only during migration/preflight, or also during the current runtime, depending on whether the renamed fragment is linked into the active detailed-fragment set.
- There may be more label-coupled Morning Prayer fragments beyond this one, which would make ad hoc renames fragile overall.

### Recommended Next Step
- Use `/research-astack` to trace the runtime contract, the migration contract, and the existing regression coverage so we can choose the smallest safe fix.

## Research

### Scope Baseline
- Investigate whether renaming the Morning Prayer fragment `Petition - Church` to `Petition - Right Use of Technology` can break Morning Prayer generation.
- Focus on the current two-list `Opus Dei` + `Detailed Fragments` runtime and any migration/preflight checks that still enforce older names.

  Why it matters: this is the migration/preflight path and still maps legacy Morning Prayer outputs into the canonical fragment contract.

### Current System Map
- The page-audio job loads all owner-linked detailed fragments from Notion with `load_detailed_fragments_from_notion(...)`, grouping them by owning page id and sorting by `(order, label)`.
- Each `Opus Dei` row is normalized through `opus_dei_two_list_settings(...)`, which decides whether the row is fragment-driven, special-builder-driven, or invalid.
- Morning Prayer is special-cased by row title in `build_opus_dei_two_list_plan(...)`.
- For Morning Prayer rows in fragment mode, the runtime calls `morning_prayer_contract_errors(...)` before assembly.
- `morning_prayer_contract_errors(...)` matches fragments by exact normalized label, kind, group, role, and relative order.
- The hard-coded Morning Prayer contract currently includes `Petition - Church` as a required text fragment.
- If validation fails, the runtime raises a blocking error telling the operator to re-run the Morning Prayer two-list migration before generating page audio.
- The migration script separately reconstructs Morning Prayer fragments from the legacy output contract and also expects the canonical label set, including `Petition - Church`.

### Reuse Opportunities
- The existing contract validator can be reused as the single place to reason about Morning Prayer completeness; we should avoid inventing a second set of rules.
- Existing tests already cover Morning Prayer assembly, nested heading parsing, cached stable fragments, and migration preflight error reporting.
- The repo already has a historical migration boundary for Morning Prayer, so a fix can likely stay narrowly focused on contract/label handling instead of rewriting the full builder.

### External References
- No external libraries or web docs were required for this research pass.
- Primary sources were local code and tests in this repository.

### Constraints
- Fact: the runtime uses exact contract labels for Morning Prayer validation, not just fragment keys or freeform content labels.
- Fact: owner-linked fragment specs are sorted by `order` and `label`, so changing only a title can affect both validation and tie-breaking behavior.
- Fact: the migration script still derives Morning Prayer from a canonical contract rather than treating titles as arbitrary editor copy.
- Inference: the system currently assumes certain Morning Prayer titles are stable identifiers, even though they are stored in human-facing title fields.

### Risks
- Highest risk: the active Morning Prayer run fails immediately because `Petition - Church` is now missing from the linked detailed fragments.
- Secondary risk: migration or repair tooling may re-create or insist on the old label, causing drift between live Notion edits and the canonical contract.
- Structural risk: using human-facing labels as contract identifiers makes future liturgical or editorial renames unexpectedly dangerous.

### Assumptions To Validate
- We still need to confirm the current live Notion Morning Prayer row actually contains the renamed fragment and no longer contains `Petition - Church`.
- We still need to confirm whether the renamed row preserved the same fragment order, kind, group, and owner linkage.
- We assume the rename was label-only and did not also change linked ownership or fragment kind.

### Unknowns
- Should `Petition - Right Use of Technology` replace `Petition - Church` in the canonical contract, or was the rename accidental?
- Is the desired long-term contract based on stable fragment keys while allowing editable display labels?
- Are there any other Morning Prayer fragment renames already present in Notion that would trigger the same exact-label failure pattern?

### Recommended Direction
- Treat this as a contract-mismatch investigation, not just a content typo.
- First confirm the live Notion fragment state.
- Then choose between:
- data-only fix: restore the canonical label if the rename was accidental;
- code-and-data fix: update the canonical Morning Prayer contract and tests if the new label is intentional;
- stronger model fix: decouple validation from human-facing labels by introducing a stable key for Morning Prayer contract matching.
- A planning pass is appropriate after live-data validation, because the fix choice depends on whether the rename reflects intentional product language or accidental drift.

## Plan

### Summary
- Replace Morning Prayer’s label-based fragment contract with a stable-key contract.
- Keep human-facing fragment titles editable in Notion while validating Morning Prayer completeness, ordering, and type safety against canonical keys.
- Choose this approach because it fixes the current rename fragility at the root instead of treating each title change as a one-off exception.

### What Already Exists
- `jobs/notion/generate_page_audio.py` already supports `Fragment Key` for legacy audio fragments and carries a `key` field through detailed-fragment parsing and child-plan assembly.
- `detailed_fragment_from_notion_page(...)` already emits both `key` and `label`, so the runtime has enough shape to stop treating labels as identifiers.
- `build_detailed_fragment_child_plan(...)` already uses `key` for cache identity and `label` for user-facing text, which is the split we want to preserve.
- `scripts/migrate_page_audio_notion_schema.py` already has a canonical Morning Prayer contract and a preflight path we can extend to seed or validate stable keys.
- `tests/test_page_audio_job.py` and `tests/test_migrate_page_audio_schema.py` already contain focused Morning Prayer regression coverage we can update instead of starting from scratch.

### Architecture
- Introduce a canonical Morning Prayer contract model with explicit stable keys plus display labels.
- Parse detailed fragments from Notion using `Fragment Key` first, then legacy fallbacks only for backward compatibility.
- Validate Morning Prayer against contract keys, kind, group, role, and order.
- Treat labels as editor-facing copy only.
- Keep assembly, TTS cache identity, and content rendering on the existing `key`/`label` split.
- Update migration/preflight tooling to assign canonical keys to Morning Prayer rows and to detect missing or duplicated contract keys.

```text
Notion Detailed Fragment row
  -> Fragment Key (stable id)
  -> Name / title (editable label)
  -> Kind / group / role / order

load_detailed_fragments_from_notion()
  -> detailed_fragment_from_notion_page()
  -> { key, label, kind, group, role, order, ... }

Morning Prayer validation
  old: match by label
  new: match by key

Assembly
  -> use key for identity/cache/order checks
  -> use label for spoken headings and visible toggles
```

### UX And States
- No app UI changes are planned in this fix.
- Operator-facing behavior changes:
  - Success: Morning Prayer continues to generate even when a contract fragment title is edited, as long as the stable key and other required metadata remain valid.
  - Error: when a required Morning Prayer fragment key is missing, duplicated, mis-typed, or out of order, the runtime should fail with a key-specific error instead of a title-specific error.
  - Migration/preflight: repair tooling should identify missing canonical keys and, where possible, populate them rather than forcing users to restore exact old labels.
- Accessibility and responsive concerns are not applicable because this work is backend/data-contract focused.

### Failure Modes
- A Morning Prayer fragment row keeps a renamed label but no canonical key.
  - Detection: key-specific validation error in runtime or migration preflight.
  - User experience: Morning Prayer generation fails with a missing-contract-fragment error that references the required key/contract item.
- Two rows share the same canonical key.
  - Detection: duplicate contract key validation error.
  - User experience: generation halts before producing ambiguous Morning Prayer output.
- Existing Notion data still relies on page-id fallback keys.
  - Detection: migration/preflight shows missing canonical keys or mismatch between expected contract key and parsed key.
  - User experience: existing rows may need one migration pass before the stronger model is fully stable.
- Ordering drift persists even after key migration.
  - Detection: order validation still fails after key match succeeds.
  - User experience: generation fails with a clear sort-order error instead of silently rearranging prayers.

### Rollout Notes
- This is a compatibility-sensitive contract change for live Notion data.
- Recommended rollout sequence:
  - land runtime support for stable keys plus backward-compatible fallback;
  - land migration/preflight support that can populate or verify canonical keys;
  - update Morning Prayer rows in Notion to carry explicit canonical keys;
  - after data is stable, consider tightening fallback behavior in a later cleanup pass.
- The first release should preserve label edits as non-breaking but still fail loudly on missing canonical keys for Morning Prayer contract rows.

### Not In Scope
- Generalizing stable-key contract validation to every prayer/output type.
- Full Notion schema migration for all fragment-backed outputs.
- Admin UI or dashboards for fragment-key repair.
- Reworking Morning Prayer content, order, or spoken text.

### Open Questions
- Should canonical Morning Prayer keys be human-readable slugs like `petition-church`, or prefixed names like `morning-prayer-petition-church` to avoid future cross-collection collisions?
- Should runtime fallback from missing key to label matching be temporary compatibility behavior only, or part of the long-term model?
- Do we want a one-time helper script or documented manual step for backfilling canonical `Fragment Key` values in live Notion?
