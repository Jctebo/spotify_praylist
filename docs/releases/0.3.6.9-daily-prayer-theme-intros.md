Date: 2026-06-15

## Scope

### Problem
- Daily Ora Pro Nobis prayers do not share one clear daily spiritual theme across the listener's day.
- Morning Prayer currently has a daily intro, but it does not reliably explain the day's theme in plain terms or why that theme was chosen from the day, Gospel reading, and liturgical season.
- Existing theme handling is too hierarchical: a feast, Gospel theme, or season can effectively displace the others instead of being woven into one inclusive daily theme.
- Some prayer intros lightly bridge into the prayer, but the wording can be awkward or theologically unclear, such as placing "11th Sunday in Ordinary Time" itself under Mary's protection.
- Novena episodes currently have no mention of the shared daily theme, so the listener does not hear how the novena fits into the day.
- Why now: the project now publishes multiple generated daily prayer surfaces, and listeners moving from Morning Prayer to Rosary, novenas, and Daily Reflection need one coherent daily focus instead of separate fragments.

### Audience
- Primary user: the maintainer shaping the Ora Pro Nobis daily prayer experience and judging whether the generated prayers sound coherent and Catholic.
- Secondary stakeholders:
  - Daily listeners who pray more than one episode and expect the day to feel spiritually unified.
  - Future maintainers adding prayer contracts, novena families, or reflection formats.
  - Spotify, RSS, and website consumers that rely on stable generated titles, sidecars, and readable prayer text.

### Current Status Quo
- `jobs/publish/daily_liturgical_context.py` already returns a normalized daily context with season, feast, Gospel-derived theme, primary theme, secondary themes, reflection focus, tone, imagery, music mood, and summary.
- The current daily context still selects a `primaryTheme` using precedence: major feast first, then Gospel, then memorial, then season, then fallback.
- `config/publish/contracts/morning-prayer.json` starts with a `daily_intro` block that can use Romcal and Gospel data, but it is not explicitly required to explain a unified theme and why it was chosen.
- `config/publish/contracts/auxilium-christianorum.json` already has a deterministic `prayer_intro` after the liturgical announcement, but the template can produce awkward wording when the day theme is an observance label rather than a spiritual focus.
- `config/publish/contracts/rosary.json` has Rosary-specific focus and intro logic, and the Rosary title uses a short focus label, but this can drift from Daily Reflection and Morning Prayer.
- `config/publish/contracts/daily-reflection.json` uses the shared daily liturgical context for the reflection, but the theme is not guaranteed to match the Rosary or Morning Prayer wording.
- `jobs/novena_contracts/*` renders active novena episodes through a separate pipeline with saint/feast/day focus context, and its intro currently welcomes the listener to the novena day without referencing the shared daily theme.
- Existing tests cover many individual paths, but there is no contract-level guarantee that every generated daily prayer surface names, explains, or lightly reinforces the same inclusive daily theme.

### Goal
- Build one inclusive daily theme model that incorporates:
  - The calendar day or celebration.
  - The daily Gospel reading when available.
  - The liturgical season.
  - The relevant saint, memorial, or feast when present.
- The theme must be presented as a synthesized spiritual focus, not as a precedence winner that ignores the other inputs.
- Morning Prayer should clearly explain the theme and why it fits today, using day, Gospel, and season language in a concise opening orientation.
- Daily Rosary and Daily Reflection should deeply incorporate the shared theme:
  - Rosary intro and decade reflections should use the same theme foundation.
  - Daily Reflection should use the same theme foundation for its title, reflection, examen, and closing.
- All other generated daily prayers should lightly reinforce the theme by naming it and transitioning naturally into the prayer:
  - Auxilium Christianorum.
  - Marian Antiphon Angelus.
  - Marian Antiphon Regina Caeli.
  - Daily novenas.
- Replace awkward object-focused transitions with spiritually coherent wording. The prayer should not place a calendar label under Mary's protection; it should place the listener, the day, the Church, or the intention shaped by the day's theme under Mary's protection.
- Preserve official prayer text bodies and source boundaries; generated theme language belongs in intros, transitions, reflections, and metadata, not inside fixed devotional texts.

### Constraints
- Scope-only release artifact for this turn; no implementation yet.
- Follow the repo's mandatory astack sequence: `/scope-astack`, then `/plan-astack`, then `/implement-astack`, then `/review-astack`, then `/ship-astack`.
- Use existing local liturgical and Gospel helpers where possible; do not add a new external readings or calendar dependency unless research proves the existing sources cannot support the theme model.
- Generated text must remain Catholic, reverent, spoken-audio friendly, and concise.
- Theme wording must be deterministic or tightly validated with deterministic fallback so daily audio publishing does not fail unpredictably.
- Tests must avoid live OpenAI, Spotify, Notion, ElevenLabs, Romcal network, or USCCB network dependence by mocking or fixture-driving the relevant context.
- Keep Spotify lookup durable; avoid adding variable theme text to required Spotify match terms.
- Preserve existing episode IDs unless a planned metadata change explicitly requires a controlled migration.

### Narrow Wedge
- Define a shared "daily prayer theme" output in or near `jobs/publish/daily_liturgical_context.py` that synthesizes day, Gospel, and season into:
  - A short theme title for metadata.
  - A concise explanation of why this is today's theme.
  - A devotional transition clause for light reinforcement.
  - A richer reflection prompt/context for Rosary and Daily Reflection.
- Wire the shared theme into the first complete set of listener-facing generated surfaces:
  - Morning Prayer: clear theme explanation and transition into prayer.
  - Daily Rosary: intro and reflections use the shared theme.
  - Daily Reflection: title/body/examen use the shared theme.
  - Auxilium Christianorum and Marian Antiphons: one natural theme transition before the prayer.
  - Novenas: one short theme-aware intro before the novena body.
- Add focused regression tests proving every included prayer type renders the theme in the expected depth: explained in Morning Prayer, deeply used in Rosary/Reflection, lightly named in transition prayers and novenas.

### Non-Goals
- Do not rewrite the full prayer bodies for fixed prayers such as Auxilium Christianorum, Marian Antiphons, Rosary canonical prayers, or imported novena prayer text.
- Do not change the traditional Rosary weekday mystery schedule.
- Do not change Spotify playlist membership, Notion row names, feed ownership, or website grouping.
- Do not redesign the generated website UI for this release.
- Do not require live model generation for test success.
- Do not solve every possible homiletic nuance or produce a long daily homily in every prayer; the strongest theme treatment belongs in Morning Prayer, Rosary, and Daily Reflection.

### Risks And Unknowns
- The current helper's `primaryTheme` is precedence-based; research must decide whether to extend it compatibly or introduce a new additive theme object to avoid breaking existing consumers.
- Gospel text can be missing or unavailable; the theme must still be meaningful from calendar day and season without sounding like it ignored the Gospel.
- Some calendar days have long or multiple celebration names; theme titles and transitions need length limits and natural wording.
- Novena content has saint-specific day themes, so the shared daily theme must complement the novena's own day focus rather than replace it.
- The exact wording standard needs care: "theme" should sound natural in spoken prayer and should not become repetitive across six daily episodes.
- Existing generated audio cache keys will change where intro text changes; planning should account for expected cache invalidation.

### Recommended Next Step
- Run `/plan-astack` next to convert this scope into a concrete implementation plan.
- The plan should first research the exact render paths for publish contracts and novena contracts, then choose whether the shared theme should extend `DailyLiturgicalContext` or become a sibling helper consumed by publish and novena pipelines.

### Current System Map
- Publish contracts flow through `load_publish_contracts()` into `build_text_jobs()` and `build_audio_jobs()` in `jobs/publish/contracts.py`.
- Each publish job builds one `runtime_context` through `_entry_runtime_context()`.
  - Rosary entries add `rosary_day_context`, title placeholders such as `rosary_focus_title`, and related prompt labels.
  - Daily Reflection entries add `daily_liturgical_context`, `daily_reflection_primary_theme`, title-cased theme metadata, tone, saint, and pause settings.
  - Morning Prayer, Auxilium, and Marian Antiphons currently do not receive shared daily context in `runtime_context`.
- Metadata rendering uses `_render_entry_metadata()`, which merges `runtime_context` into the strict publish template context before rendering titles, descriptions, and episode IDs.
- Text jobs render full text through `_entry_text_body()` and per-block sections through `_build_text_sections()`.
- Audio jobs render ordered fragments through `expand_audio_fragments()`, then attach effective TTS config and generate resume markers.
- `daily_intro`, `liturgical_announcement`, `prayer_intro`, `rosary_intro`, and `ignatian_reflection` are normal leaf block kinds for text/audio ordering.
- `prayer_intro` currently resolves its own Romcal celebration-name string through `_prayer_intro_day_theme()` and formats `{day_theme}` directly into contract templates.
- Rosary has a separate `RosaryDayContext` with `focus_source`, `focus_title`, `focus_prompt_label`, `celebration_clause`, `season_label`, Gospel data, and feast names. Its focus selection is still hierarchical.
- Daily Reflection consumes `DailyLiturgicalContext`; its title uses `context.primaryTheme`, and the prompt/fallback use `shortSummary`, `reflectionFocus`, `gospelTheme`, and `feastDay`.
- Morning Prayer `daily_intro` currently generates two or three sentences from `fetch_daily_gospel_context()` and does not consume `DailyLiturgicalContext`.
- Novenas do not use `jobs/publish/contracts.py`; they render through `jobs/novena_contracts/engine.py`.
  - `runtime_context()` exposes saint, feast, day, `theme`, and `daily_focus`.
  - `_intro_fragment()` emits only `Welcome to Day N of the Novena to {saint}.`
  - Compact block templates include that intro as the first audio fragment; legacy section-based templates may instead use rendered sections as fragments.
  - `pipeline.py` reuses existing sidecars when present, so changing intro/context text must account for old sidecar cache behavior.

- Reuse Daily Reflection's existing `DailyLiturgicalContext` dependency; it is already close to the desired shared-theme source.
- Reuse novena `runtime_context()` and `_intro_fragment()` to add daily theme fields and intro text without changing individual novena contract files.
- Reuse sidecar `render_context`, `rosary_reflections`, `daily_reflection`, and novena sidecar payloads to make theme decisions auditable after publishing.

### Constraints
- Keep all tests deterministic by patching Romcal, Gospel, and model calls.
- Keep fixed prayer templates unchanged; theme wording should live in generated intro/transition/reflection fragments and metadata.
- Do not add theme text to Spotify required title terms; current lookup contracts intentionally match durable terms plus date.
- Avoid changing episode IDs unless planning intentionally accepts downstream migration.
- Preserve `daily_intro` and `prayer_intro` validation guarantees: concise output, stable sentence count, no unbounded model prose.
- Avoid repeated network/context calls inside one job; build once per entry/date where possible and pass through runtime context.
- Novena sidecar reuse can hide changed intro text if an existing sidecar is accepted as fresh; planning must decide whether theme versioning or content hash inputs need to invalidate old sidecars.
- Generated theme wording must handle missing Gospel, missing Romcal, multiple celebrations, long celebration names, and ordinary weekdays.

### Risks
- The existing `DailyLiturgicalContext.primaryTheme` intentionally uses precedence, while the new product goal is inclusive synthesis. Reusing `primaryTheme` directly would preserve the current flaw.
- `prayer_intro` currently inserts raw celebration names into devotional wording; that is the exact source of awkward lines like placing a Sunday label under Mary's protection.
- Rosary and Daily Reflection can drift if Rosary keeps `RosaryDayContext` as a separate focus selector while Daily Reflection uses `DailyLiturgicalContext`.
- Morning Prayer is OpenAI-generated and currently validates structural sentence starts, not specific theme-explanation content; weak validation could allow the theme to disappear again.
- Novena compact blocks and section-based templates do not share identical fragment behavior, so adding a theme intro must cover both without duplicating or dropping text.
- Sidecar/content hash behavior is important: changed intro fragments should invalidate audio, but old novena sidecars may be loaded before new text is rendered.
- Adding fields to `DailyLiturgicalContext` may require updating reconstruction logic in `_get_or_build_ignatian_reflection_episode()` and existing tests that instantiate the dataclass directly.

### Assumptions To Validate
- It is acceptable for the published theme to use a short title plus a fuller explanatory sentence, rather than trying to put all day/Gospel/season detail into the title.
- The shared theme should be additive: keep existing `primaryTheme` for compatibility, but add explicit shared-theme fields for the new inclusive behavior.
- Morning Prayer should have the strongest up-front explanation, likely replacing or extending the existing `daily_intro` output rather than adding a separate long reflection block.
- Rosary titles should remain short and may continue using a concise focus title, while Rosary intro/reflections use the fuller shared theme.
- Novena shared-theme intro should complement the novena's saint/day focus and not override the novena's own `theme` / `daily_focus`.
- Existing sidecars in production may need a one-time rebuild or a theme-version hash input to prevent stale novena intros.

### Unknowns
- Exact listener-facing wording standard for "theme" versus more natural phrases like "today's focus" or "the grace we are asking for today."
- Whether every publish-contract prayer should expose the shared theme in `render_context` for website display now, or keep website surfacing out of scope.
- Whether `daily_intro` should be generalized into a `theme_intro` block kind or remain a specialized Morning Prayer intro builder.
- Whether old novena sidecars should be forcibly refreshed for this release or only naturally replaced when content hashes change.
- Whether long multi-celebration days need strict truncation rules for theme title, transition clause, or episode metadata.

### Recommended Direction
- Add a compatibility-preserving shared theme payload in `jobs/publish/daily_liturgical_context.py` rather than replacing `primaryTheme`.
- Build the shared theme once per publish entry/date in `_entry_runtime_context()` and expose stable keys such as theme title, explanation, transition clause, source parts, and reflection prompt text.
- Update Morning Prayer's `daily_intro` path to use the shared theme and validate that it explains the day/Gospel/season basis.
- Update `prayer_intro` to use the shared theme transition clause, with contract templates phrased around the listener/day/intention rather than raw calendar labels.
- Update Rosary context construction so Rosary intro/reflections consume the shared theme while retaining mystery-set selection and short title labels.
- Update Daily Reflection to title and prompt from the shared theme payload while preserving existing four-paragraph validation and fallback behavior.
- Add novena theme fields in `jobs/novena_contracts/engine.py` and a theme-aware intro fragment; account for sidecar reuse in `pipeline.py`.
- Plan tests at three levels: shared-theme unit tests, publish-contract integration tests across all daily prayer types, and novena engine/pipeline/sidecar tests.

## Plan

### Summary
- Build an additive shared daily prayer theme payload that explains the day's focus from calendar, Gospel, season, and saint/feast data without replacing the existing `primaryTheme` contract.
- Route that payload through publish-contract runtime context and the novena renderer so every generated prayer surface can use the same theme at the right depth.
- This plan is chosen because it fixes the drift and awkward wording while preserving episode IDs, fixed prayer bodies, Spotify lookup contracts, and existing helper APIs.

  - `sharedThemeSlug`

  - `sharedThemeTransition`
  - `sharedThemeReflectionFocus`
  - `sharedThemeSources`
  - `sharedThemeVersion`

  - Calendar celebration/day.

  - Liturgical season.

  - `daily_theme_transition`
  - `daily_theme_reflection_focus`
  - `daily_theme_sources`
  - `daily_theme_version`

### UX And States
- No visual UI changes are in scope.
- Listener journey:
  - Morning Prayer opens with a concise explanation of today's shared focus and why it fits the day, Gospel, and season.
  - Rosary intro and decade reflections develop the same focus more deeply.
  - Daily Reflection uses the same focus for title, reflection, examen, and closing.
  - Auxilium and Marian Antiphons name the focus and transition naturally into the fixed prayer.
  - Novenas keep their saint/day focus, preceded by one sentence connecting the novena to today's shared focus.
- Empty/fallback state:
  - If Gospel is missing, explain the theme from calendar and season without claiming Gospel grounding.
  - If Romcal is missing but Gospel exists, explain from Gospel and a generic liturgical-day phrase.
  - If both are missing, use a conservative fallback theme such as trust in ordinary life.
- Error state:
  - Invalid model output falls back to deterministic text.
  - Missing fixed prayer templates still fail closed as today.
