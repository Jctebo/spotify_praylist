- Slug: saint-centered-prayer-pipeline
- Status: Implementation complete; review and shipping in progress

## Scope

### Problem

- Daily prayer copy needs one durable theme rooted in the target day's liturgical calendar and connected to nearby saints and observances.
- Independent generation risks repetition, contradictory emphases, and unrelated themes across Morning Prayer, Auxilium Christianorum, the Rosary, and Daily Reflection.
- A single-day lookup is too narrow for the desired devotional continuity; the target date needs an inclusive `D-3..D+9` context window.

### Audience

- Primary user: a Catholic praying through a daily devotional routine and seeking liturgically grounded, saint-aware prayer.
- Secondary stakeholders: the product owner and content reviewers responsible for doctrinal fidelity, liturgical accuracy, tone, and spoken length.

### Current Status Quo

- The repository already builds a shared daily liturgical context from Romcal and Gospel data, then reuses a cached daily theme across current publish contracts.
- Existing Rosary, Daily Reflection, Morning Prayer, and Auxilium generation paths remain format-specific and do not yet consume a single multi-day saint-centered theme brief.

### Goal

- Select one coherent daily theme from the target date plus the inclusive `D-3..D+9` calendar window.
- Keep the target-day anchor primary while ranking surrounding observances by liturgical precedence and using them for continuity.
- Keep the existing daily podcast set and change only how its content uses the shared theme brief.
- Return human-readable copy plus structured metadata explaining the anchor, supporting observances, themes, rationale, confidence, exclusions, and validation results.

### Constraints

- Calendar jurisdiction and timezone must be explicit and configurable; the default must be chosen before implementation.
- Use actual calendar precedence and supersession rules; never invent saints, feasts, dates, ranks, readings, quotations, or biographical connections.
- Spoken-duration targets require a documented word-rate validation rule and reviewer-visible exceptions.
- Preserve each devotion's identity, especially the Marian/intercessory character of Auxilium Christianorum and the assigned Rosary mysteries.
- This release covers structured theme selection and copy generation only; it does not replace the calendar provider or change audio, TTS, publishing, or delivery systems.

### Narrow Wedge

- Add one deterministic theme-brief stage over the 13-day window, followed by five format-specific generation stages that receive the same approved brief.
- Normalize date, season, Sunday/weekday context, observances, saints, rank, source, and readings before selection.
- Select the target-day anchor, up to three supporting observances, three to five shared themes or virtues, confidence, rationale, and excluded/low-priority items.
- Validate required fields, calendar facts, rank consistency, mystery alignment, unsupported claims, repetition, and spoken-length targets.

### Non-Goals

- Replacing or choosing a universal/national/diocesan calendar for the user.
- Rewriting fixed liturgical, Rosary, or Auxilium prayer text.
- Building a saint encyclopedia, theological research system, spiritual director, or personalized intention source.
- Solving audio recording, TTS, publishing, scheduling, or delivery.

### Risks And Unknowns

- The authoritative calendar source and default jurisdiction are not yet fixed.
- Sunday, solemnity, feast, memorial, optional memorial, local proper, and supersession precedence must be made explicit and tested.
- Ordinary weekdays may lack a strong saint anchor; the fallback must allow season and readings to carry the theme without forcing a saint connection.
- Calendar conflicts, missing data, timezone boundaries, duplicate observances, and source rights need explicit handling.

### Recommended Next Step

- Map the existing calendar, shared-theme, prompt, contract, and validation boundaries; identify the smallest extension point for a reviewed theme brief.
- Confirm the default calendar jurisdiction, timezone/cache behavior, and spoken-duration policy before implementation planning.

## Research

### Scope Baseline

- Replace the current Gospel-derived/shared daily theme with one deterministic, reviewable saint-centered theme brief for target date `D` using the inclusive `D-3..D+9` calendar window.
- Use that one brief across the existing publish experiences; remove the old competing theme-selection fields and logic rather than maintaining parallel theme systems.

### Relevant Files

- `jobs/publish/daily_liturgical_context.py` — current single-day Romcal/Gospel normalization, feast-rank selection, season fallback, and shared-theme payload.
- `jobs/publish/daily_theme_runtime.py` — canonical daily-theme field extraction and in-process cache keyed by date, calendar, and locale.
- `jobs/publish/contracts.py` — publish-contract orchestration and injection point for shared daily theme fields.
- `jobs/publish/rosary_reflections.py` — Rosary mystery parsing, priority ordering, structured generation, semantic validation, and deterministic fallback.
- `jobs/publish/ignatian_reflection.py` — existing Daily Reflection structure, fallback text, segment/pause contract, and word-count bounds.
- `jobs/publish/daily_intro.py` and `jobs/publish/devotional_intro.py` — existing OpenAI settings, shared-theme prompt fields, retry/fallback conventions, and intro validation.
- `config/publish/contracts/{morning-prayer,auxilium-christianorum,rosary,daily-reflection}.json` — current contract shapes and generated-block entry points.
- `tests/test_publish_daily_liturgical_context.py`, `tests/test_publish_rosary_reflections.py`, `tests/test_publish_ignatian_reflection.py`, and `tests/test_publish_contracts.py` — existing precedence, fallback, shared-theme, and output validation coverage.
- `jobs/novena/liturgical_helpers.py` and `jobs/novena/sync_liturgical_calendar.py` — shared Romcal adapter/rank normalization and calendar synchronization boundaries.

### Current System Map

- Current flow: contract/runtime date → `DailyThemeRuntimeCache` → `build_daily_liturgical_context(date)` → shared theme fields → format-specific builders → audio/publish sidecars.
- `build_daily_liturgical_context` calls `romcal_fetch_day` once for the target date and separately fetches Gospel context. It selects a primary feast only from the target-day rows, with major feast rank before Gospel, then memorial, then season/fallback.
- `daily_theme_runtime.py` already provides the correct reuse boundary: one cached payload per `(date, calendar, locale)` and copied fields for downstream builders.
- Rosary currently has its own target-day context and priority hierarchy. It already accepts an optional shared theme, but intentionally keeps its Rosary-specific dominant priority authoritative.
- Daily Reflection already has a structured fallback and four-segment pause contract; it can likely receive the shared brief as context while retaining its devotional format.
- Auxilium and Morning Prayer are contract-driven generated intro/bridge paths; fixed devotional bodies are already stored in `config/publish/templates/`.

### Reuse Opportunities

- Extend the existing calendar adapter/rank normalization rather than adding a second Romcal client.
- Make the multi-day result the payload behind `DailyThemeRuntimeCache`, preserving the existing field names for consumers while adding brief-specific metadata.
- Reuse `DailyLiturgicalContext` serialization and sidecar metadata patterns for target date, calendar, locale, source, fallback reason, and theme sources.
- Reuse Rosary's structured-response validation approach and deterministic fallback strategy for the new brief and five-output package.
- Reuse existing OpenAI Responses/structured-output configuration from `daily_intro.py`, `devotional_intro.py`, and `rosary_reflections.py`.
- Preserve existing templates and contract files; add only generated brief/metadata needed to replace the old theme selection.

### External References

- No new external dependency is required by the repository evidence.
- The calendar provider and default jurisdiction remain unresolved; research must confirm the authoritative source and its published precedence/supersession semantics before planning.
- Existing `README.md` documents `ROMCAL_CALENDAR`, `ROMCAL_LOCALE`, shared daily themes, and the current publish contract boundaries.

### Constraints

- The current cache key has no timezone dimension, so a timezone-aware target-date contract must be resolved before caching or generation near midnight.
- The existing calendar helper is day-oriented; a window fetch must define inclusive date arithmetic, per-day normalization, duplicate identity, and source/conflict preservation.
- Existing Rosary priority order differs by liturgical season and must not be silently replaced by the general brief ranking; the brief should be an approved input while Rosary validation remains format-specific.
- Existing output validators use character/word bounds and structured schemas; spoken-duration policy needs one shared, explicit word-rate rule.
- Missing Gospel/calendar data already falls back with a recorded reason. The new brief must retain this fail-soft behavior while surfacing unresolved calendar conflicts for review.

### Risks

- Highest risk: incorrectly applying precedence across Sunday, solemnity, feast, memorial, optional memorial, local proper, and Easter Octave cases could produce a plausible but liturgically wrong anchor.
- A future observance may improperly displace the target day if selection is reduced to a global window sort rather than target-day-first logic.
- Passing a large 13-day window into five prompts increases token size and creates more opportunities for unsupported saint or reading claims; the approved brief should be compact and fact-bounded.
- The old `sharedThemeVersion == daily-theme-v1` payload is being replaced; all active consumers must migrate to the new brief in this release.

### Assumptions To Validate

- Default calendar is likely `general_roman` with locale `en`, matching current defaults, but the product owner must confirm whether a national or diocesan calendar is required.
- The target date is already represented as a local calendar date by current callers; timezone should be added to the input/config contract rather than inferred from the process machine.
- The calendar source can provide enough rank/season/observance metadata for deterministic supersession; otherwise conflicts must become a review state rather than an LLM decision.

### Unknowns

- Exact calendar provider API/version and jurisdiction configuration surface.
- Formal precedence table for Sundays and local/national celebrations, including multiple same-day proper observances.
- Whether readings are represented as full text, citations, or approved themes in the new brief.
- Whether human review can edit and approve the brief without regenerating calendar context, and where that state is persisted.

### Recommended Direction

- Plan a small calendar-window/theme-brief module behind `DailyThemeRuntimeCache`, using Romcal facts and Gospel context only as supplied evidence, never as a competing theme authority.
- Keep each format builder responsible for its own schema, but pass the single brief into all existing builders and use one deterministic fallback package whenever LLM generation or validation fails.
- Before `/plan-astack`, resolve the calendar jurisdiction, precedence table, and timezone/cache contract; then define fixtures for solemnity, feast, memorial, optional memorial, Sunday, ordinary weekday, conflict, missing data, and midnight-boundary cases.

## Plan

### Summary

- Replace the current Gospel-first/shared daily theme system with one deterministic saint-centered brief over the inclusive D-3..D+9 calendar window.
- Feed only that brief to the existing Morning Prayer, Auxilium Christianorum, Rosary, Daily Reflection, and Marian Antiphon contracts.
- If the LLM is unavailable or invalid, use one deterministic fallback brief and deterministic format fallbacks; do not revive the old competing theme logic.

### What Already Exists

- `jobs/publish/daily_liturgical_context.py` owns current Romcal/Gospel normalization.
- `jobs/publish/daily_theme_runtime.py` owns shared-theme caching and must become the replacement brief runtime.
- `jobs/publish/contracts.py` assembles contract blocks, audio fragments, and sidecar metadata.
- `jobs/publish/rosary_reflections.py` and `jobs/publish/ignatian_reflection.py` already provide structured validation and deterministic fallbacks.

### Architecture

```text
date + timezone + calendar -> D-3..D+9 facts -> deterministic brief
                                      |
             +------------------------+------------------------+
             |                         |                        |
       format prompts             deterministic fallback     validation
             |                         |                        |
             +-------------------------+-----------------------+
                                      v
                         five outputs -> audio -> sidecars
```

- Add `jobs/publish/saint_centered_theme.py` for date iteration, rank normalization, target-first precedence, supporting-item selection, shared virtues, rationale, confidence, exclusions, and JSON-safe brief serialization.
- Replace the current `DailyThemeRuntimeCache` builder so its payload is the new brief. Remove the old Gospel-first `primaryTheme`/`sharedTheme*` selection path from active consumers instead of maintaining compatibility theme branches.
- Use `general_roman`, `en`, and `America/Chicago` as defaults. Include timezone in cache identity and target-date resolution.
- Rank target-day Sunday/solemnity/feast/proper observances before memorial/optional memorial; surrounding dates support continuity only. Treat Easter Octave pseudo-ranks as seasonal unless a proper higher celebration exists.

### Concrete Changes

- Add `jobs/publish/saint_centered_theme.py` and replace the theme assembly in `jobs/publish/daily_theme_runtime.py`.
- Update `jobs/publish/daily_liturgical_context.py` only for reusable calendar/Gospel facts; remove its old theme-selection output from active runtime use.
- Update `jobs/publish/contracts.py` so all existing generated blocks receive the single brief and sidecars expose brief metadata.
- Remove or dead-code-gate old daily-theme selectors and update current prompt builders to reference the brief fields only.
- Add tests for all calendar ranks, Sunday, ordinary weekday, Easter Octave, duplicates, conflicts, missing data, timezone boundaries, deterministic fallback, cross-output reuse, contract loading, and tomorrow-date job assembly.
- Update `README.md` and this release artifact with the final runtime contract and operations commands.

### UX And States

- Structured metadata shows anchor, supporting observances, themes, rationale, confidence, exclusions, sources, and fallback reason for review.
- Missing data produces one deterministic brief and visible review metadata; conflicting facts fail closed rather than allowing the model to choose.

### Failure Modes

- Calendar/provider failure: deterministic brief fallback with explicit source/fallback metadata.
- LLM failure or invalid output: one deterministic fallback brief and deterministic per-format copy; never use the removed theme path.
- Conflicting calendar facts: preserve facts and mark review-required; do not silently invent precedence.
- Audio failure: fail the verification gate unless a configured provider successfully materializes the expected file.

- Contracts/audio: all JSON loads, tomorrow resolves correctly, each enabled job produces non-empty MP3 plus matching sidecar/feed metadata.
- Commands: focused publish tests, `python -m unittest discover -s tests -p "test_*.py"`, then the real/local tomorrow pipeline with credentials.
