## Scope

### Problem
- The public site currently shows only a Coming soon page, while listeners need a useful daily view of the prayers available in the Spotify playlists.
- Devotional wallpaper images are generated and delivered to OneDrive, but are not visible on the public site.

### Audience
- Primary user: listeners who want to see and open the day's devotional prayers.
- Secondary stakeholders: maintainer publishing wallpaper, audio, and Spotify content.

### Current Status Quo
- GitHub Pages stages a static Coming soon page, podcast RSS, and podcast cover art.
- Four Spotify playlists define ordered Morning, Midday, Night, and Sunday prayer membership.
- The wallpaper workflow writes generated phone/watch images to OneDrive; the Pages job does not read those images.

### Goal
- Replace the Coming soon landing page with a responsive daily prayer home.
- Show the current devotional wallpaper prominently, with a graceful branded fallback when today's image is unavailable.
- List all active playlist prayers grouped by Morning, Midday, Night, and Sunday, preserving contract order.
- Link each prayer to a useful Spotify destination and each group to its Spotify playlist.
- Preserve podcast RSS and cover art URLs and keep Notion out of the runtime.

### Constraints
- Reuse checked-in Spotify playlist definitions and queue contracts as the content source.
- Publish a copy of the current phone wallpaper from the existing OneDrive remote; keep OneDrive as the wallpaper source of truth.
- Do not restore the retired prayer directory, ICS publisher, infographic publisher, or any Notion integration.
- Support desktop and mobile with accessible layout, navigation, and links.

### Narrow Wedge
- Build one static responsive Pages homepage with current wallpaper, four ordered prayer sections, Spotify playlist/prayer links, and podcast feed access.

### Non-Goals
- New user accounts, prayer tracking, a new content database, or editing the Spotify playlists from the site.
- Publishing wallpaper queue/future images, watch images, or private workflow artifacts.
- Changing Spotify refresh behavior, audio publishing, RSS contents, or OneDrive rotation.

### Risks And Unknowns
- The user-mentioned visual reference attachment is not visible in this chat/workspace; layout should use the described devotional-wallpaper direction until it is reattached.
- Publishing the phone wallpaper makes that generated image publicly accessible on Pages; only the current devotional wallpaper will be copied.
- The publish job must handle a missing daily image without breaking podcast publishing or leaving stale images presented as today's wallpaper.

### Recommended Next Step
- Validate the current image staging contract and Spotify link mapping, then implement the static home and test desktop/mobile structure, content ordering, image fallback, and preserved podcast paths.

## Research

- `.github/workflows/publish_audio.yml` currently stages `config/site/coming-soon.html`, `docs/podcast.xml`, and podcast cover art into a Pages artifact; the feed and cover paths can remain unchanged.
- `jobs/playlist/spotify_contracts.py` validates playlist definitions and queue contracts. The four definition files own playlist IDs and ordered contract keys; contracts provide display names plus fixed Spotify URIs, seasonal links, show IDs, or resolver metadata.
- `sync/devotional_onedrive.py` and wallpaper rotation use `phone-current/<subject>__YYYY-MM-DD.jpg`; current wallpaper state is private OneDrive content. The Pages job currently has remote-name/root variables but does not configure rclone.
- `tests/test_publish_site.py` currently asserts that only Coming soon and podcast assets are staged. `tests/test_spotify_contracts.py` already protects playlist order and membership.
- No current visual reference attachment is available in the workspace. The plan follows the written description and keeps the layout responsive and content-first.

## Plan

### Summary
- Replace the Coming soon page with a responsive static daily prayer homepage, generated from the existing Spotify queue contracts and optionally featuring the current phone wallpaper.
- Keep GitHub Pages as the existing deployment host and preserve podcast feed and cover art paths.

### What Already Exists
- `jobs/playlist/spotify_contracts.py` validates and loads all playlist definitions and referenced contracts.
- `.github/workflows/publish_audio.yml` publishes the podcast feed, cover art, and Pages artifact from the existing audio workflow.
- The wallpaper pipeline rotates dated phone images into the OneDrive `phone-current` folder.

### Architecture
- A Python artifact builder loads playlist definitions/contracts and emits static JSON for the site. The Pages workflow optionally retrieves today's exact phone wallpaper, then stages page assets, podcast feed, and cover art.
- The browser renders ordered prayer cards from generated JSON. Group links go to the defined Spotify playlist; prayer links use a fixed/seasonal Spotify URI, the matching show for episode lookups, or a Spotify search URL for resolver-backed contracts.

```text
Spotify playlist JSON + contracts ──> page data builder ──┐
OneDrive phone-current (today only) ──> optional image ────┼──> Pages artifact
Podcast RSS + cover art ──────────────────────────────────┘       │
                                                        responsive prayer home
```

### Concrete Changes
- Add `config/site/index.html`, `config/site/site.css`, and `config/site/site.js` for the responsive homepage, accessible group navigation, ordered cards, Spotify links, podcast link, wallpaper hero, and branded image fallback.
- Add `scripts/build_pages_artifact.py` to validate/load Spotify data and emit the static page dataset, copy site assets, preserve `podcast.xml` and `images/logo_ora_pro_nobis.png`, and include the optional wallpaper only when provided.
- Update `.github/workflows/publish_audio.yml` to install/configure rclone only for the optional wallpaper stage, copy only the Chicago-date-matched `phone-current` image, invoke the artifact builder, and leave audio/RSS publishing steps unchanged. Missing rclone secret, remote configuration, or today's image produces a successful image-omitted build.
- Update `tests/test_publish_site.py` to cover the artifact builder contract, ordering, links, missing-image behavior, and preserved podcast assets; update `README.md` to describe the new Pages experience.

### UX And States
- Desktop: title/date masthead, large wallpaper hero, compact navigation to Morning/Midday/Night/Sunday sections, readable prayer cards, and one Spotify playlist action per section.
- Mobile: stacked hero and sections, horizontally scrollable labelled section navigation, single-column cards, and touch-sized links.
- Missing or invalid daily image: show a branded gradient fallback and keep all prayer/feed content usable. Empty groups display a brief no-prayers message. If site JavaScript fails, retain the heading and podcast-feed link in the HTML.
- Use semantic headings/landmarks, meaningful wallpaper alt text, visible keyboard focus, sufficient contrast, and reduced-motion-safe styling.

- Symbols/interfaces: generated `prayers.json` with `date`, `groups[]` (`key`, `name`, `playlist_url`, `prayers[]`), and `wallpaper` metadata; each prayer has `key`, `name`, and `spotify_url`.

- Rollback: restore the previous Coming soon page staging command.

#### Phase 2: Integrate current wallpaper and preserve Pages publishing

- Change summary: optional rclone setup/copy with exact Chicago-date filename, then artifact build; fallback to no image on unavailable remote/image.
- Verification: focused publisher/site checks and review the full Pages artifact contents.

- Dependencies: Phase 1.

### Failure Modes
- Invalid playlist or contract JSON stops the build before Pages deployment, preventing incomplete or wrongly ordered prayer content.
- Missing credentials, rclone configuration, remote folder, or today's image omits the hero image and uses the fallback; audio and RSS jobs continue.
- Resolver-backed prayer URLs use Spotify search when no stable direct item ID exists; the group-level playlist link remains a reliable direct destination.
- The optional image is restricted to `phone-current` and today's Chicago-date filename; watch, queue, archive, and manifest files are never staged.

- Confirm each group link targets its Spotify playlist and each prayer gets a valid direct or search URL.
- Build with and without a today's wallpaper; verify fallback behavior and that no old wallpaper is used.
- Inspect the artifact allowlist: `index.html`, site CSS/JS, generated prayer JSON, optional daily phone image, `podcast.xml`, and the existing cover art only.
- Verify podcast feed and cover art remain at the same published URLs.
- Review desktop and narrow mobile layout, keyboard navigation/focus, and reduced-motion styling.

### Rollout Notes
- Pages remains deployed from `main` by `publish_audio.yml`; this does not alter Spotify refresh or audio generation.
- A current daily phone wallpaper becomes publicly accessible at the Pages image URL. No wallpaper queues, watch images, private manifests, or workflow artifacts are published.

### Not In Scope
- New Site hosting, prayer text pages, user accounts, analytics, playlist editing, feed changes, calendar publishing, or any Notion integration.
