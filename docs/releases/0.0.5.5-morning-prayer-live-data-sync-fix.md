# Release 0.0.5.5 - morning-prayer-live-data-sync-fix

- Status: Draft
- Last Updated: 2026-03-23

## Scope

### Problem
- The `Daily Novena Prayer` workflow now gets through novena generation, but `Generate Auto Page Audio` still fails on the Morning Prayer preflight.
- The failure message says Morning Prayer is missing `monthly-intention` and `daily-novena-audio`, even though live Notion inspection showed those rows exist.
- This points to a durable-key drift problem: the live Notion data and the code contract do not line up cleanly yet.

### Audience
- Primary user: the maintainer running the daily novena and page-audio workflows.
- Secondary stakeholders: anyone relying on Morning Prayer audio generation to complete automatically from GitHub Actions.

### Current Status Quo
- The workflow runs novena generation first, then page-audio generation.
- `jobs/notion/generate_page_audio.py` enforces a strict Morning Prayer detailed-fragment contract.
- The repo now uses stable fragment keys as the runtime identity, but the live Notion pages still carry a few legacy key/title combinations.
- The remote workflow is failing because the code is stricter than the live data shape, not because Morning Prayer is fundamentally missing.

### Goal
- Make the Morning Prayer preflight succeed against the live Notion data without weakening validation.
- Keep the contract strict enough to still fail if a real required fragment disappears.
- Preserve the daily workflow order so novena generation still feeds page-audio generation.

### Constraints
- We should change code to match the live data, not rewrite the Notion database.
- The fix should stay narrow to Morning Prayer and should not generalize into a permissive alias system for unrelated fragment types.
- The workflow must remain safe to run in GitHub Actions without manual intervention.

### Narrow Wedge
- Add a targeted legacy-key compatibility layer for Morning Prayer.
- Make the contract accept the durable keys already present in live Notion while still requiring the same actual fragment coverage.
- Prove the live Morning Prayer rows now satisfy the preflight and that truly missing rows still fail.

### Non-Goals
- Do not rebuild the Morning Prayer Notion database.
- Do not loosen the preflight into a best-effort mode.
- Do not redesign the page-audio architecture or touch unrelated workflows.

### Risks And Unknowns
- The live Notion data may contain more than one legacy drift pattern, so the compatibility layer has to be precise.
- If aliases are too broad, the preflight could hide a genuinely missing fragment.
- The remote workflow may still fail in a different step after Morning Prayer passes, so this fix only targets the current blocker.

### Recommended Next Step
- Use `/research-astack` to map the exact Morning Prayer live keys, the contract code path, and the smallest compatibility layer needed.

## Research

### Scope Baseline
- The job failure is now specifically in Morning Prayer page-audio preflight, after the novena and upload steps succeed.
- Live inspection previously showed the Morning Prayer page already has related fragments, so the remaining issue is likely contract normalization rather than missing content.
- The code should be updated to understand the live durable keys already stored in Notion.

### Relevant Files
- `jobs/notion/generate_page_audio.py`
  Why it matters: owns the Morning Prayer contract definition and the preflight that is aborting the workflow.
- `tests/test_page_audio_job.py`
  Why it matters: covers Morning Prayer contract failures and success cases; it should pin the live-data compatibility behavior.
- `README.md`
  Why it matters: documents the Morning Prayer durable-key contract and should match the code after the fix.
- `.github/workflows/daily_novena_prayer.yml`
  Why it matters: this is the remote workflow that currently fails.

### Current System Map
- `morning_prayer_contract_items()` defines the required Morning Prayer fragment set.
- `morning_prayer_contract_errors()` checks the live fragment specs against that contract.
- `build_opus_dei_two_list_plan()` raises when Morning Prayer is incomplete.
- The workflow runs `jobs/novena/generate_daily_novena_prayer.py` first, then `jobs/notion/generate_page_audio.py`.

### Reuse Opportunities
- Reuse the existing Morning Prayer contract and preflight instead of adding a separate validation path.
- Reuse the live fragment rows already in Notion instead of creating duplicates.
- Reuse the current regression tests and extend them for the alias/compatibility case.

### External References
- GitHub Actions logs provide the authoritative runtime failure details.
- Notion relation behavior matters because the preflight is driven by linked fragment pages.

### Constraints
- The fix should keep Morning Prayer strict and deterministic.
- Compatibility should be local to the Morning Prayer path, not a repo-wide relaxation.
- The code must still reject truly missing required fragments.

### Risks
- A compatibility layer can accidentally hide a real gap if the alias map is too broad.
- The live Notion schema may differ in subtle ways from the previously inspected pages.
- The failure could move to a different step once Morning Prayer passes, so verification needs to watch the full workflow.

### Assumptions To Validate
- The missing fragments in the error message are a contract mismatch, not an actual absence of data.
- The live Morning Prayer rows still have the same durable keys observed earlier.
- A code-side compatibility mapping is safer than mutating the live database.

### Unknowns
- Whether the safest fix is to normalize legacy keys before validation, or to broaden the lookup of detailed fragments just enough to accept the live pages.
- Whether any other Morning Prayer aliases need to be recognized beyond the two rows already surfaced in logs.

### Recommended Direction
- Use `/plan-astack` after research confirms the exact alias map and the smallest code change that makes the live data pass.

## Plan

### Summary
- Repair the Morning Prayer page-audio preflight so it matches the live durable keys already present in Notion.
- Keep the validation strict, but add a narrow compatibility layer for the legacy Morning Prayer keys that are already in production data.
- Prove the fix with tests first, then rerun the remote workflow to confirm `Generate Auto Page Audio` clears.

### What Already Exists
- `jobs/notion/generate_page_audio.py` already defines the Morning Prayer contract and the preflight that aborts when the contract is incomplete.
- `tests/test_page_audio_job.py` already contains Morning Prayer contract coverage, including a stable-key happy path and a missing-fragment failure path.
- `README.md` already documents the Morning Prayer durable-key model and the current legacy key names.
- The live Notion data already contains the Morning Prayer fragment rows, so the contract should adapt to the existing rows instead of rebuilding them.

### Architecture
- `morning_prayer_contract_items()` is the canonical source of required Morning Prayer fragments.
- `morning_prayer_contract_errors()` is the right boundary to normalize live legacy keys before the contract check runs.
- `build_opus_dei_two_list_plan()` should remain the enforcement point so the workflow still fails loudly on real missing fragments.
- The compatibility layer should only affect Morning Prayer, not the broader fragment/audio system.

### Concrete Changes
- `jobs/notion/generate_page_audio.py`
  - Add a small alias map for the live Morning Prayer durable keys that differ from the canonical contract labels.
  - Normalize the live fragment specs before the contract check so the existing Notion rows satisfy the contract without changing the Notion database.
  - Keep missing-fragment detection intact so truly absent rows still produce a hard failure.
- `tests/test_page_audio_job.py`
  - Add a regression test that feeds the live Morning Prayer key set through the preflight and expects success.
  - Keep the existing negative-path coverage so missing rows still fail with a helpful message.
- `README.md`
  - Document the legacy Morning Prayer durable keys and the canonical keys they normalize to.

### Phases
#### Phase 1: Implement targeted normalization
- Goal
  - Teach the Morning Prayer preflight to recognize the live durable keys already stored in Notion.
- Verification
  - Run `python -m unittest tests.test_page_audio_job`.

#### Phase 2: Lock in regression coverage
- Goal
  - Prove the live Morning Prayer key set passes and genuinely missing fragments still fail.
- Verification
  - Run `python -m unittest tests.test_page_audio_job`.
  - Run `python -m unittest`.

#### Phase 3: Dogfood in GitHub Actions
- Goal
  - Confirm the daily novena workflow reaches completion after the Morning Prayer contract accepts the live rows.
- Verification
  - Trigger the remote `Daily Novena Prayer` workflow and inspect the `Generate Auto Page Audio` step.

### Success Criteria
- The Morning Prayer preflight accepts the live durable keys already present in Notion.
- Missing required fragments still fail with clear, specific errors.
- The remote workflow completes the page-audio step instead of aborting at Morning Prayer.
- Tests cover both the live-data path and the missing-data path.

### Open Questions
- Whether the alias normalization should be implemented as a helper next to the contract constants or inline in the preflight function.
- Whether any additional legacy Morning Prayer keys appear once the workflow is exercised again.

### Recommended Next Step
- Implement the Morning Prayer compatibility mapping in `jobs/notion/generate_page_audio.py`, add the regression test, and rerun the remote workflow.
