# Release 0.0.5.5 - morning-prayer-live-data-sync-fix

- Status: Draft
- Last Updated: 2026-03-23

## Scope

### Problem
- The `Daily Novena Prayer` workflow now gets through novena generation, but `Generate Auto Page Audio` still fails on the Morning Prayer preflight.
- The failure message says Morning Prayer is missing `monthly-intention` and `daily-novena-audio`, even though live Notion inspection showed those rows exist.
- This points to a durable-key drift problem: the live Notion data and the code contract do not line up cleanly yet.

### Audience
- Primary user: the maintainer running the daily novena and page-audio workflows.
- Secondary stakeholders: anyone relying on Morning Prayer audio generation to complete automatically from GitHub Actions.

### Current Status Quo
- The workflow runs novena generation first, then page-audio generation.
- `jobs/notion/generate_page_audio.py` enforces a strict Morning Prayer detailed-fragment contract.
- The repo now uses stable fragment keys as the runtime identity, but the live Notion pages still carry a few legacy key/title combinations.
- The remote workflow is failing because the code is stricter than the live data shape, not because Morning Prayer is fundamentally missing.

### Goal
- Make the Morning Prayer preflight succeed against the live Notion data without weakening validation.
- Keep the contract strict enough to still fail if a real required fragment disappears.
- Preserve the daily workflow order so novena generation still feeds page-audio generation.

### Constraints
- We should change code to match the live data, not rewrite the Notion database.
- The fix should stay narrow to Morning Prayer and should not generalize into a permissive alias system for unrelated fragment types.
- The workflow must remain safe to run in GitHub Actions without manual intervention.

### Narrow Wedge
- Add a targeted legacy-key compatibility layer for Morning Prayer.
- Make the contract accept the durable keys already present in live Notion while still requiring the same actual fragment coverage.
- Prove the live Morning Prayer rows now satisfy the preflight and that truly missing rows still fail.

### Non-Goals
- Do not rebuild the Morning Prayer Notion database.
- Do not loosen the preflight into a best-effort mode.
- Do not redesign the page-audio architecture or touch unrelated workflows.

### Risks And Unknowns
- The live Notion data may contain more than one legacy drift pattern, so the compatibility layer has to be precise.
- If aliases are too broad, the preflight could hide a genuinely missing fragment.
- The remote workflow may still fail in a different step after Morning Prayer passes, so this fix only targets the current blocker.

### Recommended Next Step
- Use `/research-astack` to map the exact Morning Prayer live keys, the contract code path, and the smallest compatibility layer needed.

## Research

### Scope Baseline
- The job failure is now specifically in Morning Prayer page-audio preflight, after the novena and upload steps succeed.
- Live inspection previously showed the Morning Prayer page already has related fragments, so the remaining issue is likely contract normalization rather than missing content.
- The code should be updated to understand the live durable keys already stored in Notion.
- The latest remote run narrowed the blocker: the legacy petition keys are now being accepted, but GitHub Actions still reports `monthly-intention` and `daily-novena-audio` as missing.
- That means the remaining problem is probably a missing relation, a stale/different live Notion row, or a special-fragment ingestion path that is not matching the remote data shape the way we expected.
- The migration tests already prove that renamed petition labels can be accepted when the `Fragment Key` matches, but they do not currently model the special `Monthly Intention` / `Daily Novena Audio` rows as a preflight contract case.
- Live-state inspection confirms `Daily Novena Audio` is linked to the Morning Prayer page and parses with `owner_ids` pointing at the Morning Prayer row, but `Monthly Intention` is currently unlinked in the `Opus Dei Item` relation.
- The latest live pass found a duplicate-row pattern for both special fragments: one row has the canonical key/title but is unlinked, while the linked row is attached to Morning Prayer but is missing the canonical `Fragment Key`.
- The migration helper already treats Morning Prayer special fragments as owner-linked rows and knows how to relink ownerless candidates, which strongly suggests the live split rows are a migration artifact rather than a new contract shape.

- `jobs/notion/generate_page_audio.py`
  Why it matters: owns the Morning Prayer contract definition and the preflight that is aborting the workflow.
- `tests/test_page_audio_job.py`
  Why it matters: covers Morning Prayer contract failures and success cases; it should pin the live-data compatibility behavior.

### Current System Map
- `morning_prayer_contract_items()` defines the required Morning Prayer fragment set.
- `morning_prayer_contract_errors()` checks the live fragment specs against that contract.
- `build_opus_dei_two_list_plan()` raises when Morning Prayer is incomplete.
- The workflow runs `jobs/novena/generate_daily_novena_prayer.py` first, then `jobs/notion/generate_page_audio.py`.
- `monthly-intention` and `daily-novena-audio` are special fragment kinds in `jobs/notion/generate_page_audio.py`, so their presence depends on the live Notion row shape as well as the contract relation data.
- `audio_fragment_from_notion_page()` accepts those special fragment kinds, but only if the underlying Notion rows are present and parsed into the fragment map.
- `build_monthly_intention_fragment_from_notion_or_provider()` falls back to provider content if the Notion lookup fails, which means the page-audio path can still generate audio even if the special fragment row is missing from Notion.
- The preflight failure happens before that fallback can help, so the blocker is specifically the Morning Prayer relation/contract check, not the audio renderer itself.
- The live special-fragment state is asymmetric: `Daily Novena Audio` is linked and ingested, while `Monthly Intention` exists as a fragment row but is not linked on the Morning Prayer page.
- The live database also contains duplicate special-fragment records for both items, which suggests a migration split between the canonical key row and the owner-linked row that the preflight is reading.

### Reuse Opportunities

- Reuse the current regression tests and extend them for the alias/compatibility case.
- Reuse the existing special-fragment support for `monthly-intention` and `daily-novena-audio` if the problem turns out to be relation wiring or row shape rather than the contract itself.
- Reuse the provider fallback for monthly intention audio if the live Notion lookup only fails in the rendering path, but do not let that mask the contract preflight.
- Reuse the existing `Daily Novena Audio` relation shape as the template for how the Morning Prayer page should represent special fragments.
- Reuse the migration helper patterns already in `scripts/migrate_page_audio_notion_schema.py` to understand how the canonical and linked special-fragment rows are supposed to be paired.
- Reuse the migration helper's owner-linked vs ownerless matching rules to repair the live split rows instead of inventing new matching logic.

### External References

### Constraints
- The fix should keep Morning Prayer strict and deterministic.
- Compatibility should be local to the Morning Prayer path, not a repo-wide relaxation.
- The code must still reject truly missing required fragments.
- Any repair for `monthly-intention` and `daily-novena-audio` should preserve special-fragment handling instead of downgrading them to plain text rows.
- A data-only fix may be enough if the two special fragments are linked in Notion but not being matched by the current relation traversal.
- `Monthly Intention` likely needs a live Notion relink or migration fix, not just a code-side alias change.
- The linked special-fragment rows currently appear to be missing their canonical keys, so the repair may need to normalize the live rows rather than only changing the contract.
- The safest repair path should preserve the migration helper's preference for already owner-linked rows and only use ownerless rows when relinking.

### Risks
- A compatibility layer can accidentally hide a real gap if the alias map is too broad.
- The live Notion schema may differ in subtle ways from the previously inspected pages.
- The failure could move to a different step once Morning Prayer passes, so verification needs to watch the full workflow.
- The remote workflow may be reading a stale or duplicate Morning Prayer page in Notion, which would make local inspection misleading.
- If those two special fragments are present but unlinked, the alias fix alone will not resolve the remaining failure.
- If `monthly-intention` is falling back to provider content during rendering, the workflow might still appear healthy even when the Notion relation is incomplete, so the preflight must stay the source of truth.
- The live data now suggests `Monthly Intention` is the primary structural gap, while `Daily Novena Audio` is probably a downstream symptom of a stale/duplicate relation view or a different cache path in the remote job.
- The duplicate-row pattern means a future code fix could accidentally choose the wrong row unless it explicitly prefers the owner-linked special fragment over the orphaned canonical copy.
- If the migration helper is reused naively, it could relink the wrong duplicate special-fragment row instead of the intended owner-linked record.

### Assumptions To Validate
- The missing fragments in the error message are a contract mismatch, not an actual absence of data.
- The live Morning Prayer rows still have the same durable keys observed earlier.
- A code-side compatibility mapping is safer than mutating the live database.
- The `Monthly Intention` and `Daily Novena Audio` rows exist in the same live Notion source the GitHub Actions workflow reads.
- The failure is not caused by a stale or duplicate Morning Prayer row in Notion.
- The special fragments are not being filtered out because of a missing owner relation or an unexpected fragment kind value.
- The `Daily Novena Audio` remote miss is not caused by the fragment row itself, since the live page currently parses with the correct owner relation.
- The owner-linked special-fragment row is the one the remote workflow should prefer, even if a duplicate canonical row exists without a relation.
- The migration helper's owner-linked preference is the correct rule to apply to the live data split we found.

### Unknowns

- Whether any other Morning Prayer aliases need to be recognized beyond the two rows already surfaced in logs.
- Whether the two special fragments are missing from the relation, missing from the database, or being filtered out upstream before the contract check sees them.
- Whether the remote run and local live-data inspection are definitely looking at the same Notion record.
- Whether the special fragments are attached but rendered via a provider fallback in a way that hides the underlying live-data mismatch.
- Whether `Monthly Intention` needs to be linked back to the Morning Prayer page in Notion, or whether the remote workflow is reading an older stale row that still lacks the relation.
- Why `Daily Novena Audio` was reported missing in GitHub Actions even though the live row currently shows the owner relation and parses successfully.
- Which of the duplicate special-fragment rows should be treated as authoritative when a migration helper or lookup path encounters both.
- Whether the migration helper's relink logic is already sufficient to repair the live rows once we run it on the current database state.

- If the migration helper already has the right owner-linked preference, the next plan should reuse that logic to repair the live Morning Prayer special fragments.

## Plan

### Summary
- Repair the Morning Prayer live data by normalizing the split special-fragment rows so the owner-linked records carry the canonical durable keys the preflight expects.
- Keep the page-audio contract strict, but stop trying to solve this as a contract bug now that the live database shape is understood.
- Reuse the migration helper's owner-linked vs ownerless preference to turn the current split rows into a single authoritative Morning Prayer special-fragment set.
- Prove the repair with tests first, then rerun the remote workflow to confirm `Generate Auto Page Audio` clears.

### What Already Exists
- `jobs/notion/generate_page_audio.py` already defines the Morning Prayer contract and the preflight that aborts when the contract is incomplete.
- `tests/test_page_audio_job.py` already contains Morning Prayer contract coverage, including a stable-key happy path and a missing-fragment failure path.
- `README.md` already documents the Morning Prayer durable-key model and the current legacy key names.
- `scripts/migrate_page_audio_notion_schema.py` already has the owner-linked relink logic we need for Morning Prayer special fragments.
- The live Notion data already contains the Morning Prayer fragment rows, so the fix should adapt the rows instead of rebuilding them.

### Architecture
- `morning_prayer_contract_items()` is the canonical source of required Morning Prayer fragments.
- `morning_prayer_contract_errors()` is the right boundary to normalize live legacy keys before the contract check runs.
- `build_opus_dei_two_list_plan()` should remain the enforcement point so the workflow still fails loudly on real missing fragments.
- The compatibility layer should only affect Morning Prayer, not the broader fragment/audio system.
- The remaining gap likely sits in the Notion relation data or the special-fragment ingestion path, not in the alias mapping itself.
- The special-fragment builder path already has a provider fallback, which means the runtime audio output can be more forgiving than the relation preflight.
- The live data now shows a split special-fragment pattern where one row is owner-linked and another row carries the stable key without the owner relation.
- The migration helper already models that split and prefers owner-linked rows first, which is the behavior we should reuse for repair.

### Concrete Changes
- `scripts/migrate_page_audio_notion_schema.py`
  - Reuse the existing Morning Prayer migration flow to relink ownerless or split special-fragment rows to the owner-linked records.
  - Keep the owner-linked preference and `reuse_ownerless=True` behavior intact so we do not choose the wrong duplicate.
- `jobs/notion/generate_page_audio.py`
  - Keep the strict contract check intact so future drift still fails loudly.
  - Do not broaden the contract further; the issue is now live data repair, not contract relaxation.
- `tests/test_page_audio_job.py`
  - Add or extend regression coverage for the repaired live-data shape so the preflight passes once the split rows are normalized.
  - Keep the existing negative-path coverage so missing rows still fail with a helpful message.
- `tests/test_migrate_page_audio_schema.py`
  - Extend the migration tests to cover the special-fragment split and owner-linked preference, not just the petition alias cases.
- `README.md`
  - Document that the live Morning Prayer special fragments may exist as split rows during migration and should be normalized through the migration helper.
