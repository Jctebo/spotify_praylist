# v617 — Block play disc honors position marks: an unfinished track resumes, never restarts

## §1 Scope

John's correction on the v616 block play disc (2026-11-22 09:54 CT, verbatim): "The play disc needs to honor the existing mark where the prayer is. It shouldn't automatically start a track over if it isn't finished"

Streamlined small release (Scope + Plan compressed into one pass). Run level: Implement on the branch; the coordinator reviews and ships. Base: a54db0e (the v616 shipped tree).

The correction, exactly: when a block's play disc starts its queue, EVERY track's start honors its stored position mark — a track that is not finished resumes at its mark, never at 0:00. A finished track (its played mark stands; its position row is gone by the standing discipline) starts at 0:00 as today. A track with no mark starts at 0:00. Queue composition, order, the grey rule, and the counts are UNCHANGED from v616/v615.

Grounded current state (verified in `app/worker/src/client.ts` on the base tree):

- THE SINGLE-PLAY DISCIPLINE (the rule this fix aligns to — no second rule is invented):
  - Day tracks: the position lives in the `day_positions` store, read back in the day payload's `dayPositions` fold (keyed by episodeId, seconds), kept current in-session by `writeDayPositionQuiet` (the payload fold tracks every save; a position of 0 deletes). `startDesc` hands the fold value to the standing `pendingResume` seam; the `loadedmetadata` handler seeks to it, clamped to one second short of the element's real end (the shared-seam guard — a seek onto the exact end would fire 'ended' and consume the track). Saves fire on the 15 s tick, pause, hide, pagehide, and skip-away — never at 0, never at/past the end. A natural end marks the track played AND clears its position in the same moment ("a finished prayer never resumes at its end"). There is NO near-end percentage threshold: "finished" is the played mark standing (position row deleted); a position a hair from the end resumes at duration−1 under the clamp, exactly as single play does today.
  - Podcasts: the position lives in the core store's listen record; the descriptor carries it as `podPositionS` (null when listened — a listened episode starts at 0 through the same path). `startDesc` hands it to the same `pendingResume` seam. The v614 contents-episode descriptors carry `podPositionS` folded from the core store at resolve time (`resolveProfileEpisodes614`).
  - Book prayers (kind 'prayer') hold NO day position (v484 §2.6) and homilies hold none (device-local, v551): both read 0 — the standing discipline.
  - Occurrence copies (v610): the POSITION store is keyed by episodeId — copies of one hour SHARE the one stored position (only the PLAYED mark is occurrence-keyed). A copy in a queue resumes at that shared position, exactly as a single tap on that copy does today.
- THE ELEMENT (web) QUEUE PATH ALREADY HONORS MARKS: a disc queue advances through `advanceQueue` → `startDesc(live)` per track, and `startDesc` applies the fold / `podPositionS` read above to every track, first and later alike. This release does not change that path's position behavior; the harness proves it stands (legs E1–E5, expected to pass on the old tree as regression guards).
- THE DEFECT — THE NATIVE ENGINE PATH (John's phone, the Android shell): a disc tap in native mode runs `startDesc` → `nativeSendContract`, whose contract (`nativeContractFor`) carries ONE position — `startPositionS: queueStartPos(desc)`, the START item's carry. The shell's contract item (`NativeQueueItem`, Android repo main 8e3204c) carries NO position field, and the engine advances through its window autonomously: every track after the start item begins at 0:00 whatever mark it holds. `applyNativeState` learns of each engine transition (the `changed` block) and updates the client's current — nothing seeks the new track to its mark. A half-finished prayer later in the block therefore starts over: John's report, exactly.
- THE CURRENTLY-PLAYING EDGE, grounded: with a queue standing and playback sounding, a disc tap is the standing pause toggle (`startQueue`'s no-force guard) — no restart, and this release does not change the toggle discipline. With NO queue standing, the disc's queue is built and its head is started through `startDesc`; when that head IS the standing current track, `startDesc` re-reads the FOLD for it — a value that can lag the live position (the tick's last save; in native mode the service's own write-backs never enter the client fold in-session) or read 0 — so the playing track can jump back or restart whole. The standing precedent for a re-start of the current track is `nativeResendAtCurrent`: it carries the LIVE position (`playPos()`), never a stale store value.

## §2 Plan

Client (`app/worker/src/client.ts`) only. No shell change, no server change, no dress change.

1. ONE READER — `queueMarkPos617(desc)`: the stored start position for a queue track, read from EXACTLY the sources `startDesc` reads:
   - podcast descriptor → `desc.podPositionS > 0 ? Math.floor(desc.podPositionS) : 0`;
   - kind 'podcast' handled first; kind 'prayer' (book) and kind 'homily' → 0 (no store stands for them);
   - any other (day) descriptor → the payload fold: `state.dayPayload.dayPositions[desc.episodeId] > 0 ? Math.floor(...) : 0`.
   A finished track reads 0 by the stores' own discipline (position row deleted at 'ended'; `podPositionS` null when listened) — the reader adds no threshold of its own.
2. THE NATIVE TRANSITION SEEK (the defect fix): in `applyNativeState`, inside the standing track-change block (`desc` resolved from `nativeContractDescs` and `changed` true — the client's current has just moved to the engine's new track), after the current/queueIdx update: read `var mark = queueMarkPos617(desc)`; when `mark > 0`, the published event reports the new track BELOW its mark (`(st.positionS || 0) < mark`), and no start for this descriptor stands pending (`state.pendingStart !== desc` — a pending start's own contract carry governs it), send the standing transport seek: `nativeTransportSend({ command: 'seekTo', positionS: mark })` — the Now Playing scrub's own command, no new channel. One seek per transition (the `changed` gate fires once per track change; repeat publishes of the same track do not re-seek). Symmetric for forward and backward transitions. The chain tail's items resolve through `nativeContractDescs` identically.
3. THE CURRENT-TRACK CARRY (the disc-tap edge): in `startDesc`, when the incoming descriptor IS the standing current track (same episodeId as `state.current` at the funnel's head) and a LIVE position stands — native: the mirror's position via `playPos()`, accepted only when the mirror names this track (`nativeMirror.trackId === desc.episodeId`); element: `audioEl.currentTime` — that live position is the start's carry in place of the store read, in both branches:
   - podcast branch: the live carry wins over `desc.podPositionS` when the same-current condition holds;
   - day branch: inside the standing `if (!state.pendingResume)` fold step, the live carry wins over the fold value when the same-current condition holds.
   Every deliberate carry that already stands (Continue, the restored queue, a re-send's carry — all seated in `pendingResume` before the fold step) is untouched: the day branch's guard structure stands, and the podcast branch's same-episode residue rule stands for every start that is NOT the standing current. A live position of 0 changes nothing.
4. UNCHANGED, by name: queue composition and order (`queueBuild` / `unplayedOnly` / the fully-played fallback) · the grey rule and its seam · the v615 counts · the fold (`[data-p609sethead]`) · the element path's position behavior (startDesc's standing reads, beyond the same-current carry in step 3) · the contract's shape (no new fields — an old shell parses the same bytes; the seek rides the standing transport channel).
