## Scope

### Problem
- The public GitHub Pages site is still a small publishing hub focused on RSS and audio archive links.
- It does not work as the listener-facing prayer website: there is no complete directory of daily prayers, no per-prayer destination pages, and no clear split between Ora Pro Nobis generated prayers and external Spotify-only prayers.
- The current `Morning Prayer Page Audio Test` workflow is a narrow legacy test surface; it does not represent the actual website publishing product now needed.
- Why now: the repo already publishes multiple daily Ora Pro Nobis episodes and resolves many external Spotify prayers, so the website should expose that complete daily prayer catalog instead of hiding it behind feed XML, archive files, and playlist automation.

### Audience
- Primary user: a listener on mobile or desktop who wants one clean daily prayer directory and direct links to pray or listen.
- Secondary users: the repo maintainer validating published prayer coverage, Spotify playlist users who need stable prayer destinations, and anyone landing on the GitHub Pages root from a shared link.
- Operational stakeholders: GitHub Actions publish workflows, static GitHub Pages hosting, publish audio sidecars, Spotify queue contract metadata, and tests that prevent broken links or missing directory entries.

### Current Status Quo
- `docs/index.html` is hand-authored and mostly explains where the feed and audio archive live.
- `jobs/publish/audio.py` can generate `docs/audio/index.html` and `docs/audio/index.json` from published audio sidecars, but that archive is episode-file oriented rather than prayer-directory oriented.
- Ora Pro Nobis generated daily prayers currently include Morning Prayer, Auxilium Christianorum, Marian Antiphon, Daily Rosary, Daily Reflection, and daily novenas through publish/audio contracts and RSS sidecars.
- External Spotify-only prayers live primarily in `config/spotify/contracts/*.json` through resolver-backed or direct-URI contracts such as Liturgy of the Hours, Bible in a Year, Saint of the Day, daily readings, homilies, Stations, and fixed devotional links.
- A narrow manual workflow, `.github/workflows/morning_prayer_page_audio_test.yml`, only runs legacy page-audio contract tests and is not a full website publish/test pipeline.

### Goal
- Replace the narrow publish test surface with a real website release path for a full daily prayer directory.
- Make the GitHub Pages home page the primary directory for all daily prayers, grouped so listeners can quickly distinguish Ora Pro Nobis prayers from external Spotify-only prayers.
- Use the existing publish and Spotify contracts as the primary source of prayer inventory wherever practical, extending those contracts with website-facing metadata instead of introducing a disconnected directory source.
- Provide a stable link for each prayer in the directory.
- For Ora Pro Nobis prayers, link to generated local website pages and available audio/feed artifacts when present.
- For external Spotify-only prayers, link out to Spotify without trying to mirror or republish third-party audio.
- Keep the site responsive and usable on mobile and desktop, with directory cards/lists that are scannable, tap-friendly, and not dependent on feed XML knowledge.
- Add enough automated validation that the site build catches missing required prayers, broken local links, malformed metadata, and regressions in generated output.

### Constraints
- GitHub Pages remains the hosting layer; the site must be static and publishable from the repository's `docs/` tree or Pages artifact.
- The site must work without server-side code, login, cookies, or a database.
- Do not copy, transcribe, or host third-party Spotify-only prayer audio or proprietary content; those entries should be outbound links only.
- Do not break existing `docs/podcast.xml`, `docs/audio/*.mp3`, `docs/audio/index.html`, or Spotify podcast ingestion.
- Do not change Spotify playlist membership, resolver behavior, or Notion ordering as part of the website release unless implementation research proves a small metadata field is required.
- Preserve the Ora Pro Nobis podcast feed URL and public audio URL patterns.
- Mobile and desktop layouts both need first-class treatment; the directory should not be a desktop table squeezed onto phones.
- Prefer repo-owned structured metadata on the existing contracts over scraping Spotify or relying on live Spotify API calls during the static site build.
- Website metadata extensions must not alter existing publish/audio/playlist behavior unless the site generator explicitly reads them.

### Narrow Wedge
- Build a static daily prayer website around contract-owned website metadata.
- Extend `config/publish/contracts/*.json` metadata for Ora Pro Nobis generated prayer pages.
- Extend `config/spotify/contracts/*.json` with a website-facing metadata block for external Spotify-only prayers and generated Ora Pro Nobis lookup entries that are not already represented cleanly by publish contracts.
- Include all current Ora Pro Nobis daily generated prayer families and all current daily/external Spotify prayer contracts that should appear in the listener directory.
- Redesign `docs/index.html` into the directory home page.
- Generate or maintain one static page per prayer with title, source, listening destination, availability notes, and links to local Ora Pro Nobis audio/feed artifacts or external Spotify.
- Replace or retire `morning_prayer_page_audio_test.yml` with a website validation workflow that runs the site/directory tests and verifies generated static output.
- Keep the first release focused on discoverability and link correctness, not on advanced personalization.

### Non-Goals
- No new audio generation families.
- No changes to the daily Spotify playlist queue, playlist IDs, Notion membership model, or resolver matching semantics.
- No Spotify API crawling at website build time.
- No embedded Spotify web player requirement for the first release.
- No user accounts, favorites, progress tracking, offline mode, analytics, or search indexing service.
- No migration away from GitHub Pages.
- No rewrite of the publish audio or novena pipelines beyond the minimal hooks needed to expose website metadata.
- No attempt to host third-party Spotify-only prayer audio locally.

### Risks And Unknowns
- The biggest product unknown is the exact canonical prayer set: "all daily prayers" likely means every active listener-facing daily contract, but some contracts may be seasonal, Sunday-only, fixed devotional links, duplicate playlist slots, or maintenance-only entries.
- Some resolver-backed external Spotify prayers may not have stable public Spotify URLs without a live lookup result; the directory may need source/show links instead of exact daily episode links for those entries.
- Publish contracts already preserve arbitrary metadata, but Spotify contracts currently drop unknown fields from the loaded `SpotifyQueueContract`, so adding website metadata there requires loader/model support.
- Ora Pro Nobis generated sidecars may not currently contain all metadata needed for clean per-prayer pages, grouping, and "today" links.
- Replacing the legacy test workflow could reduce coverage if page-audio tests are still useful elsewhere; research should decide whether to move those tests into the new website workflow instead of deleting them.
- The current site styling is warm and card-heavy; the overhaul should stay polished but become denser and more practical for repeat daily use.
- GitHub Pages artifact publication currently happens in `publish_audio.yml`; adding a broader website build step must not race with other Pages-deploying workflows such as devotional image publishing.

### Recommended Next Step
- Run `/research-astack` next to map how far the existing publish, novena, and Spotify contracts can be extended for website metadata, and identify the smallest schema additions needed for a contract-driven static site.

- Public hosting is static GitHub Pages. The committed root is `docs/index.html`; generated audio assets are expected under `docs/audio/`; the feed is `docs/podcast.xml`; cover art is copied to `docs/images/logo_ora_pro_nobis.png`.
- The audio pipeline loads six publish contracts and produces five jobs for any single date because only one Marian Antiphon contract is season-active at a time.
- Current generated Ora Pro Nobis families from publish contracts:
  - `morning-prayer-elevenlabs` / title `Morning Prayer`
  - `auxilium-christianorum` / title `Auxilium Christianorum`
  - `daily-reflection` / title `Daily Reflection`
  - `rosary` / title `Daily Rosary`
  - `marian-antiphon-angelus` / title `Angelus` in ordinary season
  - `marian-antiphon-regina-caeli` / title `Regina Caeli` in Easter season
- Daily novenas are not in `config/publish/contracts`; they publish through `jobs/novena_contracts/pipeline.py` and appear in Spotify integration as `config/spotify/contracts/daily-novenas.json`, also targeting the Ora Pro Nobis show ID.
- Spotify queue contracts currently include 27 entries. Seven are Ora Pro Nobis episode lookups against show `4PNxb0OazrkcEp3FAggRoD`: Morning Prayer, three Marian Antiphon slots, Auxilium Christianorum, Daily Examen, Daily Novenas, and Daily Rosary.
- External Spotify-only contracts are resolver-backed or direct/fixed URI entries: Liturgy of the Hours slots, Bible in a Year, Saint of the Day, daily readings, Gospel exegesis, Rosary, homilies, Stations of the Cross, Lenten Devotion, and Night Before Compline.
- Most resolver-backed external contracts do not contain a stable public listener URL in JSON. They contain resolver names and runtime show IDs in `refresh_playlist.py`. A static website should link to curated show/playlist URLs from a website manifest, not infer polished public links from resolver internals.
- Playlist membership is runtime-owned by Notion rows. The four checked-in playlist definitions carry identity only and no contract list, so "active in a playlist today" cannot be determined statically from the repo alone.
- Current audio sidecars contain useful page data after render: `entry_id`, `episode_id`, `published_date`, `contract_id`, `contract_type`, `frequency`, `title`, `description`, `audio_url`, `rss_guid`, `render_context`, `rosary_reflections`, `daily_reflection`, and `resume_markers`.
- There is no committed `docs/audio/` snapshot in this checkout, so the website cannot depend on sidecars being present in repository history. The directory source of truth must be checked-in metadata, with sidecars used opportunistically during publish runs.
- Publish contracts already preserve arbitrary `contract.metadata` as a dictionary and pass it into generated audio jobs. Adding a nested `website` block under `contract.metadata` is backward-compatible with the existing loader and runtime.
- Spotify contract JSON currently tolerates unknown top-level fields because the loader only reads known keys, but those unknown fields are not returned on `SpotifyQueueContract`. A website metadata extension for Spotify contracts needs a new `website` field on the named tuple and validation in `spotify_contracts.py`.
- Direct-URI Spotify contracts already contain enough destination data for fixed episode links. Resolver-backed contracts need curated public destination URLs because their runtime resolver names and show IDs are not good listener-facing links.
- Two workflows can deploy Pages today. `publish_audio.yml` deploys `docs/` directly, while `daily_devotional_image_remote.yml` deploys a staged `pages/` tree built from `docs/` plus devotional exports. Any website build must run in both paths or be expressed as a reusable script called by both.

## Plan

### Summary
- Build a contract-driven static website for the GitHub Pages root and prayer directory.
- Use existing publish and Spotify contracts as the inventory source, adding website-facing metadata directly to those contracts instead of creating a separate directory manifest.
- Add a Python generator that reads contract metadata, writes `docs/index.html`, `docs/prayers/index.json`, and one static page per prayer, while preserving the podcast feed and audio archive surfaces.
- This approach is chosen because it keeps the website catalog near the runtime contracts that already define prayer identity, reducing drift and making tests able to enforce coverage.

### What Already Exists
- `config/publish/contracts/*.json` already carry `contract.metadata` and that dictionary is preserved in publish jobs, so `contract.metadata.website` is a low-risk extension point for Ora Pro Nobis entries.
- `jobs/publish/contracts.py` already normalizes publish contract identity, season, title templates, entry IDs, and date-scoped metadata.
- `config/spotify/contracts/*.json` already define external and Ora Pro Nobis lookup identities with stable contract keys, Notion names, resolver modes, direct URIs, weekdays, and episode lookup show IDs.
- `jobs/playlist/spotify_contracts.py` already validates Spotify contract shape, but must be extended because it currently discards unknown fields.
- `jobs/publish/audio.py` already has URL helpers, sidecar archive readers, static HTML generation patterns, and manifest writing patterns.
- `jobs/publish/run_audio_pipeline.py` and `jobs/novena_contracts/pipeline.py` already write audio/feed outputs into `docs/`.
- `.github/workflows/publish_audio.yml` and `.github/workflows/daily_devotional_image_remote.yml` are the two Pages deploy paths that must share the same website build step.
- Existing tests already exercise temp `docs_root` output generation and JSON/HTML/XML parsing without live services.

### Architecture
- Add a contract-owned website metadata schema:
  - Publish contracts: `contract.metadata.website`.
  - Spotify contracts: top-level `website`.
- Website metadata fields:
  - `enabled`: boolean, default false for Spotify contracts and inferred true only when explicitly present for publish contracts.
  - `slug`: stable URL slug, required when enabled.
  - `title`: listener-facing title, required when enabled.
  - `subtitle`: optional short label for cards.
  - `summary`: required plain-language description.
  - `group`: `ora-pro-nobis` or `external-spotify`.
  - `order`: numeric display order.
  - `source_label`: visible source, such as `Ora Pro Nobis`, `Divine Office`, or `Ascension`.
  - `availability`: `daily`, `seasonal`, `weekday`, `sunday`, or `fixed`.
  - `prayer_family`: optional conceptual grouping, such as `marian-antiphon`.
  - `primary_action_label`: optional CTA label.
  - `external_url`: required for external Spotify-only entries unless the contract has a direct `spotify_uri`.
  - `notes`: optional short availability notes.
  - `aliases`: optional list for related contract keys or display labels.
- Generate a normalized site model in `jobs/publish/site.py`.
- Data flow:

```text
config/publish/contracts/*.json
        |
        v
load_publish_contracts() --> metadata.website
        |
        +----------------------+
                               v
                         site model
                               ^
        +----------------------+
        |
load_spotify_queue_contracts() --> website
        ^
        |
config/spotify/contracts/*.json

site model + optional docs/audio sidecars
        |
        v
docs/index.html
docs/prayers/index.json
docs/prayers/<slug>/index.html
```

### UX And States
- Home page:
  - First viewport is the prayer directory, not a marketing page.
  - Show two main groups: `Ora Pro Nobis` and `Spotify prayers`.
  - Each entry shows title, source label, availability, one-line summary, and a primary action.
  - The layout is a dense responsive grid/list: one column on small mobile, two columns on tablet, and wider multi-column sections on desktop.
- Prayer detail page:
  - Shows title, source, availability, summary, primary action, and secondary links.
  - Ora Pro Nobis entries link to latest local audio when available, the podcast feed, and the technical archive.
  - External Spotify-only entries link to the curated Spotify destination and clearly indicate that audio opens on Spotify.
- Empty state:
  - If no sidecars exist, Ora Pro Nobis pages still render with feed/archive links and a note that generated daily audio appears after publish.
  - The directory must never render as blank when no archive is restored.
- Success state:
  - Generated pages include stable links and `docs/prayers/index.json` lists every visible entry.
- Error state:
  - Site generation fails closed on duplicate slugs, invalid URLs, enabled entries without summaries, missing required metadata, or a visible contract without a valid destination.
- Accessibility/responsive notes:

### Failure Modes
- Invalid website metadata:
  - Detection: schema validation raises before file writes.
  - User experience: publish workflow fails instead of publishing broken directory links.
- Duplicate slugs or duplicate visible prayer families:
  - Detection: site generator validates unique slugs and merge rules.
  - User experience: no partial site deploy from a broken catalog.
- Missing sidecars/audio archive:
  - Detection: `load_published_audio_jobs()` returns empty.
  - User experience: pages still show stable feed/archive links and no latest-audio button.
- Resolver-backed external entry lacks curated URL:
  - Detection: enabled external Spotify website metadata requires `external_url` unless direct `spotify_uri` can be converted to an open Spotify URL.
  - User experience: generation fails instead of rendering a dead CTA.
- Pages deploy path drift:
  - Detection: workflow tests or grep assertions ensure both deploy workflows call the same generator.
  - User experience: devotional image publishes do not erase the website.
- HTML escaping regression:
  - Detection: unit tests include title/summary values with punctuation and assert escaped output.
  - User experience: no malformed layout or unsafe HTML injection from contract copy.
