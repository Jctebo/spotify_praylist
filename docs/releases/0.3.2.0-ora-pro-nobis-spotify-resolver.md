## Scope

### Problem
- The Spotify refresh runtime still resolves queue items through hardcoded resolver names, fixed URIs, or show-specific lookup logic.
- Morning Prayer and Daily Novenas need a reusable way to find the right Spotify podcast episodes by date and tag instead of encoding lookup rules separately in each contract.
- The current model is good for exact one-off items, but it does not express “search this Spotify podcast feed for every episode that matches this date token and these keyword tags.”

### Goal
- Add a reusable Spotify podcast episode lookup resolver that can look up episodes from config-driven show id, date, and keyword/tag rules.
- Apply that resolver to Morning Prayer and novena queue contracts first, while keeping the feature generic enough to reuse for other Spotify podcast feeds later.
- Preserve the existing resolver strings and fixed URIs as a compatibility path while the new search-based config is introduced.

### Non-Goals
- Do not redesign the entire Spotify refresh pipeline.
- Do not change playlist membership ordering, Notion sync, or the broader queue contract model unless the new resolver needs a narrow extension there.
- Do not migrate every contract in the repository at once; this release should focus on the Morning Prayer and novena resolver paths.
- Do not turn the resolver into a generic Spotify search surface for tracks, artists, or playlists; this release is about podcast episode lookup.

### Open Questions
- None for the core resolver contract.

### Success Criteria
- Morning Prayer and novena contracts can declare search-based resolver rules in config without hardcoding show-specific resolver names.
- The resolver can take a Spotify podcast show id plus required name filters and a canonical date, then try alternate date formats if the publisher changes formatting.
- The resolver returns every matching episode for the active date filter set.
- Existing string-based resolver and fixed-URI contracts continue to work.
- Unit coverage proves the new search behavior and the old paths still behave the same.

## Research

### Scope Baseline
- Build a reusable Spotify podcast episode lookup path that takes a contract-owned Spotify show id, required name filters, and a canonical date token with alternate date-format fallbacks.
- Return every episode whose name matches all configured filters, with no legacy resolver fallback path.
- Use it first for Morning Prayer and novena contracts, but keep the resolver generic enough for other podcast shows later.
- Derive the canonical date token from the existing title formats already used by the Morning Prayer monthly and novena resolvers, then layer alternate date renderings on top of that.

### Relevant Files
- `jobs/playlist/refresh_playlist.py`: current resolver dispatcher, queue builder, and the only place that currently special-cases `daily-novenas`.
- `jobs/playlist/spotify_contracts.py`: queue-contract loader and validation rules that will need a new contract shape for show id plus exact-date / required-name filters.
- `config/spotify/contracts/morning-prayer.json`, `config/spotify/contracts/daily-novenas.json`, `config/spotify/contracts/rosary.json`: current minimal contract examples that show the existing resolver-only format.
- `config/spotify/contracts/morning-prayer-monthly.json`: legacy Morning Prayer variant contract deleted during this migration.
- `tests/test_refresh_job.py`: covers queue flattening, special-case resolution, and the daily novena list-return path.
- `tests/test_refresh_job_contract_path.py`: covers the direct script entry path and the current Morning Prayer / Daily Novenas resolver behavior.
- `tests/test_spotify_contracts.py`: pins contract-shape validation and is where new config schema rules should be locked down.
- `README.md`: documents the current Spotify refresh contract model and will need to reflect any new resolver shape.
- `jobs/novena_contracts/resolver.py`: not part of Spotify lookup, but a useful pattern for date-based resolution and list ordering.

### Current System Map
- `resolve_contract_uris(...)` in `jobs/playlist/refresh_playlist.py` is the main decision point. It handles seasonal Marian Antiphons, a dedicated `daily-novenas` list resolver, then falls back to scalar resolver names or fixed URIs.
- `resolve_spec_uri(...)` only understands exact resolver keys or raw `spotify:` URIs; it does not understand show-specific search rules.
- `build_queue_for_playlist_definition(...)` already supports list-valued resolver output, so multi-episode matches can be flattened into the playlist without changing the queue writer.
- `load_spotify_queue_contracts(...)` currently allows exactly one of `resolver` or `spotify_uri`, except for the seasonal Angelus fields. Any new search-based contract shape must intentionally extend that validation with a separate branch for show id + filters.
- The runtime already loads show ids from config via `load_resolver_runtime_config(...)`, so a generic show-id lookup can reuse the existing `shows` config pattern.
- For the new resolver, the show id should come from the contract/config row itself rather than from the legacy `shows` map used by resolver-name lookups.

### Reuse Opportunities
- `daily_novenas_episode_uris(...)` already shows the basic shape we need: fetch a show, paginate with `sp.next`, dedupe by marker, then filter locally and return ordered URIs.
- `title_contains_novena_and_today(...)` already accepts both full and abbreviated month forms around the same day/year pattern, while `monthly_morning_prayer_episode(...)` uses the `Morning Prayer for {Month} {day}, {year}` shape directly. Those existing patterns are the canonical date source for the new config.
- `do_date_aware(...)` already encodes a reusable name-based date matching helper that can be generalized into the new lookup path.
- The existing helpers already show two useful date-search styles: a direct title/date regex and a small alternate-format search set for the same day. That pattern can be lifted into the new resolver without inventing a second resolver path.
- The queue builder already flattens resolver lists, so a new generic lookup helper can return multiple URIs without changing playlist write logic.
- `tests/test_refresh_job.py` already has mocks for `show_episodes`, pagination, and queue flattening, which makes this feature straightforward to cover with focused regression tests.

### External References
- Spotify Web API `GET /shows/{id}/episodes` returns episode `name`, `description`, `html_description`, `release_date`, `release_date_precision`, and `uri`, plus pagination metadata. Official docs: https://developer.spotify.com/documentation/web-api/reference/get-a-shows-episodes
- Spotify Web API also exposes general search, but the episode-specific endpoint is the better fit here because it gives us the show’s full episode list and lets us filter locally by date/tag rules.

### Constraints
- Spotify does not expose a native “tag” field for podcast episodes in the endpoint we already use, so “tag filter” must mean required keyword matching against episode name only.
- The new resolver must preserve existing scalar resolver names and direct `spotify:` URIs so current contracts keep working.
- Contract loading currently fails closed on shape errors, so the new config schema needs clear validation and regression tests.
- Returning multiple matches changes queue length, so ordering and deduping rules must be explicit before implementation.
- With no legacy resolver fallback, a bad show id or bad required-name filter becomes a hard no-match instead of silently resolving through the old resolver.
- Date matching needs a controlled fallback sequence of alternate name/date formats so publisher date-format changes do not break the lookup path outright.

### Risks
- Keyword matching can produce false negatives if the title format is inconsistent across shows or if the exact date token shifts.
- Release date precision can be `year` or `month`, so the implementation cannot assume Spotify metadata alone will always carry a day-level exact match.
- A show with many episodes may require full pagination; skipping pages would silently miss matches.
- If the resolver returns multiple URIs, playlist order and downstream membership expectations can shift.
- Because there is no fallback resolver, a config mistake can take a playlist from partial success to no output at all.
- If the alternate date-format fallback list is too loose, the resolver could match the wrong episode for a given day even when the name filter matches.

### Assumptions To Validate
- “Tag” means repo-configured keyword matching against episode name, not a Spotify-native metadata tag.
- The date filter should be matched against a canonical date token derived from the existing Morning Prayer monthly and novena title formats, plus a small fallback set of alternate renderings for publisher drift.
- Required filters should be enforced as an all-must-match gate, and the resolver should return every matching episode in show order.
- Morning Prayer and novena contracts can move to the new lookup shape without changing their playlist identity or Notion membership wiring.

### Unknowns
- None remaining for the core lookup mode.

### Recommended Direction
- Add one reusable podcast-episode lookup helper that pages through `show_episodes`, filters locally by configured show id plus date/tag rules, and returns ordered episode URIs.
- Teach `resolve_contract_uris(...)` a new search-based contract branch while leaving existing resolver-string and fixed-URI paths untouched.
- Add focused tests for contract validation, pagination, multi-match flattening, and the Morning Prayer / novena adoption path before moving to planning.

## Plan

### Summary
- Build a contract-owned `spotify_episode_lookup` mode for Spotify queue contracts.
- The lookup will match one Spotify show by required name terms and a canonical date string, then retry a short ordered list of alternate date renderings when publishers change formatting.
- This is the smallest change that lets Morning Prayer and Daily Novenas share one reusable resolver while leaving all existing resolver-name and direct-URI contracts intact.

### What Already Exists
- `resolve_contract_uris(...)` already has the single decision point we need for contract-specific routing.
- `build_queue_for_playlist_definition(...)` already accepts list-valued resolver output, so one contract can emit multiple URIs.
- `jobs/playlist/spotify_contracts.py` already owns all queue-contract validation.
- `daily_novenas_episode_uris(...)`, `monthly_morning_prayer_episode(...)`, and `title_contains_novena_and_today(...)` already prove the Spotify paging and title-matching patterns we need to reuse.

### Architecture
- Queue contracts keep the legacy `resolver` / `spotify_uri` modes, but add a third mode: `spotify_episode_lookup`.
- The new lookup object is contract-owned config, not a resolver alias.
- The runtime path becomes:

```text
config/spotify/contracts/*.json
  -> load_spotify_queue_contracts()
  -> SpotifyQueueContract.spotify_episode_lookup
  -> resolve_contract_uris()
  -> spotify_episode_lookup_uris()
  -> show_episodes / next paging
  -> name + date candidate matching
  -> ordered URI list
  -> build_queue_for_playlist_definition()
  -> recreate_playlist_items()
```

- The matcher will inspect episode `name` only.
- The matcher will require all configured name terms to be present.
- The date search will use one canonical date rendering plus a small ordered set of alternate renderings for publisher drift.
- No legacy resolver fallback will be used for these lookup-mode contracts.

### Concrete Changes
- `jobs/playlist/spotify_contracts.py`
  - Add a new `SpotifyEpisodeLookupContract` type with `show_id`, `required_name_terms`, and `date_formats`.
  - Extend `SpotifyQueueContract` with an optional `spotify_episode_lookup` field.
  - Validate that lookup-mode contracts define a non-empty show id, at least one required name term, and at least one date format.
  - Keep the existing resolver-only and seasonal Angelus validation intact.
- `jobs/playlist/refresh_playlist.py`
  - Add a reusable helper that pages a Spotify show, dedupes episodes, builds candidate date strings, and returns every matching episode URI.
  - Update `resolve_contract_uris(...)` to branch on `spotify_episode_lookup` before any legacy resolver handling.
  - Preserve legacy resolver-name behavior for all existing contracts that still use it.
- `config/spotify/contracts/morning-prayer.json`
- `config/spotify/contracts/daily-novenas.json`
  - Replace the resolver alias with `spotify_episode_lookup`.
  - Move the current show ids out of `DEFAULT_SHOWS`-backed resolver aliases and into the contract files.
  - Use `required_name_terms` that match the existing title shapes and ordered `date_formats` that start with the canonical format from the current resolvers.
  - Delete `config/spotify/contracts/morning-prayer-monthly.json` so the monthly Morning Prayer variant is folded into the canonical Morning Prayer contract.
- `tests/test_spotify_contracts.py`
  - Add acceptance and rejection tests for the new lookup object.
  - Keep the existing resolver-only and seasonal contract tests passing.
- `tests/test_refresh_job.py`
  - Add helper-level tests for canonical-date matching, alternate-date matching, pagination, dedupe, and multi-match flattening.
- `tests/test_refresh_job_contract_path.py`
  - Add contract-path coverage proving the migrated Morning Prayer and Daily Novenas contracts still resolve from the direct script entry path.
- `README.md`
  - Document the new `spotify_episode_lookup` contract mode and the required-name/date-format behavior.

### UX And States
- No UI changes.
- Success state: a migrated contract resolves all matching episodes for the target day and the playlist write proceeds normally.
- Empty state: if no episode matches, the contract contributes no URIs and the existing queue failure path still fails closed.
- Error state: malformed lookup config fails during contract loading before Spotify writes begin.

### Failure Modes
- Bad `show_id`, empty name filters, or empty date formats are caught by contract validation before any Spotify write happens.
- A publisher title change that is not covered by the ordered date-format fallback list yields no matches and the existing queue path fails closed.
- Pagination bugs would silently hide older episodes, so the helper must scan and dedupe all pages.
- Overly broad fallback formats could match the wrong episode for a day, so the candidate list must stay short and ordered.
