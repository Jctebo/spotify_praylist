# Release 0.0.5.3 - bugfix-novena-job-import-path

- Status: Shipped
- Last Updated: 2026-03-23

## Scope

### Problem
- The daily novena workflow fails in GitHub Actions with `ModuleNotFoundError: No module named 'jobs'` when `jobs/novena/generate_daily_novena_prayer.py` starts.
- The job is launched as a direct script from the repo root, but the script imports `jobs.novena.*` before the repository root is guaranteed to be on `sys.path`.
- We need the workflow to run reliably in GitHub Actions and locally without requiring users to remember a special launch form.

### Audience
- Primary user: the maintainer running the daily novena / calendar jobs.
- Secondary stakeholders: downstream Notion rows, devotional image generation, and any workflow that depends on the novena job completing successfully.

### Current Status Quo
- `daily_novena_prayer.yml` invokes `python jobs/novena/generate_daily_novena_prayer.py` directly.
- `generate_daily_novena_prayer.py` imports shared modules from `jobs.novena.*`.
- Other scripts in the repo already protect direct execution by adding the repo root to `sys.path` before importing package modules.
- The job currently works only when the interpreter can already resolve the `jobs` package, which is brittle for CI and manual execution.

### Goal
- Make the novena job import-safe when run as a direct script in GitHub Actions and locally.
- Preserve the current workflow entrypoint so the scheduled job and manual runs keep using the same command.
- Eliminate the `ModuleNotFoundError` without changing the job's output behavior.

### Constraints
- Keep the fix narrow and low risk.
- Avoid changing the GitHub Actions launch command unless there is a compelling reason.
- Reuse the existing repo-root bootstrap pattern already used by other job scripts.

### Narrow Wedge
- Add the missing repo-root path bootstrap to `generate_daily_novena_prayer.py`.
- Confirm the daily novena workflow can import all shared `jobs.novena` modules from a clean runner context.

### Non-Goals
- Do not redesign the novena job architecture.
- Do not change the Notion, Romcal, or OpenAI behavior unless it is required to support the import fix.
- Do not rewrite every job entrypoint if only one script is missing the bootstrap.

### Risks And Unknowns
- There may be other direct-run scripts with the same pattern, but this bug report is specifically about the daily novena job.
- A path bootstrap fix could hide a deeper packaging issue, but the current symptoms point to a missing `sys.path` guard.

### Recommended Next Step
- Use `/research-astack` to compare the script entrypoints and confirm the smallest safe import-path fix.

## Research

### Scope Baseline
- Fix the GitHub Actions `ModuleNotFoundError: No module named 'jobs'` that occurs when the daily novena script is run directly as `python jobs/novena/generate_daily_novena_prayer.py`.
- Keep the solution narrow: make the script import-safe without changing the workflow command or the job's functional behavior.

### Relevant Files
- `jobs/novena/generate_daily_novena_prayer.py`
  Why it matters: this is the failing entrypoint and the first `jobs.*` import happens before any repo-root bootstrap.
- `jobs/novena/sync_liturgical_calendar.py`
  Why it matters: it already uses a repo-root `sys.path` bootstrap, so it provides the local pattern to copy.
- `jobs/novena/generate_devotional_image.py`
  Why it matters: it also bootstraps the repo root before importing shared `jobs.novena.*` helpers.
- `jobs/novena/export_liturgical_ics.py`
  Why it matters: it follows the same direct-run protection pattern as the other job scripts.
- `.github/workflows/daily_novena_prayer.yml`
  Why it matters: this workflow calls the script directly and reproduces the import failure in GitHub Actions.

### Current System Map
- The novena workflow runs the Python file directly, not as `python -m ...`.
- The script imports shared Notion/Romcal helpers from `jobs.novena.generate_daily_novena_prayer` and `jobs.novena.liturgical_model`.
- The repo already has a consistent pattern for direct-run scripts: resolve the repository root from `__file__`, prepend it to `sys.path`, then import package modules.
- This means the failure is not a missing dependency or a broken module path inside the codebase structure itself; it is a startup bootstrap gap in one script.

### Reuse Opportunities
- Reuse the repo-root path bootstrap already present in `sync_liturgical_calendar.py`, `generate_devotional_image.py`, and `export_liturgical_ics.py`.
- Reuse the current workflow launch command instead of introducing a new module execution convention.
- Reuse the existing test suite to verify the script imports cleanly after the fix.

### External References
- Python import resolution behavior for direct script execution matters here: `python path/to/script.py` does not automatically add the repo root as a package base in the same way a module run does.
- GitHub Actions' Linux runner is the environment where the import error surfaced, so the fix must be path-robust there.

### Constraints
- The fix should not depend on changing the workflow command.
- The fix should preserve current script behavior and output.
- The repo should continue supporting direct local execution from the project root.

### Risks
- If the bootstrap is added inconsistently or too late in the file, the `jobs` import will still fail.
- There may be other direct-run scripts with the same anti-pattern, but this bug is specifically surfaced by the novena job.

### Assumptions To Validate
- The daily novena script is the only failing entrypoint in this workflow path.
- Adding the repo root to `sys.path` at the top of the file is sufficient to resolve the import error.

### Unknowns
- Whether the same import bootstrap should be audited across all remaining direct-run scripts as a follow-up cleanup.
- Whether GitHub Actions might expose any additional path assumptions after the import fix, though nothing else in the reported stack trace suggests that.

### Recommended Direction
- Add a repo-root `sys.path` bootstrap to `jobs/novena/generate_daily_novena_prayer.py`, then validate the direct-run script and workflow path with focused tests.
