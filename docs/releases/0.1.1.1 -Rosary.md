# Release 0.1.1.1 - add-Rosary

- Status: Shipped

## Purpose
- Add the Rosary with intentions on top of the new generic prayer runner after Morning Prayer is stable. This shipped as a contract-driven Rosary flow on the generic runner.

## Scope

### Problem
- The Rosary needs to fit the new generic prayer format instead of becoming a one-off special case.
- The Rosary changes by weekday, so we need a clean way to map each day to its mystery set and compose the right output.
- The base prayers are repeated across decades and should be generated once, cached, and reused instead of re-rendered every time.
- We already have code that composes prayer audio and fragments, so the Rosary should reuse that shape instead of introducing a separate pipeline.
- The code cannot be hardwired to one Rosary shape if we want to change the number of prayers, alter intention behavior, or add a different prayer later.
- The config should drive the flow so code can discover the prayer sequence, the weekday mystery rules, and the intention strategy without bespoke branching.
- Each Rosary decade should pair the selected mystery fruit with a random intention using a short LLM-generated reflection, similar to the previous flow.
- The config output should stay compact and only show the mystery set, the fruit, and the day's intentions instead of printing the full rosary text.
- The Rosary config should be consistent enough that code can discover mysteries, generate intentions, and follow the flow without special-case parsing.
- A visible prayer-count property should make the Rosary structure easy to inspect at a glance.

### Audience
- Primary user: the maintainer who wants a reusable Rosary prayer flow with intentions and weekday mystery mapping.
- Secondary stakeholders: future prayer configs that should be able to reuse the same generic fragment-composition pattern.

### Current Status Quo
- Morning Prayer is the first prayer on the generic runner path.
- The Rosary still lives in the older playlist/config world and does not yet have a prayer-config contract of its own.
- Reusable prayers like Our Father, Hail Mary, Glory Be, and Hail Holy Queen already exist conceptually in the repo, but not yet as a Rosary-specific reusable composition contract.

### Goal
- Add a Rosary prayer config that runs through the generic runner.
- Compose the Rosary from reusable base-prayer fragments rather than regenerating repeated text over and over.
- Support weekday-based mystery selection and intention handling from config, not from hardcoded Rosary logic.
- Reuse the existing audio/page composition pattern so the Rosary behaves like the other prayer flows.
- Generate 1-2 sentences that merge the mystery fruit with a random intention for each decade.
- Keep the Rosary config display concise: mysteries, fruit, and intentions for the day only.
- Keep the Rosary config visually traceable so a reader can follow the flow of the Rosary from the config alone.
- Make the prayer count explicit in config so the flow can be changed without editing the builder.
- Use this weekday map for the mystery rotation:
  - Monday: The Joyful Mysteries
  - Tuesday: The Sorrowful Mysteries
  - Wednesday: The Glorious Mysteries
  - Thursday: The Luminous Mysteries
  - Friday: The Sorrowful Mysteries
  - Saturday: The Joyful Mysteries
  - Sunday: The Glorious Mysteries

### Constraints
- Do not disturb Morning Prayer stability.
- Do not rewrite the generic runner architecture just for the Rosary.
- Keep the base prayers reusable and cached once.
- The weekday mystery map must be explicit and deterministic.
- The Rosary should reuse existing audio composition patterns rather than inventing a second audio stack.
- The intention reflection should stay short and consistent, not become a long meditation generator.
- The config shape should stay uniform enough for dynamic discovery of mysteries, intentions, and prayer counts.
- The config must be flexible enough that adding or removing prayers later does not require changing Rosary-specific control flow.

### Narrow Wedge
- Start with one Rosary config and one weekday mystery map.
- Build reusable fragments for the repeated base prayers.
- Compose each day's Rosary by selecting the correct mystery set and stitching the fragments together.
- Include intentions in the Rosary flow by pulling a random intention and generating a brief reflective bridge sentence or two for each mystery decade, with the prompt strategy controlled by config.
- Keep the weekday map explicit and data-driven so future changes stay in config instead of code.
- Show the Rosary config output in a concise form that exposes only the mystery, fruit, and day's intentions.
- Add a prayer-count property so the config makes the flow structure visually obvious.
- Favor one consistent schema for all Rosary days so the implementation can traverse it dynamically.
- Prefer a config schema that can also support future prayer additions without rewriting the Rosary builder.

### Non-Goals
- Rebuilding the entire prayer system.
- Adding every possible Marian devotion in this branch.
- Reworking Spotify playlist infrastructure.
- Changing the Morning Prayer contract beyond what the Rosary needs indirectly through shared runner code.

### Risks And Unknowns
- The exact weekday-to-mystery map still needs to be confirmed in the repo-friendly format.
- We need to be careful that shared reusable fragments do not accidentally duplicate audio or break caching keys.
- Rosary intentions now come from the Rosary page's own `Intention` field, so the flow stays local and editable.
- The right boundary between shared fragment generation and Rosary-specific composition is not fully proven yet.
- The LLM-generated reflection could drift away from the fruit/intention pairing if the prompt is too loose.
- The compact config output may need a dedicated formatting rule so it stays readable without printing the full prayer text.
- The biggest architectural risk is letting the current Rosary builder stay too fixed to one output shape, which would make later prayer changes require code edits instead of config edits.

### Recommended Next Step
- Use `/research-astack` to map the existing Rosary-related code, confirm the weekday mystery map, and identify the smallest config-driven wedge for reusable fragments, prayer counts, and intention strategy.

## Research

### Scope Baseline
- The Rosary enhancement is about moving the existing Rosary flow into the new generic prayer/config pattern while making the Rosary behavior itself config-driven.
- The new config should describe the prayer sequence, weekday mystery selection, prayer count, and intention strategy so code can derive behavior without hardcoded branching.

### Relevant Files
- `jobs/notion/generate_page_audio.py`
  - Already contains the Rosary dynamic builder, weekday-map parsing, intention loading, repeated-prayer fragment assembly, and the Rosary-specific Notion output block.
- `tests/test_page_audio_job.py`
  - Already covers weekday-map selection, rosary intention splitting, Rosary config parsing, repeated-prayer reuse, and file-backed Rosary content loading.
- `README.md`
  - Documents the Rosary output mode, weekday map, repeated base prayers, and the LLM-backed decade meditation template.
- `config/notion_spotify_sync_config.json`
  - Shows a legacy Rosary sync target that may need to be reconciled with the new prayer-config version later.
- `config/playlist_config.json`
  - Still contains a Spotify Rosary entry, which is useful as a legacy reference but not the target architecture for this branch.

### Current System Map
- The Rosary already has a dynamic builder path in `jobs/notion/generate_page_audio.py`:
  - `choose_rosary_mystery_set(...)` normalizes weekday mapping into one of the four mystery sets.
  - `split_rosary_intentions(...)` reads the page's `Intention` field, shuffles the day's pool deterministically, and expands shorter input to five intentions.
  - `build_rosary_dynamic_plan(...)` assembles intro, decade, and closing fragments, then builds compact toggle content with each mystery's fruit and intention.
- The Rosary config already supports a `weekday_map`, `mystery_set`, `include_intentions`, and `meditation_fragment_key` shape, so the likely work is to formalize and generalize that shape for the new prayer config rather than invent a second Rosary engine.
- Reusable base prayers are already modeled as separate fragment keys (`rosary-our-father`, `rosary-hail-mary`, `rosary-glory-be`, `rosary-hail-holy-queen`, etc.), which means the code path already knows how to cache and replay repeated prayers.
- The LLM prompt boundary already exists as `rosary-decade-meditation-template`, which currently gets rendered once per decade with `{mystery_set}`, `{mystery_title}`, `{fruit}`, `{intention}`, and `{decade_number}` substitutions.
- The current implementation already demonstrates the exact split we want to preserve: config selects the plan, code composes reusable fragments, and an LLM template handles the short intention bridge.

### Reuse Opportunities
- Reuse the existing Rosary fragment keys and dynamic plan builder instead of creating a second Rosary-specific composer.
- Reuse the deterministic daily shuffle for the Rosary intentions flow.
- Reuse the weekday mapping helper and mystery normalization logic as the config contract shape.
- Reuse the decade meditation prompt fragment as the Rosary intention bridge, since it already supports one short reflective output per decade.
- Reuse the existing compact toggle output structure that shows the mystery title, fruit, and intention instead of the full prayer text.
- Reuse the config-driven pattern already proven by the page-audio jobs, where code reads structured fields and the config decides behavior.

### External References
- No external API research was needed for this pass; the Rosary work is already grounded in repo-local Notion, TTS, and prompt fragments.

### Constraints
- Morning Prayer stability remains a hard constraint.
- The Rosary config should be readable as data, not as prose comments.
- Repeated prayers should stay reusable and cached.
- Intention reflections should stay short and should not expand into a long-form meditation generator.

### Risks
- The current Rosary implementation already mixes dynamic plan generation with output rendering, so the boundary for the new config has to stay clear enough that future prayers can reuse the same shape.
- The repo already has older Spotify-era Rosary references, so it will be easy to accidentally preserve legacy config shapes instead of the new prayer-config contract.
- If the config schema is too loose, code may need brittle string parsing instead of simple field access.
- If the prayer-count / flow fields are underspecified, the Rosary config may be hard to inspect or debug visually.
- If the config becomes too imperative, later changes like "add a prayer" or "change intention strategy" will still require code edits, which would defeat the point of this enhancement.

### Assumptions To Validate
- The existing Rosary builder is the correct base to adapt, rather than replacing it with a second implementation.
- The weekday map should remain config-driven and should not be hardcoded in the implementation.
- The Rosary should continue to use the Rosary page's `Intention` field as the pool for daily intentions.
- The decade meditation template is the right place to merge the mystery fruit and a shuffled intention in 1-2 sentences.
- A visible prayer-count field is sufficient for visual flow tracking, rather than a more complex nested schema.
- The Rosary config can stay flexible enough to add or remove prayers later without changing the control flow in code.

### Unknowns
- Whether the Rosary config should be a standalone prayer contract file or a new section inside the existing page-audio config shape.
- Whether the prayer-count should represent the five decades only or the full flow including intro and closing prayers.
- Whether the Rosary config should expose per-decade metadata directly, or whether that should stay implicit in the fragment sequence.
- Whether the intention merge prompt should be generated from the config itself or remain a reusable template fragment.
- Whether the most maintainable shape is a declarative sequence of prayer blocks, or a higher-level Rosary contract that compiles down to the same dynamic plan.

### Recommended Direction
- Move `/plan-astack` toward formalizing the existing Rosary dynamic builder into a data-driven prayer config with explicit weekday map, prayer count, reusable base prayers, and the decade meditation template as the intention bridge, while keeping the control flow driven by config rather than hardcoded Rosary branching.

## Plan

### Summary
- Formalize the existing Rosary builder into a config-driven prayer contract that describes the sequence, prayer count, weekday mystery mapping, and intention strategy.
- Reuse the current Rosary fragment engine and LLM meditation template, but remove the hardcoded dependence on one Rosary shape so future prayer variations can be driven by config.
- Keep the output compact and inspectable: mysteries, fruits, intentions, and flow metadata should be visible in config without printing the full rosary text.

### What Already Exists
- `jobs/notion/generate_page_audio.py` already has the reusable Rosary fragment composer, weekday-map normalization, intention selection, and decade meditation prompt plumbing.
- `tests/test_page_audio_job.py` already exercises the Rosary dynamic path and provides regression coverage for weekday maps, repeated fragments, and intention-library preference.
- `README.md` already documents the Rosary output mode and the repeated-prayer fragment strategy.
- `config/notion_spotify_sync_config.json` and `config/playlist_config.json` provide legacy Rosary references that can inform migration boundaries but should not define the new config shape.

### Architecture
- The Rosary config should become a declarative prayer contract that the generic runner can read and compile into the existing dynamic Rosary plan.
- Config should define:
  - the weekday map for mystery selection
  - the prayer/decade count
  - the reusable base-prayer fragment sequence
  - the intention source and merge strategy
  - the meditation prompt template or prompt fragment key
- The builder should continue to:
  - select the mystery set from config
  - load or fall back to daily intentions
  - render one short bridge per decade
  - reuse repeated fragments for the base prayers
- The implementation should avoid hardcoded Rosary-specific branching beyond a thin adapter that interprets the declarative config.

ASCII flow:
```text
Rosary prayer config
    |-- weekday map
    |-- prayer count
    |-- base-prayer fragment sequence
    |-- intention strategy
    |-- decade meditation template
            |
            v
generic prayer runner
            |
            v
config-driven rosary plan
    |-- reusable fragments
    |-- daily intentions
    |-- short LLM bridge per decade
    |-- compact config-visible summary
```

### Failure Modes
- Hardcoded flow persists: adding a prayer or changing intentions still requires code edits. Detect by reviewing config shape and builder branching.
- Weekday map drift: a day resolves to the wrong mystery set. Detect by unit tests around `choose_rosary_mystery_set(...)`.
- Intention fallback failure: the Rosary has no usable intention text. Detect by tests around `split_rosary_intentions(...)`.
- Output becomes too verbose: config no longer gives a quick visual trace. Detect by snapshot-style assertions on compact summary fields.

### Rollout Notes
- Keep the Rosary work behind the existing generic runner path until the config contract is stable.
- Reuse the current Rosary engine first, then narrow or generalize the contract shape only if the tests show the need.
- Prefer the smallest config surface that still allows future prayers to vary without code changes.

### Not In Scope
- Rebuilding the entire prayer runner architecture.
- Reworking Spotify playlist infrastructure.
- Adding new Marian devotions beyond the Rosary.
- Redesigning Morning Prayer.
- Changing the underlying prayer intention database schema in this branch.

### Resolved Decisions
- The Rosary contract lives in `config/rosary.json`.
- The prayer count represents the decade flow, with the visible intro and closing blocks expressed separately in the contract.
- The intention bridge stays as a reusable prompt fragment keyed by `rosary-decade-meditation-template`.
- The existing Rosary dynamic builder remains the engine, with a thin config-driven adapter compiling the flow.
