# Release 0.3.9.0: Flexible Prayer Introductions

Version: 0.3.9.0
Status: SHIPPED
Last Updated: 2026-07-24
Branch: `codex/flexible-non-rosary-intros`

## Scope

### Problem
- Morning Prayer introductions sound scripted because generation and validation require exact sentence counts, fixed sentence positions, and stock openings such as “In today’s Gospel” and “Today’s focus is.”
- Auxilium Christianorum and Marian Antiphon transitions are fixed one-sentence templates, so their wording repeats and can sound mechanical even when the daily theme changes.
- Novena welcome fragments use a fixed construction that can awkwardly combine the Gospel, shared daily theme, saint, and novena intention.
- The Rosary introduction is now flexible, but its prompt does not yet express a simple sentence range that keeps the spoken opening from growing too long.
- The current surfaces solve similar grounding and safety problems separately, making it difficult to improve naturalness consistently without weakening factual or theological safeguards.
- This work follows the Rosary-specific `0.3.8.0` release so all prayer-introduction prompts can share an explicit brevity policy without changing the Rosary’s shipped priority, intention, or reflection behavior.

### Audience
- Primary user: a listener praying the daily Ora Pro Nobis lineup who should hear concise, reverent introductions that sound written for that prayer and day.
- Secondary stakeholder: the publisher reviewing generated prayer audio for Catholic accuracy, natural spoken rhythm, useful variety, and reliable fallbacks.
- Future maintainers benefit from one understandable policy for generated devotional introductions instead of separate phrase-level rules.

### Current Status Quo
- Morning Prayer uses an LLM, but its prompt and validator prescribe exact three-sentence structures and mandatory sentence openings.
- Auxilium Christianorum uses one deterministic prayer-intro template after the liturgical announcement.
- Angelus and Regina Caeli each combine the generated daily intro with the same deterministic Marian transition pattern.
- Structured novenas prepend a fixed “Welcome to Day…” fragment and a formulaic daily-theme/Gospel bridge; source-owned novena introduction text may also follow.
- The Rosary generator uses flexible semantic validation and character bounds, but its introduction prompt does not set the requested sentence range.
- The shared daily liturgical context already supplies the approved theme, Gospel bridge and citation, celebration data, season, and fallback status, but each surface turns that context into prose differently.

### Goal
- Give the language model enough freedom to write natural, varied, prayerful introductions while keeping every factual claim grounded in supplied liturgical and prayer-specific context.
- Put flexible sentence ranges directly in each generation prompt so intros remain brief without restoring exact-count validation, fixed sentence positions, or stock opening phrases.
- Preserve a distinct purpose and depth for each surface:
  - Rosary: a 2–4 sentence opening that establishes the dominant focus and prepares the listener for the overall intention and five decades.
  - Morning Prayer: a concise opening reflection that orients the listener to the day, Gospel when available, and shared daily focus before the fixed prayer body.
  - Auxilium Christianorum: a brief transition that connects the day’s grace to the intention and protective character of the devotion.
  - Marian Antiphons: a brief transition specific to the Angelus or Regina Caeli that leads naturally into the fixed prayer without duplicating the daily opening.
  - Novenas: a brief welcome and bridge connecting the active novena day and saint-specific focus to the Church’s prayer for the day.
- Prompt sentence ranges:
  - Rosary and Morning Prayer: 2–4 sentences.
  - Auxilium Christianorum, Marian Antiphons, and novenas: 1–2 sentences.
- Keep lower-level source data and canonical daily-theme metadata auditable even when the spoken wording varies.
- Success criteria:
  - All five surface groups include their sentence range in the model prompt.
  - Sentence ranges guide generation but are not enforced as an exact-count acceptance rule.
  - No included model-generated intro requires an exact sentence count or exact opening phrase.
  - Every intro names or clearly identifies its prayer and uses the required daily theme or liturgical grounding appropriate to that surface.
  - Gospel content is used only when supplied and is omitted cleanly when unavailable.
  - Auxilium, Angelus, Regina Caeli, and novena intros no longer repeat one fixed transition sentence on every episode.
  - Morning Prayer, Marian Antiphon, and novena flows do not duplicate the same daily-theme explanation back to back.
  - Generated text remains concise for TTS, rejects markdown and production commentary, and does not invent Scripture, saint biography, feast, season, doctrine, quotation, or current-event details.
  - Missing model access or invalid output still produces a complete, prayer-specific deterministic introduction.
  - Canonical prayer text and source-owned novena content remain unchanged.

### Constraints
- Reuse the canonical shared daily liturgical context rather than introducing another competing feast/Gospel/season resolver.
- Do not apply the Rosary’s season-dependent dominant-priority algorithm globally; its only new Rosary change in this release is the 2–4 sentence prompt guidance.
- The model may only use supplied celebration, season, Gospel, shared-theme, prayer identity, novena day, saint, feast, and approved devotion context as factual sources.
- Keep intros short enough to serve as an entrance into prayer rather than becoming a homily or replacing Daily Reflection.
- Retain maximum spoken-length and semantic safety checks; do not turn the prompt ranges into rigid sentence-count validators.
- Different prayer surfaces may use different length and grounding requirements; one shared policy must not flatten their distinct devotional purposes.
- Preserve fixed prayers, imported traditional novena text, prayer counts, audio roles, feed identity, Spotify lookup rules, and seasonal contract gating.
- Deterministic fallbacks must meet the same semantic requirements and must never expose errors or prompt language to listeners.
- Text, audio fragments, sidecar metadata, caching, and resume markers must remain consistent and auditable.

### Narrow Wedge
- Build one reusable devotional-intro policy with surface-specific profiles for:
  - Rosary `rosary_intro`, limited to adding 2–4 sentence guidance to the existing devotional-package prompt;
  - Morning Prayer `daily_intro`;
  - Auxilium Christianorum `prayer_intro`;
  - Angelus and Regina Caeli `prayer_intro`;
  - structured novena welcome/theme transitions across generated, short-form, fixed, and traditional novena paths.
- Each profile defines its prayer-specific purpose, approved context, prompt-level sentence range, flexible character bounds, semantic requirements, and deterministic fallback.
- Generate or resolve one introduction package per prayer episode and reuse it across readable text, audio fragments, sidecar metadata, and resume markers.
- Remove duplicated adjacent prose where a general daily introduction and prayer-specific transition currently restate the same Gospel or theme.
- Add focused and integration coverage for valid generation, missing Gospel, missing model, malformed output, unsupported claims, fallbacks, fragment order, and unchanged canonical text.

### Non-Goals
- Changing the Daily Rosary priority resolver, overall intention, decade intentions, reflections, semantic validation rules, or canonical prayers shipped in `0.3.8.0`.
- Adding sentence-count rejection to the Rosary or any other intro validator.
- Rewriting Daily Reflection or adding another long reflection to prayer episodes.
- Changing the canonical shared daily-theme selection algorithm or its cross-prayer cache.
- Rewriting source-owned novena introductions, saint biographies, or traditional novena prayer bodies.
- Generating current-events intentions or using external news as devotional context.
- Changing prayer titles, Spotify matching, RSS identity, seasonal music, TTS voices, or publication schedules.
- Persisting identical model prose across independently executed text and audio jobs unless research shows this is required for correctness.
- Building a general-purpose copywriting framework beyond these prayer-introduction surfaces.

### Risks And Unknowns
- A shared policy could become another rigid template if it standardizes prose instead of standardizing safety, grounding, and output structure.
- Prompt guidance is not a hard guarantee; research must preserve maximum-length safeguards while keeping sentence counting out of semantic acceptance.
- Morning Prayer and Marian Antiphons currently combine a general daily intro with other transitions; research must determine whether to merge, shorten, or selectively suppress blocks to prevent repetition.
- Novena flows include generated, fixed, compacted, imported, and traditional content shapes; the intro boundary must be mapped carefully so source-owned material is never rewritten or duplicated.
- Semantic validation must detect missing prayer identity, missing daily grounding, prompt echoes, markdown, foreign Scripture citations, and unsupported proper-name claims without forcing stock wording.
- More model freedom may increase rerun variation; the release needs a clear cache and audit boundary even if cross-run prose identity remains out of scope.
- The appropriate balance between one structured shared generator and thin surface-specific builders is not yet proven.

### Recommended Next Step
- Run `/research-astack` to trace every Rosary and non-Rosary intro prompt, validator, fallback, contract block, novena rendering path, fragment, sidecar field, cache boundary, and test.
- Research should recommend:
  - the reusable intro-policy boundary and its surface-specific profiles;
  - the exact prompt ownership and regression tests for the 2–4 and 1–2 sentence ranges without exact-count validation;
  - whether adjacent `daily_intro` and `prayer_intro` blocks should be combined or coordinated for Marian Antiphons;
  - how generated, fixed, compacted, imported, and traditional novena paths should share a welcome/transition without altering source text;
  - semantic validation rules and deterministic fallback requirements;
  - the generation, caching, metadata, and fragment model that keeps text and audio internally consistent;
  - the smallest safe implementation sequence with complete regression coverage.

### Current System Map

#### Shared liturgical context
- `DailyThemeRuntimeCache` already resolves and caches one canonical context per date, calendar, and locale.
- The payload supplies the approved theme title, explanation, transition, reflection focus, Gospel bridge, source metadata, version, and fallback state.
- This is the correct factual input for every scoped surface. No additional calendar, Gospel, feast, or season resolver is needed.
- The shared theme priority is intentionally distinct from the Rosary's season-sensitive dominant-priority resolver and should remain unchanged.

#### Rosary
- `jobs/publish/rosary_reflections.py` generates one atomic devotional package containing the introduction, overall intention, and five decade intentions/reflections.
- The primary path uses structured Pydantic output, followed by a JSON retry and then an atomic deterministic fallback.
- The introduction currently has `INTRO_MIN_CHARS = 120` and `INTRO_MAX_CHARS = 700`.
- Its prompt explicitly allows varied language and says not to force a sentence count, but it does not yet state the desired 2–4 sentence range.
- Semantic validation checks length, priority anchors, all five decades, distinct categories, mystery and fruit grounding, markdown, prompt echoes, and unsupported Scripture citations. It does not count sentences.
- The current atomic package and runtime cache already preserve coherence across all five decades and should not be refactored into the new non-Rosary intro generator.

#### Morning Prayer
- `jobs/publish/daily_intro.py` owns both daily Gospel/celebration retrieval and intro prose generation.
- `_call_openai_prompt` currently requests exactly three sentences and uses deterministic model settings. It supports the Responses API with a chat-completions compatibility fallback.
- `_validate_daily_intro` and `_validate_theme_intro` enforce exact sentence counts, exact sentence positions, and stock openings such as “Today the Church celebrates,” “In today's Gospel,” and “Today's focus is.”
- The deterministic fallbacks reproduce the same fixed construction.
- The file's context-fetching behavior is reusable, but its prose prompt, validators, and fallbacks are the main source of the scripted sound.
- Existing tests intentionally reject flexible two-sentence output and assert the old stock phrases, so those assertions must change with the implementation.

#### Auxilium Christianorum
- The `prayer-intro` block in `jobs/publish/contracts.py` is deterministic template rendering rather than model generation.
- `_validate_prayer_intro_sentence` requires exactly one punctuated sentence.
- The contract places a liturgical announcement first, followed by a fixed transition and then the canonical prayer body.
- The liturgical announcement already carries the detailed daily context. A new 1–2 sentence transition should therefore connect that context to protection, family, and the devotion's intention without restating the full announcement.

#### Marian Antiphons
- Angelus and Regina Caeli currently place a generated general `daily_intro` immediately before a deterministic `prayer_intro`.
- Both prayer-intro templates repeat the Gospel/theme material that the daily intro has just presented.
- Generating both blocks independently would increase variation but would not solve duplication and could make the total opening too long.
- The clean boundary is one combined 1–2 sentence, prayer-specific generated intro for the active antiphon, replacing the adjacent general-plus-template pair while leaving seasonal contract gating and fixed prayer text unchanged.

#### Novenas
- `jobs/novena_contracts/engine.py` always prepends a deterministic `_intro_fragment` beginning with “Welcome to Day…” and then adds a formulaic Gospel/shared-theme bridge.
- That fragment is used for compact and normal section paths.
- Hybrid generated sections separately instruct the model to begin with a 1–2 sentence saint introduction; the standard nine-day petition template repeats this instruction. This can duplicate the engine-owned welcome.
- Fixed and imported novena contracts may also contain source-owned introductory prose. That prose must remain intact and follow, rather than be replaced by, the engine-owned bridge.
- A dedicated generated 1–2 sentence novena welcome/transition should replace only `_intro_fragment`. The generic generated-section prompt should no longer require another saint introduction.
- `render_novena` already derives its text body and audio fragments from the same rendered fragment list, so a single render is internally consistent.

#### Resolution and cache boundaries
- `resolve_block_content` generates a `daily-intro` on every resolution; the current `prayer-intro` is deterministic and has no generated-result cache.
- Text job construction resolves blocks once for the body and again for sections. Audio job construction resolves them once for audio fragments and again for the readable body.
- As a result, Morning Prayer can already call the model twice within one job. A generated prayer transition would inherit the same problem.
- Rosary avoids this through its cached atomic devotional package.
- The shared implementation needs one immutable intro result per profile/block identity in the entry runtime context, reused by body, sections, fragments, and metadata.
- Independently launched text and audio commands may still produce different prose; cross-run persistence is outside the scoped correctness boundary.

#### Sidecars and resume behavior
- Publish-contract jobs already expose render context and audio fragments in their artifacts, providing a natural place for intro provenance.
- Novena pipeline resume logic reuses an existing sidecar when the canonical daily-theme fields are current.
- An intro-policy code change by itself would not invalidate an otherwise current novena sidecar, leaving old fixed intros in place after deployment.
- The intro policy therefore needs a version recorded in rendered metadata and included in novena sidecar freshness checks.

#### Baseline verification
- `python -m unittest tests.test_publish_daily_intro tests.test_publish_rosary_reflections tests.test_novena_engine`
  - 39 tests passed.
- `python -m unittest tests.test_publish_contracts tests.test_novena_pipeline tests.test_novena_artifacts`
  - 38 tests passed.
- The focused baseline is 77 passing tests before implementation.

### Reuse Opportunities
- Keep `DailyThemeRuntimeCache` and the existing Gospel/celebration retrieval as the only canonical factual inputs.
- Keep the Rosary's atomic package generator, structured output, validators, character bounds, retry path, and fallback; add only prompt-level 2–4 sentence guidance.
- Reuse the existing Responses API and chat-completions compatibility path for short string generation. No new provider or dependency is needed.
- Introduce a small shared typed result for non-Rosary intros, carrying at least text, surface/profile, generation source, fallback reason, and policy version.
- Centralize common prose safety checks such as maximum length, markdown/prompt leakage, unsupported citations, and supplied-context grounding while leaving prayer-specific semantic requirements in profiles.
- Reuse runtime context caching so every consumer of an episode receives the same resolved intro.
- Reuse existing fragment and sidecar structures, adding intro provenance rather than introducing a parallel artifact format.

### External References
- No new external service, package, or API behavior is required.
- The installed repository environment already exercises `openai` 2.24.0 and `pydantic` 2.13.0b2 through the existing generation paths.
- Repository-local contracts, tests, and runtime behavior were sufficient for this research; no external architectural dependency was identified.

### Constraints
- Sentence ranges belong in prompts and tests that inspect prompts; they must not be enforced as exact sentence-count rejection.
- Each profile still needs a maximum character bound suitable for spoken audio. Exact non-Rosary values should be selected during planning and covered by boundary tests.
- Generated claims must be traceable to supplied liturgical, Gospel, prayer, saint, feast, or novena-day context.
- Missing Gospel data must produce a complete intro without implying that a Gospel was supplied.
- Model failure, malformed output, or failed semantic checks must resolve to a concise deterministic prayer-specific fallback.
- Canonical prayers, imported novena content, feed identity, Spotify behavior, voices, schedules, and seasonal contract selection must remain byte-for-byte or behaviorally unchanged as applicable.
- The Rosary change must not alter its dominant priority, overall intention, five-decade coherence, or reflection validation.

### Risks
- The highest correctness risk is generating the same logical intro more than once inside a job, causing readable text, spoken audio, sections, or metadata to disagree.
- The highest release/resume risk is stale novena sidecars surviving the policy change because current freshness checks only understand the daily-theme version.
- A shared generator could recreate scripted prose if profiles prescribe sentence positions or stock openings instead of purpose, approved inputs, and semantic anchors.
- A validator based on naïve proper-name or sentence parsing could reject natural Catholic language or abbreviations while still missing unsupported claims.
- Combining Marian blocks changes contract ordering and requires integration tests for both seasonal variants.
- Fixed novena contracts vary in shape; removing the engine intro or generic saint-intro instruction too broadly could delete a needed welcome or alter source-owned material.

### Assumptions To Validate
- “The other four surfaces” means Morning Prayer, Auxilium Christianorum, Marian Antiphons as one grouped surface, and novenas; Daily Reflection remains excluded.
- One internally consistent result per publish job is sufficient; identical prose across separately executed text and audio commands is not required.
- The Marian listener experience is better served by one combined prayer-specific intro than by retaining both adjacent intro blocks.
- A single model attempt followed by semantic validation and a deterministic fallback may be sufficient for these short intros; planning should decide whether one corrective retry is worth the added latency.
- Profile settings can be primarily code-owned to prevent duplicated sentence policy across multiple JSON contracts, with contracts retaining only genuinely deployment-specific model configuration.

### Unknowns
- The exact minimum and maximum character limits for the 2–4 and 1–2 sentence profiles.
- Whether invalid short-form output should receive a corrective retry before fallback.
- The final metadata field names and policy-version format used by publish-contract and novena sidecars.
- Whether contract JSON should explicitly name an intro profile or whether block type plus prayer identity is an adequate stable key.

### Recommended Direction
- Add a focused shared non-Rosary devotional-intro module with:
  - surface-specific profiles;
  - prompt construction using purpose, approved context, and sentence guidance;
  - flexible semantic and maximum-length validation;
  - prayer-specific deterministic fallbacks;
  - a typed result containing text and audit metadata;
  - an explicit policy version.
- Cache that result in the publish entry runtime by stable surface/block identity before any body, section, or audio rendering.
- Apply the module as follows:
  - Morning Prayer: retain its context retrieval, replace stock three-sentence generation and phrase validators, and guide 2–4 sentences.
  - Auxilium Christianorum: retain the liturgical announcement and generate one 1–2 sentence devotion-specific transition.
  - Angelus and Regina Caeli: replace the adjacent general `daily_intro` plus deterministic transition with one combined 1–2 sentence antiphon-specific intro.
  - Novenas: replace only the engine-owned fixed welcome/bridge with a generated 1–2 sentence result, preserve source-owned sections, and remove duplicate saint-introduction instructions from generic generated petitions.
  - Rosary: add 2–4 sentence guidance to the existing atomic prompt and otherwise leave its shipped pipeline unchanged.
- Record intro profile, policy version, generation/fallback source, and fallback reason in sidecar/render metadata without exposing that metadata in spoken text.
- Include the intro policy version in novena artifact freshness checks so existing target sidecars regenerate once after the release.
- Plan focused unit tests for prompts, permissive sentence shapes, semantic failures, fallbacks, and cache reuse, followed by contract/engine integration tests for fragment order, seasonal Marian selection, sidecar invalidation, and unchanged canonical/source-owned content.

## Plan

### Summary
- Build one shared non-Rosary devotional-intro pipeline with prayer-specific profiles, flexible prompt guidance, semantic validation, deterministic fallbacks, per-job caching, and auditable metadata.
- Keep the Rosary's existing atomic devotional package intact and add only the requested 2–4 sentence guidance to its prompt.
- Replace repeated deterministic transitions for Auxilium Christianorum and novenas, and collapse each Marian Antiphon's adjacent general and prayer-specific openings into one generated intro.
- Use prompt ranges rather than exact sentence-count validation:
  - Morning Prayer and Rosary: 2–4 sentences.
  - Auxilium Christianorum, Angelus, Regina Caeli, and novenas: 1–2 sentences.
- Use policy version `devotional-intro-v1` so generated artifacts can expose their provenance and stale novena sidecars can be refreshed.

### What Already Exists
- `DailyThemeRuntimeCache` and `build_daily_liturgical_context` provide the canonical shared daily theme, Gospel bridge/citation, celebration, season, sources, and fallback state.
- `jobs/publish/daily_intro.py` provides Morning Prayer's calendar and Gospel retrieval, OpenAI settings, and missing-Gospel behavior.
- `jobs/publish/contracts.py` already has one runtime context per publish job and established cache patterns for Rosary and Daily Reflection generation.
- `jobs/publish/rosary_reflections.py` already provides the desired Rosary atomic package, semantic validation, retry behavior, fallback, and 120–700 character intro bound.
- `jobs/novena_contracts/engine.py` already renders one shared fragment list into both readable novena text and audio.
- Publish and novena sidecars already persist render context and ordered fragments.

### Architecture
- Add `jobs/publish/devotional_intro.py` as the shared non-Rosary policy boundary.
- Define immutable `DevotionalIntroProfile` and `DevotionalIntroResult` types.
- Define code-owned profiles:
  - `morning-prayer`: 2–4 sentence prompt guidance, 80–700 characters.
  - `auxilium-christianorum`: 1–2 sentence guidance, 40–420 characters.
  - `angelus`: 1–2 sentence guidance, 40–420 characters.
  - `regina-caeli`: 1–2 sentence guidance, 40–420 characters.
  - `novena`: 1–2 sentence guidance, 40–420 characters.
- `DevotionalIntroResult` will contain `text`, `profile`, `policy_version`, `source`, and `fallback_reason`, plus a JSON-safe metadata serializer.
- Generation flow:
  1. Build a prompt from the selected profile and only the approved supplied context.
  2. Request plain devotional prose with the profile's sentence range and no stock opening.
  3. Validate non-empty text, character bounds, prayer identity, required daily grounding, Gospel availability, foreign citations, markdown, prompt echoes, and production commentary.
  4. On semantic failure, make one corrective retry including concise validation feedback.
  5. On missing model access or a second invalid result, return the profile's deterministic fallback.
- Sentence parsing may be used for diagnostics and corrective feedback, but sentence count will not determine acceptance.
- Morning Prayer will retain `build_daily_intro_text` as a string-returning compatibility wrapper over a new result-returning builder.
- Publish jobs will cache results in an internal `devotional_intro_results` map keyed by entry, block kind, profile, and prayer title. The internal cache will be excluded from raw render context; one JSON-safe `devotional_intro` metadata object will be attached after rendering.
- Novena rendering will generate its intro once before fragment assembly and use that same result for text, audio, and metadata.

```text
Canonical daily context + prayer/day context
                    |
                    v
          Devotional intro profile
                    |
                    v
        Prompt -> validate -> retry once
                    |              |
                 valid          invalid/error
                    |              |
                    +------> deterministic fallback
                                   |
                                   v
                     DevotionalIntroResult
                                   |
                 +-----------------+-----------------+
                 |                 |                 |
              text body      audio fragments    sidecar metadata
```

### Failure Modes
- Model access is unavailable:
  - Detected by the generator exception.
  - The listener receives the deterministic profile fallback; metadata records `source=fallback` and a sanitized reason.
- Generated text exceeds its maximum length or lacks prayer/daily grounding:
  - Detected by semantic validation.
  - One corrective retry occurs, followed by fallback if still invalid.
- Gospel is unavailable but the model mentions it:
  - Detected by the profile validator.
  - Corrective retry/fallback omits Gospel language.
- A generated intro invents another Scripture citation:
  - Detected against the supplied citation allowlist.
  - The invalid text is never rendered or spoken.
- Body, sections, and audio resolve the same block more than once:
  - The runtime cache returns the same immutable result.
  - Tests assert one generator call and byte-identical intro text across consumers.
- Marian contracts accidentally retain both intro blocks:
  - Contract-order tests require exactly one generated intro before the canonical prayer sequence.
- Novena target sidecars retain old intro prose:
  - The missing or stale `devotional-intro-v1` value invalidates reuse and regenerates the target artifact.
- Imported novena prose is altered or dropped:
  - Fixed, compact, traditional, and generated-path tests compare section order and source-owned text after the intro fragment.
- Metadata contains internal dataclasses or prompts:
  - Internal cache fields are excluded from render context; serialization tests require JSON-safe audit metadata only.
