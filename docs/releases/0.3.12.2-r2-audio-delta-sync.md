# Release 0.3.12.2 — R2 Audio Delta Sync

Branch: `enhancement/r2-audio-delta-sync`

## Scope

### Problem
- Daily audio publishing re-uploads the complete `docs/audio` archive to Cloudflare R2, making routine runs take tens of minutes.

### Audience
- Ora Pro Nobis listeners waiting for daily prayer audio and the maintainer operating the scheduled publish workflow.

### Current Status Quo
- The publish workflow restores the archive, renders new episodes, then calls a sequential uploader for every archive file.

### Goal
- Upload only new or changed audio archive objects while preserving public URLs, content types, and complete RSS history.
- Make unchanged daily runs avoid full-archive R2 transfer.

### Constraints
- R2 is S3-compatible and remains the source for public audio files.
- The sync must never delete remote audio as part of routine publishing.
- Upload failures must fail the workflow clearly.

### Narrow Wedge
- Add safe remote-object comparison and bounded concurrent uploads to the existing R2 sync script.

### Non-Goals
- Replacing the GitHub Actions archive cache or changing podcast URLs.
- Deleting stale R2 objects or redesigning the publish workflow.

### Risks And Unknowns
- Remote metadata must identify unchanged files without treating a changed audio file as current.
- R2 pagination and API behavior must be covered by tests.

### Recommended Next Step
- Research the current uploader, R2/S3 metadata available through boto3, and existing sync tests before planning.

## Research

### Scope Baseline
- Make routine R2 audio publishing incremental without changing public URLs, archive retention, or remote-deletion behavior.

### Relevant Files
- `scripts/sync_r2_audio.py`: builds the archive plan and currently calls `upload_file` once for every local object, sequentially.
- `tests/test_sync_r2_audio.py`: existing isolated uploader coverage and fake S3 client.
- `.github/workflows/publish_audio.yml`: restores `docs/audio`, renders current episodes, then invokes the R2 sync before Pages deployment.
- `docs/releases/0.3.6.7-r2-audio-publishing.md`: confirms R2 is the public audio host while `docs/audio` remains the local archive/cache.

### Current System Map
- The workflow restores a full `docs/audio` cache, renders prayer and novena files, builds the site, then syncs the complete archive to R2.
- The current script recursively enumerates local files and unconditionally invokes `client.upload_file` for each object.
- The July 29 run uploaded a 4.25 GB archive and spent about 38 minutes in the R2 sync step.

### Reuse Opportunities
- Retain the existing S3-compatible boto3 client, content-type routing, CLI entrypoint, and test fake.
- Keep the workflow ordering: only sync after all audio rendering and before Pages deploy.

### External References
- Cloudflare R2 uses the S3-compatible boto3 client already configured by `make_r2_client`.

### Constraints
- Do not delete remote objects during publishing.
- Existing R2 objects lack an application checksum, so the first manifest-enabled run must safely re-upload them once to establish verified state.
- The comparison must be resilient to remote object deletion: a key absent from an R2 listing is always uploaded.

### Risks
- Size-only comparison can miss a changed file with the same length; it is insufficient.
- Unbounded upload parallelism could throttle R2 or exhaust runner resources.

### Assumptions To Validate
- The R2 client supports `list_objects_v2`, `get_object`, and `put_object` through its S3-compatible endpoint; boto3 does.

### Unknowns
- None blocking the safe manifest approach.

### Recommended Direction
- Store a compact checksum manifest in R2 after successful uploads. On later runs, list remote keys once, compare local SHA-256 values to manifest entries, upload only missing/changed objects with bounded workers, and write the manifest only after all uploads succeed.

## Plan

### Summary
- Replace unconditional archive uploads with a verified, non-destructive delta sync.
- Use a remote checksum manifest rather than file size alone, so equal-size content changes still upload.

### What Already Exists
- A boto3 S3-compatible R2 client, recursive archive-plan builder, content-type handling, CLI, and mock-based tests.

### Architecture

```text
docs/audio -> hash local files -> list R2 keys + read manifest
          -> upload missing/changed files (bounded workers)
          -> write manifest only after all uploads succeed
```

### Concrete Changes
- `scripts/sync_r2_audio.py`: add SHA-256 calculation, manifest read/write, paginated remote-key listing, delta selection, bounded concurrent uploading, and accurate summary counts.
- `tests/test_sync_r2_audio.py`: expand the fake R2 client and cover bootstrap, unchanged, changed, missing-remote, pagination, failure, and content-type paths.
- `docs/releases/RELEASE_LOG.md` and this release artifact: document the optimized R2 publishing behavior.

### UX And States
- No user-interface change.
- Workflow logs will report scanned, uploaded, and skipped object counts; any upload or manifest failure stops the deployment.

### Implementation Phases

#### Phase 1: Delta-selection primitives
- Goal: derive stable local checksums and safely determine which keys require upload.
- Files: `scripts/sync_r2_audio.py`, `tests/test_sync_r2_audio.py`.
- Verification: unit tests for first-run bootstrap, unchanged objects, same-size changed objects, and remotely missing keys.
- Rollback: retain the prior sequential full-upload behavior by reverting this module only.

#### Phase 2: Bounded uploads and manifest commit
- Goal: upload selected files concurrently with a fixed small worker count, then atomically publish the new manifest only on success.
- Files: `scripts/sync_r2_audio.py`, `tests/test_sync_r2_audio.py`.
- Verification: unit tests for upload failure preventing manifest update and for configured worker bounds.
- Rollback: no remote deletion occurs; the next run can safely retry.

#### Phase 3: Release verification
- Goal: confirm script contracts and whole repository behavior remain intact.
- Files: release documentation only.
- Verification: focused sync tests, full unit suite, whitespace/diff inspection, and pre-landing review.

### Failure Modes
- Missing or malformed manifest: treat every local file as needing a safe one-time upload.
- Remote object absent from listing: upload it even if the manifest references it.
- Upload error: fail without replacing the existing manifest, so the next run retries safely.
- R2 list pagination: include every page before making skip decisions.

### QA And Test Matrix
- Initial run: all files upload and a manifest is written.
- Steady-state run: no files upload, all are counted as skipped.
- Content changed with identical size: it uploads because SHA-256 differs.
- Remote key missing despite manifest: it uploads.
- Paginated listing: later-page keys are respected.
- One upload fails: manifest is not committed.
- Run `python -m unittest tests.test_sync_r2_audio -q` and `python -m unittest discover -v`.

### Rollout Notes
- The first run after deployment uploads the existing archive once to establish the manifest; later daily runs are incremental.
- Keep the existing Actions cache and publish order unchanged.

### Not In Scope
- Cache replacement, remote deletion/pruning, or a historical archive migration.

### Open Questions
- None blocking implementation.
