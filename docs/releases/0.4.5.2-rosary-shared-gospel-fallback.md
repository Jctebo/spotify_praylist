## Scope

### Problem
- Daily Rosary can lose valid Gospel context when its independent Gospel fetch fails after the shared daily liturgical context already resolved the target day.
- The resulting prompt and priority metadata can describe a feast or memorial without Gospel text, and downstream generation may fall back unexpectedly.

### Audience
- Primary user: listeners praying the date-specific Rosary.
- Secondary stakeholders: maintainers of the shared liturgical-context and Rosary publish pipelines.

### Current Status Quo
- The publish runtime builds shared daily liturgical context, then separately builds Rosary day context.
- Rosary reads Gospel fields from its direct fetch only; shared Gospel citation/text/source fields are not used as a recovery source.
- The local calendar and authoritative USCCB data both provide Gospel readings for the reproduced September 2026 feast/memorial dates.

### Goal
- Preserve valid target-day Gospel citation and text across the shared-context handoff even when the Rosary-specific fetch is unavailable.
- Success criteria: feast/memorial Rosary context retains the shared Gospel, never silently downgrades to Gospel-free context when valid shared data exists, and regression tests cover direct-fetch failure plus generated/fallback output.

### Constraints
- Keep the General Roman Calendar and USCCB/offline lectionary authority unchanged.
- Preserve weekday mystery selection, observance precedence, deterministic fallback behavior, and existing audio/text contracts.
- Do not fabricate Gospel text or use a prior/future date as a substitute.

### Narrow Wedge
- Add shared-context Gospel fallback with explicit source/quality handling in Rosary context construction, plus focused tests for feast-day and missing-Gospel paths.

### Non-Goals
- Replacing Romcal, the USCCB reader, or the offline Douay-Rheims catalog.
- Rewriting model prompts or regenerating historical production audio in this source change.

### Risks And Unknowns
- The reported token `bsxkuo` is not present in the repository, so its exact production artifact requires deployment-side logs or artifact inspection; the source-level failure mode is nevertheless reproducible and testable.
- A cached/generated artifact may remain stale until the daily publish job is rerun after deployment.

### Recommended Next Step
- Implement the shared Gospel fallback, add regression coverage, then run the complete publish/test/review/ship workflow and validate a fresh date-scoped Rosary artifact.

## Research

- `jobs/publish/contracts.py` constructs shared daily context first, then calls `build_rosary_day_context`; the latter performs a second independent Gospel lookup.
- `jobs/publish/rosary_reflections.py` currently reads only `daily_context.gospel_*` after that second lookup and does not recover from `shared_theme` Gospel fields.
- `jobs/publish/daily_intro.py` already has a three-level live/USCCB/offline Gospel retrieval stack; the local reproduction resolved September 16, 2026 to Luke 7:31-35 from the offline cache.
- Romcal resolves September 14, 2026 as the Feast of the Exaltation of the Holy Cross and September 16, 2026 as the Memorial of Saints Cornelius and Cyprian. USCCB confirms a Gospel for both dates, including John 17:11b-19 for the September 16 memorial.
- No repository file or Git history entry contains `bsxkuo`; deployment artifact/log inspection remains a post-deploy validation concern.

## Plan

### Summary

- Preserve direct Rosary Gospel lookup when it succeeds, and use the shared daily context as a validated fallback when it does not.
- Keep fallback scoped to the exact target date, calendar, and locale so stale or foreign context cannot be used as Gospel input.

### What Already Exists

- `DailyLiturgicalContext.to_dict()` exposes `date`, `calendar`, `locale`, `gospelCitation`, `gospelSource`, and `gospelText`.
- Rosary priority ordering already prefers a major observance, then Gospel in Ordinary Time, and has deterministic generation fallback.
- Existing unit tests cover missing Gospel, feast precedence, shared themes, and model failure fallback.

### Architecture

```text
shared daily context (target date + Gospel)
              |
              v
Rosary direct lookup ---- success ----> direct Gospel
              |
            failure
              v
validated shared Gospel ---- valid ----> shared Gospel
              |
           invalid/missing
              v
Gospel-free context + existing observance/mystery fallback
```

- Add a small normalization/selection helper in `jobs/publish/rosary_reflections.py` that accepts direct context and shared mapping data.
- Direct data wins. Shared data is accepted only when its date equals the target date, its calendar/locale equal the effective values, and it contains non-empty Gospel text; citation/source remain optional metadata.
- No Gospel text is invented, and no future/past date is searched.

### Concrete Changes

- Modify `jobs/publish/rosary_reflections.py` in `build_rosary_day_context` to merge validated shared Gospel fields after direct lookup failure or incomplete direct context.
- Preserve existing calendar-row observance selection and priority ordering; include Gospel only when text is usable.
- Extend `tests/test_publish_rosary_reflections.py` with direct-fetch failure/shared-Gospel recovery, exact-date rejection, calendar/locale mismatch rejection, and direct-over-shared precedence cases.
- Extend context assertions as needed to prove feast/memorial context retains Gospel citation/text and does not trigger an unnecessary Gospel-free downgrade.
- Update this release artifact’s Progress, QA, and Release Notes after implementation and verification.

### UX And States

- No UI changes.
- Successful state: the Rosary metadata and meditation prompt contain the target-day Gospel and observance.
- Degraded state: if both sources lack valid target-day Gospel text, the existing feast/memorial or deterministic mystery-fruit path remains listener-facing and records the fallback reason.

### Failure Modes

- Direct Gospel lookup fails but shared context is valid: use shared Gospel and record its source.
- Shared context is stale, mismatched, or citation-only: reject it and retain the existing Gospel-free behavior.
- Both lookups fail: existing observance-aware deterministic fallback remains available.
- Model generation fails: existing structured-to-JSON-to-deterministic fallback chain remains unchanged.

### QA And Test Matrix

- Feast day with direct Gospel: direct Gospel wins over shared data.
- Feast/memorial with direct lookup exception and valid same-day shared Gospel: shared citation/text are retained and Gospel priority is available.
- Shared Gospel from another date, calendar, or locale: rejected.
- Citation-only shared context: rejected as Gospel text input.
- Both sources missing plus model failure: five valid deterministic decades still render.
- Run `python -m unittest tests.test_publish_rosary_reflections tests.test_publish_daily_liturgical_context tests.test_publish_daily_intro` and the full test command used by the repository.
