# Release 0.3.6.16 - Devotional Pages Audio Archive Isolation

## Scope

### Problem
- The `Daily Devotional Image (Remote OneDrive via rclone)` workflow deploys GitHub Pages after `Publish Prayer Audio` and can overwrite the public podcast surface with a Pages artifact that includes the restored `audio/` archive.
- The July 5, 2026 devotional-image run restored the publish-audio archive, rebuilt `podcast.xml`, uploaded a 2.59 GB Pages artifact, and received a GitHub warning that the artifact exceeded the 1 GB Pages limit.
- The same workflow rebuilds feed URLs without exporting `AUDIO_PUBLIC_BASE_URL`, so rebuilt podcast entries can point back at `https://jctebo.github.io/spotify_praylist/audio/...` instead of the intended R2 host `https://audio.orapronobis.media/...`.
- This matters now because the audio pipeline has moved MP3 delivery to R2 while GitHub Pages should remain a lightweight static site and feed host.

### Audience
- Primary user: the maintainer who needs scheduled audio and devotional-image workflows to publish safely without manual repair.
- Secondary stakeholders: podcast listeners, Spotify playlist refresh consumers, and devotional-image sync users who depend on stable public Pages and feed URLs.

### Current Status Quo
- `publish_audio.yml` restores/generates `docs/audio`, syncs audio to R2, then stages Pages by copying `docs/` and deleting `pages_artifact/audio`.
- `daily_devotional_image_remote.yml` restores `docs/audio`, copies `docs/` into `pages/`, rebuilds `pages/podcast.xml`, runs the site generator, and uploads the entire `pages/` tree without deleting `pages/audio`.
- The devotional-image workflow correctly refuses to publish a blank feed, but it does not protect against oversized Pages artifacts or R2 URL regression.
- The existing tests assert that `publish_audio.yml` excludes audio from Pages, but only lightly assert that the devotional-image workflow rebuilds a feed.

### Goal
- Ensure the devotional-image workflow can publish devotional image/site updates without disturbing the podcast feed or Pages artifact shape.
- Success criteria:
  - The devotional-image Pages artifact excludes `pages/audio` before upload.
  - The devotional-image feed rebuild preserves `AUDIO_PUBLIC_BASE_URL` behavior so podcast enclosures resolve to R2 in production.
  - The workflow still restores the local audio archive long enough to rebuild `podcast.xml` and generated prayer pages.
  - Tests fail if the devotional-image workflow reintroduces `audio/` into the Pages artifact or omits the production audio base wiring.

### Constraints
- Keep the fix narrow to workflow wiring and regression coverage; do not redesign Pages publishing or archive storage.
- Do not remove the audio archive restore from devotional-image publishing because the feed/site rebuild needs sidecars and archive metadata.
- Preserve `publish_audio.yml` as the authoritative audio generation and R2 sync workflow.
- Avoid changing public URL contracts beyond restoring the intended split: Pages hosts the site/feed; R2 hosts MP3 and audio sidecar files.
- Keep GitHub Pages artifacts below the practical 1 GB limit by excluding restored MP3/JSON archive payloads from the final upload.

### Narrow Wedge
- In `daily_devotional_image_remote.yml`, export `AUDIO_PUBLIC_BASE_URL: ${{ vars.AUDIO_PUBLIC_BASE_URL }}` at the job level so feed/archive URL helpers see the same production audio host as `publish_audio.yml`.
- In the devotional-image Pages build step, delete `pages/audio` after rebuilding `podcast.xml` and running `jobs.publish.site`, before `actions/upload-pages-artifact`.
- Strengthen `tests/test_publish_audio_pipeline.py` workflow-text coverage so it asserts:
  - the devotional-image workflow includes `AUDIO_PUBLIC_BASE_URL`;
  - the workflow removes `pages/audio`;
  - the removal happens in the Pages artifact path, not the restored `docs/audio` cache source;
  - the existing blank-feed guard remains.

### Non-Goals
- Do not change podcast rendering, TTS provider fallback, novena resolution, or Spotify playlist refresh behavior.
- Do not migrate Pages settings or switch from Actions deploy to branch deploy in this release.
- Do not alter R2 bucket layout or introduce deletion/sync changes for R2.
- Do not change devotional image generation, OneDrive folder layout, or public devotional image manifests.
- Do not try to download or inspect expired Pages artifacts as part of the fix.

### Risks And Unknowns
- The devotional-image workflow currently rebuilds feed items from local sidecars; existing historical sidecars may already contain older GitHub Pages audio URLs unless helpers normalize them during archive loading.
- Deleting `pages/audio` after site generation is safe only if generated pages use public URLs from sidecar/helper metadata, not local relative links that require packaged audio files.
- Pages may still show stale content briefly because of GitHub/Fastly caching, so verification should inspect both workflow logs and fetched headers/feed contents after deploy.
- The currently running `Publish Prayer Audio` workflow on July 6, 2026 may temporarily mask the bug until the next devotional-image publish runs.

## Research

## Plan

### Summary
- Build a narrow workflow hardening fix so `daily_devotional_image_remote.yml` can continue publishing devotional image/site updates without shipping the restored audio archive or regressing podcast enclosure hosts.
- The chosen approach reuses the existing `publish_audio.yml` artifact-staging pattern and existing audio URL helpers instead of adding new publishing logic.

### What Already Exists
- `.github/workflows/publish_audio.yml` already stages a Pages artifact by copying `docs/` into `pages_artifact/` and deleting `pages_artifact/audio` before upload.
- `.github/workflows/daily_devotional_image_remote.yml` already restores `docs/audio`, rebuilds `pages/podcast.xml`, runs `python -m jobs.publish.site --docs-root "${GITHUB_WORKSPACE}/pages"`, and uploads `${{ github.workspace }}/pages`.
- `jobs.publish.audio.load_published_audio_jobs()` already rewrites archive-derived `audio_url` values through `audio_public_url()`, which honors `AUDIO_PUBLIC_BASE_URL`.
- `tests/test_publish_audio_pipeline.py` already contains workflow-text tests for publish-audio R2 wiring and devotional-image feed rebuild behavior.

### Architecture
- Treat `docs/audio` as a private CI build input in the devotional-image workflow.
- Treat `pages/` as the deployable artifact root and remove `pages/audio` after all feed/site generation that needs archive metadata has completed.
- Keep URL generation centralized in `jobs.publish.audio`; expose the production R2 host through workflow environment wiring only.

```text
publish-audio cache -> docs/audio -> pages/podcast.xml + generated site
                                  -> pages/audio removed
                                  -> upload Pages artifact without MP3 archive

Public result:
GitHub Pages: index.html, prayers/, podcast.xml, devotional/
R2 audio host: *.mp3 and audio sidecar URLs
```

### Concrete Changes
- Edit `.github/workflows/daily_devotional_image_remote.yml`.
  - Add `AUDIO_PUBLIC_BASE_URL: ${{ vars.AUDIO_PUBLIC_BASE_URL }}` to the `jobs.image.env` block.
  - Add a pre-upload feed guard near the end of the `Build GitHub Pages artifact` step, after `python -m jobs.publish.site --docs-root "${GITHUB_WORKSPACE}/pages"`, that fails if `pages/podcast.xml` is missing, empty, or has no RSS item entries.
  - Add `rm -rf "${GITHUB_WORKSPACE}/pages/audio"` after that feed guard and before `Upload GitHub Pages artifact`.
- Edit `tests/test_publish_audio_pipeline.py`.
  - Strengthen `test_daily_devotional_image_workflow_rebuilds_podcast_feed_from_archive`.
  - Assert the devotional workflow exports `AUDIO_PUBLIC_BASE_URL`.
  - Assert the devotional workflow removes `"${GITHUB_WORKSPACE}/pages/audio"`.
  - Assert the upload path remains `${{ github.workspace }}/pages`.
  - Assert the audio archive restore still targets `docs/audio`.
  - Keep the existing blank-feed refusal assertion.
- No new files, migrations, or Python runtime changes are planned.

### Failure Modes
- `AUDIO_PUBLIC_BASE_URL` is missing or blank in GitHub Actions variables.
  - Detection: feed URLs fall back to GitHub Pages `/audio/...` in a workflow run.
  - User impact: podcast items may point at audio files not present in the Pages artifact.
- `pages/audio` is deleted too early.
  - Detection: feed/site rebuild logs fail or generated site lacks latest audio metadata.
  - User impact: devotional-image workflow fails before Pages upload because the blank-feed guard or site generation cannot find archive data.
- `podcast.xml` is accidentally missing or empty before upload.
  - Detection: the new pre-upload feed guard exits non-zero before `actions/upload-pages-artifact`.
  - User impact: the workflow fails closed and leaves the previous public feed in place instead of publishing a broken feed.
- `pages/audio` is not deleted before upload.
  - Detection: upload logs show a large artifact or GitHub warns that the artifact exceeds 1 GB.
  - User impact: Pages deploy may fail or overwrite the podcast surface with an oversized artifact.
- Historical sidecars contain stale public URLs.
  - Detection: rebuilt `podcast.xml` contains `github.io/spotify_praylist/audio/` when `AUDIO_PUBLIC_BASE_URL` is set.
  - User impact: podcast apps receive stale or broken enclosure URLs.
