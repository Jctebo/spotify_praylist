# Release 0.3.6.6: Prayer Page Text Sidecar

## Scope

### Problem
- Prayer pages currently help listeners find audio, feeds, and archive links, but they do not show the actual prayer text.
- The publish-audio sidecars already preserve ordered fragment/resume metadata, so hiding that content on the generated pages leaves the website less useful than the data it already publishes.
- The recently disabled Notion text workflow means GitHub Pages is the safer first surface for readable prayer text.
- The home page is organized by source type (`Ora Pro Nobis` vs. `Spotify prayers`) instead of by the actual prayer playlists people use during the day.
- The site can expose website-enabled contracts that are not active in a Spotify playlist, which makes the directory feel broader than the active praylist experience.
- Daily Novenas currently behave like a single aggregate resolver surface instead of resolving individual novena episodes cleanly.

### Audience
- Primary user: someone opening an active praylist entry who wants to choose the right Morning, Daily, or Night prayer and read or follow along with the latest generated prayer where text exists.
- Secondary stakeholders: the repo maintainer validating generated prayer output, Spotify playlist membership, sidecar metadata, and Pages publication without depending on Notion.

### Current Status Quo
- `jobs/publish/site.py` builds `docs/index.html`, `docs/prayers/index.json`, and one static `docs/prayers/<slug>/index.html` page per enabled prayer website entry.
- Site generation already calls `load_published_audio_jobs`, matches sidecars by `contract_id` or `entry_id`, and attaches latest audio metadata to Ora Pro Nobis entries.
- The per-prayer page renders summary text and links only; it does not expose sidecar `fragments`, `resume_markers`, or any readable prayer body.
- Audio sidecars under `docs/audio/*.json` can include ordered fragment data, labels, sanitized text, render context, and resume markers.
- The generated directory currently groups entries as `Ora Pro Nobis` and `Spotify prayers`, even though the runtime playlist definitions are `Morning`, `Midday`, `Night`, and `Sunday`.
- Playlist definitions are thin identity files; active membership is determined through Spotify queue contracts plus the Notion playlist membership/order path.
- Daily Novenas are tied to the Spotify playlist integration but need an individual-episode resolution model so the site and playlist can point at the specific novena episode, not only the generic daily novena family.

### Goal
- Add a readable `Prayer text` section to generated Ora Pro Nobis prayer pages when the latest matching sidecar contains enough text data.
- Keep the website aligned with the sidecar process by deriving page text from the same sidecar-backed latest-audio data instead of creating a separate website-only prayer-text source.
- Make the home page use one primary action per card: open the prayer page. Listening or Spotify navigation should happen inside the prayer page alongside the available text.
- Reorganize the home page around praylist groups instead of source groups:
  - `Morning Praylist`
  - `Daily Praylist`
  - `Night Praylist`
- Include Sunday homilies in the praylist-oriented home-page organization rather than a separate source-type group.
- Limit generated prayer pages and home-page entries to active contracts that are tied to Spotify playlist membership.
- Make Daily Novenas resolve to individual episodes cleanly enough for praylist/site surfaces to link to the intended novena episode.
- Preserve static site generation: no client-side fetch requirement, no Notion dependency, and no runtime service.
- Success criteria:
  - A sidecar with ordered fragments renders a readable, escaped prayer-text section on the matching prayer page.
  - The generated manifest exposes enough structured latest-prayer metadata for audit/debug without duplicating large unsafe blobs unnecessarily.
  - Home-page cards route through one `Open prayer` action instead of splitting users between page and audio/Spotify actions.
  - Prayer pages provide the player/link surface: sidecar-backed entries show a player or listen action plus text, and external Spotify entries show a Spotify action plus page context.
  - The home page groups entries as Morning, Daily, and Night Praylists instead of Ora Pro Nobis vs. Spotify.
  - Sunday homilies remain discoverable in the praylist layout.
  - Inactive or playlist-unbound website metadata does not create generated prayer pages.
  - External Spotify-only active praylist entries remain link-focused and do not claim generated text.
  - Daily Novenas resolve individual current episodes cleanly instead of surfacing only an aggregate family target.
  - Missing, legacy, or fragmentless sidecars degrade gracefully to the current page behavior.
  - Focused tests cover sidecar text rendering, ordering, escaping, missing data, active-contract filtering, praylist grouping, individual Daily Novena resolution, and manifest shape.

### Constraints
- Use the existing publish-audio sidecar/archive path as the source of truth for generated daily prayer text.
- Do not re-enable `.github/workflows/publish_text.yml` or depend on the disabled Notion text workflow.
- Do not change audio generation semantics, Spotify resolution, or podcast RSS behavior.
- Keep generated pages static and compatible with GitHub Pages.
- Avoid large unrelated design rewrites; the page should gain a durable content section within the existing website generator.
- Do not create competing home-page CTAs that bypass the prayer page; the detail page is the single place where prayer playback/linking and text meet.
- Preserve safe HTML escaping for all text derived from JSON sidecars.
- Treat Spotify playlist membership as the inclusion boundary for generated site entries; if the membership source is unavailable during static generation, fail closed or use a clearly checked-in active contract fixture rather than publishing inactive pages.
- Keep the public language as `Praylist`, including `Morning Praylist`, `Daily Praylist`, and `Night Praylist`.

### Narrow Wedge
- Extend `load_published_audio_jobs`/site attachment so the latest matching audio sidecar can provide a normalized ordered text payload for Pages.
- Replace source-type home-page sections with praylist sections backed by active Spotify playlist membership:
  - `Morning Praylist` for morning playlist entries.
  - `Daily Praylist` for midday/daily entries and Sunday homilies.
  - `Night Praylist` for night playlist entries.
- Filter generated pages to contracts that are active in at least one Spotify playlist.
- Simplify home-page cards to one action that opens the generated prayer page.
- Render a `Prayer text` section on Ora Pro Nobis detail pages from sidecar fragments or a clearly defined sidecar text field if present.
- Add the listening surface to the prayer page: prefer an HTML audio player for published MP3 URLs, and use a Spotify button for external Spotify-only entries.
- Include labels from fragment/resume metadata where helpful, while avoiding duplicated repeated labels that make Rosary or response-heavy prayers hard to scan.
- Update the Daily Novenas Spotify/site resolution so individual novena episodes can be resolved and linked cleanly.
- Add regression tests in the publish-site/audio-sidecar area using small fixture sidecars.
- Regenerate the checked-in `docs/` site output if implementation changes the committed generated pages.

### Non-Goals
- Re-enabling Notion prayer-text publishing.
- Building a rich interactive transcript player, synchronized audio highlighting, or client-side sidecar browser.
- Providing direct listen/Spotify buttons on home-page cards that bypass the prayer page.
- Publishing complete generated text for external Spotify-only prayer entries.
- Showing website-enabled contracts that are not active in a Spotify playlist.
- Refactoring all publish contract rendering, audio fragment generation, or sidecar schema beyond what the page-text surface needs.
- Changing the public podcast RSS feed contract.

### Risks And Unknowns
- Some sidecars may omit fragment `text` or may contain legacy shapes; the implementation must not break page generation for those episodes.
- Rosary and other repetitive prayers could produce very long pages if every fragment is rendered naively.
- The sidecar shape may contain TTS-oriented text that is correct for audio but less polished for reading; this release should prefer faithful sidecar alignment over editorial rewriting.
- Generated checked-in pages may be noisy if many current sidecars exist locally or after a remote publish.
- Active Spotify playlist membership currently depends on Notion state, so implementation must decide how static site generation gets a deterministic active-contract view in local tests and GitHub Actions.
- Mapping `Midday` plus Sunday homily entries into the user-facing `Daily Praylist` may need an explicit grouping rule so the public labels stay stable even if playlist keys remain `midday` and `sunday`.
- Individual Daily Novena resolution may require additional metadata in novena sidecars or Spotify lookup results to avoid ambiguous same-day novena matches.

### Recommended Next Step
- Run `/plan-astack` to define the exact active-contract source, praylist grouping rules, Daily Novena individual episode resolution model, sidecar-to-page data shape, rendering rules for long/repetitive fragments, tests, and regeneration/verification commands before coding.

## Research

### Scope Baseline
- Add readable prayer text to generated prayer pages from published audio sidecars.
- Rework the website home page from source-based groups to `Morning Praylist`, `Daily Praylist`, and `Night Praylist`.
- Simplify home-page cards to one action that opens the generated prayer page.
- Limit generated entries/pages to contracts active in Spotify playlist membership.
- Make Daily Novenas resolve cleanly as individual episodes instead of only as an aggregate `Daily Novenas` surface.

### Relevant Files
- `jobs/publish/site.py`: Owns static website entry loading, metadata validation, manifest shape, source-group home page rendering, detail page rendering, and generated `docs/prayers/` cleanup.
- `jobs/publish/audio.py`: `load_published_audio_jobs` reads `docs/audio/*.json` sidecars and already exposes `fragments` and `resume_markers` to the website layer.
- `jobs/publish/contracts.py`: Builds publish text/audio jobs, audio fragments, and resume markers for Morning Prayer, Auxilium Christianorum, Marian Antiphon, Daily Rosary, and Daily Reflection.
- `jobs/novena_contracts/audio.py`: Builds and writes individual novena episode sidecars with `episode_id`, `family_id`, `contract_id`, `title`, `published_date`, and fragment text.
- `jobs/novena_contracts/pipeline.py`: Resolves active novena runtimes, seeds short-form novena days, renders novena audio jobs, and publishes them into the shared audio/RSS archive.
- `jobs/playlist/spotify_contracts.py`: Loads Spotify queue contracts, website metadata, optional playlist `contracts`, and playlist identity definitions.
- `jobs/playlist/refresh_playlist.py`: Owns Notion-backed active playlist membership/order and the Spotify queue-building path.
- `config/spotify/playlists/*.json`: Defines `morning`, `midday`, `night`, and `sunday` playlist identities; currently no checked-in active contract lists are present.
- `config/spotify/contracts/daily-novenas.json`: Current Daily Novenas Spotify lookup matches `novena` plus date, which can return multiple same-day episodes.
- `tests/test_publish_site.py`: Existing website regression suite for manifest/page generation, latest audio attachment, slug merging, stale-page cleanup, and workflow wiring.
- `tests/test_publish_audio_pipeline.py`: Existing sidecar/audio regression suite with fixture sidecars and published-audio loader coverage.
- `tests/test_refresh_job.py` and `tests/test_refresh_job_contract_path.py`: Existing coverage for Notion membership grouping, Spotify episode lookup, and Daily Novenas queue flattening.

### Current System Map
- Website generation is contract-driven but source-oriented:
  - Publish contracts become `source="publish"` entries from `contract.metadata.website`.
  - Spotify queue contracts become `source="spotify"` entries from top-level `website`.
  - Entries are grouped by `group`: `ora-pro-nobis` or `external-spotify`.
  - Home cards currently render two actions: `Open prayer` plus a secondary direct listen/Spotify/feed action.
  - Matching publish/Spotify entries can merge only when they share `slug` and `prayer_family`.
- Latest audio attachment is already sidecar-backed:
  - `load_published_audio_jobs` sorts sidecars newest-first and returns title/date/audio URL plus `fragments` and `resume_markers`.
  - `_attach_latest_audio` currently copies only `title`, `episode_id`, `published_date`, and `audio_url` onto each matching site entry.
  - Matching is by `contract_id` or `entry_id` against `related_contracts`/`related_entry_ids`.
- Active Spotify membership lives outside the site generator:
  - `build_notion_playlist_memberships` fetches checked Notion rows, matches `Name` to `SpotifyQueueContract.notion_name`, requires populated `Output Folder`, validates it against playlist key/name, and sorts by `Order`.
  - `build_queue_for_playlist_definition` only receives already-ordered active contracts.
  - The static site generator currently does not call Notion and therefore cannot know active membership unless a deterministic artifact or checked-in playlist contract list is added.
- Playlist identity is checked in:
  - `morning`, `midday`, `night`, and `sunday` exist as playlist definition files.
  - The loader already supports an optional `contracts` array on playlist definitions, but the current playlist files do not use it.
- Daily Novenas are already individual in the publish/archive layer:
  - Novena audio jobs use episode IDs like `{date}-{contract_id}-day-{active_day}`.
  - Sidecars include individual `family_id`, `contract_id`, `title`, `published_date`, and fragment text.
  - RSS publishes those individual jobs.
- Daily Novenas are aggregate in the Spotify lookup layer:
  - The Spotify queue contract uses `required_name_terms: ["novena"]` plus date formats.
  - Existing tests intentionally expect a Daily Novenas contract to flatten multiple matched episode URIs into one playlist slot.

### Reuse Opportunities
- Reuse `load_published_audio_jobs` as the sidecar source instead of parsing JSON directly in `site.py`.
- Extend `_attach_latest_audio` to attach a normalized `latest_prayer_text` payload derived from returned `fragments`/`resume_markers`.
- Reuse the existing sidecar `fragments` shape for display sections: `label`, `text`, `fragment_key`, `kind`, and repeat metadata are already present.
- Reuse `SpotifyPlaylistDefinition.contracts` as the simplest deterministic active-contract source for static site generation, if playlist JSON files are allowed to become the checked-in active membership mirror.
- Reuse `normalize_spotify_contract_key`/`normalize_publish_key` to map Spotify contract keys, publish contract IDs, entry IDs, and website slugs without inventing a new identity normalizer.
- Reuse current site tests with temp publish/Spotify contract dirs and fixture sidecars; add playlist fixture dirs to cover active filtering and Praylist grouping.
- Reuse `_primary_href` logic on detail pages, but remove it from home-card CTA rendering so navigation consistently lands on the prayer page first.
- Reuse Spotify episode lookup tests to tighten Daily Novenas behavior without touching the Spotify API integration surface.

### External References
- No new external APIs or libraries are required for the website-side work.
- Spotify episode lookup behavior remains constrained by the existing Spotify Web API calls already wrapped in `refresh_playlist.py`.
- GitHub Pages stays a static output target through existing workflows.

### Constraints
- `Publish Prayer Text` remains disabled; this release should not depend on Notion text publication.
- Website generation currently runs in `publish_audio.yml` and `daily_devotional_image_remote.yml`; any new active-membership dependency must work in both workflows.
- Calling Notion from `jobs.publish.site` would introduce a secret/runtime dependency to a static site build that currently works from checked-in contracts and sidecars.
- A checked-in active contract list would be deterministic and testable, but it creates a second source of truth unless the refresh path also uses or validates it.
- Current generated `docs/prayers/index.json` has 24 entries and source groups; changing grouping/filtering will require generated output updates.
- The worktree has no checked-in `docs/audio/` sidecars, so sidecar text rendering must be verified through test fixtures and any regenerated docs will not show live text unless local audio sidecars exist.

### Risks
- Active membership source is the biggest architectural risk: using Notion directly makes static generation brittle; using checked-in playlist contracts risks drift from Notion-owned playlist membership.
- Daily Novenas may legitimately publish multiple individual episodes for one date; forcing a single URI would lose content if the product intent is "all active novenas," while leaving it aggregate fails the requested clean individual resolution.
- Rendering every sidecar fragment can make Rosary and repeated-response pages too long or repetitive; display normalization needs to collapse or group repeated fragments without falsifying the sidecar source.
- Merged publish/Spotify entries may need stronger identity mapping: e.g. `morning-prayer-elevenlabs` publish contract corresponds to `morning-prayer` Spotify contract, not an identical contract ID.
- Source group labels are baked into `VALID_GROUPS`, `GROUP_LABELS`, CSS expectations, manifest tests, and checked-in pages; changing to Praylists touches both data and HTML tests.
- Home-card action tests will need to change because direct secondary listen/Spotify buttons should move from cards to detail pages.

### Assumptions To Validate
- Recommended active membership model: add checked-in `contracts` arrays to `config/spotify/playlists/*.json` and make both site generation and playlist refresh validate/use them as the deterministic active contract list, with Notion either remaining the live override or being checked against those arrays.
- Recommended public grouping: map `morning` to `Morning Praylist`, `midday` plus `sunday` to `Daily Praylist`, and `night` to `Night Praylist`.
- Sunday homilies should appear under `Daily Praylist`, not a fourth Sunday group.
- Daily Novenas should expose/link individual sidecar episodes on the site; Spotify playlist behavior needs a decision between preserving all same-day novena URIs or creating separately addressable novena contracts/entries.
- It is acceptable for external Spotify entries to remain link-only detail pages, with prayer text only for sidecar-backed Ora Pro Nobis episodes.
- Detail pages are the canonical action surface: sidecar-backed entries should present an audio player/listen action and text; external Spotify entries should present a Spotify button and page context.

### Unknowns
- Whether Notion should remain the ultimate source of active playlist membership after this release, or whether checked-in playlist `contracts` should become authoritative.
- The exact active contract list and ordering for `Morning Praylist`, `Daily Praylist`, and `Night Praylist`.
- Whether Daily Novenas should appear as one page with multiple individual episode cards, or as separate generated pages per active novena episode.
- How aggressively repeated fragments should be collapsed for Rosary and long novena content.
- Whether to render a native `<audio controls>` player whenever a latest MP3 URL exists, or keep a styled listen button only. Planning should prefer the player because the page is now the prayer surface.

### Recommended Direction
- In `/plan-astack`, choose a deterministic active-membership bridge before coding. The least risky technical path is to populate playlist `contracts` arrays and teach `site.py` to read those arrays for active filtering/grouping while preserving tests around Notion membership behavior.
- Update `site.py` around four small seams: active praylist entry loading, one-action card rendering, prayer-page playback actions, and sidecar text extraction.
- Treat Daily Novenas as a special sidecar-backed collection: surface individual latest novena episodes from sidecars on the Daily Novenas page and tighten Spotify lookup tests so individual episodes are identifiable rather than an opaque aggregate.
- Plan focused tests first: active filtering/grouping, publish+Spotify identity merge, sidecar text rendering/escaping, long repeated fragment handling, and Daily Novena individual episode discovery.

## Plan

### Summary
- Build a Praylist-first static website surface:
  - Home page sections become `Morning Praylist`, `Daily Praylist`, and `Night Praylist`.
  - Home-page cards have one action: open the prayer page.
  - Generated prayer pages are filtered to contracts present in checked-in Spotify playlist `contracts` arrays.
  - Prayer pages host playback/navigation and text: Ora Pro Nobis pages render an audio player/listen surface plus readable sidecar text; external Spotify pages render a Spotify action.
  - Daily Novenas stays one durable praylist entry/page, but that page surfaces individual latest novena episodes from sidecars.
- Chosen approach: use `config/spotify/playlists/*.json` `contracts` arrays as the deterministic active-membership bridge for website generation. This avoids adding Notion/API dependencies to GitHub Pages builds while reusing an existing playlist definition field.
- Chosen UX approach: make the home page a clean table of contents and make detail pages the complete prayer surface.

### What Already Exists
- `jobs/publish/site.py` already builds the static site, manifest, page HTML, and stale generated-page cleanup.
- `jobs/publish/audio.py::load_published_audio_jobs` already returns sidecar-backed `fragments` and `resume_markers`.
- `jobs/playlist/spotify_contracts.py` already parses optional playlist `contracts` arrays and validates contract keys when loading playlist definitions.
- `jobs/playlist/refresh_playlist.py` already owns live Notion membership/order for Spotify playlist writes.
- `jobs/novena_contracts/audio.py` already writes individual novena sidecars with `family_id`, `contract_id`, `episode_id`, `title`, `published_date`, and fragment text.
- Existing tests cover website generation, sidecar loading, playlist membership grouping, Spotify lookup behavior, and novena sidecar output.

### Architecture
- Static site generation will read four sources:
  - Spotify playlist definitions for active contract membership and public Praylist grouping.
  - Spotify queue contracts for playlist-facing entries and external links.
  - Publish contracts for sidecar-backed Ora Pro Nobis page metadata/text identity.
  - Published audio sidecars for latest audio, prayer text, and individual novena episodes.

```text
config/spotify/playlists/*.json
  contracts[] by playlist key
        |
        v
jobs.publish.site active praylist index
        |
        +--> Spotify contracts ----------+
        |                                |
        +--> Publish contracts ----------+--> merged site entries
        |                                |
        +--> docs/audio/*.json sidecars -+--> latest audio/text/novena episodes
                                         |
                                         v
                           docs/index.html + docs/prayers/*
```

- Public Praylist group mapping:
  - `morning` -> `Morning Praylist`
  - `midday` -> `Daily Praylist`
  - `sunday` -> `Daily Praylist`
  - `night` -> `Night Praylist`
- Entry identity mapping:
  - Prefer Spotify contract keys as the active membership identity.
  - Add a small site-local alias map for generated entries whose publish IDs differ from Spotify keys:
    - `morning-prayer` -> publish contract `morning-prayer-elevenlabs`, entry `morning-prayer-elevenlabs`
    - `auxilium-christianorum` -> publish contract/entry `auxilium-christianorum`
    - `daily-rosary` -> publish contract `rosary`, entry `rosary`
    - `daily-examen` -> publish contract/entry `daily-reflection`
    - `daily-novenas` -> novena sidecars with `contract_type=novena_feast_rule`
    - Marian Antiphon Spotify keys (`angelus-morning`, `angelus-midday`, `angelus-evening`) -> publish contracts `marian-antiphon-angelus` and `marian-antiphon-regina-caeli`
- Sidecar text model:
  - Convert sidecar `fragments` into ordered display sections with `label`, `text`, `fragment_key`, and `kind`.
  - Escape all sidecar text in HTML.
  - Collapse repeated adjacent sections with identical label/text into one display row with a repeat count.
  - If no fragment text exists, omit the `Prayer text` section and keep existing link-only behavior.
- Daily Novenas model:
  - Do not create one page per historical novena sidecar in this release.
  - Keep the `daily-novenas` page as the stable praylist entry.
  - On that page, show an `Individual novena episodes` section from latest sidecars where `contract_type == "novena_feast_rule"`, grouped by `published_date` and sorted newest-first.
  - Spotify queue behavior can continue returning multiple same-day novena URIs, but tests should assert the resolver can distinguish individual titles/URIs and that the site does not present Daily Novenas as a single opaque audio item when individual sidecars exist.
- Action model:
  - `_entry_card` renders only one button linking to `prayers/<slug>/`.
  - `_prayer_page_html` owns all playback/outbound actions.
  - If `latest_audio.audio_url` exists, render a native `<audio controls>` player with that URL plus a fallback listen/download link.
  - If `external_url` exists, render one Spotify button on the detail page.
  - Feed/archive links can remain secondary detail-page links, not home-card actions.

### Failure Modes
- Playlist `contracts` arrays omit a real active item:
  - Detection: site tests and manual manifest review.
  - User impact: entry/page disappears from the directory until the array is corrected.
- Playlist `contracts` arrays drift from Notion:
  - Detection: future validation can compare Notion membership against checked-in arrays; this release documents the risk.
  - User impact: website and Spotify playlist may disagree.
- Sidecar has malformed or missing fragments:
  - Detection: fixture tests and site generation warnings/errors for invalid JSON.
  - User impact: page remains link-only instead of failing the whole site.
- Alias mapping is incomplete:
  - Detection: active generated prayer has no latest text/audio despite a matching sidecar.
  - User impact: generated prayer page lacks the new prayer text section.
- Daily Novenas multiple same-day episodes remain ambiguous in Spotify:
  - Detection: refresh-job tests and sidecar/title review.
  - User impact: playlist can still include all matched novenas, while the website provides individual links.
- Generated Pages output removes too many pages:
  - Detection: manifest count and generated docs diff review.
  - User impact: hidden pages for contracts not listed as active.
