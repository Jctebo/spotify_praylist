# Release 0.0.5.6 - morning-prayer-redesign

- Status: Draft
- Last Updated: 2026-03-23

## Scope

### Problem
- Morning Prayer has accumulated repeated failures because its current design mixes live Notion data, durable keys, migration artifacts, and workflow preflight rules in one fragile path.
- The system has been patched multiple times to chase live-data drift, legacy aliases, and special-fragment edge cases.
- We need to redesign Morning Prayer first, in isolation, before generalizing any of the patterns to the rest of the page-audio system.

### Audience
- Primary user: the maintainer who owns the Morning Prayer content and GitHub Actions workflow.
- Secondary stakeholders: anyone depending on Morning Prayer audio and page content generation completing automatically.

### Current Status Quo
- Morning Prayer is implemented as a special case inside the broader page-audio system.
- The workflow depends on Notion relations, durable fragment keys, migration helpers, and contract checks all agreeing at runtime.
- Live Notion data has already shown split records, legacy aliases, and special-fragment drift.
- Each repair has reduced one failure mode while leaving the underlying design more complicated.

### Goal
- Redesign Morning Prayer as a clear, bounded subsystem with a stable content model and explicit lifecycle rules.
- Make the live-data shape understandable, predictable, and testable before it reaches the page-audio renderer.
- Preserve strict validation while reducing the need for repeated ad hoc compatibility fixes.

### Constraints
- Start with Morning Prayer only; do not redesign the whole page-audio stack at once.
- Keep the daily workflow operational during the transition.
- Preserve the ability to run in GitHub Actions without manual intervention.
- Any new design must remain compatible with the existing Notion-backed workflow until migration is complete.
- Migration happens one Opus Dei page at a time, starting with Morning Prayer; once a page is fully moved, its old code paths and Notion config can be retired.

### Narrow Wedge
- Define a Morning Prayer-specific architecture that separates source content, canonical identifiers, relation wiring, and runtime rendering.
- Treat special fragments like `Monthly Intention` and `Daily Novena Audio` as first-class parts of the model instead of one-off exceptions.
- Make the migration and validation path explicit so the system can tell the difference between live-data repair and actual content loss.

### Non-Goals
- Do not redesign every novena or devotional workflow in the repo.
- Do not rewrite the Notion database from scratch.
- Do not weaken validation just to make the workflow pass.
- Do not solve UI/UX polish, branding, or unrelated playlist behavior in this pass.

### Risks And Unknowns
- A new architecture can accidentally overfit the current Notion shape if we do not define a clean canonical model first.
- There may be more Morning Prayer special fragments than the current failure logs exposed.
- We still need to complete the Morning Prayer move before we can retire the old code paths and Notion config.

### Recommended Next Step
- Use `/research-astack` to map the current Morning Prayer code paths, data model, and migration boundaries that the new architecture should replace.

## Research

### Baseline
- Morning Prayer is still the most fragile path in the page-audio workflow, and the current redesign is intentionally scoped to that one page first.
- The new contract is resolver-first: one ordered resolver list per Opus Dei record, with default-collapsible page sections and metadata that routes text into page content, audio, or playlist creation.
- The migration story is page-by-page, starting with Morning Prayer, and the old code paths and Notion config for a page are retired only after that page is fully moved.

### Architecture Direction
- Morning Prayer should be driven by a repo-local JSON config file for that one Opus Dei record.
- The JSON file should contain one ordered `resolvers` section and no extra layering for templates, content, or audio.
- The existing `jobs/notion/generate_page_audio.py` cache and library code already handles audio reuse, so the new contract should preserve that runtime behavior without adding a new reuse field.
- `Daily Novena Audio` remains a code-driven resolver entry that generates audio up front when a feast day window is approaching.
- `Monthly Intention` remains a month-rotated resolver that selects the right text from repo files.
- `Random Intention` remains a generated resolver entry that can target both page content and audio.
- `Spotify` stays as the final resolver and can target page content plus playlist creation.
- Audio output still needs to remain materialized as files so the existing OneDrive copy/upload flow can continue to work.
- The current live-code integration points are the Morning Prayer assembly path in `jobs/notion/generate_page_audio.py`, the migration/preflight path in `scripts/migrate_page_audio_notion_schema.py`, and the regression tests under `tests/test_page_audio_job.py` and `tests/test_migrate_page_audio_schema.py`.

### Pointer
- Full architecture is documented in `docs/architecture/morning-prayer-redesign.md`.

## Plan

### Summary
- Build a repo-local, Morning Prayer-specific JSON contract that drives one ordered resolver list per Opus Dei record.
- Keep the existing Morning Prayer output behavior intact: resolvers still produce page content, audio files, and playlist creation side effects, and audio must remain materialized for OneDrive upload.
- Migrate Morning Prayer first, then retire the old Morning Prayer Notion config and code paths only after the new contract works end to end.

### What Already Exists
- `jobs/notion/generate_page_audio.py` already handles Morning Prayer assembly, audio reuse, render hashes, and file materialization for uploads.
- `scripts/migrate_page_audio_notion_schema.py` already handles Morning Prayer preflight / relink behavior for live Notion data.
- `tests/test_page_audio_job.py` and `tests/test_migrate_page_audio_schema.py` already cover the fragile Morning Prayer cases we need to preserve.
- `docs/architecture/morning-prayer-contract.schema.json` already defines the contract shape at a high level.

### Architecture
- One config file per Opus Dei record, starting with `config/morning-prayer/morning-prayer.json`.
- The Morning Prayer config contains one ordered `resolvers` array and no separate template/content/audio top-level sections.
- Each resolver carries its own metadata, including destinations like `page_content`, `audio`, and `playlist_creation`.
- Collapsible behavior is implicit default behavior in Notion, not a contract field.
- Audio reuse stays in the runtime cache/library layer and continues to produce files for the OneDrive copy/upload flow.

ASCII flow:
```text
config/morning-prayer/morning-prayer.json
        |
        v
resolver normalization
        |
        +--> page content blocks -> Notion page body
        |
        +--> audio fragments -> cached files -> OneDrive copy/upload
        |
        +--> playlist resolver -> Spotify playlist creation
```

### Concrete Changes
- Add `config/morning-prayer/morning-prayer.json` as the first repo-local contract file.
- Add any supporting resolver-content files under `config/morning-prayer/content/` only if the Morning Prayer config references repo text files directly.
- Update `jobs/notion/generate_page_audio.py` to load the Morning Prayer contract and resolve the ordered `resolvers` list before building page content/audio.
- Keep the current cache/library persistence path in `jobs/notion/generate_page_audio.py` so audio output still lands as files for OneDrive upload.
- Update `scripts/migrate_page_audio_notion_schema.py` only where it needs to understand the new Morning Prayer contract shape during the transition.
- Extend `tests/test_page_audio_job.py` with contract-loading and resolver-order regressions.
- Extend `tests/test_migrate_page_audio_schema.py` with Morning Prayer contract compatibility checks.

### UX And States
- Morning Prayer should continue to generate the same visible page sections and audio output from the user’s perspective.
- During migration, missing or malformed resolver metadata should fail before rendering with a precise contract error.
- If a resolver can produce audio, the job must still leave an audio file available for OneDrive copying.
- Spotify resolver behavior should continue to create or update the target playlist from the same Morning Prayer contract.

### Failure Modes
- Resolver order drift: Morning Prayer sections appear in the wrong sequence. Detect via config validation and regression tests.
- Missing audio file output: the page/audio builds but OneDrive cannot copy anything. Detect via export-file assertions and workflow logs.
- Contract/runtime mismatch: the JSON file says one thing, but `generate_page_audio.py` still expects the old Morning Prayer shape. Detect via unit tests that load the contract and build the plan.
- Migration mismatch: live Notion rows still need old repair rules while the new contract is active. Detect via `tests/test_migrate_page_audio_schema.py` and live workflow runs.

### Rollout Notes
- Ship Morning Prayer first as the pilot page.
- Keep the old Morning Prayer code paths until the new contract is validated end to end.
- Retire the old Morning Prayer Notion config only after the new contract and output path are stable.
- No new database schema is introduced.
