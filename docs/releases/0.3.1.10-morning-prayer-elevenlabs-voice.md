## Scope

### Problem
- Morning Prayer currently publishes with a single shared TTS voice configuration.
- We need a configurable list of TTS providers, ordered by preference, so the runtime can try provider 1, then provider 2, and so on.
- You want to use a custom ElevenLabs voice that you trained yourself, without replacing the existing Morning Prayer voice for everyone.
- Why now: this is the narrowest safe way to test your custom voice in the API while preserving the current output as a fallback and making the provider preference explicit.

### Audience
- Primary user: the maintainer who wants a Morning Prayer variant voiced with a custom ElevenLabs model.
- Secondary stakeholders: listeners who may compare the new voice against the existing Morning Prayer audio.
- Secondary maintainers: future operators who need to understand which Morning Prayer contract uses which provider and voice.

### Current Status Quo
- Morning Prayer uses one publish contract at `config/publish/contracts/morning-prayer.json`.
- That contract currently routes audio through the repo's existing TTS settings and a single `voice` value.
- The publish path treats `audio_config` as the source of truth for TTS settings, but it does not appear to have a provider switch or ElevenLabs-specific voice identity yet.
- As a result, there is no dedicated side-by-side Morning Prayer voice variant in the repo today.

### Goal
- Add a separate Morning Prayer audio variant that uses your custom ElevenLabs voice.
- Add a configurable TTS provider preference list so the runtime can choose the first available provider from an ordered set.
- Keep the existing Morning Prayer contract intact as the default voice.
- Make the new variant observable as a distinct published output, not an overwrite of the current one.
- Success criteria:
  - the repo can represent an ElevenLabs-backed Morning Prayer contract cleanly
  - the new contract can point at your custom voice identity
  - the variant publishes side by side with the current Morning Prayer output
  - reruns remain deterministic and do not blur the two voices together

### Constraints
- Preserve the current Morning Prayer contract unless the new variant proves it needs a schema change.
- Avoid a broad audio-provider migration if a contract-level provider preference list is sufficient.
- Keep the first wedge limited to Morning Prayer only, not Rosary or the rest of the publish stack.
- The implementation should fit the existing publish contract model, or the smallest extension of it, so the change stays testable.

### Narrow Wedge
- Add one new Morning Prayer contract or contract variant that explicitly declares an ordered list of TTS provider preferences, with ElevenLabs included as a preferred option.
- Teach the publish layer how to interpret that provider list without disturbing the existing OpenAI-backed Morning Prayer path.
- Keep the original Morning Prayer contract available as the control case.
- If possible, use the same content generation and only vary the audio backend; do not expand the scope into prompt rewriting or content redesign.

### Non-Goals
- Do not replace the current Morning Prayer voice for all users.
- Do not redesign the publish contract format beyond what is needed to carry the provider and voice identity.
- Do not expand this to Rosary, novenas, or other prayer families yet.
- Do not build a voice management UI in this iteration.
- Do not optimize or rework the audio caching system unless the provider switch forces it.

### Risks And Unknowns
- It is not yet clear whether the current audio schema can support a provider preference list cleanly, or whether the change needs a new contract shape.
- ElevenLabs may require a different set of fields than the current `model` / `voice` / `format` audio config exposes.
- A side-by-side variant could accidentally create duplicate episode identities or ambiguous feed titles if the naming strategy is not explicit.
- If the custom voice API has rate limits, authentication differences, or request-size constraints, the new path may need provider-specific error handling.
- We do not yet know whether the strongest wedge is a dedicated Morning Prayer contract file, a reusable audio-provider abstraction, or both.

### Recommended Next Step
- Use `/research-astack` to map the current publish audio contract shape, determine the smallest way to represent an ordered TTS provider preference list plus custom ElevenLabs voice identity, and confirm whether a separate Morning Prayer contract or a shared provider abstraction is the cleaner wedge.

## Research

### Scope Baseline
- Add a side-by-side Morning Prayer voice variant that can use a custom ElevenLabs voice.
- Introduce a configurable TTS provider preference list so the runtime can try providers in order.
- Keep the current Morning Prayer output unchanged as the default path.

### Decisions From Follow-Up
- Model provider preference as an ordered array of provider objects.
- Require `voice_id` and `model_id` for ElevenLabs providers; keep voice tuning optional and provider-scoped.
- Reference each provider's auth by environment variable name in the contract, not by storing any secret.
- Use direct HTTP for ElevenLabs calls so the repo can reuse `requests` without adding a new SDK dependency.
- Keep the Morning Prayer title pattern familiar, but tag the variant so the feed and episode id stay distinct from the default voice.
- If the preferred provider fails during render, the runtime should try the next provider in order until one succeeds or the list is exhausted.
- Key the audio cache on provider name, voice id, model id, and tuning fields so provider variants cannot collide.

### Relevant Files
- `config/publish/contracts/morning-prayer.json` - current Morning Prayer contract and the place to inspect the existing audio settings shape.
- `config/publish/contracts/rosary.json` - comparison contract that shows the same audio settings pattern on another prayer.
- `jobs/publish/contracts.py` - normalizes publish contracts, merges `audio_target` with entry `audio_config`, and builds the audio jobs.
- `jobs/publish/audio.py` - owns `render_audio_job()`, the renderer callback seam, sidecar writing, and the published-audio skip logic.
- `jobs/publish/fragments.py` - hashes fragment audio identity from normalized TTS settings and assembles the final MP3.
- `jobs/publish/run_audio_pipeline.py` - orchestrates the audio publish flow and is where provider-specific renderers are consumed.
- `tests/test_publish_contracts.py` - contract loading, normalization, and daily-intro behavior.
- `tests/test_publish_audio_fragments.py` - fragment hashing and render-idempotence coverage.
- `tests/test_publish_audio_pipeline.py` - full audio pipeline behavior, archive rebuilds, and feed generation.
- `requirements.txt` - shows current runtime dependencies; there is no ElevenLabs SDK dependency yet.

### Current System Map
- `jobs/publish/contracts.py::_normalize_audio_config()` currently supports only `enabled`, `model`, `voice`, `format`, and `speed`; there is no provider field or provider list yet.
- `jobs/publish/contracts.py::build_audio_jobs()` merges contract-level audio defaults with the entry-level `audio_config`, so provider preferences can likely live in the same contract payload without inventing a new pipeline.
- `jobs/publish/audio.py::render_audio_job()` already accepts a `renderer` callback, which is the cleanest seam for swapping in an ElevenLabs implementation without rewriting the whole pipeline.
- `jobs/publish/audio.py::openai_tts_renderer()` is the only concrete TTS implementation today.
- `jobs/publish/fragments.py::normalize_audio_settings()` and `audio_manifest_hash()` currently hash only the existing TTS fields; provider name and provider-specific voice identity would need to become part of the identity to keep OpenAI and ElevenLabs renders distinct.
- `jobs/publish/audio.py::load_published_audio_jobs()` skips sidecars marked `audio.rendered=false` when the MP3 is missing, so the archive/feed path already tolerates seed-only artifacts.
- The existing Morning Prayer contract is the right comparison point because it is already an active daily audio contract with the same publish model as Rosary.
- ElevenLabs uses `voice_id` as the stable voice selector, `model_id` in the request body, and request-level `voice_settings` for tuning such as stability, similarity, style, and speed.
- The response and settings docs show `stability`, `similarity_boost`, `use_speaker_boost`, `style`, and `speed` as the provider-specific tuning surface.
- A provider object can therefore carry `provider`, `api_key_env`, `voice_id`, `model_id`, and optional tuning overrides without flattening provider choice into a single field.
- Because provider tuning can affect output, the audio cache and manifest hash need to include the provider-specific fields, not just the shared OpenAI-style settings.

### Reuse Opportunities
- Reuse the existing publish contract loader and `audio_config` merge path instead of adding a new top-level config file.
- Reuse the renderer callback seam in `render_audio_job()` so provider selection can stay isolated from audio assembly.
- Reuse the current content-hash and cache boundaries, but extend them with provider identity so fallback providers do not collide.
- Reuse the existing Morning Prayer contract structure and title/feed behavior if only the audio backend changes.
- Reuse the repo's `requests` dependency if ElevenLabs is called over HTTP, which would avoid adding a new SDK dependency immediately.
- Reuse the existing contract merge path by adding provider preference data under `audio_config` rather than creating a separate configuration tree.

### Constraints
- Any new provider support should remain backward compatible with the current OpenAI-backed voice settings.
- The provider preference list should be explicit and contract-driven, not hidden in environment-only selection.
- The new voice should not require changes to the morning-prayer text content unless the audio backend imposes a limit.
- The contract needs a stable way to encode provider order, preferred provider, and voice identity so cache and feed identity stay deterministic.
- If we choose the ElevenLabs HTTP API, the repo can likely avoid a new SDK dependency; if we choose the SDK, `requirements.txt` will need a new package.
- The provider list should likely be an ordered array of provider objects, because each provider can own its own auth, voice id, model id, and tuning fields.
- The feed and episode identity must stay distinct between the default Morning Prayer voice and the ElevenLabs variant.

### Risks
- Highest risk: adding provider selection in a way that breaks the current OpenAI rendering path or causes cache collisions between providers.
- Secondary risk: provider fallback changes the episode identity or feed titles in a way that makes the two Morning Prayer outputs hard to tell apart.
- Structural risk: adding one-off ElevenLabs code that is hard to generalize if other prayers later need alternate TTS providers.
- Operational risk: ElevenLabs voice/model settings may require extra per-provider tuning fields, request headers, or endpoint differences that the current contract does not represent.
- Operational risk: a flattened provider list could make fallback and tuning ambiguous, forcing awkward special-casing later.
- Operational risk: retrying on any render failure may mask a deeper provider bug unless the error surface is preserved clearly in logs.
- Cache risk: if the provider-specific fields are not part of the hash, a render can be incorrectly reused across different voices or tunings.

### Assumptions To Validate
- You want a side-by-side Morning Prayer variant, not a replacement of the current voice.
- A contract-level provider preference list is preferable to environment-only selection for this use case.
- Your custom voice can be referenced by a stable API-side voice ID.
- The existing Morning Prayer content should remain the same unless the provider requires minor formatting changes.
- We can represent provider preference as an ordered array or equivalent list object without making the schema hard to author.
- A direct HTTP client is acceptable if it keeps the dependency footprint smaller than adding another SDK.
- The first implementation should likely support provider-specific voice settings overrides, even if some values default from the voice record.
- The variant should keep the same base Morning Prayer wording and only change provider-specific audio identity.
- The cache should treat provider-specific tuning as meaningful input, not just the base text and generic TTS format.

- No major product unknowns remain.
- Remaining implementation details should be resolved in planning, not by changing the requirements.

## Plan

### Summary
- Build a sibling Morning Prayer contract that publishes the same devotional content with a plain Morning Prayer title and a distinct episode id.
- Add a provider preference list to the audio config so Morning Prayer can try OpenAI first or ElevenLabs first depending on the contract, then fall back in order.
- Keep the current Morning Prayer contract unchanged as the baseline voice, and make the new variant a separate publish path rather than a replacement.

### What Already Exists
- `jobs/publish/contracts.py` already merges contract audio defaults into each job and is the right place to carry a provider preference list through the job model.
- `jobs/publish/audio.py` already has the renderer seam and sidecar persistence, so provider switching can happen there without touching RSS assembly.
- `jobs/publish/fragments.py` already hashes TTS settings into fragment identity, which can be extended to include provider-specific fields.
- `config/publish/contracts/morning-prayer.json` already defines the current Morning Prayer content, metadata, and default OpenAI voice settings.
- `tests/test_publish_contracts.py`, `tests/test_publish_audio_fragments.py`, and `tests/test_publish_audio_pipeline.py` already cover the relevant contract, cache, and feed behaviors.

### Architecture
```text
Morning Prayer contract
  -> audio_config.providers[] (ordered preference list)
  -> build_audio_jobs()
  -> render_audio_job()
       -> provider 1 renderer
       -> if failure, provider 2 renderer
       -> ...
  -> fragment cache + manifest hash include provider identity
  -> sidecar + MP3 + RSS item
```
- Provider resolution happens in the renderer layer, not in the contract loader and not in RSS assembly.
- The ElevenLabs provider object carries `provider`, `api_key_env`, `voice_id`, `model_id`, optional `voice_settings`, and its own auth configuration.
- Cache identity includes provider name, `voice_id`, `model_id`, and tuning fields so provider variants cannot reuse the wrong fragment audio.

### Failure Modes
- Preferred provider unavailable:
  - detected by renderer exception from ElevenLabs
  - user sees the fallback provider or a hard failure if all providers fail
- Cache collision:
  - detected by regression tests and by mismatched provider-specific fields in the sidecar/hash
  - user impact is stale or wrong-voice audio if not caught
- Identity confusion:
  - detected by episode title / id assertions
  - user impact is duplicate-looking Morning Prayer items in the feed
- API mismatch:
  - detected by ElevenLabs request/response errors
  - user impact is a failed render with no published variant
