# Release 0.3.0.3 - Publish Audio Cache Persistence

Date: 2026-05-01
Status: Shipped
Branch: enhancement/publish-audio-cache-persistence
Depends On: 0.3.0.2

## Scope

### Problem
- The publish audio pipeline already has a fragment cache under `.cache/publish_audio/`, but the cache only helps when the same workspace is reused.
- On fresh GitHub Actions runs, the cache directory starts empty, so unchanged fragments and silence assets are regenerated even when nothing about the episode changed.
- Why now: the audio path is now stable enough that the remaining cost is repeated rendering work, and the daily job should not pay that cost every day for unchanged speech.

### Audience
- Primary user: the maintainer who runs or schedules the audio publish workflow and wants reruns to be faster and cheaper.
- Secondary stakeholders: podcast listeners, who should not see any change in episode behavior while the pipeline gets faster.
- Secondary stakeholders: future maintainers, who need a clear contract for what part of the audio work is cached and how it is restored.

### Current Status Quo
- `jobs/publish/fragments.py` already caches rendered leaf fragments and silence helpers under `.cache/publish_audio/`.
- `jobs/publish/audio.py` already reuses a whole episode when the episode MP3 and sidecar content hash still match.
- The GitHub Actions workflow does not persist `.cache/publish_audio/` between runs, so fresh runners lose the cache and rebuild from scratch.
- The current cache behavior is therefore useful only inside one workspace, not across daily scheduled runs.

### Goal
- Persist the publish audio fragment cache across workflow runs so unchanged fragments are restored instead of regenerated.
- Keep the published audio output and RSS feed identical to the current behavior.
- Success criteria: a second workflow run with the same content restores cached fragments and skips re-rendering unchanged pieces.
- Success criteria: cache misses still fall back to normal rendering and do not break the publish job.

### Constraints
- Keep the change narrow to workflow cache persistence and cache keying.
- Do not change the audio rendering contract, episode identity, or RSS merge behavior unless the cache integration proves a hidden dependency.
- The cache must be safe to restore across branches and over time without causing stale audio to leak into a changed episode.
- The solution should work within the existing GitHub Actions workflow instead of introducing a new storage backend.

### Narrow Wedge
- Add persisted cache restore/save around the publish audio fragment cache, then verify reruns reuse unchanged fragments without changing the published feed.
- Add regression coverage for cache-aware behavior in the workflow and the fragment renderer so the cache contract is explicit.

### Non-Goals
- Do not redesign episode identity or feed retention.
- Do not move the publish archive to a new storage system.
- Do not cache the entire `docs/` tree unless fragment persistence proves insufficient.
- Do not broaden the change to Spotify playlist refresh or novena behavior.

### Risks And Unknowns
- A bad cache key could restore stale fragments into a changed episode and make the output incorrect.
- The cache may be large enough to need careful key scoping or path filtering.
- It is still unclear whether caching only fragments is enough, or whether assembled episode outputs also deserve persistence.

### Recommended Next Step
- Run `/research-astack` to map the cacheable paths, choose the right GitHub Actions cache key strategy, and confirm what should and should not be restored between runs.

## Research
### Scope Baseline
- Add GitHub Actions cache persistence for the publish audio fragment cache so unchanged fragments and silence assets survive across fresh workflow runs.
- The goal is to keep published audio behavior unchanged while avoiding repeated regeneration of audio pieces that are already content-addressed.

### Relevant Files
- `jobs/publish/fragments.py` - owns the fragment cache layout, fragment hashing, silence generation, and fragment-level reuse logic.
- `jobs/publish/audio.py` - decides when a whole episode can be reused from the on-disk MP3 + sidecar and when the fragment cache must be consulted.
- `.github/workflows/publish_audio.yml` - the workflow entrypoint that currently installs dependencies and runs the publish audio pipeline without restoring or saving `.cache/publish_audio/`.
- `tests/test_publish_audio_pipeline.py` - contains the publish-audio regression coverage that should be extended to pin cache-aware behavior.
- `tests/test_publish_audio_fragments.py` - exercises fragment cache and assembly behavior directly and is the best place to verify cache identity assumptions.

### Current System Map
- Fact: `render_fragment_audio()` stores each fragment under `.cache/publish_audio/fragments/<hash-prefix>/<hash>/<hash>.<format>` and writes a JSON sidecar next to the fragment file.
- Fact: `assemble_audio_fragments()` also stores generated silence clips under the same cache root and reuses them when available.
- Fact: `render_audio_job()` already short-circuits on an unchanged episode if the output MP3 and sidecar content hash still match.
- Fact: the workflow only checks out the repo, installs dependencies, and runs the publish jobs; it does not restore `.cache/publish_audio/` from a prior run or save it afterward.
- Fact: the current cache directory is workspace-local, so its persistence depends on the same checkout being reused outside GitHub Actions.
- Inference: the cached fragment model is already deterministic enough to restore safely across runs if the cache key is scoped to the repo state and audio configuration.

### Reuse Opportunities
- Reuse the existing content-hash scheme in `jobs/publish/fragments.py` instead of inventing a separate cache identity format.
- Reuse the existing fragment sidecar metadata as a validation signal when deciding whether a restored cache entry still matches the fragment hash.
- Reuse the workflow’s existing single job entrypoint by inserting cache restore/save steps around it rather than splitting the pipeline into a new job.
- Reuse the publish-audio tests to prove the pipeline still renders the same output when the cache is cold and skips work when the cache is warm.

### External References
- GitHub Actions `actions/cache` for persisting `.cache/publish_audio/` across runs.
- GitHub Actions cache key behavior, especially restore keys and branch scoping, because this cache should be reusable but not leak stale audio between unrelated changes.

### Constraints
- The cache must be safe to restore on a fresh runner without changing the published MP3s or RSS output.
- Cache keying needs to account for changes in fragment text, audio settings, and any code path that changes the rendered output.
- The workflow should not treat the cache as the source of truth for feed history; `docs/podcast.xml` remains the archive, and the fragment cache is only an acceleration layer.
- Any cache persistence should be compatible with the existing GitHub Pages publish flow and not interfere with artifact upload.

### Risks
- A too-broad cache key could restore stale fragments into a changed episode and produce incorrect audio.
- A too-narrow cache key could miss often enough that the cache becomes ineffective.
- The cache may grow large enough that save/restore time offsets the rendering savings if it is not scoped carefully.
- Cache persistence that restores fragment files without the matching sidecar metadata could make stale artifacts harder to detect.

### Assumptions To Validate
- The fragment cache is meant to be shared across workflow runs, not just within one run or one local checkout.
- Restoring the cache before audio rendering is enough; we do not need to persist assembled episode MP3s separately at first.
- The cache should probably key off repo state plus audio settings, but we have not yet validated the exact key shape.

### Unknowns
- Whether the best cache boundary is fragment files only, fragment files plus silence clips, or the entire `.cache/publish_audio/` tree.
- Whether GitHub Actions cache limits make this fragment cache durable enough for the expected publish volume.
- Whether the workflow should fall back quietly on a cache miss or emit explicit cache-hit/miss logging for diagnostics.

### Recommended Direction
- Move to `/plan-astack` next and define the exact cache key, restore/save placement, and regression tests for the publish audio workflow.

## Plan

### Summary
- Persist the publish audio fragment cache across GitHub Actions runs so unchanged fragments and silence assets are restored instead of regenerated.
- Keep the published MP3s, RSS feed, and novena behavior unchanged; this is a performance and cost optimization, not a behavior change.
- Use GitHub Actions cache as the persistence layer for `.cache/publish_audio/fragments` and `.cache/publish_audio/silence`, leaving assembled episode outputs and `docs/podcast.xml` out of the cache contract.

### What Already Exists
- `jobs/publish/fragments.py` already content-addresses fragment audio and silence assets, so the cache entries are deterministic and safe to restore when the inputs are unchanged.
- `jobs/publish/audio.py` already skips rerendering a whole episode when the output MP3 sidecar hash matches, so the workflow only needs to persist the lower-level fragment cache across runs.
- `tests/test_publish_audio_fragments.py` already proves fragment reuse inside a single workspace, and `tests/test_publish_audio_pipeline.py` already exercises the audio pipeline end to end.
- `.github/workflows/publish_audio.yml` already runs audio and novena in one GitHub Actions job, which makes it a good single place to restore and save the fragment cache.

### Architecture
- Restore the fragment cache immediately after checkout so the publish job can reuse warmed fragments before any rendering starts.
- Render audio normally; unchanged fragments and silence clips should hit the restored cache, while misses fall back to the existing renderer path.
- Save the warmed cache after the audio and novena publish steps finish, but before the Pages upload/deploy steps, so a publish failure does not turn into a cache-formatting failure.
- Keep the cache boundary narrow enough that it speeds rendering without becoming a second source of truth for feed history.
- Use an exact restore key of `publish-audio-${{ runner.os }}-py311-fragments-v1-${{ hashFiles('requirements.txt') }}` plus `restore-keys: publish-audio-${{ runner.os }}-py311-fragments-v1-`, and save new snapshots under `publish-audio-${{ runner.os }}-py311-fragments-v1-${{ github.run_id }}-${{ hashFiles('requirements.txt') }}` so warm runs can reuse prior caches while still capturing new fragments.

ASCII flow:
```text
GitHub Actions job
  -> checkout repo
  -> restore .cache/publish_audio/{fragments,silence}
  -> install dependencies
  -> publish audio
       -> fragment lookup
       -> render misses only
  -> publish novena
       -> same cache root reused
  -> upload docs/
  -> cache saved after job success
```

### Concrete Changes
- `.github/workflows/publish_audio.yml`
  - Add `actions/cache@v4` around the publish job.
  - Cache only `.cache/publish_audio/fragments` and `.cache/publish_audio/silence`.
  - Restore the cache after checkout and before dependency installation.
  - Save the cache after `Publish audio files and RSS feed` plus `Publish novena audio and RSS feed`, but before GitHub Pages artifact upload/deploy.
  - Restore with `key: publish-audio-${{ runner.os }}-py311-fragments-v1-${{ hashFiles('requirements.txt') }}` and `restore-keys: publish-audio-${{ runner.os }}-py311-fragments-v1-`.
  - Save with `key: publish-audio-${{ runner.os }}-py311-fragments-v1-${{ github.run_id }}-${{ hashFiles('requirements.txt') }}` so each successful run can snapshot the cache it just warmed.
  - Keep cache restore non-blocking so a miss still runs the publish job normally.
- `tests/test_publish_audio_fragments.py`
  - Add a restored-cache regression that copies the warmed fragment cache into a fresh temp workspace and proves a second render skips the renderer for unchanged fragments.
  - Add a second assertion that the silence cache is restored too, so assembly can still reuse the cached inter-fragment silence asset.
  - Keep the existing fragment identity and reuse assertions.
- `tests/test_publish_audio_pipeline.py`
  - Add workflow-text assertions that the GitHub Actions file includes both the cache restore and cache save steps, plus the intended cache paths and key prefix.
  - Keep the existing pipeline and feed-retention tests unchanged.
- `README.md`
  - Clarify that the fragment cache is now persisted by GitHub Actions across workflow runs, not just reused inside one checkout.

- Cold cache state: the workflow runs normally and populates the cache.
- Warm cache state: unchanged fragments and silence assets are restored, and the logs should show fewer renderer calls.
- Cache miss or cache eviction: the workflow should still succeed, just with a slower render path.

### Failure Modes
- Cache miss: normal cold render, no user-visible change, just slower execution.
- Bad cache key: stale fragments restored into a changed episode, which would silently produce incorrect audio; this is why the key needs an explicit schema bump and a stable dependency fingerprint.
- Oversized cache: restore/save time could erase some of the speed gain if the cache boundary is too broad.
- Cache service outage: publish should still succeed because the cache is an optimization, not a dependency.

### QA And Test Matrix
- Workflow dispatch with a cold cache: confirm the publish job succeeds and populates `.cache/publish_audio/`.
- Workflow dispatch with a warm cache: confirm unchanged fragments are skipped and the run still produces the same `docs/audio/*.mp3` and `docs/podcast.xml` outputs.
- Daily workflow path: confirm cache restore does not interfere with novena publishing or the feed append behavior.
- Fragment-level reuse: confirm a fresh workspace with a restored cache skips rerendering an unchanged fragment set.
- Regression tests: `tests/test_publish_audio_fragments.py`, `tests/test_publish_audio_pipeline.py`, and `tests/test_novena_pipeline.py`.

### Rollout Notes
- No flag or migration is required; cache persistence is additive and safe to miss.
- If the cache key needs a future bump, it can be changed in the workflow without touching the runtime code.
- The cache should never block the publish job; correctness still comes from the existing render and feed paths.

### Not In Scope
- Reworking episode identity, feed retention, or `podcast.xml` archiving.
- Caching the full `docs/` tree or assembled MP3s as the first step.
- Introducing a new storage backend outside GitHub Actions.
- Changing novena behavior beyond benefiting from the same warmed cache.

### Open Questions
- None for this release. We are only caching fragments and silence assets, not full assembled episode MP3s.
- The cache key is intentionally versioned with `fragments-v1`; if the cache format changes later, we will bump that version instead of layering in more fingerprints now.
