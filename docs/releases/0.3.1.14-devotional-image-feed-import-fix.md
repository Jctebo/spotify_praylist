## Scope

### Problem
- The devotional image GitHub Pages workflow rebuilt the public Pages tree from `docs/`, then tried to rebuild `podcast.xml` from the restored audio archive.
- That inline rebuild imported `load_published_audio_jobs` from `jobs.publish.rss`, but the function actually lives in `jobs.publish.audio`, so the job aborted with `ImportError`.

### Goal
- Make the devotional image Pages job rebuild `podcast.xml` from the archived audio snapshot without import errors.
- Keep the blank-feed guard in place so the workflow still fails closed if the archive snapshot is missing.
- Add regression coverage for the exact workflow import so the same mistake cannot return silently.

## Research

### Findings
- `jobs.publish.audio` owns `load_published_audio_jobs`; `jobs.publish.rss` only builds and writes feed XML.
- The failing workflow step is the inline Python block in `.github/workflows/daily_devotional_image_remote.yml`, so the fix belongs in the workflow rather than the runtime modules.
- Existing tests already inspect the workflow text, which makes this a good place to pin the corrected import line.

## Plan

### Implementation
- Update the inline Python in `.github/workflows/daily_devotional_image_remote.yml` to import `load_published_audio_jobs` from `jobs.publish.audio`.
- Keep `build_rss_feed` and `write_podcast_feed` imported from `jobs.publish.rss`.
- Tighten the workflow-text regression test to assert the corrected import line.
- Run the publish-focused unittest suite and confirm the workflow still passes.
