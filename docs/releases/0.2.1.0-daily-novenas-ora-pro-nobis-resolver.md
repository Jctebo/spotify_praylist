## Scope

### Problem
- The Spotify queue system can already resolve several prayer and podcast contracts, but it has no dedicated contract for the exact `Daily Novenas` Notion row.
- The `Ora Pro Nobis` show is already wired into the runtime through the existing monthly morning-prayer show entry, but nothing maps that show to a date-scoped title search for novena episodes.
- Without a contract/resolver pair, the daily refresh job cannot reliably surface the right novena episodes, so the row stays manual or effectively inactive.
- Why now: the Notion row is already entered, so the missing piece is the last mile from queued row to Spotify episode URIs.
- The only matching rule needed is: the episode title must include the word `Novena` and the current date.

### Audience
- Primary user: the maintainer who curates the Spotify and Notion playlist database and expects the `Daily Novenas` row to resolve automatically.
- Secondary stakeholders: listeners who should see the correct novena episodes in the playlist without manual editing.
- Secondary stakeholders: future maintainers who need a clear, deterministic rule for how an Ora Pro Nobis episode is chosen.

### Current Status Quo
- `jobs/playlist/refresh_playlist.py` already resolves several contract keys into Spotify URIs, including date-aware episode lookups and show-title helpers like `monthly_morning_prayer_episode`.
- `jobs/playlist/spotify_contracts.py` already supports repo-owned queue contracts with `notion_name`, `resolver`, optional fallback, and weekday gating.
- The Ora Pro Nobis show is already available through the Spotify refresh runtime, but there is no dedicated `Daily Novenas` contract or resolver branch.
- The daily refresh job can sync Notion playlist links and rebuild playlists, but the `Daily Novenas` row has no contract-specific resolver to feed it one or more URIs.

### Goal
- Add a repo-owned Spotify queue contract for the `Daily Novenas` Notion row.
- Add a dedicated resolver that searches the Ora Pro Nobis show for episodes whose titles contain `Novena` and today’s date.
- Resolve every matching Spotify episode URI in a deterministic order so the playlist refresh can queue all relevant daily novenas automatically.
- Keep the existing daily refresh, Notion membership flow, and other resolver branches intact.

### Constraints
- The implementation should stay inside the current Spotify refresh boundary rather than introducing a new workflow.
- The resolver should be deterministic and fail closed if no matching episode exists.
- If more than one episode matches, the ordering must be stable and explainable so reruns produce the same playlist contents.
- The resolver should use a dedicated Ora Pro Nobis show config entry for `Daily Novenas` instead of reusing the Morning Prayer show key.
- Existing contracts, resolver keys, and Notion sync behavior must continue to behave exactly as they do today.

### Narrow Wedge
- Add one new queue contract file for `Daily Novenas`.
- Add one new resolver branch in `jobs/playlist/refresh_playlist.py` that looks up the Ora Pro Nobis show and matches titles containing `Novena` plus today’s date, returning every match rather than stopping at the first one.
- Add regression coverage for contract loading and the resolver’s date/title matching behavior, including the multi-match case.
- Keep the first version focused on one contract and one show, not a general podcast-search framework.

### Non-Goals
- Do not redesign the Spotify queue model or Notion membership logic.
- Do not generalize title search to every podcast show in the repository.
- Do not change the existing Morning Prayer, Rosary, Saint of the Day, or seasonal Angelus resolvers.
- Do not alter any novena publishing pipeline, RSS feed generation, or audio rendering.
- Do not add multi-show search, fuzzy matching, or a generic podcast resolver framework in this release.

### Risks And Unknowns
- It is unclear whether the date appears in a consistent format across all Ora Pro Nobis titles, so the title matcher may need a small amount of normalization.
- If multiple episodes contain `Novena` and the same date, we need a deterministic ordering rule for the returned playlist entries.
- The exact Notion row shape for `Daily Novenas` may still influence whether the new contract belongs in the existing Spotify playlists database or a different row grouping.
- The biggest open question is whether the resolver should preserve Spotify API order, release-date order, or some other explicit sort when multiple episodes match.

### Recommended Next Step
- Run `/research-astack` to validate the contract placement, choose the exact resolver key and matching rule, and confirm whether the existing title/date helpers can be reused as-is.

### Current System Map
- `load_spotify_queue_contracts()` requires each contract to define `key` and `notion_name`, then exactly one of `resolver` or `spotify_uri` unless the contract uses the special seasonal Angelus fields.
- `build_notion_playlist_memberships()` joins checked Notion rows by exact `notion_name`, then uses `Output Folder` and `Order` to decide which playlist receives the contract.
- `resolve_item_uri()` is the central resolver dispatch; `MORNING_PRAYER_MONTHLY` already routes to `monthly_morning_prayer_episode()` through a dedicated `if key == ...` branch.
- `monthly_morning_prayer_episode()` already performs a date-scoped episode title match against the Ora Pro Nobis show and is the closest existing pattern for this work.
- `episode_title_contains()` only returns the first substring match, so it is not sufficient by itself for a date-filtered multi-hit novena resolver.
- `latest_by_release_date()` and `do_date_aware()` show the repo’s existing patterns for scanning `show_episodes()` results and handling pagination or date matching.

### Reuse Opportunities
- Add a dedicated show configuration entry for `Daily Novenas` instead of reusing the Morning Prayer show key.
- Reuse the contract-first queue model already validated by `jobs/playlist/spotify_contracts.py`.
- Reuse the `monthly_morning_prayer_episode()` structure as the implementation model for a date-scoped Spotify episode search.
- Reuse `resolve_spec_uri()` / `resolve_item_uri()` / `build_queue_for_playlist_definition()` so the new contract participates in the existing refresh flow without special casing elsewhere.
- Reuse the current contract file conventions in `config/spotify/contracts/*.json` so the new row behaves like the other playlist contracts.

### External References
- Spotify Web API show-episode retrieval via `sp.show_episodes()` and pagination via `sp.next()` are the only external API surfaces that matter here.
- No new third-party libraries or external services appear necessary for this change.

### Constraints
- The matching rule should stay simple: title contains `Novena` and title contains today’s date.
- The resolver must fail closed when there is no match.
- If multiple episodes match, the returned order must be deterministic and explainable.
- The new contract must match the exact Notion row title for `Daily Novenas` or it will never activate.
- The current helper set only scans one page or the first matching item in some paths, so the new logic may need explicit pagination or a dedicated collector helper.

### Risks
- The date format in Spotify titles may vary enough to require small normalization work.
- Multi-match behavior is currently underspecified: if several episodes share the same date, we need a stable ordering rule before shipping.
- If the resolver only inspects the first page of `show_episodes()`, older or paginated results could be missed.
- If the date filter is too loose, stale novena episodes could be pulled into today’s queue.

### Assumptions To Validate
- `Daily Novenas` is the exact Notion title we should match in the Spotify contract.
- Ora Pro Nobis episode titles consistently include a parseable date string.
- The dedicated Spotify show entry for `Daily Novenas` will point at the correct Ora Pro Nobis show.
- Description matching is not required; title matching alone is enough.

### Unknowns
- Whether a new helper should return all matches in one pass or whether `resolve_item_uri()` should call a more general collector function.
- Whether the resolver should preserve Spotify API order, release-date order, or some other explicit stable sort when several matches exist.
- Whether the best regression belongs in `tests/test_refresh_job.py`, `tests/test_refresh_job_contract_path.py`, or both.
- Whether any README note is needed once the contract is added.

### Recommended Direction
- Implement one normal queue contract plus one date/title resolver helper for `Daily Novenas`, then add tests that cover no-hit, single-hit, and multi-hit cases.
- Keep the search rule narrow and deterministic, and add a dedicated show config entry for `Daily Novenas` rather than coupling it to Morning Prayer.
- After that, move to `/plan-astack` with the exact date matching and ordering rule confirmed by tests or sample data.

## Plan
### Summary
- Build a dedicated Spotify queue contract for `Daily Novenas` and a resolver path that returns every Ora Pro Nobis episode whose title contains `Novena` and today’s date.
- Keep the existing single-URI resolver branches intact for Morning Prayer, Rosary, and the other playlist contracts.
- Use a dedicated `DAILY_NOVENAS` show config key so this feature is not coupled to the Morning Prayer show key.
- The chosen approach is a small contract-first extension of the current Spotify refresh job, not a new framework.

### What Already Exists
- `jobs/playlist/refresh_playlist.py` already owns the contract dispatch, Spotify show lookup helpers, and playlist queue assembly.
- `jobs/playlist/spotify_contracts.py` already validates one contract per file with exact `notion_name` matching and fail-closed shapes.
- `monthly_morning_prayer_episode()` already proves the repo can match a Spotify episode by a date-scoped title.
- `build_notion_playlist_memberships()` already activates rows only when Notion `Enabled` is checked and `Name` matches the contract title exactly.
- The existing tests already cover contract loading, show-based resolution, and end-to-end playlist building.

### Architecture
- Flow:

```text
Notion row: Daily Novenas
    -> load_spotify_queue_contracts()
    -> build_notion_playlist_memberships()
    -> build_queue_for_playlist_definition()
    -> resolve_contract_uris()
        -> if contract.key == DAILY_NOVENAS
            -> daily_novenas_episode_uris()
                -> sp.show_episodes(show_id)
                -> sp.next(...) while pages remain
                -> keep titles with "Novena" + today's date
                -> preserve Spotify result order
        -> else
            -> existing single-URI resolver switch in resolve_item_uri()
    -> recreate_playlist_items()
```

- The "resolver switch" is the existing `if key == ...` dispatch inside `resolve_item_uri()`.
- `Daily Novenas` will not go through the one-item switch; it will use a dedicated list-producing helper so the playlist can receive multiple matching episodes from one contract.
- The queue builder will flatten the returned list in order and continue to treat all other contracts as single-item entries.

### Concrete Changes
- `jobs/playlist/refresh_playlist.py`
  - Add `DEFAULT_SHOWS["DAILY_NOVENAS"]` as a dedicated show slot.
  - Add a new list-producing helper, likely `daily_novenas_episode_uris(...)`, that pages through `sp.show_episodes()` and collects every matching URI.
  - Add a small contract-level resolver wrapper, likely `resolve_contract_uris(...)`, so `Daily Novenas` can expand to multiple queue entries while existing contracts still return one URI.
  - Update `build_queue_for_playlist_definition()` to flatten returned URIs instead of assuming one URI per contract.
  - Keep the existing `resolve_item_uri()` switch for the one-URI contracts unchanged except for any small refactor needed to share helpers.
- `config/spotify/contracts/daily-novenas.json`
  - Add the new repo-owned contract with `key`, `notion_name: "Daily Novenas"`, and `resolver: "DAILY_NOVENAS"`.
- `tests/test_spotify_contracts.py`
  - Add contract-shape coverage for the new file and confirm it loads as a normal resolver-backed contract.
- `tests/test_refresh_job_contract_path.py`
  - Add a smoke test that proves the `Daily Novenas` contract routes through the resolver path and uses the dedicated show config slot.
- `tests/test_refresh_job.py`
  - Add unit coverage for the list-producing helper, including no-hit, single-hit, and multi-hit cases.
  - Add a pagination regression that proves later pages are scanned, not just the first `show_episodes()` page.
  - Add a queue-building regression that confirms one contract can expand into multiple playlist items in order.

### UX And States
- No UI changes.
- Success state: the `Daily Novenas` row resolves into zero or more Spotify episode URIs, in stable order, and those URIs are written into the target playlist.
- Empty state: if no title matches `Novena` plus today’s date, the resolver returns no URIs and the existing empty-queue path remains fail-closed.
- Error state: bad contract JSON, a missing `DAILY_NOVENAS` show config value, or a malformed Spotify response should fail the refresh before writing the playlist.

### Failure Modes
- If the show key is missing or misconfigured, `Daily Novenas` will fail to resolve and the playlist build will fail closed.
- If the collector only reads the first page, older episodes or later-page matches will be missed.
- If the title/date filter is too broad, unrelated episodes could leak into the queue.
- If the queue builder does not flatten lists, only the first match would survive and the contract would silently underdeliver.
