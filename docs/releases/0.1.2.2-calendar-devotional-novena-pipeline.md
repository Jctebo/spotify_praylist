# Release 0.1.2.2 - calendar-devotional-novena-pipeline

- Status: Shipped
- Shipped Version: 0.1.2.3

## Scope

### Problem
- The daily devotional flow is split across multiple jobs: the devotional-image job handles images, the prayer matrix job handles contracts, and novena handling is not yet anchored to the calendar day that should drive the whole pipeline.
- The user wants the calendar job to be the source of truth for the day`s devotional content, generating the day-specific devotional images and novenas first.
- The workflow should keep one schedule and use `needs: calendar` so the matrix job only starts after the calendar job succeeds.
- The matrix contract job should then consume that calendar-produced novena output, with Morning Prayer as one contract row inside the matrix.
- The Spotify playlist job should be disabled in this branch so the pipeline stays focused on calendar, novena, prayer, and OneDrive delivery.

### Audience
- Primary user: the maintainer who wants one calendar-aware daily pipeline to drive the devotional output.
- Secondary stakeholders: the daily novena and matrix contract consumers that should reuse the calendar-aware output instead of recomputing it.

### Current Status Quo
- `daily_devotional_image_remote.yml` generates devotional images from the 9-day Romcal window and syncs the results to OneDrive.
- `daily_novena_prayer.yml` is a separate contract-driven prayer workflow, with Morning Prayer currently represented as one contract among several.
- `generate_daily_novena_prayer.py` owns novena generation, while `generate_devotional_image.py` owns devotional-image generation.
- The calendar logic already exists in the repo, but it is not yet the orchestration anchor for both the image and novena outputs.
- The Spotify playlist workflow exists in the repo history, but this branch is intended to disable it rather than fold it into the new daily flow.

### Goal
- Make the calendar job the source of truth for the day`s devotional assets.
- Have that job review the current calendar day and generate the images and novenas associated with that day.
- Keep the workflow to one schedule, one calendar job, and one downstream matrix job.
- Make the matrix contract job consume the novena output produced by the calendar job.
- Keep Morning Prayer as one matrix contract that reads the calendar-produced novena output.
- Keep OneDrive as the final delivery target for the assembled assets.

### Constraints
- Do not break the existing devotional image OneDrive sync while shifting the calendar responsibility into the job.
- Reuse the current Romcal and OneDrive mechanics rather than inventing a new calendar engine or upload path.
- Preserve the daily schedule and output stability so the workflow remains operational in GitHub Actions.
- Avoid duplicating the calendar-day decision logic in multiple jobs.
- Disable the Spotify playlist job on this branch so it cannot run alongside the calendar pipeline work.
- Model the workflow as a single dependency chain: `workflow_dispatch` / `schedule` -> `calendar` -> `matrix`.

### Narrow Wedge
- Use the existing devotional-image remote workflow as the calendar anchor.
- Teach it to inspect the current calendar day and derive the devotional image and novena outputs from that day.
- Keep the matrix contract workflow as the second stage that runs only after the calendar job completes successfully.
- Keep Morning Prayer as a consumer row inside the matrix.
- Keep the upload and publish steps at the end of the same daily flow.

### Non-Goals
- Rebuilding the entire liturgical calendar system.
- Replacing OneDrive.
- Rewriting every prayer or novena generator.
- Removing the existing image upload path before the calendar-aware replacement is verified.
- Re-enabling the Spotify playlist job on this branch.

### Risks And Unknowns
- The current novena and Morning Prayer runners may not yet share a clean handoff format, so the new boundary may need an adapter.
- The workflow will need to split into multiple jobs to keep the calendar decision, novena generation, matrix contract execution, and upload steps reliable.
- The calendar job and matrix job need an explicit output contract so the downstream `needs: calendar` step reads the right novena payload.
- If the calendar day selection and the novena output disagree, the matrix contract consumer could pick up the wrong content.

### Recommended Next Step
- Use `/research-astack` to map the calendar decision path, identify which job should own novena generation, and determine the cleanest way for the matrix contract job and Morning Prayer to consume the calendar-produced output.

### Current System Map
- The repo currently separates:
  - calendar computation
  - novena generation
  - devotional image generation
  - matrix contract prayer assembly
- The devotional-image remote workflow already handles:
  - GitHub Actions scheduling
  - Romcal-driven image generation
  - rclone OneDrive sync
  - GitHub Pages publication
- The novena generator and prayer runner already exist, but they are not yet coordinated as a calendar-aware chain.
- The likely integration choice is a two-stage dependency chain:
  - calendar job first
  - matrix contract job second via `needs: calendar`

### Reuse Opportunities
- Reuse the current devotional-image remote workflow as the orchestration home for the calendar stage.
- Reuse `generate_devotional_image.py` for the image work already tied to the calendar window.
- Reuse `generate_daily_novena_prayer.py` for novena generation.
- Reuse `generate_prayer.py` or `generate_page_audio.py` for the Morning Prayer consumer row inside the matrix.
- Reuse the existing rclone sync and GitHub Pages publish logic.

### External References
- GitHub Actions job dependencies matter because the calendar-to-novena-to-prayer handoff is likely best represented as ordered jobs.
- Romcal remains the external liturgical source behind the calendar-day decision.

### Constraints
- The new workflow should not lose the current OneDrive sync behavior for devotional images.
- The job boundaries should make it obvious where the calendar decision happens, where the novena output is consumed, and where the matrix contract job starts.
- The output directories should remain stable enough that existing local runners and upload scripts still make sense.

### Risks
- If the calendar decision is embedded too deeply in the image job, the novena consumer may be hard to test independently.
- If the workflow remains too split, the user`s desired `calendar -> novena -> matrix contract job -> OneDrive` handoff may still feel fragmented.
- The existing novena and prayer scripts may need a shared output contract to avoid duplicate generation.

### Assumptions To Validate
- The devotional-image workflow is the correct anchor for the calendar-aware pipeline.
- Morning Prayer can consume novena output produced earlier in the same daily workflow as one matrix row.
- The output contract between the novena job and the matrix job can be kept small and explicit.
- The single workflow can safely fan out to the matrix job only after the calendar job publishes its outputs.

### Unknowns
- Whether the calendar-aware novena generation should happen inside the image job or as a separate dependency job.
- Whether the matrix contract job should read a file output, a Notion row, or another shared contract from the novena job.
- Whether the combined workflow should still publish a GitHub Pages image artifact unchanged.

### Recommended Direction
- Use `/plan-astack` after research to define a calendar-driven multi-job workflow where the calendar job owns the day selection, novena generation is produced from that day, the matrix contract job consumes the novena output via `needs: calendar`, Morning Prayer is one matrix row, and OneDrive remains the final upload boundary.

## Plan

### Summary
- Build a calendar-driven daily workflow anchored on the existing devotional-image remote job.
- The workflow should inspect the current calendar day, generate the devotional images and novenas for that day, hand the novena output to the matrix contract job, and finish with OneDrive upload.
- Keep the current OneDrive sync mechanics and make the calendar-aware handoff explicit.

### What Already Exists
- `daily_devotional_image_remote.yml` already owns the OneDrive upload path and Romcal-driven image generation.
- `generate_devotional_image.py` already computes outputs from the liturgical window.
- `generate_daily_novena_prayer.py` already generates novena content.
- `generate_prayer.py` and `generate_page_audio.py` already provide the Morning Prayer assembly side.

### Architecture
- Keep a single workflow as the orchestration home.
- Split the work into ordered phases so each stage has a clear output boundary:
  - calendar/day selection
  - devotional image generation
  - novena generation
  - matrix contract consumption
  - OneDrive sync / publish
- Use the existing OneDrive sync step as the final output stage.

ASCII flow:
```text
workflow_dispatch / schedule
    |
    v
calendar day review
    |
    +--> devotional image generation
    |
    +--> novena generation
    |
    +--> matrix contract job consumes novena output
    |
    v
OneDrive sync / publish
```

### UX And States
- Scheduled run:
  - The workflow reviews the current calendar day and generates the day-specific devotional artifacts.
- Matrix contract consumption:
  - Morning Prayer reads the novena output produced earlier in the same pipeline as one matrix row.
- Upload state:
  - OneDrive receives the assembled outputs only after the generation stages complete successfully.
- Failure state:
  - If any stage fails, the pipeline should not sync partial or stale output.

### Failure Modes
- The novena output does not match the calendar day selected by the image job.
  - Detection: mismatched content in downstream matrix contract output.
  - User experience: the daily devotional set feels out of sync.
- The matrix contract job consumes stale novena output.
  - Detection: the workflow syncs older files or mismatched prayer content.
  - User experience: the daily prayer bundle does not reflect the current calendar.
- The workflow uploads partial output.
  - Detection: missing files or incomplete OneDrive directories.
  - User experience: the daily assets appear inconsistent on OneDrive.

### QA And Test Matrix
- Calendar day selection matches the current Romcal day.
- Devotional images are generated for the current day.
- Novena generation consumes the current calendar output.
- The matrix contract job consumes the novena output from the same run.
- OneDrive sync only happens after all generation stages complete successfully.

### Rollout Notes

- Prefer a dependency chain with explicit handoffs over hidden cross-job assumptions.
- Keep GitHub Pages publishing if the devotional-image output still needs it.

### Not In Scope

- Rewriting the Romcal calendar model.
- Removing the existing image workflow before the calendar-aware chain is verified.
- Expanding the pipeline beyond the daily devotional, novena, and matrix contract flow.
