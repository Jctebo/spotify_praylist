### §2.2 The contents-item model (the dynamic item's frame)

Contents items are `{kind, key}` selectors in an ordered per-block list. The seats a new kind must pass, all grounded:

- **Write validator, client:** `opnValidateContents` (client.ts ~2880) — per-kind arms; an unlisted kind throws `bad contents kind`. Its dedupe: `seen[kind + ':' + key]`, office-source exception only.
- **Write validator, server:** index.ts ~1370–1392 — the twin arms (`bad day` / `bad contents kind` / `bad seat` stand there verbatim). Both validators move together or a stored item is refused at one seat.
- **Read seam:** `opnContentsOf590` (client.ts ~3043) — the filter at ~3056 passes only named kinds with key checks; a kind it does not name is silently filtered OUT of every stored profile. A new kind that misses this seat never stands.
- **The fold:** `extRebuildDescs` walks the effective contents in order; each living kind reads a resolver map keyed `block + ':' + item.key` and expands in place (`course` → `state.courseRes590`, `day` → `state.exegesisRes611`, `episode` → `state.episodeRes614`, `video` → raw-push from `state.videoRes656`, `prayer` → the additions seam; `seat` stands nothing in the pass — `foldReadingsSeat` splices it before the Rosary, v660).
- **Resolver pass:** `buildDayFromPayload` invokes the resolvers beside the externals dispatch (client.ts ~21800): courses · exegesis day · episodes · videos · readings seat. Each resolver: jobs from the effective contents → one fetch per series of `/api/player/podcasts?series=<key>` → fill its map → `extRebuildDescs(day)` + `paintPrayersView` settle. A payload that fails to load resolves NOTHING that build (the standing rule).
- **Editor:** the contents editor paints each item through the title function at client.ts ~22998 (`course` → course title · `day` → 'Daily Gospel Exegesis' · `episode` → registry title · `video` → registry title); remove/reorder manipulate the items array generically. A new kind needs its title branch; the acts themselves are kind-blind (Implement verifies).

### §2.3 The living kinds today (the precedents the dynamic item follows)

Three contents kinds already resolve per-day instead of pinning one episode:

- **`course`** — resolves to the series' next episode by the user's own progress (`resolveProfileCourses590`). Living by progress, not by date.
- **`day`** (v611, key locked to `daily-gospel-exegesis`) — resolves to the episode whose Chicago release date is the presented date − 1 (the feed releases each day's episode the day before). GAP RULE: no such entry → the slot stands EMPTY, no fallback.

The dynamic item generalizes `day`: a per-series daily resolution, with pick A's not-updated fallback where `day` has the gap rule. That difference is John's pick, named here so Review judges it as chosen, not as drift.

### §2.5 The matchers (per series, against the series payload the client already fetches)

`presented = day.presentedDay || day.date` (the exegesis resolver's own read).

- **saint-of-the-day** — the entry whose title starts with the presented day's `MM/DD` prefix (the ext slot's own matcher form; titles stand "11/25 - …"). Among matches, the latest `publishedMs`.
- **daily-gospel-exegesis** — the entry with `ownChicagoDateStr(publishedMs) === presented − 1` (the v611 rule, verbatim).
- **daily-readings** — the entry titled `Daily Mass Reading Podcast for <Month D, YYYY>` of the presented date; exact-trim first, contains second (the seat resolver's two-step, verbatim).
- **bible-in-a-year** — the sequence-payload entry whose `day` equals the presented date's day-of-year (Jan 1 = 1). The payload carries one entry per day number (the sequence build's own dedupe), so the match is unique.
- **catholicsaints** — the video whose title's leading `<Month> <D>:` names the presented date (the channel's own dating — PRIMARY, because the publish stamp is early-UTC: today's video published ~02:00Z, which is the previous Chicago evening, so a publish-date matcher would misfire by a day); fallback: `ownChicagoDateStr(publishedMs) === presented`.

**The not-updated fallback** (payload loaded, no match): the descriptor stands on the most recent entry that would have matched a day BEFORE the presented window — operationally: saint/exegesis/readings → the newest entry by `publishedMs` that precedes the presented match window (for readings, the entry titled for the greatest date ≤ presented); BIAY → the entry with the greatest `day` < day-of-year; video → the newest video preceding the presented date by the same title/publish order. The fallback descriptor carries `stale: true` — the standing v625 paint already stands at both row seats (trackCard client.ts:17807 · episode card :10741): "Today's episode has not updated yet — showing the last one that loaded." No new paint is built for the warning. If NO earlier entry exists at all, the item resolves nothing that build (named edge; the slot stands empty).

### §2.7 The duplication rule (named head-on, per the brief)

A block can already carry the same material through a standing seat. Within ONE block, the standing seat wins and the dynamic item for the same series resolves NOTHING:

- `daily:saint-of-the-day` yields to a `source` item keyed `ext-saint-of-the-day` in the same block.
- `daily:daily-readings` yields to a `seat` item keyed `daily-readings` in the same block.
- `daily:daily-gospel-exegesis` yields to a `day` item in the same block.

(Bible in a Year and the video series have no seat twin.) The ladder prevents the confusing state at the source: on a daily series' node, if the block already carries the seat twin, the Add daily row paints in the marked, not-tappable shape with the note naming the standing seat. Fixed episodes of the same series are separate items and coexist freely (the standing dedupe is per kind:key — `daily:<series>` dedupes against itself only, once per block).
