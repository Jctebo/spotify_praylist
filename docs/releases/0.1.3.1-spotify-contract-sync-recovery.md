# Release 0.1.3.1 - spotify-contract-sync-recovery

- Status: Shipped
- Created Date: 2026-03-27
- Shipped Date: 2026-03-27
- Roadmap: `docs/roadmaps/spotify-sync-audio-publishing-refactor.md`
- Notes: This release shipped the contract-first Spotify refresh path, aligned the active contract titles to the live Opus Dei rows, and retired the archived page-audio matrix from active automation.

## Scope

### Problem
- Daily Spotify refresh is off in both CI and the local runner, so Morning, Midday, Night, and Sunday are no longer updating.
- The first-pass recovery shape still keeps too much Spotify assembly truth in Opus Dei by requiring `Output Folder` to decide playlist membership.
- The current `config/spotify/*.json` model is too coarse because it only defines four grouped playlist files and does not expose the individual contracts that actually make up each playlist.
- Resolver identity is still too implicit. The desired repo contract surface should say which resolver code path each contract calls instead of leaving that mapping only in Opus Dei row fields.
- Because playlist membership and resolver choice are split between repo config and Notion metadata, the current direction still leaves the control plane harder to audit than it needs to be.

### Audience
- Primary user: the maintainer running daily Spotify prayer automation who wants one explicit repo contract per playable Spotify item.
- Secondary stakeholders: listeners who expect Morning, Midday, Night, and Sunday playlists to resolve from stable definitions instead of drift-prone Notion grouping.
- Secondary stakeholders: future collaborators who need to see which resolver code path a given Spotify item uses without reverse-engineering Notion rows.

### Current Status Quo
- `.github/workflows/daily.yml` and `scripts/run_daily_refresh_local.ps1` were previously disabled because the old Spotify sync path no longer matched the desired source-of-truth model.
- The current branch implementation under `jobs/playlist/spotify_contracts.py` and `jobs/playlist/refresh_playlist.py` loads one file per playlist from `config/spotify/` and maps Opus Dei rows onto those playlists through `Output Folder`.
- Queue item resolver choice still comes from Opus Dei row fields such as `Spotify Resolver`, `Spotify Fallback Resolver`, and `URI`.
- Sunday enablement also depends on the same `Output Folder` mapping, which means the branch still treats Opus Dei grouping as required Spotify configuration.
- `config/legacy/playlist_config.json` already shows a closer shape to the clarified requirement: a contract-like `catalog` of individual items plus playlist-like `profiles` that order those items.

### Goal
- Restore one working daily Spotify refresh path for Morning, Midday, Night, and Sunday.
- Remove `Output Folder` as a required Spotify grouping field in Opus Dei.
- Move resolver identity into repo-owned Spotify contracts so each contract explicitly declares which code resolver it uses.
- Replace the four grouped `config/spotify/*.json` files with a more specific contract model:
- one file per Spotify queue contract;
- thin playlist definitions that own playlist identity and ordered contract references.
- Keep single-playlist validation so one playlist can be refreshed in isolation before the full schedule is re-enabled.

### Constraints
- Do not require Opus Dei `Output Folder` for Spotify queue assembly in the clarified model.
- Do not hide resolver selection only in Notion row metadata; resolver identity must live in repo config.
- Reuse the existing resolver engine in `jobs/playlist/refresh_playlist.py` instead of rewriting the Spotify lookup logic from scratch.
- Preserve committed playlist IDs in git-managed config rather than moving playlist identity into deploy-time env vars.
- Keep writes to live Spotify playlists behind targeted validation until the new contract surface is proven.

### Narrow Wedge
- Introduce a repo-owned Spotify contract catalog with one file per contract item.
- Introduce thin playlist definition files that list ordered contract keys for Morning, Midday, Night, and Sunday.
- Cut the refresh runtime over so playlist assembly comes from repo config, not Opus Dei `Output Folder`.
- Keep Opus Dei out of required playlist grouping. If Notion stays in the loop at all, use an explicit contract key reference rather than `Output Folder`.
- Re-enable the local runner and workflow only after single-playlist validation succeeds against the new contract surface.

### Non-Goals
- Podcast publication.
- Morning Prayer publishing-boundary cleanup.
- ElevenLabs migration.
- Preserving `Output Folder` as a required Spotify assembly field just for compatibility.
- Keeping resolver truth primarily in Opus Dei row fields.
- Reintroducing the removed Notion Spotify Playlists database as a new compatibility layer.

### Risks And Unknowns
- The current branch already implements the older `Output Folder`-driven shape, so the clarified release now requires re-planning rather than only doc touch-ups.
- Some current helper names, tests, and docs assume one file per playlist and will need to be renamed or rewritten for the per-contract model.
- Sunday-specific behavior may need to move from `Output Folder` heuristics into explicit playlist definitions or explicit contract gating.
- If any Notion-side overlay remains, title-based matching would be too fragile; the clarified model should prefer an explicit contract key.
- Migrating from the current grouped files to contract files could cause short-term confusion unless the doc, tests, and setup scripts all move together.

### Recommended Next Step
- Re-plan Release `0.1.3.1` around a two-layer Spotify config model:
- `config/spotify/contracts/*.json` for individual resolver-backed items;
- `config/spotify/playlists/*.json` for playlist IDs and ordered contract membership.

## Research

### Scope Baseline
- The clarified requirement is no longer "one repo file per playlist." It is now "one repo file per contract item, with explicit resolver identity."
- Opus Dei should not be required to say Morning, Midday, Night, or Sunday through `Output Folder` for Spotify assembly.
- The refresh runtime should still reuse the existing `resolve_spec_uri(...)` path and playlist recreation code where possible.

### Relevant Files
- `jobs/playlist/spotify_contracts.py`
  - Current loader for the first-pass playlist-grouped model.
  - Today it expects `key`, `name`, `playlist_id`, and `output_folder`.
- `jobs/playlist/refresh_playlist.py`
  - Main Spotify runtime.
  - Today it maps Opus Dei rows onto selected playlists through `Output Folder`, then reads resolver values from those rows.
- `config/spotify/*.json`
  - Current first-pass grouped files: `morning.json`, `midday.json`, `night.json`, `sunday.json`.
- `config/legacy/playlist_config.json`
  - Legacy but useful design reference.
  - Already separates item-like `catalog` entries from playlist-like `profiles`.
- `tests/test_spotify_contracts.py`
  - Current tests for the grouped playlist-contract loader.
- `tests/test_refresh_job.py`
  - Current refresh-runtime tests.
  - Several cases still assume `Output Folder` mapping.
- `tests/test_refresh_job_contract_path.py`
  - Current tests for the first-pass contract path.
- `README.md`
  - Currently documents the older grouped-contract model and still describes `Output Folder` as required for Spotify rows.

### Current System Map
- The current branch implementation loads selected playlist contracts from `config/spotify/*.json`.
- Each current contract file owns:
  - `key`
  - `name`
  - `playlist_id`
  - `output_folder`
- `build_queue_for_playlist_from_notion(...)` currently:
  - selects one playlist contract;
  - normalizes each Opus Dei row's `Output Folder`;
  - maps that value onto the selected contract;
  - reads the row's `Spotify Resolver`, `Spotify Fallback Resolver`, and `URI`;
  - calls `resolve_spec_uri(...)` to build the final queue.
- `sync_notion_sunday_item_enablement(...)` uses the same `Output Folder` mapping to decide which rows count as Sunday rows.
- The legacy `config/legacy/playlist_config.json` provides a more specific split:
  - `catalog` describes individual resolver-backed queue items like `MORNING`, `ROSARY`, `SUNDAY_FRMIKE`, and `ANGELUS_SONG`;
  - `profiles` describe playlists and ordered membership.

### Reuse Opportunities
- Reuse `resolve_spec_uri(...)` and the existing Spotify resolver helpers as the runtime execution engine.
- Reuse the current single-playlist selector surface via `SPOTIFY_PLAYLIST_NAME`.
- Reuse the legacy `catalog` versus `profiles` idea as the structural template for the clarified repo config.
- Reuse committed playlist IDs and setup-script knowledge when creating thin playlist definition files.

### External References
- No external web research was required.
- Primary sources were local code, tests, legacy config, and the active release artifact.

### Constraints
- Fact: the current grouped loader in `jobs/playlist/spotify_contracts.py` hard-requires `output_folder`.
- Fact: the current refresh runtime resolves playlist membership through `Output Folder`.
- Fact: the README currently documents `Output Folder` as required for Spotify rows.
- Fact: the legacy playlist config already contains the individual resolver-backed item concepts the clarified model is asking for.

### Risks
- Highest risk: leaving resolver identity in Opus Dei would keep the new repo config too thin and preserve the same maintenance problem under a different folder shape.
- High risk: trying to preserve both the grouped playlist files and the new per-contract files would create two contract systems at once.
- Medium risk: Sunday-specific inclusion may be implicitly encoded today and will need to become explicit contract or playlist behavior.

### Assumptions To Validate
- Assumption: each Spotify queue item should become its own committed contract file.
- Assumption: each contract file should explicitly name the resolver string that will be passed into `resolve_spec_uri(...)`, or a direct Spotify URI when no resolver is needed.
- Assumption: Morning, Midday, Night, and Sunday should remain as playlist definitions, but not as the only contract files in `config/spotify/`.
- Assumption: if Notion remains in the runtime for optional enablement or annotations, it should use an explicit contract key rather than `Output Folder`.

### Unknowns
- No material architecture unknowns remain after choosing the repo-owned contract catalog.
- Implementation still needs to inventory any live Sunday-only rows and codify them as explicit contract files instead of preserving `Output Folder` inference.

### Recommended Direction
- Lean fully into the contract.
- Treat the legacy `catalog` / `profiles` split as the right conceptual model, but modernize it into committed JSON files:
- `contracts/*.json` for one contract per resolver-backed item;
- `playlists/*.json` for playlist IDs plus ordered contract membership.
- Remove `Output Folder` from the Spotify contract boundary and from the active playlist-refresh path entirely.
- Make the resolver binding and weekday gating explicit in the contract file itself instead of depending on Opus Dei rows or Sunday toggles.

## Plan

### Summary
- Replace the grouped `config/spotify/*.json` model with a two-layer Spotify config surface and make that repo config the only source of playlist assembly truth.
- Make each Spotify queue item its own JSON contract with explicit resolver metadata, optional fallback metadata, and optional weekday gating.
- Keep playlist files small: they should define playlist identity and ordered contract keys, not duplicate resolver details.
- Cut the refresh runtime over so it assembles queues from repo contracts only, with no required Opus Dei `Output Folder`, no Sunday row toggling, and no Notion dependency on the hot path.

### What Already Exists
- `jobs/playlist/refresh_playlist.py` already handles Spotify auth, playlist recreation, URI resolution, and selected-playlist execution.
- `resolve_item_uri(...)` and `resolve_spec_uri(...)` already provide the resolver engine we want to keep.
- `build_queue_for_profile(...)` already demonstrates the desired repo-first execution shape: ordered items from config, resolved into a queue without Notion grouping.
- `config/legacy/playlist_config.json` already contains the important domain model:
  - explicit queue-item identities;
  - ordered playlist membership;
  - canonical playlist IDs.
- `scripts/setup_spotify.ps1` already captures playlist IDs and can be updated to target thin playlist definition files instead of the current grouped contracts.
- `.github/workflows/daily.yml` and `scripts/run_daily_refresh_local.ps1` already expose the single-playlist validation surface via `SPOTIFY_PLAYLIST_NAME`.

### Architecture
- New source of truth:
- `config/spotify/contracts/*.json`
  - one file per resolver-backed Spotify queue contract.
- `config/spotify/playlists/*.json`
  - one file per Spotify playlist definition.
- Contract files own resolver identity and conditional inclusion rules.
- Playlist files own playlist identity and order.
- The active playlist-refresh path does not read Opus Dei rows to decide membership, order, or resolver choice.
- Sunday-only and Friday-only behavior move into explicit contract metadata instead of Notion enablement rules.
- Notion side effects, if kept at all, are optional post-write helpers and cannot be required for a base Spotify refresh run.

Example contract file:

```json
{
  "key": "morning-prayer-loh",
  "name": "Morning Prayer (LOH)",
  "resolver": "MORNING",
  "fallback_resolver": "DO_MORNING"
}
```

Example fixed-URI contract file:

```json
{
  "key": "angelus-song",
  "name": "Angelus Song",
  "spotify_uri": "spotify:track:39Jgl6ST4fQj4fNyRSQZFk"
}
```

Example weekday-gated contract file:

```json
{
  "key": "fr-mike-sunday-homily",
  "name": "Fr. Mike Sunday Homily",
  "resolver": "SUNDAY_FRMIKE",
  "weekdays": ["Sunday"]
}
```

Example playlist definition:

```json
{
  "key": "morning",
  "name": "Morning",
  "playlist_id": "0sy9eBsySKuCppI0PxXRJN",
  "contracts": [
    "morning-prayer-monthly",
    "rosary",
    "morning-prayer-loh",
    "angelus-song",
    "bible-in-a-year"
  ]
}
```

ASCII flow:

```text
config/spotify/playlists/morning.json
  -> ordered contract keys
  -> load contract files

config/spotify/contracts/*.json
  -> resolver / fallback_resolver / spotify_uri / weekdays
  -> contract_runs_today(weekday)
  -> resolve_spec_uri(...) or direct URI

resolved queue
  -> recreate_playlist_items(...)
  -> optional post-write Notion helpers if creds + flags are present
```

### UX And States
- There is no product UI in this release; the operator experience is the repo config, local runner, workflow logs, and explicit runtime errors.
- Success state:
- the selected playlist definition resolves all referenced contract files;
- each contract reports the resolver or direct URI it used;
- the playlist is recreated from the ordered contract list.
- Empty state:
- a playlist definition exists but every referenced contract is gated off for today or fails to resolve.
- Error state:
- duplicate contract keys;
- playlist references an unknown contract key;
- contract file has neither `resolver` nor `spotify_uri`;
- contract file has both `resolver` and `spotify_uri`;
- contract file names an unknown resolver;
- contract file declares an invalid weekday name;
- runtime still depends on `Output Folder` or `NOTION_TOKEN` anywhere in the active path.

### Failure Modes
- Playlist definition references a contract key that does not exist.
  - Detection: loader validation before any Spotify write.
  - User experience: fail immediately with the playlist file path and missing contract key.
- Contract file has no executable target.
  - Detection: contract has neither `resolver` nor `spotify_uri`.
  - User experience: fail immediately with the contract file path and missing field.
- Contract file is internally contradictory.
  - Detection: contract has both `resolver` and `spotify_uri`, or `fallback_resolver` without `resolver`.
  - User experience: fail immediately with the contract file path and the invalid field combination.
- Contract file names a resolver that the runtime does not know how to execute.
  - Detection: resolver validation or targeted runtime error during queue build.
  - User experience: fail before the selected playlist is written.
- Sunday-only or Friday-only items leak onto the wrong day.
  - Detection: weekday-gating tests and a manual `morning` versus `sunday` validation run.
  - User experience: listeners get the wrong seasonal or weekly content in a live playlist.
- Active path still depends on `Output Folder` or `NOTION_TOKEN`.
  - Detection: code review, tests, and a workflow run with only Spotify secrets present.
  - User experience: the supposed contract-first runtime still fails unless legacy Notion config is present.
