# Release 0.4.27.0: Devotional Wallpaper Render Telemetry

**Status:** Shipped | **Updated:** 2026-10-26

## Scope

### Problem
- Wallpaper run artifacts do not consistently expose how many image generations were attempted for each asset, especially when transient request retries occur.
- The available history is insufficient to tell whether watch images commonly need regeneration or whether high-spend days came from unusually large batches or retries.

### Audience
- Primary user: repository maintainer reviewing OpenAI image costs and wallpaper quality outcomes.
- Secondary stakeholders: maintainers diagnosing failed or expensive wallpaper runs.

### Current Status Quo
- `render_variant` records successful QA attempts in a run manifest, but transport errors retried by the caller are not included in that count.
- GitHub Actions uploads each run's artifact for 30 days. There is no cumulative trend report or scheduled review.

### Goal
- Record one privacy-safe telemetry row per wallpaper asset with variant, run/date identifiers, image generation attempt count, transient retry count, QA outcomes/reasons, accepted/fallback status, model, size, quality, and timestamps.
- Retain per-run telemetry in the GitHub Actions artifact and keep a cumulative telemetry history in the existing private OneDrive wallpaper manifest area.
- Provide an analyzer that summarizes retry and QA rates over time, especially watch versus phone, including safe QA issue categories without storing prompts, generated images, OCR text, or credentials.
- Schedule a recurring monthly analysis and evidence-based code review. Preserve current image quality and generation behavior unless a later change is supported by the collected evidence.

### Constraints
- Do not change image model, requested size/quality, QA checks, or retry limits in this telemetry change.
- Do not store prompts, image bytes, full OCR text, API keys, or other secrets in telemetry.
- A telemetry persistence failure must not silently discard the run's local artifact; report the error clearly while preserving generation behavior.

### Success Criteria
- Every attempted asset has a structured telemetry record, including failed provider calls and retries.
- A completed wallpaper run produces a per-run JSONL/JSON artifact and updates a durable cumulative private history.
- A local analyzer can summarize attempts, retry counts, QA failures, and cost-relevant image counts by date and variant from accumulated data.
- The Actions artifact retention is long enough for convenient retrieval, while durable history does not depend on artifact retention.
- A monthly recurring review is configured to analyze new history and propose/implement only evidence-backed, quality-preserving changes.

### Narrow Wedge
- Add telemetry at the existing render and retry boundaries, persist a compact cumulative JSON history beside private run manifests, and add a deterministic analyzer plus a scheduled assistant review.
- Download cumulative history with `rclone copyto "$RCLONE_REMOTE_NAME:$RCLONE_REMOTE_ROOT/.devotional_wallpapers/manifests/telemetry.json" artifacts/wallpaper-telemetry.json`; analyze it with `python scripts/analyze_wallpaper_telemetry.py artifacts/wallpaper-telemetry.json`.

## Research

- The image request is created by `generate_artwork` in `jobs/novena/devotional_wallpaper_render.py`; the surrounding `render_variant` loop permits up to three QA-driven generations.
- `run_pipeline` in `jobs/novena/generate_devotional_wallpapers.py` has a separate three-attempt retry loop for transient failures, which can rerun the full render-and-QA operation.
- The remote OneDrive abstraction already supports read/write JSON under `.devotional_wallpapers/manifests/`, and the workflow uploads `artifacts/devotional-wallpapers/` after each run.
- The current GitHub Actions upload retention is 30 days. Durable history therefore belongs in the private remote manifest area; artifacts remain useful for individual run inspection.
- Existing render summaries include `render_attempts` and QA outcomes when rendering returns normally, but the accumulated history does not capture the detailed generation attempt sequence or separate transient retries.
