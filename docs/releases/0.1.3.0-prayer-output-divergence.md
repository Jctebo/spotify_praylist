# Release 0.1.3.0 - prayer-output-divergence

- Status: Shipped
- Shipped Version: 0.1.3.0
- Shipped Date: 2026-03-27
- Notes: This artifact preserves the original scope, research, and implementation plan that guided the shipped fix.

## Scope

### Problem
- Multiple prayer outputs are collapsing into the same Morning Prayer content, which means the page audio and page content are no longer reflecting the distinct contract or builder that was selected.
- Rosary and Morning Prayer output files are also missing from the expected file locations, so the pipeline is not materializing the full prayer set that the repo already knows how to generate.
- The bug is user-visible in two ways: the content is wrong, and some expected prayer files are absent, which makes the workflow look like it succeeded while producing the wrong devotional artifacts.
- This needs to be fixed now because the daily devotional pipeline is already shipping, so one bad resolver can quietly poison multiple prayer outputs at once.

### Audience
- Primary user: the maintainer who expects each prayer contract to generate its own distinct audio and page content.
- Secondary stakeholders: anyone consuming the daily devotional outputs from OneDrive or Notion who depends on Rosary and Morning Prayer appearing as separate artifacts.

### Current Status Quo
- `jobs/notion/generate_page_audio.py` already contains a large contract-and-builder system for Morning Prayer, Rosary, Divine Office, Sing the Hours, and other prayer variants.
- `jobs/notion/generate_prayer.py` is the Morning Prayer runner entrypoint and selects a page by title before delegating into the page-audio planner.
- The repo has root-level contract files like `config/morning-prayer.json` and `config/rosary.json`, plus many other `config/*.json` pages, but the generation flow appears to be reusing the Morning Prayer branch for multiple outputs.
- The shipped workflow currently fans out over the contract set, which means a shared planner/resolver bug can make many outputs look identical even when the matrix rows are distinct.

### Goal
- Restore one distinct audio/content output per prayer contract or builder.
- Make Morning Prayer, Rosary, and the other prayer families produce their own files and page content instead of collapsing into Morning Prayer.
- Ensure the expected Morning Prayer and Rosary files are emitted to the right file locations so downstream syncs can see them.
- Keep the fix small enough that it addresses the shared resolver/planner bug without rewriting the whole devotional pipeline.

### Constraints
- Do not break the working calendar-first devotional pipeline or the page-audio OneDrive sync that was already shipped.
- Preserve the existing contract-driven workflow shape.
- Keep the fix aligned with the repo's current root-level `config/*.json` contract layout.
- Avoid hardcoding another special-case path; the bug should be fixed in the resolver/planner boundary, not by patching one filename at a time.

### Narrow Wedge
- Trace the shared planner path that determines which prayer content is rendered for audio and page content.
- Identify why distinct contracts are all resolving to the same Morning Prayer output.
- Fix the selection/handoff layer so Rosary and Morning Prayer each write their own expected artifacts.
- Add regression coverage for the distinct-output cases that are currently collapsing.

### Non-Goals
- Rewriting the entire prayer-generation engine.
- Changing the devotional calendar job that already ships images and novenas correctly.
- Redesigning the prayer content schema or the OneDrive upload architecture.
- Adding new prayer families beyond the ones already represented in the repo.

### Risks And Unknowns
- The shared audio/page-content planner may be too broad, so the same fallback could be affecting multiple contract families.
- The missing files may be a symptom of the wrong output folder or file-stem calculation rather than a pure content-selection bug.
- Rosary and Morning Prayer might depend on different contract keys, builders, or page titles, so the fix may need to touch both the resolver and the file-emission path.
- If the root cause lives in a generic helper, fixing only the Morning Prayer entrypoint will leave the other prayer families broken.

### Recommended Next Step
- The shipped work kept the fix focused on the shared contract-loader and page-resolution boundaries rather than rewriting the larger prayer pipeline.

## Research

### Scope Baseline
- Morning Prayer and Rosary are supposed to land as distinct ordered files in `Morning/`, with the user expecting `1.01` for Morning Prayer and `1.02` for Rosary.
- The earlier builder-normalization fix addressed the wrong-content fallback, but the missing-file symptom remained.
- The key question for this pass was whether `1.01` and `1.02` were disappearing during OneDrive sync or never being produced in the row artifacts in the first place.

### Relevant Files
- `.github/workflows/daily_novena_prayer.yml`
  - Builds the matrix from `config/*.json`, passes each file into `PAGE_AUDIO_CONFIG_FILE`, uploads each row artifact, then merges and syncs to OneDrive.
- `jobs/notion/generate_page_audio.py`
  - `load_page_audio_config_from_file(...)` decides which configs are runnable.
  - `main()` iterates `payload["configs"]`, not the raw selected file path.
  - `page_audio_export_metadata(...)` and `persist_page_audio_output_library(...)` produce the ordered `Morning/<order> - ...` exports.
- `jobs/notion/generate_prayer.py`
  - Already acts as a true single-contract runner for Morning Prayer, which is a reusable pattern.
- `config/morning-prayer.json`
  - Distinct Morning Prayer contract with `header.builder = "morning_prayer_v1"`.
- `config/rosary.json`
  - Distinct Rosary contract with `header.builder = "rosary_v1"`.
- `tests/test_page_audio_job.py`
  - Covers export naming and config loading, but not the current workflow mistake where a raw contract file is passed to the multi-config runner.

### Current System Map
- The workflow matrix enumerates every top-level `config/*.json` file and sets `PAGE_AUDIO_CONFIG_FILE` for each row.
- `load_page_audio_config_from_file(...)` does not treat an arbitrary selected file as a runnable config row. Instead it builds `configs` by scanning `config/*.json` and explicitly skips:
  - `morning-prayer.json`
  - `rosary.json`
  - `page_audio_config.json`
  - `playlist_config.json`
  - `notion_spotify_sync_config.json`
- `main()` in `generate_page_audio.py` only executes entries from `payload["configs"]`.
- `config/morning-prayer.json` is loaded separately into `payload["morning_prayer_contract"]` for Morning Prayer builder internals, but it is not inserted into `payload["configs"]` as a runnable row.
- `config/rosary.json` is not inserted into `payload["configs"]` either; Rosary only runs when some other runnable config points at `rosary_contract_file`.
- Result: the matrix rows named `config/morning-prayer.json` and `config/rosary.json` still execute the generic page-audio configs such as:
  - `divine_office_invitatory_page_audio`
  - `sing_the_hours_morning_page_audio`
  - `bible_in_a_year_page_audio`
  - `daily_mass_readings_page_audio`
  - other bundled page-audio rows
- This means the missing `Morning/1.01` and `Morning/1.02` outputs are failing before the OneDrive sync step.

### Reuse Opportunities
- Reuse `generate_prayer.py` as the model for a true single-contract execution path.
- Reuse the normalized contract handling already added to `generate_page_audio.py` once the selected contract is actually admitted into `payload["configs"]`.
- Reuse `page_audio_export_metadata(...)` and the existing ordered-output tests; the folder/stem code is already correct when it receives the intended page and config.

### External References
- GitHub Actions run `23574689131`
  - The `config/morning-prayer.json` row logged `page_audio title=Afternoon Prayer (LOH)`, `Bible in a Year`, `Divine Office Invitatory`, `Night Prayer (LOH)`, and `Morning Prayer (LOH)`, proving that row did not execute only Morning Prayer.
  - The `config/rosary.json` row logged `page_audio title=Morning Prayer (LOH) sing_the_hours_morning_page_audio`, not a Rosary config key.
- Downloaded artifacts from run `23574689131`
  - `page-audio-library-10` from the `config/morning-prayer.json` row contained only `Morning/1.03`, `1.04`, `1.05`, plus Midday and Night files.
  - `page-audio-library-11` from the `config/rosary.json` row contained the same path set.
  - Neither artifact contained `Morning/1.01` or `Morning/1.02`.
  - The `1.04 - Morning - Morning Prayer (LOH).json` metadata in both artifacts reports `config_key: "sing_the_hours_morning_page_audio"`, not `morning-prayer` or `rosary`.

### Constraints
- The workflow currently assumes each matrix row produces one self-contained `page_audio_library` subtree.
- `PAGE_AUDIO_FAIL_OPEN=true` lets the row exit with overall success even when some intended pages fail or never run.
- `merge-multiple: true` in artifact download means identical output paths from multiple rows overwrite each other during fan-in.

### Risks
- Primary risk: the workflow gives a false sense that Morning Prayer and Rosary "ran" because the matrix row names say so, while the underlying runner never included those contracts in `configs`.
- Secondary risk: multiple rows currently emit the same `Morning/1.03`, `1.04`, and `1.05` paths, so artifact fan-in can overwrite files nondeterministically.
- Tertiary risk: the `rclone` hash-mismatch noise is real, but it is downstream of the missing-file bug and can distract from the pre-sync orchestration failure.

### Assumptions To Validate
- The intended remote outputs are `Morning/1.01` for Morning Prayer and `Morning/1.02` for Rosary, as the user clarified.
- The workflow should treat `config/morning-prayer.json` and `config/rosary.json` as first-class runnable contracts, not just auxiliary data files.
- The remaining OneDrive integrity investigation should only continue after the row artifacts contain the correct local files.

### Unknowns
- Whether the cleanest implementation is:
  - adding a true "single raw contract file" mode to `generate_page_audio.py`, or
  - invoking dedicated runners for special contract families such as Morning Prayer and Rosary.
- Whether Rosary should get its own small runner, analogous to `generate_prayer.py`, or be absorbed into the generic runner path.
- Whether `rclone check` is fully passing after retry or whether only the sync phase is recovering enough to return exit `0`.

### Recommended Direction
- The shipped implementation treated the missing `Morning/1.01` and `Morning/1.02` files as a workflow and loader bug first, then tightened the sync safety rails around the resulting page-audio uploads.

## Plan

### Summary
- The shipped implementation made each workflow matrix row execute exactly one selected contract file instead of silently rebuilding the shared bundled config set.
- It kept the existing builder branches, export metadata, artifact fan-in, and OneDrive sync path, while making `config/morning-prayer.json` and `config/rosary.json` runnable as direct page-audio configs.
- It also added explicit sync-safety checks so failed matrix rows cannot purge and replace the remote audio library with partial output.

### What Already Exists
- `jobs/notion/generate_page_audio.py` already knows how to plan and render Morning Prayer, Rosary, RSS-backed rows, and fragment-backed rows once a runnable config is in `payload["configs"]`.
- The earlier normalization helper already promotes `header.builder` into top-level `builder` for file-backed contracts.
- `jobs/notion/generate_prayer.py` already shows the desired single-contract execution pattern for a contract file.
- The workflow already has the matrix, artifact upload, artifact merge, and OneDrive sync stages we want to keep.

### Architecture
- Keep `generate_page_audio.py` as the main runner, but add a true "selected contract file" path in the file loader.
- When `PAGE_AUDIO_CONFIG_FILE` points to a concrete contract file, load only that file into `payload["configs"]` and do not auto-scan the whole `config/` directory for peers.
- Preserve the existing full-scan behavior only for the default local multi-config mode.
- Keep the export and sync stages unchanged enough that the remote test remains apples-to-apples.

ASCII flow:
```text
workflow matrix row
    |
    v
PAGE_AUDIO_CONFIG_FILE=config/<selected>.json
    |
    v
load only selected contract into payload["configs"]
    |
    v
shared planner / builder selection
    |
    +--> Morning Prayer contract -> Morning/1.01 ...
    +--> Rosary contract -> Morning/1.02 ...
    +--> other single config rows -> their own managed outputs
    |
    v
row artifact
    |
    v
merged library -> OneDrive sync
```

### Concrete Changes
- `jobs/notion/generate_page_audio.py`
  - Add a helper that resolves the selected config path and decides whether the run is in single-contract mode or default multi-config mode.
  - When running in single-contract mode, admit the selected file into `payload["configs"]` even for `morning-prayer.json` and `rosary.json`.
  - Preserve normalization so `builder` promotion still happens for raw contract files.
- `.github/workflows/daily_novena_prayer.yml`
  - Keep the current matrix shape, artifact upload, purge, sync, and `rclone check`.
  - Do not change the remote contract list unless the loader fix proves insufficient.
- `tests/test_page_audio_job.py`
  - Add loader regressions for selected single-file mode using:
    - a generic page-audio config file
    - `config/morning-prayer.json`
    - `config/rosary.json`
  - Add a regression that single-file mode does not leak peer configs into the runnable config map.
- `README.md`
  - Clarify that `PAGE_AUDIO_CONFIG_FILE` now runs only the selected contract file when it points at a specific JSON contract.
