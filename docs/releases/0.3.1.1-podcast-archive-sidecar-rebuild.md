# Release 0.3.1.1 - Podcast Archive Sidecar Rebuild

Date: 2026-05-02
Status: Shipped
Branch: fix/podcast-archive-cache-fallback
Depends On: 0.3.1.0

## Scope

### Problem
- The podcast feed rebuild still depends on the remote published `podcast.xml`, so a 404 or delayed Pages deploy can abort publishing even when the new episode audio has already been rendered.
- We want the feed to be rebuilt idempotently from the local publish artifacts instead of from the remote site archive.
- The public site root currently returns 404 for visitors in at least one deployed state, so there is no dependable landing page for people trying to inspect what is published.
- We want a public archive dashboard that shows what files and feed entries are actually in GitHub Pages, not just the raw feed URL.
- Why now: the archive source of truth is too fragile, and a publish run should not fail just because GitHub Pages does not yet have the previous feed file.

### Audience
- Primary user: the maintainer who runs the publish audio workflow and needs it to rebuild the feed reliably on every run.
- Secondary stakeholders: listeners who should keep seeing the full back catalog in the podcast feed.
- Secondary stakeholders: future maintainers who need a simple, local source of truth for feed history.
- Secondary stakeholders: anyone landing on the Pages root and needing to confirm the site is live and where the archive lives.

### Current Status Quo
- `jobs/publish/audio.py` writes each episode to `docs/audio/<episode_id>.mp3` and writes a JSON sidecar next to it.
- `jobs/publish/run_audio_pipeline.py` currently asks the RSS loader to recover history from the published feed before writing the new XML.
- `jobs/publish/rss.py` already knows how to parse RSS items, but it does not rebuild history by scanning local sidecars and audio files.
- `docs/podcast.xml` is tracked in the repo, but it is empty in this checkout.
- `docs/audio/` is not present in this checkout, which shows the archive is generated during publish runs rather than maintained in source control.
- The workflow deploys `docs/` to GitHub Pages, so the generated feed and MP3s live there after publish, not in the repository history.
- `docs/index.html` exists as the intended Pages landing page, but the live root can still 404 if the site has not been deployed or the artifact is not being served yet.
- There is no dedicated archive listing page that shows the deployed feed, MP3s, and sidecars in one place.

### Goal
- Rebuild `docs/podcast.xml` deterministically from local JSON sidecars and MP3 files.
- Make the podcast feed output idempotent for the same archive contents.
- Stop relying on the remote GitHub Pages feed as the only archive source.
- Ensure the Pages root has a useful landing page that does not 404 and points people to the archive.
- Add a browsable archive page or section that lets someone see what files are currently published in Pages.
- Success criteria: if the local archive files exist, the feed can be rebuilt without the remote `podcast.xml` being reachable.

### Constraints
- Preserve episode IDs, RSS GUIDs, audio enclosure URLs, and published dates.
- Keep the existing public output shape under `docs/audio/*.mp3` and `docs/podcast.xml`.
- Do not add a new database or external storage service.
- Keep the archive format compatible with the current publish workflow so the same sidecars remain usable.
- Avoid broad changes to the Spotify or novena publish paths.
- Keep the public site rooted in static files that GitHub Pages can serve without a runtime backend.

### Narrow Wedge
- Scan the local publish archive under `docs/audio/` for JSON sidecars and their matching MP3 files.
- Rebuild the RSS archive from those local artifacts first, with remote recovery removed or left as a temporary fallback only if absolutely needed.
- Publish a root landing page and a dedicated archive index that point to the feed, MP3s, and any sidecar listings.
- Keep the change focused on the audio publish path and RSS merge helpers.

### Non-Goals
- Do not redesign episode naming or the RSS schema.
- Do not change the audio generation or TTS behavior.
- Do not add a new persistence layer.
- Do not expand into the novena pipeline or Spotify playlist refresh logic.
- Do not build a server-side app behind GitHub Pages; this remains static publishing only.

### Risks And Unknowns
- `docs/audio/` does not exist in this checkout, so we need to confirm which job or artifact is supposed to create and preserve it across runs.
- If sidecars or MP3 files are missing, we need to decide whether that means partial publish failure or simply an empty archive.
- It is not yet clear whether the local archive scan should treat MP3 existence as required or just use the JSON sidecar metadata.
- We need to make sure the rebuild stays deterministic so identical inputs always produce the same RSS output.
- We need to confirm whether the 404 at the site root is a missing index artifact, a Pages deployment problem, or both.
- We need to decide whether the archive index should live at `/` or at a separate `/archive/` path linked from the root.

### Recommended Next Step
- Run `/research-astack` to map where the JSON sidecars and MP3s are created, how they are preserved across runs, and whether the archive scan should live in the runner, the RSS helper, or both.
- Also verify the deployed Pages root behavior so the research covers both archive rebuilds and the 404 landing-page problem.

## Research

### Scope Baseline
- The scoped task is to rebuild podcast RSS deterministically from local publish artifacts, while also fixing the GitHub Pages root so visitors do not land on a 404.
- The current archive input is the remote published feed, but that dependency is fragile and the local publish artifacts already exist as the more durable source.
- The Pages site should expose a static landing page plus an archive index so users can see what has actually been published.

### Relevant Files
- `jobs/publish/audio.py` - owns audio output paths, sidecar naming, and public URL construction for episodes.
- `jobs/publish/run_audio_pipeline.py` - currently loads archive history before writing the RSS feed, so it is the runner seam for changing archive sourcing.
- `jobs/publish/rss.py` - parses RSS items and merges archive jobs; this is the feed-rebuild seam.
- `docs/index.html` - the existing GitHub Pages landing page and the natural place to fix the root 404 and point people at the archive.
- `docs/podcast.xml` - the public RSS output in the repo, currently empty in this checkout.
- `.github/workflows/publish_audio.yml` - publishes the generated `docs/` tree to GitHub Pages and is the deployment boundary for the archive.
- `tests/test_publish_audio_pipeline.py` - current regression coverage for feed recovery and runner behavior.
- `jobs/novena_contracts/rss_publisher.py` - nearby example of reusing the RSS merge helpers with in-memory current jobs.

### Current System Map
- `jobs/publish/audio.py` writes `docs/audio/<episode_id>.mp3` plus `docs/audio/<episode_id>.json` sidecars during publish runs.
- `jobs/publish/run_audio_pipeline.py` renders current jobs, then tries to recover archive history before writing `docs/podcast.xml`.
- `jobs/publish/rss.py` currently expects archive history from the local feed file or the remote published feed, not from a local archive scan.
- `docs/index.html` already links to `/podcast.xml` and `/audio/`, but the live site root can still 404 if the Pages artifact is missing or stale.
- `docs/audio/` is not checked in, so the repository itself does not currently carry the back catalog.

### Reuse Opportunities
- Reuse the existing `docs/audio/<episode_id>.mp3` and `docs/audio/<episode_id>.json` naming pattern as the archive source of truth.
- Reuse the RSS parsing and merge helpers in `jobs/publish/rss.py` instead of inventing a new feed writer.
- Reuse `docs/index.html` as the static landing page and expand it into an archive entrypoint rather than introducing a server-backed surface.
- Reuse the current GitHub Pages deployment path that already publishes the `docs/` tree.

### External References
- GitHub Pages is the hosting layer for the public archive, but it is not a durable runtime database.
- The podcast feed should remain a static `podcast.xml` artifact under the published site.

### Constraints
- The local archive scan has to work in the ephemeral CI workspace where `docs/audio/` may not already exist.
- The feed output must stay stable enough that podcast clients do not treat a rebuild as a new show.
- The root page and archive index must be static files so they can be published with the same Pages artifact as the feed.
- The rebuild needs to be deterministic from the same local artifacts.

### Risks
- If `docs/audio/` is not preserved across runs, a local rebuild still starts empty on a fresh checkout.
- If the rebuild trusts sidecars without checking MP3 presence, it can preserve broken archive entries.
- If the Pages root is not deployed with the artifact, the site can still 404 even when the feed exists.
- If the archive index is too broad, it can become a second source of truth instead of a view over the first one.

### Assumptions To Validate
- The intended archive source is the publish workspace’s `docs/audio/` tree, not the remote GitHub Pages feed.
- Sidecar JSON plus MP3 presence is enough to reconstruct the feed history.
- The site root should be served from the same `docs/` artifact and should never require a backend.
- A simple static archive index is sufficient; there is no need for a dynamic browser app.

### Unknowns
- Whether the archive scan should read only JSON sidecars or JSON plus MP3 files.
- Whether the archive index should live at `/` or under a separate `/archive/` path.
- Whether the site root 404 is a missing `index.html`, a Pages deployment issue, or both.
- Whether the remote feed should remain a temporary fallback during the transition.

### Recommended Direction
- Make the local `docs/audio/` archive the source of truth for RSS rebuilds, keep a static landing page at the site root, and expose a browsable archive index for the published files. Use the remote feed only as a temporary compatibility fallback while verifying the local archive is complete and deterministic.

## Plan

### Summary
- Rebuild `docs/podcast.xml` from the published audio archive instead of from the remote feed archive.
- Treat the published `docs/audio/` tree as the durable archive surface, with `docs/audio/*.json` sidecars and matching `.mp3` files as the inputs to each rebuild.
- Keep GitHub Pages as the public store for the feed, the MP3s, the sidecars, and the archive listing page.
- Preserve `docs/index.html` as the root landing page and add a browsable archive dashboard under `docs/audio/` so the site no longer feels like a dead end.
- Use the remote feed only as a short migration fallback while the new archive-backed flow proves itself in CI.

### What Already Exists
- `jobs/publish/audio.py` already writes `docs/audio/<episode_id>.mp3` and the matching JSON sidecar, and it already has `load_published_audio_jobs(...)` for rebuilding episode metadata from local sidecars.
- `jobs/publish/rss.py` already deduplicates and sorts RSS jobs by `published_date` and `episode_id` before writing the feed.
- `jobs/publish/run_audio_pipeline.py` already renders the current run and writes `docs/podcast.xml`.
- `docs/index.html` already exists as the public GitHub Pages landing page and already links to the feed and generated audio folder.
- `.github/workflows/publish_audio.yml` already publishes the full `docs/` tree to GitHub Pages.
- `tests/test_publish_audio_pipeline.py` already covers audio rendering, RSS generation, archive loading behavior, and the publish workflow text.

### Architecture
- Current run:
  - render current audio jobs
  - write the current run's `.mp3` files and JSON sidecars under `docs/audio/`
  - restore the previously published archive snapshot into the local `docs/audio/` tree
  - load archive jobs from the local sidecars
  - merge current jobs and archive jobs
  - build RSS
  - write `docs/podcast.xml`
  - publish the finished `docs/` tree to GitHub Pages
- Archive files:
  - `docs/audio/*.mp3` are the public enclosures
  - `docs/audio/*.json` are the archive metadata sidecars
  - `docs/audio/index.html` is the human-facing archive dashboard
  - `docs/audio/index.json` is the machine-readable manifest used to restore the archive on the next run
- Determinism:
  - `build_rss_feed(...)` remains the single RSS writer and keeps the sort/dedupe rules stable.
  - The local archive scan must preserve `episode_id`, `published_date`, `rss_guid`, `audio_url`, and `audio_length` so rebuilding the same archive produces the same XML.

```text
Published Pages archive
   |
   +--> /audio/index.json  (restore manifest for the next run)
   +--> /audio/index.html  (human archive browser)
   +--> /audio/*.json      (episode sidecars)
   +--> /audio/*.mp3       (episode audio)
              |
              v
      restore into local docs/audio/
              |
              v
   load_published_audio_jobs(...)
              |
              v
    merge current + archived jobs
              |
              v
        build_rss_feed(...)
              |
              v
         docs/podcast.xml
```

### Concrete Changes
- `jobs/publish/audio.py`
  - Keep `load_published_audio_jobs(...)` as the local archive reader.
  - Tighten the archive reader so only complete archive entries are emitted: valid sidecar plus matching `.mp3`.
  - Preserve the fields needed by the RSS writer and archive index: `episode_id`, `published_date`, `rss_guid`, `audio_url`, `audio_length`, `generated_at`, `title`, and `description`.
- `jobs/publish/run_audio_pipeline.py`
  - Switch the archive source to the local `docs/audio/` archive rather than treating the remote `podcast.xml` as the canonical archive.
  - Keep the remote feed only as a temporary migration fallback for seed runs where the local archive has not been restored yet.
  - Merge current rendered jobs with archive jobs before calling `build_rss_feed(...)`.
- `jobs/publish/rss.py`
  - Keep `build_rss_feed(...)` as the only RSS emitter.
  - Keep the current deterministic sort order intact so rebuilds from the same archive stay byte-stable except for expected timestamp changes.
  - Keep `load_podcast_feed_jobs(...)` only as a compatibility bridge during migration, not as the long-term source of truth.
- `docs/index.html`
  - Keep the root landing page static and obvious.
  - Add a direct link to the archive dashboard so visitors can move from the home page to the file listing without guessing.
- `docs/audio/index.html`
  - Add a browsable archive dashboard that lists each published episode, its publish date, its MP3, and its JSON sidecar.
  - Show a clear empty state if the archive is not yet seeded.
- `docs/audio/index.json`
  - Add a machine-readable archive manifest that the workflow can restore before the next publish run.
  - Keep it in sync with the HTML archive listing so human and machine views show the same archive set.
- `.github/workflows/publish_audio.yml`
  - Publish the full `docs/` tree, including the root landing page and archive dashboard.
  - Add the archive restore step that seeds local `docs/audio/` from the previously published Pages archive before the RSS rebuild.
  - Keep the fragment cache behavior untouched.
- `tests/test_publish_audio_pipeline.py`
  - Add coverage for the local archive scan, the restore path, the archive manifest/dashboard shape, and the current-run plus archive merge.
  - Keep the existing feed and workflow regression tests as the safety net.

### UX And States
- Root landing page:
  - Success: `https://jctebo.github.io/spotify_praylist/` loads a static page with clear links to the feed and archive.
  - Empty: if the archive has not been seeded yet, the landing page still loads and explains where the feed and archive live.
  - Error: a Pages deployment problem should be visible as a root-page failure, not as a hidden feed-only problem.
- Archive dashboard:
  - Success: `/audio/index.html` lists the published episodes and links to their `.mp3` and `.json` assets.
  - Empty: the page shows that the archive is not seeded yet instead of failing.
  - Partial: missing sidecars or missing MP3s are omitted from the listing and logged as warnings so the dashboard never advertises broken links.
- RSS feed:
  - Success: `podcast.xml` is rebuilt deterministically from the current jobs plus the local archive jobs.
  - Empty: first-run publishes still emit a valid feed for the current run and seed the archive.
  - Error: current-run audio rendering failures still fail the workflow, because no valid new artifact was produced.

### Failure Modes
- If a sidecar exists without a matching MP3, the archive listing should omit the entry and log a warning instead of publishing a broken link.
- If the archive restore step cannot hydrate `docs/audio/`, the run should still seed the current episode and publish a valid feed, but the archive history will be incomplete until the next successful restore.
- If the root page is missing from the Pages artifact, the site can still 404 even if the feed exists, so the workflow must continue publishing the entire `docs/` tree.
- If `build_rss_feed(...)` stops sorting or deduping deterministically, podcast clients could see unnecessary feed churn.
- If the archive manifest and the archive HTML diverge, the workflow will be hard to trust because humans and the runner will be looking at different archive sets.

### QA And Test Matrix
- Unit tests:
  - `python -m unittest tests.test_publish_audio_pipeline`
- Targeted behavior checks:
  - local archive scan returns only complete entries
  - current-run jobs still render when the archive is empty
  - RSS output still contains stable GUIDs and enclosures
  - archive dashboard and manifest stay in sync
- Workflow checks:
  - publish workflow still deploys `docs/` to GitHub Pages
  - root landing page is reachable at `/`
  - archive dashboard is reachable at `/audio/`
  - `podcast.xml` is reachable at `/podcast.xml`
- Regression cases:
  - first successful run after seeding the archive
  - a run where a sidecar exists but the MP3 is missing
  - a run where the Pages restore yields no prior archive files

### Rollout Notes
- Keep the migration fallback only long enough to seed the first archive-backed rebuild.
- Do not change episode IDs, feed GUIDs, or enclosure URL shapes during the transition.
- After one or more successful archive-backed runs, remove any remaining remote-feed dependency so the local archive scan is the only long-term path.
- If the public root still 404s after the static file changes, treat that as a Pages deployment regression and fix the deployment boundary rather than the archive logic.

### Not In Scope
- Do not add a database or any new external storage service.
- Do not rewrite the audio synthesis pipeline or the contract-driven episode generation rules.
- Do not change Spotify playlist logic, novena publishing logic, or Notion text publishing logic.
- Do not introduce a server-backed browsing app behind GitHub Pages.
- Do not redesign episode identity, RSS schema, or enclosure URL structure.

### Open Questions
- None after the scope and research pass. The archive should live in the published Pages tree, the rebuild should read from the local archive snapshot, and the public site should expose both a landing page and a browsable archive dashboard.
