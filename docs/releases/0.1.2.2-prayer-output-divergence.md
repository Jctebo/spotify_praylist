# Release 0.1.2.2 - prayer-output-divergence

- Status: Draft

## Scope

### Problem
- Multiple prayer outputs are collapsing into the same Morning Prayer content, which means the page audio and page content are no longer reflecting the distinct contract or builder that was selected.
- Rosary and Morning Prayer output files are also missing from the expected file locations, so the pipeline is not materializing the full prayer set that the repo already knows how to generate.
- The bug is user-visible in two ways: the content is wrong, and some expected prayer files are absent, which makes the workflow look like it succeeded while producing the wrong devotional artifacts.
- This needs to be fixed now because the daily devotional pipeline is already shipping, so one bad resolver can quietly poison multiple prayer outputs at once.

### Audience
- Primary user: the maintainer who expects each prayer contract to generate its own distinct audio and page content.
- Secondary stakeholders: anyone consuming the daily devotional outputs from OneDrive or Notion who depends on Rosary and Morning Prayer appearing as separate artifacts.

### Current Status Quo
- `jobs/notion/generate_page_audio.py` already contains a large contract-and-builder system for Morning Prayer, Rosary, Divine Office, Sing the Hours, and other prayer variants.
- `jobs/notion/generate_prayer.py` is the Morning Prayer runner entrypoint and selects a page by title before delegating into the page-audio planner.
- The repo has root-level contract files like `config/morning-prayer.json` and `config/rosary.json`, plus many other `config/*.json` pages, but the generation flow appears to be reusing the Morning Prayer branch for multiple outputs.
- The shipped workflow currently fans out over the contract set, which means a shared planner/resolver bug can make many outputs look identical even when the matrix rows are distinct.

### Goal
- Restore one distinct audio/content output per prayer contract or builder.
- Make Morning Prayer, Rosary, and the other prayer families produce their own files and page content instead of collapsing into Morning Prayer.
- Ensure the expected Morning Prayer and Rosary files are emitted to the right file locations so downstream syncs can see them.
- Keep the fix small enough that it addresses the shared resolver/planner bug without rewriting the whole devotional pipeline.

### Constraints
- Do not break the working calendar-first devotional pipeline or the page-audio OneDrive sync that was already shipped.
- Preserve the existing contract-driven workflow shape.
- Keep the fix aligned with the repo’s current root-level `config/*.json` contract layout.
- Avoid hardcoding another special-case path; the bug should be fixed in the resolver/planner boundary, not by patching one filename at a time.

### Narrow Wedge
- Trace the shared planner path that determines which prayer content is rendered for audio and page content.
- Identify why distinct contracts are all resolving to the same Morning Prayer output.
- Fix the selection/handoff layer so Rosary and Morning Prayer each write their own expected artifacts.
- Add regression coverage for the distinct-output cases that are currently collapsing.

### Non-Goals
- Rewriting the entire prayer-generation engine.
- Changing the devotional calendar job that already ships images and novenas correctly.
- Redesigning the prayer content schema or the OneDrive upload architecture.
- Adding new prayer families beyond the ones already represented in the repo.

### Risks And Unknowns
- The shared audio/page-content planner may be too broad, so the same fallback could be affecting multiple contract families.
- The missing files may be a symptom of the wrong output folder or file-stem calculation rather than a pure content-selection bug.
- Rosary and Morning Prayer might depend on different contract keys, builders, or page titles, so the fix may need to touch both the resolver and the file-emission path.
- If the root cause lives in a generic helper, fixing only the Morning Prayer entrypoint will leave the other prayer families broken.

### Recommended Next Step
- Use `/research-astack` to map the shared prayer-selection flow, identify the exact branch that causes Morning Prayer to be reused for other outputs, and determine where Rosary and Morning Prayer file emission is being lost.

## Research

### Scope Baseline
- The user is reporting a shared-output bug, not a single missing file typo:
  - all audio sounds like Morning Prayer
  - all page content looks like Morning Prayer
  - Rosary and Morning Prayer files are not appearing where expected
- That points to a shared planner/resolver or file emission boundary rather than isolated content files.

### Early Findings
- The contract files themselves are distinct and still point at different builders:
  - `config/morning-prayer.json` uses `builder: "morning_prayer_v1"` and carries the Morning Prayer file-backed resolver list.
  - `config/rosary.json` uses `builder: "rosary_v1"` and carries the Rosary weekday-mystery contract flow.
- The shared dispatcher in `jobs/notion/generate_page_audio.py` is builder-driven:
  - `build_page_audio_plan(...)` routes `morning_prayer_v1` to `build_morning_prayer_plan(...)`
  - it routes `rosary_v1` and `rosary_dynamic_v1` to `build_rosary_dynamic_plan(...)`
  - it routes `rss_audio_v1` through the RSS builder, and `audio_fragments_v1` through the fragment builder
- The Morning Prayer runner in `jobs/notion/generate_prayer.py` does not invent its own content; it loads one contract and then delegates into `build_morning_prayer_plan(...)` and `render_page_audio_for_config(...)`.
- File emission is derived from output metadata:
  - `page_audio_runtime_config_for_page(...)` can override `output_folder` from the page row
  - `page_audio_export_metadata(...)` computes the final folder/stem used by `page_audio_output_library_paths(...)`
  - `persist_page_audio_output_library(...)` writes the audio and JSON sidecar into that derived folder
- That means the regression is likely in one of three shared places:
  - contract/page selection is collapsing to the Morning Prayer page
  - builder selection is being reused incorrectly for multiple rows
  - output-folder / file-stem derivation is pointing multiple prayers at the same library location

### Relevant Files
- `jobs/notion/generate_page_audio.py`

  - Owns the file emission paths for the page-audio library.

  - The Morning Prayer runner entrypoint that loads one contract and delegates into the page-audio planner.
- `.github/workflows/daily_novena_prayer.yml`

  - The active Morning Prayer contract source of truth.

  - Existing regression coverage for Morning Prayer contract loading and runner behavior.

  - Existing regression coverage for Rosary planning, contract flow, and page-audio output assembly.
- `README.md`
  - Documents the current prayer and page-audio contracts and their expected output behavior.

### Current System Map
- The repo has a shared, contract-driven page-audio engine that can build multiple prayer families from config.
- The Morning Prayer runner delegates into that shared engine after selecting a page by title.
- The Rosary path is already modeled as a distinct builder with weekday mystery mapping and separate content files.
- The fact that everything looks like Morning Prayer suggests one of these is happening:
  - the wrong builder is being selected for multiple contracts
  - the page-selection/filtering logic is collapsing to the Morning Prayer page
  - the output path/stem logic is reusing Morning Prayer filenames for other families
  - the page-content sync step is writing the Morning Prayer section into every page
- The file-backed contract loader reads the root-level `config/*.json` files, but those files keep the builder under `header.builder` instead of a top-level `builder` field.
- `build_page_audio_plan(...)` only reads `config["builder"]`, so any loaded contract that is not normalized first falls through to the default `morning_prayer_v1` branch.

### Contract / Output Observations
- `build_morning_prayer_plan(...)` assembles Morning Prayer from the contract file and returns page-content blocks only for resolvers that target `page_content`.
- `build_rosary_dynamic_plan(...)` independently assembles Rosary audio and page content from the Rosary contract.
- `audio_output_config_from_notion_page(...)` already knows how to build Rosary and fragment-based outputs from Notion rows, so Rosary is not a special-case dead end.
- `page_audio_output_library_paths(...)` writes files based on the computed export metadata, so missing files are more likely a selection or metadata problem than a low-level copy problem.
- `render_page_audio_for_config(...)` handles the cache short-circuit and file persistence before the Notion audio attachment, so a shared `config` object or page match could still make different rows look identical if the wrong plan is built upstream.

### Reuse Opportunities
- Reuse the existing builder branches in `generate_page_audio.py` instead of inventing new prayer-specific scripts.
- Reuse the current test modules to prove the fix preserves the distinct Rosary and Morning Prayer contracts.
- Reuse the root-level contract files as the canonical source of truth for each prayer family.

### External References
- No external dependencies need new research here.
- The main constraint is internal consistency between contract selection, page selection, audio generation, and file emission.

### Constraints
- The fix should preserve the shipped calendar/novena pipeline.
- The fix must keep the contract-driven architecture, but restore distinct outputs per contract.
- The file emission behavior must still work in GitHub Actions and locally.

### Risks
- If the wrong page title is being matched, the content could still look like Morning Prayer even when the builder is correct.
- If the output folder calculation is wrong, Rosary and Morning Prayer might generate distinct content but still fail to show up in the filesystem.
- If the same helper is used by both audio and page-content assembly, one fix may need to touch both paths to avoid partial correctness.

### Assumptions To Validate
- The Morning Prayer and Rosary contracts are still supposed to produce distinct outputs.
- The shared planner is the likely root cause of the collapse.
- The missing files are probably a file-emission bug or path mismatch, not a separate storage-system failure.

### Unknowns
- Whether the page-content bug and the audio bug share the same root cause.
- Whether the missing Rosary and Morning Prayer files are absent from the OneDrive sync path, the local library path, or both.
- Whether the current contract rows are selecting the right page but rendering the wrong builder.

### Recommended Direction
- Use `/plan-astack` after research to lock the smallest shared fix that restores distinct prayer outputs and file emission for Morning Prayer and Rosary without disturbing the already-working daily devotional pipeline.

### Research Summary
- The distinct contract files and builder names are present and appear healthy.
- The shared planner is the likely place where Morning Prayer is leaking into other outputs, and the concrete mechanism is now clearer: file-loaded contracts are not normalized from `header.builder` into the top-level `builder` key before `build_page_audio_plan(...)` runs.
- Because `build_page_audio_plan(...)` defaults missing builders to `morning_prayer_v1`, every non-normalized contract can collapse into the Morning Prayer branch.
- The output library path is derived from metadata, so a path/stem collision is still plausible and should be checked against the planner fix.
- Rosary already has a separate builder branch and dedicated tests, which makes it a good regression target for the bugfix.
- Morning Prayer and Rosary file emission should be verified together because the missing-file symptom may come from the same shared selection/metadata path.

## Plan

### Summary
- Normalize file-backed prayer contracts so the planner sees the correct builder for each contract instead of falling through to the Morning Prayer default.
- Keep the existing builder branches and output-emission machinery, but make the loaded configs preserve `header.builder` as the active top-level builder before dispatch.
- Restore distinct audio, page content, and library files for Morning Prayer and Rosary without changing the shipped calendar pipeline.

### What Already Exists
- A generic prayer runner entrypoint in `jobs/notion/generate_prayer.py`.
- A shared page-audio/content builder in `jobs/notion/generate_page_audio.py`.
- Distinct contract files for Morning Prayer and Rosary at the repo root.
- Existing tests that already cover parts of the Morning Prayer and Rosary planning logic.
- A contract loader path that already scans `config/*.json` and can be normalized once instead of patching each prayer family separately.

### Architecture
- Keep the contract-driven model.
- Add a normalization step at the contract-loading boundary so any loaded config with `header.builder` becomes a planner-ready config with top-level `builder`.
- Keep `build_page_audio_plan(...)` as the dispatcher, but make sure it receives a fully normalized config object.
- Leave the existing output-emission code in place and verify it continues to write distinct folders and filenames per contract.

ASCII flow:
```text
loaded contract file
    |
    v
normalize builder from header.builder
    |
    v
shared planner / builder selection
    |
    +--> distinct audio content
    +--> distinct page content
    +--> distinct output files
```
