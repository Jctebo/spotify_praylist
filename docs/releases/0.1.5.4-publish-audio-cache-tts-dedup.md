# Release 0.1.5.4 - Publish Audio Fragment Cache

Date: 2026-04-27
Status: Scoped
Branch: enhancement/publish-audio-cache-tts-dedup
Depends On: 0.1.5.3

## Scope

### Problem
- The publish audio path currently caches a whole MP3 per entry, which means one changed block can force an entire prayer to regenerate.
- The maintainer wants block-level reuse so unchanged prayer fragments can be skipped even when the final assembled prayer still changes.
- The concern is not just "does caching exist", but "does the cache boundary let reusable blocks survive daily reruns and partial edits?"

### Audience
- Primary user: the maintainer who edits prayer blocks and runs the audio publish workflow.
- Secondary stakeholders: podcast listeners, because unchanged blocks should not trigger avoidable TTS calls or noisy feed churn.
- Secondary stakeholders: future maintainers who need a cache boundary that matches the way prayers are authored in blocks.

### Current Status Quo
- `jobs/publish/audio.py` currently treats each publish entry as one render unit and caches one MP3 plus one `.json` sidecar per entry.
- `jobs/publish/contracts.py` already models prayers as ordered `blocks`, which gives us the structure needed for a block cache.
- `jobs/notion/generate_page_audio.py` already has a working fragment cache model: leaf fragments are hashed individually, cached under fragment storage paths, and assembled with ffmpeg.
- `tests/test_publish_audio_pipeline.py` currently proves only the whole-entry cache-hit path, not the block-level reuse path the maintainer wants.
- The open question is how much of the older fragment pipeline we should reuse versus re-create inside `jobs/publish/`.
- In the current contracts, the repeated units are mostly leaf blocks or selector outputs: Rosary repeats `hail-mary` as a single leaf three times, and the weekday mystery map reuses the same mystery file on multiple days.

### Goal
- Keep audio publication idempotent at the block level.
- Reuse already-rendered blocks when their resolved text and TTS settings have not changed.
- Let a changed block invalidate only that block, not the entire prayer, when possible.
- Keep the final assembled MP3 deterministic for GitHub Pages and podcast clients.

### Constraints
- Do not lose the contract-driven publish source of truth in `config/publish/contracts/*.json`.
- Do not break the current public audio output targets under `docs/audio/*.mp3` and `docs/podcast.xml`.
- Do not add a second whole-prayer cache layer if the fragment cache can own reuse directly.
- Do not require live OpenAI calls for unchanged blocks.

### Narrow Wedge
- Build block-level caching for Morning Prayer first, using the existing contract `blocks` tree as the unit of reuse.
- Reuse the older page-audio fragment patterns for leaf block hashing, fragment storage, and ffmpeg assembly where they fit.
- Start with leaf fragments as the cache unit, because the current contracts mostly repeat self-contained spoken pieces rather than repeated multi-block sub-assemblies.
- Keep the final publish output as one prayer MP3 per entry, but make the expensive work happen at the block level.
- Add regression coverage for unchanged leaf blocks, changed leaf blocks, and mixed block assemblies.

### Non-Goals
- Do not rewrite the entire prayer contract format.
- Do not move the active publish workflow back to the archived page-audio job wholesale.
- Do not add block-level caching to unrelated text publishing paths.
- Do not build a full media database or content-addressable store beyond what this wedge needs.

### Risks And Unknowns
- The fragment boundary is not yet defined for nested blocks, so we need to decide whether to cache only leaf blocks or also cache sub-assemblies.
- Blocks that resolve through selectors like month or weekday need hashes based on the resolved output, not just the selector name.
- The old page-audio runtime supports more fragment kinds than the publish contract currently uses, so not every old pattern may be worth carrying over.
- The final assembled MP3 may still need a file-level output cache, but that should be derived from fragment reuse rather than replace it.

### Recommended Next Step
- Run `/research-astack` to map the block-to-fragment translation, identify the reusable fragment-cache helpers in the older page-audio runtime, and decide whether the new publish boundary should borrow or port that logic.

## Research

### Scope Baseline
- The enhancement is a fragment-cache migration for contract-driven publish audio.
- The current publish runner caches whole entries; the new goal is to cache reusable prayer blocks and assemble the final MP3 from those cached fragments.

### Relevant Files
- [jobs/publish/audio.py](/workspaces/spotify_praylist/jobs/publish/audio.py): current whole-entry renderer and file-level cache boundary that likely needs to be split or replaced.
- [jobs/publish/contracts.py](/workspaces/spotify_praylist/jobs/publish/contracts.py): resolves contract `blocks` into text and audio jobs and is the source of truth for block ordering.
- [jobs/publish/run_audio_pipeline.py](/workspaces/spotify_praylist/jobs/publish/run_audio_pipeline.py): entrypoint that currently assembles final audio from one rendered job per contract entry.
- [config/publish/contracts/morning-prayer.json](/workspaces/spotify_praylist/config/publish/contracts/morning-prayer.json): contract with nested `blocks` and the clearest candidate for block-level reuse.
- [config/publish/contracts/rosary.json](/workspaces/spotify_praylist/config/publish/contracts/rosary.json): second publish contract that can validate whether the block-cache design generalizes.
- [jobs/notion/generate_page_audio.py](/workspaces/spotify_praylist/jobs/notion/generate_page_audio.py): older fragment-based audio runtime with per-fragment hashing, fragment persistence, and ffmpeg assembly.
- [tests/test_publish_audio_pipeline.py](/workspaces/spotify_praylist/tests/test_publish_audio_pipeline.py): current coverage for the whole-file cache path that will need to be replaced or extended.
- [tests/test_page_audio_job.py](/workspaces/spotify_praylist/tests/test_page_audio_job.py): existing coverage for the archived page-audio runtime and its block/fragment behaviors.
- [tests/test_novena_job.py](/workspaces/spotify_praylist/tests/test_novena_job.py): additional examples of cached audio modes and fragment reuse patterns.
- [docs/releases/0.1.5.3-publish-pipeline-cleanup.md](/workspaces/spotify_praylist/docs/releases/0.1.5.3-publish-pipeline-cleanup.md): prior release that introduced the generic publish boundary we are now refining.

### Current System Map
- The active publish audio path is still entry-oriented: contracts are loaded, each entry gets one text body, and `render_audio_job` produces one MP3 for that entire entry.
- The contract model already contains ordered `blocks`, so the source data is more granular than the current audio cache.
- The archived page-audio runtime already solved a similar problem by turning leaf fragments into `PageAudioFragment` objects, hashing each fragment, caching the fragment audio, and assembling the final file with ffmpeg.
- In the older runtime, `ensure_tts_fragment_audio` and `ensure_prompt_fragment_audio` reuse cached fragment audio before calling OpenAI, while `persist_library_audio_fragment` stores the metadata needed to keep the cache stable.
- `assemble_audio_with_ffmpeg` then combines the cached fragments, which is the behavior we likely need to recreate or reuse for publish audio.
- The publish workflow still triggers after `Daily Spotify Playlist Refresh` on `main` and also supports manual dispatch, but the cache layer underneath it is not yet fragment-aware.

### Reuse Opportunities
- Reuse the fragment-level cache shapes from `jobs/notion/generate_page_audio.py` instead of inventing a new per-block storage format.
- Reuse the contract block resolver in `jobs/publish/contracts.py` so the cache key can be based on resolved block text and settings.
- Reuse the old `PageAudioFragment` ideas of `kind`, `label`, `hash_value`, `fragment_key`, and `collection` if they map cleanly to publish blocks.
- Reuse the existing ffmpeg assembly pattern so cached leaf fragments can still be combined into one deterministic output.
- Reuse the existing tests around fragment caching and managed output cleanup as behavioral references for the new publish path.

### External References
- OpenAI Python SDK audio speech generation API used by `client.audio.speech.create(...)` in `jobs/publish/audio.py` and `shared.generate_openai_audio_bytes(...)` in the older runtime.
- `ffmpeg` as the assembly tool for stitching cached fragments into a final MP3 in `jobs/notion/generate_page_audio.py`.
- GitHub Actions workflow dispatch and workflow-run chaining used by `.github/workflows/publish_audio.yml`.

### Constraints
- Cache correctness depends on defining a stable block identity for each leaf fragment and on hashing the resolved output, not just the raw selector or template name.
- The current contracts include nested blocks, so the cache design has to decide whether nested sequences become cached sub-assemblies or simply ordered groupings of leaf fragments.
- The publish output still needs to remain deterministic for GitHub Pages and podcast clients even if the internal rendering becomes fragment-based.
- The migration should stay small enough to avoid reintroducing the archived page-audio subsystem wholesale unless that is the cleanest reuse path.

### Risks
- Highest risk: a badly chosen block hash could either reuse the wrong audio or explode the cache by treating equivalent blocks as unique.
- Second risk: nested block assembly may be more expensive to reason about than the current whole-entry render, especially if sub-sequences also become cacheable.
- Third risk: the older page-audio fragment runtime supports more fragment types than the publish contracts currently use, so porting it blindly could pull in unnecessary complexity.
- Workflow-level reruns could still repeat TTS if the fragment cache directory is cleaned or if the final assembly step is not derived from the cached block outputs.

### Assumptions To Validate
- Assumption: Morning Prayer is the best first wedge for block-level cache migration because its contract already contains a clear ordered block tree.
- Assumption: leaf block reuse is more valuable than whole-prayer reuse, even if the final assembled file still has to be written each run.
- Assumption: the publish path should cache only TTS-derived blocks first, then decide separately whether prompt-derived or source-audio blocks need to join the same model.
- Assumption: unchanged blocks should survive ordinary reruns without any special cleanup step.
- Assumption: nested sub-assembly caching is probably optional at first because the current contracts do not obviously repeat multi-block groups, only repeated leaf fragments and selector outputs.

### Unknowns
- Whether the block cache should live in `jobs/publish/` as a fresh implementation or borrow more directly from the archived page-audio runtime.
- Whether nested sequences should have their own cache key or only their leaf blocks should be cached.
- Whether prompt-derived blocks and source-audio blocks belong in the same cache model as TTS text blocks.
- Whether the final assembled MP3 should still have its own output metadata file, separate from the per-block cache entries.
- Whether nested sub-assemblies are worth caching at all in the first release, given that the current contracts mainly repeat leaf prayers instead of repeated multi-block groupings.

### Recommended Direction
- Move into `/plan-astack` with a fragment-first plan that reuses the old page-audio fragment cache patterns where possible.
- Prefer a design where the contract block tree maps to cacheable leaf fragments, and the final MP3 assembly stitches cached fragments together.
- Keep the existing publish contract files and RSS output shape, but replace the whole-entry render boundary underneath them.
- If the old page-audio fragment runtime is the cleanest source of truth, port the minimum reusable pieces rather than rebuilding a weaker whole-file cache.

## Plan

### Summary
- Build a leaf-fragment cache for publish audio so reused prayer blocks do not call TTS again on daily reruns.
- Keep Morning Prayer as the first and smallest wedge.
- Reuse the existing contract block tree and the fragment-cache patterns from the archived page-audio runtime.
- Preserve the current public outputs: `docs/audio/<entry_id>.mp3` and `docs/podcast.xml`.
- This plan is chosen because the current contracts mostly repeat leaf blocks or selector outputs, so a leaf cache solves the real reuse problem without carrying a weaker whole-MP3 cache forward.

### What Already Exists
- `jobs/publish/contracts.py` already normalizes `sequence`, `repeat`, `weekday-map`, `monthly-template`, `file`, and `inline` blocks and preserves deterministic ordering.
- `jobs/notion/generate_page_audio.py` already proves the fragment-cache shape we need: hash the small reusable unit, store it on disk, and assemble the final audio with ffmpeg.
- `jobs/publish/audio.py` already owns the current audio output pathing, OpenAI TTS call, and RSS-facing `audio_url` metadata.
- `jobs/publish/run_audio_pipeline.py` already orchestrates contract loading, audio job resolution, rendering, and feed writing.
- `tests/test_publish_audio_pipeline.py`, `tests/test_page_audio_job.py`, and `tests/test_novena_job.py` already cover the current and archived audio cache behaviors we want to preserve or adapt.

### Architecture
- Contract file -> block resolver -> leaf fragment specs -> fragment cache lookup/render -> ffmpeg assembly -> `docs/audio/<entry_id>.mp3` -> `docs/podcast.xml`.
- Leaf fragments are the only cached audio unit in v1.
- Nested `sequence`, `repeat`, and `weekday-map` blocks are traversal structure only in v1, not cacheable sub-assemblies.
- The cache key for a fragment must include the resolved spoken text plus the TTS settings (`model`, `voice`, `format`, `speed`) and stable block identity derived from the entry, contract, and block path.
- Final entry output may still use a deterministic render-hash sidecar so we can skip re-assembling unchanged audio, but that hash is derived from fragment hashes rather than from a single whole-entry TTS blob.
- Flow:
```text
config/publish/contracts/morning-prayer.json
        |
        v
resolve ordered blocks
        |
        v
build leaf fragment specs
        |
        +--> fragment cache hit -> reuse cached fragment mp3
        |
        +--> fragment cache miss -> OpenAI TTS -> write fragment cache
        |
        v
ordered fragment list -> ffmpeg concat -> docs/audio/morning-prayer.mp3
        |
        v
write docs/podcast.xml
```

### Concrete Changes
- `jobs/publish/contracts.py`: add leaf-fragment expansion helpers for audio, keep text publication intact, and expose stable block-path/selector resolution for fragment identity.
- `jobs/publish/fragments.py`: new helper module for fragment identity, fragment cache paths, fragment render/reuse, and ffmpeg assembly.
- `jobs/publish/audio.py`: replace the whole-entry TTS path with fragment orchestration, final assembly, and output metadata writing.
- `jobs/publish/__init__.py`: export the new fragment helpers if the runners or tests need them.
- `tests/test_publish_audio_fragments.py`: new tests for leaf cache hits, leaf cache misses, repeated leaf reuse, selector-driven invalidation, and fragment assembly.
- `tests/test_publish_audio_pipeline.py`: update end-to-end assertions so the pipeline proves fragment reuse instead of whole-entry reuse.
- `tests/test_publish_contracts.py`: add coverage for fragment expansion order and deterministic selector resolution.
- `README.md`: document the fragment-level publish audio cache model and the internal cache root if we introduce one.
- `docs/releases/RELEASE_LOG.md`: add the shipped release notes after implementation.

### UX And States
- No UI changes.
- Success: `Publish Prayer Audio` still produces the same public MP3 and RSS URLs, but unchanged leaf blocks are reused from cache instead of calling TTS again.
- Empty state: if no audio-enabled entries or no fragment-producing blocks exist, the job exits cleanly with zero rendered jobs.
- Error state: missing template files, invalid selector output, ffmpeg failures, or bad cache metadata fail closed with a non-zero exit.
- The user-visible behavior stays the same; only the internal audio reuse model changes.

### Failure Modes
- Wrong fragment hash: stale spoken text or unnecessary TTS calls.
- Missing fragment metadata: a cache miss and extra OpenAI work, but the output still stays correct.
- ffmpeg concat failure: the job exits non-zero before the feed is written.
- Selector drift: only the affected fragment invalidates or errors, not the whole pipeline.
- Cache directory cleanup: the job rerenders fragments, but the output remains deterministic.

### Rollout Notes
- No feature flag; the fragment cache is an internal implementation change behind the same workflow entrypoint.
- Keep GitHub Actions workflow names and public URLs unchanged.
- The audio publish workflow currently keeps both `workflow_run` chaining and a `push` trigger on `main` so GitHub Pages can republish immediately after a merge if the chained path ever lags.
- Use a dedicated publish fragment cache root such as `.cache/publish_audio/` so the new model does not collide with the archived page-audio cache.
- Ship as a straight replacement once the tests pass; the public MP3 and podcast paths stay the same.

### Not In Scope
- Nested sub-assembly caching in v1.
- Rewriting the contract schema or the publish text pipeline.
- Changing RSS shape, feed URL, or GitHub Pages hosting layout.
- Prompt-derived or source-audio publish fragments unless a future contract introduces them.
- A cross-entry media database or content-addressable storage layer.

### Open Questions
- None blocking for v1.
- Nested sub-assembly caching is intentionally deferred unless a later contract shape makes it clearly worthwhile.
