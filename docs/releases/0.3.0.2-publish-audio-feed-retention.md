# Release 0.3.0.2 - Publish Audio Feed Retention Bugfix

Date: 2026-05-01
Status: Shipped
Branch: enhancement/publish-audio-feed-retention
Depends On: 0.3.0.1

## Scope

### Problem
- The podcast feed is still being overwritten by the latest publish run instead of preserving older episodes as an append-only archive.
- The daily audio job appears to publish the next day’s episode slice, but the back catalog does not survive the rebuild in a reliable way.
- Why now: the podcast is public, so losing prior episodes is visible immediately to subscribers and makes the feed look broken even when the latest job succeeds.

### Audience
- Primary user: the maintainer who runs the publish audio workflow and expects it to add new episodes without erasing older ones.
- Secondary stakeholders: podcast listeners who should keep seeing prior episodes in the feed.
- Secondary stakeholders: future maintainers who need a clear contract for what gets preserved on every rerun.

### Current Status Quo
- `jobs/publish/run_audio_pipeline.py` renders the current target-date slice and then rebuilds `docs/podcast.xml`.
- `jobs/publish/rss.py` can merge current jobs with archived feed items, and the audio path now treats the remote `podcast.xml` as the only archive source and fails closed if it cannot be recovered.
- `docs/audio/` is generated during the workflow but is not versioned in the repository, so the checkout itself does not carry episode history.
- The novena path still uses the in-workspace feed as a same-run handoff after the audio step has written it.
- The result is a feed that can look like a complete overwrite even though the pipeline was supposed to append.

### Goal
- Preserve historical podcast episodes automatically whenever the audio pipeline reruns.
- Keep the daily publish window behavior intact if it is still intended, but make feed output append-like instead of replacing the archive.
- Success criteria: after a rerun, older episode GUIDs still appear in `docs/podcast.xml` alongside the newly published slice.
- Success criteria: intentional truncation remains possible only through an explicit reset path, not through normal daily publishing.

### Constraints
- Keep the fix narrow to feed-retention and archive-rehydration behavior.
- Preserve existing episode IDs, RSS GUIDs, audio paths, and sidecar filenames so existing subscribers do not see a churned feed.
- Avoid broad changes to Spotify refresh behavior, novena contract rules, or audio generation itself unless they are proven to be part of the overwrite path.
- The solution needs to be deterministic even when the remote GitHub Pages feed is unavailable.

### Narrow Wedge
- Make the publish workflow rebuild from a durable archive source every run, then verify the archive survives repeated publishes.
- Add regression tests that prove older episodes remain in the feed after a new run and that explicit reset behavior still truncates when intentionally requested.

### Non-Goals
- Do not redesign episode naming or the podcast schema.
- Do not change the audio generation text or TTS logic.
- Do not add new publish modes unless the existing ones cannot express the correct archive behavior.
- Do not expand scope into Spotify playlist refresh or Notion membership logic.

### Risks And Unknowns
- The remote feed is now the sole archive source for audio recovery, so a bad deploy or missing Pages artifact would still look like an overwrite.
- Because `docs/audio/` is not tracked, the repository checkout alone cannot preserve the back catalog between workflow runs.
- It is still worth deciding whether the remote archive fetch should retry once before failing closed.

### Recommended Next Step
- Monitor the next daily publish run to confirm the remote-only archive recovery continues appending older episodes correctly.

## Research
### Scope Baseline
- The scoped task is to find why the podcast publish flow still drops older episodes and leaves only the newest slice visible after a run.
- The bug is no longer about the manual publish default; it is about whether the feed rebuild has a durable archive to append from on every execution.
- The key question is where historical episodes are supposed to come from when the workflow starts on a fresh GitHub Actions checkout.

### Relevant Files
- `jobs/publish/run_audio_pipeline.py` - orchestrates the audio publish run, loads archived jobs, merges current and prior items, and writes `docs/podcast.xml`.
- `jobs/publish/rss.py` - parses existing RSS items, optionally fetches the remote GitHub Pages feed, deduplicates by `episode_id`, and sorts the final feed.
- `jobs/publish/audio.py` - writes current `docs/audio/*.mp3` files and JSON sidecars and exposes the local archive loader for reruns.
- `jobs/novena_contracts/rss_publisher.py` - uses the same RSS merge helpers and has an explicit `reset_feed` truncation path.
- `jobs/novena_contracts/pipeline.py` - shows how the novena workflow reuses the same archive assumptions after the audio step has already written `docs/podcast.xml`.
- `.github/workflows/publish_audio.yml` - defines the audio/novena job order and deploys the generated `docs/` tree to GitHub Pages.
- `tests/test_publish_audio_pipeline.py` - covers RSS parsing, archived-sidecar reuse, and the audio pipeline’s rerun behavior in a temp workspace.
- `tests/test_novena_pipeline.py` - covers feed preservation and explicit truncation for the novena rebuild path.

### Current System Map
- Fact: `run_audio_pipeline()` builds current audio jobs, renders them, loads archived jobs from `docs/podcast.xml` plus the remote feed, then writes the merged feed back to the same path.
- Fact: `load_podcast_feed_jobs()` first reads the local feed file, then tries `requests.get(<base_url>/podcast.xml)` with a 20-second timeout, and silently ignores exceptions.
- Fact: `build_rss_feed()` deduplicates by `episode_id` and sorts by `published_date` descending before serializing the feed XML.
- Fact: `jobs/novena_contracts/pipeline.py` now passes the current render results directly into `publish_novena_rss()` instead of re-reading sidecars for the current run.
- Fact: `load_published_audio_jobs()` still exists as a helper for inspecting archived sidecars, but it is no longer part of the publish-path archive merge.
- Fact: `git ls-files docs/audio docs/podcast.xml` shows only `docs/podcast.xml` is versioned; `docs/audio/` is generated, not tracked.
- Fact: in this checkout, `docs/podcast.xml` exists but currently contains 0 RSS items.
- Fact: the publish workflow uploads the generated `docs/` directory as the Pages artifact, so the deployed site carries the runtime-generated audio and feed files even though the repo checkout does not.
- Fact: `jobs/novena_contracts/rss_publisher.py` reuses the same merge helpers and only truncates history when `reset_feed=True`, but it now merges the current novena jobs directly from memory instead of loading them from sidecars.
- Inference: the append behavior works only if the current run can rehydrate history from the local feed file or the remote published feed, because the repo checkout itself does not carry the older feed history.
- Inference: a fresh workflow run can look like a full overwrite if the remote feed is stale, missing, or temporarily unreachable, because the merge input then collapses to only the current run’s rendered jobs.

### Reuse Opportunities
- Reuse the existing RSS parsing and merge helpers instead of inventing a second feed writer.
- Reuse the novena `reset_feed` split to distinguish ordinary append behavior from explicit truncation.
- Reuse the current workflow artifact deployment path so any durable archive fix stays aligned with the existing GitHub Pages publishing model.
- Reuse the temp-workspace regression pattern already used in `tests/test_publish_audio_pipeline.py` and `tests/test_novena_pipeline.py`.

### External References
- No new third-party dependency appears necessary for the investigation itself.
- The only external service boundary that matters here is GitHub Pages, because the feed loader treats the deployed `podcast.xml` as the remote archive source.

### Constraints
- The repository does not version `docs/audio/`, so cross-run history cannot depend on local sidecars in a fresh CI checkout.
- The workflow deploys `docs/` as a Pages artifact instead of committing the generated audio archive back to the repo.
- Remote feed loading is best-effort and failure-tolerant, which means history retention currently depends on the feed being reachable at publish time.
- The fix needs to preserve `episode_id` and RSS GUID stability so subscribers do not see churned history.
- Any new archive strategy has to work with both the audio and novena publish paths, because they share the same RSS merge helpers.

### Risks
- The remote GitHub Pages feed may be stale or unavailable when the next workflow run starts, which would make the archive collapse to the current run only.
- Because the deployed feed is the only durable runtime archive, a bug in the deploy step would look identical to a feed-overwrite bug.
- The current tests prove preservation in a warm temp workspace, but they do not yet prove cold-start recovery from the deployed feed artifact.
- `docs/podcast.xml` being empty in the checkout makes it easy to mistake the repo state for the deployed feed state.

### Assumptions To Validate
- The intended source of truth for older episodes is the published GitHub Pages feed, not a committed repository archive.
- The overwrite symptom is not caused by RSS readers hiding older items or by a malformed GUID/date on existing items.
- The current `docs/audio/` sidecars are expected to be ephemeral on the runner and do not need to be checked into the repo unless we decide otherwise.

### Unknowns
- Whether the right fix is just feed-only recovery, or whether the workflow should eventually check out a richer published archive before writing.
- Whether the current deployment model can be made durable enough without changing the artifact layout.
- Whether a failed remote fetch should abort the publish run instead of silently falling back to a smaller feed.

### Recommended Direction
- Keep `podcast.xml` as the only archive source, pass current novena items in memory, and remove sidecar-based archive recovery from the publish paths.
- Full architecture note: [docs/architecture/publish-audio-feed-retention.md](/workspaces/spotify_praylist/docs/architecture/publish-audio-feed-retention.md)
- The next question for planning is whether the feed loader should continue to silently ignore remote fetch failures or fail closed when the archive feed is unavailable.
