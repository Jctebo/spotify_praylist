# Release 0.3.4.5 - Rosary Reflection Root Fix

Status: Shipped
Date: 2026-06-05
Branch: enhancement/rosary-reflection-root-fix

## Scope

### Problem
- The Daily Rosary correctly chooses feast days before Gospel, season, or generic mystery-fruit fallback, but the reflection generation step can still publish generic Ordinary Time reflections.
- The observed June 5, 2026 St. Boniface episode resolved the feast correctly in the title, intro, and context, then fell through to generic Ordinary Time reflections because model output validation saw only one reflection instead of five.
- The root issue is not reflection precedence. The root issue is brittle generated-output shape plus a fallback path that drops the feast focus after the first generated attempt fails.
- This matters now because listeners expect feast-day Rosaries to keep the day-specific devotional focus through all five decades, not only in the title and intro.

### Audience
- Primary user: Daily Rosary listeners using the Ora Pro Nobis podcast feed.
- Secondary stakeholders: maintainers reviewing publish logs, sidecars, and generated audio after scheduled GitHub Actions runs.

### Current Status Quo
- Rosary day context ranks liturgical focus in this order: feast or memorial, Gospel, liturgical season, then generic mystery fruit.
- Feast precedence is currently working for St. Boniface locally: June 5, 2026 resolves to `focus_source=feast` and `focus_title=Saint Boniface, Bishop and Martyr`.
- The generation prompt asks for exactly five reflections, one line per mystery, but the validator effectively depends on line splitting.
- If OpenAI returns one paragraph containing five ideas, validation sees one item and treats generation as invalid.
- When feast generation fails, the current fallback path tries Gospel or season generation and can eventually publish generic season-aware text, losing the feast focus.
- The published sidecar can show final fragment text, but it does not make the failed generation source and fallback reason easy enough to audit.

### Goal
- Daily Rosary reflection generation must produce exactly five reflections, one per mystery or decade, in a format the runtime can parse reliably.
- When the day focus is a feast or memorial, every successful generated reflection and every deterministic fallback must remain feast-centered.
- A malformed model response, including a single paragraph response, must not silently degrade a feast-day Rosary into generic Ordinary Time reflections.
- Success criteria:
  - A regression test for June 5, 2026 St. Boniface proves feast context remains the reflection focus.
  - A regression test for a one-item or one-paragraph model response proves the runtime recovers with five feast-centered reflections.
  - Existing Gospel, season, and generic mystery-fruit behavior still works for non-feast days.
  - Logs or sidecar metadata clearly identify whether reflections came from structured generation, parsed fallback, or deterministic fallback.

### Constraints
- Preserve the existing Rosary structure: five decades, existing mystery schedule, existing fruits, and current prayer ordering.
- Keep generated reflection text short enough for spoken audio pacing and compatible with the current fragment cache model.
- Do not invent saint biographies or unsupported feast details. Feast-centered fallback should use the official feast title and the mystery fruit rather than fabricated historical detail.
- Avoid making St. Boniface a special case. The fix must apply to all feasts, memorials, and optional memorials.
- Keep current provider assumptions unless research proves the OpenAI response format API is already available in this code path.

### Narrow Wedge
- Replace or harden Rosary reflection generation so the requested output is structurally five reflections, not prose that happens to use five lines.
- Accept robust numbered or JSON-shaped output and normalize it into the existing list of five reflection strings.
- Add a feast-preserving deterministic fallback used whenever `focus_source=feast` and generated output is missing, malformed, or incomplete.
- Add targeted tests around:
  - St. Boniface day context and reflection focus.
  - malformed one-reflection model output.
  - non-feast fallback precedence.
  - sidecar or log observability for reflection source.

### Non-Goals
- Do not change the Rosary mystery calendar.
- Do not change voice selection, loudness normalization, podcast feed structure, or Spotify routing.
- Do not rewrite the full publish pipeline.
- Do not introduce manual feast content authoring for individual saints in this release.
- Do not regenerate historical audio as part of the code change unless the ship step explicitly targets a rebuild.

### Risks And Unknowns
- The exact OpenAI helper used by Rosary reflections may or may not already support strict JSON/schema responses; research must confirm the lowest-risk integration path.
- Existing cached fragments or previously published MP3s may continue to expose old text until a no-cache or content-changing rebuild replaces the episode.
- A feast-preserving fallback must avoid unsupported biographical claims while still sounding intentional and devotional.
- More observability may require sidecar schema changes; research should verify downstream consumers tolerate additional fields.

### Recommended Next Step
- Run `/research-astack` against `jobs/publish/rosary_reflections.py`, the publish audio sidecar writer, and existing Rosary tests to choose the safest parser and fallback design before implementation.

## Research

### Scope Baseline
- Fix the root Daily Rosary failure where feast precedence resolves correctly, but malformed model output causes the reflection builder to fall through to generic Ordinary Time reflections.
- Keep the release focused on Rosary reflection generation reliability, feast-preserving fallback, and auditability.

### Relevant Files
- `jobs/publish/rosary_reflections.py` - Owns Rosary mystery parsing, day-context precedence, generated reflection prompts, validation, deterministic fallback, and intro generation.
- `jobs/publish/contracts.py` - Resolves Rosary runtime context, expands Rosary text/audio blocks, attaches `render_context`, and computes audio job hashes.
- `jobs/publish/audio.py` - Writes final episode JSON sidecars containing title, description, content hash, TTS metadata, fragment text, and resume markers.
- `jobs/publish/fragments.py` - Writes per-fragment sidecars and computes fragment hashes from sanitized TTS inputs and effective TTS settings.
- `config/publish/contracts/rosary.json` - Configures the Daily Rosary contract, title/description templates, weekday mystery map, OpenAI prompt model, and audio providers.
- `tests/test_publish_rosary_reflections.py` - Current unit coverage for mystery parsing, day-focus precedence, intro fallback, generated output validation, season fallback, and invalid-output fallback.
- `tests/test_publish_contracts.py`, `tests/test_publish_audio_pipeline.py`, `tests/test_publish_audio_fragments.py`, `tests/test_publish_text_pipeline.py` - Contract and audio/text integration tests that use fake `RosaryReflectionSet` values and verify fragment behavior.

### Current System Map
- `build_audio_jobs()` and `build_text_jobs()` in `jobs/publish/contracts.py` build a shared Rosary `runtime_context` before title, description, text, and audio expansion.
- `_build_rosary_day_runtime_context()` selects the `rosary_decades` block, reads the weekday mystery template, and calls `build_rosary_day_context()`.
- `build_rosary_day_context()` currently ranks focus as feast or memorial, Gospel, season, then mystery fruit. This is correct for the St. Boniface case.
- `build_rosary_reflections()` then tries:
  - feast prompt when `focus_source == "feast"`;
  - Gospel prompt if Gospel text exists;
  - season prompt if Gospel is missing or Gospel generation fails;
  - generic `fallback_rosary_reflections()` if season generation fails.
- The faulty edge is explicit: if feast generation raises because validation saw one item, the code logs `trying gospel_or_season`, and the eventual deterministic fallback is season/generic, not feast-focused.
- `validate_rosary_reflections()` currently accepts strings by splitting lines and accepts non-strings by iterating the value. It strips numbering, then requires exactly five cleaned lines.
- `RosaryReflectionSet.source` is currently only `"generated"` or `"fallback"` and is inferred by comparing returned text to the generic fallback. It cannot distinguish feast-generated, Gospel-generated, season-generated, parsed JSON, parsed numbered text, or feast deterministic fallback.
- Final episode sidecars in `jobs/publish/audio.py` do not currently include `render_context` or reflection-source metadata, but they do include final fragment text. Audio jobs already carry `render_context`, so sidecar observability can be added without introducing a new file.

### Reuse Opportunities
- Keep `RosaryDayContext` as the single source of reflection precedence. The bug does not require another precedence resolver.
- Reuse `MAX_REFLECTION_CHARS`, `_normalize_reflection_line()`, `_reflection_style_rules()`, and existing mystery parsing rules.
- Reuse the existing deterministic fallback shape from `fallback_rosary_reflections()` for sentence length, mystery-title repetition, fruit repetition, and season wording.
- Extend the existing dataclass boundary instead of adding a new Rosary subsystem:
  - Add structured result metadata, or add a small result object used internally and preserve the public tuple return where tests expect it.
  - Expand `RosaryReflectionSet.source` from coarse `"generated"`/`"fallback"` to more specific values if downstream tests are updated.
- Reuse the existing `render_context` field on publish jobs for Rosary focus metadata. Add final reflection source/fallback metadata there or to a dedicated `rosary_reflections` sidecar field.

### External References
- OpenAI Structured Outputs guide: `https://platform.openai.com/docs/guides/structured-outputs`
  - Official docs recommend Structured Outputs over JSON mode when schema adherence matters.
  - Structured Outputs are supported in the Responses API and can ensure output matches a supplied JSON schema.
- OpenAI Responses API reference: `https://platform.openai.com/docs/api-reference/responses/create?api-mode=responses`
  - `text.format` can specify a structured JSON schema for response output.
- Local dependency check:
  - `requirements.txt` leaves `openai` unpinned.
  - The installed SDK is `openai 2.24.0`.
  - `OpenAI().responses.parse(...)` is available locally, so a Pydantic-style structured parse path is possible without adding a package.

### Constraints
- The implementation should not depend only on prompt wording. Prompt tightening alone would leave the same class of failure.
- The Rosary path must still publish without an OpenAI key or when OpenAI fails.
- Feast fallback must avoid invented saint biography. It can safely use the official feast title, mystery title, fruit, and generic language about praying the day’s celebration.
- Audio fragment hashes will change if reflection text or fragment metadata included in hashing changes. That is acceptable for corrected Rosary text, but metadata-only additions should avoid unnecessary TTS cache churn when possible.
- Additional sidecar keys should be additive because existing archive loading tolerates extra fields by reading only known keys.

### Risks
- Using strict structured output may fail if the configured model or alternate OpenAI-compatible base URL does not support `responses.parse` or schema output. The fallback path must still handle that cleanly.
- The current `build_rosary_reflections()` return type is a tuple, so source metadata cannot be propagated unless the implementation adds a new internal return type or moves metadata inference to `build_rosary_reflection_set()`.
- Comparing reflections to `fallback_rosary_reflections()` is too weak once multiple fallback types exist. Leaving that in place would hide whether a feast fallback was used.
- A one-paragraph model response may contain enough content to split heuristically, but robust recovery from arbitrary prose can become fragile. Structured output plus deterministic fallback is safer than trying to parse every bad response.
- Previously published St. Boniface audio will not be corrected unless the episode is rebuilt with a changed content hash or a force/no-cache workflow mode.

### Assumptions To Validate
- `gpt-4.1-mini` supports Responses structured output in the deployed environment. Official docs say supported models include GPT-4o and later; this is likely true for GPT-4.1-family models, but implementation should gracefully fall back if the API rejects structured parsing.
- Adding `render_context` or `rosary_reflections` metadata to the final episode sidecar will not affect any public consumers. Current archive loaders appear tolerant, but tests should prove it.
- It is acceptable for `RosaryReflectionSet.source` values to become more specific than `"generated"` and `"fallback"` if all fake test fixtures and assertions are updated.

### Unknowns
- Whether to implement structured generation through `responses.parse(text_format=...)` with local Pydantic models or through `responses.create(text={"format": ...})` and manual JSON parsing.
- Whether the implementation should keep a best-effort numbered-list parser as a compatibility fallback after structured output fails, or go directly to deterministic fallback.
- Where the exact reflection-source metadata should live:
  - in `RosaryReflectionSet`;
  - in publish job `render_context`;
  - in final episode sidecar under a dedicated `rosary_reflections` key;
  - or all of the above where each is useful.

### Recommended Direction
- Prefer structured Rosary reflection generation via `client.responses.parse(...)` with a small schema containing exactly five ordered reflection objects.
- Keep `validate_rosary_reflections()` as the final guard for count and length even after structured parsing.
- Add a deterministic feast fallback path that is used immediately when feast-focused generation fails, instead of falling through to Gospel/season/generic text.
- Add specific reflection source metadata, at minimum distinguishing `generated_feast`, `generated_gospel`, `generated_season`, `fallback_feast`, and `fallback_generic`.
- Add tests before or alongside implementation for:
  - St. Boniface context resolving as feast.
  - malformed one-reflection output on a feast day producing five feast-centered fallback reflections.
  - malformed output on Gospel/season days preserving current non-feast fallback behavior.
  - sidecar or render-context metadata exposing the final reflection source.

## Plan

### Summary
- Build a structured, feast-preserving Rosary reflection pipeline that resolves exactly five reflections once per job and carries source metadata into the publish job and final sidecar.
- Chosen approach: use OpenAI structured parsing when available, keep deterministic fallback for all failure cases, and stop feast-focused days from falling through into Gospel/season/generic fallback text.

### What Already Exists
- `RosaryDayContext` already provides the correct precedence order: feast or memorial, Gospel, season, then mystery fruit.
- `validate_rosary_reflections()` already enforces exactly five reflections and the maximum character length.
- `fallback_rosary_reflections()` already defines the desired spoken shape for deterministic fallback text.
- `build_audio_jobs()` and `build_text_jobs()` already share a mutable per-entry `runtime_context`.
- Final audio sidecars already include additive metadata such as fragments, resume markers, TTS settings, loudness normalization, and content hashes.

### Architecture
- Add a structured result boundary in `jobs/publish/rosary_reflections.py`.
- Preserve the existing tuple-returning `build_rosary_reflections()` API for callers/tests that only need text.
- Add a richer internal API for callers that need source metadata.
- Cache the resolved `RosaryReflectionSet` in `runtime_context` so text body expansion, audio fragment expansion, metadata, and sidecar output all refer to the same five reflections.

```text
Daily Rosary contract
  |
  v
_entry_runtime_context()
  |
  v
RosaryDayContext
  |
  v
_get_or_build_rosary_reflection_set()
  |
  +--> OpenAI structured output --> validate exactly five --> source=generated_*
  |
  +--> deterministic fallback ----> validate exactly five --> source=fallback_*
  |
  v
text body + audio fragments + render_context + episode sidecar
```

### Failure Modes
- Structured output unsupported by model or endpoint:
  - Detection: exception from `responses.parse`.
  - User experience: runtime tries compatible fallback or deterministic fallback; episode still publishes.
- Model returns malformed text after compatible fallback:
  - Detection: `validate_rosary_reflections()` rejects wrong count or overlong items.
  - User experience: deterministic fallback source appears in metadata.
- Feast-focused generation fails:
  - Detection: logged warning and `fallback_feast` source.
  - User experience: all five reflections still reference the feast focus.
- Metadata propagation bug:
  - Detection: contract/audio sidecar tests fail.
  - User experience: reflections may be correct but harder to audit.
- Cache staleness for already-published episodes:
  - Detection: sidecar content hash still matches old content or workflow skips rebuild.
  - User experience: old St. Boniface MP3 may remain until force/no-cache rebuild.
