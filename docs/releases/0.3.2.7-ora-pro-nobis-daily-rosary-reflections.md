# Release 0.3.2.7 - Ora Pro Nobis Daily Rosary Reflections

Status: Shipped
Date: 2026-06-02
Branch: enhancement/ora-pro-nobis-daily-rosary-reflections

## Scope

### Problem
- The repo has a contract-driven `Daily Rosary` text surface, weekday mystery selection, reusable Rosary prayer templates, and Ora Pro Nobis daily audio publishing, but the Rosary surface is still mostly static.
- Listeners need a daily Rosary episode that feels tied to the actual day of prayer: the traditional Rosary mysteries should be selected by Catholic weekday practice, and each decade should carry a short intention/reflection shaped by today's Gospel.
- Why now: the publish pipeline already has Gospel lookup, OpenAI prompt generation, date-scoped episode metadata, audio assembly, RSS publishing, and Spotify episode lookup patterns. This is a boilable enhancement to an existing surface, not a new platform.

### Audience
- Primary user: a Catholic listener using Ora Pro Nobis for daily prayer who wants the Rosary to include reverent, Gospel-rooted intentions without manually preparing meditations.
- Secondary stakeholders:
  - The repo owner/operator, who needs deterministic daily publishing and clear fallback behavior when readings or model calls fail.
  - Spotify playlist consumers who expect `Daily Rosary` to resolve to the generated Ora Pro Nobis episode for the day.
  - Future maintainers who need Rosary mystery, Gospel, and fallback rules encoded in contracts/tests instead of tribal knowledge.

### Current Status Quo
- `config/publish/contracts/rosary.json` builds the traditional Rosary structure from static files and a weekday map:
  - Monday/Saturday: Joyful
  - Tuesday/Friday: Sorrowful
  - Wednesday/Sunday: Glorious
  - Thursday: Luminous
- `jobs.publish.daily_intro` can fetch Romcal celebration context and the daily Gospel, then generate a short OpenAI-backed opening block with a Gospel-missing fallback option.
- Existing Rosary intention logic lives mostly in the archived page-audio path and Notion intention distribution flow, not the active Ora Pro Nobis publish-audio Rosary contract.
- `config/spotify/contracts/daily-rosary.json` still uses the legacy `ROSARY` resolver rather than resolving a generated date-scoped Ora Pro Nobis Rosary episode.
- This is insufficient because the active Rosary output is not yet a daily, Gospel-aware Ora Pro Nobis episode with per-mystery or per-decade intentions and durable fallback behavior.

### Goal
- Build an Ora Pro Nobis `Daily Rosary` episode that:
  - Selects the traditional Rosary mysteries for the publish date using the existing weekday mapping.
  - Generates one short, reverent reflection/intention per mystery/decade, grounded in today's Gospel when Gospel text is available.
  - Falls back to season-appropriate Rosary intentions when the Gospel lookup or prompt generation cannot produce usable output.
  - Publishes text and audio through the existing contract-driven pipeline with date-scoped metadata, sidecars, RSS entries, and resume markers.
  - Allows Spotify playlist refresh to resolve the generated Ora Pro Nobis Rosary episode by title/date from the Ora Pro Nobis show.
- Success criteria:
  - A daily Rosary publish run for a Gospel-available date includes five mystery-specific reflections/intentions that reference the day's Gospel without inventing facts.
  - A daily Rosary publish run for a missing-Gospel or model-failure date still succeeds using liturgical-season-appropriate fallback intentions.
  - The episode title/date format is searchable by the Spotify `spotify_episode_lookup` contract.
  - Tests cover weekday mystery selection, Gospel-grounded generation shape, fallback behavior, publish text assembly, audio/resume marker metadata, and Spotify lookup contract validation.

### Constraints
- Keep the implementation inside the existing contract-first publish boundary where possible: `config/publish/contracts/*.json`, `jobs/publish/*`, checked-in Rosary templates, and publish tests.
- Do not revive the archived page-audio Rosary path as the main runtime.
- Generated reflections must be short enough for daily audio and should not replace the traditional prayers.
- Prompting must preserve Catholic devotional tone and avoid doctrinal speculation, unsupported claims, or free-form exegesis beyond the day's Gospel.
- Gospel retrieval is an external dependency and already has known failure modes; fallback behavior must be first-class, logged, and testable.
- The fallback phrase in the user request is interpreted as: "default to season-appropriate Rosary intentions."

### Narrow Wedge
- Add a reusable publish block for `rosary_reflections` or equivalent that:
  - Resolves the day's mystery set from the existing weekday map.
  - Fetches today's Gospel context through the existing daily intro helper.
  - Produces exactly five short reflection/intention strings, one for each mystery.
  - Inserts each reflection before its corresponding mystery/decade text in the active Rosary publish contract.
  - Uses deterministic fallback templates keyed by liturgical season and/or mystery set when Gospel-aware generation is unavailable.
- Enable Rosary audio for the new daily episode only after text generation is deterministic enough to validate.
- Add or migrate the Spotify Rosary queue contract to `spotify_episode_lookup` so `Daily Rosary` can resolve the Ora Pro Nobis episode by date.

### Non-Goals
- No new UI or manual authoring interface.
- No rewrite of the entire Rosary contract schema unless the research step proves the current block model cannot express the feature cleanly.
- No custom scripture source beyond the existing USCCB/catholic-mass-readings fallback stack for this release.
- No attempt to generate long homilies, catechesis, or full Gospel exegesis.
- No replacement of personal/intercessory Notion intentions across the whole playlist system.
- No support for alternate Rosary schedules beyond the current traditional weekday mapping in this iteration.

### Risks And Unknowns
- The current publish block model may not have a clean way to interleave generated reflections with each of the five mysteries without adding a new structured block type.
- Existing mystery template files may already include enough text that inserting extra reflections could make the episode too long once audio is enabled.
- The right fallback taxonomy needs validation: liturgical season, mystery set, weekday, or celebration rank could each be the correct fallback axis.
- Spotify lookup will depend on the exact title/date metadata chosen for the generated Rosary episode.
- Prompt output validation must be stricter than the current daily intro path because five reflections need stable count, ordering, and mystery association.

### Recommended Next Step
- Run `/research-astack` to map the active publish contract block renderer, audio fragment/resume marker behavior, Rosary template contents, and Spotify lookup patterns before planning implementation.
- Research should specifically decide whether to add a new block kind, extend `weekday_map`, or introduce a Rosary-specific generator helper behind the existing contract loader.
- Research should also propose the fallback intention taxonomy and the exact title pattern for Spotify lookup.

## Research

### Scope Baseline
- Build the active Ora Pro Nobis `Daily Rosary` into a real daily Rosary episode: traditional weekday mystery selection, five short Gospel-aware reflections/intentions, deterministic fallback intentions, publish text/audio output, and Spotify lookup against the generated Ora Pro Nobis episode.
- The implementation must use cached canonical Rosary prayers (`Our Father`, `Hail Mary`, `Glory Be`, etc.) for repeated prayers. Generated audio should be limited to date-specific reflections and other genuinely variable content.

### Relevant Files
- `config/publish/contracts/rosary.json` - Active Rosary publish contract. It already selects mysteries by weekday, but it currently inserts only one mystery summary file and has audio disabled.
- `config/publish/templates/rosary/*.txt` - Canonical Rosary prayer text library used by the active publish contracts. These are the right source for cached standard prayer fragments.
- `config/publish/templates/rosary/mysteries/*.txt` - Current mystery-set summaries. Each file has the set title plus five `Mystery - Fruit` lines, which can be parsed into decade metadata.
- `config/publish/templates/rosary/decade-meditation-template.txt` - Existing short meditation prompt template from the Rosary path. Useful for tone, but it is intention-based rather than Gospel-context-based.
- `jobs/publish/contracts.py` - Active publish contract loader, text resolver, section builder, audio fragment expansion, role override support, and resume marker source.
- `jobs/publish/daily_intro.py` - Existing Romcal/Gospel lookup and OpenAI prompt helper boundary. It can fetch Gospel context with `allow_missing_gospel=True`, but its generation validator is built for a single daily intro, not five Rosary reflections.
- `jobs/publish/fragments.py` - Publish audio fragment cache and assembly layer. Repeated fixed-prayer fragments should flow through this cache instead of being expanded into unique text blobs.
- `jobs/notion/generate_page_audio.py` - Archived Rosary dynamic builder. It contains useful prior logic for weekday mystery selection, intention splitting, decade metadata, and Rosary fragment keys, but it still points at discontinued `config/legacy/rosary.json` / `config/content/rosary` paths and should not become the active runtime.
- `config/spotify/contracts/daily-rosary.json` and `config/spotify/contracts/rosary.json` - Existing Spotify queue contracts still use the legacy `ROSARY` resolver.
- `config/spotify/contracts/auxilium-christianorum.json`, `config/spotify/contracts/daily-novenas.json`, and `config/spotify/contracts/morning-prayer.json` - Current examples of `spotify_episode_lookup` contracts against the Ora Pro Nobis show.
- `tests/test_publish_contracts.py`, `tests/test_publish_audio_fragments.py`, `tests/test_publish_audio_pipeline.py`, `tests/test_spotify_contracts.py`, `tests/test_refresh_job.py`, and `tests/test_refresh_job_contract_path.py` - Existing coverage for contract loading, publish text/audio behavior, fragment metadata, and Spotify lookup.

### Current System Map
- Publish contracts are JSON-first. `load_publish_contracts` validates block shapes, `build_text_jobs` resolves full text/sections, and `build_audio_jobs` expands the same contract tree into fragment specs.
- Supported publish block kinds are generic (`sequence`, `repeat`, `weekday_map`, `file`, `inline`, `daily_intro`, `liturgical_announcement`, etc.). There is no active block that can generate five structured Rosary decades from mystery metadata plus Gospel context.
- `weekday_map` currently chooses a single file by weekday. For Monday/Saturday it picks Joyful, Tuesday/Friday Sorrowful, Wednesday/Sunday Glorious, and Thursday Luminous.
- The checked-in mystery files are summaries, not full decade text. The active Rosary text output therefore shows opening prayers, a mystery list, and closing prayers, but not five decades of `Our Father` / ten `Hail Marys` / `Glory Be` / `Fatima Prayer`.
- Audio fragment expansion already supports leaf fragments, repeated blocks, text hashes, resume markers, and role/provider overrides. With the right block expansion, the cache can reuse one `Hail Mary` fragment wherever it appears rather than producing unique audio for every repetition.
- `daily_intro.py` owns the current Gospel retrieval stack: Romcal celebration context, `catholic_mass_readings` lookup, USCCB HTML fallback, and OpenAI text generation. That should remain the source of Gospel context, but Rosary reflection generation needs its own output contract and validator.
- The archived Notion Rosary dynamic builder demonstrates the old shape: resolve weekday mystery set, derive mystery metadata, insert decade meditations, and assemble ordered fragments. Its concepts are reusable; its file paths and Notion dependencies are not.
- Spotify refresh already has a generic `spotify_episode_lookup` path that scans show episodes by required title terms and date formats. Rosary should migrate to that path once the publish title is date-scoped.

### Reuse Opportunities
- Reuse the active Rosary prayer templates directly for fixed prayers. This gives stable text, stable fragment hashes, and maximum audio cache reuse.
- Reuse the existing publish `repeat` and fragment-cache semantics for repeated `Hail Mary` prayers where possible. If a Rosary-specific block emits fragments itself, it should emit repeated fixed-prayer fragments with stable labels/paths instead of one concatenated decade string.
- Reuse the current weekday mystery mapping and mystery template files as the source of mystery names/fruits; avoid duplicating the Rosary schedule in Python.
- Reuse `fetch_daily_gospel_context(..., allow_missing_gospel=True)` from `jobs.publish.daily_intro` for Gospel availability and fallback metadata.
- Reuse the new Auxilium role/provider override model only if Rosary later needs distinct voices. This release does not require multi-speaker Rosary audio; the cache requirement is higher priority.
- Reuse `spotify_episode_lookup` contract patterns from Auxilium/Morning Prayer/Daily Novenas for `Daily Rosary - {date_display}` title matching.
- Reuse the archived Rosary helper ideas (`choose_rosary_mystery_set`, `rosary_mystery_metadata`, fixed fragment keys) as reference behavior, not as imported runtime code.

### External References
- Romcal and `catholic_mass_readings` remain the relevant external sources through `jobs/publish/daily_intro.py`.
- Spotify episode lookup depends on the Spotify Web API `show_episodes` behavior already wrapped in `jobs/playlist/refresh_playlist.py`.
- OpenAI is only needed for Gospel-aware reflection generation; missing API key, missing Gospel, or invalid model output must not prevent a deterministic Rosary from publishing.

### Constraints
- Keep implementation inside the active contract-first publish boundary; do not revive the archived page-audio Rosary runtime.
- Audio must be cache-friendly: standard Rosary prayers are stable fragments, and only daily reflections should be date-specific generated fragments.
- Reflections must be exactly five items, ordered to match the selected mystery file, and short enough not to materially inflate the episode.
- Fallback behavior must be deterministic and testable without live Gospel, Spotify, Notion, or OpenAI calls.
- Rosary audio is currently disabled. Enabling it changes the daily feed surface and must be covered by audio job/sidecar/resume marker tests.
- The metadata title must become date-scoped before Spotify lookup can reliably resolve the generated Ora Pro Nobis episode.
- Current tests assert the old Rosary text has three sections and audio disabled; implementation will need intentional test updates.

### Risks
- The largest implementation risk is generating the full Rosary as one large text block, which would defeat fragment caching and create excessive repeated TTS work. The plan must require structured fixed-prayer fragments.
- A new block kind must participate in both text resolution and audio fragment expansion. If only text is updated, resume markers and cached audio fragments will drift from the visible episode structure.
- Prompt output validation is stricter than `daily_intro`: the Rosary generator must reject missing, extra, reordered, or overly long reflections.
- Date-scoped Spotify matching depends on the exact published title format and Spotify indexing delay.
- The existing mystery templates have a simple `Mystery - Fruit` text shape. Any future formatting change could break parsing unless the parser is defensive and covered by tests.

### Assumptions To Validate
- `Daily Rosary - {date_display}` is the desired published episode title and the best Spotify search target for the Ora Pro Nobis show.
- A complete audio Rosary with five decades is acceptable in length and cost when fixed prayers are cached.
- Fallback intentions should be keyed primarily by mystery set and fruit, with liturgical season or Gospel context used only when available.
- The current traditional weekday mapping is still the desired schedule for this release.
- One speaker is acceptable for Rosary prayers/reflections in this release; the Auxilium multi-speaker idea does not need to be generalized to Rosary now.

### Unknowns
- Whether the visible text should include the full text of every repeated prayer or a compact display with audio-only repeated fragments. Current publish behavior generally writes full resolved text, so planning should decide this explicitly.
- Whether `config/spotify/contracts/rosary.json` should also migrate, or only `daily-rosary.json`. The active Notion row naming will determine which queue contract matters.
- Whether reflection generation should persist sidecar text to avoid re-calling OpenAI on reruns for the same date, beyond relying on audio fragment caching.

### Recommended Direction
- Add a Rosary-specific publish block, likely `rosary_decades`, that resolves the configured weekday mystery file, parses five mystery/fruit entries, obtains Gospel context, builds or falls back to five reflections, and expands each decade as structured content.
- Implement the block in both text and audio paths. For audio, emit stable file-backed prayer fragments for `Our Father`, ten repeated `Hail Mary` fragments, `Glory Be`, and `Fatima Prayer`, plus one date-specific reflection fragment per decade.
- Add a small helper module such as `jobs/publish/rosary_reflections.py` for mystery parsing, fallback intentions, prompt construction, output validation, and Gospel-aware generation.
- Update `config/publish/contracts/rosary.json` to use the new decade block between the existing opening and closing sequences, enable audio only after deterministic fallback tests are in place, and set date-scoped metadata.
- Migrate `config/spotify/contracts/daily-rosary.json` to `spotify_episode_lookup` against Ora Pro Nobis show id `4PNxb0OazrkcEp3FAggRoD` with required name terms `["Daily Rosary"]` and the same date formats used by Auxilium/Morning Prayer.

## Plan

### Summary
- Build a contract-driven Ora Pro Nobis `Daily Rosary - {date_display}` episode with five full decades, one short daily reflection per decade, deterministic fallback reflections, audio enabled, and Spotify lookup by generated episode title/date.
- The chosen approach is a new structured publish block, `rosary_decades`, rather than hand-expanding the Rosary in JSON. This keeps weekday mystery selection, Gospel-aware generation, text rendering, audio fragments, and resume markers aligned in one runtime path.
- Standard Rosary prayers must stay cache-friendly: the block will emit stable file-backed prayer fragments for `Our Father`, repeated `Hail Mary`, `Glory Be`, and `Fatima Prayer`; only the five reflection fragments should be date-specific generated audio.

### What Already Exists
- `config/publish/contracts/rosary.json` already owns the active Rosary entry, opening prayers, closing prayers, and weekday mystery schedule.
- `config/publish/templates/rosary/*.txt` already provides canonical fixed prayer texts.
- `config/publish/templates/rosary/mysteries/*.txt` already provides five mystery/fruit rows per mystery set.
- `jobs/publish/contracts.py` already validates publish blocks, resolves text jobs, expands audio fragments, builds resume markers, and renders date-scoped metadata.
- `jobs/publish/daily_intro.py` already retrieves Gospel context and has the OpenAI settings/call patterns Rosary generation should follow.
- `jobs/publish/fragments.py` already caches identical leaf fragment text/provider settings, including repeated prayers.
- Spotify `spotify_episode_lookup` already supports Ora Pro Nobis show title/date matching.

### Architecture
- Add `jobs/publish/rosary_reflections.py` as the Rosary-specific helper boundary.
- Add `rosary_decades` handling to `jobs/publish/contracts.py` in three places: block normalization, text resolution, and audio fragment expansion.
- Keep text and audio assembled from the same decade model so resume markers match the spoken structure.
- Use full visible text for the Rosary, including every repeated prayer, because the publish text surface currently resolves actual spoken text rather than compact audio-only instructions.

```text
rosary.json
  |
  | opening sequence -> fixed file fragments
  |
  | rosary_decades
  v
weekday -> mystery file -> 5 mysteries/fruits
  |
  +-> Gospel context -> OpenAI five reflections
  |                  -> deterministic fallback on missing/invalid output
  |
  +-> text: 5 full decade sections
  +-> audio: reflection fragment + cached fixed prayer fragments
  |
  | closing sequence -> fixed file fragments
  v
Daily Rosary - April 6, 2026
  |
  +-> docs/audio sidecar + podcast feed
  +-> Spotify lookup by "Daily Rosary" + date
```

### Failure Modes
- Missing or malformed mystery file:
  - Detection: parser raises during text/audio job building.
  - User experience: publish fails before writing a bad episode.
- Missing Gospel or OpenAI unavailable:
  - Detection: helper logs fallback reason and returns deterministic fallback reflections.
  - User experience: episode still publishes with non-Gospel-specific but mystery-appropriate reflections.
- Invalid model output:
  - Detection: reflection validator rejects wrong count, blank items, or overly long items.
  - User experience: fallback reflections are used.
- Missing fixed prayer template:
  - Detection: existing `_read_text_file` failure during block resolution.
  - User experience: publish fails closed before audio generation.
- Fragment-cache regression:
  - Detection: audio fragment tests assert repeated prayers keep identical text/effective config and render cache tests cover identical text reuse.
  - User experience: without detection, Rosary audio would be slower and more expensive, so this is a required test.
- Spotify lookup miss:
  - Detection: Spotify contract tests validate config; live refresh logs unresolved lookup if Spotify has not indexed the new episode yet.
  - User experience: playlist may omit Rosary until the feed episode appears in Spotify.
