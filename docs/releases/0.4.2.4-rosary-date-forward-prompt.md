# Release 0.4.2.4 - rosary-date-forward-prompt

- Status: Shipped
- Created Date: 2026-08-20
- Last Updated: 2026-08-20

## Scope

### Problem
- Daily Rosary prompting can inherit a backward-looking or generic saint-centered theme instead of explicitly stating the deterministic date, weekday mystery set, and selected liturgical observance.
- The generated package does not require the requested contemplative structure: biblical scene, traditional fruit, observance application, personal questions, and a closing petition for every mystery.
- Upcoming observances can be presented ambiguously, making an approaching feast sound as though it is celebrated today.

### Audience
- Primary user: a Catholic listener who reads or hears the Rosary meditation immediately before praying each decade.
- Secondary stakeholder: the scheduled text/audio publishing pipeline, which needs a stable five-decade contract and deterministic fallback.

### Current Status Quo
- `jobs/publish/rosary_reflections.py` builds a five-decade devotional package from Romcal, Gospel, shared daily-theme, and saint-witness inputs.
- Existing priority resolution is primarily about the current day's rows and does not expose a date-forward observance-selection contract to the Rosary prompt.
- The prompt asks for introduction, overall intention, and decade intention/reflection pairs, rather than the user-facing meditation sections requested here.

### Goal
- Make the prompt explicitly date-forward and local-date aware while keeping calendar authority deterministic: state the already-selected weekday mysteries and observance, including whether it is today or upcoming and its actual date.
- Require a brief opening that clearly distinguishes today's celebration from an upcoming celebration and states the central Rosary theme.
- Require five reverent, Scripture-rooted meditations with the exact sections needed for immediate prayer: mystery heading, biblical introduction, traditional fruit and practical meaning, observance application, one or two questions, and a short petition.
- Preserve safe generation, validation, caching, audio rendering, and deterministic fallback behavior.

### Constraints
- Keep the General Roman Calendar and reliable supplied calendar data authoritative; do not encourage obscure saint-of-the-day substitutions.
- Do not imply an upcoming observance is today's celebration, invent biographical facts, quotations, Scripture citations, or liturgical ranks, or force weak saint-to-mystery associations.
- Preserve exactly five ordered mysteries, current publishing contracts, human-need metadata, Scripture-citation safeguards, and no-key fallback behavior.
- Use the actual target date and configured local timezone/date context; tests must use fixed dates and must not depend on the machine clock.

### Narrow Wedge
- Replace the Rosary generation prompt and structured prose fields with a compact, validated meditation contract that carries explicit observance timing/date and five sectioned meditations.
- Pass the deterministic observance selection and timing metadata into the prompt without adding model-driven calendar selection or web search.
- Update fallback prose and focused tests without changing providers, routes, audio voices, or unrelated devotional prompts.

### Non-Goals
- Building a complete independent liturgical-calendar database or replacing Romcal/shared calendar ingestion.
- Changing the weekday mystery schedule, Rosary prayers, audio pipeline, publishing routes, or unrelated saint/novena prompts.
- Guaranteeing external calendar verification when no calendar data or network is available; the prompt must degrade safely to supplied facts.

### Risks And Unknowns
- The current shared-theme builder may not expose enough selected-observance date/rank information to the Rosary context, so the prompt input may need additive metadata plumbing.
- A richer meditation schema may require adapting renderers that currently expect `intention` and `reflection` fields.
- Calendar rank names and observance titles vary by provider; normalization must avoid selecting an optional memorial over a higher-ranked later celebration.

### Recommended Next Step
- Map the current Rosary render contract and deterministic calendar-context payload, then lock the smallest prompt/schema changes in `/plan-astack` before implementation.

## Research

- The deterministic `build_saint_centered_theme_brief()` already fetches a target-day plus future calendar window, ranks observances, and supplies selected dates/ranks in its brief.
- `build_rosary_day_context()` currently carries the selected witness but not all timing metadata into the Rosary prompt.
- Rosary rendering currently emits five headings, fruit, intention, reflection, and prayers; the requested prompt can remain compatible by strengthening the existing intention/reflection prose contract and renderer labels.

## Plan

### Summary
- Add deterministic observance timing fields to `RosaryDayContext` and expose them in the Rosary prompt.
- Rewrite the prompt as a date-forward Catholic meditation brief with explicit weekday mystery mapping, observance timing rules, and the requested five-mystery structure.
- Keep the existing structured response shape and publishing/audio interfaces stable; update deterministic fallback prose and focused tests to enforce the new content contract.

### What Already Exists
- `build_saint_centered_theme_brief()` deterministically selects the primary calendar anchor and saint witness from Romcal data.
- `build_rosary_day_context()` supplies the selected mysteries, priorities, Gospel, season, witness, and quote to the prompt.
- Existing validators, structured/JSON retry paths, cached devotional sets, and renderers provide compatibility boundaries.

### Architecture
```text
local target date + deterministic calendar brief
                 |
                 v
        RosaryDayContext (date, weekday set,
          selected observance + timing/rank)
                 |
                 v
       date-forward meditation prompt
                 |
       structured JSON + existing validators
             /                 \
       generated prose       deterministic fallback
             \                 /
              cached five-decade Rosary
```

### Concrete Changes
- Edit `jobs/publish/daily_theme_runtime.py` only if needed to preserve selected observance date/rank fields from the deterministic brief.
- Edit `jobs/publish/rosary_reflections.py`:
  - extend `RosaryDayContext` with selected observance date/rank/timing metadata;
  - build explicit “today” or “as we approach [name] on [date]” instructions from deterministic inputs;
  - replace generic package instructions with the user's opening and per-mystery structure, including Scripture narration, traditional fruit, observance application, reflection questions, and petition;
  - explicitly forbid backward-looking calendar search, model-selected observances, false “today” wording, invented facts, and weak forced connections;
  - retain the current structured fields and validator boundaries, using `intention` for the petition/intention and `reflection` for the biblical, fruit, application, and question material;
  - update deterministic fallback sentences to state timing accurately and include the requested spiritual movement.
- Edit `jobs/publish/contracts.py` only if renderer labels need to expose the structured sections; preserve existing audio fragment keys.
- Extend `tests/test_publish_rosary_reflections.py` with fixed-date tests for weekday mystery instructions, today/upcoming wording, date/rank metadata, the complete five-mystery prompt contract, and fallback timing.
- Run the existing Rosary, publish-contract, text, audio, and formatting regression suites.

### UX And States
- Normal success: the opening names the weekday mysteries and deterministic observance, then each decade reads as a self-contained meditation before prayer.
- Upcoming observance: the prose says it is approaching and includes the actual calendar date; it never says the feast is celebrated today.
- Missing observance metadata: use the deterministic current-day priority/season wording without inventing a date or saint.
- LLM failure: the deterministic fallback remains publishable and follows the same timing distinction as far as supplied metadata permits.

### Failure Modes
- Missing future/timing metadata: prompt states only the supplied deterministic observance; no model selection occurs.
- Generated prose says an upcoming observance is today: validation or prompt-facing test catches the contract regression; fallback uses explicit timing.
- Generated prose omits a mystery section: existing five-decade validation plus prompt contract tests catch it.
- Provider failure: existing JSON retry and deterministic fallback remain active.
