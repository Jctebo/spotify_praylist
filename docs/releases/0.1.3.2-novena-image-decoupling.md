# Release 0.1.3.2 - novena-image-decoupling

- Status: Future
- Created Date: 2026-03-28
- Depends On: 0.1.3.1
- Roadmap: `docs/roadmaps/stabilization.md`
- Notes: This release splits devotional image generation and daily novena generation into separate pipelines while keeping the shared liturgical helper surface intact.

## Scope

### Problem
- The devotional image and daily novena jobs still run together in one workflow job, so a failure in one path can take down the other.
- The shared import surface between `jobs/novena/generate_devotional_image.py` and `jobs/novena/generate_daily_novena_prayer.py` makes the two pipelines harder to fail, retry, and ship independently.
- The local operator entrypoints mirror the image job more than they expose separate novena and image controls.

### Audience
- Primary user: the maintainer who needs devotional images and novenas to recover independently.
- Secondary stakeholders: operators who run the workflows locally or in GitHub Actions and need separate failure domains.

### Current Status Quo
- `.github/workflows/daily_devotional_image_remote.yml` currently runs devotional image generation and daily novena generation in the same `calendar` job.
- `jobs/novena/generate_devotional_image.py` imports shared constants and helpers from `jobs/novena/generate_daily_novena_prayer.py`.
- `scripts/run_daily_devotional_image_rclone_local.ps1` mirrors the image job directly instead of exposing a split image/novena operator path.
- `scripts/run_daily_novena_prayer_local.ps1` exists, but the workflow surface still does not present two independent pipeline entrypoints.
- The existing shared liturgical model and Notion helpers are already reusable, but the boundary between job-specific code and shared code is still blurred.

### Goal
- Split the devotional image and daily novena jobs into separate pipelines so they can fail, retry, and ship independently.
- Keep shared liturgical and helper logic available to both jobs without duplicating it.
- Preserve current behavior initially so the split is low risk and easy to validate.
- Expose two clear entrypoints or workflow paths: one for devotional images and one for daily novena generation.

### Constraints
- Do not fix the OpenAI secret boundary for image generation in this release.
- Do not change Morning Prayer publishing behavior in this release.
- Do not migrate TTS providers in this release.
- Keep the shared liturgical model and helper code available to both paths.
- Avoid over-sharing helpers in a way that recreates a single shared-core bottleneck.

### Narrow Wedge
- Extract only the helper code that is truly shared between the image and novena jobs.
- Split the current combined workflow so the image path and novena path can run independently.
- Keep each path's output and runtime behavior the same at first, then tighten boundaries after the split is stable.
- Update local wrappers so operators can run the image and novena paths separately.

### Non-Goals
- Fixing the OpenAI credential issue behind the image pipeline.
- Morning Prayer publishing changes.
- TTS provider migration.
- Reworking devotional image rendering quality or prompt style.
- Re-architecting the full liturgical model beyond the helper boundary needed for the split.

### Risks And Unknowns
- The current import coupling may hide helper assumptions that need to move together.
- Splitting the workflow without cleaning up shared setup could duplicate environment configuration.
- Over-shared helpers could blur the boundary again and recreate a monolithic maintenance surface.
- It is not yet proven whether the novena and image workflows need distinct local scripts or can share a thin wrapper layer.

### Recommended Next Step
- Use `/research-astack` to inventory the shared helper code, identify exactly which functions should move into a common module, and map the workflow and local-script boundaries for the split.
