# Release 0.1.3.2 - novena-image-decoupling

- Status: Shipped
- Shipped Date: 2026-03-28
- Last Updated: 2026-03-28
- Created Date: 2026-03-28
- Depends On: 0.1.3.1
- Roadmap: `docs/roadmaps/stabilization.md`
- Notes: This release moved the shared liturgical helpers into `jobs/novena/liturgical_helpers.py`, cut the devotional image workflow over to that module with no compatibility shims, and kept the novena workflow disabled while the image pipeline was restored first.

## Scope

### Problem
- Devotional image generation previously borrowed generic helpers from `jobs/novena/generate_daily_novena_prayer.py`.
- The image job depended on a separate `jobs/novena/liturgical_model.py` eligibility file instead of one shared helper boundary.
- The active image workflow was still coupled to a novena step that was not the main release target.
- The image path needed a hard cutover into the new helper model with no temporary fallback imports.
- The novena workflow stayed disabled in this release; the goal was to restore the image pipeline, not to turn novena generation back on.

### Audience
- Primary user: the maintainer who needs devotional images running again.
- Secondary stakeholders: operators who run the image workflow locally or in GitHub Actions.

### Current Status Quo
- `jobs/novena/generate_devotional_image.py` imported generic env, Notion, Romcal, and title helpers from `jobs/novena/generate_daily_novena_prayer.py`.
- `jobs/novena/generate_daily_novena_prayer.py` imported `devotional_output_is_eligible` from `jobs/novena/liturgical_model.py`.
- `.github/workflows/daily_devotional_image_remote.yml` bundled devotional image generation with a novena step.
- `.github/workflows/daily_novena_prayer.yml` already existed as a disabled workflow and stayed disabled in this release.
- The image job already had local runner and test coverage, but the helper boundary was still split across old novena-branded files.

### Goal
- Move the shared liturgical helper surface into `jobs/novena/liturgical_helpers.py`.
- Repoint the devotional image job and the novena runner to the new helper module directly.
- Remove the old eligibility split so the image path has one clear helper boundary.
- Keep the novena workflow disabled.
- Make the image pipeline the active, successful outcome of the release.

### Constraints
- Do not enable the novena workflow in this release.
- Do not keep compatibility shims or shadow imports in the active image path.
- Do not broaden the helper module into a catch-all utility layer.
- Keep the helper module specific to the liturgical domain.
- Preserve direct execution and temp-cwd bootstrap for the image job.

### Narrow Wedge
- Extract only the helper code that the image job and its shared liturgical boundary needed.
- Move the eligibility contract into the new helper module.
- Cut the image workflow over to the new module with no dual-path fallback.
- Leave the novena workflow disabled and out of rollout.

### Non-Goals
- Turning on novena generation.
- Renaming the novena runner.
- Reworking Morning Prayer or page-audio behavior.
- Keeping the old helper paths alive as compatibility layers.
- Changing devotional image design or storage layout.

### Risks And Unknowns
- A helper cutover could have missed a symbol that the image job still needed.
- Removing the old helper module too soon could have broken direct execution if a callsite still pointed at it.
- The image workflow could still have failed if workflow env or imports were not updated in the same pass.
- The disabled novena workflow needed to remain disabled and not accidentally become a rollout target.

### Recommended Next Step
- Use `/ship-astack` once the helper boundary and image-only rollout path are verified.

## Plan

### Summary
- Move the shared liturgical helpers into `jobs/novena/liturgical_helpers.py`.
- Cut the devotional image pipeline over to that module directly, with no fallback import path to the old novena helper surface.
- Leave the novena workflow disabled; the release target is a working image pipeline.

### What Already Exists
- `jobs/novena/generate_devotional_image.py` already contains the image pipeline logic that needs the helper cutover.
- `jobs/novena/generate_daily_novena_prayer.py` already contains the reusable helper surface and eligibility logic that the image job currently borrows.
- `.github/workflows/daily_devotional_image_remote.yml` already contains the image job that should be the active rollout target.
- `.github/workflows/daily_novena_prayer.yml` already exists as a disabled placeholder and should remain disabled.
- `tests/test_devotional_image_job.py` already covers image-side eligibility behavior and import-time assumptions.

### Architecture
```text
                     jobs/novena/liturgical_helpers.py
                        /                         \
                       /                           \
jobs/novena/generate_devotional_image.py     jobs/novena/generate_daily_novena_prayer.py
                 |                                      |
        active image workflow                   disabled novena workflow
```
- The image job becomes the first-class consumer of the new helper module.
- The novena workflow stays off, so the release does not depend on enabling that path.
- No compatibility wrapper should be left in the active image path.

### Concrete Changes
- Add `jobs/novena/liturgical_helpers.py`.
- Update `jobs/novena/generate_devotional_image.py` to import `require_env`, `int_env`, `bool_env`, `local_today`, `notion_*`, `romcal_*`, `page_title`, `infer_celebration_rank`, `infer_precedence`, and `devotional_output_is_eligible` from `liturgical_helpers.py`.
- Update `jobs/novena/generate_daily_novena_prayer.py` to use the new helper module for the shared helper surface it still needs.
- Remove `jobs/novena/liturgical_model.py`.
- Update `.github/workflows/daily_devotional_image_remote.yml` so it runs only the image job.
- Update `README.md` so the image workflow is documented as the active target and the novena workflow is described as disabled.
- Update `tests/test_devotional_image_job.py` for the new helper import path and any bootstrap assumptions.
- Update `tests/test_novena_job.py` if the shared helper move changes its import path or bootstrap behavior.
- Add `tests/test_liturgical_helpers.py` for the new helper module if coverage is needed for the extracted shared boundary.

### UX And States
- There is no new UI; this is a pipeline and module boundary change.
- Success state: the image workflow runs without importing from the old novena helper surface.
- Disabled state: the novena workflow remains disabled and clearly documented as such.
- Error state: an old import path or missing helper symbol fails fast with a non-zero exit.

### Implementation Phases
#### Phase 1: Shared helper module
- Goal: create `liturgical_helpers.py` and move the reusable helper surface and eligibility contract into it.
- Exact files to edit: `jobs/novena/liturgical_helpers.py`, `jobs/novena/generate_daily_novena_prayer.py`, `jobs/novena/liturgical_model.py`, `tests/test_liturgical_helpers.py`.
- Symbols/interfaces touched: the helper functions that the image job currently imports, plus `devotional_output_is_eligible`.
- Change summary: centralize the shared helper boundary and remove the separate eligibility file.
- Verification steps or commands: `python -m unittest tests.test_liturgical_helpers tests.test_novena_job` if the novena import path changes.
- Rollback note: if a symbol is missed, move that symbol into the helper module in the same pass rather than adding a compatibility shim.
- Dependencies on earlier phases: none.

#### Phase 2: Image cutover
- Goal: make `generate_devotional_image.py` consume the new helper module directly and make the image workflow the only active rollout target.
- Exact files to edit: `jobs/novena/generate_devotional_image.py`, `.github/workflows/daily_devotional_image_remote.yml`, `README.md`, `tests/test_devotional_image_job.py`.
- Symbols/interfaces touched: the image job imports, the combined workflow step, and the image-job test bootstrap.
- Change summary: cut the image path over to the new helper module and remove the novena step from the active image workflow.
- Verification steps or commands: `python -m unittest tests.test_devotional_image_job`, plus a manual or workflow-based image smoke run.
- Rollback note: if the image job still points at the old module, fix the import rather than restoring the fallback.
- Dependencies on earlier phases: phase 1.

#### Phase 3: Disabled novena hold
- Goal: leave the novena workflow disabled and documented as out of scope for this release.
- Exact files to edit: `README.md`, `.github/workflows/daily_novena_prayer.yml` only if wording needs a refresh.
- Symbols/interfaces touched: release docs and the disabled workflow note.
- Change summary: make sure the repo clearly says novena is not being turned on as part of this work.
- Verification steps or commands: confirm the workflow remains disabled and is not referenced as the active target.
- Rollback note: none, because the release intentionally does not activate novena.
- Dependencies on earlier phases: phases 1 and 2.
