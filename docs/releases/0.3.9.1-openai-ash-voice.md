# Release 0.3.9.1 - OpenAI Ash Voice

- Status: Shipped
- Date: 2026-07-24
- Branch: `enhancement/openai-ash-voice`

## Scope

### Problem
- Active OpenAI text-to-speech contracts and runtime fallbacks still select the `alloy` built-in voice.
- The approved `ash` sample better matches the desired spoken identity for Ora Pro Nobis.

### Audience
- Primary user: listeners of generated Ora Pro Nobis prayer and devotional audio.
- Secondary stakeholders: maintainers operating the publish-audio, novena, and archived page-audio compatibility paths.

### Current Status Quo
- Publish contracts, novena contracts, runtime defaults, and provider fallbacks can select `alloy`.
- Tests and fixtures encode `alloy` as the expected OpenAI voice, so changing configuration alone would leave inconsistent defaults and assertions.

### Goal
- Make `ash` the OpenAI TTS voice everywhere active code or configuration currently uses `alloy`.
- Keep provider routing, TTS model, format, speed, role-specific non-Alloy voices, and ElevenLabs settings unchanged.
- Update regression coverage so tests prove the effective OpenAI default and configured fallback are `ash`.
- Success means no `alloy` reference remains in active code, configuration, contracts, or tests, while historical release documentation remains unchanged.

### Constraints
- Preserve `gpt-4o-mini-tts` and the current OpenAI speech API behavior.
- Do not alter explicitly configured role voices such as `echo` or `nova`.
- Do not rewrite historical release artifacts that describe previously shipped behavior.
- Preserve cache correctness by allowing the existing normalized TTS settings to distinguish the new voice automatically.

### Narrow Wedge
- Replace exact OpenAI `alloy` voice values and runtime fallback defaults with `ash`.
- Update directly coupled tests and fixtures.
- Run focused audio, publish-contract, novena, and page-audio test suites plus a repository-wide active-source search.

### Non-Goals
- Changing TTS providers, provider priority, model, speed, audio format, pronunciation, or voice instructions.
- Regenerating or publishing production audio.
- Replacing non-Alloy role-specific voices or ElevenLabs voice IDs.
- Editing historical release records.

### Risks And Unknowns
- Generated audio caches may retain old Alloy fragments until normal cache-key invalidation selects the new Ash settings; the current fragment hash is expected to include normalized TTS settings and must be verified.
- Archived compatibility paths may still be executable and therefore need the same default even though their configuration files are not primary publish surfaces.

### Recommended Next Step
- Use `/plan-astack` to enumerate the exact production, contract, fixture, and assertion changes and define focused verification commands.

## Research

- OpenAI's speech API documentation confirms that `ash` is a supported built-in voice for `gpt-4o-mini-tts`.
- A live `ash` sample request returned a valid MP3 and the resulting voice sample was approved before implementation.
- Repository-wide searches mapped the active voice contract across publish configuration, novena configuration, runtime fallbacks, authoring helpers, compatibility paths, and coupled tests.
- The existing fragment and manifest hashing includes normalized TTS settings, including `voice`, so Ash renders use distinct cache entries without deleting prior Alloy audio.

## Plan

### Summary
- Replace every active exact OpenAI `alloy` voice setting and fallback with `ash`, then update the tests and fixtures that encode the former voice.
- Use a repository-wide mechanical value change because all affected surfaces share the same built-in OpenAI voice contract and no schema or routing change is required.

### What Already Exists
- `gpt-4o-mini-tts` already accepts the approved built-in `ash` voice; the sample request completed successfully.
- Publish and novena contracts already carry explicit voice configuration.
- Runtime loaders already normalize missing/blank voice values to a deterministic default.
- `jobs/publish/fragments.py` includes normalized TTS settings, including `voice`, in fragment and manifest hashes, so changing the voice invalidates stale Alloy cache entries.
- Existing publish, novena, contract, branding, and page-audio tests cover the affected configuration and fallback paths.

### Architecture
- No new components, schemas, dependencies, UI, or migrations are needed.
- The effective voice continues to flow through the existing path:

```text
contract/provider voice ("ash") ─┐
runtime default ("ash") ─────────┼─> normalized TTS settings
                                 └─> voice-inclusive fragment hash
                                      ├─> new cache entry
                                      └─> OpenAI speech request
```

### Failure Modes
- A missed runtime fallback could continue producing Alloy when a contract omits `voice`; detect with the active-source search and fallback tests.
- A missed contract could keep Alloy for one devotion; detect by scanning all publish and novena JSON.
- Test-only replacement could accidentally erase deliberate multi-voice coverage; detect by reviewing explicit `echo`, `nova`, and ElevenLabs assertions.
- Stale cached Alloy audio could be reused if the cache key omitted voice; detect with the existing fragment-hash test plus a direct Ash-vs-Alloy hash assertion.
