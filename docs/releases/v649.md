## §2 Grounding — the failing seams (shipped code, base = pin ora-pro-nobis-v648-1)

Read firsthand from `app/worker/src/client.ts` and
`app/worker/src/index.ts` on the base tree.

### Seam 1 — ADOPTION: a boot-restored queue blocks the v648 build forever (CONFIRMED)

`opnSafe647()` (client.ts ~25410) returns false whenever
`state.current` stands or `state.queue` is non-empty.
`standRestoredQueue(day)` (~5860) stands BOTH at every boot that
carries a same-day queue snapshot (`opn-queue-v355`) — queue and
current set, paused, before any user act. The restored stand is
not a user act, yet it fails the safe-moment predicate at every
5 s re-check (`opnTryAdopt647`) for as long as the queue stands.

And a cold boot never pends adoption by itself:
`opnCheck647()`'s first fetch in a session sets
`opnRunPin647 = served` and returns — the pend requires a
mid-session or foreground pin-change detection, after which the
restored queue blocks the safe moment indefinitely. John's queue
stood from the morning (the Daily Rosary in the dock, his 08:27
screenshot) and restores at every boot. His 12:57 close/reopen
therefore proves nothing about which pin his phone runs, and a
phone in this state can stay on the pre-v648 client — whose
download path is choice-blind (Seam 2's origin) — indefinitely.

**The rule this fix stands:** a boot-restored queue the user has
not touched this session does not block adoption; a queue built
or played this session still does. The seat already exists:
`state.restoredQueue` stands from `bootQueueSnapshot` until
`clearRestoredQueue()` drops it at the standing clearing
moments. The Implement grounds the exact touch points (any
start/transport act this session counts as a touch, the podcast
restore's stand included) and makes `opnSafe647` read the
current/queue pair as blocking only when the stand is not the
untouched restore.

### Seam 2 — BYTES: the audio cache entry is source-blind, and the restore trusts it (CONFIRMED)

Every external slot's audio is downloaded into the Cache API
under `offlineDayKey(date, slotId)` — one key per (date, slot),
no source dimension. The writers stamp nothing about provenance:
`extDownload`'s put (~20263) and the offline completeness pass's
put (~19581) each store `new Response(blob, { Content-Type:
'audio/mpeg' })` and nothing else. The reader,
`extRestoreCached` (~20366), mints whatever bytes stand under
the key and settles them present under the record's meta — the
bytes are never compared to the record they will play under.

The v648 prune (~20035) tests the RECORD's fields only (standing
source = the preference's first choice · backup present ·
imageUrl non-null) and evicts record + audio entry together when
a field fails. A record whose fields stand whole over the OTHER
source's bytes passes the prune untouched — and the courier
leg's pointer-confirm (v648 F2) likewise compares pointers,
never bytes.

The poison's origin is the pre-v648 pair: the old client's
`extDownload` fetched the pass-through WITHOUT `src`; the old
Worker re-resolved Divine-Office-first and answered 200 with
Divine Office audio; the client stored those bytes under the
slot's key beneath a Sing the Hours record. The pre-v648 offline
completeness pass (choice-blind in the same way) could write the
same poison ahead of the day, and a restore from that entry
settles it present under a whole-fields record. Title right,
thumbnail right, audio wrong — John's row, produced by the
download/restore path regardless of what the payload, the
choice, or the pass-through's new `src` rule say.

**The rule this fix stands:** a cached audio entry is bound to
the enclosure it was fetched for. Both day-keyed put sites stamp
the stored Response with that enclosure URL (header
`x-opn-enclosure` — for a pass-through fetch, the meta's
enclosureUrl, since the v648 `src` rule makes the served bytes
that pointer's source; for a direct fetch, the fetched URL).
`extRestoreCached` compares the stamp to the record's
enclosureUrl: a match mints as today; a mismatch — or a missing
stamp — is a cache miss and the slot re-downloads through the
standing routes (which re-stamp). The rule is uniform across
external slots (a server-side Sing the Hours fill on an
unlabeled Divine Office slot carries its own enclosureUrl and
obeys the same compare). The offline pass's reuse read (~19591)
applies the same compare before it treats an entry as standing.

### Seam 3 — THE NATIVE PATH: stands correct on v648 code; its truth is the record (GROUNDED)

`nativeContractItem` delegates non-podcast tracks to
`oraSnapshotTrack` (~17793/17804): for the two labeled slots the
contract's mediaUri is the Worker pass-through carrying
`&src=` + the settled record's `source`. The shipped Worker
(index.ts ~5807) serves the day's `ext_resolutions` row by that
src — `stream_url` for the standing source, `backup_url` for
the backup source, 404 for an unmatched src, never a silent
serve of the other source. So on v648 code the engine is handed
the chosen source; the contract inherits the RECORD's source,
which Seam 2's poison never corrupts (the record's fields were
right — only the downloaded bytes were wrong, and the native
path does not play the downloaded bytes). This is exactly why
the v648 harness — which modeled the contract and the payload —
passed while the field failed on the download/restore path
behind an un-adopted client. No change to the contract seat;
the gates keep its legs and add the engine-request leg under
the field state (§4 G4).

### Seam 4 — THE FLIP: two ways it cannot reach the sound (GROUNDED)

The Edit-form chips (client.ts ~21633) call
`opnSthFirstSet632(...)` (the store write) and then
`state.extResettleLabeled638()`. On v648 code the resettle
re-settles the slot's pointer whole — but:

- (a) on a pre-v648 client (Seam 1: his phone can be one,
  indefinitely) the same tap downloads through the src-less
  pass-through, which without `src` re-resolves Divine-Office
  first BY DESIGN (the standing no-src behavior) — Divine
  Office bytes again, under the new title. The flip cannot fix
  a phone the fix never reached.
- (b) on v648 code, the resettle's no-change guard compares
  enclosure pointers only: when the record's pointer already
  equals the choice's, the resettle no-ops — while the blob
  minted this session may be Seam 2's poisoned bytes, and the
  next play sounds them.

**The rule this fix stands:** inside the resettle hook, a
labeled slot whose pointer already matches the choice still
verifies its audio entry's stamp (Seam 2's compare); on a
mismatch or a missing stamp it evicts the entry and re-settles
through `settleMeta` under a taken epoch — the standing
machinery, no new path. With Seam 1 fixed, the flip also
reaches phones it never reached before.

## §3 The fix (numbered to the seams)

1. **Adoption (client, v647 family):** `opnSafe647` treats a
   standing `state.current` / `state.queue` as blocking only
   when the stand is not the untouched boot restore. The
   restore's own stand (day form and podcast form) is marked
   untouched at stand time; any user transport or queue act
   this session (a start, a resume/play command, a queue edit)
   marks it touched. Every other v647 blocker (sounding
   transport, gate paints, the edit form, a sheet/menu open)
   is unchanged.
2. **Enclosure stamp (client):** both day-keyed put sites
   (extDownload · the offline completeness pass) store the
   fetched-for enclosure URL as the `x-opn-enclosure` header
   on the cached Response. `extRestoreCached` and the offline
   pass's reuse read compare the stamp to the record's /
   item's enclosureUrl; mismatch or absence = miss →
   re-download through the standing routes.
3. **Flip heal (client):** the resettle hook's no-change
   branch verifies the labeled slot's stamp before it no-ops
   (§2 Seam 4b).
4. **Nothing else moves:** the pass-through's `src` rule, the
   choice function, the settle machinery, the queue discipline
   (v645), the marks (v617), and the adoption act itself
   (record-then-reload, one reload per pin) stand as shipped.
