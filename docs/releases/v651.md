# v651 — v650's two office tracks both sound Divine Office on the phone: the native offline file is keyed by track id alone

## §1 The item (DevOps Board row 1628 · field failure of v650, live pin ora-pro-nobis-v650-1)

v650 shipped the redesign John directed: for each labeled
office slot (Morning Prayer · Evening Prayer) the app paints
the Divine Office episode and the Sing the Hours episode as
SEPARATE TRACKS, each standing on its own record whole — its
original title, its stream, its image, its duration. In the
field on John's phone:

- Both tracks paint, each with its own title and image —
  John confirms the titles/images are each track's own.
- The AUDIO is Divine Office whichever track he taps: tap
  the Sing the Hours track, Divine Office sounds; tap the
  Divine Office track, Divine Office sounds.

Proven by the main seat firsthand before this Plan opened
(not re-litigated here): the live payload carries both
records whole; the Worker audio pass-through discriminates
— `&src=Sing the Hours` serves bytes MD5-identical (first
16 KB) to the direct castos file, `&src=Divine Office`
serves the Divine Office file (ID3-verified). The server is
whole. The wrong turn is the last hop on the phone:
tapped track → speaker.

**The ask:** a tap on the Sing the Hours track sounds the
Sing the Hours episode through the phone's engine, and a
tap on the Divine Office track sounds the Divine Office
episode — Morning and Evening alike — with each track's
title, image, marks, and queue behavior exactly as v650
paints them.

**Scope note stated at the head, per the grounding in §2:
THIS FIX NEEDS AN APK CHANGE.** The losing hop stands in
the Android shell (repo `Jctebo/ora-pro-nobis-android`,
local clone `~/workspace/android-apk/`), not in the web
client and not in the Worker. The shell consequence: a NEW
APK version must be built and John must install it — the
v647-style silent web adoption cannot carry this fix, and
no web-only build can heal his phone. §2.5 proves the
web-only alternative (a side-suffixed bridge id) breaks the
bridge contract's identity surfaces and is rejected.

### 2.1 (a) The StH-side descriptor, as the queue and engine consume it — WHOLE per side

The two sides part nowhere in the client until the bridge
id (§2.2):

- `extPaintSides650` (client.ts:2228) returns one view per
  painting side; under 'Both' it sorts Sing the Hours
  first, Divine Office second. `extStandingView650`
  (:2219) and `extSide2View650` (:2223) each carry their
  side's own `{ title, source, imageUrl, durationSec,
  enclosureUrl, streamUrl }` — the standing side from the
  record's standing fields, the other from `record.side2`.
- `extPaintTracks650` (:2246) builds one descriptor per
  side through `extSlotTrack(slot, v)` (:17901), which
  stamps `source: st.source` and
  `streamUrl: st.state === 'present' ? st.streamUrl : null`
  from THAT side's view; the second-painted descriptor
  additionally carries `_side650 = extSideTag650(v.source)`
  (:2253).
- The one expansion seam, `trackDesc` (:15410), carries
  every play-side field per side: `url: t.streamUrl`,
  `source: t.source`, and `_side650` beside `_occ`
  (:15426). `descCardKey` (:17192) appends `'@' + tag` for
  the second side and `descMarkKey` (:4864) appends the
  same suffix to the played key — cards, marks, and draws
  are per-side distinct, exactly as v650 §3.3 designed.
- The WebView byte store is likewise per side:
  `extAudioKey650` (:2215) keys a labeled side's Cache
  Storage entry `day/<date>/<slotId>~<tag>`;
  `extRestoreSide650` matches that key, requires the v649
  stamp to equal THAT side's `enclosureUrl`, deletes the
  side's entry on mismatch, and deletes the pre-v650 bare
  key on sight; `extDownloadSide650` mints under a per-side
  owner (`extSlotOwner(slot, sideMeta.source)`). A copy
  fetched under the retired bare key, or under the Divine
  Office side's key, can never mint under the Sing the
  Hours descriptor in the WebView store. **(c) is CLEARED
  for the WebView store** — and §2.3 shows the native store
  never received this discipline.

### 2.2 (b) The engine hand-off — mediaUri per side, id shared

- `oraSnapshotTrack`'s labeled branch (client.ts:18184)
  returns, per descriptor:
  `id: d.episodeId` — THE SAME id for both sides
  (`ext-morning-prayer` / `ext-evening-prayer`) — and
  `mediaUri: origin + '/api/player/externals/audio?date=…&slot=' + episodeId + '&src=' + encodeURIComponent(d.source || st.source)`
  (:18185), the v650 §3.3 fix: `&src=` names the
  DESCRIPTOR's own source, so the two items' mediaUris
  differ exactly by `&src=Sing the Hours` vs
  `&src=Divine Office`. `nativeContractItem` (:18580)
  passes `t.id` / `t.mediaUri` through unchanged, and
  `nativeContractFor` (:18607) keeps items and descriptors
  positionally parallel. The hand-off is whole: distinct
  URIs, shared id.
- In native mode the start funnel sends that contract and
  returns (`startDesc`, :5251: `if (oraNativeMode()
  && nativeSendContract(desc)) return;`) — the WebView
  element never loads on John's phone. **(d) is CLEARED:**
  the element path, when it runs at all, is
  `loadDescAudio` (:5051) setting `audioEl.src = desc.url`
  — the descriptor's own per-side minted blob (§2.1). No
  labeled-side play on the element can sound the other
  side.
- The hypothesized Media3 byte cache keyed by mediaId is
  **CLEARED by absence**: the shell builds its player as
  `ExoPlayer.Builder(this)` (OraLibraryService.kt:294)
  over `DefaultDataSource.Factory(this,
  AuthDataSourceFactory(this))` (:292); a full-source grep
  finds no `SimpleCache`, no `CacheDataSource`, no cache
  factory anywhere in the shell. Media3 does not cache
  bytes by mediaId here. The shared mediaId
  (`.setMediaId(item.id)`, OraLibraryService.kt:1070) is
  real but it is an IDENTITY collision, not a byte cache —
  its byte-level damage runs through the offline store
  (§2.3), and its identity-level echoes are §2.4.

### 2.3 THE LOSING HOP — the native offline store keys bytes by track id alone

The shell keeps a SECOND offline store the WebView never
shares — its own header says so: "The WebView store and
this store never share bytes… the car's ExoPlayer reads
files, and each pass keeps its own store complete"
(OfflineAudioStore.kt:15-18). That store's one file-name
rule is a pure function of the track id alone:

- `OfflineFiles.fileNameFor(trackId)` (OfflineAudioStore.kt:25)
  = sanitized trackId + `.mp3`; `audioFile(filesDir, date,
  trackId)` (:31) and `OfflineAudioStore.fileFor(date,
  trackId)` (:95) build `offline-audio/<date>/<trackId>.mp3`.
  No source, no mediaUri, no side enters the key. Both
  sides of a labeled slot therefore name ONE file:
  `offline-audio/<date>/ext-morning-prayer.mp3`.
- The store is filled from the day SNAPSHOT on every day
  build: `OraDayBridgePlugin.setDaySnapshot` runs
  `OfflineDownloader.ensure(context, parsed)` on every
  snapshot write (OraDayBridgePlugin.kt:~194), and
  `oraDaySnapshot` (client.ts:18216) emits BOTH labeled
  tracks (both `oraSnapshotTrack` items, §2.2).
  `OfflineDownloader.runPass` (OfflineAudioStore.kt:223)
  computes `OfflineDownloadPolicy.missingTracks` (:70)
  ONCE, keyed by `fileNameFor(track.id)` in a standing-size
  map — with no file standing, BOTH same-id tracks enter
  the missing list; `fetchOne` (:267) then fetches each in
  snapshot order, each writing the SAME target
  `store.fileFor(date, track.id)` with no standing check
  and no enclosure stamp. Last writer wins. Snapshot order
  is paint order — under 'Both', Sing the Hours first,
  Divine Office second (§2.1) — so the surviving bytes in
  `ext-morning-prayer.mp3` are the DIVINE OFFICE bytes.
  (Under a single-side setting only one track stands in
  the snapshot and the file is that side's — the defect
  needs the two-track paint, which is exactly v650's new
  field shape.)
- At play, the substitution discards the correct URI:
  `contractMediaItem` (OraLibraryService.kt:1020) for a
  day-form item computes
  `OfflineAudioStore(filesDir).fileFor(contract.day, item.id)`
  (:1023) and, when that file exists with bytes, replaces
  `uriStr` with the file URI — `item.mediaUri`, the one
  field that names the side (`&src=`), is never consulted
  again. Both contract items carry the same id, so both
  resolve to the one file. Tap either track: Divine
  Office sounds. This is the field failure, byte for byte.
- The snapshot/browse builder repeats the same
  substitution: `trackMediaItem` (OraLibraryService.kt:1565)
  resolves `fileFor(snapshot.presentedDay, track.id)`
  (:1590) through `MediaUriChoice.choose` into
  `.setUri(uri)` with `.setMediaId(track.id)` (:1597).

**The v650 asymmetry, in one line:** v650 gave the WebView
Cache Storage a per-side key, a per-side stamp, and a
per-side mint owner (§2.1); the native offline store —
the store the phone's actual engine prefers at play —
kept the pre-v650 id-only key, no stamp, and a
last-writer-wins fill. The fix in §3 carries the side
dimension across the bridge in the only field the shell
already receives per side: the mediaUri.

### 2.4 Ranked second hop (contributing, browse/car path only) — snapshot expansion resolves by id

`SnapshotMapper.expandFor` (SnapshotMapper.kt:92) resolves
a tapped snapshot track with
`snapshot.tracks.firstOrNull { it.id == mediaId }` (:99):
with duplicate ids, a browse/car tap on the Divine Office
child expands from the FIRST same-id track (Sing the
Hours). Its queue still contains both tracks in snapshot
order, and once §3 keys each `trackMediaItem`'s file by
its own mediaUri, both sound correctly in order — the
residual loss on this path is only the start INDEX (the
block starts at the first side, not the tapped side). It
cannot produce the phone-tap field failure (§2.3 does,
alone) and is ranked second for that reason; §3.3 names
its bounded fix.

Identity echoes of the shared id that are NOT byte hops
and must not be "fixed" by renaming the id: the state
channel matches `state.pendingStart.episodeId ===
st.trackId` (client.ts:18857) and syncs the current track
by `desc.episodeId === st.trackId` (:18862) positionally
through `nativeContractDescs`; the service's day-position
write-back posts `episodeId` = the item id to
`/api/player/day-position` (NativeWriteback.kt:68,
`postDayPosition`), a server store keyed by the real
episode id; the snapshot's `queueIds` carry episodeIds.
The id is the bridge contract's identity on every surface.

### 2.5 Why the fix is not web-only (rejected alternative, with evidence)

A client-only change — `oraSnapshotTrack` returning a
side-suffixed id (e.g. `ext-morning-prayer@sth`) — would
give the native store two file names, but the returned
`trackId` on the state channel would then be the suffixed
string, and every identity match in §2.4 fails verbatim:
the pending-start ack (client.ts:18857) never closes, the
current-track sync (:18862) never lands, and day-position
write-backs would post a suffixed episodeId the server
store does not key by. Repairing those means changing the
client AND the shell's state publishing together — a
bridge-contract change on both sides, strictly larger
than §3's shell-only key change, and it still ships an
APK. Rejected: the id stays the episode id everywhere;
the side enters only the shell's byte key, derived from
the mediaUri the client already sends per side.

## §3 The fix (APK change — shell-only; client and Worker unchanged)

**Head of the fix, plainly: this is an APK release.** The
shell consequence stands: a new APK version (1.0.55+) is
built from `Jctebo/ora-pro-nobis-android` with this change,
and John's install step changes — he installs the new APK;
the fixed web build adopting silently (the v647 path)
cannot heal the field failure, because the defective code
is the shell's own. The web pin does not need to move for
the fix itself.

1. **The native byte key gains the mediaUri dimension
   (§2.3).** In `OfflineFiles`, the day-file name becomes a
   pure function of (trackId, mediaUri): the sanitized
   trackId + `'~'` + a short stable discriminator of the
   mediaUri — for a pass-through URI, its `&src=` value
   sanitized (`Sing the Hours` → `sth`, `Divine Office` →
   `do`, the client's own `extSideTag650` vocabulary); for
   any other URI, a short hash of the full URI string. One
   helper, `fileNameFor(trackId, mediaUri)`, is the only
   naming rule; `OfflineAudioStore.fileFor(date, trackId,
   mediaUri)` carries it. MediaItem mediaIds, contract ids,
   snapshot ids, write-back episodeIds: all UNCHANGED
   (§2.4).
2. **Every key consumer re-points to the pair (§2.3).**
   `OfflineDownloadPolicy.missingTracks` keys its standing
   map by the pair name, so two same-id tracks with
   distinct mediaUris are two missing entries, not one;
   `OfflineDownloader.fetchOne` writes the pair-named
   target (the sequential fill now lands two files, order
   no longer matters); `stampLocalFiles` stamps the pair
   name as `localFile`; `contractMediaItem`'s day-form
   substitution and `trackMediaItem`'s `MediaUriChoice`
   read consult `fileFor(day, id, mediaUri)` with the
   item's/track's OWN mediaUri — a standing file answers
   only the side whose URI named it. The podcast form's
   substitution (`podcastFileFor(series, id)`) is untouched:
   podcast episode ids are unique per episode.
3. **The legacy id-only file is inert (§2.3).** A file
   under the old name (`<trackId>.mp3`) matches no pair
   key, so it is never chosen for either side; the first
   new-shell snapshot pass re-downloads each side under
   its pair name (the old file is orphaned bytes in a
   per-date folder the standing eviction already deletes
   whole before yesterday — no migration code). No stamp
   is added: the pair key IS the side binding the v649
   stamp gave the WebView store, since a file can only be
   written under the key its own fetch URI produced.
4. **Bounded second-hop fix (§2.4).** `trackMediaItem`
   under §3.2 already sounds each side correctly in a
   browse-expanded block queue. The start-index residue is
   answered without renaming any id: `expandFor` keeps its
   id match (the expansion is the whole block, in order),
   and no further change is made in this release — the
   car/browse tap starts the block at its first side, as
   a block tap does today. Named here so Review does not
   re-raise it as undiscovered; if John wants tap-side
   starts on the car surface, that is a separate item
   (it needs an occurrence dimension in the browse
   mediaId, a bridge-contract change).
5. **Nothing else moves.** client.ts: no change (the
   hand-off is already whole, §2.2). Worker: no change
   (the pass-through discrimination is proven). The v650
   WebView per-side store, the v645 queue discipline, the
   v610 occurrence discipline: untouched.
