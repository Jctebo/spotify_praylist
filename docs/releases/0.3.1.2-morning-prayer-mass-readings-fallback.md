# Release 0.3.1.2 - Morning Prayer Mass Readings Fallback

Date: 2026-05-02
Status: Shipped
Branch: enhancement/morning-prayer-mass-readings-fallback
Depends On: 0.3.1.1

## Scope

### Problem
- The Morning Prayer publish still fails when the daily intro cannot find a usable Mass reading, even though 0.3.1.0 was supposed to make that class of missing Gospel data recoverable.
- The current error path is too coarse: a live USCCB or `catholic_mass_readings` failure can bubble up as a fatal "no usable mass readings" error and abort the whole run.
- Why now: the remaining failure mode is not a new prayer-content problem; it is a robustness gap in the daily intro fetch path that still blocks a routine publish.

### Audience
- Primary user: the maintainer running Morning Prayer and expecting the daily publish to keep going when USCCB is flaky or returns no usable readings.
- Secondary stakeholders: listeners who should still get the episode on schedule even when today's Gospel lookup is unavailable.
- Secondary stakeholders: future maintainers who need the missing-data boundary to be obvious and narrow.

### Current Status Quo
- `jobs/publish/daily_intro.py` already has Gospel-free fallback behavior, but the fetch path can still raise when the Mass lookup itself produces no usable reading data.
- `jobs/publish/contracts.py` already supports block-level `skip_if_missing`, but that only helps once the resolver classifies the failure as skippable.
- The publish flow still treats "no usable mass readings" as a hard stop instead of converting it into the controlled fallback path that Morning Prayer already expects.

### Goal
- Keep the Morning Prayer publish running when the Mass-reading lookup returns nothing usable.
- Make the failure boundary explicit so missing Gospel data becomes controlled fallback behavior instead of a fatal pipeline error.
- Success criteria: the daily intro should either produce a Gospel-free fallback or skip only the explicitly opt-in block, while the rest of Morning Prayer continues to publish normally.

### Constraints
- Preserve fail-closed behavior for real contract mistakes, malformed config, and non-missing-data errors.
- Keep the fix narrow to Morning Prayer's dynamic daily intro path rather than broadening into a global ignore-errors mode.
- Keep the user-visible change limited to the missing Mass-reading path so unrelated publish blocks still fail loudly when they should.
- The solution has to work whether the upstream issue is a transient transport failure, an empty dependency response, or a bad live reading parse.

### Narrow Wedge
- Harden the daily intro's Mass-reading lookup so "no usable mass readings" is translated into the controlled fallback path instead of aborting the run.
- Keep the Morning Prayer daily intro on a Gospel-free path when the reading lookup is unavailable.
- If the block still cannot produce safe output, skip only that block when it is explicitly marked as skippable, not the whole prayer.

### Non-Goals
- Do not redesign the liturgical calendar lookup.
- Do not replace the `catholic_mass_readings` dependency unless the fallback path proves insufficient.
- Do not make all dynamic blocks optional by default.
- Do not change the overall Morning Prayer wording unless the fallback logic needs a shorter prompt to stay safe.

### Risks And Unknowns
- The biggest risk is confusing a genuinely malformed calendar or contract with a missing-reading condition and accidentally hiding a real bug.
- It is not yet fully clear whether the right fix is to harden the lookup path, broaden the Gospel-free fallback, or both.
- If the error classification is too broad, other hard failures could start disappearing instead of surfacing.
- If the classification is too narrow, the same "no usable mass readings" error will keep blocking the run.

### Recommended Next Step
- Run `/research-astack` to trace the exact missing-reading failure path, confirm where to classify it as recoverable, and decide whether the fix belongs in the resolver, the daily intro fetch helper, or both.

## Research
### Scope Baseline
- Morning Prayer still needs a safe answer when the daily intro cannot get usable Mass/Gospel data.
- The current checked-in code already has a Gospel-free intro mode and block-level missing-data skipping, so the remaining research question is why the live "no usable mass readings" failure still escapes the fallback path.
- The current root-cause hypothesis is no longer a stale runtime copy: the contract metadata sets `allow_missing_gospel: true`, but the resolver can overwrite it with the daily-intro block's normalized default before calling the builder.
- For this release, keep the focus on the USCCB / `catholic_mass_readings` lookup path. Romcal is only providing the celebration names and is not the source of the reported `No mass for date` warning.

### Relevant Files
- `jobs/publish/daily_intro.py` - fetches Romcal celebrations, tries the `catholic_mass_readings` library, falls back to direct USCCB HTML parsing, and can render a Gospel-free intro when `allow_missing_gospel` is enabled. The fatal `"Mass readings returned no usable Gospel data..."` error is raised here at the final fallback (`jobs/publish/daily_intro.py:323-329`).
- `jobs/publish/daily_intro.py` - also raises `DailyIntroMissingDataError` immediately when Romcal returns no celebrations or no usable celebration names, before any Gospel fallback is attempted.
- `jobs/publish/contracts.py` - resolves publish blocks, threads `daily_intro` metadata into `build_daily_intro_text(...)`, and already catches `PublishMissingDataError` for `skip_if_missing`. The important detail is that `_normalize_block(...)` also injects a daily-intro `allow_missing_gospel` field with a false default, which can overwrite the contract-level true value during the merge.
- `jobs/publish/errors.py` - defines the shared missing-data exception hierarchy used to distinguish skippable publish failures from hard failures.
- `config/publish/contracts/morning-prayer.json` - current Morning Prayer contract; the `daily_intro` metadata already opts into `allow_missing_gospel: true`.
- `tests/test_publish_daily_intro.py` - covers the library path, the HTML fallback, the Gospel-free prompt path, and missing-data failures.
- `tests/test_publish_contracts.py` - covers contract loading, `skip_if_missing`, and the Morning Prayer metadata wiring.
- `tests/test_publish_text_pipeline.py` and `tests/test_publish_audio_fragments.py` - show that empty sections/fragments already disappear cleanly downstream once a resolver returns empty text.
- `jobs/publish/run_audio_pipeline.py` - the runner that surfaces resolver failures as a pipeline abort when the daily intro does not recover cleanly.
- GitHub Actions run `Publish Prayer Audio #53` (`run_id=25260002101`, `job_id=74065621902`) on `main` commit `4382d31` - this is the concrete failure evidence from the public CI log, including the exact `"Mass readings returned no usable Gospel data for 2026-05-03..."` line.

### Current System Map
- `resolve_block_content(...)` in `jobs/publish/contracts.py` is the only production call site for `build_daily_intro_text(...)`.
- `resolve_block_content(...)` merges contract metadata with block overrides, but the merge order matters: `intro_config` starts from contract metadata and then `intro_config.update(...)` applies block fields, so a normalized block field can win over contract-level defaults.
- `_normalize_block(...)` in `jobs/publish/contracts.py` always normalizes `daily-intro.allow_missing_gospel`, which means a missing block-level value becomes `false` and can mask the `true` value set in the contract metadata.
- `fetch_daily_gospel_context(...)` in `jobs/publish/daily_intro.py` tries three layers in order: Romcal celebrations, a `catholic_mass_readings` lookup with retry, and direct USCCB HTML parsing.
- The Romcal celebration lookup is a hard prerequisite for the intro text. If it returns nothing usable, `fetch_daily_gospel_context(...)` raises `DailyIntroMissingDataError` before `allow_missing_gospel` can help.
- If both Gospel lookup paths fail and `allow_missing_gospel` is false, `fetch_daily_gospel_context(...)` raises `DailyIntroMissingDataError` with the "no usable Gospel data" message; if `allow_missing_gospel` is true, it returns an empty Gospel context instead. In other words, the code path is correct, but the runtime value can still be wrong if the merge overwrites the contract metadata.
- `build_daily_intro_text(...)` chooses a three-sentence prompt when Gospel text exists and a two-sentence prompt when Gospel text is absent, then validates the model output count accordingly.
- `build_text_jobs(...)` and `build_audio_jobs(...)` already prune empty strings, so a resolver that returns `""` or skips a block can disappear cleanly from both text and audio output.
- The checked-in Morning Prayer config already has `allow_missing_gospel: true`, which proves the source of truth is set correctly in the contract file.
- The GitHub Actions log for `Publish Prayer Audio #53` shows the runner checked out `main` at `4382d31`, restored the fragment cache and the audio archive cache, then failed in `Publish audio files and RSS feed` after printing two `No mass for date:` lines for `2026-05-02` and `2026-05-03` and the final `ERROR: Mass readings returned no usable Gospel data for 2026-05-03...` line.

### Reuse Opportunities
- Reuse the existing `PublishMissingDataError` hierarchy instead of inventing a new error channel for missing readings.
- Reuse the existing USCCB HTML fallback and the already-tested Gospel-free prompt path instead of replacing the dependency outright.
- Reuse the contract metadata merge in `resolve_block_content(...)` so the fallback can stay contract-driven.
- Reuse the downstream empty-content pruning in text and audio pipelines so a skipped intro does not need special handling later.
- Reuse the current test harnesses to prove the missing-reading failure, the Gospel-free fallback, and the resolver skip path end to end.

### External References
- `catholic_mass_readings` is a live HTTP client over `bible.usccb.org`, not a cached source, so transport and challenge-page failures are expected possibilities.
- USCCB daily readings pages can return challenge pages or incomplete mass objects even when the liturgical day should have a Gospel.
- `curl_cffi` is the transport layer behind the dependency and supports browser impersonation, headers, and retries.
- OpenAI still generates the daily intro text, so the Gospel-free path must not mask model-generation failures.
- Romcal remains the source of liturgical day metadata and celebration names.

### Constraints
- Keep fail-closed behavior for real contract, file, or configuration errors.
- Keep the change narrow to Morning Prayer’s daily intro path rather than broadening into a global ignore-errors mode.
- Preserve the existing option for block-level `skip_if_missing`, but do not make that the default for all dynamic blocks.
- Keep the two-sentence Gospel-free prompt valid if the missing-reading path is the intended behavior.
- Avoid changing the rest of Morning Prayer wording or the downstream audio/text assembly rules unless the fallback absolutely needs it.

### Risks
- The main risk is classifying a genuine contract or liturgical-calendar bug as "missing data" and hiding it behind a fallback.
- If the live USCCB edge keeps serving challenge pages, retries may reduce but not eliminate the failure rate.
- If the contract metadata merge keeps allowing normalized block defaults to overwrite the contract-level `allow_missing_gospel: true`, the same fatal message will keep appearing even though the repo source looks ready.
- If the two-sentence validation is wrong or the prompt drifts, the fallback can still fail even after the Gospel lookup is recovered.
- The exact loose point is the final `DailyIntroMissingDataError` raise in [jobs/publish/daily_intro.py](/workspaces/spotify_praylist/jobs/publish/daily_intro.py#L323-L329); there is no second production call site, so the bug is most likely a stale runtime/config boundary rather than a hidden alternate path.
- The public GitHub Actions log does not show any explicit trace proving `allow_missing_gospel` was set on the resolved block, so a small resolver log line would still help confirm the merged runtime value on future runs.

### Assumptions To Validate
- The reported "no usable mass readings" error came from the current checked-in code path, not a stale deployed branch or older runtime copy.
- The desired user experience is to publish Morning Prayer without the Gospel sentence when readings are unavailable, not to skip the entire opening block.
- The repository’s `allow_missing_gospel: true` contract metadata should win unless the block explicitly overrides it, rather than being silently replaced by the normalized block default.
- `DailyIntroMissingDataError` is the right abstraction for the remaining failure shape, or whether the resolver should treat one more subclass as skippable.
- Missing mass-object, missing Gospel section, and USCCB challenge-page failures should all be considered the same user-visible missing-reading condition.
- The failing runtime used the checked-in code on `main`, but the effective `allow_missing_gospel` value was likely clobbered during block normalization.
- A short resolver-level log of the merged daily-intro config would make this class of bug much easier to prove in CI.

### Unknowns
- Whether the current tests already exercise the exact "no usable mass readings" shape end to end, or whether a fresh regression test is needed at the pipeline level.
- Whether a runtime log or explicit flag trace is needed so future failures can show the merged `allow_missing_gospel` value before the error surfaces.

### Recommended Direction
- Fix the merge order so contract-level `allow_missing_gospel: true` survives normalization unless a block explicitly overrides it, then add a small runtime log and regression coverage so CI can prove the effective merged value on the USCCB mass-readings path.

## Plan
### Summary
- Fix the Morning Prayer daily intro so `allow_missing_gospel: true` from contract metadata actually survives into runtime unless a block explicitly overrides it.
- Keep the existing USCCB / `catholic_mass_readings` fallback path; the bug is in how the resolver merges config, not in the Gospel-free prompt itself.
- Add a small runtime trace of the resolved daily-intro settings so the next CI run proves what value was actually used.

### What Already Exists
- `jobs/publish/daily_intro.py` already degrades to a Gospel-free prompt when `allow_missing_gospel` is true.
- `jobs/publish/contracts.py` already centralizes block resolution and already knows how to skip `PublishMissingDataError` blocks.
- `config/publish/contracts/morning-prayer.json` already sets `metadata.daily_intro.allow_missing_gospel` to `true`.
- `tests/test_publish_daily_intro.py` already covers the Gospel-free fallback path.
- `tests/test_publish_contracts.py` already exercises contract loading and Morning Prayer metadata wiring.

### Architecture
- The resolver should treat contract metadata as the default daily-intro config, then apply only explicit block overrides on top of it.
- `allow_missing_gospel` should not be synthesized as a false default during block normalization; if the block omits it, the contract metadata value should win.
- The runtime trace should log the merged daily-intro settings right before `build_daily_intro_text(...)` is called.

ASCII flow:

```text
morning-prayer contract metadata
        |
        v
resolve_block_content(...)
        |
        +--> merge metadata.daily_intro
        +--> apply explicit block overrides only
        |
        v
build_daily_intro_text(...)
        |
        +--> catholic_mass_readings / USCCB HTML
        +--> Gospel-free fallback when allowed
```

  - Keep the existing Gospel-free fallback test as the behavior-level guard for the USCCB failure path.
