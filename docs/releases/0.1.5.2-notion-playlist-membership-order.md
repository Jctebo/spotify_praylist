# Release 0.1.5.2 - notion-playlist-membership-order

- Status: Shipped
- Created Date: 2026-04-25
- Last Updated: 2026-04-25
- Depends On: 0.1.5.1
- Roadmap: `docs/roadmaps/stabilization.md`
- Notes: Scope for moving Spotify playlist membership and ordering back under the Notion `Opus Dei` database while keeping repo-owned Spotify contract files as the canonical contract catalog.

## Scope

### Problem
- Spotify playlist membership is currently split across repo-owned playlist JSON files such as `config/spotify/playlists/midday.json`.
- The maintainer wants the Notion `Opus Dei` database column currently labeled `Output Folder` to decide which Spotify contracts belong to which playlists.
- The maintainer also wants the Notion `Enabled` checkbox to be the explicit inclusion gate: only checked rows should be eligible for playlist writes.
- Spotify contract files currently use the field `name`, but the intended meaning is really "the Notion row title this contract should join against."
- The system also needs a trustworthy answer for ordering: if playlist item order is not currently coming from Notion, this enhancement must restore Notion-owned order.
- The pain is duplicated control. Right now playlist grouping and likely ordering can drift between committed JSON and the live Notion list.

### Audience
- Primary user: the maintainer editing the `Opus Dei` Notion list as the day-to-day control surface for playlist grouping and sequence.
- Secondary stakeholders: anyone relying on the generated Morning, Midday, Night, and Sunday Spotify playlists to reflect the current Notion curation.
- Secondary stakeholders: future maintainers who need one obvious source of truth for playlist grouping, title matching, and ordering.

### Current Status Quo
- The active Spotify refresh path loads contracts from `config/spotify/contracts/*.json` and playlist membership from `config/spotify/playlists/*.json`.
- Each playlist definition owns an ordered `contracts` array, so repo JSON is currently the visible source of playlist membership and order.
- The contract loader in `jobs/playlist/spotify_contracts.py` treats each contract file's `name` as a required unique identifier.
- The README and shipped release notes for `0.1.3.1` explicitly say the active Spotify path removed required Notion `Output Folder` grouping from the refresh runtime.
- `jobs/playlist/refresh_playlist.py` still contains older Notion-oriented helpers, including `Output Folder` and `Order` handling, but those are not the active contract-first playlist assembly path and parts of that code no longer match the active contract model.

### Goal
- Make the Notion `Opus Dei` `Output Folder` property the active source of truth for which contracts participate in which Spotify playlists.
- Make the Notion `Enabled` checkbox a required checked gate for playlist inclusion; unchecked or missing `Enabled` rows must not enter playlists.
- Rename the Spotify contract field `name` to `notion_name` so the contract explicitly declares which Notion row title it should join against.
- Ensure the active playlist refresh path sources playlist ordering from Notion `Order` rather than from repo playlist JSON ordering.
- Keep repo-owned contract files as the authoritative catalog of contract keys and resolver metadata.
- Allow repo-owned contract files to exist without a matching enabled Notion row; those contracts remain available in the catalog but are not written to any playlist.
- Eliminate the need to hand-edit playlist membership arrays in files like `config/spotify/playlists/midday.json` whenever the Notion grouping changes.
- Remove the stale legacy Spotify/Notion queue assembly code and skipped legacy tests once the new Notion-driven active path exists, so the repo has one playlist-construction model instead of two.

### Constraints
- The active runtime already shipped a contract-first model, so this change must avoid accidentally reviving unrelated legacy behavior.
- Notion title matching is inherently brittle if row titles and contract-owned names drift apart.
- Existing playlist ids still live in `config/spotify/playlists/*.json`, so the enhancement likely needs to preserve those thin identity files or replace them intentionally.
- The join needs to behave predictably when a contract has no matching enabled Notion row, a row is unchecked, multiple enabled rows share one title, a row has a blank `Output Folder`, an unknown `Output Folder`, or a checked placed row is missing `Order`.
- Current tests assume repo-owned playlist membership arrays, so the implementation will need a coordinated test rewrite rather than a narrow one-line change.

### Narrow Wedge
- Keep `config/spotify/contracts/*.json` as the source for contract keys, resolver fields, weekday gates, and fixed Spotify URIs.
- Change the contract shape so `name` becomes `notion_name`, with that field used solely to join a contract to a checked `Opus Dei` row when that row exists.
- Use only Notion rows whose `Enabled` checkbox is explicitly checked and whose `Output Folder` is populated as active playlist membership candidates.
- Treat unmatched contracts, unchecked/missing-`Enabled` rows, and rows with blank/missing `Output Folder` as inactive catalog/list items, not runtime errors.
- Use each checked matched Notion row's `Output Folder` to determine playlist membership for the active Spotify playlists.
- Use each checked matched Notion row's `Order` to determine the queue sequence within each playlist.
- Remove the inactive legacy queue-builder functions and their skipped test coverage as part of the same cutover, rather than leaving dead path-selection code behind.
- Leave unrelated Notion helpers, page-audio flows, and devotional-image behavior out of scope.

### Non-Goals
- Rewriting the entire Spotify refresh pipeline around fully live Notion-defined contracts.
- Removing repo-owned contract files or moving resolver logic into Notion.
- Redesigning the Notion schema beyond using the existing `Output Folder`, `Order`, and row title fields needed for the join.
- Changing how playlist ids are stored unless research proves the current thin playlist-definition files can no longer serve that purpose.
- Broad cleanup of all historical legacy Notion code outside the active Spotify playlist path.
- Removing legacy Notion-to-Spotify URI autosync mapping helpers unless they are proven to block or conflict with this enhancement.

### Risks And Unknowns
- The active path is confirmed to be JSON-owned for playlist order today, so the implementation must replace a live code path rather than merely turning on an existing Notion hook.
- `Output Folder` values may not map one-to-one to the active playlist keys and names (`morning`, `midday`, `night`, `sunday`) without normalization rules, even though live samples already show `Morning` and `Midday`.
- Renaming `name` to `notion_name` touches contract validation, duplicate detection, README/docs, and all related tests.
- If a Notion row title changes without the matching contract update, the contract intentionally drops out of the playlist because only checked matched rows are active; logs/tests should make this catalog-vs-active distinction obvious.
- Multiple enabled Notion rows with the same title remain ambiguous and should fail clearly because one contract would have two active membership rows.
- Removing the stale legacy queue-builder path in the same enhancement increases change surface, but leaving it behind would preserve a second contradictory model in the repo.

### Recommended Next Step
- Run `/research-astack` to inspect the live `Opus Dei` schema and representative rows, confirm how current code treats `Enabled`, identify the exact stale legacy queue-builder symbols to remove, and recommend the thinnest surviving role for `config/spotify/playlists/*.json` after the Notion-driven cutover.

### Current System Map
- Active entrypoint:
  - `jobs/playlist/refresh_playlist.py:main()` loads all queue contracts with `load_spotify_queue_contracts()`.
  - It then loads playlist definitions with `load_spotify_playlist_definitions()`.
  - For each selected playlist definition, it calls `build_queue_for_playlist_definition()`.
  - That function iterates `playlist_definition.contracts` in file order and appends one resolved URI per eligible contract.
- Current ownership boundaries:
  - `config/spotify/contracts/*.json` own resolver metadata and weekday gating.
  - `config/spotify/playlists/*.json` own playlist ids and the ordered contract membership.
  - Notion is only used for optional post-write helpers such as URI autosync and prayer-intention distribution.
- Order source, confirmed:
  - The active playlist sequence is JSON-owned today.
  - `build_queue_for_playlist_definition()` preserves the order of `playlist_definition.contracts`; it does not read Notion `Order`.
- Legacy Notion path, not active:
  - `build_queue_for_playlist_from_notion()` still exists and sorts rows by `jobs/prayer_order_contract.py`.
  - The active `main()` path never calls it.
  - The corresponding tests in `tests/test_refresh_job.py` are explicitly skipped as legacy.
- Existing `Enabled` handling, confirmed from code:
  - `page_property_checkbox()` in `jobs/playlist/refresh_playlist.py` returns `True`, `False`, or `None` when the property is missing or not a checkbox.
  - Legacy playlist helpers such as `load_notion_playlists()` and `build_queue_for_playlist_from_notion()` currently skip only `Enabled is False`, so a missing `Enabled` property defaults to included in those paths.
  - `distribute_prayer_intentions()` already uses the stricter pattern requested here: it includes Opus Dei targets only when `Enabled is True`.
  - `jobs/notion/generate_page_audio.py:list_audio_candidate_pages()` also requires a checked enabled property for auto-audio candidates by calling `page_property_checkbox(..., default=False)`.
  - Therefore the active replacement should use the stricter checked-only pattern, not the older legacy playlist helper behavior.
- Legacy helper quality:
  - Some helper code is stale against the current contract model.
  - Example: `spotify_contracts_by_output_folder()` expects `contract.output_folder`, but `SpotifyQueueContract` in `jobs/playlist/spotify_contracts.py` no longer has that field.
  - This means the old Notion queue-builder code is a reference, not a safe drop-in reuse path.
- Live Notion schema, confirmed:
  - The active `Opus Dei` database contains `Name` (title), `Order` (number), `Output Folder` (text), `Enabled` (checkbox), `Completed` (checkbox), and `Intention` (text).
  - The primary table views are sorted ascending by `Order`, which matches the intended playlist sequencing model.
- Live Notion row examples, confirmed:
  - `Marian Antiphon  (Morning)` is enabled with `Order = 1.06` and `Output Folder = Morning`.
  - `Saint of the Day` is enabled with `Order = 2.04` and `Output Folder = Midday`.
  - `Auxillium Christianorum` is enabled with `Order = 2.05` and `Output Folder = Midday`.
  - These rows mirror the repo’s current title quirks, including the double space in `Marian Antiphon  (Morning)` and the `Auxillium` spelling variant.
- Playlist identity boundary:
  - `config/spotify/playlists/*.json` still cleanly store `key`, display `name`, and `playlist_id`.
  - Only the ordered `contracts` arrays conflict with the desired Notion-owned grouping/order model.

### Constraints
- `README.md` currently documents the Spotify refresh as contract-first and not dependent on Notion for base playlist construction, so docs must change with the runtime.
- `jobs/playlist/spotify_contracts.py` currently requires contract `name` and enforces duplicate-name validation on that field.
- `load_spotify_playlist_definitions()` currently requires every playlist definition to contain a non-empty `contracts` array, so the loader contract must change if playlist files are kept for identity only.
- The old Notion queue-builder path is not production-ready as-is because parts of it still assume the older contract shape.
- The implementation must not require every contract to have a matching enabled Notion row; unmatched contracts are inactive catalog entries.
- The implementation must include only checked `Enabled` rows with populated `Output Folder`; unchecked rows, missing/non-checkbox `Enabled` values, and blank/missing `Output Folder` values are inactive.
- The implementation must fail clearly when more than one checked row matches the same contract title, or when a checked matched row has an unknown `Output Folder` or a populated playlist folder but missing `Order`.
- Contract names in the repo already contain data-quality inconsistencies, including spelling differences and double spaces, so a strict title join will expose mismatches quickly.
- If the stale legacy queue-builder path is kept after the new cutover, the repo will still advertise two contradictory ways to assemble playlists.

### Risks
- Highest risk: reviving the old Notion queue-builder logic wholesale would reintroduce stale assumptions such as `contract.output_folder` and could silently mix legacy behavior back into the active path.
- Renaming `name` to `notion_name` is a broad schema change touching contract JSON files, loader validation, status labels, docs, and tests.
- If playlist definition files keep requiring `contracts`, the runtime could accidentally remain split-brain even after a partial Notion cutover.
- The repo contains evidence of historical label drift between contract names, legacy Notion mappings, and probable live Notion row titles; exact title-join failures are likely unless normalized carefully or failed closed.
- If an intended playlist row is accidentally unchecked, the runtime will omit it by design; logging should report ignored/unmatched catalog counts so this is discoverable without treating it as an error.
- Because the active tests currently assert JSON-owned ordering, a partial implementation without coordinated test updates will give misleading coverage.
- Removing the stale legacy path in the same change means test and docs cleanup must be coordinated with runtime changes, not deferred.

### Assumptions To Validate
- Assumption: the live `Opus Dei` `Output Folder` values map cleanly onto the active playlist keys/names (`Morning`, `Midday`, `Night`, `Sunday`) without needing a separate translation layer.
- Assumption: every active Spotify playlist item should be represented by exactly one checked Notion row title that matches a repo contract's `notion_name`.
- Assumption: contracts without checked matching Notion rows are intentional inactive catalog entries and should not fail the run.
- Assumption: the correct long-term role for `config/spotify/playlists/*.json` is "playlist identity only" rather than full removal.
- Assumption: Notion `Order` is populated for every checked row that should participate in Spotify playlists.
- Assumption: the live Notion row titles match the intended contract join strings closely enough that `notion_name` can be the primary join key.

### Unknowns

- Whether multiple Spotify contracts should ever be allowed to point at the same Notion title, or whether uniqueness must be enforced at load time.
- Whether `Output Folder` should support one playlist per row only or multiple playlist assignments via CSV / multi-select semantics.
- Whether Sunday-only items should continue to rely solely on contract-level `weekdays` gating or also respect any live Notion toggles.
- Whether any currently committed contract names should be corrected while renaming to `notion_name`, or whether the exact existing live spellings should be preserved first and normalized later.

### Recommended Direction
- Keep the active refresh entrypoint and resolver system, but replace the membership/order assembly step inside the active path rather than reviving the old legacy Notion path.
- Keep `config/spotify/contracts/*.json` as the source of contract keys and resolver metadata, but rename `name` to `notion_name` and validate uniqueness on that new field.
- Preserve `config/spotify/playlists/*.json` for playlist identity (`key`, `name`, `playlist_id`) and remove or deprecate their ownership of ordered `contracts`.
- Add a new active assembly step that:
  - loads checked `Enabled` Notion rows from `Opus Dei`
  - joins checked rows to contracts by `notion_name`
  - ignores contracts with no checked matching Notion row or with a row whose `Output Folder` is blank
  - groups checked matched contracts by populated Notion `Output Folder`
  - sorts by Notion `Order` using `jobs/prayer_order_contract.py`
  - then resolves URIs with the existing contract resolver logic and weekday gating
- Treat the existing legacy Notion queue-builder code as reference material only while implementing the replacement, then remove the stale queue-builder functions and skipped legacy tests in the same enhancement so only one playlist-construction model remains in the repo.

## Plan

### Summary
- Build a Notion-driven Spotify playlist assembly step for the active refresh path: contracts still live in `config/spotify/contracts/*.json`, but membership and sequence come from matching `Opus Dei` Notion rows via `notion_name`, `Output Folder`, and `Order`.
- Gate active playlist membership on two required row facts: `Enabled` must be checked and `Output Folder` must be populated. Unchecked rows, missing-`Enabled` rows, blank/missing-`Output Folder` rows, and contracts with no checked matching row are omitted from playlists.
- Keep `config/spotify/playlists/*.json` as thin playlist identity files (`key`, `name`, `playlist_id`) and remove the committed ordered `contracts` arrays from the active contract.
- Remove the stale legacy Notion queue-builder path once the replacement active path exists, so there is one playlist-construction model.
- This is the chosen approach because it restores the maintainer's Notion editing surface without moving resolver metadata or playlist ids out of the repo.

### What Already Exists
- `jobs/playlist/spotify_contracts.py` already loads and validates queue contracts and playlist definitions.
- `jobs/playlist/refresh_playlist.py:main()` already has the active Spotify write loop, weekday/runtime-date handling, URI resolution, optional Notion URI autosync, and prayer-intention distribution.
- `jobs/playlist/refresh_playlist.py` already has reusable Notion helpers: `notion_get_all_pages`, `page_title`, `page_property_text`, `page_property_values`, `page_property_number`, `page_property_checkbox`, and `page_property_normalized_values`.
- `jobs/prayer_order_contract.py` already parses and sorts Notion-style `Order` values.
- Existing resolver functions and `resolve_contract_uri()` already handle fixed URIs, resolver fallback, weekday gates, and Marian Antiphon seasonal URI selection.

### Architecture
- Rename `SpotifyQueueContract.name` to `SpotifyQueueContract.notion_name`; validate it as the required Notion title join string and keep duplicate detection on the normalized `notion_name`.
- Keep `SpotifyPlaylistDefinition.name` for playlist display/filter matching, but make its `contracts` field optional/empty and stop validating playlist-to-contract references.
- Add a small Notion membership layer in `jobs/playlist/refresh_playlist.py` that loads all `Opus Dei` rows once per run, keeps only rows where `Enabled is True`, indexes those checked rows by Notion title, joins them to available contracts, and emits ordered contracts per playlist definition.
- Treat contracts without a checked matching row as inactive catalog entries, not errors.
- Fail closed before any Spotify write if checked Notion rows create ambiguous title matches for a contract, if a checked placed row has an unknown `Output Folder`, or if a checked placed row has missing/unparseable `Order`; blank/missing `Output Folder` is treated as inactive and omitted.
- Continue applying contract-level `weekdays` after Notion membership/order is known, so Sunday-only contracts remain gated by contract metadata.

```text
config/spotify/contracts/*.json
  key + notion_name + resolver metadata
            |
            v
     join to checked Notion rows on notion_name
            |
            v
Opus Dei Notion rows: Name + Enabled=true + nonblank Output Folder + Order
            |
            v
group by Output Folder -> playlist key/name
sort by Order -> resolve existing Spotify URI logic -> recreate playlist
```

### UX And States
- There is no app UI scope.
- Maintainer journey:
  - Add an item to a playlist by making sure the Notion row title matches a contract's `notion_name`, checking `Enabled`, setting `Output Folder`, and setting `Order`.
  - Remove an item from playlists by unchecking `Enabled`, clearing `Output Folder`, or removing the matching Notion row, without deleting the repo contract.
  - Edit playlist membership by setting `Output Folder` on the matching `Opus Dei` row.
  - Edit playlist order by changing `Order` in Notion.
  - Edit resolver behavior by changing the matching repo contract's resolver fields.
- Success state:
  - The refresh logs `SUMMARY playlist=<name> ... tracks_written=<n>` as today, with `source=notion_membership`.
- Empty state:
  - In a multi-playlist run, a playlist with only weekday-gated contracts for another day is skipped with an explicit `no_eligible_contracts` message.
  - A playlist with no checked matched Notion rows is skipped in all-playlist runs, and fails clearly when selected directly.
  - Any selected playlist with checked matched rows but no resolved URIs remains a hard failure.
- Error states:
  - Missing `NOTION_TOKEN` or inaccessible `Opus Dei` database fails before Spotify writes.
  - Contracts with no exact checked Notion title match are omitted, not failed.
  - Multiple checked rows matching one `notion_name` fail before Spotify writes.
  - Row with blank/missing `Output Folder` is omitted as inactive, the same way an unchecked row is omitted.
  - Checked placed row with unknown `Output Folder` or missing `Order` fails before Spotify writes.

### Failure Modes
- Missing Notion credentials/database access: detected before queue assembly; user sees a clear runtime error and no Spotify playlists are rewritten.
- Contract title drift: an unmatched contract is omitted by design; user sees inactive/unmatched counts in logs rather than a failed run.
- Duplicate active title drift: detected when more than one checked Notion row matches the same `notion_name`; user sees the title and duplicate row context in the error.
- Unchecked or missing `Enabled`: row is ignored by design and does not enter any playlist.
- Blank Notion grouping: blank/missing `Output Folder` is treated as inactive and omitted, with an ignored-row count in logs.
- Bad Notion grouping: unknown `Output Folder` fails before Spotify writes; user sees the Notion row title and invalid folder value.
- Bad Notion ordering: missing/unparseable `Order` fails before Spotify writes; user sees the Notion row title.
- Resolver failure after successful membership assembly: existing resolver status behavior marks unresolved contracts; selected playlist fails if no queue can be written.
- Weekday-gated playlists: multi-playlist runs skip playlists where every matched contract is gated off for the day; single selected runs fail clearly.
