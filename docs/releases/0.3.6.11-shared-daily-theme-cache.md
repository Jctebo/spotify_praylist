Date: 2026-06-16

## Scope

### Problem
- The `0.3.6.9` daily theme work successfully added theme metadata and prayer intros, and the `0.3.6.10` hotfix restored the remote publish job.
- The successful remote `Publish Prayer Audio` run for **Tuesday, June 16, 2026** still exposed a product bug: the day did not receive one truly shared theme across all prayers.
- Published sidecars showed mixed theme results for the same date:
  - Morning Prayer: `Trust`, sourced from calendar day and Ordinary Time.
  - Daily Rosary: `Trust`, sourced from calendar day and Ordinary Time.
  - Daily Reflection: `Humility And Trust`, sourced from calendar day, Ordinary Time, and Gospel `Matthew 5:43-48`.
  - Auxilium Christianorum: `Humility And Trust`, sourced from calendar day, Ordinary Time, and Gospel `Matthew 5:43-48`.
  - Angelus: `Trust`, sourced from calendar day and Ordinary Time.
- No sidecar reported an explicit `fallbackReason`, so this was not the conservative limited-data fallback. It was inconsistent context resolution across prayer entries.
- This breaks the original product promise: one inclusive daily focus should be lightly or deeply reinforced everywhere, not rebuilt independently per contract and allowed to drift.

### Audience
- Primary maintainer: needs to trust the generated prayer day is spiritually coherent before publishing or reviewing output.
- Daily listeners: should hear one recognizable daily focus across Morning Prayer, Rosary, novenas, Daily Reflection, Auxilium Christianorum, and Marian Antiphons.
- Future maintainers: need a clear system boundary where the daily theme is resolved once per date and reused across daily publish surfaces.

### Current Status Quo
- `jobs/publish/contracts.py` builds `runtime_context` independently per contract entry through `_entry_runtime_context()`.
- `_entry_runtime_context()` calls `_build_daily_theme_runtime_context(contract, entry, target_date)` for every entry.
- `_daily_theme_config()` merges contract metadata and block options, including `allow_missing_gospel`.
- Some contracts allow missing Gospel data, and some builder paths can end up with calendar/season-only context while others obtain Gospel context.
- `build_audio_jobs()` and `build_text_jobs()` have one loop over contracts/entries, but they do not provide a per-date shared theme object to each entry.
- The render context and sidecars already expose enough metadata to detect the drift after publication, but there is no pre-publish assertion that all entries for one date share the same `daily_theme_version`, title, explanation, sources, and fallback status.

### Goal
- Resolve one canonical publish daily theme per target date and reuse that same theme payload across all publish-contract daily entries for that date.
- The canonical theme must remain inclusive of:
  - calendar day or celebration,
  - Gospel reading when available,
  - liturgical season,
  - relevant saint/feast/memorial context when present.
- Morning Prayer, Rosary, Daily Reflection, Auxilium Christianorum, and the active Marian Antiphon should all carry the same `daily_theme_*` fields and the same `daily_liturgical_context` payload for a given date.
- If Gospel data is available to any publish surface for that date, all publish surfaces should use the Gospel-inclusive canonical theme rather than silently falling back to calendar/season-only variants.
- If Gospel data is genuinely unavailable for the date, every publish surface should share the same fallback status and explanation.

### Non-Goals
- Do not redesign the theme wording model beyond what is required for consistency.
- Do not change fixed prayer bodies.
- Do not change Rosary mystery scheduling.
- Do not change Spotify lookup terms, episode IDs, RSS ownership, or R2 publishing behavior.
- Do not add a new external readings/calendar dependency.
- Do not solve novena Gospel integration in this release; novenas currently use their own deterministic light theme bridge and are outside the publish-contract drift observed in the June 16 sidecars.
- Do not regenerate checked-in audio artifacts locally as part of the scope stage.

### Narrow Wedge
- Introduce a per-date shared daily theme context in the publish-contract pipeline.
- `build_audio_jobs()` and `build_text_jobs()` should compute or pass one canonical theme payload per target date and inject it into every entry runtime context.
- Entry-specific contract options may still influence non-theme behavior, but they should not cause per-prayer daily theme drift for the same date.
- Add regression coverage that stubs one contract path to miss Gospel and another to receive Gospel, then proves all built audio jobs share the same Gospel-inclusive theme context.
- Add a guard or test assertion that all publish jobs for one date have identical `daily_theme_title`, `daily_theme_explanation`, `daily_theme_sources`, and `daily_liturgical_context.fallbackReason`.

### Success Criteria
- For a single target date, all publish-contract audio jobs expose the same:
  - `render_context.daily_theme_title`,
  - `render_context.daily_theme_explanation`,
  - `render_context.daily_theme_sources`,
  - `render_context.daily_liturgical_context.sharedThemeTitle`,
  - `render_context.daily_liturgical_context.gospelCitation`,
  - `render_context.daily_liturgical_context.fallbackReason`.
- A regression test reproduces the June 16 class of drift and fails on the current implementation.
- The test passes after the shared per-date theme context is introduced.
- `python -m jobs.publish.run_audio_pipeline` continues to run locally.
- A remote `Publish Prayer Audio` workflow run after ship should produce one shared theme across the June 17 or next-target publish sidecars.

### Risks And Unknowns
- Some block metadata currently carries `allow_missing_gospel=true`; research must decide whether the canonical theme resolver should force `allow_missing_gospel=false` first and fall back only after a real failure, or use a two-pass strategy.
- Contract-specific calendar/locale values are currently possible; the first wedge can assume existing publish contracts use `general_roman` and `en`, but research should verify before implementation.
- Caching must not become stale across different target dates, calendars, locales, or publish modes.
- Existing tests may patch helper functions at module scope; the implementation must remain easy to stub without live Romcal, USCCB, OpenAI, ElevenLabs, R2, or Notion.
- Daily Intro and Rosary builders may still perform their own Gospel/context fetches for prose generation. The scope is shared theme consistency, not eliminating every duplicate lookup unless needed to prevent drift.

### Open Questions
- Should the canonical publish theme be keyed strictly by date, or by `(date, calendar, locale)` to preserve future multi-calendar support?
- Should a publish run fail closed if one entry diverges from the canonical daily theme, or should tests enforce this while production logs a warning?
- Should novena pipeline eventually consume the same canonical publish theme, or remain deterministic and novena-local as scoped in `0.3.6.9`?

### Recommended Next Step
- Run `/research-astack` or `/plan-astack` next.
- Research should map the exact call graph from `run_audio_pipeline.run_publish_audio_pipeline()` through `build_audio_jobs()`, `_entry_runtime_context()`, `daily_intro`, Rosary builders, and Daily Reflection builders to decide the smallest safe injection point for a per-date canonical theme.

## Research

### Production Symptom
- Remote workflow run `27581843347` succeeded after the `0.3.6.10` hotfix, so the publish pipeline is operational.
- Published June 16 sidecars confirmed the consistency bug:
  - `morning-prayer-elevenlabs-2026-06-16`: `sharedThemeTitle=Trust`, `source=season`, no `gospelCitation`, no `fallbackReason`.
  - `daily-rosary-2026-06-16`: `sharedThemeTitle=Trust`, `source=season`, no `gospelCitation`, no `fallbackReason`.
  - `daily-reflection-2026-06-16`: `sharedThemeTitle=Humility And Trust`, `source=gospel`, `gospelCitation=Matthew 5:43-48`, no `fallbackReason`.
  - `auxilium-christianorum-2026-06-16`: `sharedThemeTitle=Humility And Trust`, `source=gospel`, `gospelCitation=Matthew 5:43-48`, no `fallbackReason`.
  - `marian-antiphon-angelus-2026-06-16`: `sharedThemeTitle=Trust`, `source=season`, no `gospelCitation`, no `fallbackReason`.
- The absence of `fallbackReason` means the drift is not an explicit limited-data fallback. Different entries independently resolved different effective daily contexts.

### Relevant Files
- `jobs/publish/run_audio_pipeline.py`
  - `run_audio_pipeline()` loads contracts and calls `build_audio_jobs(contracts, target_date=date_value)` once per target date.
  - This is the remote workflow path that produced the inconsistent sidecars.
- `jobs/publish/audio.py`
  - Exposes `build_audio_jobs()` as a thin wrapper around `jobs.publish.contracts.build_audio_jobs()`.
  - Writes sidecar `render_context` through `render_audio_job()`.
- `jobs/publish/contracts.py`
  - Owns publish-contract loading, render metadata, text job building, audio job building, block rendering, fragment expansion, and shared theme flattening.
  - `_daily_theme_config()` currently reads `calendar`, `locale`, and `allow_missing_gospel` from contract metadata and entry blocks.
  - `_build_daily_theme_runtime_context()` currently calls `build_daily_liturgical_context()` per entry.
  - `_entry_runtime_context()` currently builds daily theme runtime fields independently per entry, then passes that payload into Rosary and Daily Reflection paths.
  - `build_text_jobs()` and `build_audio_jobs()` both call `_entry_runtime_context()` inside their per-entry loops.
- `jobs/publish/daily_liturgical_context.py`
  - Owns the inclusive `DailyLiturgicalContext` and shared theme fields.
  - This should remain the canonical builder for one theme payload, but it should not be called independently for every publish entry.
- `jobs/publish/daily_intro.py`
  - Morning Prayer intro generation accepts `shared_theme` but still fetches daily Gospel context for prose generation.
  - That duplicate fetch can remain if the canonical `shared_theme` payload controls theme fields.
- `jobs/publish/rosary_reflections.py`
  - Rosary context and prompts accept `shared_theme`, but Rosary day context can also fetch Gospel independently for Rosary-specific prose.
  - The shared theme payload should stay authoritative for `rosary_focus_title` and shared explanation.
- `jobs/publish/ignatian_reflection.py`
  - Daily Reflection already prefers `sharedThemeTitle`, `sharedThemeExplanation`, and `sharedThemeReflectionFocus`.
- `tests/test_publish_contracts.py`
  - Best home for contract-level regression tests around `build_audio_jobs()` and render context consistency.
  - Existing tests monkey-patch `build_daily_liturgical_context`, `build_daily_intro_text`, Rosary builders, and Daily Reflection builders.
- `tests/test_publish_audio_pipeline.py`
  - Best home for pipeline-level assertions if sidecar/job behavior needs coverage across the audio facade.

### Call Graph
```text
Publish Prayer Audio workflow
  -> python -m jobs.publish.run_audio_pipeline
    -> run_audio_pipeline()
      -> load_publish_contracts()
      -> for each target date:
           build_audio_jobs(contracts, target_date=date)
             -> for each contract entry:
                  _entry_runtime_context(contract, entry, date)
                    -> _build_daily_theme_runtime_context(contract, entry, date)
                      -> _daily_theme_config(contract, entry)
                      -> build_daily_liturgical_context(...)
                    -> _build_rosary_day_runtime_context(..., shared_theme=runtime.daily_liturgical_context)
                    -> daily-reflection fields from runtime.daily_liturgical_context
                  _render_entry_metadata(..., runtime_context)
                  expand_audio_fragments(..., runtime_context)
                  _entry_text_body(..., runtime_context)
                  sidecar render_context receives runtime-derived theme metadata
```

### Root Cause
- The theme builder is correctly additive inside `DailyLiturgicalContext`, but it is invoked at the wrong scope.
- The publish pipeline wants one daily theme per target date, but the implementation resolves one daily theme per entry.
- Entry-specific metadata such as `allow_missing_gospel` can change whether Gospel is included. This allowed one contract to publish a calendar/season-only theme while another contract published a Gospel-inclusive theme for the same date.

### Design Review
- No frontend/UI surface is in scope.
- The listener-facing design principle is consistency: the same daily theme should appear everywhere, with depth varying by prayer type.
- The planned fix should not change visual design, website routing, episode IDs, Spotify lookup terms, or fixed prayer text.

### Key Decisions
- Cache key should be `(date, calendar, locale)`, not date alone. Existing contracts use `general_roman` and `en`, but keying by all three preserves future multi-calendar support.
- Canonical publish theme resolution should prefer Gospel-inclusive context first by using `allow_missing_gospel=False`. If that fails, it should fall back once with `allow_missing_gospel=True` and share that same fallback payload with every entry for the key.
- Production should not fail solely because an entry would have built a different theme; the shared cache should prevent divergence. Tests should enforce identical theme render context across jobs.
- Novena contract publishing remains out of scope for this release.

## Plan

### Summary
- Build a per-date/calendar/locale shared daily theme cache inside `jobs/publish/contracts.py`.
- Reuse the existing `DailyLiturgicalContext` builder and flattening helpers, but move canonical theme resolution outside the per-entry runtime loop.
- Pass the canonical runtime theme fields into `_entry_runtime_context()` for every publish entry on that date.
- Add regression tests proving all audio jobs for one target date share the same Gospel-inclusive theme payload, even if independent per-entry resolution would have drifted.

### What Already Exists
- `DailyLiturgicalContext` already contains shared theme fields and JSON-safe `to_dict()`.
- `_daily_liturgical_context_to_payload()` converts dataclass/dict contexts into a payload.
- `_daily_theme_runtime_fields()` flattens `sharedTheme*` fields into `daily_theme_*` runtime keys.
- `_entry_runtime_context()` is already the central place where Rosary and Daily Reflection receive theme context.
- `build_text_jobs()` and `build_audio_jobs()` already compute one `effective_date` per entry.
- Tests already use module-level monkey-patching, so the new behavior can be tested without network/model calls.

### Architecture
```text
build_audio_jobs/build_text_jobs
  -> create PublishDailyThemeCache for this job-building call
  -> per entry:
       config = _daily_theme_config(contract, entry)
       shared_theme_runtime = cache.get(target_date, config.calendar, config.locale)
       runtime_context = _entry_runtime_context(..., shared_theme_runtime=shared_theme_runtime)
       render metadata, text, and fragments using that same runtime_context
```

- New helper: `_daily_theme_cache_key(target_date, config)` returns `(date_iso, calendar, locale)`.
- New helper: `_build_canonical_daily_theme_runtime_context(target_date, *, calendar, locale)`:
  - First tries `build_daily_liturgical_context(..., allow_missing_gospel=False)`.
  - If that raises, retries with `allow_missing_gospel=True`.
  - Converts the resulting context through `_daily_liturgical_context_to_payload()` and `_daily_theme_runtime_fields()`.
- New lightweight class or closure-backed dict: `_PublishDailyThemeRuntimeCache`.
  - Owns a `Dict[tuple[str, str, str], Dict[str, Any]]`.
  - Returns a shallow copy of cached runtime fields so entries cannot mutate shared state accidentally.
- `_entry_runtime_context()` gains optional `shared_theme_runtime: Optional[Dict[str, Any]]`.
  - If provided, start runtime from that payload.
  - If omitted, preserve current standalone behavior by calling `_build_daily_theme_runtime_context()`.
- `build_text_jobs()` and `build_audio_jobs()` each instantiate one cache for their call and pass cached theme runtime into every `_entry_runtime_context()` call.

### Concrete Changes
- `jobs/publish/contracts.py`
  - Add cache key and canonical theme helper functions near `_build_daily_theme_runtime_context()`.
  - Add `_PublishDailyThemeRuntimeCache` or equivalent small helper.
  - Update `_entry_runtime_context()` signature to accept `shared_theme_runtime`.
  - Update `build_text_jobs()` and `build_audio_jobs()` to share one cache per call.
  - Ensure `render_context` still contains the flattened `daily_theme_*` fields and `daily_liturgical_context`.
- `tests/test_publish_contracts.py`
  - Add a regression test where the fake `build_daily_liturgical_context()` returns a Gospel-inclusive payload only when called with `allow_missing_gospel=False`, and a season-only payload when called with `allow_missing_gospel=True`.
  - Assert all audio jobs for one target date share the Gospel-inclusive title, Gospel citation, sources, and empty fallback reason.
  - Assert the canonical builder call count is one per `(date, calendar, locale)` for the built jobs, not one per entry.
- `tests/test_publish_audio_pipeline.py`
  - Add or update sidecar/job-level coverage only if `tests/test_publish_contracts.py` does not fully cover the audio facade.
- `docs/releases/0.3.6.11-shared-daily-theme-cache.md`
  - Update `Progress`, `QA`, and `Release Notes` during implementation and ship stages.

### Failure Modes
- Cache key too broad.
  - Symptom: future non-default calendar/locale contracts could get the wrong context.
  - Mitigation: key by `(date, calendar, locale)`.
- Cached runtime dict mutated by one entry.
  - Symptom: later entries inherit accidental runtime-only fields.
  - Mitigation: cache returns shallow copies and `_entry_runtime_context()` copies its starting dict.
- Strict Gospel fetch unavailable.
  - Symptom: publish job could fail more often than before.
  - Mitigation: canonical builder retries once with `allow_missing_gospel=True` and shares that fallback.
- Duplicate Gospel/context fetches still happen inside Daily Intro or Rosary prose builders.
  - Symptom: extra network/model work but shared theme fields remain consistent.
  - Mitigation: keep this out of the first wedge unless tests show it causes theme drift.
