# Release 0.0.5.4 - morning-prayer-fragment-completeness

- Status: Shipped
- Last Updated: 2026-03-23

## Scope

### Problem
- The remote daily novena workflow now gets past the import-path failure, but it stops later in `Generate Auto Page Audio` because Morning Prayer's two-list configuration is incomplete.
- The job reports missing detailed fragments for `Monthly Intention`, `Petition - Technology`, `Petition - Sanctification of the Church`, `Petition - Sick and Departed`, and `Daily Novena Audio`.
- The workflow cannot finish audio generation until the Morning Prayer contract rows and their linked detailed fragments are complete enough for the preflight to pass.

### Audience
- Primary user: the maintainer running the daily novena / page-audio workflow.
- Secondary stakeholders: anyone depending on Morning Prayer page audio generation, Notion page completeness, and the remote daily workflow finishing successfully.

### Current Status Quo
- `.github/workflows/daily_novena_prayer.yml` runs the novena job and then the auto page-audio job in the same workflow.
- `jobs/notion/generate_page_audio.py` enforces a two-list Morning Prayer contract and raises when required detailed fragments are missing.
- The workflow currently fails after novena generation, so the downstream audio export never finishes even though the earlier import-path bug is fixed.
- The repo already describes the Morning Prayer fragment model as a stable-key two-list setup, but the live Notion schema/data still appears incomplete for a subset of required fragments.

### Goal
- Make the Morning Prayer page-audio preflight pass by ensuring the required detailed fragments and contract links exist.
- Preserve the existing daily workflow shape so novena generation and page audio generation still run in sequence.
- Keep the fix aligned with the stable-key Morning Prayer contract instead of making the workflow brittle to display-label changes.

### Constraints
- The fix should be narrow and focused on the Morning Prayer contract rows and their fragment links.
- We should not loosen the preflight check just to let the workflow continue; the underlying contract should be completed.
- The change must keep supporting the current direct-run GitHub Actions workflow.

### Narrow Wedge
- Audit the Morning Prayer two-list contract rows and identify the missing detailed fragments.
- Determine whether the missing pieces are absent rows, missing relations, or outdated schema/migration state.
- Restore the minimal contract needed for the workflow to complete successfully.

### Non-Goals
- Do not redesign the broader page-audio architecture.
- Do not convert the workflow into a best-effort mode that ignores missing Morning Prayer fragments.
- Do not change unrelated audio outputs or devotional jobs.

### Risks And Unknowns
- The live Notion Morning Prayer database may be missing rows, relations, or stable fragment keys, and the exact gap is not fully visible in the repo.
- The workflow error may be a downstream symptom of an incomplete migration rather than a simple missing row.
- There may be other Morning Prayer fragments that are not currently surfaced in the failure message but are still required by the contract.

### Recommended Next Step
- Use `/research-astack` to map the Morning Prayer contract, the preflight check, and the exact live-data gaps before planning the fix.

## Research

### Scope Baseline
- The remote daily novena workflow now passes the import/bootstrap step, but it fails later because Morning Prayer's two-list page-audio contract is incomplete.
- The immediate research question is whether the missing `Monthly Intention`, petition, and `Daily Novena Audio` pieces are absent Notion rows, missing relations, or a stale migration state.
- Live inspection shows the `Morning Prayer` Opus Dei row exists, uses `Assembly Mode = fragments`, and already has a populated `Detailed Fragments` relation with 13 linked fragment pages.
- The live fragment data shows a durable-key drift: some linked pages still carry legacy keys or titles instead of the canonical keys the contract now expects.
- The user wants the code to match the live data, so the repair path should preserve the current Notion rows and teach the contract layer to understand the legacy key set.

### Relevant Files
- `jobs/notion/generate_page_audio.py`
  Why it matters: it owns the Morning Prayer contract definition, the two-list preflight, and the error that stops the workflow.
- `tests/test_page_audio_job.py`
  Why it matters: it already covers the Morning Prayer contract happy path and the incomplete-contract failure mode.
- `config/page_audio_config.json`
  Why it matters: it defines the Morning Prayer config rows and the current builder/audio-caption wiring.
- `README.md`
  Why it matters: it documents the intended Morning Prayer two-list contract, the required fragment categories, and the stable-key guidance.
- `.github/workflows/daily_novena_prayer.yml`
  Why it matters: it is the exact remote sequence that now fails after novena generation completes.

### Current System Map
- `generate_page_audio.py` loads the shared novena module and then builds page-audio plans from Notion `Opus Dei`, `Audio Outputs`, `Page Audio Configuration`, and `Audio Fragments` rows.
- `morning_prayer_contract_items()` defines the required stable fragment keys for Morning Prayer, including `monthly-intention`, `petition-technology`, `petition-sanctification-of-the-church`, `petition-sick-and-departed`, and `daily-novena-audio`.
- `build_opus_dei_two_list_plan()` rejects Morning Prayer rows when the detailed fragment relation is incomplete, and the remote workflow surfaces that exact exception.
- The repo already treats `Fragment Key` as the runtime identity for Morning Prayer rows, which means titles can vary while keys remain fixed.
- The failure appears after the novena job and upload step, so the page-audio job is the real blocker now rather than the earlier import issue.
- Live page inspection shows:
  - `Morning Prayer` row id `0e8a66b1-2be7-4ea0-8a92-39695f930ecd`
  - `Detailed Fragments` relation contains 13 pages, not the full 14-key stable set
  - `Monthly Intention` is already present and linked with key `monthly-intention`
  - `Daily Novena Audio` is already present and linked with a matching stable row
  - the `Petition - Technology` slot is still represented by a legacy page titled `Petition - Right Use of Technology` with key `petition-church`
  - the `Petition - Sanctification of the Church` / `Petition - Sick and Departed` rows are also cross-wired, with keys `petition-sick-departed` and `petition-7` observed on the live pages

### Reuse Opportunities
- Reuse the existing Morning Prayer contract array instead of inventing a parallel fragment list.
- Reuse the current two-list preflight and make the live Notion data conform to it, rather than weakening the guard.
- Reuse the existing regression coverage in `tests/test_page_audio_job.py` to pin down the contract and any migration assumptions.
- Reuse the current live fragment rows where possible, but repair the stable keys and relation wiring instead of creating duplicate Morning Prayer content.
- Reuse the existing page-audio contract machinery by adding a small legacy-key alias map rather than rewriting the whole Morning Prayer path.

### External References
- Notion database relation behavior matters here because the `Detailed Fragments` relation is what the preflight checks.
- GitHub Actions logs are the source of truth for the exact missing fragment keys and the step that aborts.

### Constraints
- The fix should preserve the stable-key Morning Prayer model.
- The workflow should continue to fail loudly if the contract is incomplete, but it should pass once the live data is corrected.
- This is a data-and-contract problem first; code changes should be minimal and targeted.
- Because the live row already has most relations, a targeted compatibility layer is likely lower risk than a migration helper that rewrites Notion.

### Risks
- The live Notion rows may be missing both fragment pages and their relations, which could require a migration/backfill rather than a simple config tweak.
- Some missing pieces may actually be legacy rows with the wrong stable key, not absent rows, which means a naive relink could still fail the contract.
- If the live database contains stale or duplicate Morning Prayer rows, the preflight may still fail even after the obvious missing keys are added.
- A compatibility layer that accepts legacy keys must be careful not to mask genuinely missing fragments.

### Assumptions To Validate
- The missing fragments really are the cause of the runtime failure, not a separate bug in the relation traversal code.
- The live Notion databases for `Opus Dei` and `Audio Fragments` are the authoritative sources we need to repair.
- The Morning Prayer contract should keep including `Daily Novena Audio` as part of the same stable-key fragment set.
- The live page-audio data can be repaired by retagging existing fragment rows to the canonical stable keys rather than rebuilding the whole Morning Prayer database.
- The safer approach is to add code-side aliases for the legacy keys already present in Notion, not to mutate the live database.

### Unknowns
- Whether `Petition - Right Use of Technology` should be renamed/rekeyed to `petition-technology` and `Petition - Church` should be a separate canonical fragment, or whether the live pages need a two-row relink plus a key correction.
- Whether the `petition-sick-departed` and `petition-7` keys should be normalized to the canonical `petition-sanctification-of-the-church` and `petition-sick-and-departed` rows.
- Whether any migration helper already exists to repopulate the Morning Prayer two-list contract from the stable-key list, or whether manual Notion repair is cleaner.
- Which canonical code-path should own the alias mapping so Morning Prayer can accept both the legacy and canonical durable keys without weakening unrelated fragment contracts.

### Recommended Direction
- Use `/plan-astack` to add a focused legacy-key compatibility layer in the Morning Prayer contract code, then prove it against the live Notion data and the existing regression tests.

## Plan

### Summary
- Repair the Morning Prayer two-list contract so `Generate Auto Page Audio` can complete after the novena job finishes.
- Treat the 0.0.5.1 durable-key change as the likely root cause: the code now expects stable `Fragment Key`-based Morning Prayer rows, but the live Notion data still uses a few legacy keys and titles.
- Prefer a compatibility repair over relaxing the preflight, so the workflow still fails loudly if the Morning Prayer rows drift again.

### What Already Exists
- `jobs/notion/generate_page_audio.py` already defines `morning_prayer_contract_items()` and the preflight that checks the contract.
- `tests/test_page_audio_job.py` already includes a failure test for incomplete Morning Prayer fragments and a happy-path test for the full stable-key contract.
- `README.md` already documents the durable-key Morning Prayer model, the required fragments, and the expectation that `Fragment Key` is the runtime identity.
- `.github/workflows/daily_novena_prayer.yml` already runs novena generation before page-audio generation, so the failure is isolated to the Morning Prayer page-audio contract.
- The live Notion data already contains the Morning Prayer fragment rows; the mismatch is primarily in the key names and a few relation links.

### Architecture
- The page-audio flow loads Notion `Opus Dei` rows, then resolves `Detailed Fragments` relations for Morning Prayer rows.
- `morning_prayer_contract_errors()` checks each required stable key, expected fragment kind, expected group, assembly role, and ordering.
- If any required key is missing, `build_opus_dei_two_list_plan()` raises before generation begins.
- The plan should keep that validation intact while teaching it to recognize the live legacy key aliases that already exist in Notion.

- If the alias map is too broad, it could hide a genuinely missing Morning Prayer fragment.
- If the alias map is too narrow, the workflow will continue to fail on the legacy row names already present in Notion.
- If the contract is repaired by loosening validation instead of normalizing the legacy keys, the workflow may pass once but silently regress later.
