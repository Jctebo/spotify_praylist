## Scope

### Problem
- The Catholic Novena App importer already supports bulk imports by month, but the local workflow for traditional novenas still requires a maintainer to run the July and August slices separately and keep the resulting reports straight by hand.
- That manual repetition is small, but it is exactly the kind of operator step that gets mistyped, forgotten, or run out of order when the goal is to populate several traditional novena contracts quickly.
- We want a local helper that makes the July-to-August traditional novena sweep a one-command task without changing the importer itself.

### Audience
- Primary user: the maintainer importing traditional novena contracts from Catholic Novena App.
- Secondary users: future maintainers who need a repeatable local entrypoint for importing a known seasonal batch.

### Current Status Quo
- `scripts/new_novena_url_contract.py bulk` can import a single month at a time.
- The importer already writes validated novena contracts and bulk reports, so the missing piece is orchestration, not parsing.
- Today a July/August sweep means remembering two separate invocations and managing two separate report outputs manually.

### Goal
- Add a local runner that imports the traditional novena catalog slices for July and August by default.
- Keep the existing importer logic unchanged and reuse it as the source of truth for parsing and contract generation.
- Write per-month bulk reports so July and August results stay separate and easy to review.

### Constraints
- Do not change the importer parser, validation rules, or novena contract schema for this wedge.
- Keep the new helper local-only and avoid introducing any new remote workflow.
- The runner should fail the same way the underlying importer fails, but it should keep July and August isolated so one month's failure does not erase the other month's results.
- The new run should stay inside the existing `artifacts/novena-url-overrides/` reporting convention.

### Narrow Wedge
- Add one reusable helper that batches the existing bulk importer across July and August.
- Add one thin local script that operators can run from the repo root.
- Default the new local run to the July/August window, but keep month overrides available for adjacent maintenance.

### Non-Goals
- Do not build a general-purpose date-range engine for every possible month combination.
- Do not change how individual novena pages are parsed.
- Do not alter the runtime novena publishing path.
- Do not introduce a new contract type just for the local import helper.

### Risks And Unknowns
- The biggest risk is report-file collision if the runner does not give each month its own output stem.
- Another risk is accidental ambiguity about whether the helper is meant to import all traditional novenas or only the July/August batch that the maintainer is currently working through.
- We need to keep the helper simple enough that it remains a thin layer over the importer instead of becoming a second importer with its own drift.

### Recommended Next Step
- Implement a reusable July/August import helper, add a local script that calls it, and add regression coverage for the batching and report-path behavior.

## Research

### Scope Baseline
- Build a local wrapper around the existing Catholic Novena App bulk importer so a maintainer can run the July and August traditional novena catalog slices in one go.
- Keep the import logic inside `jobs/novena_contracts/url_import.py` as the single parsing and contract-generation source of truth.

### Relevant Files
- `jobs/novena_contracts/url_import.py`: existing single-month bulk importer and bulk report writer.
- `scripts/new_novena_url_contract.py`: current manual importer CLI and its option surface.
- `scripts/run_daily_novena_prayer_local.ps1`: pattern for a thin local runner that wraps an existing job.
- `README.md`: operator-facing documentation for local novena workflows.
- `tests/test_novena_url_import.py`: current importer regression coverage that can be extended for the new batch helper.

### Current System Map
- `import_bulk_catalog(...)` already accepts a `month` filter and returns a report object with counts and entries.
- `write_bulk_report(...)` already writes `.json` and `.md` report siblings, but it assumes a single report stem, so a multi-month helper needs distinct report paths.
- The importer already uses the Catholic Novena App catalog page as the discovery anchor, so the local helper only needs to orchestrate multiple month-scoped imports.

### Reuse Opportunities
- Reuse `import_bulk_catalog(...)` instead of inventing a second crawler.
- Reuse `write_bulk_report(...)` for the output files, just with month-specific report stems.
- Reuse the existing `artifacts/novena-url-overrides/` directory as the default reporting home.
- Reuse the importer's own dry-run and force semantics rather than adding a new behavior matrix.

### External References
- Catholic Novena App catalog page: `https://catholicnovenaapp.com/list-of-all-novenas/`
- Existing importer entrypoint: `python scripts/new_novena_url_contract.py bulk --month may`

### Constraints
- The helper should not assume the same pages appear in both months or that every month will produce the same number of imports.
- The report stem must be month-specific so sequential runs do not overwrite one another.
- The helper should remain compatible with the current month filter shape already supported by the importer.

### Risks
- If month normalization is too loose, a typo could silently become an empty run or a surprise default.
- If report stems are not unique per month, the second import will overwrite the first report and hide useful review context.
- If the new helper tries to be smarter than the underlying importer, it could become another maintenance surface with its own bugs.

### Assumptions To Validate
- A July/August traditional novena sweep is the intended first local batch, not a broader all-month import job.
- The maintainer wants separate month reports rather than one merged report.
- A thin local wrapper is enough; no new parser features are needed for this request.

### Unknowns
- Whether the helper should default to the July/August pair or accept any month list supplied by the operator.
- Whether the report directory should live under a dedicated subfolder or a flat `artifacts/novena-url-overrides/` stem convention.
- Whether the operator wants the helper to print a combined summary after both month runs finish.

### Recommended Direction
- Make the helper default to July and August, keep the importer as-is, and write month-scoped report files so the operator gets one repeatable local command with clear outputs.

## Plan

### Summary
- Add a tiny reusable batch helper for the July/August traditional novena import window.
- Add a local script that invokes the helper from the repo root.
- Add tests that prove the helper batches the existing importer and keeps the monthly report outputs separate.

### What Already Exists
- `jobs/novena_contracts/url_import.py` already imports and validates traditional novena contracts.
- `scripts/new_novena_url_contract.py` already exposes the importer as a CLI.
- `write_bulk_report(...)` already knows how to write the report files once the caller chooses a unique stem.

### Architecture
- The new helper will live alongside the novena contract code and will call the existing bulk importer once per month.
- The local script will stay thin: parse arguments, choose the month list, run the helper, and write month-specific reports.
- Contract generation remains entirely inside the current importer path.

### Concrete Changes
- `jobs/novena_contracts/traditional_import.py`
  - Add month normalization and a reusable July/August batch helper.
  - Add month-specific report stem helpers for the local runner.
- `scripts/run_traditional_novena_import_local.py`
  - Add the default July/August local command.
  - Write one report pair per month.
- `tests/test_novena_traditional_import.py`
  - Add regression coverage for default batching, month overrides, and report-path separation.
- `README.md`
  - Document the new local import command and the default July/August window.

### UX And States
- Success state: one command imports July and August, writes separate report files, and leaves the traditional novena contracts in the expected location.
- Empty state: if a month has no matching entries, the helper still finishes the other month and reports the empty slice clearly.
- Error state: if one month fails, the other month still runs and the final summary makes the partial failure obvious.

### Implementation Phases
#### Phase 1: Add The Batch Helper
- Goal
  - Wrap the existing importer in a reusable July/August batching helper.
- Exact files to edit
  - `jobs/novena_contracts/traditional_import.py`
  - `tests/test_novena_traditional_import.py`
- Verification steps or commands
  - `python -m unittest tests.test_novena_traditional_import`

#### Phase 2: Add The Local Script And Docs
- Goal
  - Expose the helper as a local command and document the default workflow.
- Exact files to edit

### Failure Modes
- The helper could accidentally overwrite its own reports if the report stem is not month-specific.
- A malformed month override could route the helper into an empty run or a failed importer call.
- A single bad month should not block the other month from finishing.

### QA And Test Matrix
- Default batching
  - Confirm the helper runs July and August in order when no month list is provided.
- Override handling
  - Confirm explicit month arguments are normalized and deduplicated in the expected order.
- Report isolation
  - Confirm July and August write different report stems and do not overwrite one another.

### Rollout Notes
- This is a local convenience wrapper, not a runtime change.
- Ship the helper and script together so the README command always points at a real entrypoint.

### Not In Scope
- Importer parser changes.
- Contract schema changes.
- Runtime novena publishing changes.
