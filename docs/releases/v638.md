# v638 — Flipping the Morning & Evening source choice takes effect in the standing session (no app restart)

## §1 Scope

John's field report, 2026-11-23 16:32–16:33 CT, on the live v637 build: "I switched to sing the hours and it didn't work right away" — "Have to delete and restart the app." He flipped the Morning & Evening Prayer source choice at its new door in the Praylist edit form (v637); the standing session never took the flip. Only a cold start settled Morning/Evening Prayer under Sing the Hours.

Ground truth, verified firsthand from the parent seat at report time: the server side is whole — the live payload's two labeled slots each carry **both** sources (Divine Office standing + a backup object `{streamUrl, source 'Sing the Hours', title 'Morning Prayer - Sing the Hours'}`). The defect is client-side and in-session only.

**Fix:** a flip of the choice re-settles the two labeled slots **in the standing session** — on the flip itself, or at the editor's Done at the latest — from the live payload under the new preference, and the Praylist repaints under the new standing source and title ('Morning Prayer - Sing the Hours' when flipped to Sing the Hours first, back to '- Divine Office' when flipped back). Both directions. The v637 no-blank discipline stands: a re-settle that cannot complete leaves the standing rows as they are — never missing, never blank.

Run level: To Ship (DevOps Board row 1615). Streamlined small-release path: Plan · Implement · light Review · Ship. Base: production pin `ora-pro-nobis-v637-1` (Worker 14b22730) = rollback target. Web-only, no APK, no migration.

## §2 Grounding — the seam, named

All seams in `app/worker/src/client.ts`, verified firsthand on the base tree (`366007b`, the v637 ship tree):

- **The choice's write path terminates in a repaint of the already-composed day.** The flip handler (`[data-p637sth]` wiring, ~line 21073) is: `opnSthFirstSet632(...)` — a localStorage write of the one key, nothing more — then `opnRepaintHome604()`, which is `paintPrayersView(state.dayPayload)` (~line 21295): a pure repaint. The settled descriptors in `state.extSlots` and the rebuilt list in `state.dayDescs` are not recomposed; the marker moves in the form and nothing else in the session changes.
- **The editor's Done path is the same repaint.** `opnExitEdit607()` (~line 21642) clears the editing posture and calls `opnRepaintHome604()`. No rebuild, no refetch, no resolve. (Other editor writes reach `profileRebuild()` — a `/api/player/day` refetch — through `opnWrite604`'s completion; the choice write never passes through `opnWrite604`, so it never earns that rebuild either.)
- **`opnExtChoice628` is applied at exactly one site, and the v637 prune stands in the same function — a function the flip never calls.** The choice is applied in the courier leg inside `resolveExternals` (~line 19984), and the v637 prune of a mis-sourced cached labeled slot stands in that function's cache-read (~line 19676). `resolveExternals` is invoked only from `buildDayFromPayload` — cold open and profile-rebuild refetches. In-session, after a flip, nothing calls it: **the prune is on the cache-read path of a function the flip never reaches**, so the standing session's slots keep the old source until a cold start re-runs the pass — exactly John's report.
- **The settled slot record does not retain the other source's pointer.** `settleMeta` (~line 19844) stands a 'downloading' record carrying `backup {title, streamUrl, source}`; `extDownload`'s success then calls `settle()` (~line 19780) with a record that carries **no backup field**, and `settle` replaces `state.extSlots[slotId]` whole. So once a slot stands present, the flipped-to source's pointer exists nowhere in session state — an in-session swap cannot be composed from the settled record alone. The re-settle must re-read the served entry from the live payload (the standing courier route, `/api/player/externals/live?date=<date>`) and re-apply `opnExtChoice628` over it, exactly as the courier leg does.
- **The machinery the fix needs already stands inside `resolveExternals`' closure** (`settleMeta` · `extDownload` · `settle` · `writeCache`, ~lines 19744–19930) and is unreachable from the flip handler. The fix therefore stands a narrow hook from that closure onto `state` during the pass (the `state.ownWriteCache` / `state.restoreProbe` precedent, ~lines 19779/19765): a re-settle entry the flip path can call, closing over the standing `day`, `standing`, and settle machinery of the current pass.

### §2.1 Fix shape

1. **Hook.** During `resolveExternals`' build, stand `state.extResettleLabeled638` (name at Implement's discretion, shape fixed here): a no-arg function that (a) refetches the day's live payload through the standing courier route; (b) for each of the two labeled slots standing in the pass (`ext-morning-prayer` · `ext-evening-prayer`), takes the served entry and re-applies `opnExtChoice628(slot, e, src)`; (c) hands the result to the standing `settleMeta` — whose own guard (a present slot with the same enclosureUrl is a no-op) makes a flip to the already-standing source free. `settle` writes the day cache through the standing `writeCache`, so the record the next cold start reads already carries the new standing source (no double-flip; the v637 prune then finds the record's source equal to the preference's first choice and leaves it standing).
2. **Trigger.** The flip handler calls the hook after `opnSthFirstSet632(...)` (the flip itself; Done is the latest acceptable point — the flip is the named target). The form repaint stands as today; the re-settle's own `extSwapCard` / `extRebuildDescs` / paint legs repaint the Praylist rows as each slot settles.
3. **No-blank guard.** With the choice re-applied, the new meta's `backup` **is** the previously standing source, so `extDownload`'s standing failure flip (v628 discipline) lands the slot back on the old source present — the rows never blank on a one-route failure. For a both-routes failure during a flip re-settle, the slot must not settle `missing` over a standing present row: the re-settle path keeps the prior slot record and restores it if the re-settle would settle missing (Implement names the exact guard; the harness leg below proves the outcome, not the shape).
4. **Sounding slot — conservative, named.** A labeled slot that is **sounding** when the flip lands (its descriptor is `state.current`, or it stands in the live queue already built) is **not** restarted and its sounding descriptor is not swapped mid-play: the re-settle updates the standing slot record, the rebuilt descriptors, and the list paint — the prayer sounding finishes on the enclosure it started with, and the next play of the slot takes the new source. Reason: the queue and Now Playing hold descriptor snapshots taken at queue build; swapping a sounding descriptor's enclosure under the player is a restart by another name, and no standing code re-settles a sounding slot. The already-built queue's not-yet-played copies likewise stand as queued (a queue is a snapshot the listener already holds); a new queue build reads the rebuilt descriptors.
5. **Nothing else moves.** The four choice functions, the store, the v637 prune, the editor's furniture, and every other slot stand byte-identical. No new store, no new cache key, no settings-version bump (a version bump would re-resolve the whole day — the opposite of this fix's narrowness).

## §4.1 Fix-forward — PROBE-D supersession (per-slot re-settle epoch)

Fix commit: `63eec71` on `release/v638` (on top of the §4 Review commit `5f3bbe4`). STOP at BRANCH READY — no merge, no deploy, no board touch. SW pin untouched. Scope of the delta: `app/worker/src/client.ts` (+57/−12 net within the diff, all hunks inside `resolveExternals`' `buildWithSettings` closure) and `app/harness-v638.mjs` (new legs S6 · L6 · L6b · L6c + the delayed pass-through posture in the fetch stub). ### The epoch mechanism

- **Seat.** `extResettleEpoch638` — a per-slot epoch map stood beside `extResettlePrior638` in the same per-pass closure. Per-pass, like the prior map: a cold open or profile rebuild builds a fresh map, and no epoch can leak across passes.
- **Taking an epoch.** The hook (`state.extResettleLabeled638`) takes the slot's next epoch (`(map[slotId] || 0) + 1`) only when a re-settle actually starts — after its no-change guard has passed (see the same-source paragraph below) and immediately before it hands the meta to `settleMeta`. Each labeled slot epochs independently.
- **Carriage.** The epoch rides the re-settle's whole download chain as an added trailing parameter: hook → `settleMeta(slot, meta, epoch638)` → `extDownload(slot, meta, epoch638)` → `settle(slot, st, epoch638)`. The v628 backup flip inside `extDownload`'s catch recurses with the **same** epoch — the backup retry is the same re-settle, not a new one. Every non-hook caller of `settleMeta` / `extDownload` / `settle` (the pass's own courier leg, `extRestoreCached`, the watchdogs, cold opens) passes no epoch (`undefined`) and is never gated.
- **The check.** `settle` checks the epoch **first**, before any other act: a completion whose epoch is not the slot's current epoch returns whole — no `state.extSlots` write, no descriptor rebuild, no card swap, no `writeCache`. `extDownload` additionally tests `stale638()` at its two completion points before acting: on success before the mint (a stale mint under the shared owner could revoke the blob URL the newer settle minted), and on failure before the backup retry (a superseded chain does not start a second download). Both outcomes are gated — a stale `present` and a stale `missing` alike (L6 and L6b).

### Composition with the prior-record restore guard (exact)

The epoch check fires **first** in `settle`, before the guard is read. Consequences, by case:

- A **stale** settle never reaches the guard: it cannot restore its (stale) prior record, and it cannot discharge the guard a newer re-settle armed. This closes PROBE-D's no-blank edge — in the pre-fix tree the newer `present` settle discharged the guard and the stale chain's later `missing` then blanked the row (L6b's pre-fix shape: both slots `missing`).
- A **current-epoch** settle meets the guard exactly as §3 specified: `missing` is replaced whole by the armed prior record, `present` discharges (deletes) the entry. Prior entries now carry their arming epoch (`{ rec, epoch }`); the restore/discharge act itself is unchanged and is reached only by a settle that has already passed the epoch gate (or carries no epoch).
- An **ungated** settle (no epoch — courier, cache restore, watchdog) retains the guard's §3 behavior, as before: the resolve watchdog's long-stop `missing` aimed at an armed slot still restores the prior record.
- Arming is unchanged in shape, one addition: the hook arms the prior record under the epoch it just took, and only for a slot standing `present` whose enclosure actually changes. A second flip while the first download hangs still does not re-arm (the slot stands `downloading`, not `present`) — the first flip's prior record remains the armed record, and a current-epoch `missing` from the newer chain restores it (a real standing present record; the row never blanks).

### The same-source interleaving — outcome decided and proven

Flip to Sing the Hours (chain 1 in flight) → flip back to Divine Office (chain 2 settles) → flip to Sing the Hours again (chain 3). The store's final source **is** Sing the Hours, the same source chain 1 was carrying. **The epoch rule decides: chain 1's late completion FALLS.** An epoch names a re-settle, not a source — chain 1 is superseded the moment chain 2 takes the slot's next epoch, and no later flip revalidates it. Only chain 3 (the current epoch) may settle the slot. The final state still matches the store, because chain 3 settles Sing the Hours itself; what the rule buys is that no stale chain ever writes — record, descriptors, or cache — at any point in the interleaving.
