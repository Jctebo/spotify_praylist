# Release 0.1.5.5 - Daily Podcast Episode Metadata

Date: 2026-04-27
Status: Shipped
Branch: enhancement/daily-podcast-episode-metadata
Depends On: 0.1.5.4

## Scope

### Problem
- Daily prayer publishing needs per-day episode metadata instead of one static episode title and description.
- Morning Prayer should publish a title like `Morning Prayer for April 27, 2026` based on the run date, and a matching dated description.
- Re-running the same day should be safe and idempotent, overwriting only that day’s scoped episode output and metadata instead of creating drift across older episodes.
- Each episode should be date-scoped, so April 27, 2026 has its own identity and reruns only overwrite that date’s record.
- The first lines of the episode should feel liturgical and current, not like copied boilerplate.
- The spoken output should use OpenAI's `alloy` voice, which matches the current repo defaults and is already supported by the existing TTS path.

### Audience
- Primary user: the maintainer who runs Morning Prayer publishing each day.
- Secondary stakeholders: listeners who expect each episode to reflect the current date and liturgical day.
- Secondary stakeholders: future maintainers who need the metadata rules to stay contract-owned and predictable.

### Current Status Quo
- `jobs/publish/contracts.py` already supports recurring daily prayer contracts, ordered blocks, and contract-level audio metadata, but the title and description are still mostly static text.
- `jobs/publish/rss.py` uses the rendered job title and text directly when building podcast items, so the feed does not yet have a dedicated template layer for date-based episode metadata.
- `jobs/publish/audio.py` can write a recurring output file for a given `entry_id`, but it is not yet modeling date-scoped episode replacement as an explicit contract behavior.
- `jobs/novena/liturgical_helpers.py` already provides Romcal-backed liturgical day lookup, which can supply the feast-day context for the opening block.
- The repo does not yet have a dedicated daily episode intro that combines liturgical celebration, praise, and Gospel summary into the start of the prayer.

### Goal
- Publish each daily Morning Prayer episode with a date-aware title and description derived from contract templates.
- Support f-string-style variables in the contract-owned title and description strings so date formatting stays declarative.
- Use OpenAI TTS with the `alloy` voice for the generated audio so the new flow stays aligned with the current repo defaults.
- Add a dynamic Morning Prayer opening block that:
  - uses Romcal to determine the liturgical day and one or more celebrations,
  - passes that day context to OpenAI for a short opening sentence about what the Church celebrates,
  - emits a second sentence of praise,
  - uses `catholic-mass-readings` to fetch the day’s Gospel and summarize it in a single sentence.
- Keep reruns idempotent so today’s episode can be regenerated without mutating out-of-scope episode history.
- Write over only the current date-scoped episode when rerun, instead of updating a single evergreen episode record.

### Constraints
- Keep Morning Prayer as the first wedge, even if the contract model is general enough to support other daily podcasts later.
- Reuse the existing publish contract, RSS, and audio pipeline rather than inventing a parallel publishing system.
- Use the repo’s liturgical helper boundary where possible instead of duplicating Romcal plumbing.
- Fail closed when date templating, Romcal lookup, mass-reading lookup, or OpenAI generation cannot produce valid output.
- Preserve the current public audio and RSS output shapes under `docs/audio/*.mp3` and `docs/podcast.xml`.
- The TTS voice decision must stay within the voices the selected OpenAI API surface actually supports; if `Cove` is only available in ChatGPT Voice Mode, the release needs a fallback or a custom-voice decision instead of assuming API parity.
- The TTS voice decision should remain on `alloy` unless a later release explicitly chooses to change the audio voice family.
- The episode identity should be date-scoped, not a single stable evergreen item.

### Narrow Wedge
- Implement date-templated title and description support for daily episodes, starting with Morning Prayer.
- Add one dynamic opening block at the start of Morning Prayer that is generated from the current day’s Romcal context and Gospel reading.
- Treat `daily` as the first recurrence pattern to support, since it is the immediate publishing cadence already in use.
- Make the rerun behavior explicit: a run for today should overwrite only today’s date-scoped episode output, sidecar metadata, and feed item content.

### Non-Goals
- Do not build a general-purpose template language or arbitrary code execution in contract strings.
- Do not redesign all publish contracts or all prayer products at once.
- Do not backfill or rewrite historical episode metadata unless a later release explicitly asks for that.
- Do not add a UI for editing templates inside the app.
- Do not change the public podcast feed URLs or storage layout beyond what the new metadata needs.

### Risks And Unknowns
- The safest implementation shape for f-string-style templating still needs to be validated so contract text stays flexible without becoming unsafe.
- Multiple feast days on one date may need careful formatting so the generated opening sentence reads naturally and joins celebrations with `and`.
- The quality and consistency of OpenAI’s short liturgical intro need to be constrained so the output stays reverent and deterministic enough for daily publishing.
- `catholic-mass-readings` integration may require a separate validation step if its day lookup or Gospel summary surface differs from the existing runtime assumptions.
- Idempotent replacement logic must be precise so daily reruns update only the intended episode and do not churn older feed items.
- `alloy` is the current implementation default, so any voice change would need its own validation and regression coverage.
- Date-scoped episode identities need a clear file/guid naming rule so the rerun target is unambiguous and historical items do not get overwritten accidentally.

### Recommended Next Step
- Run `/research-astack` to map the current publish metadata path, confirm where contract-templated title and description fields should live, and validate the safest daily intro generation flow.

## Research
### Scope Baseline
- The scoped change is a daily Morning Prayer publishing enhancement: date-aware episode metadata, contract-owned title/description templates, and a dynamic opening block that reflects the current liturgical day and Gospel.
- The implementation needs to be idempotent so rerunning today only refreshes today’s scoped episode output and metadata.

### Relevant Files
- `jobs/publish/contracts.py` - owns contract loading, `target_date` resolution, block flattening, and job assembly for text and audio; this is the best place to understand how date-aware content already flows through the publish system.
- `jobs/publish/audio.py` - owns audio file naming, content-hash short-circuiting, fragment assembly, and sidecar metadata; this is the current overwrite/idempotence boundary for `docs/audio/<entry_id>.mp3`.
- `jobs/publish/rss.py` - builds the podcast feed item title, description, guid, and enclosure from rendered jobs; any daily metadata templating must ultimately feed this module.
- `jobs/publish/notion.py` - maps text jobs into Notion page properties and body blocks; useful if the daily metadata also needs to appear in the review surface.
- `jobs/notion/generate_page_audio.py` - contains the repo's existing OpenAI prompt-generation pattern, including `responses.create`/`chat.completions` fallback behavior and `Prompt Model` defaults that already resolve to `OAI_MODEL` or `gpt-4.1-mini`.
- `jobs/novena/liturgical_helpers.py` - provides Romcal-backed day lookup, celebration naming, and optional-celebration handling; this is the clearest reusable source for the new opening block’s liturgical context.
- `jobs/novena/generate_daily_novena_prayer.py` - contains the existing daily readings fetch/parsing and block-construction patterns; it is the closest in-repo example for daily scripture-derived content.
- `tests/test_publish_contracts.py` - covers contract resolution and fragment expansion order.
- `tests/test_publish_audio_pipeline.py` - covers audio idempotence, RSS generation, and the current public feed shape.
- `tests/test_publish_text_pipeline.py` - covers Notion text upsert behavior and replacement semantics.
- `requirements.txt` - confirms `romcal==4.0.0b6` and `openai` are already present; `catholic-mass-readings` is not listed yet.

### Current System Map
- `build_text_jobs` and `build_audio_jobs` already accept a `target_date` and use contract timezone to resolve date-sensitive selectors.
- `expand_audio_fragments` already turns a contract’s block tree into leaf audio fragments, which means the new dynamic intro can be inserted as another resolved fragment instead of inventing a parallel pipeline.
- `render_audio_job` writes one MP3 and one JSON sidecar per `entry_id`, then skips work when the stored `content_hash` matches; that is the current rerun gate.
- `build_rss_feed` uses the rendered job’s `title`, `text`, `audio_url`, and `entry_id` guid directly today, so the plan needs a date-scoped archive scan rather than a one-run-only feed rebuild.
- `jobs/novena/liturgical_helpers.py` already returns the primary celebration plus suppressed optional celebrations for a date, so it can supply the "Today the Church celebrates..." input without a second calendar lookup.
- `jobs/novena/generate_daily_novena_prayer.py` already demonstrates how this repo fetches daily readings, cleans text, and emits structured blocks for Notion; the new daily intro can reuse that general pattern even if it swaps in `catholic-mass-readings`.
- The repo already uses `OAI_MODEL` defaults of `gpt-4.1-mini` for prompt generation in the novena and page-audio paths, so the daily intro can follow the same text-model convention while TTS stays on `alloy`.
- The current publish flow is recurrence-aware in content, but not in episode identity: the public file name and RSS guid are still rooted in `entry_id`, so the daily enhancement will need a date-scoped naming rule and an archive scan from `docs/audio/*.json`.

### Reuse Opportunities
- Reuse the contract `target_date` plumbing already in `build_text_jobs`, `build_audio_jobs`, and `resolve_block_content`.
- Reuse `romcal_fetch_day`, `celebration_name`, and `infer_celebration_rank` to build the liturgical summary for the opening line.
- Reuse the existing `render_audio_job` content-hash and sidecar model as the daily rerun/idempotence boundary.
- Reuse the RSS writer and Notion upsert surfaces so the enhancement changes the rendered metadata, not the downstream publication plumbing.
- Reuse the novena job’s daily-reading parsing approach as a validation model for scripture lookup, text cleanup, and structured output, even if the new dependency is `catholic-mass-readings`.

### External References
- `catholic-mass-readings` on PyPI, version `0.7.3`, provides an async `USCCB` client plus `get_mass`, `get_mass_from_date`, `get_mass_types`, and related helpers for scraping USCCB Daily Readings. PyPI lists it as a Python 3.10+ package and describes it as an API for the USCCB Daily Readings site: https://pypi.org/project/catholic-mass-readings/
- `romcal==4.0.0b6` is already pinned in `requirements.txt` and is the current liturgical-calendar source in the repo.
- The USCCB Daily Readings site is the upstream source behind the mass-readings package and the repo’s existing novena reading fetch flow.
- `openai` is already a runtime dependency, so the dynamic intro can use the same model boundary the repo already uses for generated speech or text.
- OpenAI's text-to-speech API docs list built-in voices such as `alloy`, `ash`, `ballad`, `coral`, `echo`, `fable`, `nova`, `onyx`, `sage`, `shimmer`, `verse`, `marin`, and `cedar`; `Cove` appears in the ChatGPT Voice Mode FAQ instead of the public TTS voice list, so API compatibility needs validation before implementation.
- The repo’s existing publish and novena code paths already default to `alloy`, so the enhancement can stay aligned with an already-supported voice choice.
- The repo’s existing prompt-generation path already defaults to `OAI_MODEL` or `gpt-4.1-mini`, which is the right text-model convention for the daily intro helper.

### Constraints
- Any f-string-style contract interpolation needs a constrained formatter, not Python `eval`, or the contract layer becomes a code execution surface.
- The daily episode identity model is still unresolved: the current public guid is `entry_id`, so a daily publish flow must decide whether it overwrites one moving episode in place or creates date-scoped episode ids.
- `build_rss_feed` sorts and writes directly from rendered jobs, so daily metadata needs to be resolved before feed generation unless the writer itself becomes template-aware.
- The dynamic opening block must tolerate multiple celebrations on one day and produce natural joining text, especially when optional memorials or commemorations are present.
- The Gospel summary source needs to be deterministic enough for daily publishing and should fail closed if the reading lookup is missing or ambiguous.

### Risks
- The biggest implementation risk is choosing a metadata-templating mechanism that is either unsafe or too weak for date formatting.
- A second risk is episode identity drift: if the project keeps `entry_id` static while publishing day-specific content, historical and current episodes may collapse into one public item unless that behavior is explicitly intended.
- A third risk is overfitting the opening block to one calendar shape and producing awkward language when Romcal returns multiple feast-day celebrations.
- `catholic-mass-readings` is an external dependency that is not yet installed in this repo, so API assumptions still need confirmation during planning and implementation.

### Assumptions To Validate
- Morning Prayer is the first and only daily-episode wedge for this release.
- The intent is overwrite-in-place for today's date-scoped episode, with each date getting its own identity.
- The dynamic intro should be spoken as part of the episode audio, not only stored in Notion or RSS metadata.
- `catholic-mass-readings` can provide enough Gospel text to summarize in one sentence without adding a second scripture source.
- The contract timezone is the authoritative source for "today" unless a run-time override is explicitly introduced.

### Unknowns
- Where the date-templated title and description should live in the contract shape: a dedicated field, a metadata sub-object, or another contract-owned block.
- Whether the opening block belongs in the existing audio fragment tree as a new resolved leaf or should be assembled as a preamble before the current Morning Prayer blocks.
- How the date-scoped episode id should be derived so the generated file, RSS guid, and sidecar metadata always point at the current day.
- Whether the Gospel summary should come directly from `catholic-mass-readings` output or from an OpenAI summarization step over that output.
- Whether the repo should keep the existing novena USCCB fetch path as a fallback or replace it completely for this enhancement.
- Whether the audio voice should stay fixed on `alloy` for this release or become configurable later.

### Recommended Direction
- Move into `/plan-astack` next, with planning centered on a safe daily-template mechanism, a clear episode identity decision, and a reusable intro-block helper that combines Romcal with `catholic-mass-readings`.

## Plan
### Summary
- Build a date-scoped Morning Prayer publishing path where the title, description, episode id, audio file, and feed item all key off the run date instead of a single evergreen episode.
- Keep the pipeline contract-first and reuse the current publish/audio/text flow, but add safe template rendering plus a generated daily opening block at the start of Morning Prayer.
- Use `alloy` for TTS, `gpt-4.1-mini` via the repo's existing `OAI_MODEL` prompt convention for the opener text, and fail closed if the daily calendar or reading lookup cannot be resolved.

### What Already Exists
- `build_text_jobs` and `build_audio_jobs` already accept `target_date` and already resolve date-sensitive selectors from contract data.
- `jobs/novena/liturgical_helpers.py` already provides date-based Romcal lookup and multiple-celebration handling.
- `jobs/notion/generate_page_audio.py` and `jobs/novena/generate_daily_novena_prayer.py` already show the repo's OpenAI prompt-generation conventions, including `responses.create` fallback behavior and `OAI_MODEL` defaults.
- The current publish audio code already hashes fragment manifests and reuses unchanged pieces, which gives us the rerun/idempotence boundary we want.
- The current publish RSS writer already accepts rendered jobs and can stay the final assembly point once jobs become date-scoped and archive-aware.

### Architecture
- Contract metadata holds the templated episode surface:
  - `metadata.title_template`
  - `metadata.description_template`
  - `metadata.episode_id_template`
- `jobs/publish/formatting.py` will render safe `{name}` / `{date:%B %-d, %Y}`-style placeholders from a fixed context object and will never evaluate arbitrary Python.
- `jobs/publish/daily_intro.py` will assemble the Morning Prayer opener by:
  - reading the liturgical day from Romcal,
  - fetching the day's Gospel from `catholic-mass-readings`,
  - prompting OpenAI to produce a three-sentence opener,
  - validating that the output is exactly the requested shape before it enters the prayer text.
- `jobs/publish/contracts.py` will treat `kind: daily_intro` as a supported block and will expand it into plain text for both text and audio jobs.
- `jobs/publish/audio.py` will use a derived `episode_id` for `docs/audio/<episode_id>.mp3` and the matching sidecar JSON, while keeping fragment-level reuse underneath that boundary.
- `jobs/publish/rss.py` will build the podcast feed from date-scoped sidecars, not just from the current run, so historical episodes remain in the feed and today's rerun only replaces today's record.
- `jobs/publish/run_audio_pipeline.py` will merge the current run's rendered jobs with archived sidecars from `docs/audio/` before writing `docs/podcast.xml`.

```text
config/publish/contracts/morning-prayer.json
        |
        v
safe template render (title / description / episode_id)
        |
        v
daily intro resolver (Romcal + catholic-mass-readings + OpenAI)
        |
        v
ordered text/audio fragments -> fragment cache -> assembled MP3
        |
        v
date-scoped sidecar in docs/audio/
        |
        v
archive scan -> rss feed rebuild -> docs/podcast.xml
```

### UX And States
- No UI changes.

### Failure Modes
- Template rendering can fail if a contract references a missing field or uses an unsupported placeholder; the pipeline should reject the contract before publishing.
- The daily intro can fail if Romcal returns no celebrations, the mass-readings client returns an unexpected payload, or OpenAI emits malformed text; the pipeline should abort before writing the MP3 or RSS item.
- Date-scoped file naming can fail if the derived `episode_id` collides or the feed scan misses a sidecar; the pipeline should keep the prior day's files intact and surface the mismatch in tests.
- RSS rebuild can fail if archived sidecars are missing required metadata; the runner should fail closed rather than emitting a partial feed.
