# Release 0.4.2.0 - rosary-saint-context-fallback

- Status: Shipped
- Created Date: 2026-08-19
- Last Updated: 2026-08-19

## Scope

### Problem
- Daily Rosary generation can fall through to deterministic fallback prose with awkward sentence structure.
- Fallback composition prepends `Saint` even when the supplied witness already begins with `Saint`, producing errors such as `Saint Saint John Eudes, Priest`.
- The current prompt makes an approved quotation effectively mandatory, increasing fallback use when no approved quotation is available.

### Audience
- Primary user: listeners receiving the daily Rosary audio and text.
- Secondary stakeholder: the maintainer reviewing scheduled generation failures and fallback output.

### Current Status Quo
- `jobs/publish/rosary_reflections.py` builds a structured Rosary package, retries plain JSON, then creates a deterministic package.
- The prompt receives the liturgical priority, Gospel, mysteries, shared context, saint witness, and optional approved quotation.
- Validation requires the witness and quotation when supplied, and requires every decade to mention its mystery title or fruit.

### Goal
- Reduce avoidable fallback use by asking the LLM for relevant information about the day's primary observance and applying it to the Rosary intentions and mysteries.
- Support saints, feast-day events, Marian observances, and other liturgical subjects without forcing them into a theme taxonomy.
- Keep quotations optional and never fabricate them.
- Ensure deterministic fallback output is natural, grammatically sound, and correctly names the supplied witness.

### Constraints
- Preserve the existing five-decade structured response, priority precedence, human-need categories, length limits, and Scripture-citation guard.
- Do not invent saint biographies, feast events, quotations, or citations.
- Continue publishing when the LLM is unavailable.
- Keep the change limited to Rosary context retrieval, prompt/validation behavior, fallback prose, and regression coverage.

### Narrow Wedge
- Add one LLM-generated observance-context object containing relevant facts or event information, optional quotation material, and concise alignment guidance for the five Rosary intentions.
- Use that object in the existing Rosary generation prompt and deterministic fallback.
- Normalize witness display names before rendering them in prose.

### Non-Goals
- Building a reusable saint-theme taxonomy or curated theme database.
- Changing Rosary mystery scheduling, audio providers, voices, publishing routes, or unrelated devotional prompts.
- Treating an LLM-generated quotation as approved without attribution or confidence checks.
- Replacing the existing fallback path with a hard failure.

### Risks And Unknowns
- LLM research may hallucinate historical facts or quotations unless the prompt and validation explicitly constrain claims.
- A single context shape must work for individual saints, groups, Marian titles, and event-based feasts.
- More context may increase prompt size and make prose overly explanatory unless the output contract stays concise.

### Recommended Next Step
- Run `/research-astack` to map the Rosary generation path, existing saint context data, tests, and the safest LLM/context contract; then lock the implementation with `/plan-astack`.

## Research

### Scope Baseline
- The active Rosary path is `jobs/publish/rosary_reflections.py`; it builds one structured five-decade devotional package, retries plain JSON, and then uses a deterministic fallback.
- The requested improvement is observance-specific LLM context, not a theme classifier: the subject may be a saint, event, Marian observance, feast, or another liturgical celebration.
- Quotes are optional. The output must remain useful when no approved quotation exists.

### Relevant Files
- `jobs/publish/rosary_reflections.py`: owns Rosary context assembly, OpenAI calls, structured response validation, witness validation, and deterministic fallback prose.
- `jobs/publish/contracts.py`: builds and caches the Rosary devotional set for text/audio jobs and exposes source/fallback metadata; no new publishing boundary is needed.
- `jobs/publish/saint_centered_theme.py`: supplies the existing saint witness and curated quote when available. Its fields can remain backward-compatible inputs; this task should not expand its theme model.
- `jobs/publish/daily_theme_runtime.py`: maps shared liturgical context into the Rosary context, including saint and quote fields.
- `config/publish/contracts/rosary.json`: defines the active Rosary contract and existing reflection configuration.
- `tests/test_publish_rosary_reflections.py`: covers priority precedence, prompt wording, semantic validation, structured/JSON retry behavior, and fallback output.
- `tests/test_publish_contracts.py` and `tests/test_publish_audio_pipeline.py`: cover the cached Rosary set and metadata propagation that must remain stable.
- `README.md`: documents the current Rosary generation contract and fallback metadata.

### Current System Map
- `build_rosary_day_context()` combines Romcal, Gospel data, shared daily context, and the five mysteries into `RosaryDayContext`.
- `_available_priorities()` and `_ensure_priority_context()` establish the dominant observance hierarchy: major celebration, season/Gospel/memorial as applicable, then mystery fruits.
- `build_rosary_devotional_set()` calls `_build_devotional_prompt()`, tries `responses.parse()` through `_call_openai_structured()`, retries `responses.create()` JSON through `_call_openai_json()`, then calls `_deterministic_devotional_set()`.
- `validate_rosary_devotional_response()` enforces five ordered decades, prose lengths, dominant-priority anchors, mystery title/fruit coverage, distinct human-need categories, Scripture-citation limits, and saint-witness presence.
- `_deterministic_devotional_set()` currently composes the fallback by mechanically prefixing `Saint ` to the supplied witness and repeats the witness in every decade, which explains both duplicate honorifics and awkward prose.
- `jobs/publish/contracts.py` already caches one devotional set and carries source/fallback metadata into text/audio jobs, so the planned change can remain localized to context generation and Rosary text.

### Reuse Opportunities
- Reuse the existing Responses structured-output and plain-JSON compatibility paths rather than introducing a new provider abstraction.
- Reuse `RosaryDayContext` and `RosaryPriority` as the source of the observance and intention context; do not create a parallel calendar/theme taxonomy.
- Reuse the existing Pydantic response validation and deterministic fallback validation as the final safety boundary.
- Reuse the existing cached devotional-set path and sidecar metadata; add only additive context/source metadata if implementation needs observability.
- Reuse `_normalize_for_match()` and `_normalize_whitespace()` while adding a display-name helper that avoids duplicate `Saint`/`St.` prefixes.

### External References
- OpenAI Responses structured output is already used in `_call_openai_structured()` and is covered by the repository's current SDK dependency; implementation should verify the installed SDK behavior with mocks, not add a new dependency.
- The repository's existing Romcal and Gospel adapters remain the authoritative supplied inputs for the day's observance; the LLM should summarize and contextualize those inputs rather than invent unsupported liturgical facts.

### Constraints
- The new context must work for named persons, groups, Marian titles, and event-based observances without requiring a `subject_type` or theme vocabulary.
- The LLM must distinguish supplied facts from optional general knowledge and must omit uncertain details instead of filling them with plausible fiction.
- A quotation may be used only when supplied/attributed by the existing approved context or returned with explicit attribution; absence of a quote must not invalidate the package.
- All final prose must still satisfy the current character, five-decade, mystery, priority, category, and Scripture validators.
- The fallback must remain deterministic and valid without an API key.

### Risks
- A new LLM research call adds latency and another failure point; it must degrade cleanly to supplied liturgical fields and still produce a valid fallback.
- Free-form LLM facts may be hallucinated or too verbose. The context schema and prompt must cap the number and length of details and reject empty/obviously instructional output.
- Requiring the saint witness in every decade can still produce repetitive prose. Validation should require natural presence across the package, while the prompt should specify the introduction plus at least two reflections rather than every field.
- Event celebrations may not have a saint witness. The prompt and validator must preserve observance-centered generation when the saint field is absent.

### Assumptions To Validate
- A compact structured context response can be generated reliably by the configured model before the existing devotional response call.
- Existing `RosaryPriority.title`, `prompt_context`, and `anchors` are sufficient to identify the primary observance without changing calendar precedence.
- A normalized display helper can preserve titles such as `Saint John Eudes, Priest` and `Saints Nereus and Achilleus, Martyrs` without changing matching behavior.

### Unknowns
- Whether to make the context call mandatory before devotional generation or use it opportunistically when an API key is available. The recommended plan makes it best-effort and keeps the existing generation/fallback chain intact.
- Whether context details should be persisted in public sidecars. The recommended plan keeps them private or excludes them from sidecars unless needed for debugging, avoiding a public metadata contract.

### Recommended Direction
- Add a small structured `RosaryObservanceContext` response inside `jobs/publish/rosary_reflections.py`. Populate it with concise relevant information about the dominant observance, optional attributed quotation, and no categorical theme fields.
- Call that helper best-effort before devotional generation, include its result in both generation prompts, and use it as an input to the deterministic fallback when available.
- Relax quote validation from “required whenever context has one” to “validate exact inclusion only when the generated package chooses to use the supplied quote”; never require a quote when none is available.
- Fix witness rendering with a canonical display helper and replace the fallback templates with varied, grammatically complete sentences tied to the observance and each mystery.
- Proceed to `/plan-astack`; the remaining decisions are implementation-level and can be covered by focused tests.

## Plan

### Summary
- Add a best-effort LLM observance-context step before Rosary prose generation.
- Feed concise, non-taxonomized observance information into the existing structured and JSON generation prompts.
- Make quotations optional, normalize saint display names, and rewrite the deterministic fallback into natural observance-aware prose.
- Preserve the existing five-decade contract, validation gates, caching, and no-key fallback behavior.

### What Already Exists
- `RosaryDayContext` already contains the dominant priority, celebration title, Gospel, season, mysteries, saint witness, and optional approved quotation.
- The Responses API structured and JSON retry paths already exist.
- `jobs/publish/contracts.py` already resolves one devotional set per job and propagates source/fallback metadata.

### Architecture
```text
Romcal + Gospel + shared liturgical context + mysteries
                         |
                         v
                 RosaryDayContext
                         |
             best-effort LLM context call
                         |
       concise observance facts + optional quotation
                         |
          structured devotional generation
             /                       \
       valid package                 failure
             |                         |
             v                         v
       existing validators     deterministic fallback
             \                         /
              v                       v
             one cached five-decade Rosary package
```

### Concrete Changes
- Edit `jobs/publish/rosary_reflections.py`:
  - Add a small structured `RosaryObservanceContext` model with only concise observance information, optional details, and optional attributed quotation fields; do not add theme/category fields.
  - Add `_build_observance_context_prompt()` and `_call_openai_observance_context()` using the existing model/settings and Responses structured-output compatibility pattern.
  - Add a best-effort context resolver that returns an empty context on API failure and records the failure for the existing fallback reason.
  - Include the resolved context in `_build_devotional_prompt()` and `_call_openai_json()` instructions. Tell the model to use information relevant to the primary observance—whether person, event, Marian title, or feast—and connect it naturally to each mystery and human need.
  - Make quotation use optional. If included, require exact use of the supplied approved wording and attribution; absence of a quotation must not reject the package.
  - Add a witness display-name helper so already-prefixed values are rendered once (`Saint John Eudes, Priest`, not `Saint Saint John Eudes, Priest`).
  - Rewrite `_deterministic_devotional_set()` with complete sentence templates that vary the introduction, overall intention, decade intentions, and reflections while using the observance context when present.
  - Keep `_require_saint_witness()` permissive enough for event-based days: require the witness only when one is supplied, and require it in the package plus at least two reflections rather than mechanically repeating it in every decade.

### Failure Modes
- Context call unavailable: log the failure, use an empty context, and continue through the existing generation chain.
- Context response malformed or too long: reject it and continue without context.
- Structured devotional response invalid: use the existing JSON retry, then the improved deterministic fallback.
- Generated quotation invented or altered: reject the package if it presents a quotation as the approved quote; the fallback omits quotations unless an approved exact quote is available.
- Event has no saint witness: skip witness-specific requirements and validate observance/mystery/priority anchors instead.
- Witness includes an honorific: normalize only display composition; preserve matching and source data.

### QA And Test Matrix
- Saint case: `Saint John Eudes, Priest` never becomes `Saint Saint John Eudes`; optional approved quote can be omitted without fallback.
- Event case: an event-based feast produces context and prose about the event, with no fabricated saint witness.
- Marian/group case: titles and plural witnesses remain grammatical.
- Context failure: mocked LLM context failure still permits structured generation or deterministic fallback.
- Prose quality: fallback introduction, overall intention, five intentions, and five reflections are complete sentences, non-empty, within existing limits, and free of prompt/schema commentary.
- Existing semantic rules: dominant priority, mystery title/fruit, five distinct human-need categories, supported Scripture citations, and exactly five ordered decades remain enforced.
- Integration: cached Rosary devotional sets are reused by text/audio jobs and existing reflection source/fallback metadata remains compatible.
- Commands: focused Rosary tests, then the existing publish/audio regression set and `git diff --check`.
