# Release 0.3.2.8 - Auxilium Response Audio Cleanup

Status: Shipped
Date: 2026-06-02
Branch: enhancement/ora-pro-nobis-daily-rosary-reflections

## Scope

### Problem
- The generated Auxilium Christianorum audio currently speaks printed response markers such as `V.` and `R.` aloud.
- Those markers are rubrical labels for a call-and-response prayer, not words intended to be spoken.
- In a one-person listening context, the desired behavior is a natural pause between the versicle and response.
- A stronger version would make the audio feel like two people praying by assigning one speaker voice to the versicle and a second speaker voice to the response.
- Why now: Auxilium Christianorum is already generated as an Ora Pro Nobis daily episode, resolved by Spotify, and rendered through fragment-based audio. The remaining issue is audio polish on an already active daily surface.

### Audience
- Primary user: a listener praying along with the daily Auxilium Christianorum episode who expects the recording to sound like prayer, not like source markup being read aloud.
- Secondary stakeholders:
  - The repo owner/operator, who needs repeatable daily audio generation without manual post-processing.
  - Future maintainers, who need source text cleanup and speaker handling encoded in contracts/tests rather than one-off edits.
  - Spotify playlist users, who receive the generated Auxilium episode through the daily queue and will hear any audio-quality defects.

### Current Status Quo
- `config/publish/templates/auxilium-christianorum/daily-offering.txt` begins with:
  - `V. Our help is in the name of the Lord.`
  - `R. Who made heaven and earth.`
- `config/publish/templates/auxilium-christianorum/litany-most-precious-blood.txt` includes:
  - `V. Thou hast redeemed us with Thy Blood, O Lord.`
  - `R. And made of us a kingdom for our God.`
  - `Through the same Christ our Lord. R. Amen.`
- The publish renderer treats file blocks as plain text, so the TTS provider receives the literal `V.` and `R.` strings.
- Audio assembly already inserts silence between fragments, but the affected versicle/response lines live inside larger file fragments, so there is no controllable pause at those internal response boundaries.
- Audio contracts already support provider preferences such as ElevenLabs first and OpenAI fallback, but voice/provider settings are currently entry-level rather than line-level or fragment-level.

### Goal
- Remove spoken `V.` and `R.` labels from Auxilium Christianorum generated text/audio while preserving the devotional response structure.
- Insert natural pauses where the printed source indicates a versicle/response transition.
- Explore and, if practical, support different speakers for versicle and response lines in the Auxilium audio.
- Success criteria:
  - Generated Auxilium text/audio no longer includes literal `V.` or `R.` labels in the spoken content.
  - Versicle/response boundaries still read naturally, with a short pause between the initiating line and response line.
  - The final `R. Amen.` in the Litany conclusion becomes a natural concluding response, not a spoken label.
  - Regression tests cover the checked-in Auxilium templates, rendered text, audio fragments, content hashes, and sidecar metadata.
  - If dual-speaker support ships, tests prove the two roles produce separate fragment cache identities and render through configured provider fallback.

### Constraints
- Keep this release focused on Auxilium Christianorum response audio quality.
- Preserve the source-grounded lay-member Auxilium prayer content; this is markup normalization, not a prayer rewrite.
- Do not change the Spotify Auxilium resolver, episode title, episode id, feed location, or Notion membership behavior.
- Do not introduce manual audio editing or post-processing outside the existing publish pipeline.
- Any speaker-role feature must be cache-safe: changing a speaker/voice must invalidate the affected fragment audio without corrupting reused fragments.
- Any speaker-role feature must degrade cleanly when only one provider or one voice is configured.

### Narrow Wedge
- First, normalize Auxilium response markers so `V.` and `R.` are stripped before TTS and replaced by explicit pause boundaries.
- Prefer splitting the affected response pairs into structured blocks or smaller fragments over relying on ad hoc punctuation tricks inside template text.
- Add focused tests that render Auxilium for a known date and assert:
  - no standalone `V.` or `R.` appears in generated text,
  - the response lines remain present,
  - audio fragments expose separate boundaries around the response pairs,
  - resume markers remain useful and ordered.
- Then decide whether to add a minimal speaker-role contract shape, such as `speaker: "versicle"` and `speaker: "response"` on leaf blocks/fragments, with role-to-voice mappings in `audio_config`.

### Non-Goals
- No changes to priest-only Auxilium prayers.
- No changes to the weekday prayer selection map beyond response-marker cleanup if those files do not contain response labels.
- No changes to Rosary, Morning Prayer, Marian Antiphon, novena, or Spotify playlist behavior.
- No new UI for choosing voices.
- No broad SSML system unless research proves the current TTS providers require it for reliable pauses.
- No attempt to synthesize overlapping dialogue; this should remain a reverent, sequential prayer recording.

### Risks And Unknowns
- The safest text representation needs validation: removing labels directly from templates is simple, but structured response blocks may preserve source intent and audio control better.
- Existing audio fragments are cached by text and TTS settings; any internal pause or speaker-role metadata must participate in the hash or old audio may be reused incorrectly.
- OpenAI and ElevenLabs have different voice/speaker capabilities; a dual-speaker abstraction may need provider-specific validation.
- Splitting response pairs into small fragments may increase API calls unless caching offsets the cost.
- Text publication may need slightly different formatting from audio: visible text can omit `V.`/`R.`, but it still needs readable line breaks.

### Recommended Next Step
- Run `/research-astack` to inspect the publish contract renderer, audio fragment hashing, sidecar schema, provider fallback, and all Auxilium templates for response-marker occurrences.
- Research should recommend one of two implementation paths:
  - complete cleanup only: structured pauses with one voice, or
  - complete cleanup plus speaker roles: separate versicle/response voices with cache-safe metadata.
- RECOMMENDATION: Choose cleanup plus speaker-role research because it answers the user-facing defect and validates the higher-quality recording option before implementation.

### Current System Map
- Contract loading:
  - `load_publish_contracts()` reads JSON from `config/publish/contracts/*.json`.
  - `_normalize_block()` currently accepts `sequence`, `repeat`, `weekday_map`, `monthly_template`, `file`, `inline`, `daily_intro`, and `liturgical_announcement`.
  - Unknown block kinds fail closed, which is good for adding a small explicit response/speaker shape if needed.
- Text rendering:
  - `resolve_block_content()` reads `file` blocks as plain text and joins `sequence` children with `\n\n`.
  - `build_text_jobs()` renders sections from top-level blocks and exposes `resume_markers` per text section.
  - Current Auxilium text for April 6, 2026 still contains `V.` and `R.`.
- Audio rendering:
  - `expand_audio_fragments()` flattens leaf blocks into ordered fragments.
  - Current Auxilium audio has 10 fragments; `daily-offering.txt` and `litany-most-precious-blood.txt` are each one large `file` fragment, so their internal response boundaries cannot receive a controlled pause.
  - `assemble_audio_fragments()` inserts `DEFAULT_FRAGMENT_SILENCE_MS = 350` ms of cached silence between fragments.
  - Splitting response lines into separate leaf fragments is enough to create a pause without adding SSML.
- TTS providers:
  - `render_audio_job()` tries configured providers in order for the whole job.
  - `_effective_provider_audio_config()` maps OpenAI and ElevenLabs provider settings into the request shape.
  - OpenAI speech generation uses one `voice` value per request in `openai_tts_renderer()`.
  - ElevenLabs speech generation posts to `/v1/text-to-speech/{voice_id}`, so it also uses one `voice_id` per request.
  - Therefore, different speakers are possible by rendering different fragments with different effective provider/voice settings, not by sending one mixed-speaker text blob to the current TTS calls.
- Cache and sidecars:
  - `fragment_content_hash()` hashes fragment text plus normalized audio settings.
  - `audio_manifest_hash()` hashes the job identity, normalized job audio settings, and each fragment key/hash.
  - `render_fragment_audio()` writes per-fragment sidecars with `tts`.
  - `render_audio_job()` writes episode sidecars with `tts`, `fragment_manifest_hash`, `fragments`, and `resume_markers`.
  - Any speaker-role implementation must update hash inputs before render time, not only renderer behavior, or stale cached audio can be reused.

### External References
- OpenAI Text to Speech docs show the speech endpoint taking model, voice, and input for a single speech request, and document custom voice IDs as values supplied through the `voice` parameter: https://developers.openai.com/api/docs/guides/text-to-speech
- ElevenLabs Create Speech docs show the request as `POST /v1/text-to-speech/:voice_id` with request text, model, and optional voice settings: https://elevenlabs.io/docs/api-reference/text-to-speech/convert
- Inference from both provider docs: the current provider APIs do not give this repo a single-request multi-speaker primitive through the paths it uses. Multi-speaker quality should be modeled as multiple fragments with role-specific voices.

### Risks
- A template-only cleanup would remove spoken labels but would not give precise pauses unless the affected text is split into fragments.
- A contract-only split using existing `inline` blocks gives pauses but no dual-speaker behavior.
- Adding fragment-level speaker roles touches shared publish-audio hashing and rendering; missing one hash path could cause stale cache reuse.
- `normalize_audio_settings()` currently preserves known TTS fields and provider lists, but not arbitrary future keys such as `speaker_roles`; adding roles requires deliberate normalization.
- `render_audio_job()` currently chooses one provider config for all fragments. Per-fragment roles require a helper that derives effective fragment config during both hash computation and rendering.
- Splitting the Litany into many tiny fragments would increase render calls. The narrow split should only isolate actual response pairs and final `Amen` unless planning chooses broader line-level dialogue.

## Plan

### Summary
- Build Auxilium response-audio cleanup as a complete publish-pipeline improvement:
  - remove `V.` / `R.` from generated Auxilium text and audio,
  - split response pairs into separate audio fragments so pauses are real,
  - add minimal fragment speaker-role support so versicle and response lines can render with different voices.
- This plan is the chosen approach because a template-only cleanup would stop the bad spoken labels but would not give reliable response pauses or future-proof speaker quality.

### What Already Exists
- `config/publish/contracts/auxilium-christianorum.json` already owns the active Auxilium block tree and TTS provider preferences.
- `jobs/publish/contracts.py` already normalizes block trees, renders text jobs, expands leaf audio fragments, and builds resume markers.
- `jobs/publish/fragments.py` already hashes fragment text plus TTS settings and assembles MP3 output with cached inter-fragment silence.
- `jobs/publish/audio.py` already renders fragments one by one, persists fragment/episode sidecars, and falls back across provider preferences.
- Existing tests already cover Auxilium text assembly, audio fragment order, provider fallback, sidecar persistence, and cache invalidation.

### Architecture
- Add an optional leaf-block field named `audio_role`.
- Supported roles for this release:
  - `versicle`
  - `response`
- Add optional `audio_config.role_overrides` at entry level.
- Role override shape:
  - keys are normalized role names,
  - values are partial audio config objects merged into the fragment's effective TTS config,
  - values may include `providers` to override provider order for that role.
- Default behavior:
  - blocks without `audio_role` keep existing behavior,
  - blocks with `audio_role` but no matching override still render with the entry-level audio config,
  - existing contracts remain valid.
- Auxilium response fragments should use OpenAI built-in voices by default for the short call/response pairs:
  - `versicle`: OpenAI `alloy`
  - `response`: OpenAI `echo`
  - normal Auxilium fragments keep the current ElevenLabs-first provider list.
- No new public UI.

```text
Auxilium contract
  -> normalize blocks + role_overrides
  -> build text sections from clean inline/file blocks
  -> expand audio fragments
       fragment.text
       fragment.audio_role
       fragment.effective_audio_config
  -> hash each fragment using text + effective_audio_config
  -> render each fragment with its effective provider/voice
  -> assemble MP3 with existing silence between fragments
  -> persist sidecar with fragment role + TTS metadata
```

### Failure Modes
- Role override misconfiguration:
  - Detection: contract loading test fails or provider rendering fails with a clear provider error.
  - User experience: publish audio job fails before a bad episode is shipped.
- Cache hash misses role config:
  - Detection: tests comparing content hash changes across role voices fail.
  - User experience if missed: stale one-voice fragments could be reused.
- Text cleanup drops prayer text:
  - Detection: Auxilium text tests assert the response lines remain present and ordered.
  - User experience if missed: published prayer omits part of the source prayer.
- Provider fallback fails per fragment:
  - Detection: provider fallback regression test fails.
  - User experience: publish job fails as current all-provider failure behavior.
- Resume marker noise:
  - Detection: fragment count/order assertions fail.
  - User experience: archive/bookmark surfaces show confusing labels.

- Existing sidecar readers remain compatible because added fragment metadata is additive.
- If a better ElevenLabs response voice becomes available, add it to `role_overrides.response.providers` without changing the renderer.

### Not In Scope
- Changing Spotify lookup contracts or Notion membership names.
- Reworking the whole publish contract schema.
- Adding SSML support.
- Adding live dialogue, overlapping speech, or conversational agents.
- Editing Rosary, Morning Prayer, Marian Antiphon, novena, or legacy page-audio behavior.
- Backfilling all historical Auxilium episodes.

### Open Questions
- No blocker for implementation.
- Non-blocking follow-up: choose a dedicated ElevenLabs response `voice_id` if a higher-quality second voice is available.
