# Release

- Version: 0.4.4.0
- Slug: intro-fallback-observability
- Status: shipped
- Last updated: 2026-09-11

## Scope

### Problem
- Many generated devotional introductions appear to fall back, but current logs do not distinguish model transport failures, validation failures, missing Gospel context, or deterministic fallback assembly.
- A recent symptom is an introduction that mentions the day's Gospel citation/verses without explaining the Gospel passage, suggesting that citation-only context can be treated as sufficient input.
- The current generator suppresses one provider error, overwrites the first attempt's validation error with the second attempt's error, and exposes only a short final fallback reason.

### Audience
- Primary user: the maintainer reviewing daily published prayer audio and its sidecars.
- Secondary stakeholders: future operators diagnosing scheduled publish failures and listeners who need introductions grounded in the actual day's Gospel.

### Current Status Quo
- The shared devotional intro builder makes two attempts, retries with a correction prompt, and then uses a deterministic profile-specific fallback.
- Sidecars include `source`, `policy_version`, and `fallback_reason`, but not a structured attempt trail or context-quality diagnosis.
- Gospel retrieval has live library, USCCB HTML, and offline cache paths, but retrieval failures are mostly represented as a generic missing-context result.
- The shared theme bridge can preserve a citation or short bridge even when full Gospel text is unavailable, allowing prose that names verses without meaningful detail.

### Goal
- Make every intro outcome auditable enough to answer why generation succeeded, retried, or fell back.
- Reduce citation-only introductions when Gospel text is available by passing a concise, bounded Gospel detail/context field and validating that generated Gospel-grounded prose uses more than a bare citation when required.
- Preserve deterministic, safe fallback behavior when external services or source data are unavailable.
- Success criteria: tests cover each fallback class and retry path; sidecars expose structured, redacted generation diagnostics; logs identify entry/date/profile/source and the failed stage without secrets or full prompt text; existing scheduled publish behavior remains compatible.

### Constraints
- Do not log API keys, authorization headers, full prompts, or full Gospel text.
- Keep the existing OpenAI provider order and deterministic fallback available.
- Maintain backward-compatible `source` and `fallback_reason` fields for existing consumers.
- Keep the change within the shared publish intro/context path; no broad observability platform or unrelated audio-provider rewrite.

### Narrow Wedge
- Add structured per-attempt diagnostics to `DevotionalIntroResult`, including stage, provider path, validation outcome, and redacted reason; emit concise operator logs at the shared resolver boundary.
- Preserve both first and retry errors instead of only the last error.
- Add bounded Gospel context quality metadata and a prompt/validation rule for profiles configured to require Gospel detail, while allowing citation-only behavior when the Gospel text is genuinely unavailable.
- Add regression tests for Responses-to-Chat fallback, validation retry, deterministic fallback metadata, missing-vs-citation-only Gospel context, and sidecar/log serialization.

### Non-Goals
- Replacing the Gospel source providers or guaranteeing live USCCB availability.
- Introducing a new logging service, dashboard, or alerting dependency.
- Rewriting all devotional prose or changing novena-specific rules unrelated to fallback diagnosis.
- Automatically regenerating historical audio in this change.

### Risks And Unknowns
- Existing published sidecars may not contain enough data to classify past fallbacks; new diagnostics will primarily improve future runs.
- Requiring Gospel detail too aggressively could create unnecessary fallbacks on days where only a citation is reliably available.
- Provider exceptions may contain sensitive text, so redaction and bounded logging must be tested explicitly.

### Recommended Next Step
- Validate the current call graph, sidecar schemas, and test seams, then produce the implementation plan for structured diagnostics and citation-only Gospel handling.

## Research

- `jobs/publish/devotional_intro.py` owns shared generation, validation, retry, deterministic fallback, and the public `DevotionalIntroResult` metadata.
- `_default_generate_text` tries the Responses API first and then Chat Completions, but discards the first provider exception; `build_devotional_intro` retries once and stores only the most recent exception as `fallback_reason`.
- `jobs/publish/daily_intro.py` retrieves Gospel data from the mass-reading library, USCCB HTML, and the offline lectionary. It passes full Gospel text into the prompt, but the shared theme runtime may provide only a bridge/citation.
- `jobs/publish/daily_theme_runtime.py` and `jobs/publish/contracts.py` carry shared context into all devotional profiles and serialize intro metadata into job/sidecar structures.
- Existing tests cover deterministic fallback, validation retry, secret/URL redaction, missing Gospel behavior, and context propagation, but not provider-attempt provenance, structured fallback classes, or citation-only Gospel detail.
- The safest compatibility boundary is to extend `DevotionalIntroResult.metadata()` and existing sidecar dictionaries while retaining the current `source` and `fallback_reason` keys.

## Plan

### Summary
- Add structured, redacted diagnostics for each intro generation attempt and provider path.
- Preserve both failed attempts when falling back, and emit one concise stderr log at the publish resolver with date, entry, profile, source, and diagnostic code.
- Make Gospel context quality explicit so citation-only context is distinguishable from full-text context; require a meaningful Gospel anchor for the Morning Prayer profile when full Gospel text is supplied.
- Keep deterministic fallbacks and all existing metadata keys backward-compatible.

### What Already Exists
- Shared profile definitions, validation, retry, and deterministic fallback in `jobs/publish/devotional_intro.py`.
- Provider/source fallback chain and offline lectionary in `jobs/publish/daily_intro.py`.
- Shared daily context cache and sidecar/job metadata attachment in `jobs/publish/contracts.py` and `jobs/publish/daily_theme_runtime.py`.
- Unit-test loader patterns in `tests/test_publish_devotional_intro.py`, `tests/test_publish_daily_intro.py`, and publish-contract tests.

### Architecture

```text
Gospel providers ──> context quality ──> intro prompt
                                      │
OpenAI Responses ──success────────────┤
       │ exception                    │
       └──> Chat Completions ──success┤
                    │                 │
                    └── failure ──> validation retry
                                      │
                         success ────┤
                         failure ────> deterministic fallback
                                      │
                         result + diagnostics
                                      │
                         stderr log + sidecar
```

- `DevotionalIntroResult` remains the transport object. Add a serializable diagnostics collection and context-quality fields without changing its existing required keys.
- Provider calls return or raise through a small internal helper that records provider name, attempt number, outcome, and redacted exception class/message. Responses-to-Chat fallback remains inside the default generator.
- Validation failures are recorded separately from provider failures. The retry correction continues to use the first validation/provider failure, while the final result retains the complete bounded trail.
- Gospel context quality is derived from available citation, bridge, and full text. A full-text context gets a `full_text` quality; citation/bridge-only gets `citation_only`; neither gets `missing`.

### Failure Modes
- Responses API fails but Chat Completions succeeds: mark provider retry provenance; do not fall back.
- Both provider paths fail: use deterministic fallback and persist both redacted failures.
- First generated response fails validation and correction succeeds: persist retry/validation diagnostics while keeping source `openai`.
- Both generated responses fail validation: use deterministic fallback with validation reasons.
- Full Gospel text is available but output names only a bare citation: reject and retry once; fallback remains safe if retry fails.
- Only citation/bridge is available: permit citation-aware prose and mark context quality `citation_only`.
- No Gospel data is available: preserve existing no-Gospel rules and mark context quality `missing`.

### QA And Test Matrix
- Unit: Responses success; Responses failure → Chat success; both provider failures; empty provider output.
- Unit: first validation failure → corrected success; two validation failures → fallback; exact diagnostic ordering and redaction.
- Unit: full-text Gospel context requires meaningful Gospel anchor/detail; citation-only and missing context do not falsely require unavailable detail.
- Integration: text job sidecar includes intro diagnostics and context quality for Morning Prayer and prayer-intro profiles.
- Integration: audio job sidecar carries identical metadata; resolver log identifies entry/date/profile and omits prompt, API key, URL, and full Gospel text.
- Regression commands: `py -3 -m unittest tests.test_publish_devotional_intro tests.test_publish_daily_intro tests.test_publish_contracts tests.test_publish_audio_pipeline` and full test suite.

### Rollout Notes
- No feature flag or migration; metadata additions are additive.
- The policy version should be bumped so cached/stale intros can be recognized and refreshed if the validation contract changes.
- Existing consumers continue reading `source` and `fallback_reason`; new diagnostics are optional for older sidecars.

### Not In Scope
- New external telemetry infrastructure or remote alerting.
- Changes to audio TTS provider fallback, Spotify refresh fallback, or novena body content.
- Reprocessing historical episodes.

### Open Questions
- None blocking implementation; use `citation_only` as the compatibility behavior unless tests reveal a contract that intentionally supplies no full text but still requires a Gospel-specific claim.
