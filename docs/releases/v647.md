# v647 — A new build takes hold without an app restart

## §1 The item (John, 2026-11-24 01:11–01:12 CT)

"Make sure a restart isn't necessary" — spoken after the v644/v645
builds reached his phone and stood waiting on a manual restart: the
new build was fully served, and the running app kept the old build
until he restarted it.

Registered as v647 · DevOps Board row 1624 · streamlined
small-release path (Scope passed by the main seat) · run level
To Ship on John's order.

**The ask:** the app adopts a new build on its own. A running
session learns that a newer build stands served, and at the next
safe moment it takes the new build in place — no manual restart,
no banner, no prompt. It never cuts a sounding prayer, never drops
a standing PIN/vault gate, never loses an open edit.

## §2 Grounding — the update seam as it stands (shipped client, base = pin ora-pro-nobis-v645-1)

Read firsthand from `app/worker/src/` on the base tree and from the
live served `/sw.js`.

1. **The service worker already installs eagerly.** The SW source
   is `SW_JS` in `ui.ts` (~line 1076), served by `index.ts` at
   `/sw.js`. Its cache name IS the pin: `var CACHE =
   "ora-pro-nobis-v645-1"`. On `install` it precaches the shell set
   (`/`, `/styles.css`, `/app.js`, `/logo.png`, `/logo-512.png`,
   `/manifest.json`) and calls `self.skipWaiting()` — a new SW
   never waits for tabs to close. On `activate` it purges the old
   shell caches (preserving `opn-ext-audio-v1` and
   `opn-offline-meta-v1` by the standing v334/v392 rule) and calls
   `self.clients.claim()` — the new SW takes control of running
   pages at once.
2. **A fresh load always lands the new build.** The SW `fetch`
   handler races the network against a 3 s stall timer for shell
   paths (v429 §2.3), cache as fallback — so any reload or cold
   open composes the newest shell the network can give.
3. **A running session never learns any of this.** The client
   registers the SW exactly once, at the boot tail
   (`client.ts:25302`: `navigator.serviceWorker.register('/sw.js')`,
   result ignored). Grep-verified across `client.ts` / `ui.ts` /
   `index.ts`: **no** `registration.update()` call, **no**
   `updatefound` listener, **no** `controllerchange` listener. The
   browser's own SW update check fires on navigation and on its
   ~24 h cadence — never on a running session's timescale. And
   `clients.claim()` changes the page's controller, not the code
   in memory: the page keeps executing the `/app.js` it loaded
   with (the document loads it bare, `ui.ts:77`) until a reload.
   **That is the whole gap: install + control already happen;
   adoption (a reload onto the new shell) is never triggered.**
4. **The pin lives in exactly one place.** No pin or version
   constant stands in `client.ts`; the only pin string in the
   build is the SW's `CACHE` name in `ui.ts`. A client-side pin
   read must therefore come from the SW script itself (its text
   carries the name) — there is no second source to drift.
5. **Standing cadence seams to ride.** A `visibilitychange`
   listener stands at `client.ts:6157`; a 5 s interval stands at
   `client.ts:18697` (the native mirror tick, a no-op outside
   native mode); 1 s sleep/stall ticks stand at
   `client.ts:6451-6452`. Boot already fetches `/api/prayer/day`
   and warms the day-set download (v569).
6. **A one-shot reload discipline already exists.** The v429
   §2.5 boot stamp (`opn-boot` / `opn-boot-healed`,
   `client.ts:25303`) re-arms a one-shot boot heal at every
   completed boot — proof the estate already trusts a
   localStorage-guarded single reload, and the neighbor adoption
   must compose with, never double-fire against.
7. **What a reload keeps, and what it does not.** Everything a
   restart keeps, a reload keeps: the vault and every on-device
   store, day positions, played marks, the profile document —
   all persisted. Session-only state that a reload resets
   exactly as a restart does, named so none reads as a defect:
   the per-block fold overrides (`opnFoldSession604`, reset at
   every page load by the v612 design) and **the standing queue
   + current track** (session state; nothing persists them).
   The queue's session nature drives Plan call (a) below.

## §3 Plan — the seams and the named calls

One client-side addition in `client.ts`, seated at the boot tail
beside the standing SW registration. No SW change (its install /
activate discipline already does its half), no `index.ts` change,
no APK change — the same bundle and the same SW mechanics serve
the APK WebView, the installed PWA, and the plain tab, so one
code path covers all three shapes. **Stop condition:** if
Implement's grounding finds a shape where the SW lifecycle does
not run as §2 reads, it stops and names it rather than widening.

### 3.1 Detection — the served pin, read from the SW script

- At boot the client records its **running pin**: it fetches
  `/sw.js` with `cache: 'no-store'`, parses the `CACHE` name
  (`ora-pro-nobis-vNNN-N`), and holds it as the session's pin.
  At a fresh boot the served shell and the running shell are the
  same build (the network-first race, §2.2), so the served name
  at boot IS the running build's name.
- A **check** repeats that read. If the served pin differs from
  the running pin, a newer build stands served: detection fires.
  The check also calls `registration.update()` on the standing
  registration, so the browser installs the new SW promptly
  (skipWaiting + claim already stand, §2.1) and the eventual
  reload lands on the new cache deterministically.
- **Named call (b):** detection reads the pin from the SW text
  rather than listening for `controllerchange` alone —
  `controllerchange` also fires on a first-ever claim, carries
  no pin, and cannot say *which* build arrived; the parsed name
  is shape-uniform, directly comparable, and is the value the
  adoption record (§3.2) must name anyway.
- **Cadence (cheap):** at boot · on `visibilitychange` to
  visible (the app returning to the foreground — the exact
  moment this gap bites) · every 30 min on a dedicated interval.
  Each check costs one small conditional fetch of `/sw.js`
  (~3 KB) plus, on change only, the update call. A failed fetch
  is a silent no-op; detection simply tries again next cadence.

### 3.2 The adoption record — at most one reload per pin, provable

- One localStorage record, `opn-adopt-v647`, holding the target
  pin of the adoption this device has already fired for:
  `{target: <pin>}`.
- The reload for a pin fires **only** on the transition where
  detection names a target with no standing record for it: the
  record is written **before** `location.reload()` is called.
- On the next boot: running pin == record target → the adoption
  landed; the record is cleared. Running pin != record target
  (the reload landed back on the old build — §3.5) → the record
  stands, and detection for that same target never fires a
  second automatic reload. One pin, one automatic reload, by
  construction — the state machine has no path back to the
  firing transition for the same pin.
- A later pin supersedes: detection of a newer served pin than
  the recorded target replaces the record when its own firing
  transition comes (the record names one target at a time).

### 3.3 The safe moment — all of it, or adoption waits

Adoption fires only when **every** term holds; the predicate is
re-checked on the 5 s standing interval's cadence while a
detected adoption stands pending, and the pending adoption
survives in memory until it fires or the session ends:

- **Player fully idle** — nothing sounding on the web element or
  the native engine, **and** no current track / standing queue.
  **Named call (a):** the bar is *idle*, not merely
  *not-sounding*. A queue standing paused is mid-use — since
  v645 it may be a hand-built queue (Play next / Add to queue)
  that exists only in session state (§2.7); a silent reload
  would discard it. A stopped player with nothing loaded loses
  nothing.
- **No PIN/vault gate standing** — neither the v609 Praylist
  lock gate / unlock card nor a `renderPinGate` sheet is
  painted.
- **No edit form open** — the in-place editor
  (`opnEditSetHtml609`'s form) is not standing.
- **No sheet or menu open** — the shared sheet layer paints
  nothing.

Implement grounds each term against the client's exact state
fields and paint markers; the Plan names the surfaces, the
predicates must be the client's own standing signals (playback
state + native mirror · the gate paints · the editor's DOM
seat · the sheet root), never new parallel state.

### 3.4 The adoption act — one reload, silent

When detection stands and the safe predicate holds: write the
§3.2 record, then `location.reload()`. The new session boots on
the new shell through the standing network-first path. **Silence
discipline:** the adoption path paints nothing — no banner, no
prompt, no toast, no What's New surface in the app (the board's
What's New entry is the record). Grep + paint legs prove it
(§3.7 leg 7).

### 3.5 Failure — the old build keeps running, no loop

If the reload lands back on the old pin (an asset fetch failed
mid-swap and the shell race served the old cache), the session
simply continues on the old build: the standing §3.2 record
blocks any second automatic attempt for that pin, and the next
natural reload or cold open takes the new shell by the standing
§2.2 path. No blank page: adoption introduces no paint of its
own, and the v642 composed-set paint discipline is untouched —
a reload is the boot the app already survives daily.

### 3.6 Composition with the neighbors

- **v429 boot heal:** adoption's record is its own key; it
  never reads or writes `opn-boot` / `opn-boot-healed`. The
  post-adoption boot runs the heal machinery exactly as any
  boot does.
- **v642 paint:** the adoption reload is an ordinary reload;
  the composed-set / loading-state discipline governs the
  repaint unchanged.
- **v638 re-settle, v645 queue discipline:** untouched —
  adoption fires only when no queue stands (§3.3), so it can
  never discard or re-settle a live one.

### 3.7 Gates — harness-v647 (fail-on-old where the base lacks the behavior)

Fixtures per Improvement D: the harness drives the real client
in the estate's jsdom recipe with the SW seam stubbed at the
client's own surfaces (the `/sw.js` fetch, the registration,
the reload act — the v645 harness's stub pattern), production
day fixtures as the standing harnesses use them.

1. A session running pin N with pin N+1 served **detects** the
   new build (the check names N+1); on the base tree no
   detection exists.
2. Idle + ungated → **exactly one** adoption reload, and the
   new session stands on N+1 (the boot read-back names N+1,
   the record clears).
3. **Never twice for one pin:** a session whose record already
   names the served target fires no reload, however many
   checks run.
4. Playback sounding (and, per call (a), a queue standing
   paused) → **no** adoption; at the stop + idle, adoption
   fires at the next safe-moment check.
5. Vault gate standing, then edit form open → no adoption
   while either stands; adoption after both clear.
6. A reload that lands back on pin N leaves the old build
   running, fires no second reload, and paints no blank or
   error surface (the boot completes; the day paints).
7. The adoption path paints **no** banner / prompt / toast —
   paint assertions + a grep leg over the adoption seam for
   user-facing strings.
- Regressions: harness-v645 · v644 · v642 · v641 tables clean
  or standing named sets only.

### 3.8 The honest limit, stated plainly

**v647 itself arrives the old way.** The adoption machinery
lives in the new build; a session running v645 cannot adopt
v647 in place, because the code that would do it is in v647.
John restarts once more for v647 — and **every build after
v647 is the first that can be adopted in place**. The field
proof of this release is therefore the *next* ship: a session
left running across that ship takes it without a restart. The
ship report (§5) names this leg as the release's standing
field proof rather than claiming a same-day pass.
