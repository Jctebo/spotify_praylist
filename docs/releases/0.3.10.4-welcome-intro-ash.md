# Release 0.3.10.4 — Welcome Intro Ash

Status: Ready to ship
Branch: enhancement/welcome-intro-ash
Last Updated: 2026-07-25

## Scope

### Problem
- Prayer audio begins without a shared Ora Pro Nobis welcome or statement of its saint-focused mission.
- Listeners need a consistent spoken opening that identifies the ministry before every prayer.

### Audience
- Primary: people listening to Ora Pro Nobis prayer audio.
- Secondary: maintainers publishing daily, novena, and devotional prayer episodes.

### Current Status Quo
- Prayer pipelines assemble prayer-specific spoken fragments and transitions.
- The configured OpenAI voice is Ash, but no universal Ora Pro Nobis welcome is prepended to each generated prayer audio item.

### Goal
- Prepend the exact spoken intro “Welcome to Ora Pro Nobis. Where we pray with the saints.” to every newly generated prayer audio item.
- Render the intro with Ash whenever the OpenAI TTS path is used, without changing the configured provider or voice for the prayer itself.

### Constraints
- Preserve existing prayer text, prayer-specific introductions, musical transitions, timing, and provider selection.
- Apply the intro once per generated prayer audio item; it must not duplicate on retries or fragment-cache reuse.
- Keep the change limited to future generation; existing published files are not regenerated.

### Narrow Wedge
- Add one reusable spoken intro fragment at the common prayer-audio assembly boundary and verify its exact placement and configured Ash voice.

### Non-Goals
- Changing the wording, selecting a new voice, or bulk-regenerating existing audio.
- Adding a website-only welcome or altering non-prayer podcast episodes.

### Risks And Unknowns
- Prayer pipelines may have separate assembly paths, so the shared boundary must cover all intended prayer outputs without affecting unrelated shows.
- Cached fragments need a stable identity that changes when this intro is introduced.

### Recommended Next Step
- Inspect all audio assembly entry points, their shared fragment helper, and existing voice/cache tests to identify the narrowest universal insertion point.

## Research

### Relevant Files
- `jobs/publish/contracts.py`: expands every approved publish entry into ordered `audio_fragments`, applies per-fragment audio settings, computes the manifest hash, and creates resume markers.
- `jobs/novena_contracts/engine.py`: creates ordered `audio_fragments` for contract novenas before their audio job is rendered.
- `jobs/novena_contracts/audio.py`: renders those novena fragments with their effective provider settings.
- `jobs/novena/generate_daily_novena_prayer.py`: retains a legacy daily-novena audio path with Ash as its default OpenAI voice.
- `tests/test_publish_contracts.py` and `tests/test_novena_engine.py`: cover fragment ordering and generated prayer-audio structures.

### Findings
- The publish path has one universal expansion boundary for Morning Prayer, Auxilium, Marian Antiphons, Rosary, and Daily Reflection episodes.
- Contract novenas use a separate fragment builder and therefore need an equivalent insertion there.
- Individual fragments can carry role-specific audio configuration, which enables the welcome to use OpenAI Ash even when a prayer body uses another configured provider.
- `audio_manifest_hash` includes the fragment list and effective configuration, so a new stable welcome fragment naturally invalidates stale generated audio and fragment cache keys for future runs.
- Existing prayer-specific and devotional intros remain valuable content; the new welcome must precede them rather than replace them.

## Plan

### Summary
- Add one reusable `Ora Pro Nobis Welcome` fragment with the exact text “Welcome to Ora Pro Nobis. Where we pray with the saints.” before every generated prayer-audio sequence.
- Give that fragment an explicit OpenAI Ash configuration, while preserving each existing body fragment’s provider and voice settings.

### What Already Exists
- Publish and novena pipelines both render ordered audio fragments, support fragment-level effective audio configuration, and include fragment/configuration data in cache and episode hashes.
- OpenAI Ash is already the configured default for the prayer pipelines.

### Architecture

```text
publish entry / novena render
          |
          v
Ora Pro Nobis welcome (OpenAI Ash)
          |
          v
existing prayer-specific intro + prayer fragments (unchanged)
```

### Concrete Changes
- Add a small shared welcome-fragment builder in `jobs/publish/contracts.py` and reuse it from the publish expansion and contract-novena engine.
- Update `jobs/publish/contracts.py` so `expand_audio_fragments` prepends the welcome exactly once before all entry blocks, including text-only fallback entries.
- Update `jobs/novena_contracts/engine.py` so `render_novena` prepends the same welcome before its existing day-specific devotional intro.
- Update `tests/test_publish_contracts.py` and `tests/test_novena_engine.py` to assert exact text, first position, one occurrence, explicit OpenAI/Ash override, unchanged following fragment order, and changed manifest identity.
- Update this release record with final implementation and QA evidence.

### UX And States
- There is no visual UI change.
- A listener hears the fixed Ora Pro Nobis welcome in Ash first, then the existing prayer-specific introduction and prayer content.
- Provider fallback remains available if OpenAI cannot render the welcome; no internal error language is spoken.

### Failure Modes
- The intro is duplicated: ordering/count assertions require exactly one fixed welcome fragment per job.
- The body voice is unintentionally changed: assertions inspect only the welcome’s role override and preserve following fragments.
- Cached audio remains stale: the fragment and effective settings participate in the existing manifest hash.
- A novena control or prayer fragment moves: existing ordered-fragment tests and the new first-fragment assertions catch the regression.

### QA And Test Matrix
- Publish contracts: each generated job begins with the exact welcome, OpenAI/Ash override, and a single occurrence.
- Rosary, Marian, Morning Prayer, Auxilium, and Daily Reflection: existing first prayer fragment follows the welcome in its previous order.
- Contract novenas: welcome precedes `Welcome to Day N`, while canonical prayer and control fragments retain their prior sequence.
- Rendering metadata: fragment hash and job content hash change when the welcome is present.

### Rollout Notes
- No migration, feature flag, or bulk regeneration is needed. Future job generation produces a new content hash and refreshes affected episode audio.

### Not In Scope
- Changing existing prayer-specific intro copy, body providers, non-prayer shows, or already published audio files.
