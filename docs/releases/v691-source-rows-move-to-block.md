# v691 — Daily-source rows can't move blocks: the cross-block move joins their menu

## §1 Scope

**Field report (John, 2026-11-26 08:30 CT):** the Daily Gospel Exegesis row's ⋮ menu in the Edit form carries Move up · Move down · FREQUENCY (Daily · Sundays only · Fridays only) · Remove — but **no "Move to block…"**, the cross-block move contents items have carried since v686. The exegesis stands in Midmorning as a Daily-source representation row; the v687 source-row menu was built without the cross-block act. John's words (relayed with the field report): the Daily Gospel Exegesis row's menu has "NO 'Move to block…'". v687 §1.3 C-687-3 already names the standing line this release reverses for the rows that can take it: "daily-source rows get no Move-to-block (§2.7)".

**Run level: To Ship** (streamlined). Base: `main` at `19cc5c2` (the v688 tree). Branch `release/v691`, worktree `~/workspace/.worktrees/v691` off the one standing clone. Holder: chain-v691. All line citations are `app/worker/src/client.ts` / `index.ts` at base unless named otherwise.

### §1.1 The fix shape

1. **The source-row ⋮ menu gains "Move to block…"** — for every source-representation row whose cross-block move composition can honor (§2.3's table names each row: TAKES or REFUSES). The act opens the standing v686 picker sheet (§2.6) and moves the row's representation item to the **end** of the target block's list, exactly as a contents item moves.
2. **The move is a dual write** (§2.2): the contents item moves through the standing Move machinery **and** the source-settings store row's `block` field moves with it. A contents-only move composes nothing in the target block and silently drops the source from its home block — §2.2 grounds this from the composition walk; the dual write is the release's core, not an embellishment.
3. **A refused row paints its reason in the menu** where the act would stand (a disabled "Move to block…" item + the reason line under it) — no dead item, no silent absence, per the no-dead-item rule that governed v687's C-687-5.
4. **Frequency and standing settings travel**: the store row carries `dayRule` + `enabled` unchanged through the block change (the same whole-table write that already carries them, §2.2); the contents item object moves whole.

### §1.2 Boundaries

**IN:** `opnOpenSourceMenu687` (the source-row menu) · a source-move wrapper beside `opnMove686` · `opnSaveSourceSettings686`'s store write carrying the moved row's new `block` · `opnSpliceSourceRows686`'s per-block row set (it must follow the store row's standing block, §2.6) · the picker sheet's block set for source acts (the six hour blocks only, §2.6) · harness-v691 + the harness-v687 regression.

**OUT — unchanged, named:**
- **Within-block move stands exactly as v687 built it**: ▲▼ on the row and Move up / Move down in the menu, both riding `opnMove684` on the representation item (§2.1). No seat, handler, or boundary rule changes.
- **Every other v687 act stands**: Frequency (menu pick via `opnSetSourceDay686`), Remove (non-pinned rows, `opnRemove604` on the representation), Disable/Enable (pinned rows via the store write; office contents items via the `off` flag), the toggle, the subtitle, the row dress.
- The contents items' own Move to block… (`opnOpenMoveMenu686` → `opnOpenMovePicker686` → `opnMove686`) — no change; source acts join its machinery, they do not fork it.
- The closing "Mass and Homilies" section's membership, order, and acts (§2.3: the act does not apply there).
- What a day composes for any list nobody moved (the byte-identical gate, §2.6).
- The resolver gates themselves: `enabled` + `dayRule` stand as the store row's fields; only the row's `block` field gains a second writer.

### §2.2 The Move machinery — and what stands in a source row's way

**The standing machinery (v686 §2.6, as shipped and repaired):**

- `opnMove686(fromBlock, rowId, toBlock)` (client.ts:24550): occurrence-walk resolution of the addressed copy (`opnParseRowId610` + the `opnTodayItemId594` walk over `opnMaterialize604(fromBlock)` — the Remove discipline); the duplicate-office refusal **before** any list change (a `kind:'source'` item whose key is in `EXT_TOKENS` and already stands in the target returns `{ok:false, reason, sub}` — "<Hour> already stands in <Block>." / "An office hour stands once in a block — remove it there first, or pick another block."); snapshot of both lists; the item splices out and **pushes whole onto the end** of the target list; persist via `opnWrite604(fromBlock)` under the Move flag; a failed persist restores both snapshots whole and surfaces the failure.
- **The write envelope**: while a Move write stands in flight, `opn686MoveWrite`/`opn686MoveBlocks` ride `opnWrite604` (client.ts:24247) — the flag keeps both scopes' non-core drops from deleting the Move's two lists, and the envelope `move686: {from, to}` rides the request body itself: `profPut('/api/prayer/profiles/today-edit', body686)` in today scope, `profPut('/api/prayer/profiles/save', payload)` in standing scope.
- **The validator seats** (all three, plus the read seat):
  1. Client mirror `opnCheckContents590(contents, coreBlocks)` (client.ts:3035): refuses a contents entry for a block outside `coreBlocks` **unless** the Move flag stands and the block is one of the envelope's two; item rebuild keeps `{kind, key, side?, off?}` (off scoped to the labeled slots).
  2. Server `validateProfileContents(contents, coreBlocks)` (index.ts:1357) behind the wrapper `validateProfileContents686(contents, coreBlocks, extraBlocks?)` (index.ts:1476), with `parseMoveEnvelope686(raw)` (index.ts:1468) admitting the envelope only when `from`/`to` are two distinct members of the six hour blocks (`Morning · Midmorning · Midday · Afternoon · Evening · Night` — **Novenas is not a legal Move target at any seat**). The save route (index.ts:5420 ff) and the today-edit twin (index.ts:5333 ff) both parse the envelope and pass `[from, to]` as the wrapper's extra blocks — a Move-written list for a non-core source or target block stands, for that request only.
  3. **The store re-validation** (v686 Review repair, the read seat): `prayerProfileStore` (index.ts:1307) re-validates stored contents on every read with `storedExtra686` — the non-core blocks the record itself carries — so a persisted Move is not dropped by the next read.
  - Item-shape rule that matters here: the validators accept `kind:'source'` with any non-empty key, and `kind:'seat'` only with key `daily-readings`; the dedupe exception (duplicates stand) covers only the eight office slots — **a second copy of `ext-gospel-exegesis`, `ext-saint-of-the-day`, or the seat item in one list is silently deduped away** (both validators, same literal list). §2.6's wrapper therefore carries its own already-stands refusal for the rows it moves.

**What a cross-block move writes for a CONTENTS item:** the item object, whole, leaves the source block's stored contents list and stands at the end of the target block's stored contents list — nothing else. Composition follows because a contents item's descriptor legs (course/day/daily/episode/video/prayer, and the gated-source candidate walk below) resolve **per block from that block's contents list**.

**The source-representation row's underlying item.** A source row is not a contents item of its own kind: `opnSpliceSourceRows686` converts a standing contents entry into the row (`t:'s'`, carrying `repRid` = the entry's occurrence-qualified rid). The representation item is:

- for a gated slot row: **`{kind:'source', key:'ext-<slot>'}`** — the inverse of `OPN686_SLOT_ROW` (client.ts:24349): exegesis = `source:ext-gospel-exegesis`, Saint of the Day = `source:ext-saint-of-the-day`, the Office hours = `source:ext-<hour>`. (`opn687RepIds687` enumerates exactly these ids per source key.)
- for the readings: **`{kind:'seat', key:'daily-readings'}`** (the seat item converts in preference to a stray `source:ext-usccb-readings`, v687 §2.5 precedence).
- A row whose representation does **not** stand in the list splices in by standing rank with **no `repRid`** — there is no item to address.

**How v687's within-block ▲▼ moves it:** `opnMove684(block, rowId, dir)` (client.ts:24321) — the same occurrence walk, a swap with the neighbor in the materialized list, persist through the standing `opnWrite604(block)` (no Move flag, no envelope: both lists already stand inside one block). The swap moves the playing seat because the composition walk emits a gated candidate **at its contents item's index** in that block.

**What stands in the way of the same path across blocks — the gate is not the contents list.** `extRebuildDescs` builds each block's candidate set (`merged`, client.ts:21210 ff) from the **standings** — `state.ownStanding` / `state.extStanding` filtered by `s.block === b.block` — and the server builds those standings from the **source-settings store rows**: each slot's payload entry carries `block: row.block || EXTERNAL_SLOTS[cs.slotId]` (index.ts:2285/2315/2335 — the store row's `block`, the fixed table only as fallback). The contents pass then gates: a candidate stands in a block only when a contents selector names it **in that block's list** (`merged.filter` via `selIdx590`, client.ts:21229 ff), and emits at that item's index. Consequences for a contents-only cross-block move of, e.g., `source:ext-gospel-exegesis` from Midmorning to Evening:

- In Midmorning's walk the candidate is filtered out (no selector names it there any more) — it stops playing at home. ✓ (the intended half)
- In Evening's walk the candidate **is not in `merged` at all** (its standing block is still Midmorning) — the moved item's `emitCand619(idx)` finds no candidate and emits nothing; the item is inert in its new list.
- Net: **the source vanishes from the composed day whole** — the forbidden silent loss. The contents envelope and validators are *not* the obstacle (a `source` item with any key validates in any hour block at every seat above); the obstacle is that composition seats a gated source by its **store row's block**, and no contents write touches that field.

**The way through — the dual write.** The store row's `block` is a standing, writable field: `opnSaveSourceSettings686` (client.ts:24537) PUTs every row as `{sourceKey, block: r.block, dayRule, enabled}` to `/api/player/source-settings` and reads back. So the cross-block source move = the standing contents move (`opnMove686`, envelope and all) **plus** setting `opn686Row(key).block = toBlock` and the whole-table settings write. After both writes: the slot's standing block is the target (server payload + client standings follow the store row), `merged` for the target block carries the candidate, the moved contents item names it there, and it emits at the item's index — the end of the target list, where `opnMove686` pushed it. Frequency/enabled travel because they ride the same row object through the same PUT, untouched. §2.6 prescribes the wrapper, its order, and its failure restore.

### §2.4 The readings fold — ruling (b): the readings row REFUSES

Grounded in the code, the fold does **not** follow the item:

1. `foldReadingsSeat(descs, seat)` (client.ts:14480) splices the readings descriptor **immediately before the Morning `daily-rosary` descriptor** — it searches `descs` for `block === 'Morning' && episodeId === 'daily-rosary'` and knows no other anchor. No Rosary standing in Morning → no seat.
2. The v687 contents-pass seat is Morning-locked in the same way: the pass records the seat position only when `b.block === 'Morning'` (client.ts:21394, `seatPos687`), and the descriptor it stands is `readingsSeatDesc549` (client.ts:14470), which hardcodes `block: 'Morning'` on the descriptor itself.
3. So if the seat item left Morning's contents for another block: Morning's pass records no seat (`placed619.seat` stays false), `foldDayAdditions` runs `foldReadingsSeat` on both exits (client.ts:14520/14534), and **the readings still compose immediately before the Morning Rosary** — provided the Rosary stands. The playing seat does not move one inch; only the Edit row would repaint in the target block (as an unconverted contents row there, since `OPN686_BLOCK_ROWS` for the target block carries no readings key). The act would paint a move and play nothing — the exact dead act the no-dead-item rule forbids.

**Ruling: (b).** The readings row REFUSES the cross-block move; its menu paints the disabled act + the reason where the act would stand: **"The readings stand before the Daily Rosary in Morning."** Option (a) — teaching the fold a new anchor — is not prescribed: the fold's anchor is the Rosary in Morning by John's standing rule (v549 Q5, re-grounded v660/v687), and re-anchoring it is a composition change beyond this release's field report. No third, silent outcome is built.

### §2.5 The pinned rows — ruling: all five REFUSE

What a cross-block move of the Invitatory representation would mean to composition, grounded: mechanically, the dual write *would* carry it — its candidate would leave Morning's `merged` (store block changed + selector gone) and emit in the target block at the moved item's index. The refusal is therefore a **rule**, stated as a rule, not dressed as an impossibility:

- Each pinned row **is its block's hour**. The slot's title names the hour of the block it stands in ("Midmorning Prayer" · "Midday Prayer" · "Midafternoon Prayer" · "Night Prayer"), and the Invitatory is the opening psalmody of Morning Prayer — it stands in Morning because Morning is where the Office it opens is prayed. A "Midmorning Prayer" descriptor composed inside Evening would carry a title that contradicts its block on its face.
- The server's own fallback table names the same binding: `EXTERNAL_SLOTS[slotId]` (index.ts:892 ff) gives each Office slot its hour's block, used whenever a store row's block is absent — the system's default picture of these slots is block-bound.
- John's v687 amendment granted the pinned rows **within-block** move ("Make the pinned source rows movable too", in the Edit seat) and withheld Remove, giving Disable instead — the pin's meaning is *fixed to its hour, ordered within it*. Cross-block move is a stronger unpinning than the Remove he withheld; this Plan does not take it on a field report about the exegesis row.

**Ruling:** the five pinned rows (`OPN687_PINNED`, client.ts:24354) REFUSE the cross-block act, each painting its §2.3 reason in the menu where the act would stand. Their within-block ▲▼, Disable/Enable, Frequency, and toggle stand untouched. If John wants an Office hour portable across blocks, his word re-opens this ruling — the machinery (§2.2) already carries it, so the follow-on is a menu change only.

### §2.6 The prescription — the exact build

1. **Menu item** — in `opnOpenSourceMenu687` (client.ts:24675), after the Move up/down items and before `opn687FreqItems(key)` (the contents menu's relative seat, §2.1):
   - TAKES rows (`daily-gospel-exegesis` · `saint-of-the-day` · `do-office-of-readings`) **with a standing `rid`**: `{label:'Move to block…', act: function(){ opnOpenMovePicker686(block, rid, key); }}`.
   - REFUSES rows (the readings + the five pinned): `{label:'Move to block…', disabled:true}` followed by `{head:true, label:<the §2.3/§2.4/§2.5 reason>}` — the reason paints in the menu where the act would stand (`openSheetMenu` already carries the `disabled` and `head` item flags, v687).
   - Rows without a standing `rid`, and closing rows: no item (standing absence rule, §2.3).
   - The TAKES/REFUSES sets stand as two named literals beside `OPN687_PINNED` (e.g. `OPN691_MOVE_OK` / a reason map `OPN691_MOVE_REFUSAL`) so the harness can read them and a future row kind must be classified to paint.
2. **Picker** — `opnOpenMovePicker686(fromBlock, rowId, sourceKey?)` gains the optional third argument. Contents callers pass nothing and get today's sheet byte-for-byte. A source caller gets: rows = the **six hour blocks** in `opnPaintBlocks686` order filtered to the envelope's HOURS set (Novenas never listed); disabled blocks greyed + "· Off" named and **tappable** (the C3 envelope carries them); the current block marked "Here" and inert — the v686 §2.6 shape, unchanged. A tap calls the source wrapper (step 3) instead of `opnMove686` directly; refusal/failure keeps the sheet open with its reason + sub lines, as today.
3. **The act — a wrapper beside `opnMove686`**, `opnMoveSource691(fromBlock, rowId, toBlock, key)`:
   1. **Already-stands refusal, before any write:** if the target block's materialized list already holds this row's representation id (`opn687RepIds687(key)`), return the refusal in the picker's shape — reason `"<Name> already stands in <Block>."`, sub `"It stands once in a block — remove it there first, or pick another block."` (the validators would otherwise dedupe the moved copy away silently, §2.2). For the Office of Readings, `opnMove686`'s standing duplicate-office refusal already returns this shape — the wrapper's check covers the two non-office TAKES rows; one check for all three is the simpler build and is prescribed.
   2. **Store write first:** snapshot `row.block`; set `opn686Row(key).block = toBlock`; `opnSaveSourceSettings686()` (whole-table PUT + read-back, standing). If the read-back does not carry the new block, restore `row.block`, repaint, and return `{ok:false, reason:'That move did not save.', sub:'Try again.'}` — no contents write attempted.
   3. **Contents move second:** `opnMove686(fromBlock, rowId, toBlock)` — standing machinery, envelope and all; the item pushes whole onto the end of the target list. If it resolves `{ok:false}`, roll the store back (restore `row.block`, `opnSaveSourceSettings686()` again) and pass the failure through to the picker. `opnMove686`'s own failure path has already restored both lists.
   4. Success = both writes read back: the settings read-back carries the new block, and the contents write's `done` path has repainted + rebuilt — the composed day seats the source at the end of the target block.
4. **The splice follows the store** — `opnSpliceSourceRows686`'s row set stops reading the static `OPN686_BLOCK_ROWS` map and derives from the standing rows: the keys whose `opn686Row(key).block === block` among the `OPN686_SLOT_ROW` values + `usccb-daily-readings`, in standing-rank order (the splice's own rank machinery already orders conversions/splices; the derivation changes only *which* keys a block claims). Without this, a moved exegesis row repaints spliced into Midmorning by rank (its static key still stands there) while its item paints unconverted in the target block — the v687 duplicate class all over again.
