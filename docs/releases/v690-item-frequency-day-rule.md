# v690 — Item frequency: the day rule on every contents item

## §1 Scope

**Direction (John, 2026-11-26 08:29 CT, verbatim):** "Exfend daily, Friday,.Sunday option to all.items. Will dictate if an item paints or not. For example, I can use for stations of the corss or homilies. But can be used generically"

**Reading of the direction (the Plan's, stated for correction):** the frequency options that today stand only on the Daily-source rows — the source-settings rows whose `dayRule` offers Daily · Sundays · Fridays (and the wider standing set, §2.1) — extend to **all contents items**. Every contents item can carry a frequency (a day rule). The frequency **dictates whether the item paints on a given day**: an item whose rule does not match the presented day does not stand in the composed day at all. John's named uses: Stations of the Cross on Fridays only · a homily item on Sundays only. The mechanism is **generic** — it is not Stations-specific or homily-specific; it stands on every kind of contents item (§2.5).

**Base:** remote `main` at `19cc5c2` (v688 ship record; production pin `ora-pro-nobis-v688-1`). Branch `release/v690`, worktree `~/workspace/.worktrees/v690` off the one standing clone. Holder: chain-v690-plan · contract 1190. All line citations are `app/worker/src/client.ts` (client) or `app/worker/src/index.ts` (server) at base unless named otherwise.

### §1.1 What ships

1. **A `dayRule` field on the contents item** (§2.2), carried through both contents validators, both Edit-form builders, the today layer, and profile save/load round-trips. Absent field = `daily` (paints every day — today's behavior for every standing item).
2. **A composition gate** (§2.3): in every walk that composes a day from contents, an item whose rule fails the presented day does not paint, is not counted by the section counts, and cannot be queued by block Play. It **still stands in the Edit form**, with its frequency subtitle visible — the form is where the rule is seen and changed.
3. **The control** (§2.4): the ⋮ menu's Frequency pick — today standing only on source rows (v687) — extends to **every** contents item, showing the current value. The row subtitle paints the frequency in small letters, in v687's source-row form ("Generates daily" and its per-value family, §2.4).
4. **Kind-by-kind composition** (§2.5): the item rule composes with each kind's own day machinery (the daily kinds' per-day resolution, the office slots' resolution, the v677 settled picks) under one named rule — the item gate runs **first and outermost**; no kind is silently excepted.

### §1.2 Boundaries

**IN:** the contents item shape + its two validators (client `opnCheckContents590` · server `validateProfileContents` / `validateProfileContents686`) · the Move-envelope write path's carriage (the field rides the item object; no envelope change) · both Edit-form builders (`opnEditGroupHtml609` · `opnEditPostureHtml604` via `opnExpansionHtml604`) and the contents-row builder `opnContentsRowHtml687` · the today layer (`opnApplyTodayLayer594` client · the `profileFoldOf` today-layer merge server) · profile save/load round-trips · the client composed-day walk (`extRebuildDescs` + `foldReadingsSeat` via `foldDayAdditions`) · the server-side contents consumers in the day payload (`profileFoldOf` fold · `dayAdditionsFold`'s contents-prayer synthesis) · the ⋮ menu (`opnOpenMoveMenu686`) + a contents-item frequency writer modeled on `opnSetSourceDay686` · the new harness `app/worker/harness-v690.mjs`.

**OUT, named:** no change to the source-settings rows' own `dayRule` system (the store rows, `OPN_SEED_SOURCES`, the source-settings PUT, `opnSetSourceDay686`) — this release adds the **item-level** rule beside it; where a contents item *represents* a source row, §2.5 names the double-gate and its resolution · no new day-rule values (§2.1: the item offers exactly the standing set) · no new predicate (the gate calls the standing `extDayRulePasses`, §2.1) · no change to the Add ladder (an added item starts `daily`; its frequency is set in the Edit form) · no migration (contents ride the profiles' layers JSON, as `side`/`off` already do) · no APK work.

## §2 Plan

### §2.1 Vocabulary — the standing dayRule set, exactly as the code holds it

**The set (no invented values).** Both validators hold the identical closed list:

- Client: `OPN_DAY_RULES = ['daily', 'weekdays', 'weekends', 'sundays', 'fridays', 'fallback-only']` (client.ts:1434), enforced on source-settings writes at client.ts:3959.
- Server: `DAY_RULES = ["daily", "weekdays", "weekends", "sundays", "fridays", "fallback-only"]` (index.ts:1969), enforced at index.ts:6286.
- The seed rows instantiate only three of them: `daily` (most rows), `sundays` (`fr-mike-homily`, `barron-sermon`), `fridays` (`stations-of-the-cross`), plus `fallback-only` on the two Sing the Hours fallback rows (`sth-lauds`, `sth-vespers`) — all in `OPN_SEED_SOURCES` (client.ts:2771). **No `saturdays` value and no first-Friday (or any first-‹weekday›) shape exists anywhere in the code** — neither in the lists, the seeds, nor the predicates. None is added.

**The predicate (reuse, not a new one).** `extDayRulePasses(rule, wd)` stands in both files with identical semantics — client.ts:18819–18826, index.ts:2289–2297. `wd` is Monday=0 … Sunday=6 (client `extWeekdayMon0`, client.ts:18815; server computes the same `(getUTCDay()+6)%7` inline):

| Value | Passes when |
|---|---|
| `daily` | always |
| `weekdays` | `wd < 5` (Mon–Fri) |
| `weekends` | `wd >= 5` (Sat–Sun) |
| `sundays` | `wd === 6` |
| `fridays` | `wd === 4` |
| `fallback-only` | **never** through `extDayRulePasses` (returns `false`); it passes only through the separate fills test — client `extDayRuleFills` (client.ts:18827), server inline at index.ts:2916 / 6153 |

**Prescription.**
1. The item frequency offers exactly the five paint values — `daily · weekdays · weekends · sundays · fridays`. **`fallback-only` is excluded from the item offer, named:** it is not a paint rule but the fallback-row marker (a primary row carrying it never passes, per the index.ts:2290 comment); offering it on an item would be a silent never-paint trap indistinguishable from a bug. It remains valid in the stored vocabulary (§2.2's validators accept the full standing set, so no stored shape is ever refused) — it is simply never offered by the item menu (§2.4).
2. **The item gate calls `extDayRulePasses(item.dayRule || 'daily', wd)`** — the client twin in the client walk, the server twin in the server folds (§2.3). No new predicate, no second weekday convention.

### §2.5 Kinds — how the item rule composes with each kind's own day machinery

**The composition rule (one, no silent exceptions):** the item gate is **outermost and first** — an item whose rule fails today resolves nothing, fetches nothing, settles nothing, and paints nothing, whatever its kind's machinery would have done. Where a kind *also* has a per-day mechanism, the mechanisms **AND**: the item paints only on days both admit. No kind's machinery is modified.
