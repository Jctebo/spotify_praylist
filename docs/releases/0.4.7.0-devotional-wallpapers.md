## Scope

### Problem
- Add an independent daily phone/watch wallpaper pipeline with repository-owned OneDrive rotation. Keep the existing infographic pipeline and its web publishing active and unchanged.
- The initial weekly proposal is superseded: daily run checks today and the next nine dates (10 dates total), filling gaps without regenerating existing images.

### Audience
- Primary user: the operator using devotional phone backgrounds and Galaxy Watch backgrounds.
- The release includes OneDrive rotation only. The operator owns local synchronization and phone/watch rotation separately.

### Current Status Quo
- The existing workflow generates subject/window-based infographics, duplicates the approved portrait asset into the wide path, maintains current/archive folders, synchronizes through rclone, and deploys a public image tree alongside the prayer site.
- This does not provide independently composed, date-specific phone/watch wallpapers.

### Goal
- Resolve one subject for each target date from Outlook Devotion ICS; use an eligible calendar feast/private devotion first and the target month's built-in devotion only when no eligible event exists.
- Generate each missing date/variant independently: normally two new images daily, at most twenty initially for an empty ten-date window.
- Existing date/variant images in the corresponding current or queue folder count as present regardless of prompt/model/calendar changes. Never automatically overwrite them.
- Deliver new JPEGs through the existing rclone connection into `watch-queue` and `phone-queue`. A separate repository-owned rotation stage promotes the correct date into `watch-current` and `phone-current`, preserving existing artwork bytes.
- Success: all ten dates have both variants present or an explicit actionable failure; a repeated successful run generates/uploads nothing; existing artwork bytes are preserved; only the rotation stage changes live current membership.
- Run the new wallpaper workflow alongside the existing infographic workflow. Their calendar sources, entrypoints, folders, manifests, and operational state must remain separate.

### Constraints
- Reuse `RCLONE_CONFIG_B64`, `RCLONE_REMOTE_NAME`, and `RCLONE_REMOTE_ROOT`; local execution reuses the existing rclone profile. Do not introduce another OneDrive integration.
- Own both filename production and rotation parsing: use full ISO dates and explicit variant identity; migrate only recognized existing files without guessing dates.
- Chicago-local date arithmetic across DST, month, leap-day, and year boundaries.
- Independently composed 1024x1024 watch and 1080x1920 phone JPEGs. Never derive one device composition from the other.
- Mary references define the large centered white serif title and smaller subtitle; Eucharist references define crisp detail, rich material rendering, luminous light, and depth. Phone composition leaves calm launcher space; watch lettering and important iconography must survive circular masking.
- Feast/private-devotion classifications remain explicit and accurate. Repeated subjects may vary composition and devotional subtitle without mislabeling classification or sequence day.
- Render exact text deterministically after artwork generation; retain private provenance and QA evidence outside Gallery folders.
- Public ICS URL stays secret-managed and redacted. A failed calendar read must not silently turn every date into a monthly fallback.

### Domain And Calendar Contracts
- `AssetKey = (target_date, variant)`; subject/title changes never invalidate an existing asset. `DailyImageSpec` records source identity, title, classification, sequence, optional subtitle, iconography, fallback month, and feed checksum.

- Ten Chicago-local dates inclusive; month/year/DST/leap boundaries are date arithmetic. Empty bootstrap needs at most twenty initial renders; ordinary runs usually need two. Process missing slots earliest first.
- Inventory queues, current folders, and managed archive by key. Reuse verified accepted staging after interruption. Never infer a year from legacy MM-DD window names. Unknown/ambiguous files are reported, never overwritten or automatically deleted.
- Own the new filename convention `<slug>__YYYY-MM-DD.jpg`; queues are grouped into ISO-date subfolders and current folders remain flat for consumers. Existing flat ISO-date files can be recognized and retained; rotation uses discovered paths rather than requiring bulk migration.
- Add pinned compatible `icalendar`, `recurring-ical-events`, and `tzdata`; expand only the bounded window. Respect all-day exclusive DTEND, timezone dates, exceptions/cancellations, and occurrence identity rather than rejecting all repeated UIDs.
- Fetch HTTPS with bounded redirects/body (10 MiB), 10/30-second connect/read timeouts, at most three transient attempts, and URL-redacted errors. Failed fetch/parse must never become monthly fallback.
- Parse the observed title convention deterministically: case-sensitive [F]/[M]/[m], explicit classification suffixes, private-devotion marker, Triduum/Octave and Day n. Strip emoji/rank decorations from display titles. Recognized ordinary weekday/Sunday context does not compete. Do not derive candidates from personal prose descriptions. ### Additive Generation Delivery
- Use subprocess argument arrays, validated paths and fixed folders. Reuse `RCLONE_CONFIG_B64`, `RCLONE_REMOTE_NAME`, `RCLONE_REMOTE_ROOT` and existing local profile; never reuse legacy blind live-folder sync.
- Fail on inventory permission/listing errors. Existing occupied slots suppress generation regardless of render version; unreadable occupied files are reported rather than overwritten.
- Save and verify accepted staging under the private operational root before queue delivery. Recheck key before adding, use explicit no-overwrite guards, and verify bytes by readback/SHA-256 when backend hashes are incompatible. A skipped copy is not proof of successful delivery.
- Partial delivery keeps verified additions and resumes only missing slots. No twenty-file transaction, no automatic whole-folder restoration. Generation does not alter current membership; the rotation component is its sole owner.

### Rotation Design (OneDrive execution confirmed)
- A distinct `rotate_current(date)` stage runs before any paid generation and again afterward only if today's previously incomplete pair is now ready. It can run alone without calendar or model credentials.
- Recommended trigger: 00:15 America/Chicago daily using a timezone-aware schedule; generation follows rotation. Delayed jobs use actual Chicago date and jump straight to today, rather than replaying obsolete days. Manual `--run-date` controls generation only; live rotation defaults to actual today to avoid publishing a future wallpaper accidentally.
- Require both today's verified watch and phone assets before beginning. If either is absent, retain the last complete current pair, report stale current and missing variant, and prioritize filling today's gap. Never promote a future image or silently mix dates. If no prior pair exists, leave current empty until both are ready.
- Prepare: record current listings/hashes, verify next pair, copy prior pair into `.devotional_wallpapers/archive/<prior-date>/`, and verify archive. Keep a durable per-operation journal before live mutations. Only manage files recorded as pipeline-owned; unknown current files block rotation pending explicit adoption, not deletion.
- Commit: copy today's dated files into current without overwriting prior filenames; verify both; remove only the journaled previous current files after their archives and replacements are verified; verify final membership is exactly today's pair. Then publish a committed manifest pointer/snapshot and remove only verified consumed queue copies. Prior art stays archived without automatic expiry in this release.
- Queue cleanup is limited to consumed verified files and empty pipeline-owned date directories. Missed past queued dates remain preserved and are not promoted; broad retention cleanup is out of scope.
- This is a recoverable multi-step operation, not an atomic swap of two OneDrive folders. Folder-sync consumers may briefly observe overlap or mixed dates; a manifest-aware consumer must use only the committed pair. Document the committed manifest as the stable handoff boundary; any device-visible switching behavior belongs to the operator-owned local process.
- Recovery: inspect journal and actual bytes, finish a valid promotion or restore the previous verified pair; never overwrite conflicting unknown files. On unverifiable state stop mutation, keep archive/staging, and produce exact recovery instructions. Rerun after committed rotation is a no-op.
- Single writer: generation and rotation share a fixed Actions concurrency group with `cancel-in-progress: false`; disable competing OneDrive writers before activating the new rotator; retain the independent local rotator. Local live mutation requires scheduling the CI job off. A copied remote lock file is not treated as an atomic distributed lock.
- Rotation success and generation completeness are separate status fields. A wallpaper model outage must not prevent an already queued pair rotating or affect infographic/audio/site pipelines.

### UX And States
- No new product UI. Workflow summary shows rotation date/current date, generated/skipped/missing counts and recovery instructions. No Todoist.
- Modes: resolve-only, delivery-disabled preview, generation-only, rotate-only, resume-run, dry-run rotation. Dry runs show exact additions/removals without mutation. Live manual rotation defaults to today; historical/future previews cannot mutate live current folders.
- All assets existing means no generation; rotation may still be required. Calendar/model failure blocks generation only. Missing today's pair means last complete current remains, with a stale-date warning.
- Cloud folder promotion does not itself change Android wallpaper settings or install a Galaxy Watch face. The release verifies remote folder contents and publishes their contract; local device consumption and installation remain operator responsibilities, not release gates.
