## Scope

### Problem
- The active scheduled workflows currently start in a 02:00-02:30 CST / 03:00-03:30 CDT window.
- That is later than the desired "ready by midnight" cadence for daily automation.
- The pain is timing, not job behavior: the workflows mostly do the right work, just too late in the night.
- GitHub Actions cron is UTC-based, so the current schedule also hides the local-time shape of the automation.

### Audience
- Primary user: the maintainer who wants the repo's automated outputs to feel ready at the start of the day.
- Secondary stakeholders: anyone consuming the daily Spotify playlists, devotional images, Notion resets, or liturgical exports early in the morning.
- Secondary stakeholders: future maintainers who need the schedule layout to be obvious and easy to reason about.

### Current Status Quo
- `.github/workflows/daily.yml` runs the Spotify refresh at `08:05 UTC` and only executes on schedule when `SPOTIFY_REFRESH_SCHEDULE_ENABLED=true`.
- `.github/workflows/daily_notion_reset.yml` runs at `08:00 UTC`.
- `.github/workflows/daily_devotional_image_remote.yml` runs at `08:15 UTC`.
- `.github/workflows/liturgical_calendar_yearly_sync.yml` runs on Jan 1 at `08:20 UTC`.
- `.github/workflows/publish_liturgical_ics.yml` runs on Jan 2 at `08:30 UTC`.
- Manual `workflow_dispatch` entrypoints still exist on several workflows, and the disabled novena workflow stays out of the active schedule.
- The job bodies do not appear to need these late start times; the spacing is mostly historical.

### Goal
- Move the active scheduled workflows into a midnight-local startup window.
- Keep the jobs staggered so they do not all start in the same minute.
- Preserve each workflow's behavior, inputs, outputs, and manual dispatch behavior.
- Make the automation feel anchored to the start of the day instead of the middle of the night.

### Constraints
- GitHub Actions cron expressions are UTC-based and do not account for daylight saving time.
- Exact midnight year-round is not possible with a single static cron expression in Central time.
- Some workflows are annual and must still land on the intended January calendar day.
- Existing schedule gates, especially `SPOTIFY_REFRESH_SCHEDULE_ENABLED`, should remain intact.
- Manual `workflow_dispatch` triggers should not be broken.

### Narrow Wedge
- Change only the cron expressions for the active scheduled workflows.
- Keep the same workflow files and job bodies; do not rewrite the automation logic.
- Stagger the current active schedules into a compact midnight-ish window instead of introducing an orchestrator.

### Non-Goals
- Rewriting job internals or changing what any workflow produces.
- Unifying all workflows behind one controller job.
- Changing manual workflow dispatch behavior.
- Reviving the disabled novena workflow.
- Solving daylight saving time with dynamic cron logic beyond the selected schedule window.

### Risks And Unknowns
- A single UTC cron cannot hit exact midnight in both CST and CDT, so the result will be "around midnight" rather than perfectly exact all year.
- Tight staggering could create temporary contention if two workflows hit external services at the same time.
- The annual January workflows may need a slightly different offset so they still land on the intended date in both time offsets.
- It is not yet confirmed whether every active scheduled workflow should move to the same midnight window or whether one or two should stay later.

### Recommended Next Step
- Run `/research-astack` to validate the exact set of active scheduled workflows, confirm the local-time target window, and map any cron collisions before changing schedules.

## Research

- **Scope Baseline**
  - Shift the active scheduled GitHub Actions workflows from the current 08:00-08:30 UTC band into a midnight-ish Central time window.
  - Preserve behavior, stagger, and manual dispatch paths; this is a scheduler-only change.

- **Relevant Files**
  - `.github/workflows/daily_notion_reset.yml` - current 08:00 UTC daily Notion reset cron.
  - `.github/workflows/daily.yml` - current 08:05 UTC Spotify refresh cron plus the `SPOTIFY_REFRESH_SCHEDULE_ENABLED` gate.
  - `.github/workflows/daily_devotional_image_remote.yml` - current 08:15 UTC devotional-image cron.
  - `.github/workflows/liturgical_calendar_yearly_sync.yml` - current Jan 1 08:20 UTC yearly sync cron.
  - `.github/workflows/publish_liturgical_ics.yml` - current Jan 2 08:30 UTC yearly publish cron.
  - `README.md` - documents the current schedule times and should be updated when the cron window moves.
  - `docs/releases/0.1.5.0-midnight-job-start-window.md` - canonical release artifact that should keep the schedule assumptions in sync.

- **Current System Map**
  - The active scheduling surface is five independent GitHub Actions workflows, each with its own cron trigger.
  - There is no shared orchestrator or dependency chain between these scheduled jobs.
  - `daily.yml` is the only scheduled workflow with an explicit gate that can suppress schedule runs.
  - The manual `workflow_dispatch` entries for the active workflows are separate from the schedule and should remain untouched.
  - The disabled novena workflow is not part of the active cadence and should stay off the schedule.

- **Reuse Opportunities**
  - Keep the existing workflow files and only edit their cron expressions and comments.
  - Reuse the current schedule order and relative spacing instead of inventing a new orchestration layer.
  - Reuse the existing README schedule table/notes format so the documentation change stays small.

- **External References**
  - GitHub Actions schedule syntax uses UTC cron expressions.
  - Central time comments in the repo already provide the human-facing interpretation of those cron values.
  - DST drift is an external platform constraint, not a repo bug.

- **Constraints**
  - Exact midnight Central time all year is not possible with a single static UTC cron.
  - The new schedule band should stay safely after the local date flips so daily jobs still target the intended day.
  - Annual January jobs must still land on their intended calendar day.
  - Schedule gates and manual dispatches must continue to behave exactly as they do now.

- **Risks**
  - A UTC cron that is too early could run before the local date changes in winter.
  - A UTC cron that is too late would defeat the purpose of the enhancement.
  - Tight staggering could create accidental overlap if external services are slow.
  - README and release notes could drift from the workflow files if the docs are not updated together.

- **Assumptions To Validate**
  - The intended target is "around midnight Central time", not exact midnight in every season.
  - Only the five currently scheduled workflows are in scope, not the manual-only workflows.
  - The January yearly jobs should keep their day-of-month and simply move earlier within that day.

- **Unknowns**
  - Whether the annual jobs should share the same minute offsets as the daily jobs or use a slightly different stagger.
  - Whether any of the active schedules should remain later than the rest for service-safety reasons.

- **Recommended Direction**
  - Move the five active cron triggers into a compact 06:00-06:30 UTC window, keep the existing workflow bodies intact, and update README commentary to match.

## Plan

### Summary
- Shift the active scheduled GitHub Actions jobs earlier so they start around midnight Central time instead of the current 02:00-03:30 window.
- Keep the workflow bodies unchanged and preserve the current stagger and manual dispatch behavior.
- This is the smallest useful change because the problem is when the jobs start, not what they do.

### What Already Exists
- Five independent scheduled workflows already cover the active automation surface.
- The daily Spotify refresh already has a schedule gate, so the schedule move can stay separate from enablement logic.
- README already documents the current schedule windows in human-friendly Central time comments.
- The disabled novena workflow and manual `workflow_dispatch` jobs already sit outside the active automated cadence.

### Architecture
- The system stays as five separate GitHub Actions workflows with independent cron triggers.
- There is no new orchestrator, queue, or shared scheduler layer.
- The only moving parts are cron expressions, inline schedule comments, and the README schedule notes.

```text
GitHub Actions cron (UTC)
  |
  +--> daily_notion_reset.yml          -> 06:00 UTC
  +--> daily.yml                       -> 06:05 UTC (schedule-gated)
  +--> daily_devotional_image_remote.yml -> 06:15 UTC
  +--> liturgical_calendar_yearly_sync.yml -> 06:20 UTC on Jan 1
  +--> publish_liturgical_ics.yml      -> 06:30 UTC on Jan 2
```

### Concrete Changes
- `.github/workflows/daily_notion_reset.yml`
  - change the cron from `0 8 * * *` to `0 6 * * *`
  - update the inline time comment to match the new Central-time interpretation
- `.github/workflows/daily.yml`
  - change the cron from `5 8 * * *` to `5 6 * * *`
  - keep the `SPOTIFY_REFRESH_SCHEDULE_ENABLED` gate untouched
  - update the inline time comment
- `.github/workflows/daily_devotional_image_remote.yml`
  - change the cron from `15 8 * * *` to `15 6 * * *`
  - update the inline time comment
- `.github/workflows/liturgical_calendar_yearly_sync.yml`
  - change the cron from `20 8 1 1 *` to `20 6 1 1 *`
  - keep the existing January 1 yearly cadence and update the inline time comment
- `.github/workflows/publish_liturgical_ics.yml`
  - change the cron from `30 8 2 1 *` to `30 6 2 1 *`
  - keep the existing January 2 yearly cadence and update the inline time comment
- `README.md`
  - update the schedule descriptions so the documented times match the new midnight-ish window
  - keep the manual dispatch and schedule-gate notes intact

### UX And States
- No UI surface changes.
- Loading, success, and error state are all workflow runtime concerns, not app states.
- The user-facing change is purely temporal: the same jobs will appear earlier in the day.
- Accessibility and responsiveness are not relevant to this slice.

- If the new window is too early, day-based jobs could resolve the wrong local date in winter.
