# v642 — Praylist set vanishes on a tab return (fix-forward)

## §1 Field report (John, 2026-11-23 19:44 CT, live v641 build, with screen recording)

"Praylist menu completely disappears. somerimes see video."

The recording (10.9 s, frames read by the coordinator) shows the round trip
twice: the Praylist stands whole (Morning / Midday / Afternoon groups,
Auxilium Christianorum playing, the dock standing) → Catechesis opens → back
to the Pray tab → **the block set is gone**: only the Daily profile card, the
Favorites card, and the counts line ("On this phone: today's prayers 20/21 ·
podcasts 33/33 · tomorrow's prayers 15/15") stand → seconds later the set
repaints whole. Intermittent ("sometimes").

The counts line standing in the empty frame is the diagnostic anchor: the
day's data stands on the phone. The defect is in the set PAINT on a tab
return, not in the data. It fires mid-session, vault unlocked — it is not
the v609 repair-2 locked cold-open shape.

## §2 Plan — the seam, named from the code (client.ts, base = v641-1 tree)

### The return path

Every Pray-tab entry runs the full day build from scratch:

`setTab('prayers')` → `renderPrayers()` → `paintMergedContainer('prayers')`
→ `paintTabSide` → `renderPrayersSide()`:

1. `view.innerHTML = skelHtml('prayers')` — the skeleton paint.
2. `api('/api/player/day')` → `buildDayFromPayload(day, null)`.

### The overwrite

`buildDayFromPayload` (line ~20326) builds `allDescs` from the payload alone
— `day.blocks[].tracks` + `day.episodes` through `expandDescs` — and assigns

```
state.dayDescs = foldDayAdditions(allDescs, ...)
```

then paints the home (`paintPrayersView` → `paintListenHome` →
`opnSetHtml609`, which paints **only** `state.dayDescs`, grouped by block).

On a client-composed day the payload's block tracks do not carry the
composed substance — it enters through the profile contents + settings rows
(the v609 repair finding, standing). So this first paint's list is the
payload-only fold: on John's day it stands empty of the set. The paint's
other furniture — `profPlanRowHtml` (the Daily card), the Favorites folder
row, `offlineLineHtml` (the counts line) — reads other state and stands
whole. Result: exactly the recording's frame — cards + counts, no set.

### The late repaint

The composed set exists only after the async resolution pass that
`buildDayFromPayload` dispatches *after* the paint: `resolveExternals`
awaits the settings read, seeds `state.extStanding` / `state.ownStanding`,
and `extRebuildDescs` (line ~18773) rebuilds `state.dayDescs` from the
standings + contents + slots and repaints. That leg carries the vault /
settings read and, on a cold or invalid day cache, the externals courier
fetch — seconds in the field. The set "comes back" when the first rebuild
lands.

### Why intermittent, and why the round trip

The empty paint is structural — it stands on every render, between the
payload fold and the first rebuild. It is *seen* only when the resolution
leg is slow enough (day cache invalid or pruned, a settings read, a courier
fetch) — hence "sometimes". A tab round trip is the reliable trigger
because `renderPrayersSide` re-runs the whole build on every entry and the
payload fold **discards the composed list already standing in
`state.dayDescs`** before painting; nothing on the return path consults it.

### The fix shape

1. **The composed list is the paint source of record.** `extRebuildDescs`
   is the one builder of the composed set. When it completes, the composed
   list stands keyed by its presented date. On a later build for the same
   presented day, the payload fold must not replace it before the paint:
   the home paint reads the standing composed list for the day, and the
   resolution pass's rebuild refreshes it exactly as today. (Mechanism is
   the Implement seat's: keep the composed list standing in
   `state.dayDescs` across the build's paint, or hold it in a
   date-keyed snapshot the paint consults — the harness judges the
   outcome, not the mechanism. The build's other consumers of the payload
   fold — `pushDaySnapshot`, `readTracks`, `refreshRepeatIds` — keep
   their standing inputs.)
2. **No composed list stands yet** (true cold open, or a new day): the
   set's place carries a plain loading state until the first rebuild
   paints the real set — never the empty set. The standing skeleton is
   the cold-open loading paint; a return with a composed list standing
   does not blank to it.
3. **A genuinely empty day stays truthful:** a day whose composed set is
   empty paints its true empty state once the resolution settles — no
   perpetual loading.
4. **The vault-locked discipline stands byte-for-byte in behavior:**
   `paintListenHome`'s locked branch substitutes the unlock gate before
   `homeBodyHtml` reads any list; the standing-set paint never bypasses
   it (the v609 repair-2 / harness-v609vault discipline).

### Harness — `app/harness-v642.mjs` (new)

World: John's exported document (production shape, the v609vault pattern —
real envelope, cold-opened), the day composed through the real resolution
pass so `extRebuildDescs` builds the set.

- **L1 (the round trip, fail-on-old):** the set paints whole → a tab
  return is simulated in the field's timing shape (the day fetch and the
  settings/resolution legs deferred) → the return's first home paint
  carries the standing set (or the loading state) — never the empty set;
  the deferred legs then complete and the settled paint is the full set.
  On the base tree the return's first paint is the empty set of the
  recording.
- **L2 (cold open):** no composed list stands — the set's place carries
  the loading state, not the empty set, until the first rebuild paints.
- **L3 (locked return):** the vault locked at the return — the unlock
  gate substitutes, exactly as harness-v609vault proves today.
- **L4 (true empty day):** a day with no composed set settles to its true
  empty paint — no loading state stands forever.
- Regressions: harness-v641 · v639 · v638 · v637 · v609vault — clean, or
  standing named sets only.

### Risks / edges (named)

- **Date rollover:** the standing composed list is keyed by presented
  date; a return after midnight Chicago must not paint yesterday's set —
  the date key governs, and a new day takes the L2 path.
- **Profile / contents change mid-session:** an edit-form save already
  re-resolves and rebuilds (`extRebuildDescs` repaints); the standing
  list is refreshed by that same rebuild — no stale-set window opens
  beyond the one the resolution pass already governs.
- **Queue identity:** the queue builds from `state.dayDescs`; keeping the
  composed list standing keeps paint and queue one source (the v609
  repair construction) — the payload fold never becomes the queue's list
  on a return.

## §3 Implement record (2026-11-23, Implement seat, contract 974)

### Seams changed — all in `app/worker/src/client.ts`

1. **State record (state initializer):** three v642 fields stand beside
   `dayDescs` — `composed642` (the composed list), `composedDate642`
   (its presented-date key), `dayPending642` (a build with no composed
   list standing), plus `rebuildGuard642` (below).
2. **`extRebuildDescs`:** every rebuild now records its result as the
   composed list of record — `state.composed642 = descs`,
   `state.composedDate642 = date`, `dayPending642` cleared — before
   its standing tail (`refreshRepeatIds` · `pushDaySnapshot` ·
   `settleTrackDraws` · `starredLoad` · `homilySettle`, unchanged).
   When the rebuild settles a pending build (`wasPending642`), it
   repaints the home in place (`paintPrayersView`, home view only,
   this build's own day only, never when `opnVaultLocked()`), so the
   first rebuild paints the real set at once instead of waiting on a
   settle swap.
3. **`buildDayFromPayload`:** the payload fold is computed into
   `payloadFold642` and assigned to `state.dayDescs` for its standing
   consumers exactly as before (`refreshRepeatIds` · `pushDaySnapshot`
   · `readTracks` all read their standing inputs). Then, before the
   paint: if a composed list stands for this presented day it stands
   back in `state.dayDescs` (paint + queue read it); otherwise
   `dayPending642` is set. Either way `rebuildGuard642` is set for
   the window until this build's resolution pass re-seeds.
4. **`opnSetHtml609`:** with `dayPending642` standing (and the edit
   form not standing — that branch still returns first), the set's
   place carries the plain loading state — a `data-p642loading`
   block ("Loading today's prayers…" + the standing skeleton) inside
   the `data-p609set` container — never the payload fold's empty set.
   The vault-locked path never reaches this function:
   `paintListenHome`'s locked branch still substitutes the gate
   before `homeBodyHtml` reads any list (v609 repair 2, untouched).
5. **`resolveExternals`:** `buildWithSettings` clears
   `rebuildGuard642` at entry (the standings re-seed synchronously
   inside it, before any rebuild can interleave); the settings-read
   failure catch also clears the guard and settles the pending state
   with a home repaint on the payload fold — no perpetual loading.

### The mechanism (Plan §2, fix shape 1 — snapshot choice)

The composed list is kept standing in `state.dayDescs` itself,
backed by the date-keyed snapshot `state.composed642` /
`state.composedDate642` that only `extRebuildDescs` writes. A
same-day build paints the snapshot; a new day (date key mismatch)
takes the loading path. One addition the Plan's grounding did not
name, found in Implement and guarded: **rebuilds that land before
the resolution pass re-seeds the standings compute partial lists**
— `resolveExternals` clears `state.extStanding` / `state.extSlots`
synchronously at dispatch, and the contents resolvers
(`resolveProfileEpisodes614`'s device-local homily settle is
synchronous) call `extRebuildDescs` in that window. Without the
guard, such a settle overwrote the record with a partial list
(measured in the harness: 13 of 16, with the courses and the
readings seat missing) and painted it. `rebuildGuard642` makes a
guarded rebuild return its list to its caller exactly as today
but record nothing, replace nothing, and settle nothing; the
first `buildWithSettings` rebuild is the first that records.

### Differences from the Plan's grounding

- The Plan names the settings read as the slow leg; in the public
  build the source-settings read is a personal path answered by
  the local layer (`opnIsPersonalPath`), never a fetch. The slow
  legs in the field shape are the resolution pass's network legs
  (courier · feeds · audio), which is what the harness gate hangs.
  The defect and the fix are unaffected: the payload fold still
  paints before any rebuild, whatever the rebuild's trigger.
- The pre-seed partial-rebuild race (guard, above) is not named
  in the Plan; it is a second overwrite of the same list in the
  same window, and the fix closes it in the same seam.
