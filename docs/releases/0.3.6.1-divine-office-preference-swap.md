## Scope

### Problem
- Morning Prayer and Evening Prayer in the Spotify refresh path currently prefer Sing the Hours first.
- When Sing the Hours is available, the Divine Office versions are only used as fallback matches.
- The desired listening order for these two prayer slots should be reversed so Divine Office is the primary source.

### Audience
- Primary user: listeners whose Morning Prayer and Evening Prayer playlist entries should resolve in the new preferred order.
- Secondary stakeholders: the Spotify refresh runtime, contract tests, and release documentation.

### Current Status Quo
- The refresh job resolves `MORNING` by trying Sing the Hours `Lauds` first and only then falling back to Divine Office morning.
- The refresh job resolves `EVENING` by trying Sing the Hours `Vespers` first and only then falling back to Divine Office evening.
- Contract files and tests still describe the old preference order.

### Goal
- Make Morning Prayer and Evening Prayer prefer Divine Office first.
- Keep Sing the Hours available as the fallback path when the Divine Office lookup fails.
- Preserve the existing contract keys, playlist membership, and Spotify lookup surface.

### Constraints
- Do not change unrelated playlist contracts.
- Do not alter the Morning Prayer or Evening Prayer Notion row names.
- Keep the change deterministic and test-covered.
- Keep the implementation small enough to review in one pass.

### Narrow Wedge
- Swap the resolver order only for the morning and evening prayer lookup helpers.
- Update the minimal tests that assert the old order.
- Adjust release notes and documentation wherever the preference order is explicitly described.

### Non-Goals
- No new prayer families.
- No changes to the Spotify playlist identity files.
- No changes to the page-audio runtime or custom TTS contracts.
- No broader refactor of the Spotify resolver architecture.

### Risks And Unknowns
- The main risk is changing the order in a way that affects existing playlist match coverage if one source is missing or malformed.
- We need to make sure the fallback still behaves exactly like the current Sing the Hours fallback path when Divine Office is unavailable.
- Documentation may mention the old source order in more than one place, so the scope should include a quick sweep for stale wording.

### Recommended Next Step
- Validate the runtime resolver helpers and tests for the morning/evening swap, then ship the updated preference order.

## Plan

### Summary
- Swap the Spotify refresh runtime so Morning Prayer and Evening Prayer prefer Divine Office first and only then fall back to Sing the Hours.
- Keep the contract surface thin and reuse the existing resolver names, so this remains a routing change rather than a schema migration.
- Add focused regression coverage that proves both morning and evening resolve in the new order.

### Current System Map
- Morning Prayer and Evening Prayer are resolved in `jobs/playlist/refresh_playlist.py` through `get_morning_prayer()` and `get_evening_prayer()`.
- The morning helper currently needs to resolve Divine Office before Sing the Hours so the existing `MORNING` routing reflects the new listening preference.
- The evening helper needs the same source order flip for Vespers versus Divine Office evening.
- Contract loading is intentionally thin: the JSON files mostly carry identity, so the order change is primarily a runtime-helper change rather than a contract-schema change.
- The Spotify refresh tests already isolate the resolver behavior with mocked Spotify responses, which makes this a low-risk change to verify locally.
- README guidance is already focused on page-audio and does not need to absorb this Spotify-only source-order swap.

### Architecture
- Flow:

```text
Spotify playlist contract
        |
        v
resolve_contract_uris()
        |
        v
resolve_spec_uri("MORNING" / "EVENING")
        |
        v
get_morning_prayer() / get_evening_prayer()
        |
        +--> Divine Office lookup first
        |
        +--> Sing the Hours fallback second
        |
        v
playlist queue write
```

- The routing change stays inside the playlist refresh runtime, so Spotify lookup behavior changes without introducing new config files or new resolver types.

### Reuse Opportunities
- Reuse the existing `DO_MORNING` and `DO_EVENING` token-based lookup helpers instead of introducing new resolver modes.
- Reuse the existing `sth_match_today()` and `do_date_aware()` helpers for the alternate source path.
- Reuse the current contract load/validation path so no schema migration is needed.
- Reuse the current unit tests and add small expectation flips rather than building a new test harness.

### External References
- No external API or library research is needed for this swap.
- The only behavior contract that matters is the existing Spotify lookup response shape already exercised by the tests.

### Constraints
- The change should preserve the existing Notion row names and playlist keys.
- The fallback should still be deterministic for a given date and source catalog.
- Any documentation change should distinguish Spotify refresh behavior from the separate page-audio/Notion audio output descriptions in the README.
- The plan should keep the user-visible contract filenames stable unless a regression test proves a schema change is required.

### Risks
- The biggest risk is accidentally changing the meaning of the fallback status labels while reversing the source order.
- Morning Prayer has an explicit `fallback_resolver` in the contract file, so the runtime order needs to stay aligned with that fallback path.
- Evening Prayer currently depends more on the runtime helper than the contract JSON, so it is easy to miss if only contract files are edited.

### Assumptions To Validate
- Divine Office has the correct target lookup terms for the morning and evening prayer shows already present in the runtime config.
- The intended swap is for both Morning Prayer and Evening Prayer, not only one of them.
- The contract JSON should stay thin, with the preference change represented in runtime logic rather than a new schema field.

### Unknowns
- Whether the user wants the public README wording changed beyond the release notes.
- Whether the fallback status labels should continue to mention Sing the Hours explicitly after the order is reversed.
- Whether there are any other docs outside README and the release artifact that still describe Sing the Hours as primary for these slots.

### Recommended Direction
- Proceed to `/implement-astack` with a runtime-helper swap and focused regression tests for both morning and evening prayer resolution.

### UX And States
- Empty state: if neither source returns an episode, the playlist item stays unresolved and the playlist build should fail as it does today.
- Success state: Morning Prayer and Evening Prayer both resolve to Divine Office when available, with Sing the Hours only used when Divine Office is missing.
- Error state: if a source lookup fails unexpectedly, the runtime should still fail closed rather than silently reshuffling to an unrelated episode.
- No UI surfaces are changing, so there is no loading state to design.

- Users would experience the issue as a missing Morning Prayer or Evening Prayer item in the affected playlist.
