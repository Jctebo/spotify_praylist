## Task

Investigate why Morning Prayer rendered as novenas only on March 17, 2026, map how Morning Prayer audio is composed today, and identify what must be fixed before making code changes.

## Executive Summary

- The live page-audio runtime no longer builds Morning Prayer from the older `MORNING_PRAYER_OUTPUT -> morning-prayer-wrapper -> MORNING_PRAYER_PAGE_AUDIO` path.
- `jobs/notion/generate_page_audio.py` now runs the two-list `Opus Dei` + related `Detailed Fragments` model in `main()` and does not load the legacy config path for active rows.
- The live `Morning Prayer` row is configured as `Assembly Mode = fragments` and `Text Sync Mode = page_content`, but it currently has exactly one related detailed fragment: `Daily Novena Audio`.
- The active plan therefore assembles only novena content: three TTS header fragments plus three novena source-audio fragments for today's novenas.
- Because the row also syncs `page_content`, the same plan writes novena toggles back into the page body. The live Morning Prayer page body now contains only the generated audio block, bookmark blocks, and autogenerated novena toggles.
- The older Morning Prayer fragment set still exists in Notion:
  - 12 `Audio Fragments` rows with `Collection = Morning Prayer`
  - `Morning Prayer Sequence`
  - `Morning Prayer Wrapper`
  - `MORNING_PRAYER_OUTPUT`
  - `MORNING_PRAYER_PAGE_AUDIO`
- Those older rows are orphaned from the active runtime because they are not linked to the Morning Prayer row through `Opus Dei Item`.
- Switching back to `morning_prayer_v1` would not rescue the current live state by itself. Against the current Morning Prayer page body, that builder now raises `No audio fragments were produced for Morning Prayer.`

## Current Architecture

### 1. Daily pipeline order

The daily workflow runs in this order:

1. `jobs/novena/generate_daily_novena_prayer.py`
2. `jobs/notion/generate_page_audio.py`

That means Morning Prayer page audio consumes the daily novena output generated earlier in the same run.

Source:
- `.github/workflows/daily_novena_prayer.yml:66-145`

### 2. Active page-audio entrypoint

The current `main()` flow in `jobs/notion/generate_page_audio.py`:

1. loads candidate `Opus Dei` pages
2. loads `Detailed Fragments` from the `Audio Fragments` database
3. builds `row_settings` from `Assembly Mode`, `Text Sync Mode`, and related fragment rows
4. builds a row plan with `build_opus_dei_two_list_plan(...)`
5. applies text/page-content sync if needed
6. renders the assembled audio

This is the active runtime path. It is not using the old merged `load_page_audio_config(...)` path for live rows anymore.

Sources:
- `jobs/notion/generate_page_audio.py:5378-5474`
- `tests/test_page_audio_job.py:2298-2349`

### 3. What counts as an active detailed fragment

`detailed_fragment_from_notion_page(...)` returns `None` if a fragment row has no `Opus Dei Item` relation.

That means:
- legacy rows can still exist in the `Audio Fragments` database
- but if they are not related to the owning page, the live two-list runtime will ignore them completely

Sources:
- `jobs/notion/generate_page_audio.py:1287-1304`
- `jobs/notion/generate_page_audio.py:1368-1397`
- `docs/notion-detailed-fragments-views.md`

### 4. How `daily_novena_audio` composes output

For a detailed fragment of kind `daily_novena_audio`, the runtime:

1. finds the `Daily Novenas from Liturgical Calendar` page
2. reads the toggle blocks and generated audio blocks on that page
3. creates a TTS header fragment for each novena title
4. reuses each generated novena audio block as `source_audio`
5. returns page-content toggles for sync back to the owning page

Sources:
- `jobs/notion/generate_page_audio.py:1975-2033`
- `jobs/notion/generate_page_audio.py:2554-2621`

### 5. How text sync affects Morning Prayer

`normalize_plan_for_row_text_sync(...)` preserves `page_content` output when a row's `Text Sync Mode` is `page_content`.

`sync_page_content_blocks(...)` then:
- preserves `audio` and `bookmark` blocks
- archives every other block
- appends the desired blocks

So if the plan only contains daily novena toggles, the page body gets reduced to daily novena toggles.

Sources:
- `jobs/notion/generate_page_audio.py:2494-2520`
- `jobs/notion/generate_page_audio.py:3630-3652`
- `jobs/notion/generate_page_audio.py:5438-5453`

### 6. How final audio is assembled

`build_assembled_audio(...)` resolves each fragment into audio in order, normalizes the files, and concatenates them with ffmpeg.

So the fragment list is the direct source of the final Morning Prayer MP3.

Source:
- `jobs/notion/generate_page_audio.py:4809-4837`

## Why The Bug Happened

This is primarily a live data-model wiring problem, not an ffmpeg or TTS problem.

### Failure chain

1. The current runtime only uses owner-linked detailed fragments for active page assembly.
2. The Morning Prayer row is owner-linked to exactly one fragment: `Daily Novena Audio`.
3. `build_opus_dei_two_list_plan(...)` therefore builds a plan from only that one child fragment.
4. `daily_novena_audio` expands into novena headers plus novena source audio.
5. Because the row uses `Text Sync Mode = page_content`, the same plan also syncs only novena toggles back into the page body.
6. The older Morning Prayer fragment rows still exist, but they are orphaned and therefore invisible to the active runtime.

### Important implication

The system is behaving consistently with the current live row configuration.

The bug is that the current live Morning Prayer row does not describe the full Morning Prayer assembly anymore.

## Why The Legacy Builder Is Not A Safe Quick Fix

The older `morning_prayer_v1` builder still exists, but against the current live Morning Prayer page body it now fails with:

- `No audio fragments were produced for Morning Prayer.`

That happens because the current page body no longer contains the static Morning Prayer text or placeholder blocks that builder expects. It now contains only:

- audio blocks
- bookmark blocks
- autogenerated novena toggles

So even if the code were temporarily switched back to `MORNING_PRAYER_PAGE_AUDIO`, the live source page would first need to be restored.

Sources:
- `jobs/notion/generate_page_audio.py:2970-3066`
- live read-only invocation of `build_morning_prayer_plan(...)` on March 17, 2026

## What Needs To Be Fixed

## 1. Restore the real Morning Prayer source of truth

Choose one canonical source of truth and make the runtime match it.

Given the current codebase, the cleanest path is:

- keep Morning Prayer in the two-list model
- complete the migration instead of reintroducing legacy fallback as the primary source

## 2. Repair the Morning Prayer detailed-fragment relations

The Morning Prayer row needs a full owner-linked fragment set, not only `Daily Novena Audio`.

At minimum, the live row should have related detailed fragments for:

- `Morning Offering`
- `Daily Consecration`
- `Baptismal Renewal`
- `Petitions Intro`
- the petition fragments
- `Intercessory Litany`
- `Monthly Intention`
- `Daily Novena Audio`

Those rows also need correct detailed-fragment metadata:

- `Opus Dei Item` relation pointing to the Morning Prayer row
- `Fragment Kind` set explicitly
  - `text` for the static prayers
  - `monthly_intention` for the monthly intention row
  - `daily_novena_audio` for the novena row
- `Assembly Role = append`
- stable `Order` values matching the intended prayer order

## 3. Stop relying on the current Morning Prayer page body as backup content

The current page body has already been reduced to novena-only content.

That means:

- it is not a reliable source for rebuilding the static Morning Prayer fragments
- any fix that depends on the current page body must restore the missing text first

## 4. Rebuild the page body after the fragment set is fixed

Once the correct detailed fragment set is related to Morning Prayer:

- rerun page audio generation
- let `page_content` sync repopulate the full Morning Prayer body
- confirm that the page body again contains the static sections plus today's novena toggles

## 5. Add code-level guards so this cannot silently collapse again

Recommended hardening:

- add a validation check for Morning Prayer rows that fails when the related fragment set contains only `daily_novena_audio` or otherwise lacks any static text fragments
- log a clear error instead of producing a valid-but-wrong novena-only Morning Prayer
- optionally add a QA/reporting command that compares owner-linked detailed fragments against the legacy Morning Prayer sequence and flags missing owner links

## 6. Add regression coverage

Current tests cover pieces of the system, but not the exact failure that happened here.

Missing coverage worth adding:

- a two-list Morning Prayer integration test where the row must include static text fragments plus monthly intention plus daily novena
- a guard test that rejects a Morning Prayer relation set containing only `daily_novena_audio`
- a migration test ensuring Morning Prayer migration does not leave the parent row linked only to novena while the old static fragment rows remain ownerless

## Things That Will Not Fix The Problem By Themselves

- Re-running `generate_page_audio.py` without repairing the Morning Prayer relation set
- Re-running the novena generator by itself
- Leaving the Morning Prayer row on `auto-audio` while hoping `Auto Audio Resolver 1/2` will rescue it
- Switching to `morning_prayer_v1` without restoring the page body content

## Open Questions

1. Should Morning Prayer stay fully in the two-list model, or should it intentionally return to a dedicated `morning_prayer_v1` builder?
2. If the two-list model is canonical, should the old `Morning Prayer` collection rows, wrapper, and sequence be retired after migration to reduce confusion?
3. Should `Text Sync Mode = page_content` remain enabled for Morning Prayer once the full fragment set is restored?
4. Should the README be updated so it no longer describes Morning Prayer as though the legacy output/config path is the active runtime?

## Working Conclusion

The Morning Prayer audio bug happened because the active Morning Prayer row in Notion is only linked to `Daily Novena Audio` in the new two-list model, while the older Morning Prayer fragment set still exists but is orphaned from the active runtime.

The current runtime is assembling exactly what the live row says to assemble.

The real fix is to reconnect or recreate the full Morning Prayer fragment set in the active owner-linked `Detailed Fragments` model, then add guards and tests so the page cannot silently degrade to novena-only output again.
