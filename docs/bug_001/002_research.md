## Objective of research
Determine which code paths produce, retain, and sync the daily novena audio artifacts, and identify the most likely boundary where stale audio can survive a rerun. The goal is to distinguish between generation, local cleanup, and remote sync behavior so planning can focus on the true failure mode.

## Architecture and flow

The daily novena workflow currently has two distinct concerns:

1. Notion content generation
2. Local audio artifact generation plus OneDrive sync

The Notion path already contains explicit cleanup for autogenerated page sections and audio markers. The `main` flow in `jobs/novena/generate_daily_novena_prayer.py` computes the daily prayer text, optionally writes to Notion, and, when audio is enabled, generates or refreshes cached audio before attaching it to the target page.

The audio-library path is separate. The workflow in `.github/workflows/daily_novena_prayer.yml`:

1. prefetches the existing OneDrive audio library into a local `onedrive_sync` tree
2. runs the novena generation job against that local library root
3. syncs the local library back to OneDrive with `rclone sync`

That means stale audio can persist in one of three places:

- the local novena audio library, if regenerated files are added but old files are not removed
- the remote OneDrive destination, if the local library does not fully reflect the current intended state before `rclone sync`
- the Notion page itself, if old autogenerated audio blocks are not removed before reattaching new ones

The current code strongly suggests the Notion side already uses marker-based removal. The more likely stale-output path is the local library plus sync boundary, especially if filenames or ordering changed and the output set was not truncated first.

## Patterns and conventions

- Marker-based cleanup is already the repo’s preferred pattern for autogenerated Notion content.
- The page-audio job uses explicit env-driven behavior and keeps the scheduled workflow as the orchestrator.
- Managed output cleanup, when present, is done locally before sync rather than by mutating the remote destination directly.
- Existing docs describe `Playlist Audio` as a OneDrive-managed tree with optional local truncation before regeneration.
- Tests in `tests/test_page_audio_job.py` treat ordered export collisions and truncation as first-class behaviors.

## Constraints and dependencies

- The daily novena job depends on Notion, OpenAI, Romcal, and local filesystem access.
- The OneDrive sync path depends on `rclone` and the local `onedrive_sync/Praylist Audio/...` mirror.
- The workflow already prefetches remote audio before generation, so cleanup must be careful not to delete unrelated remote content.
- The bug scope is narrow: do not change the novena audio content itself unless needed to prove the stale-output fix.
- Current ordering changes may have altered filenames, which makes cleanup behavior more important if the output set is not fully rewritten.

## Potential approaches

1. Treat the novena audio library as fully managed and truncate the targeted output subtree before regeneration.
   - Summary: rebuild the managed local folder from scratch each run, then sync it to OneDrive.
   - Pros: simplest mental model; stale files cannot survive in the managed subtree.
   - Cons: requires clear definition of the managed boundary.
   - Compatibility: matches the existing `rclone sync` model and the page-audio truncation precedent.

2. Add targeted cleanup based on the current render hash or generated filename set.
   - Summary: delete only artifacts proven to be obsolete for the current run.
   - Pros: more conservative than full truncation.
   - Cons: easier to miss files when ordering or naming changes.
   - Compatibility: feasible, but more complex than the current local managed-output pattern.

3. Keep generation as-is and rely on remote sync behavior only.
   - Summary: assume `rclone sync` will resolve stale files.
   - Pros: minimal code change.
   - Cons: does not help if old files remain locally and the local tree is not rebuilt correctly.
   - Compatibility: weakest fit with the symptom and least likely to explain mixed old/new outputs.

## Key findings

- The Notion cleanup helpers already remove old autogenerated audio and sections by marker, so the bug is probably not primarily a Notion page-body retention problem.
- The scheduled workflow explicitly syncs a local OneDrive mirror back to remote storage, so local artifact state is the most likely source of stale files.
- The page-audio job already contains an explicit managed-truncation pattern, which is a strong precedent for how to solve this bug safely.
- The bug description is consistent with a filename or ordering change leaving prior artifacts outside the newly generated set.

## Risks

- Risk: cleanup might be defined too broadly and remove audio that should remain.
  - Why it matters: the novena library may include cached files that are not meant to be rebuilt on every run.
  - Possible mitigation: scope cleanup to the managed daily novena output subtree only.

- Risk: changing order or naming may produce the appearance of a cleanup bug when the actual issue is a filename contract mismatch.
  - Why it matters: stale files can coexist with new files if the old names no longer collide.
  - Possible mitigation: verify the current stem contract before deciding on deletion logic.

- Risk: focusing only on the remote sync step may miss the local build-state bug.
  - Why it matters: `rclone sync` only mirrors what the local tree contains.
  - Possible mitigation: inspect the local output tree before and after regeneration.

## Unknowns / assumptions to validate

- Which exact novena output subtree should be considered managed and safe to truncate?
- Whether stale files remain because the local library is not cleaned, or because the sync target is not being fully mirrored as expected.
- Whether the order change affected filenames, making old artifacts appear as “extra” files instead of true duplicates.

## Recommendation for planning

Plan around a managed-output cleanup boundary for the daily novena audio library, then verify whether the current filename/order contract still causes old files to survive the rerun. The implementation should likely follow the existing local-truncation-before-sync pattern used by playlist-audio exports, while preserving the current Notion marker-based cleanup behavior.
